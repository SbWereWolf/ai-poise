# Чек-лист плана проверок

Обновлено: **2026-09-12**.

Этот чек-лист применяется при создании или изменении `verification_plan`, перед регистрацией методов проверки и повторно перед выходом из тестового этапа. Заполненная матрица принадлежит содержимому формальной Task: она не ведётся отдельным неуправляемым файлом и не заменяет зарегистрированные методы.

Для каждого check зафиксировать одну строку:

| Поле | Что указать |
|---|---|
| Check | Устойчивый идентификатор метода |
| Этапы и состояние | На каких этапах ожидается RED или GREEN |
| Самый ранний GREEN | Первый этап, после которого все необходимые изменения уже разрешены процессом |
| Ответственность | Поведение, документация или итоговая регрессия |
| Поверхность изменений | Явные группы путей, необходимые для получения GREEN |
| Проверка RED | Точные ожидаемые падающие тесты и отсутствие дополнительных падений |

Обязательные решения:

1. Check нельзя требовать GREEN раньше указанного этапа.
2. Дополнительное падение не считается допустимой частью ожидаемого RED.
3. Поведенческие, документационные и итоговые проверки разделяются, если их изменения принадлежат разным этапам.
4. Тесты вне изменяемой сейчас ответственности запускаются отдельным GREEN guard, чтобы ожидаемый RED не скрывал регрессию.
5. Матрица сверяется с `allowed_paths` соответствующих этапов. Несовпадение исправляется разделением check или переносом его обязательного GREEN, а не расширением этапа без продуктовой причины.

Не требуется рекурсивно вычислять все файлы, которые тест теоретически способен прочитать. Достаточны явно объявленная ответственность метода, предусмотренная поверхность изменений и фактический список падений. Автоматическая валидация этого контракта является отдельной продуктовой возможностью; до её реализации агент применяет матрицу вручную.
