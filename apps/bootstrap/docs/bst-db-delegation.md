# Подготовка БД публичной командой владельца

Эта страница описывает поставленный в T028 адаптер Bootstrap. База данных остаётся
ресурсом своего приложения: только его публичная команда проверяет готовность,
создаёт недостающее состояние или отказывает в изменении. Bootstrap не открывает
чужую БД, не содержит её SQL/DDL, не импортирует внутренние модули владельца и не
добавляет второй исполнитель команд.

[Контракт Bootstrap](contract-bst.md) задаёт границу приложения.
[Обслуживание среды T027](bst-maintenance.md) описывает общий CLI, конфигурацию,
надзор, ограничения и отчёт. Его legacy repair-протокол сохраняется. Новая схема
ниже дополняет этот исторический срез: обычная публичная CLI-команда владельца
больше не обязана реализовывать JSON-протокол `RepairRouter`.

## Подключение и формат bindings

Шесть полей профиля `stride-bootstrap-project/v1` не меняются. Поле `repairs`
ссылается на файл bindings относительно `projects_root`; `null` означает отсутствие
таблицы. В примере операционные файлы расположены так:

```text
projects/
  alpha.json
  alpha-assets/
    catalogue.json
    bindings.json
```

```json
{
  "schema": "stride-bootstrap-project/v1",
  "id": "alpha",
  "catalog": "alpha-assets/catalogue.json",
  "repairs": "alpha-assets/bindings.json",
  "values": {},
  "parameter_values_files": []
}
```

Новый файл содержит **ровно** `schema` и `repairs`. Версия —
`stride-bootstrap-owner-commands/v1`; `repairs` — объект, не массив.
Каждый ключ — непустой UTF-8 ID требования без NUL. Значение содержит ровно
`check`, `apply` и `recommendation`:

```json
{
  "schema": "stride-bootstrap-owner-commands/v1",
  "repairs": {
    "db.prepare": {
      "check": {
        "argv": ["/absolute/path/to/public-owner-cli", "database", "check", "--path", "${database_path}"],
        "timeout": 10
      },
      "apply": {
        "argv": ["/absolute/path/to/public-owner-cli", "database", "prepare", "--path", "${database_path}"],
        "timeout": 30
      },
      "recommendation": "Проверьте диагностику владельца; не удаляйте повреждённую БД."
    }
  }
}
```

Это шаблон контракта, а не установленный DB-инструмент. Его executable, аргументы,
дедлайны и политика готовности должны соответствовать конкретному публичному API
владельца. В репозитории отдельно поставлены
[bindings.example.json](../examples/owner-commands/bindings.example.json) и
[catalogue.example.json](../examples/owner-commands/catalogue.example.json).
Примеры не копируются в операционный `projects/` автоматически, не заменяют
конфиги установки и не создают БД.

| Поле binding | Контракт |
| --- | --- |
| `check` | Обычное действие существующего ядра: `argv`, `timeout`, необязательные `cwd`, `env`, `max_output_bytes` |
| `apply` | Такое же действие с собственными аргументами, каталогом, окружением и пределами |
| `recommendation` | Непустой UTF-8 текст без NUL; после подстановки также непустой текст, не команда |

`argv` — непустой массив строк без NUL, первый элемент непустой. `timeout` —
положительное конечное число не более 3600 секунд; bool не считается числом.
`env` — объект строковых значений; имена переменных непустые, без `=` и NUL.
`cwd`, если задан, — строка без NUL. `max_output_bytes` — целое от 1 до 16777216.
Неизвестные поля, пропущенный режим и рекурсивное действие `{"repair": ...}` внутри
binding отвергаются. Поля вроде `sql`, `schema` или `import_module` не являются
способом настройки действия.

Каталог требований сохраняет `environment-maintenance/requirements/v1`.
У требования с `id: "db.prepare"` каждое из полей `check`, `apply`, `recommendation`
может содержать `{"repair":"db.prepare"}`. ID маршрута обязан точно совпадать с ID
этого требования и существующим ключом bindings. Адаптер заменяет только такую
ссылку соответствующим полем binding. Обычные команды и текстовые рекомендации
самого каталога остаются без замены; смешанный каталог допустим.

## Валидация до выполнения

Существующий ограниченный reader фиксирует UTF-8 JSON без повторяющихся ключей,
нечисловых констант и неконечных чисел; ограничения
размера, глубины, обычного файла и запрет symlink для входных assets сохраняются.
Пути assets не допускают абсолютных ссылок, `..`, пустых компонентов и обхода
корня. Эти правила относятся к читаемым конфигурациям, а не к доступу доверенной
публичной команды к её собственному ресурсу.

Адаптер проверяет **все bindings**, включая неиспользуемые: структуру обоих
действий, текст рекомендации и результат подстановки параметров. Корректные
неиспользуемые bindings разрешены, но не вызываются. Затем проверяются все
маршруты каталога, в том числе требования категории, которую текущий `infra`
или `deps` не исполняет. Отсутствующая binding, чужой ID, рекурсия или неизвестный
placeholder не допускают частичного старта этой цели.

Проекция строится на копиях объектов и снова проверяется публичным
`environment_maintenance.catalogue.load_catalogue`. Исполнение принадлежит только
`environment_maintenance.engine.execute` из закреплённого
`environment-maintenance==0.1.1`; адаптер не дублирует check/apply/recheck,
редактирование секретов или процессный надзор.

## Параметры, cwd и публичный вызов

Значения разрешаются существующим resolver: catalogue default, затем объединённые
`values` и `parameter_values_files` профиля, объявленный environment и последнее
явное `--set NAME=VALUE`. Все имена и типы параметров должны быть объявлены в каталоге.
В поставленном примере `database_path` получает значение из `OWNER_DATABASE_PATH`
и помечен `secret: true`. Альтернативой остаётся явный `--set`.

Ниже пути — явные параметры оператора. Команды предполагают уже настроенный профиль,
пригодный публичный owner executable и выбранный Python с установленной зависимостью.
Bootstrap не устанавливает их скрыто:

```bash
PYTHON=/absolute/path/to/installed/python
CHECKOUT=/absolute/path/to/checkout
BOOTSTRAP_CONFIG=/absolute/path/to/bootstrap.json

export OWNER_DATABASE_PATH=/absolute/path/to/owner/database.sqlite
"$PYTHON" -B "$CHECKOUT/apps/bootstrap/bin/bootstrap" --config "$BOOTSTRAP_CONFIG" check --target alpha
"$PYTHON" -B "$CHECKOUT/apps/bootstrap/bin/bootstrap" --config "$BOOTSTRAP_CONFIG" infra --target alpha --dry-run
"$PYTHON" -B "$CHECKOUT/apps/bootstrap/bin/bootstrap" --config "$BOOTSTRAP_CONFIG" infra --target alpha
```

`--config` расположен перед командой. Выбор цели одинаков для `infra`, `deps`,
`check`: явный `--target` важнее настроенной переменной `target_env`, затем
используется `default_target`. Отдельного публичного `repair` verb или флага
`--repairs` не добавлено.

Каждый элемент `argv` передаётся отдельным аргументом, без shell-интерпретации.
Обычная команда получает пустой stdin, не `repair-request/v1`. Её stdout/stderr
могут быть обычным текстом: специальный JSON-ответ владельцу для новой схемы не нужен.
Наследуется только явно объявленное `inherit_env` каталога; `env` конкретного
действия задаёт дополнительные значения и переопределяет совпадающие имена.

Для owner binding база `cwd` — **исходный каталог файла bindings**. При отсутствии
`cwd` используется этот каталог; относительный путь разрешается от него,
абсолютный остаётся абсолютным. У обычной команды, заданной непосредственно
в каталоге требований, база по-прежнему каталог исходного requirements-файла.
Временный каталог snapshot не становится рабочим каталогом владельца.

Подстановка `${name}` однопроходная. Адаптер проверяет раскрытые действия, но
сохраняет исходные `argv`, `env` и `recommendation` для исполнения ядром.
Раскрытый `cwd` привязывается через непрозрачный приватный alias: буквальная строка
`${...}` внутри уже подставленного значения не раскрывается повторно.
Alias существует только на время вызова ядра. `planned_apply` — диагностика,
не переносимая команда повторного запуска с действующим после завершения alias.

## Готовность, отказ владельца и отчёт

`check` проверяет обе категории и не вызывает `apply`. `infra` и `deps` обслуживают
соответствующую категорию. При `--dry-run` выполняется initial check и показывается
`planned_apply`, но `apply` не запускается. Текст `recommendation` не исполняется
как отдельная команда.

Успешный initial check означает готовность без ремонта. При разрешённом ремонте
после неуспешного check ядро вызывает `apply`, затем повторяет check; повторный check
выполняется и после отказа `apply`. `repaired` возможен только при успехе и `apply`,
и final check. Ошибка запуска, timeout, ненулевой код владельца или провал final check
не подменяются успехом. Новый явный запуск снова начинается с проверки готовности.

Сохраняется общий `stride-bootstrap/v1` envelope и вложенный
`environment-maintenance/result/v1` в `core`. В частности, `ready`/`repaired` дают
код 0, `action_required` — 3, `failed` — 4. При `all` результат агрегируется,
поэтому нужно читать и отдельные строки `targets`: ошибка одной цели не отменяет
исполнение остальных и не создаёт общей транзакции.

Недопустимый каталог или binding даёт `invalid_target_catalogue`, код 4,
`effects: "none"`, без вызова владельца. Ошибка разрешения объявленных параметров
даёт `invalid_target_parameters`. Отсутствующее или неподходящее ядро сохраняет
`maintenance_unavailable`/`action_required`, код 3. Неуспешный ремонт отражается
через `maintenance_failed` и фактические наблюдения initial/apply/final в `core`.
Коды, stdout/stderr и признаки timeout сохраняются в рамках существующих ограничений
захвата и редактирования секретов; полнота не обещается сверх этих ограничений.

`effects` — оценка оболочки, а не журнал транзакций БД. После запущенного неуспешного
`apply` она может быть `applied`, при неопределённом исходе — `unknown`.
Bootstrap не делает автоматического повторного `apply` после такого исхода,
не удаляет повреждённую БД, не сбрасывает схему и не заменяет отказ владельца прямым
SQL. Семантику «готово», безопасную подготовку, отказ при повреждении/занятости и
идемпотентность повторного обращения задаёт владелец публичной команды.

## Snapshot, секреты и границы доверия

До первого действия замораживаются выбранные конфигурационные объекты всех целей,
включая bindings. Перезапись файла после freeze не влияет на текущий запуск;
она учитывается следующим вызовом. Это не атомарная публикация нескольких файлов
и не заморозка executable, рабочего каталога или внешней БД.

Объявленный `secret` редактируется существующим ядром в видимом отчёте.
`config_digest` подавляется, если хотя бы один параметр не имеет явного
`secret: false`. Этот digest относится к входному snapshot, не к фактически
подставленным CLI/env-значениям. Необъявленные секреты, логи владельца, видимость
аргументов в ОС и политика доступа к внешним ресурсам остаются ответственностью
оператора и владельца. Секретные операционные файлы не предназначены для handoff.

Настроенные executable являются доверенными. Запрет SQL и внутренних импортов
в коде Bootstrap не делает произвольную команду sandbox-безопасной. Даже `check`
должен быть квалифицирован владельцем как проверка без нежелательных изменений:
оболочка запрещает свой вызов `apply`, но не анализирует поведение стороннего кода.
Лимиты времени/вывода и Linux-надзор из [T027](bst-maintenance.md) сохраняются.

## Совместимость legacy и целевые проверки

`environment-maintenance/repairs/v1` остаётся прежней таблицей
`requirement_id → command`: одна команда получает режим в JSON-запросе
`environment-maintenance/repair-request/v1` и возвращает согласованный
`environment-maintenance/repair-result/v1`. В новой схеме три явных поля binding
заменяют эту необходимость. Автоматического угадывания или преобразования legacy
нет: форма определяется `schema`, а смешивание структур отклоняется.

Следующие команды запускают только целевые сценарии. `PYTHON` и `CHECKOUT` имеют
то же значение, что выше; исполняемые тесты используют временные тестовые БД и
прозрачную fixture-команду, которая одна владеет их схемой:

```bash
cd "$CHECKOUT"
"$PYTHON" -B apps/bootstrap/tests/test_owner_commands.py --suite behavior
"$PYTHON" -B apps/bootstrap/tests/test_owner_commands.py --suite documentation
"$PYTHON" -B apps/bootstrap/tests/test_maintenance.py --suite behavior
"$PYTHON" -B apps/bootstrap/tests/test_profiles.py --suite behavior
"$PYTHON" -B apps/bootstrap/tests/test_shell.py --suite behavior
"$PYTHON" -B tools/check_documentation.py --checkout "$CHECKOUT" --changed apps/bootstrap/docs/bst-db-delegation.md
```

Новый набор содержит 20 поведенческих групп и 4 документационные; совместимость
сохраняют прежние 32/20/8 групп. Проверяются реальные argv/cwd/env и пустой stdin,
готовая/отсутствующая/повреждённая БД, отказ/timeout/recheck, повторный вызов,
некорректные и неиспользуемые bindings, `all`, snapshot, секреты и однократная
подстановка. Статическая проверка запрета SQL/внутренних импортов ограничена
исходниками адаптера, не произвольными программами владельцев.
Ссылки и входящие ссылки на изменённую страницу проверяет существующий
`tools/check_documentation.py`, отдельный сканер не вводится.
