# Доказательства и наблюдения — контракт DDD-04

Обновлено: **2026-09-12**. Срез **POISE-DDD-04 / task 0037**.

## Владение и цель
`CheckRegistry` (verification) хранит точные команды и расписание. `EvidencePlan` определяет роль результатов и обязательные аргументы/осмотры. `EvidenceBook` хранит неизменные наблюдения, ревизии аргументов и решения. Task композиционно владеет планом/книгой и фазой; runner не правит доменные поля. Правило одинаково для всех goal types.

## Явный evidence_plan задачи
Для каждого stage нужен объект `subject_methods`, `arguments`, `review_arguments`; даже отсутствие обязанностей задаётся явно тремя пустыми коллекциями. Пример двух этапов:

```json
{
  "measure": {
    "subject_methods": {
      "M": {"exit_codes": [0, 1], "stdout_contains": ["VALUE="], "stderr_contains": []}
    },
    "arguments": [
      {"id": "A", "kind": "logical", "phase": "continue", "observation_methods": ["M"]}
    ],
    "review_arguments": []
  },
  "audit": {"subject_methods": {}, "arguments": [], "review_arguments": ["A"]}
}
```

Числа/строки выше — пример конкретной задачи, не defaults runtime. M обязан существовать в methods и расписании measure. Каждая команда содержит полный argv, cwd относительно task worktree, явное окружение, expected_exit_code и признаки ожидаемого stdout/stderr. Verification method не ограничивает время исполнения: после запуска AI poise ждёт конечный результат. AI poise ничего не узнаёт о способе запуска проекта самостоятельно.

Каждый новый verification method дополнительно содержит обязательный `source_under_test`.
Для исходников репозитория это `{"kind":"repository","bindings":[...]}` с одним или
несколькими явными binding: `cwd` меняет рабочий каталог на путь внутри текущего task
worktree, `environment` связывает названную переменную с таким путём. Существующий ключ
окружения нельзя молча заменить binding. Команда без репозиторного исходника использует
`{"kind":"external","reason":"..."}` с содержательной причиной. Пути абсолютные, с `..`,
отсутствующие или выходящие из worktree отклоняются до subprocess.

`CheckRegistry` отклоняет методы с одинаковой полной семантикой, даже если их ID различны,
а на одном этапе — один вызов с разными ожиданиями или разной декларацией provenance.
Разные source bindings образуют разные вызовы. Для nonzero expectation нужен явный
stdout/stderr marker: RED считается связанным только при совпадении failure predicate и
успешном разрешении `source_under_test`.

### Два разных результата команды
1. **Наблюдение распознано**: процесс завершён без timeout/signal, код и признаки результата соответствуют явному observation rule. Поле receipt `interpretable`.
2. **Критерий выполнен**: actual exit и признаки совпали с expected contract метода. Поле receipt `passed`.

У `observe` отрицательный критерий остаётся наблюдением, outcome=complete. У `check` он даёт not_satisfied, а не ошибку AI poise. Неопознанный вывод, сбой запуска, timeout/signal не дают ложного опровержения продукта. Проектные automatic checks всегда guard: включение их ID в subjects не снимает блокировку. Прочие task checks тоже guards.

У check outcomes: satisfied / not_satisfied / inconclusive. Наличие отрицательного аргумента/subject даёт not_satisfied; при отсутствии отрицания inconclusive аргумент даёт inconclusive. Это протокольные результаты семейства; конкретные переходы выбираются явным route config. Статус этапа verified означает корректность проведения работы, не положительность предметного результата.

## Один пакет результата
В существующий stage result добавлено обязательное поле:

```json
{"evidence_work": {"phase": "prepare", "arguments": [], "decisions": []}}
```

Остальные поля sections/artifact_paths/commit_message/content_additions/trace/method_additions/stage_work остаются. Agent не передаёт exit_code, tree hash или receipts; они приходят от адаптера.

Аргумент: `id`, `kind` (logical/inspection), непустые `facts`, явный список `assumptions` (может быть пуст), `inference`, `conclusion`, `verdict` (proved/disproved/inconclusive), `observation_ids`.

Решение: `argument_id`, точная `revision`, `decision` (accepted/rejected), `reason`. Revision копируется из предъявленного предмета осмотра как ссылка. Решение допускается только в отдельно объявленном inspect. Аргумент сам себе verdict acceptance не назначает. Собственный `verdict` аргумента — его вывод о критерии, не признание аргумента достаточным.

## Фазы
PREPARE принимает готовый аргумент по известным фактам. Обязательное отсутствие такого аргумента блокирует дорогие команды. Он может ссылаться на предусмотренные наблюдения прежнего этапа того же дерева, но не на будущие текущие.

Для аргумента CONTINUE сначала выполняются методы текущего этапа. AI poise сохраняет batch и возвращает `awaiting_continuation` с receipts/контекстом. В result file меняется только evidence_work.phase. Агент добавляет аргумент и снова вызывает verify. Независимого пользовательского этапа и нового claim нет.

Повтор ожидания с незаполненным аргументом не запускает команду заново. CONTINUE принимает только наблюдения соответствующей задачи, этапа, итерации и текущего batch. Ссылки на другое/устаревшее наблюдение отклоняются. Изменение дерева или явно переданной среды даёт observations_stale, а не тихую подстановку старого результата. Агент возвращает phase=prepare, удаляет неподтверждённый continue-аргумент и получает новое наблюдение. Это инженерное исправление, не автоматическая выдумка evidence.

## Актуальность и повтор
Ключ исполнения включает stage, iteration, наблюдаемое Git tree, точные выбранные методы, роли guard/subject, observation rules, разрешённый cwd и фактически переданный env. Env участвует в hash, не записывается целиком в receipt. Исторический batch не заменяется. Повтор без изменения входов использует здоровые receipts; неуспешные guard/transport можно повторить в рамках явного verify_attempts.

До продолжения проверяется существование и digest raw output. При неизвестном исходе прерванного внешнего процесса сохраняется прежнее безопасное блокирование DDD-03 — recovery runner не имитируется.

После push failure повтор доставки также сверяет execution_key. Изменение env требует нового запуска; неизменное состояние не запускает тесты повторно. Receipt хранит разрешённую `source_provenance`, `provenance_digest` и отдельный `expectation_digest`; они входят в identity исполнения и позволяют отличить проверяемый источник от ожидаемого результата.

Не заявляется полная идентичность внешней среды: время, состояние внешнего сервиса и ignored файлы автоматически не fingerprint-ятся. Для таких зависимостей нужны явные команды/наблюдения проекта; адаптеры и более точные правила актуальности расширяются по реальному использованию.

## Осмотр и обратная связь
Процесс может задать: measure → audit(clear→terminal, changes_requested→measure). Отказ по аргументу выбирает changes_requested без создания фиктивного исправления или новой задачи. Новый подход создаёт новую revision; старый аргумент и отказ сохраняются. Inspect может одновременно работать с обычными findings/resolutions DDD-03.

EvidenceBook обеспечивает наличие фактов/структуры/ссылок, но не истинность текста. Она проверяется агентом. Представленные demo decisions — fixtures, не независимый peer review.

## Инструменты
`verify` принимает весь пакет; `show --evidence` показывает текущий план, assessment, сохранённые аргументы/решения и компактные observations. Полный stdout/stderr — файлы у задачи. `cancel` не требует заполнить недостающее evidence. Артефакты по-прежнему передаются только путями, без новых деклараций.
Для RED поле `verification_plan.red_failure` фиксирует код выхода и полные
`stdout_equals`/`stderr_equals`. Совпадение буквальное: дополнительный сбой или
любой иной дополнительный вывод не подтверждает ожидаемый RED, даже если старые
маркеры присутствуют.
