# Архитектура Harness: домены, общие библиотеки и данные

Создано: **2026-09-06T16:04:53+05:00**.

Статус: **проект целевой архитектуры; существующие исходники, конфиги и тесты не изменены**.

## 1. Решение

Применяем DDD ко всему Harness как архитектурный инвариант. **Одна поставка модульного монолита, отдельные библиотеки доменов, один application API инструментов, общий runner и семь стратегий этапов.** Task и Sprint — разные владельцы правил и данных; общая механика содержимого и инфраструктуры не копируется между ними.

Не превращаем 13 goal types в 13 классов процесса, 13 сервисов или 13 разных баз. Они остаются независимыми конфигурациями над общей библиотекой. Выбранный ранее вариант A запрещает наследование бизнес-конфигов, но не повторное использование реализации.

DDD применяется через предметные методы и границы согласованности, а не только названия каталогов. `Task.accept_iteration()` и `Sprint.add_dependency()` проверяют правила. В CLI не должно появляться их альтернативных реализаций через `UPDATE status` или generic JSON update. Сведения о применяемых паттернах и их ограничениях — в [источниках](sources.md).

## 2. Схема зависимостей

```text
Пользователь / агент
        │
CLI, hooks, прочие поддерживаемые входы
        │
HarnessApplication — одна библиотека всех инструментов
        │
CommandPipeline / QueryPipeline
        │
Use cases + общий RouteRunner + handlers
        │
┌──────────────────────────────────────────────────────────┐
│ tasks       sprints      processes      verification     │
│       content — общая механика слоёв и ссылок             │
├──────────────────────────────────────────────────────────┤
│ sessions    workspaces   executions     artifacts        │
├──────────────────────────────────────────────────────────┤
│ metrics     operations   configuration/foundation        │
└──────────────────────────────────────────────────────────┘
        │ порты
SQLite/UoW | filesystem | Git | exact commands/parsers
runtime/IDE adapters | transfer | operational journal
```

Стрелки ниже домена означают вызовы через порты, а не импорт инфраструктуры в модели. Конкретные adapters связываются только в `composition.py`. Общий runner не получает произвольный SQL connection.

## 3. Где находятся доменные границы

| Область | Ответственность |
|---|---|
| **Task** | Один тип цели, контракт, этапы/итерации, результаты, findings, proposals, evidence и решения о работе |
| **Sprint** | Цель набора задач, membership, DAG, готовность следующей работы, закрытие/судьба ветвей |
| **Content** | Переиспользуемый алгоритм текстовых слоёв, шаблонности, refs; изменение разрешает владелец Task/Sprint |
| **Verification** | Методы/обязательства, пригодность evidence, разделение реального наблюдения и решения о соответствии |
| **Sessions** | Текущая работа агента и work cycle, изолированный runtime |
| **Workspaces/Executions** | Фактическое состояние codebase, точный запуск и receipt; не оценка бизнес-успеха task |
| **Artifacts** | Path-only registration, owner roots, стабильный ID и сохранность referenced файлов |
| **Metrics** | Измеренные затраты, собственный конечный результат, credit/reversal, разрезы по цели и в целом |

Task и Sprint имеют общий язык и находятся в одном контексте управления работой, но остаются отдельными агрегатами/библиотеками. Sprint не загружает весь Task с историей как дочерний mutable объект. Он оперирует IDs и компактными фактами состояния.

[Подробные модели, методы и 14 архитектурных инвариантов](docs/01-domain-model.md).

## 4. Все инструменты — одна библиотека, но не один класс на всё

На верхнем уровне `HarnessApplication` предоставляет bootstrap, verify/continue, show, handoff/discard, пользовательские решения, публикацию планов и manifest wizard. CLI и hooks являются тонкими adapters.

Внутри неё используются TaskCommands, SprintCommands, ArtifactRegistry, TaskQueries/SprintQueries, ExecutionService и другие типизированные API. Их общий код — pipeline, UoW, content revisions, exact command execution, path checks, output rendering и operation receipts. Бизнес-правила остаются у конкретного домена.

Пример нормальной записи:

```text
один result file агента
  sections + findings/proposals + manual evidence
  methods/decisions + artifact_paths + commit_message
        ↓
VerifyStage
        ↓
TaskCommands.submit_stage_result
        ↓
Task.apply_submission + общие content/artifact/verification функции
        ↓
один кандидатный ChangeSet в короткой транзакции
        ↓
проверки и finalization
```

Не надо выполнять отдельный LLM tool call для каждой секции/находки/пути. Адресные методы сохраняются для самостоятельных осмысленных действий, но используют те же правила и не обходят этап.

**Композиция важнее общего базового класса.** Большой `BaseHandler`, который умеет изменять любое состояние, запускать Git и писать все таблицы, лишь перенёс бы прежний монолит в другое имя.

[Контракты библиотек, команд и запросов](docs/02-libraries-and-api.md).

## 5. Семь handler-семейств сохраняются

| Handler | Узлов | Доменные и технические библиотеки |
|---|---:|---|
| `produce` | 43 | Task/content/verification: принять результат агента |
| `observe` | 8 | Execution/artifacts/verification: получить факты |
| `check` | 9 | Verification/execution: проверить требования |
| `inspect` | 24 | Task/content/verification: read-only осмотр и отдельные решения |
| `revise` | 9 | Produce/apply_plan + Task findings/resolution rules |
| `apply_plan` | 2 | Execution/workspaces: выполнить согласованный план внешних изменений |
| `publish` | 3 | Координатор публикации: Task/Sprint или Git target через соответствующий API |

Все **98 узлов**, **13 goal types** и **34 именованных обратных перехода** из предыдущего проектирования сохранены. DDD не размножает и не сокращает самовольно маршруты. Обработчики не владеют lifecycle Task/Sprint: они возвращают результат стратегии, Task и RoutePolicy разрешают переход, runner координирует его только в рамках пользовательской инструкции.

## 6. Хранение и чтение

Одна SQLite хранит обычные тексты секций, корни задач/спринтов, версии содержательных records, связи, execution receipts и метрики. Файлы содержат raw output, images/archives и другие artifacts. Целевой Git хранит deliverables приложения.

В [каталоге хранения](docs/03-data-storage.md) заданы владельцы и отношения логических таблиц. Это проект покрытия данных, не требование сначала реализовать полную схему, прежде чем продолжить работающий happy path. Нет новой БД для каждой библиотеки.

**Запись:** доменный метод → ChangeSet → Repository → общий короткий UnitOfWork. Ни generic `save(dict)`, ни внешний `UPDATE` не обходят domain API.

**Чтение:** специализированные indexed Query projections. Сводка по спринту не восстанавливает в памяти 2000 задач со всей историей. Старые слои, raw output и полный trace graph читаются только адресно.

Task/Sprint share SectionBook и соответствующий mapper. Для обычных секций остаётся SQLite TEXT. Структурированные бизнес-записи отображаются в typed records: индексируемые state/owner/kind и реальные связи находятся вне произвольных текстовых payloads.

## 7. Два уровня согласованности

**В БД** используются реальные foreign keys, versions и короткие транзакции с единым внешним файловым lock. Простая локальная публикация спринта и новых задач может быть одной UoW: это специально разрешённая многокорневая операция контекста управления работой.

**За пределами БД** используются intent → effect → receipt. Git commit/push, запуск команд и публикация файла не являются частью SQL-транзакции. Неизвестный исход не повторяется вслепую. Корректная остановка приемлема там, где автоматическое восстановление ещё не реализовано.

Именно поэтому TaskRepository не должен сам запускать тесты, а verify не держит state lock, пока они идут.

[Порядок коротких транзакций и сквозные примеры](docs/04-runner-and-transactions.md).

## 8. Артефакты без возврата к декларациям

Вход — только пути. Корни runtime/task/sprint передаёт bootstrap. Library определяет owner, ID, относительный путь и технические факты. Повтор не размножает artifact identity. Count rules по owner/path pattern остаются простыми; количество файлов не выдаётся за число тест-кейсов.

Ссылки внутри БД опираются на owner и относительный путь/ArtifactId, а не на абсолютный prefix cloud или WSL. Для сохранённого evidence фиксируется конкретное содержимое файла внутри того же owner root. Это не новая обязанность агента и не семантическая классификация артефактов.

Рабочий `src/foo.py` в codebase — WorkspaceResultRef, не внутренний artifact. Его изменения и полезный delta получает Git adapter; агент не регистрирует список changed files.

## 9. Как это отразится в существующем коде

Прототип сохраняется. Его `_tree/_changed` становятся основой Git adapter, `_select_checks` — verification service, `Store.transaction` — UoW, path helpers — ArtifactRegistry. `Harness.verify` разделяется между use case, Task API и общим finalizer, а не копируется в каждый goal type.

Не выполнялся ни этот refactoring, ни перенос старых данных. [План извлечения и реальные исходные методы](docs/05-realization-and-checks.md) основаны на чтении текущего prototype archive.

## 10. Критерий DDD для следующего изменения

Перед добавлением кода должно быть понятно:

- какой домен владеет решением и через какой метод его выражает;
- какой контракт он получает и какой ChangeSet/outcome возвращает;
- какой repository/adaptor осуществляет I/O и где заканчивается transaction;
- каким коротким и feedback-маршрутом проверяется реальная работа.

Если ответ «это просто новый UPDATE в handler» — граница нарушена. Если ответ требует новой подсистемы, не нужной ни одному реальному маршруту, — абстракция преждевременна.

[Готовая формулировка инварианта для документации и AGENTS.md](docs/06-ddd-invariant.md).

## 11. Что проверено в этом комплекте

Проверяются принадлежность всех прежних узлов и переходов, однозначность владельцев, связи каталога таблиц, направления проектных зависимостей, локальные ссылки и неизменность исходных архивов. Это **не unit/integration tests будущего Harness**. Не заявляется, что текущий прототип уже соответствует новому архитектурному правилу.

Фактические результаты и ограничения — [в отчёте проверки](evidence/design-check.md). Следующий этап работы может быть непосредственно реализационным срезом библиотек Task/content/UoW на существующем happy path, без нового общего круга поиска экзотических комбинаций.
