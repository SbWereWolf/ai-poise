# Текущие решения: упрощение и начало разработки

Обновлено: 2026-09-06T14:30:44+05:00.

## Артефакты

Агент подаёт только путь к файлу внутри текущего runtime, task или sprint. Harness назначает внутренний ID; у агента не запрашиваются purpose, роль, тип, hash или описание. Это заменяет прежний смысловой artifact_declarations contract. Пути уровня task/sprint уже указывают окончательного владельца; автоматическое перемещение по предполагаемому смыслу не выполняется.

Первый срез проверяет существование обычного файла, confinement после разрешения symlinks, принадлежность конкретной сессии/задаче/спринту, отсутствие двойного учёта и явные ограничения количества файлов по признаку пути. Требования конкретного этапа проверяются на этом этапе, общие artifact_requirements задачи — на последнем этапе. Вход stage-result называется artifact_paths; выход индекса — id/path.

Размер, checksum и техническое происхождение допустимы внутри БД, но не являются новыми обязанностями агента. Более сложные типы артефактов и содержательный подсчёт тестов уточняются по практике. Нет эвристики «один файл равен одному тесту».

## Явные несогласованности

В E2E-DEV после планирования сохранены TEST_RED/TEST_GREEN, не вводится неизвестный K1. В трёх некомандных ветвях согласованы manual_proposals=1, command_receipts=0. Отрицательный осмотр использует rework_required, а не неподдерживаемый alias rework. Остальные неточные общие fixtures не объявлены реализованными; они не блокируют этот ограниченный happy path.

## Порядок работы

Следующая работа — разработка и использование, а не ещё один общий цикл вычитки. Неизвестные нюансы без живого примера записываются как ограничения среза и не раздувают API. Неосуществлённая автоматизация не маскируется успешным статусом. Один рабочий цикл по-прежнему заканчивается докладом после одного этапа; новый этап требует следующей инструкции пользователя.
