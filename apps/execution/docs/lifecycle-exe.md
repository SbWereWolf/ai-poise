# Согласование и повторная работа Execution

## Назначение и подготовка

Действующий интерфейс `lifecycle` сохраняет существующее поведение согласования
пересмотра условий, перезапуска и возврата на этап в самостоятельном Execution.
Используйте [оболочку](shell-exe.md#запуск) с Python 3.13 в POSIX/Linux.
Requirements публикует постановку и снимки; Sequencing предоставляет допуск и
Workspace. Вызывающая сторона передаёт их результаты явно.

Подготовьте собственный конфигурационный файл и
[process-enabled setup](process-exe.md#правильное-создание-изменение-и-настройка-исполнения).
Настройка сохраняет полный фактический процесс, контракт и canonical Task в
`draft`, generation `1`, iteration `1`, с пустым текущим этапом. Для процесса
с `worktree_required: false` используйте `workspace_id: null`.

Передавайте полный опубликованный снимок Requirements для того же `task_id`.
Его `snapshot_revision` — положительное целое JSON-число, совпадающее с
`requirements_snapshot_revision` контракта. Внешний `statement_revision` и
`statement.statement_revision` — равные положительные целые JSON-числа;
`statement.task_id` совпадает с Task, `statement.goal` содержит исходную цель.
Execution сохраняет полученный снимок и связывает цель при первой заморозке.
При последующих поколениях используется та же цель. Публикация изменённых
требований выполняется через Requirements до предложения пересмотра.

## Явная настройка участников и политики

Добавьте в полный файл конфигурации компонент `lifecycle`. Следующий фрагмент
совпадает с настройкой в [санитизированном примере](../config/execution.example.json):

```json
{
  "lifecycle": {
    "actors": {
      "executor-A": "writer",
      "reviewer-B": "reviewer",
      "executor-C": "writer"
    },
    "policies": {
      "restart-rule": {
        "approving_roles": ["reviewer"],
        "revision_fields": [
          "requirements_snapshot_revision",
          "process_ref",
          "stage_expectations",
          "methods",
          "evidence_plan"
        ]
      }
    }
  }
}
```

| Поле | Значение и применение |
| --- | --- |
| `actors` | Непустое отображение явных идентификаторов участников в их непустые роли |
| `policies` | Непустое отображение ID политик в полный объект политики |
| `approving_roles` | Непустой список различных ролей согласующих |
| `revision_fields` | Явный список различных изменяемых полей из пяти полей примера; пустой список задаёт пустую маску изменений |

`restart_policy_id` контракта выбирает существующую политику. `actor_id` каждой
операции выбирает участника из `actors`. Роль входящего на этап соответствует
роли route entry; роль представляющего результат — роли текущего этапа.
Согласующий имеет роль из `approving_roles` и отличается одновременно от
исходного исполнителя и автора предложения. Эти две личности могут различаться.
Решение сохраняет реального согласующего, его роль, причину и разрешённые поля;
применение перезапуска отдельно сохраняет участника, выполнившего его.
Конфигурация задаёт явные роли вызывающих участников; внешний resolver личности
имеет отдельного владельца. Все значения выбирает оператор установки.

## Пакеты и результаты

Передайте одну строку JSON схемы `stride-execution/v1` с `operation: "lifecycle"`.
`input` состоит ровно из общих полей и полей выбранного действия:

| Общее поле | Правильное значение |
| --- | --- |
| `action` | Строка с одним из семи действий ниже |
| `request_id` | Непустой ID нового запроса |
| `expected_revision` | Актуальная целая revision собственного store, начиная с `0` |
| `task_id` | Канонический ID по настроенной политике |
| `expected_generation` | Текущее положительное целое поколение |
| `expected_contract_revision` | Точная текущая непустая редакция контракта |
| `actor_id` | Явно настроенный участник |

Все дополнительные строки в таблице непусты. Снимок и контракт передаются полными
объектами; контракт имеет [поля действующего setup](store-exe.md#пример-правильного-использования).

| Действие | Дополнительные поля | Условие и результат |
| --- | --- | --- |
| `freeze` | `requirements_snapshot` | Из `draft` связывает опубликованный снимок и цель, получает `ready`; после restart принимает сохранённый согласованный снимок |
| `enter` | `entry_tree` | Из `ready` входит в route entry сохранённого процесса, получает `active` и iteration `1` |
| `present` | `context_id`, `candidate_id` | Из `active` представляет принятый собственный результат gate текущего этапа, iteration, generation, контракта и процесса; получает `verified` |
| `propose_restart` | `proposal_id`, `contract`, `requirements_snapshot`, `reason` | Из `ready`, `active` или `verified` сохраняет точное предложение, исходный и желаемый договоры, снимки, процесс и участников |
| `decide_restart` | `proposal_id`, `decision`, `reason` | Сохраняет решение `approved` либо `rejected` независимого согласующего по существующему предложению текущего поколения |
| `restart` | `proposal_id`, `approval_id` | Из `ready`, `active` или `verified` применяет согласованное предложение того же исходного поколения и контракта; получает новое поколение в `draft` |
| `rework` | `target_stage_id`, `reason`, `entry_tree` | Из `verified` с действительно представленным результатом возвращает работу на разрешённый `rework_targets` текущего этапа, получает `active` |

Предложение изменяет поля, явно разрешённые выбранной маской. Сохраняются
`task_id`, `workspace_id`, `admission_id`, `restart_policy_id` и исходная цель.
При прежнем `process_ref` используется уже сохранённый процесс исполнения;
новый выбранный процесс разрешается при создании предложения. Перезапуск
использует именно согласованный снимок этого процесса. Последующая публикация
редактора сохраняет самостоятельность прежних поколений.

Успех возвращает exit `0` и один объект с точными полями
`schema,status,revision,replayed,task_id,generation,contract_revision,state,current_stage,iteration,result`.
`status` равен `lifecycle_applied`; `result` всегда содержит `action,id` события.
Дополнительно `enter` возвращает `entry_tree`; `present` —
`context_id,candidate_id,presented_result`; `propose_restart` — `proposal_id`;
`decide_restart` — `proposal_id,approval_id,decision`; `restart` —
`proposal_id,approval_id`; `rework` — `target_stage_id,entry_tree`.
Для `freeze` дополнительных полей результата нет.

## Правильный порядок работы

1. Получите опубликованный снимок Requirements, допуск и Workspace; выполните
   process-enabled setup с полным контрактом и настройте участников/политику.
2. Передайте `freeze`, затем `enter` с явно выбранным исходным деревом Git либо
   другим непустым идентификатором базового дерева, предоставленным владельцем
   рабочей области. Execution сохраняет переданное значение.
3. Выполните работу этапа и [приёмку gate](gate-exe.md). Передайте полученные
   `context_id,candidate_id` через `present`. При оценке gate canonical состояние
   остаётся прежним; `present` выполняет отдельный переход.
4. Для повторной работы передайте `rework` с разрешённой целью, причиной и новым
   базовым деревом. Для пересмотра условий опубликуйте требуемый снимок,
   передайте `propose_restart`, затем решение независимого согласующего и
   `restart` с возвращённым `approval_id`.
5. После restart выполните `freeze` согласованного снимка и `enter` нового
   поколения. Для каждого нового действия берите текущие revision, generation
   и contract revision из ответа или собственного запроса исполнения.

Перезапуск увеличивает generation на `1`, устанавливает iteration `1`, очищает
текущий этап, указатель представленного результата, посещения и entry tree нового
поколения. Возврат на этап сохраняет generation и контракт; iteration равен
следующему посещению выбранного целевого этапа: первое посещение — `1`, следующее — `2`.
Снимки и факты прежних поколений остаются с исходной принадлежностью.
Task, Workspace и незавершённая работа сохраняются. Физические операции Git и
Workspace выполняются их владельцами; lifecycle меняет собственное состояние
Execution и переданные ссылки/базовое дерево.

## Исполняемый пример начала работы

После публичного setup установите переменные: `EXECUTION_CONFIG` — абсолютный путь
к полному файлу установки, `REQUIREMENTS_SNAPSHOT` — путь к JSON-файлу с настоящим
опубликованным снимком выбранной Task, `EXECUTION_TASK_ID` — её канонический ID,
`EXECUTION_ACTOR_ID` — участник с ролью route entry, `EXECUTION_ENTRY_TREE` —
полученное от владельца Workspace базовое дерево. Для установки с приложенным
примером ролей участником может быть `executor-A`.

Из корня checkout выполните выбранным Python:

```sh
python -B apps/execution/docs/examples/lifecycle-start.py
```

[Пример](examples/lifecycle-start.py) читает актуальную запись через CLI,
замораживает переданный снимок, входит в начальный этап и выводит результаты
`query/lifecycle` и `query/restart_history`. Запускайте его для подготовленного
`draft`; последующие шаги выполняйте по процедуре выше.
ID запросов примера включают канонический ID Task, поколение и действие:
каждая Task использует собственное пространство имён в общем журнале установки.

## Чтение, повтор и продолжение

`query` принимает точные элементы `{id,kind,task_id}` с `kind: "lifecycle"` либо
`"restart_history"`. Корень ответа: `schema,status:"read_only",revision,results`.
Элемент результата имеет `{id,kind,result}`. Для lifecycle `result` содержит
`registered_goal,requirements_snapshot,execution,entry_tree,history`;
`execution` содержит `task_id,generation,contract_revision,state,current_stage,iteration,workspace_id,admission_id`.
История включает все собственные события lifecycle данной Task в порядке записи.
`restart_history` возвращает только события предложения, решения и restart,
включая прежние поколения. Полные предложения и решения доступны через
[чтение фактов store](store-exe.md#запись-чтение-и-повтор).

Один новый успешный запрос увеличивает общую revision на `1`; результат и все
его изменения сохраняются одной короткой транзакцией собственного store.
Для точного повтора отправьте весь исходный пакет с тем же `request_id` и
исходными ожидаемыми версиями: сохранённый ответ возвращается с `replayed: true`.
Для следующего действия используйте новый ID и актуальные версии.

Обычный отказ возвращает одну строку JSON `status: "rejected"` с `reason`,
exit `2` и пустым stderr; состояние, факты, revision и результаты повторов сохраняются.
Устраните названную причину, прочитайте актуальные версии и отправьте новый
корректный запрос. При ошибке записи вся операция откатывается, включая уже
выполненное изменение canonical состояния. Оператор исправляет причину внешним
инструментом; после этого работа продолжается через тот же публичный интерфейс.

## Границы и проверки

Действующие семь действий отделены от проектных схем
[целевого контракта](contract-exe.md). Автоматическое продвижение, внешний runner,
terminal outcome, повторное использование доказательств и удаление материалов
имеют отдельные задачи поставки. Сохранённые методы/доказательства остаются
историей своих поколений; новую успешную проверку выполняет её владелец.

Целевые проверки действующего поведения:

```sh
python -B -m pytest -q apps/execution/tests/test_lifecycle_restart.py apps/execution/tests/test_lifecycle_rework.py
```

Проверка локальных ссылок, включая входящие ссылки на изменённые страницы:

```sh
PYTHONPATH=src python -B tools/check_documentation.py --checkout . --changed apps/execution/docs
```
