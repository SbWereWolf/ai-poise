Все 13 исходных определений задают роли executor и reviewer явно. Четыре шага

проверяющий проверяет результат» описывают общий цикл предметного этапа; число
узлов каждого принятого графа сохраняется. См. [этапы и роли](../workflows/paired-task-stages.md#остальные-парные-шаблоны).

в текущих маршрутах, 19 выведены из них; в текущем справочнике 143 узла.
Справочник именует 52 возврата: 47 явных changes_requested к разрешённому rework target
десяти перенесённых типов и пять сохранённых FB-DEV-01, FB-DEV-03, FB-TST-01,
FB-VER-01 и FB-VER-02. Прежние 25 именованных возвратов остальных типов заменены
ссылками на принятые графы ERP; исторические материалы остаются неизменными.
Полный граф включает и остальные переходы. В частности, review inspection →
execution_inspection при changes_requested ведёт к проверке отчёта, а не к rework.
Это референсные определения процессов, а не обещание автоматически доказать содержательную
полноту любого проекта или выполнение всего исторического каталога приёмки.

Шаблоны каждого типа самодостаточны. Нет `extends`, наследования другого goal_type,
Python-переключателя по именам целей в runner или подстановки отсутствующих команд.
13 эталонных предметных сценариев находятся только в примере/тестах. Стандартные семейства
produce/inspect/revise/observe/check/apply_plan/publish остаются общими.

## Общие исходники ERP и справочные представления

Общий каталог содержит принятые определения процессов. Новое готовое определение
производителя переносится в workflow-templates вместе с обязательным изменением
TaskBlueprint, если оно есть. Подготовленная форма workflows обновляется существующим
GoalConfig с точной текущей revision, сохранённой БД редактора и устойчивым request_id.
Полномочия, роли, переходы, разрешённые пути, требования и инструкции переносятся
из принятого источника. Справочные таблицы отражают этот граф, а не задают другой.

Для каждого определения различайте общий исходник, подготовленную форму,
рабочий workflow проекта и фактически выбираемый TaskBlueprint. Создание нового
проекта берёт подготовленные общие определения; существующий проект обновляет
свой выбор и рабочие определения через владельца конфигурации. Потребители общей
библиотеки выбирают версию и обновляются отдельно. Текущие Task сохраняют frozen snapshot.
Подробный [порядок обслуживания](#development-исходник-подготовленная-форма-и-выбранный-рабочий-маршрут)
сохраняет отдельные подтверждения каждого результата.

У десяти перенесённых типов reference.stages.before перечисляет дополнительные
поля stage.sections, заполняемые перед отправкой результата; after перечисляет
ID дополнительных content_contract.sections, доступных для записи этому этапу.
Сохранённые source_id связывают прежние идентификаторы; новые source_id указывают
принятое решение производителя и узел. source_path/source_line обратной связи
указывают объявление исходного этапа в общем исходнике.

method_schedule и methods справочника относятся к конкретным учебным сценариям.
Фиксированные карты checks пяти TaskBlueprint согласованы с их реальными этапами;
остальные восемь принимают явный caller checks. Учебные имена методов не становятся
скрытой политикой starter или глобальной настройкой cfg.checks. Семантическую
применимость и конкретные методы определяет собственная Task.

## Состав и использование

Текущий development поставляется в `config/catalogue/workflow-templates/development.json`
и `config/catalogue/workflows/development.json`; обе формы содержат 16 этапов.
Прежний восьмиэтапный `config/workflows/development.json` удалён из исходной поставки.
Для конкретной Task применяется
[выбор источника процесса](../workflows/task-planning.md#выбор-источника-процесса):
сохранённая Task продолжает свой процесс, новая использует явно выбранный проект
и исходную форму. Удаление reference не публикует изменения в рабочие проекты
и не мигрирует уже сохранённые Task.

Текущий формат требует явные `purpose` и `criteria_authority` каждого этапа;
см. [критерии этапов](../workflows/stage-criteria.md) и
[полный пример](../workflows/stage-criteria-workflow.example.json).
Перечисленные исторические packs без этих полей не становятся валидными за счёт
имени роли, handler или загрузки новым кодом. Перед применением их классифицируют
явно. Для сохранённой установки требуется отдельно разрешённая
[инвентаризация и
миграция](../task-workflow-snapshot-migration.md#миграция-типов-и-критериев-этапов).
Изменение формата исходного шаблона само по себе не мигрирует сохранённые packs,
их managed-конфигурации или снимки Task.

`workflow-templates` — исходные шаблоны продукта. `workflows` — готовые рабочие файлы,
созданные существующим GoalConfigCommands, не скопированные агентом в обход редактора.
`editor.example.json` явно задаёт пути исходных шаблонов и рабочие назначения.
`settings.example.json` задаёт типизированные шаблоны задач и лимит пакета.
Рабочие `editor.json`/`settings.json` принадлежат конкретной установке и явно выбирают
владельца, корень, назначения и хранилище редактора. Не копируйте новый шаблон поверх managed
workflow.
Обновление новых Task и существующих frozen snapshots — разные операции.

Для нового пустого назначения `catalogue install` принимает явные create-запросы;
для уже поставленных конфигов применяется update с их точным expected_revision и template=null.
Повтор прежнего запроса возвращает его receipt. Не удаляйте конфиг, чтобы обойти конфликт.
Исходный шаблон можно развивать как код продукта; рабочий конфиг изменяют через инструмент.

### Development: исходник, подготовленная форма и выбранный рабочий маршрут

Текущий `development` содержит 16 обычных этапов и 18 входных требований. Проектирование
ближайшего этапа и независимое принятие проекта предшествуют исполнению и отдельному
принятию его результата. Полный маршрут и результаты перечислены в
[описании разработки](../workflows/paired-task-stages.md#шесть-пар-разработки).
Отклонение исполнения возвращает работу тому же исполнителю под уже принятым проектом.
В `solution_planning` согласуют общий путь, решения и предположения. Его
`documentation_scope` называет возможные канонические документы и предварительную
необходимость их изменения: `required`, `not_required` или `unknown` с обоснованием.
Подробный `documentation_plan` впервые создают в `documentation_planning` после принятия
реализации. Предварительная область помогает найти владельцев документации; подробные
результаты и способы её проверки определяет поздний план.

Полномочия `criteria_authority` принадлежат собственным парам ближайшего исполнения:

| Автор проекта | Независимый проверяющий проекта | Исполнение, для которого задают критерии |
|---|---|---|
| `verification_planning` | `verification_planning_inspection` | `test_implementation` |
| `implementation_design` | `implementation_design_inspection` | `implementation` |
| `documentation_planning` | `documentation_planning_inspection` | `documentation` |

Ранняя пара `solution_planning` / `solution_planning_inspection` имеет пустые списки
предложения и решения критериев. Смысл назначения этапа и протокол редакций описаны
в [договоре критериев](../workflows/stage-criteria.md#договор-и-критерии).

Различайте три объекта: продуктовый файл в `workflow-templates`, подготовленный редактором
файл в `workflows` выбранного checkout и фактически выбранный snapshot из project manifest.
Последний может находиться по другому пути. Перенос исходного шаблона между проектами
переносит исходные данные; назначение, регистрация редактора и рабочая revision каждого
проекта обновляются отдельно через их владельцев.

Порядок обслуживания корня и его потребителей:

1. Принятый переносимый образец включают в `workflow-templates`. Согласуют связанные
   метаданные `reference.json` и типизированный шаблон задачи, если изменился его контракт.
   У `development` раннее поле `solution_planning.before` в справочнике содержит
   `documentation_scope`; Task blueprint сохраняет параметризованное расписание `checks`.
2. Существующий подготовленный файл обновляют через
   [пакетный редактор](goal-config.md#предметные-изменения): `mode=update`, точная текущая
   `expected_revision`, `template=null`. Проверяют фактические файл, receipt и
   [managed head / live revision](goal-config.md#сверка-управляемой-revision-с-live-конфигурацией).
   Для выделенного Task worktree собственные ignored `editor.json` и runtime редактора —
   обычная настройка этой рабочей копии. Её отдельный target и первый managed head отличают
   от регистрации основного checkout. Общая база редактора сохраняет своё назначение.
3. Новый проект создают по явно выбранному project blueprint через
   [владельца подготовки](project-setup.md#пакетный-путь-для-агента).
   `linux-reference` и `wsl-poise` берут исходные данные маршрутов из подготовленных корней
   `config/catalogue/workflows/`. Полученные проектные файлы — отдельные копии с явно
   заданными индивидуальными настройками.
4. Для уже выбранного в manifest существующего `goal_type` применяют
   [project-config](project-setup.md#обновление-действующего-проекта) с `workflow_updates`,
   точной revision всего проекта и отдельной revision выбранного workflow. Этот update
   работает с существующими ключами `workflows`. Если требуется изменить сам выбор или
   добавить ключ, сначала устанавливают доступный маршрут и полномочия его владельца.
   Подтверждение обновления потребителя — реальный receipt и повторное чтение выбранного
   файла, графа, требований и настроек с сохранением остальных маршрутов и private values.

Обновление корня и создание нового проекта имеют отдельные результаты от обновления
существующих проектных копий. Интеграция исходников и публикация выбранного рабочего
снимка также имеют собственные квитанции. После разрешённой доставки исходников
согласованность managed head основного checkout проверяют через `status`; при
подтверждённом расхождении применяют существующий `reconcile` с наблюдёнными revisions
и основанием полномочий. История прежнего владельца сохраняется в его базе.

Сохранённые снимки действующих Task продолжают свой согласованный граф. Обновление
`development` не переписывает их историю. Этот маршрут изменён отдельно; остальные
12 типов задач сохраняют собственные текущие определения.

### Самостоятельная разработка тестов

Текущий `test_development` содержит 9 этапов и 16 входных требований. Наблюдение,
план покрытия и проект тестов имеют собственный независимый осмотр. После реализации
тестов исполнитель получает механическое наблюдение чувствительности, затем проверяющий
независимо принимает результат. Полная последовательность приведена в
[исполнимом маршруте](../workflows/paired-task-stages.md#исполнимый-маршрут-test_development)
и [карте этапов](catalogue-stage-map.md#test_development).

критерии `test_implementation`; остальные списки полномочий этого шаблона пусты.
Успешная проверка чувствительности ведёт в `test_inspection`. Отрицательное или
неопределённое наблюдение и замечания независимого осмотра возвращают работу в
`test_implementation` под согласованным проектом.

Типизированный Task blueprint сохраняет 14 параметров, включая явные `checks` и
`executable_obligations`. Собственный проект задаёт реальные методы, их расписание
и аргументы наблюдения по [договору доказательств](../workflows/evidence.md#один-пакет-результата).
Начальный шаблон и позднее проектирование проверок описаны в
[типизированном договоре](#типизированный-шаблон-задачи).

Различайте исходник `workflow-templates/test_development.json`, подготовленную форму
`workflows/test_development.json` и выбранный manifest конкретного проекта. Их обслуживают
по [порядку обновления корня и потребителей](#development-исходник-подготовленная-форма-и-выбранный-рабочий-маршрут).
Новые проекты `linux-reference` и `wsl-poise` получают собственные копии подготовленного
маршрута. Действующий проект обновляется через своего владельца конфигурации; сохранённая
Task продолжает свой frozen snapshot.

Историческая DDD-карта сохраняет 102 записи, текущий справочник содержит 143 узла.
С текущими маршрутами сопоставлены 83 исторических идентификатора; 19 выведены
из актуальных графов и входят в unmapped. В extra перечислены 60 текущих узлов,

Эти поля описывают сопоставление версий; исполнение и независимая приёмка

### Проверка соответствия результата

Текущий `verification` содержит пять этапов и 19 требований содержимого. Исполнитель
проектирует программу проверки, отдельный проверяющий принимает её и критерии
`execution`. Наблюдения и анализ выполняет исполнитель; итог получает независимый
осмотр. Полная последовательность, назначения и возвраты приведены в
[исполнимом маршруте](../workflows/paired-task-stages.md#исполнимый-маршрут-verification)
и [карте этапов](catalogue-stage-map.md#verification).

Типизированный Task blueprint сохраняет 12 параметров. Конкретная Task предоставляет
свои `methods`, `method_inputs`, содержательные критерии и evidence-контракт.
Полное расписание задаёт `execution: [VERIFY]`, остальные четыре этапа имеют пустые
списки checks. Метод `VERIFY` объявляется в собственном реестре методов Task;
отдельная глобальная настройка `cfg.checks.VERIFY` для этого starter не требуется.
При материализации отсутствие объявленного метода даёт отказ о неизвестной ссылке
расписания. Параметры и доказательства следуют
[типизированному договору](#типизированный-шаблон-задачи) и
[договору результата](../workflows/evidence.md#один-пакет-результата).

Результаты наблюдения `satisfied`, `not_satisfied` и `inconclusive` ведут в `analysis`.
Отрицательное или неопределённое наблюдение остаётся фактом для анализа. Завершение
маршрута требует отдельного решения `execution_inspection`, а не одного exit-кода метода.
Сам шаблон проверки соответствия предоставляет наблюдения и вывод, исправление
проверяемого продукта относится к отдельно согласованной работе.

Различайте `workflow-templates/verification.json`, подготовленный редактором
`workflows/verification.json`, выбранный workflow проекта и фактически выбираемый
Task blueprint. Обновление общего источника не обновляет каталог, частный выбор
starter или рабочую конфигурацию существующего проекта. Новые проекты семейств
`linux-reference` и `wsl-poise` получают собственную подготовленную definition;
создание Task требует совместимого BP из явно выбранного каталога. Владелец
конфигурации обновляет действующий проект, а сохранённая Task продолжает frozen snapshot.

Используйте [порядок обслуживания корня и потребителей](#development-исходник-подготовленная-форма-и-выбранный-рабочий-маршрут).
Если live definition существует без managed head, штатный `update` использует её
точную текущую revision и существующий редактор. Точный повтор завершённого запроса
возвращает прежний результат. Неизвестный исход продолжайте через существующие
[status и восстановление публикации](goal-config.md#публикация-повторы-и-ошибки).
[Сверка managed head](goal-config.md#сверка-управляемой-revision-с-live-конфигурацией)
применяется к существующей управляемой редакции после подтверждённой внешней публикации;
создание новой БД не заменяет этот маршрут.

## CLI и API

```bash
export PYTHONPATH="$PWD/src"
python -m poise catalogue --settings "$PWD/config/catalogue/settings.json"
```

В stdin — один JSON с точными полями `action`, `items`, `project_config`.

Для `action=install`: `project_config=null`, items — список из `goal_type`, `request_id`,
`mode`, `expected_revision`, `template`, `changes`. Схема отдельного пакета редактора
добавляется самим инструментом. Шаблон create выбирается явно объектом `{"id":"documentation-v1"}`.
Все формы запросов и конечные workflow definitions проверяются до первой публикации.
Для файлов остаются отдельные receipts: это **не транзакция всей файловой системы**.
Конфликт ревизии или I/O после начала может оставить уже опубликованные валидные конфиги;
повтор возвращается к тем же request IDs и не создаёт дубликаты.

Для `action=tasks`: `project_config` — абсолютный путь выбранного проекта, items — список
`template` (объект с единственным `id`) и `parameters`. Возвращаются полностью развёрнутые задачи.
Они пока не записываются в Task store: контракт передают в обычный bootstrap, план спринта
или результат planning-этапа. Нет отдельного потока хранения черновиков в редакторе.

`CatalogueCommands.install(items)` и
`CatalogueCommands.tasks(items,workflows,automatic_checks,decomposition_policy)`
доступны как прикладная библиотека. Оба используют явный max_items.
Ответ краткий; полный JSON сохраняется по адресуемому пути с ограничениями существующего редактора.

## Типизированный шаблон задачи

`task-blueprint-1` содержит goal_type, параметры с типами и полный task-object.
Плейсхолдер `{"$input":"identity"}` занимает целое значение: подстановка не является
интерполяцией кода, eval или неявным наследованием. Для списка/объекта сохраняется тип.
Все использованные параметры должны быть объявлены, все объявленные — переданы явно;
лишние значения и отсутствие значения отклоняются. Допустимый null задаётся типом параметра.

Текущие общие параметры исходных шаблонов:

- `identity`;
- `membership`;
- `goal`;
- `requirements`;
- `dod`;
- `methods`;
- `method_inputs`;
- `artifact_requirements`;
- `contract`;
- `evidence`;
- `stage_contracts`;
- `decomposition`.

Полные договоры этапов и их критерии задают по
[договору критериев](../workflows/stage-criteria.md#договор-и-критерии).
При материализации порядок `stage_contracts` соответствует порядку объявлений этапов
выбранного workflow; последовательность исполнения задают его переходы.
Шаблоны `development` и `test_development`
дополнительно требуют `executable_obligations`: явную классификацию только тех requirement/DoD
refs, которым требуется executable evidence.
Шаблон `development` также требует параметр `checks`: вызывающая сторона явно передаёт
полное начальное расписание проверок. В проверенной полной форме типизированного контракта
каждому идентификатору этапа сопоставлен список методов; для пустого начального расписания
все эти списки пусты. Непустые списки проходят обычную проверку ссылок на методы и этапы.
Будущие RED/GREEN методы,
их расписание и артефакты проектируются и регистрируются защищённой мутацией на этапе
`verification_planning`; creation contract не требует знать их заранее.

Каждый шаблон сам фиксирует goal_type. `methods` содержит
**реальные точные команды**, а не символические названия проектного runner.
`contract` позволяет добавить поэтапные требования, секции и индивидуальные цепочки трассировки;
`evidence` определяет командные/логические методы и осмотр конкретных аргументов.
Итог проходит тот же `validate_creation`, что отдельная задача и публикация спринта.

Полная материализация через каталог проверяет цель, требования, DoD, разрешимый процесс,
точные методы и их ссылки, явные artifact/content/evidence contracts. Это отдельная граница
от [первичной регистрации цели](../workflows/task-execution-contract.md#постановка-и-подготовка-задачи).
Типы отличаются
запланированными этапами, обязательными секциями, ограничениями изменений и benefit.
Это не 13 новых Python validators и не автоматическая оценка истинности плана.

## Получение фактов и обратная связь

Предварительно известные факты можно передать в PREPARE. Поля, требующие свежего наблюдения,
обязательны на post; точный evidence-план задаёт CONTINUE и связь с текущими receipt IDs.
Следующий осмотр передаёт своё решение, даже если прежний осмотр уже принимал тот же аргумент.
Решения разных осмотров не подменяются молчаливым reuse.

produce/observe/check могут принять `stage_work={"resolutions":[...]}` для исправления
**уже зарегистрированных** находок. Исправление не принимает себя. Поздний inspect
проверяет каждое предложение отдельно. В самостоятельном review отчёт этапа inspection роли executor
принимает execution_inspection роли reviewer; исправление сохраняет этот порядок
и явные переходы принятого определения.
Полностью неактивный `observe` без `subject_methods`, arguments и этапных checks допустим.
Если такой `observe` активирован arguments или ссылками в расписании, creation contract его
отклоняет: активному наблюдению нужен явный subject method.
В environment_remediation применение изменения выполняет application с handler apply_plan.
Отклонение результата возвращает работу в application по согласованному плану.

## Публикация результата planning

Три публикации — механические узлы с явной пользовательской санкцией, а не новые
содержательные этапы или автоматическая приёмка. `accept` сам по себе не запускает publication.

Task planning публикует через stage_work:
`{"kind":"tasks","section":"planned_task","authorization":"<явная инструкция>"}`.
В сохранённой секции — список полных standalone creation intents. Для нового Task штатная
форма — `{request_id, task без id}`; поддержанный explicit contract остаётся допустимым.
Publication возвращает `allocations`, а зависимости Sprint до публикации используют
`request_id` automatic-ребёнка как alias и после allocation сохраняются с фактическими IDs.

Sprint planning:
`{"kind":"sprint","section":"planned_sprint","authorization":"<явная инструкция>"}`.
Секция содержит `sprint_id`, точный `template`, пакет `changes` существующего Sprint API.

В публикации нельзя заменить draft новым inline-объектом. Читается уже сохранённая секция,
не разрешённая для записи в этом этапе, после принятого осмотра согласно графу.
Каждый ребёнок валидируется собственным выбранным workflow contract. Task/Sprint IDs не
должны пересекаться. Explicit IDs полного пакета и новый Sprint ID резервируются до первой
automatic allocation, поэтому порядок детей не определяет коллизию. Все дочерние строки,
граф, allocation receipts и receipt публикации записываются одним UoW.
Нет worktrees у ещё не начатых детей. Обычный bootstrap опубликованной standalone task
подготавливает её работу так же, как для опубликованного участника спринта.

Изменение ранее опубликованного состава через эту операцию не поддерживается: существующий
ID означает конфликт, а не перезапись. Поздние интеграция, перенос и метрики используют
прежние API владельцев.

## Примеры

```bash
python examples/catalogue_walkthrough.py --directory /tmp/poise-catalogue-dev-new --goal development --scenario feedback
python examples/catalogue_walkthrough.py --directory /tmp/poise-catalogue-plan-new --goal sprint_planning --scenario short
```

Каталоги должны быть новыми. Другие `--goal`: test_development, verification, review, design,
analysis, profiling, environment_diagnostics, environment_remediation, documentation,
task_planning, integration. `--scenario short|feedback` выбирается явно.
Создаются только учебные репозитории и bare remote, сеть не нужна.
Исходные тексты приложения меняет сценарный драйвер нативно; служебные Task/Sprint состояния
создаются через публичные API, не SQL. Fault-injection tests используют SQL только для установки
заведомо аварийного trigger, а не подстановки будущего бизнес-состояния.

Команды, Git/SQLite, слияния и публикации настоящие. Reviewer-решения, аргументы и пользовательские
инструкции — **тестовые данные**, не независимая оценка модели. Содержательные тексты референса
не следует копировать как реальные требования продукта. Качество реальной работы оценивается
при применении на проекте, не количеством пройденных конфигов.

## Что пока не заявляется

Не исполняются автоматически все исторические 653 нормативных тест-кейса. Не добавлены
недостающие live Gmail/JetBrains/полный usage feed. Не реализован автоматический доказатель
истинности логических аргументов, универсальная предметная полнота creation validator,
полная семантическая инвалидация произвольного графа или выбор applicability за пользователя.
В данном каталоге применимость обязательных базовых/документационных этапов выбрана явно
в самих reference definitions; вариант без этапа должен быть отдельной явной настройкой графа.
Никаких исключений в kernel по имени цели.

Task schema — `ddd-accounting-12`, SQLite user_version=13. Schema 11 и более ранние версии
не поддерживаются. Единственная миграция 12 → 13, введённая для физической эксклюзивности
ownership, выполняется под тем же writer lock: она сохраняет Task, совпадающую с привязкой
worktree этой сессии, и освобождает остальные дублирующие claims. Если эта привязка не
позволяет однозначно выбрать владельца, открытие store прекращается с actionable ошибкой и
ничего не угадывается. У завершённой Task без claim несколько привязок worktree уже не
являются владением: миграция освобождает их все. Optional telemetry использует явно выбранные
отдельные database/lock.

## Редактируемые исходники и сохранённые задачи

Запись `templates` редактора требует `path`; запись `task_templates` каталога —
`path` и `goal_type`. Новые пакеты выбора требуют только `id`. Селекторы каталога
возвращают этот же формат. Каталог читает текущее корректное содержимое файла:
редактирование исходника не требует новой версии или хэша. Неизвестные опции
рабочих настроек сохраняются; старые поля version/digest не являются условием чтения.

При создании задачи текущий шаблон разворачивается в её собственный draft.
После этого редактирование, ready и загрузка задачи используют сохранённый договор;
удаление или изменение исходного шаблона его не заменяет. `planning.template`
равен null либо содержит обязательный непустой `id` и необязательные известные
поля `version`, `digest` как исторический текст. Для этих audit-полей допустимы
любые строки, включая пустые; они сохраняются без сверки с исходником.
Посторонние поля контракта задачи отклоняются. Существующие записи задач не мигрируются.

Сохраняются согласованность типа цели задачи с записью каталога, структура графа,
явные параметры и проверка конкурентной публикации. Низкоуровневый редактор
может создать новый тип цели из графа другого типа; это отдельный допустимый
сценарий от выбора собственного зарегистрированного шаблона каталогом.
Удаление требований хэшей не исправляет исторические шаблоны с отсутствующими
обязательными полями этапов, описанные выше.

## Строгое чтение исходников примера

`examples/catalogue_walkthrough.py` читает оригинальные `settings.example.json` и
`editor.example.json` существующим `read_document` до первой записи. Повторяющиеся
поля, NaN/Infinity и корень другого типа отвергаются до bootstrap save, копирования
и публикации. Оба документа должны быть корректны; пример не нормализует ошибочный
исходник записью промежуточного JSON.

Пример создаёт фиксированные settings/editor внутри явно выбранного disposable home,
привязывает туда root, затем существующие FileCatalogue/EditorSettings проверяют все
назначения до копирования шаблонов. Для подготовки Task используется
`task_selection(goal)` с единственным `id`, а не workflow selection с version/digest.
Действующий development route продолжает одну Task через обычный release/bootstrap.
Явные purpose/criteria_authority этапов и обязательные параметры среды сохраняются.
