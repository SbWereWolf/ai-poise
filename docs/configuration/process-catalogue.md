## Состав и использование

`process-templates` — исходные шаблоны продукта. `processes` — готовые рабочие файлы,
созданные существующим GoalConfigCommands, не скопированные агентом в обход редактора.
`editor.json` явно задаёт шаблоны, версии, digest и конечные пути.
`settings.json` задаёт типизированные шаблоны задач и максимальное число объектов в пакете.

Для нового пустого назначения `catalogue install` принимает явные create-запросы;
для уже поставленных конфигов применяется update с их точным expected_revision и template=null.
Повтор прежнего запроса возвращает его receipt. Не удаляйте конфиг, чтобы обойти конфликт.
Исходный шаблон можно развивать как код продукта; рабочий конфиг изменяют через инструмент.

## CLI и API

```bash
export PYTHONPATH="$PWD/src"
python -m poise catalogue --settings "$PWD/config/catalogue/settings.json"
```

В stdin — один JSON с точными полями `action`, `items`, `project_config`.

Для `action=install`: `project_config=null`, items — список из `goal_type`, `request_id`,
`mode`, `expected_revision`, `template`, `changes`. Схема отдельного пакета редактора
добавляется самим инструментом. Шаблон create выбирается явно по id/version/digest.
Все формы запросов и конечные process definitions проверяются до первой публикации.
Для файлов остаются отдельные receipts: это **не транзакция всей файловой системы**.
Конфликт ревизии или I/O после начала может оставить уже опубликованные валидные конфиги;
повтор возвращается к тем же request IDs и не создаёт дубликаты.

Для `action=tasks`: `project_config` — абсолютный путь выбранного проекта, items — список
`template` (id/version/digest) и `parameters`. Возвращаются полностью развёрнутые задачи.
Они пока не записываются в Task store: контракт передают в обычный bootstrap, план спринта
или результат planning-этапа. Нет отдельного потока хранения черновиков в редакторе.

`CatalogueCommands.install(items)` и `CatalogueCommands.tasks(items,processes,automatic_checks)`
доступны как прикладная библиотека. Оба используют явный max_items.
Ответ краткий; полный JSON сохраняется по адресуемому пути с ограничениями существующего редактора.

## Типизированный шаблон задачи

`task-blueprint-1` содержит goal_type, параметры с типами и полный task-object.
Плейсхолдер `{"$input":"identity"}` занимает целое значение: подстановка не является
интерполяцией кода, eval или неявным наследованием. Для списка/объекта сохраняется тип.
Все использованные параметры должны быть объявлены, все объявленные — переданы явно;
лишние значения и отсутствие значения отклоняются. Допустимый null задаётся типом параметра.

Текущие общие параметры исходных шаблонов:
identity, membership, goal, requirements, dod, methods, method_inputs,
artifact_requirements, contract, evidence. Шаблоны `development` и `test_development`
дополнительно требуют `executable_obligations`: явную классификацию только тех requirement/DoD
refs, которым требуется executable evidence.
Шаблон `development` также требует параметр `checks`: вызывающая сторона явно передаёт
полное начальное расписание проверок: пустое начальное расписание `{}` допустимо;
непустое проходит обычную проверку ссылок на методы и этапы. Будущие RED/GREEN методы,
их расписание и артефакты проектируются и регистрируются защищённой мутацией на этапе
`verification_planning`; creation contract не требует знать их заранее.

Каждый шаблон сам фиксирует goal_type. `methods` содержит
**реальные точные команды**, а не символические названия проектного runner.
`contract` позволяет добавить поэтапные требования, секции и индивидуальные цепочки трассировки;
`evidence` определяет командные/логические методы и осмотр конкретных аргументов.
Итог проходит тот же `validate_creation`, что отдельная задача и публикация спринта.

Минимумы текущего Task creation API: цель, требования, DoD, разрешимый процесс, точные методы
и проверки их ссылок, явные artifact/content/evidence contracts. Типы отличаются
запланированными этапами, обязательными секциями, ограничениями изменений и benefit.
Это не 13 новых Python validators и не автоматическая оценка истинности плана.

## Получение фактов и обратная связь

Предварительно известные факты можно передать в PREPARE. Поля, требующие свежего наблюдения,
обязательны на post; точный evidence-план задаёт CONTINUE и связь с текущими receipt IDs.
Следующий осмотр передаёт своё решение, даже если прежний осмотр уже принимал тот же аргумент.
Решения разных осмотров не подменяются молчаливым reuse.

produce/observe/check могут принять `stage_work={"resolutions":[...]}` для исправления
**уже зарегистрированных** находок. Исправление не принимает себя. Поздний inspect
проверяет каждое предложение отдельно. Самостоятельный review может на повторном inspection
предложить исправление своего отчёта: этот пакет не содержит новых findings и решений о
собственном принятии; следующий self_inspection принимает/отклоняет его.
Полностью неактивный `observe` без `subject_methods`, arguments и этапных checks допустим.
Если такой `observe` активирован arguments или ссылками в расписании, creation contract его
отклоняет: активному наблюдению нужен явный subject method.
В environment_remediation correction использует apply_plan, а не текстовый revise:
это явная специализация общей библиотеки для реального изменения среды.

## Публикация результата planning

Три публикации — механические узлы с явной пользовательской санкцией, а не новые
содержательные этапы или автоматическая приёмка. `accept` сам по себе не запускает publication.

Task planning публикует через stage_work:
`{"kind":"tasks","section":"planned_task","authorization":"<явная инструкция>"}`.
В сохранённой секции — список полных standalone creation intents. Для нового Task штатная
форма — `{request_id, task без id}`; поддержанный explicit contract остаётся допустимым.
Publication возвращает `allocations`, а зависимости Sprint до публикации используют
`request_id` automatic-ребёнка как alias и после allocation сохраняются с фактическими IDs.

Sprint planning:
`{"kind":"sprint","section":"planned_sprint","authorization":"<явная инструкция>"}`.
Секция содержит `sprint_id`, точный `template`, пакет `changes` существующего Sprint API.

В публикации нельзя заменить draft новым inline-объектом. Читается уже сохранённая секция,
не разрешённая для записи в этом этапе, после принятого осмотра согласно графу.
Каждый ребёнок валидируется собственным выбранным process contract. Task/Sprint IDs не
должны пересекаться. Explicit IDs полного пакета и новый Sprint ID резервируются до первой
automatic allocation, поэтому порядок детей не определяет коллизию. Все дочерние строки,
граф, allocation receipts и receipt публикации записываются одним UoW.
Нет worktrees у ещё не начатых детей. Обычный bootstrap опубликованной standalone task
подготавливает её работу так же, как для опубликованного участника спринта.

Изменение ранее опубликованного состава через эту операцию не поддерживается: существующий
ID означает конфликт, а не перезапись. Поздние интеграция, перенос и метрики используют
прежние API владельцев.

## Примеры

```bash
python examples/catalogue_walkthrough.py --directory /tmp/poise-catalogue-dev-new --goal development --scenario feedback
python examples/catalogue_walkthrough.py --directory /tmp/poise-catalogue-plan-new --goal sprint_planning --scenario short
```

Каталоги должны быть новыми. Другие `--goal`: test_development, verification, review, design,
analysis, profiling, environment_diagnostics, environment_remediation, documentation,
task_planning, integration. `--scenario short|feedback` выбирается явно.
Создаются только учебные репозитории и bare remote, сеть не нужна.
Исходные тексты приложения меняет сценарный драйвер нативно; служебные Task/Sprint состояния
создаются через публичные API, не SQL. Fault-injection tests используют SQL только для установки
заведомо аварийного trigger, а не подстановки будущего бизнес-состояния.

Команды, Git/SQLite, слияния и публикации настоящие. Reviewer-решения, аргументы и пользовательские
инструкции — **тестовые данные**, не независимая оценка модели. Содержательные тексты референса
не следует копировать как реальные требования продукта. Качество реальной работы оценивается
при применении на проекте, не количеством пройденных конфигов.

## Что пока не заявляется

Не исполняются автоматически все исторические 653 нормативных тест-кейса. Не добавлены
недостающие live Gmail/JetBrains/полный usage feed. Не реализован автоматический доказатель
истинности логических аргументов, универсальная предметная полнота creation validator,
полная семантическая инвалидация произвольного графа или выбор applicability за пользователя.
В данном каталоге применимость обязательных базовых/документационных этапов выбрана явно
в самих reference definitions; вариант без этапа должен быть отдельной явной настройкой графа.
Никаких исключений в kernel по имени цели.

Task schema — `ddd-accounting-12`, SQLite user_version=12. Schema 11 не поддерживается;
автоматической миграции нет. Optional telemetry использует явно выбранные отдельные database/lock.
