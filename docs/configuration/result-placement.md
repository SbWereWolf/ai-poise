# Размещение рабочих результатов

## Назначение и границы

Команда `poise placement` выбирает и проверяет место результата по политике выбранного
проекта. Агент заранее объявляет результаты собственной работы и вызываемых инструментов:
назначение, получателя, срок использования и имя. `prepare` закрепляет допустимые места;
`check` проверяет явно выбранные пути по текущим условиям. Обе операции доступны без Task.

Политика определяет категории и правила, а не фиксированный общий каталог. Версионируемые
исходники и документация принадлежат продукту; конфигурация установки, данные, резервные копии,
создаваемые зависимости и индекс исходников — локальному хранению соответствующего продукта.
Временные материалы агента и передаваемые отчёты получают собственные корни, получателя и срок.
Материалы Task/Sprint используют подключённого владельца текущей работы.

Закрепление — декларация в пространстве caller и checkout, а не глобальная исключительная
аренда файла. Команда не создаёт сам результат, не перехватывает автоматически другие инструменты,
не подключает hooks, не отправляет сообщения, не меняет `.gitignore` или Git index.
`lifetime` участвует в выборе правила, но не запускает удаление или истечение разрешения.
Право менять содержимое, регистрировать неизменяемые доказательства и публиковать результат
остаётся у соответствующих владельцев. Обычная запись исходника не требует регистрации его
как immutable artifact. См. [разделение хранения](storage-layout.md#назначение-и-состояние).

## Подготовка проекта и вызов

Нужны установленная поставка Poise, полностью настроенный проект и его зарегистрированный
Git checkout. Используйте [публичную подготовку проекта](project-setup.md), включая обязательные
workflow-документы, `runtime_resources` и связь `project_setup`. Отсутствие текущей Task допустимо;
физическое удаление Task-плагина из поставки этим контрактом не поддерживается.

`--config`, `--checkout`, `--policy` обязательны и принимают абсолютные пути. Checkout должен
быть корнем Git working tree, зарегистрированным в том же Git common directory, что и
`git.repository` проекта. Выбор другой папки не переключает установленный код инструментов.
Рабочая политика и данные находятся вне VCS; managed-конфигурацию проекта меняют через её
публичного владельца, а не ручной правкой рабочего manifest.

```bash
poise=( "${poise_python:?Абсолютный путь установленного Python Poise}" -I -B -m poise )
"${poise[@]}" placement --config "$project_json" --checkout "$checkout" \
  --policy "$placement_policy" < "$placement_packet"
```

Все четыре переменные путей оператор задаёт явно; `placement_packet` содержит один JSON
[описанного ниже формата](#пакет-prepare-и-check). Это отдельный CLI-вход, не Work-пакет
`operation/input/messages`. Передавайте полный stdout машинному потребителю.

Caller берётся из подлинного `CODEX_SESSION_ID`/`CODEX_THREAD_ID` либо из существующего механизма
`POISE_CALLER_BINDING`: абсолютного постоянного файла с уже существующей родительской папкой.
Без native identity этот механизм может создать binding при первом вызове. Native identity
и binding одновременно запрещены. Не подставляйте чужие значения и не используйте
`POISE_SESSION` для имитации caller. Даже `check` может инициализировать caller binding;
его read-only гарантия относится к placement state, а не ко всем внешним эффектам запуска.

## Политика размещения

Файл — UTF-8 JSON. Все известные поля обязательны; неизвестные опции конфигурации игнорируются
без удаления исходных значений. Хеш политики учитывает все исходные байты, включая неизвестные
поля и форматирование. Request, state и result имеют строгую форму.

| Поле | Значение |
|---|---|
| `schema` | Точно `poise-placement-policy-1`. |
| `version` | Непустая строка версии оператора; порядок версий команда не интерпретирует. |
| `roots` | Непустой массив корней с уникальными `id`. |
| `rules` | Непустой массив правил с уникальными `id`. |
| `owner_provider` | Явный `null` или `"poise"`. |
| `state` | Настройки отдельного placement state. |

Каждый корень содержит:

| Поле | Значение |
|---|---|
| `id` | Непустой идентификатор, используемый правилами и разрешениями. |
| `owner` | `product`, `harness`, `task` или `sprint`. |
| `path` | Абсолютный путь для product/harness; ровно `null` для task/sprint. |
| `versioning` | `versioned` или `ignored`; классификация, а не автоматическая настройка Git. |
| `authority` | Непустая ссылка на основание согласованного корня. |

Пути product/harness приводятся к абсолютному разрешённому filesystem path. Владелец
product/harness в ответе имеет `id` выбранного проекта. Для task/sprint фактические `id` и корень
предоставляет текущий владелец; оператор не записывает их вручную в политику.

Каждое правило содержит:

| Поле | Значение |
|---|---|
| `id`, `category` | Непустые идентификатор правила и категория результата. |
| `priority` | Целое число, включая отрицательное; boolean не является целым при проверке. |
| `when` | Объект `purposes`, `recipients`, `lifetimes`: массивы уникальных непустых строк. |
| `root` | `id` существующего корня. |
| `directory` | Относительный каталог для выбора пути; `""` означает сам корень. |
| `paths` | Непустой массив уникальных допустимых относительных component glob patterns. |

Все три оси `when` соединены через AND; пустой массив по оси допускает любое значение.
Значения сравниваются точно. Среди подходящих правил выбирается единственное с наибольшим
`priority`; отсутствие и равенство приоритетов дают диагностику. `directory` определяет
автоматически предложенный путь, а `paths` проверяет весь путь относительно корня.
`*` сопоставляет один компонент, `**` — ноль или больше компонентов: `src/*/report.py`
допускает один вложенный каталог, `src/**/report.py` также допускает `src/report.py`.

Относительные пути состоят из непустых компонентов через `/`, без `.`, `..`, ведущего `/`,
backslash, двоеточия и управляющих символов. В обычных именах/путях также запрещены
`* ? [ ]`; в policy patterns эти символы допустимы для сопоставления компонента.

`state.directory` — абсолютная папка внутри настроенного `paths.state` проекта.
`state.filename` и `state.lock` — различные допустимые basename. Лимиты переиспользуются
из проекта: `batch.max_input_bytes` ограничивает JSON stdin, `batch.max_items` — число items,
`batch.file_mode` — режим записи состояния, `limits.lock_seconds` и `limits.lock_poll_seconds` —
ожидание блокировок, `limits.git_seconds` — Git-проверку checkout. Отдельных скрытых лимитов
placement нет.

## Пакет prepare и check

Пакет содержит ровно `operation`, `items`, `authorizations`. `operation` — `prepare` или
`check`. `items` — от одного до `batch.max_items` элементов с уникальными ключами;
`authorizations` — массив, в том числе пустой.

```json
{
  "operation": "prepare",
  "items": [
    {
      "key": "report",
      "purpose": "documentation",
      "recipient": "product",
      "lifetime": "versioned",
      "name": "report.md",
      "path": null
    }
  ],
  "authorizations": []
}
```

Каждый item содержит ровно шесть полей. `key` соответствует `[A-Za-z0-9._-]+`, кроме `.` и
`..`; `purpose`, `recipient`, `lifetime` — непустые строки, используемые политикой.
`name` — допустимый basename. `path` — допустимый относительный путь с последним компонентом
равным `name`. Только `prepare` принимает `path:null`: выбранное правило добавляет `name`
к `directory`. `check` требует явный путь и не переносит его на автоматически выбранный.

Предварительно объявляйте все ожидаемые outputs, включая вывод вызываемых инструментов.
Одна batch-проверка оценивает все items. При частичном отказе `prepare` не добавляет новые
закрепления и разрешения; допустимая отдельная строка ещё не означает успех всего пакета.
Команда не пишет содержимое объявленных файлов.

## Согласования и владельцы

При первом допустимом для разбора `prepare` сохраняется baseline фактических имён первого
уровня checkout, включая файлы и `.git`. Это исходная область размещения, а не право менять
содержимое. Последующее создание папки, изменение ignore или tracking не расширяет baseline.
Если корень `product` совпадает с выбранным checkout, неизвестный элемент первого уровня
требует предметного согласования. Запрет текущего правила действует и для старого закрепления.
Явно настроенные внешние product/harness корни уже имеют своё основание `authority`.

Каждое разрешение содержит ровно следующие поля:

```json
{
  "reference": "decision:approved-report-area",
  "root": "product",
  "prefix": "reports",
  "purposes": ["documentation"],
  "recipients": ["product"],
  "lifetimes": ["versioned"]
}
```

`reference` ссылается на реальное полученное решение; строка сама по себе не является
криптографическим доказательством или согласием пользователя. Boolean вместо разрешения
не принимается. `root` существует в текущей политике; `prefix` — непустой относительный путь.
Массивы scope непусты и содержат уникальные непустые строки. Должны совпасть корень,
точный prefix либо его потомок по границе `/`, а также все три смысловые оси.
`reports-extra` не является потомком `reports`.

Идентичные разрешения объединяются; один набор `(root,prefix,reference)` с различным scope
отклоняется. Сохраняются только использованные разрешения принятого `prepare`. Сохранённое
согласование не отменяет проверку текущей политики, владельца и пути.

При `owner_provider:null` обычные product/harness правила работают без Task; task/sprint
правила дают `owner_disabled`. При `"poise"` адаптер только читает существующее хранилище:
требуется действительная нетерминальная Task, принадлежащая текущему caller, и для sprint —
её действительное членство. Отсутствие, несовместимость или недоступность этих сведений даёт
`owner_unavailable`; новая Task/DB/session не создаётся. Конкретный Task/Sprint root вычисляет
его существующий владелец, а не таблица рекомендуемых имён папок.

## Ответ и состояние

Обычный JSON-ответ содержит ровно `schema`, `status`, `project`, `checkout`, `policy_sha256`,
`state`, `items`, `diagnostics`. `schema` — `poise-placement-result-1`; `checkout` — разрешённый
путь выбранной копии; `policy_sha256` — SHA-256 исходных байтов политики.

| `status` | Exit | Значение |
|---|---|---|
| `ready` | 0 | Все строки допустимы, операция завершена. |
| `needs_agreement` | 1 | Для продолжения не хватает только предметного согласования. |
| `needs_inputs` | 1 | Есть иная диагностика; имеет приоритет над дефицитом согласования. |
| `rejected` | 2 | Нарушен входной контракт; форма ответа описана ниже. |

Каждая строка `items` содержит `key`, `status` (`allowed`, `denied`, `needs_agreement` или
`needs_inputs`), `category`, `rule`, `root`, `versioning`, `owner`, `path`, `absolute_path`,
`reserved`, `authorization_refs`. Неопределённые значения равны `null`; `owner` — `null`
либо объект `kind/id`. Строки отсортированы по key, ссылки разрешений уникальны и отсортированы.
`reserved:true` у успешного `prepare` означает подтверждённую запись; у `check` — наличие
совместимой сохранённой декларации. `check` может вернуть `ready` и `reserved:false` для
допустимого ещё не закреплённого пути. При неподтверждённой записи новые результаты не
объявляются закреплёнными.

`diagnostics` содержит объекты `key`, `code`, `field`, `action`; общий отказ имеет `key:null`.
Порядок детерминирован: общие ошибки, затем ключи items, code, field и action.

`state` показывает:

| Поле | Значение |
|---|---|
| `path` | Абсолютный путь файла состояния этого caller/checkout. |
| `before_sha256` | Хеш прочитанного до операции файла или `null`. |
| `after_sha256` | Хеш намеренной записи; у `check` всегда `null`. |
| `observed_sha256` | Хеш реально прочитанных байтов после операции; `null`, когда байты неизвестны/отсутствуют. |
| `effect` | `none`, `unchanged`, `committed` или `unconfirmed`. |
| `confirmation` | `not_applicable`, `confirmed` или `unconfirmed`. |

Хеш — 64 lowercase hex символа. `null` не доказывает отсутствие эффекта.
`check` не создаёт placement baseline/state, не обновляет закрепления и не выполняет их fsync:
`effect:none`, `confirmation:not_applicable`. Операционные resource locks остаются у своих
владельцев. Первый корректно разобранный, но недопустимый `prepare` может сохранить только
baseline без новых reservations/grants. Отказ для существующего состояния сохраняет его байты
и может подтвердить старую запись через fsync.

Физический JSON state содержит ровно `schema:poise-placement-state-1`, `project`, `checkout`,
`caller_key`, `baseline:{entries:[...]}`, `authorizations`, `reservations`. Путь:

```text
<state.directory>/<existing caller key>/<sha256 canonical checkout>/<state.filename>
```

Используется существующий ключ caller; это не новая session identity, Task DB или журнал
попыток. Baseline отсортирован и уникален. Reservations отсортированы по key и содержат
исходные `key/purpose/recipient/lifetime/name`, `root/owner/path/absolute_path` и производные
`category/rule/versioning/authorization_refs`. `owner` содержит ровно `kind/id`.
Разрешения нормализованы и отсортированы. Запись — канонический UTF-8 JSON с `ensure_ascii=False`,
сортировкой ключей, compact separators и одним LF. Учёт и вычисление хешей выполняет команда;
агент не ведёт параллельный реестр вручную.

## Отказы и повтор

Повтор оценивает текущие доступные входы и состояние: сохраняет посторонние действительные
декларации, повторно проверяет политику/владельца/согласование. Изменение исходного смысла key,
владельца, корня или места вызывает `reservation_conflict`; совместимое обновление производных
category/rule/refs допускается. Конфликт одного места с другим несовместимым назначением даёт
`destination_conflict`. Исторического request ID и сравнения с неизвестным прошлым состоянием
нет.

Если полный намеренный канонический образ равен текущим байтам, `prepare` подтверждает файл
и его родительскую папку через fsync без замены (`unchanged/confirmed`). Иначе существующий
atomic writer заменяет файл (`committed/confirmed`). До replace при отказе остаются старые
байты; после replace отказ fsync папки может оставить видимыми новые байты с
`unconfirmed/unconfirmed`. Равенство `observed_sha256` и `after_sha256` не доказывает durability.
Неудачный readback также означает неподтверждённый результат; неизвестный observed хеш — `null`.

Сохраните полный ответ и явно повторите `prepare` после устранения причины. Новый вызов проверит
актуальные данные и подтвердит либо изменит текущий образ; автоматического повтора нет.
`check` показывает видимое состояние, но не подтверждает durability. При повреждении state
сначала сохраните свидетельства и выясните причину через владельца; восстановление ведите
по [правилам аудируемого обхода](../governance/development-rules.md#сбой-harness-и-ручной-обход).
Не удаляйте state для сброса baseline или снятия чужих закреплений.

| Code | Action | Действие оператора |
|---|---|---|
| `invalid_request` | `provide:request` | Исправить точную форму/типы/лимит пакета и scope разрешений. |
| `invalid_paths` | `provide:paths` | Исправить basename, относительный путь и их согласованность. |
| `invalid_caller` | `provide:caller` | Восстановить подлинный native caller либо разрешённый binding. |
| `invalid_project` | `provide:config` | Восстановить полную конфигурацию и связь runtime resources. |
| `project_binding` | `select:checkout` | Указать зарегистрированный корень нужного репозитория. |
| `unreadable_policy` | `restore:policy` | Восстановить чтение явно выбранного файла. |
| `invalid_policy` | `correct:policy` | Исправить известные обязательные поля, корни и state directory. |
| `unmapped_intent` | `configure:policy` | Согласовать правило для указанного назначения. |
| `ambiguous_rules` | `configure:policy` | Устранить равенство приоритетов подходящих правил. |
| `path_not_allowed` | `choose:placement` | Выбрать путь внутри текущих patterns. |
| `approval_required` | `agree:<root>:<top entry>` | Получить реальное scoped разрешение для нового места. |
| `owner_disabled` | `enable:owner_provider` | Подключить владельца через явную настройку политики. |
| `owner_unavailable` | `provide:task_owner` или `provide:sprint_owner` | Восстановить фактическое текущее владение через его владельца. |
| `reservation_conflict` | `choose:new_key` | Сохранить исходную декларацию и выбрать новый ключ для другого результата. |
| `destination_conflict` | `choose:placement` | Выбрать совместимое место без коллизии деклараций. |
| `state_missing` | `prepare` | Сначала выполнить разрешённое предварительное объявление. |
| `state_lock` | `retry:prepare` или `retry:check` | После освобождения штатной блокировки явно повторить свою операцию. |
| `state_read` | `inspect:state` | Проверить доступность файла, сохранив свидетельства. |
| `invalid_state` | `inspect:state` | Проверить строгую форму и принадлежность состояния; использовать владельца восстановления. |
| `state_write` | `retry:prepare` | Устранить отказ записи/подтверждения и явно повторить prepare. |

В таблице альтернативы `или` зависят от фактической операции/владельца; wire action содержит
одно значение. `rejected` имеет ровно `schema`, `status`, `error:{code,field,action}`,
без обычных items/state. Ошибки CLI arguments до входа в обработчик используют обычные
stderr/exit argparse, а не обещанный JSON rejected.

## Пример и проверка

[Обезличенный пример политики](../../config/examples/result-placement.example.json) содержит
явные tokens `@CHECKOUT@`, `@PRODUCT_DATA@`, `@WORK_ROOT@`, `@HANDOFF_ROOT@`, `@HARNESS_DATA@`.
Скопируйте его в рабочее ignored-хранение и замените каждое вхождение на согласованные
абсолютные пути. Runtime не раскрывает tokens. `@HARNESS_DATA@/placement` должен попадать
в `paths.state` проекта; корни продукта, работы и передачи задаются независимо.
`owner_provider:null` оставляет обычные сценарии независимыми от Task; для task/sprint
правил подключите `"poise"` и действительного владельца. Широкие `paths:["**"]` — стартовый
пример, оператор определяет согласованные patterns конкретного проекта.

Пример содержит отдельные правила для source, documentation, installation-config,
installation-data, backup, generated-dependency, code-index, agent-work, handoff,
task-material и sprint-material. Значения purpose/recipient/lifetime — данные этой политики,
а не скрытый глобальный словарь команды. Для приведённого выше пакета `prepare` предлагает
`docs/report.md`; затем передайте тот же item с `operation:"check"` и
`path:"docs/report.md"`. Действующий baseline должен содержать docs либо требуется настоящее
разрешение. Успешный check подтверждает допустимость выбранного места, а не наличие файла.

Исполняемый consumer `tests/placement/test_documentation_example.py` читает именно поставляемый
пример, заполняет paths, выполняет настоящий CLI prepare с проверкой полного состояния, затем
read-only check. Он дополняет сценарии placement и проверки существующих владельцев artifacts,
caller, instruction preparation и bounded smoke. Ссылки и точные заголовки проверяет
[существующий documentation
checker](../workflows/documentation-checks.md#проверка-ссылок-и-точных-заголовков);
проверка ссылок не заменяет поведенческое исполнение примера.
