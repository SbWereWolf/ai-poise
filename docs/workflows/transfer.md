# Перенос сохранённой работы между хранилищами

Редакция: **2026-09-07T00:25:38+05:00**. Срез **POISE-DDD-07B**.

## Назначение и граница

Одна декларативная операция сохраняет выбранную работу в переносимый пакет. Вторая принимает пакет в явно настроенную среду. Агент не копирует таблицы, не правит пути внутри БД и не создаёт worktrees вручную.

Поддерживается пакет самостоятельных задач либо **целый опубликованный спринт** со всеми участниками. Участники могут быть ещё не начаты, завершены, отменены или сохранены через handoff. Чужая активная задача не освобождается автоматически. Пакет содержит только выбранных владельцев; независимая работа в исходной и принимающей БД не заменяется.

В этой версии импорт создаёт отсутствующих владельцев. Если task/sprint с таким ID уже существует, возвращается конфликт без автоматического merge/замены. Это распространяется и на возвращение задачи в её исходный store: обновление существующего владельца по общему baseline пока не реализовано. Частичная синхронизация спринта, применение миграций и автоматическая внешняя доставка не входят в срез.

## Пакетный API

Обычный `poise work` принимает один объект `operation/input/messages`. `operation` — `transfer`.

Экспорт уже сохранённых самостоятельных задач:

```json
{"operation":"transfer","input":{"action":"export","request_id":"export-01","task_ids":["T1","T2"],"sprint_id":null,"handoff":null},"messages":[]}
```

Экспорт текущей работы вместе с её сохранением:

```json
{"operation":"transfer","input":{"action":"export","request_id":"export-02","task_ids":null,"sprint_id":null,"handoff":{"request_id":"checkpoint-02","reason":"Продолжить в другой среде","result":null,"commit_message":"WIP: preserve current work","artifact_paths":[]}},"messages":[]}
```

`result` может содержать пакет незавершённого результата; `null` сохраняет уже зарегистрированное состояние. Для непустого изменения Git требуется содержательное сообщение коммита по правилам проекта. `handoff` вызывает существующую библиотеку, а не второй механизм сохранения.

Для всего спринта указать его `sprint_id`, а `task_ids` — явно `null`. Если текущая задача передаётся вместе со спринтом, она должна входить в него; остальные активные владельцы должны быть предварительно корректно освобождены.

Ответ содержит `package_path`, `package_digest`, `task_ids`, `sprint_ids` и признак повтора. `delivery=local_package_only` не означает загрузку в Gmail или другое внешнее хранилище.

Импорт:

```json
{"operation":"transfer","input":{"action":"import","request_id":"import-01","package_path":"/absolute/input/work.zip","package_digest":"<точный SHA-256 из результата экспорта>"},"messages":[]}
```

После импорта обычный `bootstrap` выбранного ID возвращает текущую работу. Импорт сам не переключает уже активную задачу принимающего агента и не начинает следующий этап. Повтор принятого пакета не откатывает дальнейший прогресс.

## Конфигурация

Полный раздел `runtime_services.transfer` обязателен. Пример задан в `config/runtime.example.json`: каталог операций, имена архива/manifest/SQLite, каталоги файлов и bundles, пределы количества задач/файлов/байтов, размер блока копирования и режим файла. Отсутствующее поле — ошибка. Примеры значений не являются встроенными значениями по умолчанию.

Принимающая среда использует **свой** существующий конфиг проекта. Пакет не устанавливает конфиги, секреты, плагины или зависимости. Для этого среза сохраняется одинаковая политика исполнения; различаться могут физические пути store/repository и расположение файлов process packs. Конкретный process snapshot задачи переносится без подмены актуальным шаблоном.

Точные команды и значения их параметров не переписываются. Если команда ссылается на отсутствующий interpreter, внешний сервис или внешний файл, принимающая среда должна быть подготовлена для этой команды. Файлы вне выбранных task/sprint roots и Git-объектов автоматически не собираются.

## Содержимое пакета

- SQLite текущей схемы, содержащая только выбранные задачи/спринт, их слои, методы, findings/resolutions, доказательства, события и привязанные пользовательские сообщения.
- Все обычные файлы выбранных task/sprint roots, в том числе raw output и материализованные представления.
- Самодостаточный Git bundle для каждого начатого рабочего дерева, с точным HEAD и необходимой историей.
- Manifest состава, исходной политики, владельцев, зафиксированных состояний и контрольных сумм.

Сессии, внешние runtime bindings/cursors и независимые задачи в пакет не входят. Символические ссылки не обходятся. Зарегистрированный артефакт должен совпадать со своим прежним digest, а не только с вновь созданной копией. Игнорируемые внешние конфиги приложения в Git bundle не входят.

Пакет не зашифрован. Он содержит выбранные исходники и результаты. Не помещать секреты в содержательные секции и артефакты; не считать файловую проверку целостности средством удаления секретов. Внешняя передача выполняется только выбранным пользователем способом; этот инструмент сам её не делает.

## Возобновление и актуальность

Тексты секций и аргументов не изменяются из-за переноса. Меняются только технические привязки физического расположения. Полные исходные receipts и файлы представлений сохраняют исходное содержимое; читающий адаптер разрешает их старые пути в новые task/sprint roots. Артефакт получает устойчивый ID из scope, owner и относительного пути, а не физического корня машины.

Сохранённая проверка — **историческое evidence исходной среды**, не утверждение, что команда уже исполнена на новой машине. Активная итерация при `verify` получает новый execution key из нового cwd/окружения и выполняет необходимые команды. Перенесённый уже verified этап остаётся предъявленным результатом прежней среды; его принятие — отдельное решение пользователя. Для новых наблюдений выполняется явная новая работа/rework.

Новая сессия получает ту же позицию процесса и тот же исходный Git baseline. Связь предыдущего handoff переносится без активного source claim. Счётчики итераций и лимиты не обнуляются. Пользовательские message identities сохраняются, поэтому повтор импорта не увеличивает счётчик.

Числовые SQLite submission IDs локальны. При импорте они переназначаются вместе с FK, чтобы не столкнуться с существующими записями другой задачи. Стабильные task, finding, argument и receipt IDs не заменяются.

## Согласованность и ошибки

1. Экспорт фиксирует выбранные данные под короткой внешней блокировкой store. Копирование файлов/Git происходит вне SQL-транзакции. Перед упаковкой проверяются неизменность выбранного состояния и файлов.
2. Импорт проверяет SHA-256 архива, состав, размеры, все файлы, текущую SQLite schema и FK. Неожиданные пути/ссылки, недостающий файл и несовместимая политика отклоняются.
3. До подготовки назначений проверяется отсутствие всех task/sprint ID и веток. Перед filesystem/Git работой сохраняется намерение импорта.
4. Файлы и рабочие деревья подготавливаются без перезаписи чужого содержимого. Повтор известной незавершённой операции проверяет их, а не сбрасывает.
5. Владельцы публикуются в одной короткой SQL-транзакции через Task/Sprint repositories. При ошибке SQLite нет частично видимой задачи или графа. Подготовленные файлы остаются для безопасного повтора; общей атомарности Git/filesystem/SQLite не заявляется.

Сбой сохранения перед экспортом может оставить уже корректно handed-off работу без готового архива. Это не потеря работы и не повод откатывать handoff: следующий вызов экспорта сохраняет её. Копии БД на разных машинах не создают распределённый lock; пользователь по принятому правилу не запускает одну задачу одновременно в двух копиях.

## Основания реализации

SQLite backup/snapshot относится к БД, не к произвольным внешним файлам: https://sqlite.org/backup.html . В этой реализации создаётся новая SQLite **текущей схемы** из согласованного выбранного набора записей; старые схемы не преобразуются.

Git bundle переносит Git-объекты и refs, но не состояние внешней среды: https://git-scm.com/docs/git-bundle . Рабочее дерево в destination создаётся из точного сохранённого коммита.

Пример полностью локален. Успех CLI-demo не объявляет живые ChatGPT hooks, JetBrains или Gmail подключёнными.
