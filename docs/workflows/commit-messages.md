# Сообщения коммитов AI poise

Обновлено: **2026-10-04**. Это действующее правило написания новых сообщений,
а не требование переписать существующую Git-историю.

## Продуктовый смысл и формат 50–70

Заголовок — одна содержательная строка **не длиннее 50 символов**.
После неё — **одна пустая строка**, затем содержательное тело. Каждая строка тела —
**не длиннее 70 символов**. Это верхние пределы, не обязательная длина текста;
70 относится к каждой строке, а не ко всему телу. Считаются символы, включая
пробелы и знаки, а не UTF-8 байты. Не обрезать смысл ради длины: переформулировать
заголовок и переносить строки тела по границам слов.

И заголовок, и тело объясняют **конечный эффект изменения и его смысл**:
что теперь может пользователь или оператор, какое неверное поведение устранено,
какая гарантия или правило стало понятным и зачем это нужно. Тело уточняет сценарий,
ограничение или причину, а не повторяет заголовок другими словами.

Не перечислять изменённые файлы, функции, классы, импорты и внутренние перестановки
как содержание сообщения. Вместо «перенесён валидатор в clock.py» описать важный
результат для пользователя — например, сохранение исходного времени наблюдения
без подмены временем доставки. Коммит тестов описывает проверяемую гарантию;
коммит документации — уточнённое поведение или правило. Документация черновика
не должна выдавать запланированную функцию за уже работающую.

Пример сообщения о гипотетическом исправлении повторной отправки:

```text
Повтор отправки больше не создаёт дубликаты

После сбоя пользователь может безопасно повторить отправку.
Уже сохранённый результат не создаётся повторно.
```

Неподходящие сообщения: «обновлены файлы», «добавлен класс», «исправлен импорт»,
«рефакторинг runner». Они не объясняют конечный эффект и его значение.
Новый обязательный префикс, нумерованный список тела или подпись AI-автора этим
правилом не вводятся; существующие требования к авторству сохраняются отдельно.

## Запуск и границы полномочий

Обычный Task-процесс использует существующий `commit_message` в своём допустимом
пакете результата и владеющую коммитом операцию Poise. Передавать туда полный текст
с теми же ограничениями, не создавать второй коммит после штатного сохранения.
Полномочия на коммит, приёмку и интеграцию остаются разными; правило оформления
не отменяет [Git-ограничения репозитория](../governance/development-rules.md#общие-правила-агентов).

При публичной локальной интеграции передавайте отдельные `authorization` и `commit_message`:
первое фиксирует разрешение, второе содержит полный заголовок и тело. Сообщение сохраняется
целиком для создаваемых интеграционных коммитов, конфликтов и возобновления; при повторе
с тем же идентификатором сохраняйте оба исходных значения. Настроенный `git.commit_pattern`
проверяет всё сообщение до операций Git. Продуктовый смысл и длину 50–70 проверяет автор;
автоматическая проверка этих правил не добавлена. Не сокращайте сообщение
и не подменяйте его разрешением ради прохождения правила. Точный пакет, оформление завершающего
перевода строки Git и отказы определены в
[контракте интеграционного сообщения](batch-work.md#разрешение-и-сообщение-интеграционного-коммита).
Для старого запроса без записанного сообщения действуют
[отдельные ограничения восстановления](batch-work.md#сохранённый-запрос-без-сообщения-коммита).

Для явно разрешённого прямого коммита, после проверки `git status` и
`git diff --cached` и выбора только относящихся к работе файлов, короткий пример:

```bash
git commit -m 'Коммиты объясняют результат для пользователя' \
  -m 'По сообщению понятны конечный эффект и смысл изменения.'
```

Два `-m` отделяют заголовок от тела пустой строкой. Это пример существующей команды
Git, **не новый safe-commit wrapper и не автоматический валидатор**: длину и смысл
перед запуском проверяет автор. Команда фиксирует уже подготовленный index;
она не выбирает безопасный scope за агента. Не использовать `git add .` или
`git commit -a` для захвата чужих изменений. Для длинного тела передать заранее
проверенный UTF-8 файл через `git commit -F /конкретный/путь/к/сообщению.txt`.
Образец не разрешает обход штатного lifecycle активной Task, переписывание принятого
коммита, изменение чужой рабочей копии или `git push`.

## Что взято из ERP safe-commit

В предоставленном ERP-архиве `safe-commit` ссылается на
`ai-assistant/agent/commit.sh`; тот вызывает `commit-with-message.sh`.
Просмотренный helper ограничивает заголовок 50 символами, создаёт пустую строку
и переносит тело с шириной **72**. Для AI poise действует последнее прямое
требование пользователя — **70**, а не 72. Правило продуктового смысла задано
пользователем; проверка длины сама по себе не оценивает содержание.

ERP wrapper также связан с его runtime, Task delivery, списками исключений и
форматированием. Эти зависимости не перенесены ради оформления сообщений;
существующий владелец коммита Poise не заменяется. В этом документационном срезе
нет нового commit hook или автоматической проверки смысла и формата 50–70. Существующая
проверка настроенного выражения при интеграции описана выше. Дополнительную автоматизацию
нужно отдельно согласовать и проверить, а не описывать как уже установленную.
