# Ретроспектива устаревших передач ERP-MERGE-RESIDUALS-001

## Происхождение и пределы доказательств

Служебные материалы задачи удалены. Служебные журналы уничтожены.

Первоначальный файл `DELIVERY-HANDOFF-INCIDENT.json` был указан в реестре
известных багов внутри удаляемого каталога задачи. На 16 октября 2026 года
этот каталог отсутствует. Подлинный первичный снимок ручного исправления
не восстановлен; текущие данные не выдаются за его замену.

[Сохранившаяся история](surviving-history.json) получена из действующей
SQLite-базы в режиме `mode=ro` и `query_only`, без изменения данных.
Она содержит буквальные значения сохранившихся строк задачи, передач,
событий и общего журнала. SHA-256 файла:
`bbea04443e87478e706844027df6ec6f5c50cc91953e53c5501a197c35e09a72`.

Наблюдаемое состояние: задача `completed`, версия `121`, владелец отсутствует.
Строки передач `882` и `1174`, соответствующие историческим версиям `5`
и `38`, имеют состояние `recovered`. Это подтверждает нынешнее состояние
и сохранённые идентичности, но само по себе не доказывает точные байты
первичного снимка или все проверки первоначального ручного исправления.

Сохранены также подлинные ответы публичного API из внешнего runtime-каталога:

- [До коррекции](before-correction-response.json): задача завершена, но поставка
  заблокирована ожидающей передачей.
- [После коррекции](settle-response.json): требуется интеграция.
- [Завершение поставки](delivery-complete-response.json): поставка завершена,
  служебные материалы удалены.

Это сохранившиеся ответы, а не восстановленный первичный снимок.

Для нового случая той же ошибки в
[ERP-HARNESS-MODULARITY-001](../erp-harness-modularity-001-20261016/README.md)
исходные строки, настоящий журнал проверок и квитанции сохранены заранее,
до восстановления и удаления материалов задачи.

## Сохранённое направление исходного ремонта

Владелец ошибки `DELIVERY-STALE-HANDOFF-001` — исходники Poise.
Первоначальный черновик не имел native-регистрации; его удалённый файл
не объявляется доступным. Сохраняемое направление: выбор доступной
передачи должен учитывать последующие настоящие возобновления и изменения
состояния задачи, сохраняя историю и отдельное владение.

Новая native-задача и новый рабочий процесс этим документом не создаются.
Точечный обход исправляет только установленные устаревшие ссылки;
неизвестный исход внешней проверки требует отдельного решения и не
подменяется вымышленной квитанцией.
