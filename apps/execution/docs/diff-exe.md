# Договор сравнения изменений этапа

## Статус и владельцы

Это договор следующей реализации Git adapter Execution. Текущий provider поставляет
[process, setup, gate, files/check и чтение](shell-exe.md#запуск).
Описанные здесь `files/diff`, `query/file_diff_result` и компонент конфигурации `git`
предназначены для последующей реализации. Наличие этого документа и примеров
подтверждает проект договора; выполнение будущего интерфейса ими не доказывается.

Существующий исходный процесс сравнения использует сохранённый `entry_tree`,
наблюдаемый net-снимок файлов и `git diff --name-only --no-renames -z`.
Договор сохраняет этот смысл и уточняет состав будущего коммита. Execution владеет
наблюдением, применением [правил этапа](files-exe.md) и собственным решением.
Sequencing сохраняет владение [физическим
Workspace](../../sequencing/docs/contract-seq.md#60-реализованная-подготовка).
Вызвавший передаёт его публичные `workspace_id`, `kind`, `position`, `path`.
Владелец жизненного цикла этапа передаёт действительную исходную версию этапа.

Проверка решения и физический коммит — отдельные действия. Решение само по себе
сохраняет состояние Task, текущий этап, generation и iteration. Integration остаётся
обычным этапом: допуск записи в main определяется явным правилом выбранного этапа.

## Исходная версия и два сравнения

Для одного запроса выберите один объявленный корень `{kind,position}` из сохранённого
`file_policy` контекста gate. Его путь должен обозначать корень настоящей рабочей
копии Git: имена Git и имена относительно корня политики тогда имеют один смысл.
Для нескольких корней используйте отдельные явные запросы. Дополнительные корни
Workspace сами по себе не объявляют отдельные Git repositories.

Передайте `baseline_ref` от владельца выбранного этапа. Он обозначает commit либо
tree, разрешаемый Git в исходное дерево при новом запросе. Сохраните разрешённый
`baseline_tree` в результате. Git IDs служат ссылками сравнения; отдельные хэши
содержимого файлов для этого договора не нужны.

| Момент процесса | Смысл исходной версии в существующем владельце |
| --- | --- |
| Первичная подготовка | Дерево чистой рабочей копии на сохранённой исходной версии Task |
| Обычный переход этапа | Проверенное дерево принятого предыдущего результата |
| Новый запуск после restart | Дерево сохранённого HEAD в момент запуска; существующий грязный WIP сохраняется отдельно |
| Явный rework | Текущее наблюдаемое дерево, переданное владельцем при согласованном переходе |

Сохранённая исходная версия этапа, creation base Task и текущий HEAD — разные факты.
Для проверки используйте ссылку действительного этапа. Переход на другую исходную
версию выполняйте через его владельца; повторный активный bootstrap её не обновляет.

Кандидат представляет текущие файлы рабочей копии в смысле существующего Git-снимка:
временный индекс отдельного вызова загружается из HEAD, получает `add --all`, затем
записывается дерево. Реальный индекс, пользовательские файлы и HEAD сохраняются.
Временный индекс и обычные объекты Git могут создаваться в ходе наблюдения.

Отдельное staged-содержимое реального индекса в такой снимок не копируется.
Если индекс содержит B, а рабочий файл C, кандидат содержит C. Обычные неигнорируемые
новые файлы участвуют; игнорируемые untracked-файлы остаются на диске вне кандидата.
Это наблюдение net-состояния, а не две независимые публикации staged/unstaged.

| Результат | Сравнение |
| --- | --- |
| `stage_paths` | Исходное дерево этапа → дерево кандидата |
| `commit_paths` | Дерево независимо наблюдаемого текущего HEAD → тот же кандидат |

Оба списка содержат уникальные относительные имена, отсортированные по Unicode code
point. Используется NUL-разделённый вывод без распознавания переименований: перенос
файла представлен старым и новым именем. Удалённое имя остаётся изменённым путём,
хотя обычного файла по нему уже нет. Изменение режима или вида записи учитывается
как изменение Git-дерева по имени.

Для допуска применяется WRITE-правило этапа к отсортированному объединению обоих
списков. Каждый путь проверяется один раз. Это сохраняет обе границы: изменение
этапа может отсутствовать в будущем коммите после компенсации относительно HEAD,
а коммит может содержать WIP, существовавший до входа в этап.

Результат `allowed` означает допуск всех решений объединения; пустое объединение
даёт true. `read_only` запрещает непустое объединение. Разрешения и исключения,
роль и решение для main берутся из сохранённого процесса и `file_policy` выбранного
этапа. Имя этапа само по себе разрешений не добавляет.

## Запрос и результат

Верхний пакет имеет ровно `schema: "stride-execution/v1"`, `operation: "files"`,
`input`. Для `input` предусмотрены точные поля:

| Поле | Значение |
| --- | --- |
| `action` | `diff` |
| `request_id` | Новый непустой собственный ID запроса |
| `expected_revision` | Актуальная неотрицательная целая revision собственного store |
| `task_id`, `generation`, `context_id` | Каноническая Task, её положительное поколение и существующий собственный контекст с `file_policy` |
| `stage_id` | Этап сохранённого процесса |
| `root` | Ровно `{kind,position}` объявленного корня политики |
| `baseline_ref` | Непустая действительная ссылка Git от владельца исходной версии этапа |

[Шаблон запроса и независимые примеры](examples/stage-diff-cases.json) содержат
точные поля. В `request_template` подставьте значения из своего настроенного
исполнения, актуальную revision и действительную ссылку этапа. Сохраните числовые
типы generation/revision. Запрос применяется к поставке, реализующей этот договор.
Список изменённых путей вычисляет adapter, вызывающая сторона передаёт контекст.

Ответ имеет ровно следующие поля:

| Поля | Значение |
| --- | --- |
| `schema`, `status` | `stride-execution/v1`, `diff_checked` |
| `revision`, `replayed` | Общая revision после записи собственного результата и признак точного повтора |
| `task_id`, `generation`, `context_id`, `stage_id` | Выбранная собственная принадлежность решения |
| `root`, `role` | Выбранный квалифицированный корень и роль сохранённого этапа |
| `baseline_tree` | Разрешённое исходное дерево этапа |
| `head_commit`, `head_tree` | Наблюдаемые HEAD и его дерево |
| `candidate_tree` | Наблюдаемый net-кандидат |
| `stage_paths`, `commit_paths` | Два точных списка изменений |
| `decisions` | Решения WRITE для отсортированного объединения путей |
| `allowed`, `result_id` | Общий допуск и непрозрачный ID собственной записи |

Элемент `decisions` имеет ровно `root`, `path`, `allowed`, `reason`, как
[существующее файловое решение](files-exe.md#проверка-чтения-и-записи).
Причины: null, `read_only`, `denied`, `outside_allow`.
Допущенный результат имеет exit `0`, отрицательное scope-решение — exit `2`.
Оба сохраняют собственный результат. Структурный отказ или недоступный вход имеют
существующий формат `rejected` с `reason`, exit `2` и пустым stderr; исходное
бизнес-состояние, реальные файлы, индекс и HEAD сохраняются.

Сопоставление путей удаления с WRITE выполняется по имени. Допустимость обычного
файла как доказательства READ остаётся [отдельной
приёмкой](files-exe.md#приёмка-файлового-доказательства).
Она не заменяет полноту Git-сравнения и не применяется к отсутствующему удалённому
файлу вместо проверки его изменённого имени.

## Собственная запись, чтение и повтор

Producer сохраняет `file_diff_decision` через существующие владельцы record/request
и revision. Общий writer сохраняет свои [пять видов](store-exe.md#формат-факта).
Новая запись использует существующий envelope
`{task_id,kind,id,revision,generation,data}`; revision неизменного факта — `1`.

`data` имеет ровно `context_id`, `request_id`, `stage_id`, `root`, `role`,
`baseline_ref`, `baseline_tree`, `head_commit`, `head_tree`, `candidate_tree`,
`stage_paths`, `commit_paths`, `decisions`, `allowed`, `contract_revision`,
`process_ref`, `workspace_id`. Происхождение соответствует сохранённому собственному
контексту, договору и снимку процесса.

Будущий query selector имеет ровно `id`, `kind: "file_diff_result"`, `task_id`,
`generation`, `context_id`, `request_id`. Элемент ответа — `{id,kind,result}`;
`result` содержит свою запись либо null. Batch читает один снимок, корень ответа
имеет `{schema,status: "read_only",revision,replayed: false,results}`.
Чтение сохранённого решения не наблюдает файлы и Git заново.

Общий request ID разделяется с остальными мутациями Execution. Новый запрос читает
свой frozen-контекст и revision, выполняет конечное наблюдение Git вне транзакции
записи, затем собственная транзакция снова сверяет expected revision и атомарно
записывает решение/request/revision один раз. Устаревшая revision даёт отказ с
сохранением исходного состояния. Общая блокировка на время работы этапа, Git других
корней или внешних тестов этому договору не требуется.

Точный повтор передаёт прежний пакет целиком, включая старую revision. Он возвращает
исходный ответ с `replayed: true` и не наблюдает изменившиеся файлы или refs заново.
Для нового наблюдения используйте новый request ID и актуальную revision.

## Явная настройка следующей поставки

Для будущего `files/diff` предусмотрен компонент `git` с обязательными известными
параметрами. Пример его правильного заполнения:

```json
{"git":{"seconds":30.0,"observations":"git-observations"}}
```

| Параметр | Значение |
| --- | --- |
| `git.seconds` | Явное положительное конечное ограничение времени одной команды Git, секунды |
| `git.observations` | Явный непустой относительный каталог материалов наблюдения внутри `paths.state` |

Каждый вызов создаёт и удаляет только собственный временный каталог индекса.
Используйте POSIX/Linux, Python 3.13, Git в выбранном PATH и интерпретируемые UTF-8
имена файлов. Настройки process/gates и файловой политики берутся из
[действующего руководства](files-exe.md#настройка-и-объявление-политики).
Неизвестные опции сохраняются как расширения, обязательные известные значения
задаются явно. Текущая поставка ещё не реализует этот новый компонент для diff.

## Правильная работа с кандидатом и WIP

1. Выберите свой Task worktree, сохранённый контекст и действительную исходную
   версию этапа. На время проверки и намеченного коммита обеспечьте одного
   авторизованного автора изменений этого корня.
2. Получите новое сравнение и прочитайте оба списка. `allowed: true` допускает
   объявленный net-кандидат; физический коммит выполняет его владелец, проверяя
   текущий намеченный кандидат через этот договор непосредственно перед записью.
3. При лишних путях сохраните всю работу. Через её владельца перенесите постороннюю
   работу в её рабочий контекст, исправьте только разрешённые изменения текущей
   задачи и получите новое наблюдение. Действительное изменение исходной версии
   оформите обычным согласованным rework у владельца этапа.
4. Перед выбором net-кандидата для реального all-files коммита сохраните через
   владельца отдельно предназначенную staged-версию, если она отличается от рабочих
   файлов. Проверка сохраняет реальный индекс; сам коммит подготовит свой индекс
   из выбранного net-кандидата.

При пустом HEAD→candidate net-diff новый содержательный коммит не требуется;
независимое содержимое реального индекса сохраняется у своего владельца. Даже при
пустом `commit_paths` остаётся проверка `stage_paths`. Физическое выполнение и
результат коммита подтверждаются своими фактами, а не одним `allowed`.

Договор описывает наблюдение, отрицательное решение и правильную ручную коррекцию.
Автоматическое исправление рабочей копии или произвольная выборочная публикация
индекса не являются возможностями этой поставки.

## Независимые примеры и проверка договора

[13 буквальных примеров](examples/stage-diff-cases.json) задают явные entry, HEAD,
реальный index, working и ожидаемый candidate, оба списка и решения. У каждой
проверки сохраняются исходные working/index/HEAD, включая отрицательные исходы.
Пример `correction` дополнительно сохраняет работу в другом контексте; её перенос
задан условием входа, а не приписывается приложению.

Обычное изменение, удаление, перенос и новые файлы дополняются двумя различающими
случаями: `preentry-extra` содержит лишнее только в `commit_paths`,
`stage-cancellation` — только в `stage_paths`. Поэтому обе стороны объединения
имеют независимое ожидание. `index-only` и `index-working` различают staged и net,
`main-stage` содержит два выбора этапа в одинаковой файловой ситуации,
`readonly` проверяет сохранённый режим этапа.

Проверка JSON через стандартный `json.tool` подтверждает синтаксис примеров.
Существующий checker документации проверяет ссылки и точные заголовки, включая
входящие ссылки изменённых страниц. Исполнитель и независимый проверяющий
сопоставляют смысл каждого примера с исходниками и принятым анализом. Эти проверки
не объявляют будущий producer/consumer реализованным или прошедшим end-to-end тест.
