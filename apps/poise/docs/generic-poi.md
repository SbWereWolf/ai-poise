# Самостоятельные общие функции Poise

Эта страница описывает работающий `apps/poise/bin/poise-generic`: общий контекст,
проверку команд и MCP, каталог навыков, подготовку инструкций и навигацию.
Это выделенные функции исходного Poise с явными входами и собственными результатами.
Для их выполнения достаточно каталога приложения и стандартной библиотеки CPython 3.13.
Проверенная среда — POSIX/Linux. Настройте доступные внешние команды отдельно.

Вызов имеет форму `poise-generic --config PATH`. Относительный `PATH` относится
к текущему каталогу вызывающего. На stdin передайте один JSON-объект UTF-8
и закройте поток; на stdout приходит один JSON-объект UTF-8 с завершающим LF.
Обработанные исходы оставляют stderr пустым. Каждый процесс выполняет одну операцию.

Общие функции используют собственные входы без обязательных Task, Stage, Workspace
или Session. Внешний контекст подключается явным публичным вызовом его владельца.
Каталог приложения можно перенести целиком; вход добавляет в импорт только свой корень.
Отдельный [действующий вход Session](shell-poi.md) использует команду `bin/poise`
и схему `stride-poise/v1`. [Целевой договор Poise](contract-poi.md) описывает
более широкие будущие возможности.
Общие операции этой страницы используют отдельную схему `poise-generic/v1`.
[Действующий транспорт hooks](hooks-poi.md) использует эти же наблюдения
и настройки внешних действий через `bin/poise` со схемой `stride-poise/v1`.

## Подготовка и первый вызов

Выберите CPython 3.13 в `PATH` под именем `python3`. Из корня поставки выполните
следующий правильный пример. Он создаёт собственную временную конфигурацию,
задаёт отдельный каталог результатов и запрашивает контекст текущей рабочей копии.

```bash
POISE_PYTHON="$(command -v python3)"
POISE_CHECKOUT="$(pwd -P)"
POISE_EXAMPLE="$(mktemp -d)"
cp apps/poise/config/generic.example.json "$POISE_EXAMPLE/generic.json"
"$POISE_PYTHON" - "$POISE_EXAMPLE" "$POISE_CHECKOUT" <<'PY'
import json
from pathlib import Path
import sys
directory, checkout = Path(sys.argv[1]), sys.argv[2]
config_path = directory / 'generic.json'
config = json.loads(config_path.read_text())
config['results_root'] = str(directory / 'results')
config_path.write_text(json.dumps(config) + '\n')
packet = {'schema': 'poise-generic/v1', 'operation': 'context',
          'input': {'checkout': checkout, 'facts': ['selected-project'], 'external': None}}
(directory / 'context.json').write_text(json.dumps(packet) + '\n')
PY
"$POISE_PYTHON" -B apps/poise/bin/poise-generic \
  --config "$POISE_EXAMPLE/generic.json" < "$POISE_EXAMPLE/context.json"
```

Результат — `status="ok"`, exit `0`, `error=null`. Объект `result` содержит
`installation_source` с каталогом приложения, абсолютный `checkout`, переданные
`facts` и `external=null`; `evidence=[]`. Этот вызов читает собственный контекст.
Для постоянной установки подготовьте рабочий конфиг из того же
[очищенного примера](../config/generic.example.json) в выбранном оператором месте.
Храните рабочие настройки вне исходных коммитов.

## Настройки и пути

Все известные поля ниже обязательны. Неизвестные параметры конфигурации игнорируются,
исходный файл сохраняет их значения. Поля публичных запросов имеют точный состав.

| Поле | Значение и единицы |
| --- | --- |
| `schema` | `poise-generic-config/v1` |
| `results_root` | Непустой путь без NUL; абсолютный или относительно каталога выбранного конфига |
| `file_mode` | Целое от `0` до `511` включительно; права созданных файлов результатов, в примере `420` (`0644`) |
| `files.stdout` | Имя файла полного stdout провайдера, в примере `stdout.txt` |
| `files.stderr` | Имя файла полного stderr провайдера, в примере `stderr.txt` |
| `files.receipt` | Имя JSON-квитанции фактического вызова, в примере `receipt.json` |
| `files.result` | Имя полного результата при превышении размера ответа, в примере `result.json` |
| `limits.packet_bytes` | Максимум исходных UTF-8 байтов stdin, включая пробелы и завершающий LF |
| `limits.input_bytes` | Максимум байтов каждого читаемого каталога, политики или материала |
| `limits.result_bytes` | Максимум JSON-кодировки объекта `result` в UTF-8, без общего envelope |
| `limits.batch_count` | Максимум проб `capabilities` или провайдеров `navigation` в одном запросе |
| `limits.provider_timeout_seconds` | Общий потолок длительности одного внешнего действия, секунды |
| `limits.provider_output_bytes` | Общий потолок суммы фактических stdout и stderr одного действия |

Четыре имени файлов различны, непусты, без NUL и состоят из одного компонента пути.
Все ограничения количества и размера — положительные целые; длительность —
положительное конечное число. Используйте числовые значения этих типов.
Пределы отдельных проб явно задаются в пределах глобальных потолков.

Каждое внешнее действие получает собственный подкаталог `results_root`.
Пути `checkout`, `workspace`, `catalog`, `policy`, `instruction_root` и внешний `cwd`
передаются абсолютными. Рабочие копии и каталоги инструкций подготавливает оператор.
Пути материалов и профилей задаются относительно соответствующего корня через `/`,
каноническими компонентами. `paths` подготовки инструкций содержат пути файлов
относительно выбранной рабочей копии. Контекст, результаты и конфигурация разных
установок определяются переданными аргументами.

## Запросы и общий ответ

Envelope запроса содержит ровно `schema`, `operation`, `input`; `input` — объект.
Общие поля ответа — ровно `schema`, `status`, `result`, `error`, `evidence`.
`schema` ответа равно `poise-generic/v1`.

| `status` | Exit | Смысл |
| --- | --- | --- |
| `ok` | `0` | Получен результат операции, `error=null` |
| `unavailable` | `1` | Фактическое действие или сохранение результата недоступно; причина и продолжение в `error` |
| `needs_inputs` | `1` | Подготовке инструкций нужны обязательные материалы; текущий результат и диагностика сохранены |
| `rejected` | `2` | Требуется исправить объявленные входные данные или настройки |

`result` — объект либо `null`. Ошибка содержит ровно `code`, `details`, `action`.
`evidence` — список ссылок с ровно `kind` и абсолютным `path`; виды:
`stdout`, `stderr`, `receipt`, `result`. Читайте файлы по этим ссылкам для полного
машинного результата. Квитанция описывает фактический запуск и его исход.

### Контекст

`operation="context"`, `input`:

| Поле | Договор |
| --- | --- |
| `checkout` | Абсолютный путь существующего каталога проекта |
| `facts` | Явный список уникальных непустых текстовых фактов; допустим пустой список |
| `external` | `null` либо объект ровно с `argv`, `input`, `cwd`, `environment` |

`external.argv` — непустой список аргументов публичной команды владельца;
`input` — JSON-объект, который команда получает одной записью на stdin;
`cwd` — абсолютный существующий каталог; `environment` — полный явно заданный
набор строковых переменных процесса. При необходимости включите в него `PATH`.
Команда получает глобальные пределы длительности и вывода.

Успешный внешний ответ возвращается в `result.external.response` с фактическим
`exit_code`. При обычном внешнем отказе сохраняется доступный собственный контекст.
Предметные данные Task запрашиваются публичной командой соответствующего приложения;
её собственные schema и полномочия сохраняются. Полученный ответ является данными
владельца, а результат Poise описывает фактически выполненный вызов.

### Проверки возможностей

`operation="capabilities"`, `input` содержит ровно `workspace` и `probes`.
`workspace` — абсолютный существующий каталог; `probes` — список проб с уникальными ID.
Полная пачка проверяется до первого запуска. Все её пробы наблюдаются перед
вычислением `result.ready`, `missing_required` и `observations`.

| Поле пробы | Назначение |
| --- | --- |
| `id`, `tool_ref`, `remediation` | Явные непустые ID, ссылка инструмента и операторское продолжение |
| `kind` | `command` или `mcp_stdio` |
| `required` | Булево: участвует ли доступность пробы в итоговой готовности |
| `argv`, `cwd`, `environment` | Точный список аргументов, каталог и полный набор переменных процесса |
| `timeout_seconds`, `max_output_bytes` | Положительные длительность и целый размер в пределах глобальных потолков |
| `expected_exit_code` | Целый ожидаемый код завершения команды |
| `stdout_contains`, `stderr_contains` | Явные списки непустых подстрок фактических потоков |
| `json_assertions` | Список объектов с ровно `path` и `equals`; `path` — непустой список ключей JSON-объектов |
| `project_bound` | Булево: требуется ли точное наблюдение выбранной рабочей копии |
| `mcp` | `null` для команды или объект протокола MCP ниже |

В значениях пробы `${workspace}` заменяется выбранным абсолютным каталогом.
При `project_bound=true` задайте JSON-проверку с `equals="${workspace}"`.
Совпадение `equals` учитывает значение и тип. Команда выполняется через argv.
Полные stdout/stderr сохраняются до анализа JSON и условий.

Наблюдение содержит `id`, `status` (`available`/`unavailable`), `tool_ref`,
`project_path`, `version`, `observation`, `tools`, `receipt`, `remediation`, `reason`.
Типизированный отказ также сохраняет `error`. Для обычной команды подтверждение —
`observation="command_executed"`. Отсутствующая необязательная возможность сохраняет
`ready=true`; обязательные отсутствующие ID перечислены в `missing_required`.
При одной обязательной пробе ошибка лимита возвращается с точными ID и пределом.
Для пачки нескольких проб общий исход — `capabilities_unavailable`, подробности
каждой типизированной ошибки остаются в её наблюдении.

В `hook.intercept` те же наблюдения имеют advisory-смысл: `ready` и
`missing_required` сохраняются отдельно от исхода основного внешнего вызова.
Точный порядок, полный результат и продолжение описаны в
[договоре hooks](hooks-poi.md#наблюдения-возможностей).

### MCP stdio

Объект `mcp` содержит ровно следующие поля:

| Поле | Договор |
| --- | --- |
| `protocol_version` | Явно выбранная непустая версия протокола |
| `client_info` | Объект ровно с непустыми `name`, `version` |
| `required_tools` | Непустой список уникальных имён необходимых инструментов |
| `call` | `null` либо объект ровно с `name`, `arguments`, `read_only` |
| `max_messages`, `max_pages`, `max_message_bytes` | Положительные целые пределы полученных сообщений, страниц и размера сообщения |
| `shutdown_seconds` | Положительный конечный предел завершения процесса в рамках оставшегося общего срока |

Для MCP задайте `expected_exit_code=0`, пустые списки текстовых условий.
Вариант `call=null` использует пустые `json_assertions` и `project_bound=false`:
он выполняет initialize/initialized и постраничный tools/list, возвращая
`mcp_tools_listed`. `version` берётся из реального `serverInfo.version`.

Для проверки действия выберите `call.name` из `required_tools`, передайте
объект `arguments`, `read_only=true` и условия `json_assertions` результата вызова.
Подтверждение — `mcp_smoke_passed`; ответ `isError` учитывается фактически.
Список инструментов подтверждает обнаружение, а tools/call — выбранное действие.
Потоки и отправленные протокольные сообщения отражаются в собственной квитанции.
При завершении stdin закрывается, stdout читается одновременно с ожиданием child;
конечный вывод сохраняется полностью перед исходом превышения размера.

### Каталог и выбор навыков

`skills.list` получает ровно `catalog`, `instruction_root`; `skills.read` —
те же поля и `skill_ids`. Оба пути абсолютны. Каталог имеет схему
`poise-skill-catalog-1` и непустой список `skills`. Каждая запись содержит
`id`, `path`, `purpose`, `class`, `level`, `responsibility`.

`id` уникален и состоит из строчных латинских букв/цифр с одиночными дефисами между
частями. `path` уникален, относителен корню инструкций и заканчивается `SKILL.md`.
`purpose` — непустой текст. Для `class="working"` задайте положительный целый
`level` и непустую `responsibility`; для `meta`/`common` оба поля равны `null`.
Неизвестные настройки каталога игнорируются при загрузке.

Обе операции возвращают `result.skills`, отсортированный по ID. `skill_ids`
содержит уникальные ID выбранных навыков; пустой список возвращает пустой выбор.
Метаданные читаются независимо от содержимого файлов инструкций. Пример структуры
находится в [тестовом каталоге](../tests/fixtures/generic/catalog.json).

### Подготовка инструкций

`skills.prepare` получает ровно `catalog`, `instruction_root`, `project`,
`checkout`, `policy`, `paths`, `previous`. `project` — явное непустое имя проекта;
`paths` — непустой список относительных путей файлов; `previous` — `null` при первом
вызове либо полный прежний объект `result` этой операции для тех же проекта и корней.

Политика имеет схему `poise-project-instruction-policy-1`, непустую `version`,
список `universal_skills` и список `profiles`. Профиль содержит обязательные
поля `name`, `paths`, `baseline`, `recommended_skills`, `profile_file`.
Имена профилей уникальны, непусты, без двоеточий. `paths` профиля — непустой список
канонических префиксов каталогов с завершающим `/`; ссылки на навыки выбираются
из каталога. `profile_file` равен `null` или относительному пути файла проекта.
Пример — [тестовая политика](../tests/fixtures/generic/policy.json).

По выбранным путям операция объединяет универсальные навыки, baseline и рекомендации
подходящих профилей, их файлы и существующие родительские `AGENTS.md` вплоть до корня.
Повторный материал читается один раз и объединяет `scopes`/`reasons`/обязательность.
Навыки читаются от `instruction_root`, правила и профили — от `checkout`.
Текст UTF-8 сохраняет исходные переводы строк, включая CRLF.

`result` содержит `status` (`ready`/`needs_inputs`), `project`, `checkout`,
`instruction_root`, упорядоченные `paths`, `materials`, `diagnostics`, `delta`.
Материал содержит `kind` (`skill`/`profile`/`rule`), `id`, `root`
(`instructions`/`checkout`), `path`, `scopes`, `required`, `reasons`, `available`,
`content`. Недоступный материал имеет `content=null` и явную диагностику.
Универсальные/baseline навыки, файлы выбранных профилей и найденные правила обязательны;
рекомендованные навыки допускают результат `ready` при отсутствии файла.

При первом вызове `delta=null`. При повторном — `added`, `removed` и `changed`;
изменённая запись содержит `key` и список изменённых полей. Ключ объединяет
`kind:id:root:path`. Сравниваются фактические `available`, `content`, `reasons`,
`required`, `scopes`. Сохраните целый предыдущий результат для следующего вызова.

### Навигация

`navigation` получает ровно `checkout`, `operation`, `files`, `providers`.
`files` — непустой список уникальных имён файлов выбранной области, `providers` —
список объектов с уникальными `id`, `kind` (`ide`/`ast`), `operations`,
`identity_path`, `probe`. `probe` имеет полный договор проверки возможностей;
`operations` перечисляет поддержанные действия провайдера, `identity_path` —
непустой список ключей фактического JSON-результата с идентичностью рабочей копии.
Poise добавляет к проверкам пробы точное равенство этой идентичности `checkout`.
Передайте в argv/аргументах самого провайдера нужные проект, действие и область.

Действия: `symbol`, `usages`, `hierarchy`, `inspection`, `documentation`, `structural`.
Для `structural` выбираются AST-провайдеры; для остальных сначала IDE, затем
подходящие AST. AST применяется к `symbol`, `usages`, `hierarchy`, `structural`.
Порядок внутри одного типа соответствует списку. Полная пачка проверяется до
первого вызова; затем выполняются подходящие провайдеры до первого доступного.

Успешный `result` содержит `status="proved"`, `provider`, `checkout`, отсортированный
`scope`, фактические `observations`, `limitation` и `receipt`. При недоступности
подходящего действия результат содержит `status="unavailable"`, `provider=null`
и реальные попытки. Наблюдение относится к объявленному действию и области проекта.
Содержимое результата внешнего инструмента доступно в полных потоках квитанции.

## Лимиты, результаты и продолжение

| Код ошибки | Существенные данные и правильное продолжение |
| --- | --- |
| `invalid_config` | `details.path`, `action="correct:config"`; задайте корректное известное поле настроек |
| `invalid_json`, `unsupported_schema`, `invalid_request` | Подготовьте корректный JSON, выбранную схему и точный состав входа; у request есть путь поля |
| `packet_limit`, `input_limit`, `batch_limit` | Уменьшите пакет/пачку либо явно настройте подходящий лимит; input указывает файл |
| `provider_timeout`, `provider_output_limit` | `details.id` и effective `limit`, `action="adjust:provider"`; настройте конкретный провайдер и предел |
| `provider_unavailable`, `external_unavailable`, `external_response` | Проверьте настроенную публичную команду и её фактические потоки/код/JSON-ответ |
| `capabilities_unavailable`, `navigation_unavailable` | Используйте наблюдения и remediation для настройки необходимых возможностей |
| `invalid_catalog`, `invalid_selection`, `invalid_preparation` | Исправьте явный каталог, выбранные ID, политику, пути или полный previous |
| `materials_unavailable` | Восстановите обязательные файлы по диагностике и повторите подготовку |
| `io_unavailable` | `details.reason`, `action="configure:files"`; подготовьте доступные каталоги/права собственных результатов |
| `result_limit` | Полный объект сохранён как evidence `kind="result"`; прочитайте файл (`action="read:result"`) |

Для конечного вывода ограничения провайдера определяются после сохранения полных
stdout/stderr. При настоящем timeout сохраняются фактически испущенные байты,
процесс останавливается и ожидается его завершение. Общий срок MCP и его предел
завершения ограничивают ожидание. Предел размера `result` относится к самому объекту,
а небольшой envelope отказа возвращается целиком. Ошибка записи полного объекта
даёт `io_unavailable` и только реально созданные ссылки. Оператор подготавливает
каталоги и конфигурацию, затем повторяет выбранное действие.

## Правильные проверочные примеры и границы доказательства

## Владельцы реализации

`domain` содержит чистые модели каталога, выбора/дельты материалов, проб и порядка
навигации. `application` объединяет их в контекст, возможности, навыки и навигацию.
`infrastructure` читает явные файлы, запускает команды/MCP и сохраняет полный вывод.
`generic.py` связывает владельцев и формирует публичный ответ. Чтение явной
generic-конфигурации имеет общий filesystem-владелец `infrastructure/generic_config.py`;
каждый вход сохраняет собственную политику ответа и лимитов. Общий JSON-декодер
используется также действующим входом Session. Управление задачами, Session-состоянием,
hooks, reader и асинхронными заданиями остаётся у соответствующих владельцев.
