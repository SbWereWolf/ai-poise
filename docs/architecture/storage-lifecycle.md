# Жизненный цикл хранилищ

Актуализировано 18 сентября 2026 года по реализации AI-poise. Это описание текущего контракта, не разрешение на перенос данных или новую миграцию. Датированные архитектурные эскизы и старые протоколы проверок остаются историей.

## Владельцы и версии

Номер `PRAGMA user_version` принадлежит конкретному SQLite-файлу. Строка конфигурации `ddd-accounting-12` — другой контракт; её нельзя менять на основании номера SQLite schema.

| Хранилище и владелец | Текущая schema | Явное расположение | Создание и допустимое изменение версии |
|---|---|---|---|
| Task DB: Task/Sprint, execution, Evidence, Ownership и authoritative accounting через общую Unit of Work | 13 | `paths.database` и `paths.lock` внутри настроенного `paths.state` | Пустая schema 0 создаётся; известная 12 проходит только описанный ниже ownership upgrade. Остальные несовместимые версии отклоняются. |
| Requirements DB: канонические System/Application требования и связи | 1 | `paths.requirements_database` и `paths.requirements_lock`; относительные значения — от `paths.state`, абсолютные — точно | Пустая schema 0 создаётся; непустая неизвестная либо версия не 1 отклоняется. Общей автоматической миграции нет. |
| Optional telemetry: необязательные измерения, отдельно от authoritative Task accounting | Общая SQLite schema 13 при ленивой инициализации | `accounting.storage.database` и `accounting.storage.lock`, отдельно от Task и Requirements | Используется общий `Database`, но его создание отложено до работы worker. Необязательная телеметрия не должна блокировать основной результат. |
| HookRegistry: установки, bindings, операции и hook events | 1 | `database` и `lock` настроек hook transport | Пустая schema 0 создаётся; несовместимая версия отклоняется. Эти записи не заменяют Task ownership. |
| Goal/config editor: операции редактирования и heads конфигураций | 1 | `database` и `lock` настроек редактора относительно его root | Пустая schema 0 создаётся; несовместимая версия отклоняется. Состояние редактора не является вторым владельцем Task. |

Реализация: [Task Database](../../src/poise/infrastructure/sqlite/database.py), [RequirementsStore](../../src/poise/infrastructure/requirements_registry.py), [TelemetryDatabase](../../src/poise/infrastructure/telemetry.py), [HookRegistry](../../src/poise/infrastructure/sqlite/hook_transport.py), [GoalConfigRepository](../../src/poise/infrastructure/goal_config.py). Project-config сохраняет собственные pending/operation receipts в файлах; это не ещё одна каноническая Task DB.

Общая Task write boundary получает `BEGIN IMMEDIATE` до чтений и ограниченно повторяет только SQL-границы `BEGIN`/`COMMIT`, а не тело операции. RequirementsStore сейчас использует отдельный flock и deferred `BEGIN` с SQLite `timeout=0`: краткая блокировка независимым writer может дать немедленный отказ. Общая гарантия ожидания на него пока не распространяется.

Task DB хранит собственные Task requirements и согласованный исторический снимок System → Application → Task. Это не копия изменяемого канонического Requirements Registry. Правила полноты, статусов и согласования — в [реестре требований](../workflows/requirements-registry.md#публикация-и-исторический-снимок).

## Ограниченный переход Task DB 12 в 13

При открытии известной schema 12 выполняется только ownership upgrade. Он может очистить terminal worktree binding, если Task уже `completed`/`cancelled` и у неё отсутствует claimant. Если остаются неоднозначные legacy связи, база сохраняет version 12: уникальные индексы не создаются, выбор владельца не угадывается. Незатронутая работа не должна блокироваться глобально.

Точное состояние читают через `show` с `kind: ownership_conflicts`. Исправление одного связного конфликтного компонента выполняют публичным `recover_ownership` с его фактическим снимком и явным решением пользователя. После устранения конфликтов создаются уникальные индексы claimant/worktree owner и устанавливается schema 13. Это не перенос Worktree/Git-файлов и не право сбрасывать чужой claim.

Сначала сохранить исходную базу; затем следовать [публичному контракту восстановления владения](../workflows/batch-work.md#восстановление-неоднозначного-владения). Незнакомая непустая schema 0, schema 11 и другие неподдерживаемые версии отклоняются. Общего преобразователя произвольных старых баз нет.

## Явные пути и переносимая поставка

`paths.state` — явный root рабочих данных, а checkout/worktree — объект кодовой работы, не альтернативный root установки. Task DB, Requirements DB и optional telemetry не должны ссылаться на один физический файл либо общий lock. Политика новых проектов и ранее разрешённое расположение ai-poise различаются: см. [владение и явные пути](../workflows/requirements-registry.md#владение-и-явные-пути).

В доставленной конфигурации ai-poise Requirements DB настроена на `/home/sbwerewolf/workdata/poise-project-data/ai-poise/requirements.sqlite`, lock — соседний `requirements.lock`. Переносимая копия в полном архиве находится в `projects/ai-poise/database/requirements.sqlite`. Распаковка архива сама по себе не записывает её на пользовательский хост и не перенастраивает runtime.

Для другого расположения явно сопоставить все настроенные пути и сверить существующую базу с доставленной. Не перезаписывать более новое состояние, не запускать повторный seed и не считать статус `future` утверждением о реализованном требовании. История однократного импорта — в [импорте утверждённой поставки](../workflows/requirements-registry.md#однократный-импорт-утверждённой-поставки).

## Резервное копирование и восстановление

`poise backup` охватывает **только Task DB**. Он не сохраняет Requirements DB, Git, конфигурацию и материалы Task/Sprint. Создание/восстановление требуют исключительного операторского окна: см. [обязательное условие Task DB backup](../task-db-backups.md#обязательное-условие). Наличие одной SQL-копии не доказывает восстановимость полного проекта.

Полную копию создают существующим [checkpoint toolkit](../workflows/checkpoint-recovery.md#полная-копия-для-облачных-агентов): репозиторий с `.git`, конфигурация, все постоянные БД и авторские материалы. Внешние настроенные БД должны быть явно включены в переносимую поставку вместе с описанием отображения путей; инструмент не должен угадывать их расположение и заменять более новые файлы. Остановить writers на время снимка; не представлять разные моменты нескольких БД как одну распределённую транзакцию.

Для Gmail используют [prepare → отправку → полное обратное получение → confirm](../workflows/checkpoint-recovery.md#полные-резервные-копии-в-gmail-при-непрерывной-разработке). Успешная отправка или список имён вложений не заменяют восстановление байтов. `delivery_verified: false` внутри подготовленного манифеста корректен: факт доставки подтверждает последующий отдельный receipt.

Восстанавливать только в новый каталог. Проверить transport/archive SHA-256, файлы манифеста, Git refs и целостность/FK каждой SQLite-базы, затем применить явное сопоставление путей. Исторические или дублирующие базы нельзя удалять только из-за одинакового имени; их роль и происхождение должны быть установлены отдельно. Утверждение о целостности снимка не является повторным запуском тестов продукта.
