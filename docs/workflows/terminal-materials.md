# Поставка результата и удаление материалов Task

## Договор и граница хранения

Папка Task — удаляемая рабочая область, а не постоянное место результата.
До любого терминального перехода принимается решение об интеграции результата
либо отказе от неё. Интеграция включает коммит в выбранную рабочую ветку и/или
перенос материалов в место заказчика. Отмена означает отказ и разрешает удаление
всех рабочих материалов задачи, её дерева и временной ветки вместе с непоставленными
изменениями и уникальными коммитами без дополнительного согласования.
Уже поставленные результаты и учётная история сохраняются. Это целевой договор;
ниже отдельно описаны ещё не приведённые к нему операции действующего API.

До удаления рабочих материалов явно согласуйте весь сохраняемый результат через
`delivery/agree`: точный Git-коммит и ref в настроенном репозитории, отдельный
файл, игнорируемую рабочую конфигурацию либо передачу заказчику. Если результата
нет, явно укажите `no_result` с пустым `outputs`; это не способ скрыть обязательную
поставку. Правило действует для standalone Task и участников Sprint.

Удаление материалов не удаляет Task из реестра или её DB-историю. Договор,
минимальные подтверждения, идентичность, прежние результаты и история остаются
у существующих владельцев. Полные потоки проверок, доказательства-файлы,
временные артефакты, handoff-файлы, локальные checkpoint и остальные файлы
внутри Task-root удаляются вместе с ним, без скрытого архива. Нужный заказчику
файл сначала объявляется самостоятельным результатом и поставляется наружу.
Общие материалы Sprint, файлы других Task, основные checkout, операторские
резервы и данные незавершённых операций не становятся материалами этой Task.

## Публичный договор поставки

Пакет передаётся выбранному проекту существующим `poise work`, с нативной
идентичностью caller и `messages=[]`. Пример формы для файлового результата:

```json
{
  "operation": "delivery",
  "input": {
    "action": "agree",
    "request_id": "result-delivery-1",
    "task_id": "EXPLICIT-TASK-ID",
    "expected_version": 42,
    "authorization": "Согласованная поставка результата",
    "declaration": {
      "disposition": "deliver",
      "outputs": [
        {
          "id": "result-file",
          "kind": "file",
          "source": "/absolute/task-root/artifacts/result.bin",
          "destination": "/absolute/agreed-location/result.bin",
          "digest": "<точный SHA-256 содержимого>"
        }
      ]
    }
  },
  "messages": []
}
```

Пути, digest и `42` в примере заменяются фактическими значениями. Для newborn
`expected_version` берётся из публичного `revision`, для остальных состояний —
из `version`. `request_id` стабилен для точного повторения того же пакета.
Смена намерения требует разрешённого restart до терминального исхода и начала
удаления; terminal/начатое удаление не допускают изменения договора.

Черновик, отменённый до выбора типа исполнения и начала работы, допускает первое
согласование уже после отмены. Для существующих собственных рабочих материалов
передайте `declaration: {"disposition":"no_result","outputs":[]}` через
`delivery/agree` с актуальным публичным `version` отменённой Task. Выбирать тип
исполнения и создавать договор исполнения не требуется; Task остаётся отменённой.
Отсутствующий каталог отменённой Task приводит к явному отказу согласования,
а не к восстановлению каталога.

При сохранении согласования проверяются существование Task, однозначность владения,
актуальная версия и допустимый владелец. Отсутствующая Task, неоднозначное или чужое
владение либо устаревшая версия дают явный отказ без записи нового согласования
и с сохранением имеющихся материалов.

Точный повтор исходного пакета `delivery/agree` возвращает сохранённый ответ
с `replayed: true`, в том числе после удаления материалов. Он не создаёт новое
согласование и не восстанавливает Task-root. Изменённое намерение с тем же
`request_id` отклоняется; новый `request_id` также не разрешает изменить уже
согласованный договор терминальной Task.

| kind | Поля одного output помимо уникального `id` и `kind` | Подтверждение |
|---|---|---|
| `git` | `repository`, `target_ref`, `commit` | Точный commit существует и является предком согласованного ref в настроенном репозитории |
| `file` | `source`, `destination`, `digest` | Отдельный постоянный файл имеет согласованный SHA-256 |
| `ignored_configuration` | `source`, `destination`, `digest` | Файл имеет согласованные байты, находится в настроенном репозитории, ignored и не tracked |
| `customer` | `source`, `destination`, `digest`, `acknowledgement` | Полученный файл и отдельное подтверждение заказчика совпадают с договором |

`acknowledgement` содержит ровно `path` и `receiver`; файл подтверждения вне
Task state содержит JSON с точными `receiver`, `digest`, `received_path`.
`received_path` равен `destination`. Сам инструмент не отправляет письмо и не
создаёт подтверждение заказчика. Для `file` и `ignored_configuration` отсутствующий
файл публикуется общим файловым владельцем; совпавшие байты принимаются,
конфликтующие не перезаписываются. Пути абсолютные, без `.`/`..` и symlink.
Файловые источники принадлежат Task-root; постоянное назначение находится вне защищённых
state/runtime/config-путей. Рабочие конфиги не помещаются в Git.

## Порядок завершения операций с материалами

Перед отменой, интеграцией или удалением рабочих материалов завершите текущие
записи и запросы, использующие материалы этой Task. После отмены или интеграции
новые записи в её рабочую папку не запускаются. Чтение сохранённой истории и
поставленных постоянных результатов выполняется по
[существующему договору](#чтение-и-повторное-использование-после-удаления),
без восстановления удалённой рабочей папки.

Одновременное удаление папки и ещё выполняющий запись запрос не входят в этот
порядок использования. Для двух одинаковых запросов восстановления воспроизведён
случай, когда один завершился, удаление прошло, а второй вновь создал папку.
Этот случай не исправлен в коде: пользователь исключил его доработку.
Подробная граница сохранена в
[реестре ограничений](../operations/known-bugs.md#material-use-accepted-attempts-007).

## Завершение и продолжение

По [правилу полномочия на переход](../governance/development-rules.md#полномочие-на-переход-в-статус)
решение о переходе в статус разрешает все предусмотренные его договором действия,
включая уборку. Повторное согласование судьбы коммитов и удаления рабочего дерева
не является отдельным условием такого перехода. Описанные ниже требования текущего
API к дополнительным разрешениям отражают ещё не устранённое расхождение реализации
с этим правилом, а не действующее требование повторного решения пользователя.

`accept`, `cancel`, `cleanup` и `integrate` вызывают settlement согласованной
поставки для возвращённой Task. При отмене Sprint либо после снятия блокировки
используйте явный `settle` для каждой Task. Уже существующим Task договор
автоматически не придумывается: отсутствие договора не удаляет материалы.
Согласование не даёт полномочий на приёмку, интеграцию или судьбу уникальных
коммитов. Эти решения сохраняют собственные gates.

После согласования поставки отменённого черновика ответ `delivery_agreed` ещё
не означает удаление материалов: вызовите явный `delivery/settle`. Завершение
требует терминального исхода, подтверждённых постоянных результатов и закрытия
обязательных потребителей и ресурсов. При блокировке материалы сохраняются до
устранения причины; `no_result` не разрешает отбросить уникальный Git-коммит.

Ресурсная очистка через `cleanup` работает и для отменённого черновика,
по которому работу не начинали. Отсутствие записи исполнения и договора
исполнения допускается: сохраняется штатное состояние очистки. Терминальное
состояние повторно проверяется при инициализации в той же транзакции.
Существующая незавершённая внешняя операция или повреждённая запись исполнения
приводит к явной ошибке без подмены данных. Когда ресурсов нет, очистка
завершается; точный повтор подтверждает результат без восстановления
рабочих каталогов.

```json
{"operation":"delivery","input":{"action":"settle","request_id":"result-settlement-1","task_id":"EXPLICIT-TASK-ID"},"messages":[]}
```

Чтение состояния не требует захвата Task:

```json
{"operation":"show","input":{"queries":[{"id":"delivery","kind":"task_delivery","task_id":"EXPLICIT-TASK-ID"}]},"messages":[]}
```

`delivery_agreed` означает сохранённое намерение; `delivery_pending` — выполняемую
поставку; `delivery_partial` — зафиксированное разрешение удаления после всех
подтверждений. При существующем договоре `delivery_blocked` содержит `reason`
и описание `recovery`. Без договора отдельный ответ `delivery_blocked` содержит
`reason: agreement_required`, но не содержит `recovery`: недостающий договор
задаётся через `delivery/agree`, после чего продолжают `delivery/settle`.
`delivery_complete` означает проверенное фактическое отсутствие Task-root.
Исключение удаления не объявляет успех: durable-состояние сохраняет возможность
продолжить частичную уборку. Системный сбой не превращается в фиктивный PASS.

Для `handoff_pending` учитывается последняя по порядку запись передачи Task
со статусом `released` или `resumed`. Только её состояние `released` означает
незавершённую передачу. Если последняя передача уже `resumed`, более старые
записи `released` не блокируют поставку; сами записи и история сохраняются.
Это не снимает остальные ограничения: незавершённую проверку, открытый draft,
обязательного потребителя артефакта, незавершённый export и требуемую интеграцию.
Приоритет этих проверок не меняется.

Исторический пример прежней ошибочной блокировки и границы сохранившихся
свидетельств описаны в [ретроспективе ERP-MERGE-RESIDUALS-001](../operations/evidence/erp-merge-residuals-001-retrospective-20261016/README.md).

| Причина | Продолжение через владельца |
|---|---|
| `agreement_required` | `recovery` отсутствует; задать действительный договор через `delivery/agree`, затем вызвать `delivery/settle` |
| `task_not_terminal` | Завершить либо санкционированно отменить Task |
| `integration_required`, `resource_cleanup_pending` | Завершить разрешённую интеграцию либо cleanup с явной судьбой коммитов |
| `checks_pending`, `external_operation_pending` | Разрешить исходную незавершённую внешнюю операцию |
| `artifact_draft_open`, `handoff_pending`, `artifact_consumer_pending` | Закрыть исходный draft/передачу/потребителя через его API |
| `transfer_pending` | Продолжить исходный export с теми же actor/request до независимого пакета |
| `source_integrity_failed` | Восстановить согласованный исходник до начала удаления |
| `destination_unavailable`, `destination_conflict` | Восстановить согласованное назначение/доступ/ignore-контракт, не перезаписывая чужие байты |
| `customer_acknowledgement_required`, `customer_acknowledgement_invalid` | Получить действительное подтверждение и согласованные полученные байты |

После устранения причины повторяется исходный settlement; `recovery` не является
готовым work-пакетом без `input`, `messages` и `request_id`. Перед продолжением
незавершённого удаления заново наблюдаются все постоянные подтверждения и
обязательные потребители. Удалённые источники не перечитываются, поставка не
повторяется, внешние данные автоматически не ремонтируются. Это действует и
при уже отсутствующем каталоге до сохранения окончательного complete.
Завершённый исторический replay возвращает прежний результат без нового аудита.

## Владение каталогом и намеренная замена

Каталог по настроенному Task-пути может быть намеренно заменён оператором обычным
каталогом. Сохранённые device/inode — начальное наблюдение для аудита, а не запрет
продолжения. Отдельная защита от намеренной подмены корня, quarantine и закрепление
inode не входят в договор. При замене оператор сохраняет правильную принадлежность
содержимого. Остаются проверки владельца, настроенного пути, обычного типа каталога,
символических ссылок и чужих/общих материалов; разрешение замены не разрешает
удалять произвольный путь.

## Чтение и повторное использование после удаления

При отображении исторической квитанции задачи в терминальном состоянии приложение
сообщает: «Служебные материалы задачи удалены. Служебные журналы уничтожены».
Основание сообщения — терминальное состояние задачи, которой принадлежит квитанция,
в том числе при фактически сохранившихся журналах. Принадлежность определяется через
владельца результата: обычное доказательство этапа либо сохранённый интеграционный
результат. Ошибка получения состояния отображается явно.

Полный сохранённый ответ содержит это сообщение и исторические идентификатор
квитанции, метод, код завершения, признак прохождения проверки и связь с задачей.
Краткое и развёрнутое представления не обязаны перечислять все квитанции:
их объём ограничен, полные сведения доступны по ссылке на файл. Форматы описаны в
[договоре трёх представлений](runner.md#три-представления-вывода).
Другое представление того же сохранённого ответа читается через
[`result-view`](runner.md#чтение-сохранённого-результата-без-повторного-выполнения),
без повторной интеграции и восстановления удалённых материалов.

Terminal inspection и точные завершённые публичные повторы возвращают сохранённую
историю без захвата Task, восстановления Task-root и raw proof. Исторический PASS
относится к проверенному commit. Сообщение представления отражает состояние задачи;
фактическую поставку и удаление подтверждает существующий владелец поставки.

При переносе состояния проекта действует то же различие: история проверок завершённой
задачи сохраняется без повторной регистрации и физического чтения её raw-журналов.
Это действует и для старой истории без договора поставки, и при оставшихся журналах.
Статус задачи сам по себе не отменяет регистрацию файлов: зарегистрированные рабочие
материалы, в том числе ранее привязанные журналы, проверяются по прежним identity и digest.
Их удаление и доступ к согласованным постоянным назначениям остаются у владельца поставки.
Одна классификация истории применяется при публикации материалов и подтверждении
потребителей; исходные receipts и сведения об их владельцах не переписываются.

Для завершённой интеграции это относится и к объявленным сохраняемым входам, манифестам
и зарегистрированным файлам без `artifact_inputs`. Интеграционный владелец распознаёт начало
удаления через существующего владельца поставки. Повтор и запрос возвращают прежние checks,
не создают новых ссылок `acceptance_manifests` как текущего доказательства и не восстанавливают
Task-root. Отсутствие папки без сохранённого разрешения не освобождает от проверки живых
материалов. Продолжение частичного удаления и наблюдение постоянных назначений остаются
у владельца поставки.

Зарегистрированный файл после удаления доступен потребителю только через
единственное согласованное постоянное назначение с тем же исходным путём и digest.
Логическая identity регистрации сохраняется; общий material resolver выбирает
физические байты. Отсутствие такого назначения либо конфликт не исправляются
копированием receipt. Accepted duplicate reuse сохраняет проверки семейства,
локальной доступности и самостоятельной приёмки; удалённые raw outputs не
становятся свежими evidence. Новый export удалённых рабочих материалов не
поддерживается; заранее подготовленный пакет и его точный replay самостоятельны.

## Владельцы механики

`TaskDeliveryCommands` владеет договором и журналом подтверждений/удаления;
`RuntimeTaskDelivery` наблюдает Git/filesystem, потребителей и удаляет Task-root.
Lifecycle Task, ресурсный cleanup, интеграция, export и публикация файлов остаются
у своих владельцев. `ArtifactMaterialResolver` выбирает постоянные байты без
перезаписи регистрации. Общей блокировки материалов проекта нет.
`TaskDeliveryCommands` согласует допуск к материалам и начало удаления короткими
транзакциями по записям конкретной Task; файловые эффекты выполняются вне
длительной транзакции записи. Это не делает filesystem и DB единой атомарной
транзакцией и не гарантирует атомарную публикацию всего файлового пакета.
Порядок работы перед удалением задан
[отдельно](#порядок-завершения-операций-с-материалами).

Владелец Task предоставляет её текущее состояние без восстановления договора
исполнения. Финальная проверка версии и владельца выполняется в той же
DB-транзакции, что и запись согласования в журнал.

Checkpoint, экспорт или handoff не являются неявным бессрочным резервом папки
Task. Если архив нужен как самостоятельный результат, его назначение согласуется
и подтверждается до удаления; локально архив без отдельного поручения не создаётся.
