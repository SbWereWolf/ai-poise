# Подготовка и восстановление локальной конфигурации

Обновлено: **2026-10-04**.

## Назначение и владельцы

`poise local-assets` восстанавливает объявленные файлы из явно выбранного
снимка в существующий Git checkout. Операция сохраняет установочные значения
и создаёт только отсутствующие файлы. Обычный clone не возвращает игнорируемую
рабочую конфигурацию.

[Подготовка проекта Poise](project-setup.md#назначение) публикует managed
project manifest и процессы. Для файлов целевого приложения используется
описанная здесь отдельная операция. Она не открывает Poise Task DB, не создаёт
сессию Poise и не захватывает Task или worktree.

Выбор первоначальных значений принадлежит `start-dev repair` приложения.
Restore не генерирует значения, не выполняет строку `repair`, не подставляет
example вместо рабочего файла и не заимствует настройки другого checkout.
Если нужен repair, владелец приложения выполняет его по своему действующему
контракту и затем предоставляет соответствующий снимок. Эта команда не
устанавливает собственный вариант repair.

## Входы и подготовка

Нужен Python **3.13** с установленным Poise либо явно выбранными его исходниками.
`POISE_PYTHON` указывает абсолютный путь к этому интерпретатору. При проверке
исходников `PYTHONPATH` должен явно выбирать `src` проверяемой копии; при работе
с установленным пакетом используется его штатное окружение.

Оператор заранее предоставляет:

- существующий целевой Git checkout: обычный или linked worktree;
- отдельный существующий каталог снимка с разрешёнными к переносу файлами;
- декларацию `MANIFEST` и запрос `REQUEST`, содержащие согласованные project
  и target_root;
- точные SHA-256 исходных файлов и выбранные права новых файлов.

Корни задаются каноническими абсолютными путями, без symlink, `.` или `..`.
Source и target не совпадают и не вложены друг в друга. Права доступа и
разрешение на перенос установочных данных обеспечивает владелец снимка.
Секреты не помещают в версионируемые examples или документацию.

Запрос содержит ровно четыре поля:

```json
{
  "schema": "local-assets-restore-1",
  "project": "ERP",
  "target_root": "/absolute/selected/checkout",
  "source_root": "/absolute/supplied/snapshot"
}
```

Декларация содержит ровно `schema`, `project`, `target_root`, `assets`.
Её schema — `local-assets-1`. Каждый элемент assets содержит ровно следующие
поля:

| Поле | Контракт |
|---|---|
| `path` | Безопасный относительный путь целевого файла |
| `source_path` | Безопасный относительный путь файла в выбранном снимке |
| `sha256` | 64 шестнадцатеричных символа, точный digest исходных байтов |
| `kind` | `tracked`, `versioned_example`, `untracked_example` или `working` |
| `mode` | Целое число от 0 до 511; 384 соответствует `0600` |
| `repair` | `null` либо непустая строка только для `working`; информация для оператора |

`tracked` обозначает поставляемый файл, examples различают версионируемые и
невключённые в Git образцы, `working` — установочную конфигурацию. Роль задаёт
владелец декларации; команда не вычисляет её по Git index.

Относительные пути не содержат абсолютного префикса, обратного слеша,
двоеточия, пустых сегментов, `.` или `..`. Целевые пути разных файлов не
совпадают и не образуют пару файл/его потомок. Source и существующий destination
должны быть обычными файлами; symlink не обходятся.

Лишние поля, неверные типы и повторные JSON-ключи отклоняются. Непарные
Unicode surrogate в текстовых входах дают безопасный `invalid_request` или
`invalid_manifest` до файловых эффектов: exit 2, JSON с `asset: null`, пустой
stderr. Корректные Unicode, пробелы, emoji и экранированные surrogate pairs
сохраняются без нормализации.

### Санитизированный шаблон

[config/local-assets.example.json](../../config/local-assets.example.json)
содержит каркас из 14 путей: политики reader, настройки proxy, host runtime,
development settings/env и Codex. Его абсолютный root и нулевые digests —
**заполнители**, а не пригодная к запуску декларация.

До запуска владелец сверяет каждый путь, источник, роль и digest с текущим
checkout и разрешённым снимком. В каркасе proxy example обозначен как
`untracked_example`; это не утверждение о текущем ERP, где этот example уже
может быть версионируемым. Шаблон не является автоматически поддерживаемым
инвентарём живой установки. Команда не заполняет его и не создаёт отсутствующие
исходные значения. Рабочие файлы могут отличаться от examples.

## Восстановление и результаты

`MANIFEST` и `REQUEST` — абсолютные пути к заранее подготовленным JSON-файлам.
В примерах `:?` требует явного значения переменной; подстановки default нет.

```bash restore-example
"${POISE_PYTHON:?}" -B -m poise local-assets --manifest "${MANIFEST:?}" < "${REQUEST:?}"
```

До создания любого файла проверяются весь запрос и декларация, идентичность
project/root, действительный Git root, все источники, digests, назначения и
коллизии. Проверка Git root локально исключает унаследованные `GIT_` переменные
из окружения своего subprocess. Чужой `GIT_DIR`/`GIT_WORK_TREE` не заменяет
выбранный checkout; окружение вызывающего процесса не меняется. Linked worktree
с `.git`-файлом поддерживается.

Успех даёт exit 0 и один JSON с `project`, `target_root`, `assets`:

- `status: restored`, если создан хотя бы один файл;
- `status: unchanged`, если создавать файлы не потребовалось;
- для каждого объявленного пути — `created` или `preserved`.

Source проверяется даже при существующем destination. Существующие файлы
сохраняют байты, права и mtime, включая значения, отличающиеся от снимка.
Source, декларация и посторонние файлы не изменяются. Повтор с теми же входами
возвращает `unchanged` и сохраняет состояние файлов.

Публикация одного файла использует временный файл в том же каталоге, fsync и
create-only link. Ошибка I/O во время публикации нескольких файлов может оставить
уже созданные файлы и каталоги. Тогда JSON имеет `status: incomplete`, exit 2,
причину и известные результаты. Это не обещание rollback всей пачки.

## Отказы и восстановление

При отказе JSON содержит `status`, `code`, `asset`, `reason`, `recovery`.
Для ошибки всего запроса/root `asset` равен `null`; для файловой ошибки указан
безопасный объявленный путь. Значения файлов и секреты не выводятся.

| Код | Exit | Действие владельца |
|---|---:|---|
| `invalid_request`, `invalid_manifest` | 2 | Исправить форму, типы и текстовые значения входов |
| `project_mismatch`, `target_root_mismatch` | 2 | Выбрать точные project/root декларации |
| `invalid_target_root`, `unsafe_source_root` | 2 | Предоставить действительный checkout и отдельный реальный снимок |
| `unsafe_asset_path`, `unsafe_source_path`, `unsafe_symlink` | 2 | Исправить небезопасный путь через его владельца |
| `invalid_source_asset`, `invalid_destination_asset`, `asset_path_collision` | 2 | Предоставить обычные файлы и независимые назначения |
| `source_digest_mismatch` | 2 | Вернуть точные исходные байты либо исправить декларацию через её владельца |
| `missing_tracked_source`, `missing_example_source` | 3 | Предоставить объявленный файл или example в снимке |
| `missing_working_source` | 3 | Предоставить совпадающий рабочий файл снимка |
| `missing_repairable_source` | 3 | Предоставить рабочий файл либо отдельно выполнить объявленный owning repair и повторить |
| `io_failure` | 2 | Проверить доступ и известные результаты, затем повторить те же согласованные входы |

Для `missing_working_source` точная recovery-строка:
`Supply the matching snapshot asset; owner repair is unavailable.`
Для repairable источника сообщение предлагает действие владельца, но команда
его не выполняет. Отсутствующий поздний source тоже обнаруживается до публикации
ранних файлов. Не исправляйте этот отказ удалением рабочих настроек или сбросом БД.

## Проверка владельцем reader

Факт копирования не доказывает пригодность конфигурации для приложения.
Для ERP `ERP_READER` явно выбирает установленный приложением `content-read.py`,
а `TARGET_ROOT` совпадает с root восстановленного checkout. В его снимке должны
быть все три объявленные политики: document-intake, document-intake-registry
и output. Рабочая intake policy предоставляется явно, без fallback к example.

Для ограниченной проверки fixture с `AGENTS.md`:

```bash reader-check-example
"${POISE_PYTHON:?}" -B "${ERP_READER:?}" --repository-root "${TARGET_ROOT:?}" --path AGENTS.md --lines 1:1 --json --session-id local-assets-reader-fixture
```

Здесь `local-assets-reader-fixture` — явный контекст тестового reader, не
идентификатор вызывающего агента Poise. Reader отдельно ведёт свой runtime-журнал
в выбранном checkout; обещание отсутствия записей restore на него не переносится.
Для реальной работы reader использует свой действующий контракт контекста.

`tests/local_assets/test_docs.py` исполняет оба именованных блока в контролируемых
Git fixtures: успешное восстановление трёх политик и реальное чтение первой
строки, затем отсутствие working source с точным exit 3 и без ранних публикаций.
Образец intake применяется только как явно подготовленные байты тестового снимка,
а не как fallback production-команды. Никакая живая установка или исходный архив
при этой проверке не изменяется.

Ссылки и точные заголовки проверяет существующий
[владелец документации](../workflows/documentation-checks.md#проверка-ссылок-и-точных-заголовков).
Его успех подтверждает ссылки; исполнимость приведённых команд проверяется отдельно.
