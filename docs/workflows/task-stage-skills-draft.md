# Навыки по этапам Task: черновик требования

Обновлено: **2026-09-16**. Статус: **черновик для последующего оформления задачи**.
Это описание замысла и инструкция для обсуждения/подготовки, не новая схема API.
Task DB, шаблоны процессов и runtime в этой работе не изменяются. Задача на tooling
будет оформлена после получения актуальной пользовательской Task DB и планирования.
Ожидание БД не замораживает другую явно порученную работу; у каждого изменения
сохраняются собственные исходная версия, результат, проверки и резервная копия.

## Два набора навыков у каждого этапа

В предлагаемой модели постановщик определяет для **каждого этапа выбранного процесса**
два отдельных набора. Оба первоначально заполняются из явно выбранного шаблона этапа
и сохраняются в самой Task при её создании. Постановщик просматривает начальные наборы,
удаляет неприменимые навыки и добавляет необходимые для конкретной задачи.
Шаблон помогает подготовить решение, но не заменяет постановщика.

**Метанавыки** определяют способ выполнения работы на этом этапе: подготовка и
исполнение тестов, реализация продуктового изменения, проверка тестов, проверка кода.
Это назначения навыков, а не четыре новые роли агента. Существующие роли
`executor` и `reviewer`, их независимость и полномочия сохраняются.

**Предметные навыки** определяют конкретную специализацию: язык, фреймворк,
доменная архитектура, API, SQL, инфраструктура и другие применимые знания.
Постановщик выбирает их для работы именно этого этапа, а не один общий список
на всю Task и не весь каталог проекта. Метанавык проверки не заменяет предметного
навыка о проверяемом результате, а предметный навык не заменяет методику проверки.

Примеры назначения на этапы существующего `development` — **иллюстрации**, а не
новые предустановки или обязательный комплект для любой кодовой базы:

| Этап | Назначение метанавыков | Примеры существующих skills | Предметный выбор постановщика |
|---|---|---|---|
| `test_implementation` | Подготовить тесты и выполнить нужные проверки | `tdd`, `direct-checks` | Применимый test framework и специальность проверяемого поведения |
| `test_inspection` | Независимо проверить тесты и их ожидания | `review` | Навыки для оценки тестового инструмента и предметного контракта |
| `implementation` | Реализовать требуемый результат и осмотреть свою работу | `exec-task`, `self-review` | Конкретные навыки языка, API, домена или хранения |
| `implementation_inspection` | Независимо проверить конечный эффект и ограничения | `review` | Навыки предмета проверки, а не только общий review |

Эти назначения не требуют сейчас создавать skills с такими же названиями, как
этапы, или новый каталог. `tdd`, `review`, `exec-task` и другие существующие skills
переиспользуются там, где их содержания достаточно. Нужность отдельных новых
метанавыков решается по обнаруженному пробелу. Для исправлений, повторных проверок,
документации и других этапов наборы также определяются явно, если эти этапы есть
в выбранном процессе. Процесс не обязан иметь именно четыре этапа.

## Шаблон и решение постановщика

Нужный будущий результат: шаблон каждого этапа имеет оба набора навыков; создание
Task копирует их как исходное предложение и сохраняет итоговый выбор постановщика
по каждому этапу. Явные изменения постановщика не должны теряться при сохранении
или заменяться значениями шаблона. При просмотре Task должно быть понятно, что
требуется на текущем этапе, без повторного поиска по всему шаблону или каталогу.

Изменение шаблона впоследствии не должно молча менять уже созданную Task. Решение
об изменении её наборов принадлежит постановщику, в том числе агенту, явно
действующему в этой роли. Исполнитель и проверяющий не удаляют обязательный навык
из контракта только ради удобства или прохождения проверки. Они сообщают о пробеле
и передают постановщику обоснованное предложение изменить назначение.

Автоматический router может помогать подбором, но его рекомендация не заменяет
сохранённое назначение навыков этапа. Существующие границы focused decomposition
сохраняются: назвать предметный narrow skill метанавыком ради обхода разделения
нельзя. Ни новый список, ни успешная структурная проверка не доказывают качество
самого навыка или фактическое применение агентом его инструкции.

## Использование навыков и сообщение о нехватке

В целевой механике Task требует от агента использовать **оба сохранённых набора
текущего этапа**. При входе, возврате на этап или возобновлении агент получает
назначение именно этого этапа, читает необходимые инструкции и применяет их.
Не требуется заранее загружать навыки всех будущих этапов или все references.
Назначение навыков не разрешает менять роль, расширять scope или исполнять
инструменты из проверяемой рабочей копии вместо работающего экземпляра Poise.

Уже сейчас, если агент обнаруживает, что для конкретной специфики ему не хватает
skill, он **обязан сообщить об этом в финальном ответе** и в допустимой секции
результата/передачи, если она предусмотрена текущим процессом. Указать этап,
недостающую компетенцию, почему существующих навыков недостаточно, влияние на
результат и что нужно постановщику: найти существующий skill, уточнить назначение
или поставить разработку нового. Различать отсутствующий skill, недоступный файл
и недостаточное содержание имеющегося навыка. Не выдумывать готовый skill или
заявлять применение непрочитанной инструкции.

Это не требование каждый раз писать «навыков хватает». Обнаруженный пробел нельзя
скрывать, даже если работа завершена с ограничениями. При реальном блокере надо
сообщить сразу, не ждать финала; при отсутствии блокера продолжать разрешённую
работу и явно описать оставшуюся неопределённость. Недостающий skill сам по себе
не разрешает молча разрабатывать его или менять Task.

## Что существует сейчас и что отложено

Действующая декларация `decomposition.phases` уже содержит `stage`, `skills`, `areas`.
Она проверяет согласованность фокуса, а не реализует новые два набора, их копирование
из шаблона и требование использования при исполнении. Текущий `stage_contracts`
имеет свой [точный контракт](content-requirements.md#точный-stagecontract-task).
Нельзя отправлять в эти DTO придуманные поля метанавыков или предметных навыков.
До поставки tooling используются только реально поддержанные поля и разрешённые
содержательные секции; действующие Tasks не блокируются из-за отсутствия ещё
не реализованных полей черновика. Новые настройки и данные БД вручную не добавляются.

После получения БД нужно согласовать точные формулировки и оформить настоящую Task:
расширить существующих владельцев шаблонов и Task, подготовку постановщиком и выдачу
контекста этапа; предусмотреть проверку ссылок на skills и ясный отчёт о пробелах.
Не создавать отдельный Task store, router или механизм определения путей.
Кандидаты приёмочных проверок: два набора из шаблона; сохранение добавлений и удалений
постановщика; неизменность ранее созданной Task при изменении шаблона; назначение
текущего этапа после resume/rework; предметные навыки на review-этапе; сообщение о
недостающем навыке. Это план проверок, а не утверждение об их выполнении.

Открыты до постановки: имена полей и формат хранения; момент заполнения newborn
без выбранного типа цели; допустимость пустого набора для конкретных этапов;
изменение назначений после начала работы; обновление старых Tasks; способ
подтверждения применения навыков и пределы автоматической проверки. Простое
acknowledgement не считать доказательством осмысленного применения.
