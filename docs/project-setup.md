# Пакетная подготовка проекта и анкета

Обновлено: **2026-09-07T14:15:55+05:00**.

## Назначение

Получить независимый полный конфиг проекта и выбранные process snapshots без ручного
редактирования файлов. Это подготовка окружения, не создание Task/Sprint, не выполнение
бизнес-этапа и не разрешение на изменение целевого приложения.

Источники шаблонов и публикуемые project manifests лежат внутри явно заданного Harness root.
Настройки самого генератора: `config/project-setup.json`. Корень задан в этих настройках
относительно файла, а не угадан по текущему каталогу. Mutable project state может находиться
вне Harness root: `paths.state` задаётся явно и может быть абсолютным. Относительное значение
по-прежнему разрешается относительно project manifest. Остальные managed mutable paths
задаются относительно выбранного `paths.state`.

## Интерактивный путь

```bash
export PYTHONPATH="$PWD/src"
python -m harness project-init \
  --settings "$PWD/config/project-setup.json" \
  --template linux-reference \
  --destination config/projects/erp-local \
  --request-id ERP-SETUP-1 \
  --probe-repository yes
```

`linux-reference` — явно выбранный полный шаблон, а не default. Его версия и digest берутся
из выбранной записи registry, проверяются по файлу и фиксируются в receipt. Все прочие
обязательные аргументы явные. Назначение должно быть новым.

Анкета спрашивает идентификатор, существующий Git repository, base ref, remote, имя/email
автора, необходимость push, явный state root (абсолютный либо относительный) и имена наследуемых environment variables.
Вопросы, их порядок, типы и подсказки определяются данными шаблона, не условием по имени проекта.

Ответы:

* `set "ERP"` или `set "/home/user/erp"` — задать JSON-строку;
* `set false` — явное отключение push; `set ["PATH","HOME"]` — список;
* `keep` — явно принять показанное значение (из шаблона либо свой прежний ответ);
* `back` — вернуться, сохранив все ранее введённые ответы;
* `abort` или EOF — не публиковать;
* `publish` — доступно на финальном просмотре полного кандидата.

Пустая строка не означает ни согласие, ни default. После возврата изменение ответа попадает
в новый полный кандидат; при публикации повторно проверяются все связанные правила. Число
шагов анкеты ограничено `max_survey_steps`. Обнаруженное значение не подставляется скрыто.
Промпты идут в stderr, один итоговый JSON — в stdout.

## Пакетный путь для агента

```bash
python -m harness project --settings "$PWD/config/project-setup.json"
```

На stdin один объект `project-setup-1` с полями:

| Поле | Значение |
|---|---|
| `schema` | `project-setup-1` |
| `request_id` | Идентичность этого намерения создания |
| `destination` | Новый относительный каталог внутри Harness root |
| `template` | Явные `id`, `version`, `digest` из registry |
| `edits` | Список `{path: [имена полей], value: точное значение}` |
| `probe_repository` | Явное true/false |

`path` адресует поле выбранного project definition, не файл или таблицу. Каждый путь должен
существовать в полном шаблоне. Список/подобъект заменяется целиком. Дубликаты и одновременная
правка родителя и потомка отклоняются; порядок пакета не выбирает победителя. Поля вопросов
обязаны быть явно переданы. Остальные значения берутся из выбранного полного шаблона,
не из встроенных defaults. Изменение `automatic_checks` передаёт точные правила проекта;
редактор не читает команды из prose AGENTS и не изобретает их.

Перед публикацией инструмент проверяет весь кандидат штатным `load_config`, в том числе
каждый process через общий GoalTypeDefinition. Затем (при true) выполняются только локальные
Git-проверки: repository root, разрешимость base ref, имя ветки, настройка remote при push.
Ни fetch/push, ни установка пакетов, ни изменение trust не выполняются. Наличие remote в
конфиге отражено как `configured_not_contacted`: это НЕ доказательство credentials/network.
При false явно возвращается `not_checked`; такую запись нельзя называть проверенной.

## Публикация и повтор

Под общим bounded Linux lock создаётся отдельный кандидат с manifest, process snapshots и
receipt. Он не является действующим проектом. Только после валидации всех файлов и локальных
проверок кандидат публикуется атомарным rename каталога на той же файловой системе. Task DB,
сессия, worktree и код приложения до bootstrap не создаются и не меняются.

Существующий destination не перезаписывается. Повтор того же запроса проверяет receipt и
контрольные суммы опубликованных файлов и возвращает прежний результат. Позднее изменение
файла, другая операция или изменённое намерение приводит к VersionConflict. Источники могут
обновиться после публикации: повтор проверяет сохранённый независимый результат, не подменяет
его актуальным шаблоном. Перед публикацией источники должны совпадать с выбранными digest.

Ошибка до rename не оставляет опубликованной половины проекта. Если ошибка возникла после
rename, повтор того же запроса позволяет проверить сохранённый receipt; запрещён слепой
reset/overwrite. Mutable state и project manifest не могут занимать один файловый путь или вложенные взаимно области.
Пути файлов конфигурации остаются confined к Harness root; абсолютный `paths.state` допускается
как явно выбранный внешний mutable root и затем ограничивает database/runtime/task/sprint/worktree paths.

## Результат

`status`, `project`, `config_path`, `revision`, `process_count`, `readiness`, `replayed`.
Один небольшой результат заменяет последовательность copy/edit/validate/register.
Выходной лимит проверяется до публикации. Все настройки механики явно определены в settings.
Коды успеха/отказа/отмены анкеты также задаются settings; ошибка загрузки settings использует
существующий базовый CLI error contract.

## Пилот на реальном коде Harness

```bash
python examples/project_pilot.py \
  --harness-root "$PWD" \
  --repository /absolute/git/checkout/of/harness \
  --base-ref tasks/HARNESS-PILOT-01 \
  --destination state/pilots/self-check \
  --task-id SELF-PILOT \
  --check-seconds 60
```

Нужен реальный закоммиченный revision этой версии с `tests/projects`. Имя repository/ref
оператор задаёт явно. Пример создаёт конфиг инструментом, задачу через Catalogue, затем
выполняет **один** read-only planning stage полного verification route. В этот же пакет
регистрируется точная readiness-команда `python -m pytest tests/projects -q`, выполняемая
над реальными исходниками в отдельном worktree. Отчёт и stdout сохранены. Повтор verify
не перезапускает команду. Задача остаётся verified: пользовательское принятие не подделывается,
следующий этап не начинается. Наблюдения этого примера не измеряют качество чужой модели.

## Границы

Создание нового проекта, одна целевая codebase (граница текущего runtime), 13 reference
процессов в поставленном шаблоне. Редактирование действующего project manifest, автоматическая
миграция, multi-codebase, настройка живого IDE/Gmail и установка интерпретатора не включены.
Уже работающие задачи не затрагиваются. Проектный wizard теперь реализован, но не является
универсальным мастером установки всех внешних зависимостей.


## Локальный проект ai-poise

Настройка от 2026-09-10 для `/home/sbwerewolf/workdata/ai-poise` создана публичной командой `harness project` из явно выбранного `linux-reference`. Реестр `wsl-harness` расходится с текущей версией своего шаблона; он не исправляется этой настройкой. Проект получает 13 самостоятельных конфигураций процессов.

| Назначение | Путь относительно корня ai-poise |
|---|---|
| Рабочая конфигурация | `config/projects/ai-poise/project.json` |
| Конфигурации процессов | `config/projects/ai-poise/config/processes/` |
| Результат публикации | `config/projects/ai-poise/setup-receipt.json` |
| Task DB | `projects/ai-poise/database/tasks.sqlite` |
| Блокировка Task DB | `projects/ai-poise/database/tasks.lock` |
| Резервные копии Task DB | `projects/ai-poise/database/backups/` |
| Временные данные сессий | `projects/ai-poise/.runtime/` |
| Задачи и их артефакты | `projects/ai-poise/task/` |
| Спринты и их артефакты | `projects/ai-poise/sprint/` |
| Рабочие деревья Git | `projects/ai-poise/worktrees/` |
| Локальный Python 3.13 | `projects/ai-poise/.python/` |
| Окружение с установленным Harness | `.venv/` |

Пользователь явно потребовал рабочие данные внутри проекта. Здесь используется `projects/ai-poise/`, исключённый из Git, вместо размещения вне обслуживаемой кодовой базы. Task DB, её lock и резервные копии изолированы в `projects/ai-poise/database/`; совместимых файлов или ссылок на них в корне `projects/ai-poise/` нет. Это уточнение конкретной установки. Временные данные сессии удаляются при завершении; пустые корневые папки задач и спринтов ещё не означают создание задач или спринта.

`bootstrap` и `verify` — значения поля `operation` публичной команды `work`. Отдельных команд оболочки или скиллов с такими именами нет. Существующий навык — `skills/harness/SKILL.md`, его агент читает по ссылке из корневых правил. Автоматическое обнаружение навыка будет настроено отдельным согласованным переносом в `.agents/skills/`.

Один раз выбрать конфигурацию, путь команд и уникальную сессию:

```bash
export AI_POISE_ROOT=/home/sbwerewolf/workdata/ai-poise
export HARNESS_CONFIG="$AI_POISE_ROOT/config/projects/ai-poise/project.json"
export PATH="$AI_POISE_ROOT/.venv/bin:$PATH"
export HARNESS_SESSION="$("$AI_POISE_ROOT/.venv/bin/python" -c 'import uuid; print(uuid.uuid4())')"
```

Значение `HARNESS_SESSION` сохранять до окончания работы. Если инструмент запускает каждый shell изолированно, передавать те же значения окружения в каждом вызове; не генерировать новую сессию для `verify`.

Начать чтение без формальной задачи:

```bash
harness work <<'JSON'
{"operation":"bootstrap","input":{"task":null,"decision":null,"feedback":null,"rework_stage":null},"messages":[]}
JSON
```

После проверки результата чтения завершить ту же сессию:

```bash
harness work <<'JSON'
{"operation":"verify","input":{"result":null,"artifacts":[]},"messages":[]}
JSON
```

Для новой сессии без задач ожидаются `read_only` и `read_only_verified`. Последний статус подтверждает завершение runtime, а не содержательную проверку ответа: список `checks` пуст. Пустой `messages` в этих проверочных командах не означает, что пользовательских сообщений не было; это демонстрация вызова без их регистрации. В обычной работе действуют правила наблюдаемых событий из [контракта пакета](batch-work.md#пользовательское-сообщение).

Для формальной задачи bootstrap принимает существующий ID либо полный новый контракт. Результат этапа передаётся по выданному `result_template`; taskless-пакет не заменяет проверку работы над задачей. См. [контракт работы](batch-work.md) и [спринты](sprints.md).

При создании исходная Git-ветка — `master`, коммитов ещё нет. Поэтому запрос явно содержит `probe_repository=false`, а receipt — `repository=not_checked`. Это ограничение готовности, не пройденная Git-проверка. Перед работой с исходниками нужен начальный коммит с кодом и проверка разрешимости `master^{commit}`. Необходимый для порученной задачи коммит разрешён рабочим процессом; включать только согласованные файлы проекта. Публикация конфигурации и taskless-цикл не создают коммит. Remote `origin` указан как явное неиспользуемое имя: `push_required=false`; remote в репозитории не создаётся.

`automatic_checks` у выбранного шаблона пуст: эта установка не объявляет автоматическое покрытие тестами. Конкретные проверки формальных задач должны быть заданы их действующим контрактом. Исходный bootstrap-комплект спринта и эталонная БД здесь не импортируются.


### Каталог конфигураций и расположение задач

Рабочие данные находятся в `projects/ai-poise/`, конфигурации — отдельно в `config/projects/ai-poise/`. Основной файл `project.json` соседствует с receipt и подкаталогом `config/processes/` из 13 конфигураций. Имя manifest задаётся в настройках генератора и не является требованием JSON-формата; текущий публичный генератор публикует целый новый каталог. Один файл `config/projects/ai-poise.project.json` не заменяет весь комплект.

Изменение размещения выполнено повторной публикацией нового комплекта штатным инструментом после сохранения исходного комплекта. Рабочих задач в первоначальной базе не было; её проверочные журналы сохранены отдельно, не перенесены как задачи. Текущая база создана runtime в новом месте. Lock генератора находится в `projects/.project-setup.lock` и исключён из Git.

Сейчас файлы любой задачи находятся в `projects/ai-poise/task/<task-id>/`, а артефакты спринта — в `projects/ai-poise/sprint/<sprint-id>/`. Принадлежность задачи спринту хранится в SQLite через `sprint_id`. Ожидаемое пользователем размещение `sprint/<sprint-id>/task/<task-id>/` не реализовано текущим кодом и не получается подстановкой `paths.tasks`: это отдельное изменение механизма вычисления путей и его потребителей. Пустые папки не подтверждают такую вложенность.
