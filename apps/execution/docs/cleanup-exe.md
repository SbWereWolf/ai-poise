# Очистка ресурсов завершённой работы

## Подготовка и настройка

Используйте Python 3.13 и POSIX/Linux, включая Ubuntu в WSL. Запускайте
[самостоятельный CLI](shell-exe.md#запуск) со своим полным файлом конфигурации:

```sh
python -B apps/execution/bin/execution --config "$EXECUTION_CONFIG"
```

Для новых действий очистки добавьте к конфигурации компонент:

```json
{"cleanup": {"roles": ["writer"]}}
```

Это фрагмент полного файла. Версионный
[пример](../config/execution.example.json) уже содержит его и соответствующих
участников. Храните рабочую конфигурацию отдельно от примера.

| Параметр | Правильное заполнение |
| --- | --- |
| `cleanup` | Объект настройки новых действий очистки |
| `cleanup.roles` | Непустой список уникальных непустых идентификаторов ролей из значений `lifecycle.actors` |
| `lifecycle.actors` | Сопоставление передаваемого `actor_id` его роли; в примере `executor-A` имеет роль `writer` |

Участников и остальные настройки заполните по
[руководству lifecycle](lifecycle-exe.md#явная-настройка-участников-и-политики).
`cleanup.roles` задаёт отдельное разрешение на действия очистки. Решение об
[итоге работы](outcomes-exe.md) и решение об очистке передаются явно.
Известные опции обязательны для нового действия; неизвестные опции игнорируются,
а приложение сохраняет исходный файл конфигурации без перезаписи.

Историческое чтение и точный повтор сохранённого запроса используют свои
сохранённые данные и доступны при отсутствии текущего компонента `cleanup`.
Остальные операции приложения сохраняют свои требования к конфигурации.

## Владельцы и правильный порядок

Execution хранит обязанность, решение, очередь работы, наблюдения и результат
очистки. Sequencing владеет привязкой Workspace, Poise — общими физическими
инструментами. Вызывающий или Orchestrator явно передаёт публичную работу владельцу
и возвращает его фактическое наблюдение в Execution.

В текущей поставке процессный API очистки реализован. Самостоятельный Sequencing
обслуживает подготовку Workspace; его физический release и самостоятельный
провайдер удаления Poise остаются отдельными частями поставки. Для физического
шага подключите действующий публичный адаптер владельца, который принимает
описанный ниже `work` и возвращает `observation`. Его конкретные `argv` и `cwd`
задаёт оператор. Статус Execution описывает сохранённую работу и полученные
наблюдения, а физический эффект подтверждает владелец ресурса.

1. Получите канонический `task_id`, текущие revision, generation и редакцию договора
   через `query/execution`, а фактический итог — через `query/outcome`.
2. Получите привязку ресурсов от их владельца. Для Workspace используйте фактический
   ответ его подготовки или проекцию Workspace из публичного чтения Task у Sequencing.
3. Передайте `cleanup/prepare` с адресом итога, явным решением оператора и ресурсами.
4. Передайте выданный `work` указанному владельцу. Верните его действительное
   `observation` через `cleanup/observe`, используя текущие revision и адреса шага.
5. Продолжайте объявленные шаги до `cleanup_complete`; результат и историю читайте
   через `query/cleanup`. При отказе или неизвестном исходе следуйте
   [явному продолжению](#продолжение-и-сверка).

Физические инструменты и чужие хранилища остаются у их владельцев. Собственный
store Execution сохраняет предыдущие итоги и наблюдения вместе с очисткой.

## Пакеты действий

Корень имеет ровно `schema: "stride-execution/v1"`, `operation: "cleanup"`, `input`.
Каждое новое действие содержит следующие общие поля:

| Поле | Тип, смысл и источник |
| --- | --- |
| `action` | `prepare`, `continue` или `observe` |
| `request_id` | Непустой уникальный адрес обращения; сохраните исходный пакет для точного повтора |
| `expected_revision` | Текущая целая revision собственного store, от нуля |
| `task_id` | Канонический идентификатор по настроенной политике Task |
| `expected_generation` | Текущее целое поколение исполнения, от единицы |
| `expected_contract_revision` | Непустая текущая редакция договора исполнения |
| `actor_id` | Участник из `lifecycle.actors` с ролью из `cleanup.roles` |
| `cleanup_id` | Непустой постоянный адрес этой обязанности очистки внутри Task |

Для нового действия выберите совпадающие Task, поколение и договор обязанности.
Строковые идентификаторы непусты. Известные поля пакетов и вложенных объектов
задаются точно; числовые поля содержат целые числа соответствующего диапазона.

### Подготовка

`prepare` добавляет ровно четыре поля:

| Поле | Значение |
| --- | --- |
| `outcome_id` | Адрес фактически записанного собственного итога той же Task, поколения и договора |
| `resources` | Явный упорядоченный список ресурсов из следующего раздела, включая допустимый пустой список |
| `commit_disposition` | Явное решение по следующему разделу либо `null` для регистрации обязанности до решения |
| `authorization` | Непустое содержательное решение оператора о выбранной очистке |

Пустой список даёт `cleanup_complete` и `work: null` без обязательного решения
о коммите. Любой непустой список при `commit_disposition: null` даёт
`disposition_required`, `work: null` и причину с порядком продолжения. Затем
оператор выбирает решение через `continue`.

### Ресурсы и решение

Каждый ресурс имеет ровно `resource_id`, `kind`, `owner`, `reference`.
`resource_id` уникален внутри списка; `owner` — непустой адрес публичного
получателя работы. Для одного обязательства укажите не более одного worktree
и одной ветки. Их `workspace_id` соответствует сохранённой привязке исполнения.

| `kind` | Точные поля `reference` |
| --- | --- |
| `worktree` | `workspace_id`, `path` |
| `branch` | `workspace_id`, `name`, `commit` |
| `temporary` | `path` |
| `temporary_backup` | `path` |

Все поля `reference` — непустые строки фактической привязки владельца.
`name` задаёт имя ветки, `commit` — её выбранный коммит. Пути являются ссылками
владельца ресурса; Execution хранит их как данные публичной работы.
Worktree удаляется раньше его ветки. Остальные ресурсы сохраняют заданный порядок.

| Решение | Точные поля и поведение |
| --- | --- |
| `discard_authorized` | `kind`, `expected_commit`; оператор разрешает удаление выбранного результата |
| `preserved` | `kind`, `expected_commit`; сначала требуется успешное наблюдение владельца о сохранении результата |
| `integrated` | `kind`, `expected_commit`, `target_commit`, `integration_request_id`; сначала требуется наблюдение адресованного факта интеграции |

При наличии ветки `expected_commit` совпадает с её `reference.commit`.
Для непустого списка без ветки выберите `discard_authorized` с
`expected_commit: null`. Сохранение и интеграция относятся к ресурсу ветки.
`preserved` и `integrated` сначала выдают соответствующую работу её владельцу.
Полученный результат связывается с текущей попыткой; факт интеграции дополнительно
сопоставляется по исходному коммиту, целевому коммиту и адресу запроса интеграции.
После выбранного решения продолжайте ту же обязанность с тем же решением.

### Продолжение и наблюдение

`continue` добавляет к общим полям ровно `commit_disposition`, `authorization`.
Для первоначального выбора передайте своё явное решение. Для дальнейшей работы
передайте прежнее решение и содержательное разрешение на продолжение.

`observe` добавляет ровно `step_id`, `attempt_id`, `observation`.
Адреса берутся из текущего `work`; `observation` приходит от владельца этого шага.

## Работа владельца и наблюдение

`work` равен `null` либо содержит ровно:

| Поле | Смысл |
| --- | --- |
| `step_id` | Постоянный адрес текущего логического шага |
| `attempt_id` | Адрес одного физического обращения, по которому владелец устанавливает его исход |
| `owner` | Получатель из объявления ресурса |
| `operation` | `preserve`, `integration_status` или `remove` |
| `resource` | Полный текущий ресурс с его привязкой |
| `disposition` | Сохранённое решение оператора |
| `mode` | `execute` для допущенного действия или `reconcile` для выяснения прежнего исхода |

Перед выдачей работы Execution сохраняет её адреса. Владелец использует
`attempt_id` и остальные данные работы для адресного чтения своего результата;
для такой сверки достаточно адреса попытки, даже если ответ с `receipt_id` был потерян.

`observation` содержит ровно `status`, `receipt_id`, `result`:

| `status` | `receipt_id` и точный `result` |
| --- | --- |
| `succeeded`, удаление | Непустой адрес результата; `{effect: "removed"}` |
| `succeeded`, сохранение | Непустой адрес результата; `{effect: "preserved", preservation_ref}` с непустой ссылкой сохранения |
| `succeeded`, интеграция | Непустой адрес результата; `{effect: "integrated", source_commit, target_commit, integration_request_id}` с непустыми совпадающими ссылками |
| `failed` | Непустой адрес результата; `{reason, recovery}` с непустой причиной и способом продолжения |
| `unknown` | Адрес результата либо явный `null`; `{reason, recovery}` |
| `not_started` | Адрес результата либо явный `null`; `{reason, recovery}` после выяснения владельцем отсутствия начала действия |

Записи в таблице обозначают поля объекта; фактический пакет передаётся JSON.
`effect` соответствует текущей `operation`, а адреса — текущим шагу и попытке.
`not_started` принимается для текущего `reconcile`. Это наблюдение разрешает
`execute` той же попытки и сохраняет перечень ещё ожидающих ресурсов.

## Результат и история

Успех каждого нового действия имеет ровно
`schema`, `status: "cleanup_recorded"`, `revision`, `replayed`, `cleanup`.
Обычное новое обращение увеличивает revision на единицу. Поле `cleanup` содержит:

| Поля | Значение |
| --- | --- |
| `cleanup_id`, `task_id`, `generation`, `outcome_id` | Постоянные адреса и поколение исходной обязанности |
| `disposition` | Выбранное решение либо первоначальный `null` |
| `status` | `disposition_required`, `cleanup_pending`, `cleanup_blocked`, `cleanup_complete` |
| `resources` | Упорядоченный остаток объявленных ресурсов |
| `removed` | Упорядоченные ресурсы с успешным наблюдением удаления |
| `history` | Полная сохранённая история этой обязанности |
| `work` | Текущая работа владельца либо `null` |
| `issue` | `null` либо объект ровно `reason`, `recovery` |

`cleanup_complete` означает, что все требуемые наблюдения получены и остаток пуст.
`cleanup_blocked` сохраняет известный отказ, а `cleanup_pending` — ожидающую работу,
в том числе выяснение неизвестного исхода. Физический владелец сохраняет собственные
результаты; публичный результат Execution отражает уже переданные наблюдения.

Каждый элемент `history` содержит ровно `event`, `step_id`, `attempt_id`,
`resource_id`, `observation`. События — `obligation_recorded`,
`disposition_recorded`, `owner_observed`, `retry_requested`.
У первоначальных событий адреса шага и наблюдение явно равны `null`.
Наблюдения и предыдущие версии состояния остаются в собственном хранилище.

Для чтения примера Task `0042` с обязанностью `cleanup-1` передайте:

```json
{"schema":"stride-execution/v1","operation":"query","input":{"queries":[{"id":"cleanup-read","kind":"cleanup","task_id":"0042","cleanup_id":"cleanup-1"}]}}
```

Ответ чтения имеет `schema`, `status: "read_only"`, `revision`, `results`.
Единственный элемент примера — `{id, kind: "cleanup", result: cleanup}`.
Чтение сохраняет состояние и адреса работы. История доступна и после нового
поколения исполнения. Точный повтор исходного запроса возвращает первоначальный
ответ и revision с `replayed: true`.

## Продолжение и сверка

Сохраняйте полный отправляемый пакет до вызова. При потере ответа повторите его
точно для получения прежнего результата, затем прочитайте текущую очистку.
Исторический ответ и исторический `work` описывают прежнюю выдачу работы.

После перезапуска вызывающего либо неопределённости физического исхода:

1. Прочитайте `query/cleanup` и актуальную revision.
2. Отправьте **новый** `continue` с новым `request_id`, актуальными данными
   и прежним решением оператора до любого физического вызова.
3. Для неподтверждённой выданной работы используйте возвращённый `reconcile`
   с прежними `step_id` и `attempt_id`, даже если ранее не поступало ни одного `observe`.
4. Получите адресный результат владельца. Передайте его через новый `observe`.
   При `not_started` выполните вновь выданный `execute` той же попытки;
   при сохранённом успехе продолжайте следующую работу.
5. При `unknown` сохраняйте `reconcile`, пока владелец устанавливает исход.
   Дальнейшее действие определяется фактическим ответом владельца.

При известном `failed` сначала выполните указанный владельцем способ устранения
условия отказа. Новый явный `continue` сохраняет логический шаг и выдаёт новую
попытку для оставшейся работы. Уже успешно удалённые ресурсы и старый отказ
остаются в истории. Продолжение обслуживает реальные наблюдения; восстановление
конфигурации и физического состояния выполняется их отдельными владельцами.

Обычный отказ обращения имеет `schema`, `status: "rejected"`, содержательный
`reason`, exit `2` и пустой stderr. Используйте актуальные собственные адреса,
явную настройку и корректный пакет по таблицам выше. Принятое ограничение
[RV2-03](../../../docs/operations/known-bugs.md#rv2-03--повтор-уже-применённого-удаления-этапа)
относится к отдельному редактору конфигурации; выделение очистки сохраняет его статус.

## Примеры через настоящий CLI

Заполните входы примера фактическими данными своей установки:

| Переменная | Источник |
| --- | --- |
| `execution_command` | Объект `{argv, cwd}` с выбранным Python, абсолютным app-owned CLI, `--config` и абсолютным рабочим файлом |
| `owner_commands` | Явное сопоставление каждого `owner` объекту `{argv, cwd}` его публичного адаптера работы/наблюдений |
| `common` | Ровно семь общих полей действия без `action`: текущие адреса и редакции, участник, `cleanup_id`, новый `request_id` |
| `outcome_id`, `resources` | Собственный записанный итог и фактические привязки владельцев |
| `disposition`, `authorization` | Явное решение оператора и его содержательное основание |
| `observe_request_id` | Новый адрес обращения для возвращаемого наблюдения |

Все Python-блоки этого раздела используются вместе. Первый задаёт транспорт
и точные действия; обязательные входы передаются аргументами:

```python
import json
import subprocess


def run_json(command, body):
    completed = subprocess.run(
        command["argv"], cwd=command["cwd"],
        input=json.dumps(body, ensure_ascii=False) + "\n",
        text=True, capture_output=True,
    )
    if completed.returncode != 0:
        raise RuntimeError(completed.stdout or completed.stderr)
    return json.loads(completed.stdout)


def execution_call(command, operation, inputs):
    return run_json(command, {
        "schema": "stride-execution/v1", "operation": operation, "input": inputs,
    })


def read_cleanup(command, task_id, cleanup_id):
    return execution_call(command, "query", {"queries": [{
        "id": "cleanup-read", "kind": "cleanup",
        "task_id": task_id, "cleanup_id": cleanup_id,
    }]})


def prepare_cleanup(command, common, outcome_id, resources, disposition, authorization):
    inputs = dict(common, action="prepare", outcome_id=outcome_id,
                  resources=resources, commit_disposition=disposition,
                  authorization=authorization)
    return execution_call(command, "cleanup", inputs)


def continue_cleanup(command, common, disposition, authorization):
    inputs = dict(common, action="continue", commit_disposition=disposition,
                  authorization=authorization)
    return execution_call(command, "cleanup", inputs)


def observe_cleanup(command, common, work, observation):
    inputs = dict(common, action="observe", step_id=work["step_id"],
                  attempt_id=work["attempt_id"], observation=observation)
    return execution_call(command, "cleanup", inputs)
```

Второй блок задаёт одно обращение к текущему владельцу и возврат его наблюдения.
Для каждого нового обращения используйте новый `request_id` и revision последнего
полученного результата. При восстановлении сначала выполните процедуру
[сверки](#продолжение-и-сверка); она выдаёт актуальный режим работы владельца.

```python
def next_common(common, response, request_id):
    return dict(common, request_id=request_id, expected_revision=response["revision"])


def perform_once(execution_command, owner_commands, common, response):
    cleanup = response["cleanup"]
    work = cleanup["work"]
    if cleanup["status"] != "cleanup_pending" or work is None:
        return response
    observation = run_json(owner_commands[work["owner"]], work)
    return observe_cleanup(execution_command, common, work, observation)
```

Третий блок регистрирует выбранную очистку и исполняет один объявленный шаг.
Предварительно заполните все переменные по таблице. Сохраните исходный `common`
для точного повтора подготовительного обращения:

```python
prepared = prepare_cleanup(
    execution_command, common, outcome_id, resources, disposition, authorization,
)
observed = perform_once(
    execution_command, owner_commands,
    next_common(common, prepared, observe_request_id), prepared,
)
print(json.dumps(observed, ensure_ascii=False))
```

Проверьте `observed["cleanup"]["status"]`. Для очередного обычного шага передайте
полученный ответ в `perform_once` с новым `common` и адресом наблюдения.
Для выбора первоначального решения, известного отказа или сверки после потери
процесса сначала вызовите `continue_cleanup` по соответствующей процедуре выше.
При `unknown` ожидайте установления исхода владельцем. При `cleanup_complete`
прочитайте и сохраните полный результат; очистка объявленных ресурсов завершена.

## Проверки

Из корня checkout выбранным тестовым Python выполните:

```sh
python -B apps/execution/tests/test_cleanup.py --suite behavior
python -B apps/execution/tests/test_shell.py --suite behavior
```

Первый вход проверяет семь групп и 45 именованных условий, включая 31 конкретный
представитель обычных ошибок wire/политики, отдельное связывание трёх полей
интеграции и допустимость `not_started` в текущей сверке. Используются реальный
CLI/store, независимый физический тестовый владелец и действительное завершение
