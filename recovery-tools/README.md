# Recovery toolkit для облачных агентов

## Назначение и границы

Этот каталог — постоянная часть **AI-poise для облачных агентов**. Он сохраняет и
восстанавливает самостоятельную рабочую копию проекта после прерывания облачной
сессии и готовит слияние с сохранившейся локальной копией. Он не является новым
Task harness, runner или источником сообщений. Git-операции и старый формат
checkpoint переиспользуют владельца `tools/work_checkpoint.py`.

Требуются Python 3.13, Git, `xz` и `zstd`. Внешних Python-зависимостей нет. Команды
ниже запускаются **из корня AI-poise**; вместо `/absolute/...` передаются реальные
выбранные оператором пути. Для восстановления из ещё не распакованного checkpoint
агент использует отдельный комплект `recovery-tools/` + `tools/work_checkpoint.py`,
полученный вместе с поставкой, либо доверенную уже установленную копию этих файлов.
Не исполняйте код неизвестного архива только ради его проверки.

Входы должны быть остановленными автономными копиями; путь нового назначения
не должен одновременно использоваться другим процессом. Упаковка не останавливает
писателей автоматически: для рабочей Task DB сначала используйте штатный backup
owner. Наличие WAL/journal, незавершённой блокировки Git, внешнего object alternate
или зарегистрированных linked worktrees требует подготовить самостоятельную копию.
**Не удаляйте живые lock/WAL-файлы ради прохождения проверки.**

Основные ограничения безопасности: существующее место назначения не заменяется;
ссылки, специальные файлы и выход из корня архива запрещены; проверяются точные
имена, размеры, права, SHA-256, HEAD, refs, рабочее состояние Git и SQLite integrity/FK.
Безопасный предел распаковки по умолчанию — 8 GiB; при известном большем объёме его
можно явно изменить через `--max-unpacked-bytes`. SHA-256 подтверждает целостность,
а не личность отправителя. Код, hooks, тесты и миграции из архива не запускаются.

## Подготовка и упаковка

`pack` сохраняет **все обычные файлы переданного каталога**, включая `.git`,
игнорируемые БД, конфиги и незакоммиченные файлы. Он ничего не очищает неявно.
Оператор заранее готовит отдельную копию и проверяет её состав: убирает
воспроизводимые caches, virtualenv, test outputs, logs, старые checkpoint-транспорты
и временные worktrees. Авторские документы, реальные БД и единственный WIP не мусор.
Не удаляйте единственную копию изменений из worktree: сначала сохраните их в
отдельном Git ref/commit либо отдельном checkpoint. Нужные ветки остаются в `.git`.
Для нескольких linked worktrees делайте отдельные самостоятельные снимки.

```bash
python recovery-tools/cloud_recovery.py pack \
  --project /absolute/prepared/ai-poise \
  --output /absolute/new-checkpoint \
  --compression compare
```

`compare` один раз сжимает **тот же tar** посредством `xz -9e -T1` и
`zstd --ultra -22 -T1`, измеряя фактические время и размер. Выбирается меньший архив,
кроме случаев, когда он требует более 600 дополнительных секунд или не менее чем
десятикратного времени самого быстрого варианта. В этих случаях выбирается быстрый.
Измерения сохраняются в `CHECKPOINT.json`; промежуточные tar и проигравший вариант
удаляются из нового временного каталога, а не из исходного проекта.

Результаты:

- `checkpoint.tar.xz` **или** `checkpoint.tar.zst` — обычный полный архив с
  `ai-poise/.git` и файлами проекта;
- `checkpoint.recovery.txt` — открыто обозначенный ASCII/Base64 транспорт **тех же
  байтов**, с заголовком `AI-POISE-RECOVERY-TEXT-1` и SHA-256;
- `CHECKPOINT.json` и `*.sha256` — идентификаторы, checksum и измерения.

Внутри находится `ai-poise/RECOVERY-MANIFEST.json`. Он описывает все остальные файлы
и не хеширует сам себя. `HANDOFF.md` включается как обычный файл поставки, но не
должен попадать в `git add`/commit. Манифест также не нужно коммитить.

## Gmail: два представления одного checkpoint

Обязательная почтовая доставка и проверка обратного чтения относятся только к
облачной разработке. При локальной разработке они выполняются по прямому поручению
и не являются условием завершения Task или интеграции; локальная проверка checkpoint
сохраняется. Каноническая граница: [контрольные точки и
восстановление](../docs/workflows/checkpoint-recovery.md#контрольная-точка-и-восстановление).

Почтовую авторизацию выполняет **подключённый Gmail-инструмент агента**, не этот
скрипт. Отправляйте резервную копию в согласованный собственный почтовый ящик:
обычный бинарный архив и отдельно текстовый транспорт с manifest/checksums.
Бинарная часть нужна также для ручной передачи пользователем, когда коннектор
блокирует загрузку архива. Текстовую часть нужно отправлять с MIME `text/plain`,
а JSON — `application/json`; одна лишь смена расширения MIME не исправляет.

Перед `read_attachment` прочитайте метаданные письма. Если
`read_attachment_supported=false`, не объявляйте вложение прочитанным и не
повторяйте неподдерживаемый вызов. Блокировка MIME/провайдера — ограничение транспорта,
а не доказательство повреждения checkpoint. Пользователь может скачать обычный
архив и приложить его к новому чату; `restore` принимает его напрямую.

После отправки прочитайте поддерживаемое **полное** текстовое вложение обратно,
сохраните реально полученные байты и выполните:

```bash
python recovery-tools/cloud_recovery.py verify \
  --checkpoint /absolute/downloaded/checkpoint.recovery.txt \
  --sha256 EXACT_BINARY_SHA256_FROM_CHECKPOINT
```

Сверьте также SHA-256 скачанного текста с `transport_sha256`. Только после
совпадения и успешного восстановления записывайте receipt с настоящим message ID
и `readback_verified=true` **снаружи** уже запечатанного архива. Для полного формата
этот receipt ведёт агент; старый `seal-delivery` обслуживает только legacy payload.
`pack`/`verify` никогда сами не выставляют успешную доставку в Gmail.

Если размер письма не допускает оба представления, отправляйте их отдельно.
При необходимости текст можно разбить на нумерованные `text/plain` части,
сохранив SHA-256 каждой и всего текста; восстановитель принимает **собранный полный
файл**, а не отдельный фрагмент. Сначала проверяется комплектность и порядок частей.
Не маскируйте блокировку провайдера переименованием бинарных байтов в текст.

Последняя пригодная копия определяется не только датой письма: нужны полный
комплект, совпадающий SHA-256, успешная проверка и подходящая линия истории.
Отправленное письмо, доставленное вложение, работоспособный checkpoint и завершённая
Task — разные факты. Недоступность readback явно остаётся в handoff-отчёте.

## Восстановление после прерывания

Сначала проверьте уже приложенные файлы; произвольное имя вложения не означает,
что checkpoint отсутствует. Сохраните выданные пользователем оригиналы неизменными.

```bash
python recovery-tools/cloud_recovery.py restore \
  --checkpoint /absolute/checkpoint.tar.xz \
  --sha256 EXACT_BINARY_SHA256_FROM_CHECKPOINT \
  --destination /absolute/new-restoration
```

Точно так же принимаются `.tar.zst` и полный `.recovery.txt`. Для нового формата
результат — `new-restoration/ai-poise/`. Читайте его `HANDOFF.md`, затем Task DB.
Старый формат `ai-poise-work-checkpoint-1` автоматически передаётся существующему
восстановителю: результат у него — `repository/` + `payload/`, а следующий шаг
лежит в `payload/state.json`. Старый формат не содержит всего mutable project state;
не выдавайте его за полный проект.

Не заменяйте восстановлением текущую установку. Не создавайте заново Task DB/seed.
Исходный конфиг может содержать абсолютные пути пользовательского хоста. Для
облачной диагностики допустима **явно выделенная операционная копия** конфигурации:
скопируйте весь каталог выбранного project.json вместе с относительными processes,
измените в копии только `git.repository` и `paths.state` на фактические восстановленные
пути. Канонические конфиги из поставки остаются неизменными. Не делайте все внутренние
относительные process-пути абсолютными: их контракт требует относительные пути.

Укажите копию через `POISE_CONFIG`, существующий внешний каталог для
`POISE_CALLER_BINDING` и запускайте `PYTHONPATH=src python -m poise work`.
Caller binding создаёт сам штатный identity owner. Не придумывайте native session,
не подставляйте чужой launcher и не считайте этот запуск подтверждением доставки hooks
или сообщений из пользовательской IDE.

Используйте работоспособные операции Poise. Если пользователь разрешил обход
сломавшегося workflow, не устраивайте фиктивные этапы, тесты или отмену задачи ради
разблокирования; примените минимальный обход с сохранением данных. По каждому
реальному инциденту определите повторяемость, необходимость/возможность исправления,
причину (конфиг, постановка/правила или tooling), воспроизведение и исправление.
Существующую Task дополните только существенно новой информацией; повторный случай
не повод засорять историю. Новый неучтённый дефект зарегистрируйте, не исправляя его
попутно вне текущего поручения. Целостность БД, чужой WIP и ограничения платформы
не являются обходными церемониями.

## Слияние облачной и локальной копий

Сначала восстановите обе стороны в разные каталоги. Обычный вызов — **dry-run**:

```bash
python recovery-tools/cloud_recovery.py merge \
  --cloud /absolute/cloud/ai-poise \
  --local /absolute/local/ai-poise \
  --destination /absolute/new-merged-candidate > /absolute/merge-plan.json
```

Он ничего не создаёт в destination и не меняет источники. Сравнение показывает
различающиеся пути, Task identity-кандидатов и необходимость SQL-решений. Для
применения повторите команду с `--apply`. Создаётся только новый кандидат:
история cloud берётся за основу, local refs сохраняются в отдельном namespace,
изменённые tracked-файлы обеих сторон сохраняются как WIP-коммиты, а staged/unstaged
патчи сохраняют различие исходного индекса и рабочих файлов. Новые staged-файлы
учитываются. Hooks не запускаются. Git merge выполняется только в новом кандидате.

При code conflict сохраняются оба родителя и `MERGE_HEAD`; при конфликте mutable
данных остаётся облачный файл, а локальный экземпляр помещается в
`.recovery-sources/local/`. Команда возвращает `needs_decisions` и код 3, а не ложное
«слияние завершено». `RECOVERY-MERGE.json` содержит конкретные конфликты. Их разрешают
в новом кандидате; источники остаются неизменными. Существующий кандидат команда
не перезаписывает. Для продолжения уже начатого слияния используются Git/SQL в нём,
а не ещё один `merge --apply` поверх него.

Это не автоматическая семантическая дедупликация. Особенно **совпавший `task_id`
не доказывает, что записи описывают одну задачу**. Полный общий префикс неизменяемых
`task_events` (version, timestamp, data) даёт проверяемый признак общего происхождения;
расхождение или отсутствие истории требует изучить постановки и связанные записи.
Схемы разных поколений сначала приводятся к совместимому виду на отдельных копиях
через соответствующие владельцам миграции. Универсальной миграции схем здесь нет.

### Транзакционный SQL-план

```bash
python recovery-tools/cloud_recovery.py merge-db \
  --cloud /absolute/cloud/tasks.sqlite \
  --local /absolute/local/tasks.sqlite > /absolute/task-db-plan.json
```

Заполните план после чтения фактической схемы и обеих постановок. Он содержит
`cloud_sha256`, `local_sha256`, решение для **каждой** входящей задачи в
`task_identity` (`target`, `kind`: `same/new/different`, `reason`), список `statements`
и непустые `checks`. В `statements` допускаются только `INSERT`/`UPDATE` с
`parameters` и точным `expected_changes`; в `checks` — `SELECT`, `parameters` и
ожидаемые строки `expected`. Источник доступен read-only как `incoming`, новая копия
облачной базы — как `main`. `INSERT OR REPLACE`, DELETE, DDL и запись в incoming
не допускаются.

Для разных задач задайте **разные** target IDs и перенесите через INSERT весь их
граф: Task, события, submissions, sections, evidence, Sprint membership/dependencies
и другие связанные записи фактической схемы. SQL `seq` и ссылки на submissions
перенумеровываются согласованно. Одинаковая session identity также не разрешает
перезаписать другой binding. Не переписывайте старую историю в качестве разрешения
конфликта. Для уточнения реально общей задачи допустим явный UPDATE текущей записи.
Проверки должны доказывать сохранность обоих смысловых графов: одних итоговых count
и FK недостаточно для утверждения, что весь смысл перенесён.

```bash
python recovery-tools/cloud_recovery.py merge-db \
  --cloud /absolute/cloud/tasks.sqlite \
  --local /absolute/local/tasks.sqlite \
  --plan /absolute/reviewed-task-db-plan.json \
  --output /absolute/new-merged-tasks.sqlite
```

Инструмент проверяет hashes до применения, выполняет одну транзакцию на новой копии,
проверяет affected rows, postconditions, наличие всех target Task IDs, integrity/FK,
повторно сверяет источники и лишь затем публикует новый файл. При ошибке транзакция
откатывается и output не появляется. Сам выбор правильного identity mapping и
полнота прикладных SQL-проверок остаются ответственностью рассматривающего схему
агента; инструмент не объявляет автоматическое понимание смысла задач.

Для одновременного слияния проекта передайте `merge --database-plans FILE.json`:
объект отображает repository-relative путь каждой БД в соответствующий проверенный
SQL-план. Без такого плана различающиеся SQLite-базы сохраняются как конфликт, не
накладываются друг на друга и не объявляются объединёнными.

## Проверки и передача следующему агенту

```bash
PYTHONPATH=src python -m pytest -q \
  tests/delivery/test_cloud_recovery.py tests/delivery/test_work_checkpoint.py
PYTHONPATH=src bash tests/smoke.sh "$(command -v python)"
```

Это узкие проверки recovery и штатный bounded smoke, **не full suite** и не проверка
живой IDE. В `HANDOFF.md` указывайте HEAD/branch, DB SHA, текущую Task, оставшуюся очередь
в порядке регистрации, реальные ограничения, сохранённый WIP и полученный Gmail
receipt. Не коммитьте HANDOFF, временные receipts или результаты этой упаковки.
