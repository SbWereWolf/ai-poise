# Повторяемые проверки без потери диагностики

Срез начат: **2026-09-07T14:42:55+05:00**. Документ сохранён: **2026-09-07T15:04:48+05:00**. Срез: **HARNESS-PILOT-02**.

## Зачем изменён существующий инструмент

В HARNESS-PILOT-01 общий запуск оставил семь отказов и один незавершённый модуль.
Адресные повторы прошли, но не доказали причины первоначальных отказов. Более того,
старый `run_test_packages.py` удалял временный каталог каждого pytest-процесса после
отказа. Пути к полным результатам вложенных команд в traceback переставали работать.

Исправлен существующий вспомогательный инструмент, а не создан ещё один runtime Harness.
Он по-прежнему исполняет модули отдельно: это требуется текущим тестам с одинаковыми
именами файлов и разными локальными conftest. Весь набор принимается одним запуском.

## Явный вызов

```bash
export PYTHONPATH="$PWD/src"
python tools/run_test_packages.py \
  --root "$PWD" \
  --output /tmp/harness-regression-new \
  --workers 2 \
  --timeout 900 \
  --success-workspaces delete
```

Все параметры обязательны. `output` — новый каталог вне проверяемого дерева.
`--timeout` ограничивает один процесс pytest модуля; он не меняет зарегистрированные
таймауты проверок проекта или таймауты внутри тестов. Значение 900 использовалось для
внешнего супервизора в этом срезе, не является новым скрытым значением по умолчанию.
Два worker выбраны явно для данного контрольного прогона, не выведены из количества CPU.

`--success-workspaces keep` сохраняет и успешные временные каталоги. При `delete` удаляются
только успешно завершённые. Каталог отказа, таймаута или отсутствующего итогового XML
остаётся независимо от этого выбора. Никаких автоматических повторов нет.

## Файлы результата

* `NN-test_module.log` и `.stderr.log`: исходные потоки pytest;
* `.xml`: полученный от pytest JUnit, когда он существует;
* `.json`: команда, timestamps, код, timeout, ошибка отчёта, случаи, путь workspace;
* `workspaces/NN-test_module/`: изолированная тестовая среда; обязательно сохраняется при отказе;
* `result.json`: один итог всех пакетов и отсутствие автоматических повторов;
* `source-hashes-before.json` / `source-hashes-after.json`: контроль кода, тестов,
  конфигов, примеров, инструментов и pyproject.

Имена здесь — протокол вспомогательного development-инструмента, не бизнес-формат Task.
Рабочие данные приложения не регистрируются агентом вручную. Их создают существующие
Task/Artifact/Evidence API из выполняемых тестов; инструмент лишь не удаляет их при отказе.

## Что считается успехом

Нужны завершённый процесс с кодом 0, корректный непустой JUnit, отсутствие failure/error,
уникальность идентификаторов случаев и неизменность проверяемых исходников. Skip выводится
отдельно и не считается PASS. Пустой выбор модулей — ошибка, не зелёный набор из нуля тестов.

Отсутствие или повреждение XML записывается как отдельная диагностическая причина.
Одинаковые имена методов разных тестовых классов не объединяются. Подготовленная ранее
рабочая папка пакета и его результаты не затираются повторным вызовом.

## Исполнение и ограничения

Используется существующий `harness.execution.run_command`, а не отдельная реализация
ожидания команды. При timeout останавливается POSIX process group запущенного pytest;
проверен обычный дочерний процесс в той же группе. Это не обещание остановить произвольного
демона, намеренно создавшего другую session, и не интерфейс управления живыми IDE/Codex.

Повторный зелёный запуск не переписывает первоначальный неуспешный. Устойчивость на двух
worker сама по себе не доказывает, что причиной каждого старого отказа была нагрузка.
