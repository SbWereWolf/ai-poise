# Пересчёт выполнения требований

## Статус и область

Это согласованный предметный проект политики Requirements. Таблица и примеры
определяют смысл пересчёта. Автономный CLI реализует граф, постановки, публикацию,
приём исходов, глобальную оценку и явный выбор подтверждений. Точные рабочие
пакеты и последовательность действий приведены в
[инструкции исходов](outcome-operations.md). Настоящий документ не добавляет запускаемую команду или wire schema.
Действующие команды описаны в [руководстве графа](graph-req.md), проект публичной
границы — в [Requirements contract](contract-req.md#44-outcome-и-satisfaction).

## Основание текущего решения

Requirements сам решает, какие требования выполнены. Execution предоставляет
факты положительного, отрицательного или отменённого исхода, а публичный
вызывающий переносит эти факты между владельцами. Requirements не читает
хранилище Execution. Переход процесса в terminal сам по себе не подтверждает
выполнение требования.

Текущая глобальная оценка Application/System включает:

1. Актуальную выбранную редакцию реестра Application/System и верхних связей.
2. Все относящиеся к ней содержательные `current` требования из текущих
   зарегистрированных постановок **всех** Task, с их полными нижними связями.
3. Собственную выбранную публикацию каждой Task для её текущей постановки либо
   явно отмеченное ожидание публикации. Непубликованное текущее обязательство
   остаётся невыполненным ребёнком.
4. Явно допущенное Requirements положительное подтверждение каждого текущего
   ключа либо его отсутствие. Подтверждение совместимо с выбранными постановкой
   и публикацией этой Task; совпадение текста или local key этого не доказывает.

Task key имеет смысл вместе с Task и постановкой. Факт подтверждения имеет
точную ссылку `{task_id, snapshot_revision, key}`. `Task-A/R1` и `Task-B/R1` —
разные обязательства, даже когда local keys одинаковы. Generation Execution,
постановка Requirements, публикация snapshot и отдельная attempt различны.
Номер runtime version не определяет новую попытку.

Локальный запрос по одному Task snapshot описывает только выбранную Task и её
исторические связи. Его полнота не является глобальным выполнением Application
или System: у того же Application остаются требования других Task. Глобальное
решение использует весь описанный выше набор. Это предметное различие;
Транспорт реализован в [текущем профиле](outcome-operations.md), физические записи —
в [собственном хранилище](storage-req.md#публикации-исходы-и-решения).

## Правила оценки

- TR выполнен при явно допущенном положительном подтверждении его точного
  текущего основания. Отрицательный или отменённый факт положительного
  подтверждения не содержит.
- AR выполнен, когда его полный набор связанных текущих TR непуст и выполнен
  каждый TR из всех Task. SR выполнен, когда его полный набор связанных текущих
  AR непуст и выполнен каждый AR.
- Содержательный `current` AR без TR остаётся невыполненным ребёнком своего SR.
  Содержательный `current` SR без AR тоже невыполнен. `future` placeholder и
  `obsolete` не дают положительного evidence.
- `applicable` отражает присутствие содержательного current узла в текущем
  основании. Пустой child set такого узла даёт `applicable=true`,
  `satisfied=false`. Узел, вышедший из current applicability, имеет оба значения
  `false`; прежний положительный результат остаётся историческим.
- Показанные child sets являются полными текущими применимыми наборами. У
  неприменимого узла текущий эффективный набор пуст. Исторические рёбра при этом
  сохраняют собственный смысл.

## Факты, текущий выбор и история

Факт исхода и выбор подтверждения — разные данные. Exact повтор того же
`outcome_id` и содержания сохраняет один факт и текущий выбор. Он не отменяет
более позднее явное решение Requirements о замене подтверждения.

Новая, неудачная или отменённая альтернативная attempt сама по себе не меняет
ранее допущенный положительный результат. Для замены Requirements явно
устанавливает применяемый новый результат по конкретным ключам либо отсутствие
положительного подтверждения. Старый факт сохраняется в истории. Если явное
решение установило отсутствие подтверждения, ключ невыполнен вследствие этого
решения, а не вследствие автоматического отзыва при отрицательном исходе.

Флаги успеха альтернативных attempts не объединяются OR. Разные TR могут иметь
разные явно допущенные подтверждения в одном глобальном решении; затем действует
правило всех связанных детей. Выбор не определяется скрытым last-write-wins.
Выбор оформляется реализованной операцией `select_confirmation`, которая
принимает известный положительный `outcome_id` или `null`. Первый положительный
факт текущей публикации допускается автоматически только при отсутствии решения
для ключа. Первое явное `null` уже является решением; последующий новый факт
сохраняется в истории и ожидает явного выбора. Negative/cancelled сами решения
не создают, поэтому последующий первый positive допускается обычным порядком.

| Принят последний недостающий положительный TR | Подтверждения всех Task сохранены | Выполнены AR с полным набором TR и SR с полным набором AR | C02 |
| Exact повтор факта | История и текущий выбор прежние | Ни второго вклада, ни перемотки более позднего выбора | C03, C12 |

## Старые и новые родители

Для изменения нижней связи учитываются затронутые прежние и новые AR, затем все
их прежние и новые System parents. Для изменения верхнего ребра учитываются оба
его прежних и новых родителя. Родитель, который был только в старом окружении,
тоже получает текущую оценку: он мог опустеть или выйти из applicability.

Изменение live реестра даёт новое текущее решение, но не переписывает frozen
snapshot. Смена публикации одной Task не выбрасывает обязательства и подтверждения
остальных Task. Если новое основание требует использовать прежний факт, его
совместимость и допуск оформляет Requirements отдельным явным решением.

## Независимые проверяемые примеры

Полные вымышленные данные находятся в
[outcome-recalculation-examples.json](outcome-recalculation-examples.json).
Каждый пример самостоятелен: повторяемые ID не связывают разные примеры в одну
историю. `before`/`after` содержат текущие постановки, выбранные публикации,
полный верхний граф, факты и выбранные подтверждения. `expected_before` и
`expected_after` содержат все TR, полные AR/SR child sets и явные значения
applicability/satisfaction. `affected_systems` отдельно задаёт затронутых родителей.
Это предметные данные для разбора, **не пакет публичного CLI**.

| Примеры | Ручной разбор |
| --- | --- |
| C01 → C02 | A.R1 и B.R1 имеют разные Task identities. При одной A выполнен только APP-Y; APP-X ждёт B. После B выполнены оба AR и оба SR. |
| C03, C12 | Повтор не создаёт второй факт. После явного снятия выбора A повтор старого o-A не выбирает его заново. |
| C04, C09 | Cancelled/negative — штатные факты без положительного подтверждения. Они не выполняют B и не отзывают выбранный A. |
| C05–C07 | Прежний snapshot при restart сохраняет оценку. Новая A-постановка без допущенного подтверждения делает A невыполненной; B и его подтверждение остаются. Ожидание публикации не исключает A из детей. |
| C08 | APP-Z без TR невыполнен. SYS-B требует APP-X и APP-Z и невыполнен; SYS-A по APP-X/APP-Y выполнен. |
| C10–C11 | Явный новый положительный выбор A сохраняет выполнение. Явное отсутствие подтверждения A оставляет B выполненным, но делает оба AR/SR невыполненными. |
| C13 | У APP-X нет TR, у SYS-B нет AR. Оба current узла applicable, оба невыполнены; SYS-A также ждёт APP-X. |
| C14 | Отдельный нижний граф: APP-X требует только подтверждённый A, APP-Y — неподтверждённый B. OLD теряет единственного ребёнка и становится невыполненным; NEW требует X и Y и тоже невыполнен. Проверены OLD и NEW. |
| C15 | Прежний OLD становится obsolete: текущие applicable/satisfied равны false. Его исторический положительный результат сохраняется. |

Проверка примера состоит в чтении его собственных полных child sets, сопоставлении
каждого TR с явно выбранным exact положительным фактом и разборе каждого AR/SR по
правилу непустого полного набора. Независимый проверяющий повторяет этот разбор.
Чтение JSON и проверка ссылок подтверждают форму документа; они не являются
исполнением приложения или доказательством runtime satisfaction. Поведение CLI
проверяют отдельные [17 исполнимых сценариев](../tests/test_outcome_cascade.py),
а [рабочая инструкция](outcome-operations.md) показывает текущий транспорт.
