# Общая ограниченная граница SQLite-записи

Текущий контракт подготовки и записи Task/Sprint и специализированного Requirements apply.
Актуализировано 20 октября 2026 года. Политика физического ожидания из R03 сохранена;
подготовка доменного изменения отделена от окончательной пишущей транзакции.

## Подготовка и короткая запись

Обычный native-путь записи Task разделяет работу на три части:

1. Короткое чтение фиксирует согласованные исходные строки выбранных владельцев.
   Снимок, соединение и охватывающий их project fence закрываются до полной подготовки.
2. Вне этого контекста выполняются восстановление доменных объектов, валидация,
   внешние наблюдения и подготовка сохраняемых значений. Длительная подготовка A
   позволяет независимой операции B завершить запись.
3. Пишущий владелец открывает существующую транзакцию, сначала проверяет квитанцию
   запроса, затем актуальность выбранных источников и полномочий. Подготовленные
   изменения и квитанция сохраняются атомарно; ошибка до COMMIT откатывает запись.

В Task-пути [SqliteUnitOfWork](../../src/poise/infrastructure/sqlite/uow.py) возвращает
закрытый снимок `SqliteTaskInputs`. Его [проверка
источников](../../src/poise/infrastructure/sqlite/task_inputs.py)
сравнивает факты объявленного read-set; пространство распределения ID имеет собственную
проверку выбранного ID и квитанции. Application владеет доменным решением, repository —
подготовленной записью с optimistic version и FK. Отдельные версии execution, ActionRun,
Sprint и других владельцев продолжают защищать их собственные изменения.

Публичные `record/content/evidence_view/verification_registry` в
[TaskQueries](../../src/poise/infrastructure/sqlite/queries.py) закрывают свой SQL-снимок
перед соответствующим восстановлением и проекцией. `content`, `evidence_view` и активный
`verification_registry` восстанавливают полный Task с прежней валидацией. Newborn registry
сохраняет отдельные draft methods и исторический реестр; они не становятся активным договором.
`record`, Store и accounting используют собственные проекции и проверки, а не добавленную
полную проверку Task. Связанные данные читаются совместно там, где нужны ответу:
например, Task и locations для evidence либо metadata, methods и история для record.

Requirements использует отдельный путь: read-only запрос получает согласованный снимок,
а постоянное изменение сначала записывается в DML-файл и применяется стандартным yoyo.
Истории DDL и DML разделены; транзакция каждой миграции и её учёт принадлежат инструменту.
Этот путь не использует Task receipts как журнал миграций. Его точный
[контракт](../workflows/requirements-registry.md#конкурентная-запись) принадлежит реестру
требований.
Разделение подготовки не распространяется автоматически на произвольный callback или
библиотечный helper, которому вызывающий код явно передал открытую транзакцию.

Снимок чтения использует query-only соединение и существующие бюджеты допуска:
`lock_seconds` для подготовки пишущего владельца, `sqlite_read_seconds` для operational read.
Чтение не создаёт и не мигрирует хранилище. Закрытие SQL-контекста не освобождает
Task/worktree claim. Параллельных физических SQLite writers этот протокол не обещает.

## Конфликт и повтор запроса

| Условие | Результат и продолжение |
|---|---|
| Найдена квитанция точного запроса | Владелец возвращает сохранённый результат; устаревший подготовленный снимок не заменяет replay. |
| Тот же request ID использован с другим intent | Предметный отказ; сохранённая квитанция остаётся прежней. |
| Изменились источники, revision или полномочия, от которых зависит запись | Подготовленное изменение не публикуется. Вызывающий код получает конфликт/отказ соответствующего владельца и явно согласует повтор. |
| Требуется только переждать физическую SQLite-границу | Повторяется разрешённая SQL-граница в её бюджете, а не всё тело операции. |
| Поздняя SQL-ошибка до COMMIT | Откат всего набора изменений и его новой квитанции. |

После освобождения блокирующей записи запрос повторяют явно. Для восстановления
неопределённого результата сохраняют исходный пакет целиком: request ID, ожидаемую
версию и операции. Если исходный запрос уже был принят, точный replay найдёт его
квитанцию. Если нужен пересмотр intent по новым данным, сначала читают и согласуют
актуальное состояние; изменённый пакет не называют точным replay. Особенности
[Requirements API](../workflows/requirements-registry.md#ошибки-и-восстановление)
проверяют фактический файл, данные и применённую историю yoyo; Task request receipts
не подменяют состояние миграционного инструмента.

Отдельное узкое продолжение принадлежит распределению Task ID: preview ничего не
резервирует. При занятом выбранном автоматически распределяемом ID владелец может
заново выбрать ID и чисто скомпилировать зависящие от него значения из сохранённого
preflight. Внешняя подготовка не запускается повторно этим циклом. Явный занятый ID
отклоняется; границы пространства задаёт существующая policy. Не гарантируются новый
лимит попыток или успех при непрерывной конкуренции. Пакетная публикация сохраняет
дочерние Task, родительский результат, Sprint и квитанции в своей общей транзакции.
Владельцы описаны в [границах ответственности](boundaries.md#подготовка-независимых-записей).

## Основание

Историческое основание R03: до исправления
[RequirementsStore._transaction](../../src/poise/infrastructure/requirements_registry.py)
брал application flock, открывал SQLite с timeout=0, затем deferred BEGIN. Независимый
SQLite writer не обязан брать тот же lock-файл. Поэтому первое чтение может пройти,
а DML — немедленно завершиться database is locked. Исходный опыт —
`../../projects/ai-poise/standalone/REVIEW-PLAN-20260918/artifacts/source-review/evidence/R03-requirements-contention.json`
(исторический артефакт; не включён в исходную поставку 044A)
фиксирует такой отказ за ~0.00032 s при writer hold 0.15 s и lock_seconds=1.0.
Повреждение БД в этом опыте не показано; нужен bounded wait, не восстановление утраченных
данных. Task Database к тому моменту уже использовал общую физическую границу.
Решение `REVIEW-ARCH-A05` внедрено в `REVIEW-BUG-R03` 18 сентября 2026 года на базе
`101304f58aca34a1104d2cdcc27d6434e5f9fca8`. Эти числа описывают прежний опыт, а не
текущую гарантию задержки или повторно выполненное измерение.

## Решение и отображение параметров

Task SQLite использует существующий
[write_transaction](../../src/poise/infrastructure/sqlite/transaction.py).
Настроенные `paths.database`/`paths.lock` выбирают именно Task store;
`limits.lock_seconds` и `limits.poll_seconds` задают конечные ожидания физических границ.
Последовательность записи: flock → connect → FK ON → BEGIN IMMEDIATE →
однократное тело → COMMIT → close. Повторяются разрешённые границы BEGIN/COMMIT при
SQLITE_BUSY, а не тело операции. Отдельный бюджет каждой границы не является общим
timeout запроса. При неуспешном COMMIT транзакция откатывается; диагностика сохраняется.

Постоянная запись Requirements выполняется другим существующим владельцем:
[RequirementsMigrations](../../src/poise/infrastructure/requirements_data_migrations.py)
создаёт прямой DML-файл и применяет его стандартным backend yoyo под project fence.
Стандартная блокировка yoyo и SQLite busy timeout используют `limits.lock_seconds`;
FK включены. Истории схемы и данных разделены. Read-only RequirementsStore ничего
не создаёт, не мигрирует и не содержит постоянного writer.

## Неизменяемые контракты

Task сохраняет собственные проверки версии, полномочий, request ID и сохранённого
результата. Изменения и Task receipt атомарны в транзакции своего владельца.
Requirements использует применённые ID стандартной истории yoyo; `command` принимает
литеральный SQL и его откат, а revision реестра изменяется только явно записанным DML.
Исторические Task snapshots не переписываются. Проверка реестра перед публикацией Task
не создаёт распределённую транзакцию между двумя файлами.

Новое Requirements-хранилище создаётся из непустой инфраструктурной DDL-истории
и DML-истории документации, существующее не перезаписывается. Обычный read не создаёт
схему. Порядок применения, отката, переноса и замены истории принадлежит
[реестру требований](../workflows/requirements-registry.md#предметные-области-и-миграция-схемы);
размещение — [матрице хранилищ](storage-lifecycle.md#владельцы-и-версии).

## Историческая матрица проверки R03

| Сценарий | Ожидаемый инвариант |
|---|---|
| Независимый writer отпускает за 0.15 s при budget1 s | Apply дожидается, revision увеличена один раз, receipt request один. |
| Writer держит дольше маленького явного бюджета | Контролируемая ошибка в пределах бюджета+погрешности, исходные rows/revision/request IDs неизменны. |
| COMMIT блокирует короткий читатель DELETE-журнала | Повторяется только COMMIT; счётчик исполнения domain apply=1. |
| COMMIT блокирован сверх бюджета | Полный rollback, version/links/request response не опубликованы. |
| Revision устарела во время ожидания | VersionConflict после acquisition, без потери чужой записи. |
| Точный replay / reused ID с другим digest | Первый не меняет registry/revision; второй отвергается. |
| Domain exception/SQL constraint внутри тела | Полный rollback, FK/integrity остаются корректными. |
| Две инициализации и независимый SQLite writer | Одна целая schema, обе совместимые операции проходят после bounded wait; неизвестная schema не меняется. |

Таблица сохраняет матрицу исторического R03, выполненную во временных SQLite-файлах
с короткими удержаниями и Events. Текущие причинные проверки подготовки используют
порядок событий: A остановлена на подготовке, B действительно COMMIT до продолжения A.
Отдельные проверки покрывают изменение источников, точный replay, поздний rollback,
публичные Task-проекции и конкуренцию при создании. Они не задают норматив времени
или throughput; сохранённое свидетельство относится к своей точной source revision.

## Альтернативы и ввод

Повысить sqlite connect timeout недостаточно для точного различения boundary retry и
read-to-write upgrade; новый blanket retry ещё хуже — повторяет тело. Удаление flock
ломает существующую сериализацию сотрудничающих владельцев. Объединение Requirements
с Task DB не требуется для устранения дефекта и меняет их независимые обязанности.

Исторический ввод R03 заменял делегирование физической записи. Нынешнее разделение
подготовки также сохраняет формат данных и настроенные пути; новой миграции схемы
для него нет. Размещение данных, допустимые переходы версий и резервное копирование
остаются у [существующих владельцев](storage-lifecycle.md#владельцы-и-версии).
