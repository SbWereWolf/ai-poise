# Harness recovery

Apply when supported harness automation, including Poise, fails or has a demonstrated
capability gap that prevents authorized work through its ordinary owner.
A failing subject test needs subject remediation, not a harness workaround.

Use working applicable compositions rather than rebuilding their sequence manually
out of preference or unfamiliarity. Select the operation matching the actual intent;
do not invent a combined form or submit fake stage work for a partial-material handoff.
For a genuine gap, follow the [automation proposal contract](../../../docs/operations/harness-incident-journal.md#неподходящая-автоматизация).

Canonical policy: [harness failure and manual
recovery](../../../docs/governance/development-rules.md#сбой-harness-и-ручной-обход).
Read that section before choosing a recovery; it owns classification, authority,
logs, rollback, repair drafts and reconciliation. This skill adds no repair API.
Record confirmed defects in the appropriate existing Task, or register one draft.
Keep substantive incident/recovery descriptions in that Task; keep
only a concise Task-linked known-bug summary in versioned documentation. Follow
[Task-owned incident materials](../../../docs/operations/harness-incident-journal.md#материалы-в-задаче-дефекта).
Remove completed Task/session working files after delivery. Do not create external
permanent operation archives unless the user explicitly requests them.
For lasting history preserve conditions, cause or uncertainty, effects, actions
and outcomes: up to ten representative examples per equivalent failure type plus
an actual-event counter and observation period. Copies and repeated output lines
are not extra incidents; unknown frequency stays unknown. Extract unique useful
facts before deleting full outputs, snapshots, databases, environments, traces
and checksum material. Independently sample-check a dry run before old-attachment
cleanup. Follow [narrative-only retention](../../../docs/operations/harness-incident-journal.md#содержательная-история-без-технического-архива).
Before an agreed restart, both roles inspect the actual progression/position using
the [canonical preflight](../../../docs/workflows/pilot-task-preflight.md#сверка-продолжения-перед-restart).

1. Read the actual input, full saved response, contract/configuration and effect state.
   Classify agent/task-planner misuse, configuration, code or manual-data damage;
   keep unproved causes explicitly unknown and assess recurrence separately.
2. Use the available public owner first. Choose a proportionate correction or manual
   route within the assignment. Configuration defects remain obligations until corrected;
   reject and safely roll back failed fixes rather than layering contradictory settings.
3. Record the refusal and recovery in Task-owned materials with cause, authority,
   exact changes, alternatives and verification. Transfer only necessary reproduction
   inputs to the defect Task before current-work cleanup. If an API is unavailable,
   use the authorized manual owner route there; do not invent an API or external store.
4. Reuse the matching defect Task or register one draft when none fits. Repeated
   occurrences append their date and facts there. Registration does not authorize
   code repair. An expected refusal or caller error is not automatically a defect.
5. Verify the originally blocked action and affected adjacent scenarios. Distinguish
   recovered subject work, repaired configuration/code, unknown outcomes and native
   lifecycle status. Reconcile through the public owner when available again.

A one-value database edit is not automatically safe. A manual managed-data correction
needs the canonical authorization, exact before/after, preserved recovery inputs,
exclusive writers and integrity verification. Preserve foreign WIP and claims, historical
stages and native receipts. Never infer an unknown external effect, acceptance or delivery.
Keep a real blocker explicit when no safe authorized route exists; do not invent success.
