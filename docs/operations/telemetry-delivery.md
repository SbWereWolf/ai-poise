# Отказоустойчивая доставка телеметрии AI-poise

## Асинхронная доставка без блокирования работы

`OptionalTelemetry` передаёт неизменяемый `TelemetryEnvelope` существующему
`AsyncTelemetryDispatcher`. Сохранение spool, ожидание optional SQLite и обработка
наблюдений выполняются **в worker**, не на пути результата Task. Сбой диска, очереди,
получателя или worker не отменяет корректный результат работы. Основная Task DB
не участвует в доставке и не ослабляет свои проверки ради необязательных наблюдений.

`TelemetrySpool` — адаптер доставки для того же dispatcher, а не второй runner,
Task store, источник сообщений или универсальный механизм тестирования приложений.
Единственный получатель `SqliteAccounting.accept_telemetry` сохраняет envelope и
его допустимые проекции **в одной транзакции optional DB**. Неудачная проекция
откатывает и envelope: retry не должен принять недоставленный результат за duplicate.

Подтверждение постановки в оперативную очередь **не означает fsync**. Между capture
и сохранением worker существует окно потери при аварийном завершении всех процессов.
После атомарного сохранения запись переживает перезапуск, доставка становится
at-least-once; идентичный envelope принимается получателем идемпотентно. Сбой после
commit получателя, но до удаления файла приводит к безопасному повтору, не новому
учёту. Exactly-once и полнота всех наблюдений не заявляются.

## Подключение и пределы

Необязательный именованный раздел manifest `telemetry_delivery` подключается через
существующий редактор `poise project`. Его значение — объект
[готового примера](../../config/development/telemetry-delivery.json), а не строка
с путём к этому файлу. Без раздела сохраняется прежняя best-effort доставка без
durable spool. Пользовательский manifest автоматически не переписывается.

`directory` — явный путь optional storage: абсолютный используется буквально,
относительный — внутри уже настроенного mutable state. Это не меняет разрешение
путей инструментов, hooks, исходников или рабочей копии. Все численные пределы
задаются явно: количество/байты записей, размер события, число попыток, размер
пакета replay, интервал повтора и ожидание lock. Для retry-метаданных резервируется
ограниченный запас; очередь может отказать до исчерпания физической ёмкости диска.

In-flight обработка учитывается в лимите dispatcher; его локальная память duplicate
ограничена. Постоянная идемпотентность принадлежит получателю optional DB, не этому
ограниченному кэшу. Завершённые detached receipts собираются без ожидания. Существующее
Linux detached-исполнение сохранено; поддержка другого host здесь не добавляется.

## Повтор и явная диагностика

При новом envelope worker выполняет ограниченный replay. Для восстановления
без новой работы есть отдельная явная операция:

```bash
python tools/telemetry_delivery.py --config /absolute/project.json status
python tools/telemetry_delivery.py --config /absolute/project.json replay
```

`status` не создаёт очередь или базу и не меняет Task. Он сообщает pending,
исчерпанные попытки, повреждённые записи, байты и ограниченные метаданные; содержимое
сырого payload и тексты исключений не публикуются. Ошибки отражаются классом
исключения. Это наблюдение очереди, не доказательство полноты телеметрии.

`replay` — сознательный I/O, который может ждать в пределах настроенных locks и
получателя. Фоновый бесконечный polling не создаётся. Для каждой записи выполняется
не более одной due-попытки за replay, всего не более `batch_items`. Попытка сохраняется
до вызова получателя, поэтому авария worker тоже расходует ограниченный бюджет.
`next_attempt_at` — техническое время следующей попытки, **не время события источника**.

После `max_attempts` запись остаётся для диагностики, но автоматически не повторяется.
Устранить причину и увеличить явный бюджет доставки можно через редактор конфигурации;
это не сбрасывает уже записанное число попыток. Повреждённые файлы, symlink, неожиданные
файлы и переполнение не очищаются автоматически и не выдаются за успешную доставку.
При заполнении spool новые наблюдения могут быть потеряны; основные операции продолжают
работать, coverage остаётся partial. Отдельный монитор/daemon и живая внешняя API
доставка не заявляются; воспроизводимые сбои проверяются локальными получателями.
