# Таймауты зарегистрированных проверок AI poise

Эта политика относится к единому исполнителю зарегистрированных проверок AI poise. Она не задаёт способ тестирования, кэширования или построения произвольного внешнего репозитория.

## Профиль таймаута

История выбирается по точному профилю `command + workload + runtime executable/platform`. `cwd` и расположение рабочей копии в идентичность профиля не входят: конкретный filesystem path передаётся непосредственно запуску как `cwd` и не меняет правила разрешения путей самого Poise.

## Выбор лимита

Без подтверждённой истории используется явный `runtime_services.check_runner.initial_seconds`. Значение в поставляемой конфигурации является начальным эксплуатационным пределом, а не результатом измерения или переноса ERP-истории.

После успешных зарегистрированных запусков лимит вычисляется как `max(initial_seconds, ceil(1.10 × longest_verified_success))`. В историю входят только сохранённые успешные receipts того же профиля; таймауты, отмены и неуспешные проверки её не расширяют.

`progress_gap_seconds` отслеживает отсутствие байтов в stdout/stderr зарегистрированного процесса. Это только доступный сейчас configured progress probe: отсутствие вывода не является доказательством предметного зависания, поэтому hard limit и причина остановки сохраняются отдельно.

## Диагностический override

Увеличение лимита допускается только с непустой причиной и ссылкой на существующий evidence receipt. Оно не может уменьшать обычный лимит и ограничено `diagnostic_override_max_seconds`. Сам override не становится verified-success history, пока запуск не завершился успешно.

## Maintenance materialization

Каждый запуск сохраняет `timeout-policy.json` рядом с run evidence. В нём фиксируются профиль, выбранный лимит, основание выбора и IDs receipts, использованных как история. Отдельный ledger таймаутов не создаётся; авторитетной историей остаётся существующее evidence-хранилище.
