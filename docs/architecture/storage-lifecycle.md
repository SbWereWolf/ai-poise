# Жизненный цикл хранилищ

Актуализировано 29 октября 2026 года по реализации AI-poise. Это описание текущего контракта, не
разрешение на перенос данных или новую миграцию. Датированные архитектурные эскизы и старые
протоколы проверок остаются историей.

## Владельцы и версии

Пакетный [Requirements CRUD](../workflows/requirements-registry.md#пакетный-crud)
читает через RequirementsStore, а пишет через буквальные SQL-пары активной Task
и обычный yoyo. Query читает единый snapshot; предметные строки, revision и
квитанция Command входят в одну транзакцию SQL-тела. Учёт yoyo может фиксироваться
отдельно — действует [ручное восстановление](../workflows/requirements-registry.md#ошибка-записи-статуса-yoyo).
Task snapshots остаются у Task DB.

Номер `PRAGMA user_version` принадлежит конкретному SQLite-файлу. Строка конфигурации
`ddd-accounting-12` — другой контракт; её нельзя менять на основании номера SQLite schema.

| Хранилище и владелец | Текущая schema | Явное расположение | Создание и допустимое изменение версии |
|---|---|---|---|
| Task DB: Task/Sprint, execution, Evidence, Ownership и authoritative accounting через общую Unit of Work | 13 | `paths.database` и `paths.lock` внутри настроенного `paths.state` | Пустая schema 0 создаётся; известная 12 проходит только описанный ниже ownership upgrade. Остальные несовместимые версии отклоняются. |
| Requirements DB: канонические System/Application требования, области, имена и связи | 2 | `paths.requirements_database` и `paths.requirements_lock`; относительные значения — от `paths.state`, абсолютные — точно; mutable-файлы вне Git | Пустая БД создаётся отдельными начальными DDL/DML-парами обычного yoyo; открытие само схему не создаёт. Историческая schema 1 обновляется явным Task-owned `migrate` через SQL-пару; несовместимое открытие отклоняется. |
| Optional telemetry: необязательные измерения, отдельно от authoritative Task accounting | Общая SQLite schema 13 при ленивой инициализации | `accounting.storage.database` и `accounting.storage.lock`, отдельно от Task и Requirements | Используется общий `Database`, но его создание отложено до работы worker. Необязательная телеметрия не должна блокировать основной результат. |
| HookRegistry: установки, bindings, операции и hook events | 1 | `database` и `lock` настроек hook transport | Пустая schema 0 создаётся; несовместимая версия отклоняется. Эти записи не заменяют Task ownership. |
| Goal/config editor: операции редактирования и heads конфигураций | 1 | `database` и `lock` настроек редактора относительно его root | Пустая schema 0 создаётся; несовместимая версия отклоняется. Состояние редактора не является вторым владельцем Task. |

Реализация: [Task Database](../../src/poise/infrastructure/sqlite/database.py),
[RequirementsStore](../../src/poise/infrastructure/requirements_registry.py),
[TelemetryDatabase](../../src/poise/infrastructure/telemetry.py),
[HookRegistry](../../src/poise/infrastructure/sqlite/hook_transport.py),
[GoalConfigRepository](../../src/poise/infrastructure/goal_config.py). Project-config сохраняет
собственные pending/operation receipts в файлах; это не ещё одна каноническая Task DB.

Обычные Task-пути сначала получают короткий
согласованный снимок исходных строк. Полная доменная подготовка выполняется после
закрытия этого снимка и project fence. Окончательная запись использует общий механизм:
собственный flock хранилища → `BEGIN IMMEDIATE` → квитанция запроса, проверка актуальных
источников/revision и подготовленная запись → `COMMIT`. Изменения и квитанция атомарны.
Чтение-подготовка не повышается в пишущую транзакцию. Существующий пакетный Requirements
Query/Command сохраняет [свой транзакционный контракт](../workflows/requirements-registry.md#конкурентная-запись).

Для этих Task-операций повторяются только SQL-границы `BEGIN IMMEDIATE`/`COMMIT` при `SQLITE_BUSY`, не тело
операции. `lock_seconds` — отдельный бюджет каждого ожидания flock, BEGIN и COMMIT,
не общий timeout запроса. При исчерпании COMMIT-бюджета выполняется rollback.
Семантический конфликт возвращается вызывающему коду для явного согласованного повтора.
Requirements DB остаётся отдельной schema 2 со своими путями; проверка её состояния
при создании Task не образует распределённую транзакцию. См. [точную политику
записи](sqlite-write-boundary-design.md#подготовка-и-короткая-запись) и [явную миграцию
Requirements](../workflows/requirements-registry.md#предметные-области-и-миграция-схемы).

Task DB хранит собственные Task requirements и согласованный исторический снимок System →
Application → Task. Это не копия изменяемого канонического Requirements Registry. Правила полноты,
статусов и согласования — в [реестре
требований](../workflows/requirements-registry.md#публикация-и-исторический-снимок).

Наблюдение существующих рабочих данных использует отдельную read
boundary без writer flock,
инициализации и миграции. Snapshot закрепляется до тела операции;
configured SQLite admission
может повторить только эту границу при `SQLITE_BUSY`. Тело и внешние
эффекты не повторяются.
Версии в таблице выше описывают initializer/command owner; они не
разрешают upgrade из query.
Короткий снимок подготовки пишущего владельца также использует query-only соединение,
но его допуск ограничен существующими `lock_seconds` и `poll_seconds`. Operational read
сохраняет явный `sqlite_read_seconds`. В разделённых путях Task и Requirements
`registry/read/apply` после захвата строк собственный контекст закрывается перед полной
подготовкой/проекцией. Нового параметра, смены journal mode или миграции
для этого разделения нет; Task/worktree claims от закрытия SQL-снимка не освобождаются.
Первичный допуск caller и приём сообщений отделены от наблюдения.
Полный контракт и инструкция:
[наблюдение и пишущие намерения](../configuration/runtime-services.md#наблюдение-и-пишущие-намерения).

## Ограниченный переход Task DB 12 в 13

При открытии известной schema 12 выполняется только ownership upgrade. Он может очистить terminal
worktree binding, если Task уже `completed`/`cancelled` и у неё отсутствует claimant. Если остаются
неоднозначные legacy связи, база сохраняет version 12: уникальные индексы не создаются, выбор
владельца не угадывается. Незатронутая работа не должна блокироваться глобально.

Точное состояние читают через `show` с `kind: ownership_conflicts`. Исправление одного связного
конфликтного компонента выполняют публичным `recover_ownership` с его фактическим снимком и явным
решением пользователя. После устранения конфликтов создаются уникальные индексы claimant/worktree
owner и устанавливается schema 13. Это не перенос Worktree/Git-файлов и не право сбрасывать чужой
claim.

Сначала сохранить исходную базу; затем следовать [публичному контракту восстановления
владения](../workflows/batch-work.md#восстановление-неоднозначного-владения). Незнакомая непустая
schema 0, schema 11 и другие неподдерживаемые версии отклоняются. Общего преобразователя
произвольных старых баз нет.

## Явные пути и переносимая поставка

`paths.state` — явный root рабочих данных, а checkout/worktree — объект кодовой работы, не
альтернативный root установки. Task DB, Requirements DB и optional telemetry не должны ссылаться на
один физический файл либо общий lock. Requirements DB допускается вне репозитория или внутри него;
пользователь самостоятельно выбирает версионирование БД в Git, без разрешительного флага и
Git-проверки размещения. Точные условия отказа и разрешение путей: см. [владение и явные
пути](../workflows/requirements-registry.md#владение-и-явные-пути).

В доставленной конфигурации ai-poise Requirements DB настроена на
`/home/sbwerewolf/workdata/poise-project-data/ai-poise/requirements.sqlite`, lock — соседний
`requirements.lock`. Переносимая копия в полном архиве находится в
`projects/ai-poise/database/requirements.sqlite`. Распаковка архива сама по себе не записывает её на
пользовательский хост и не перенастраивает runtime.

Для другого расположения явно сопоставить все настроенные пути и сверить существующую базу с
доставленной. Не перезаписывать более новое состояние, не запускать повторный seed и не считать
статус `future` утверждением о реализованном требовании. История однократного импорта — в [импорте
утверждённой
поставки](../workflows/requirements-registry.md#однократный-импорт-утверждённой-поставки).

## Резервное копирование и восстановление

`poise backup` охватывает **только Task DB**. Он не сохраняет Requirements DB, Git, конфигурацию и
материалы Task/Sprint. Создание/восстановление требуют исключительного операторского окна: см.
[обязательное условие Task DB backup](../task-db-backups.md#обязательное-условие). Наличие одной
SQL-копии не доказывает восстановимость полного проекта.

При облачной разработке полную копию создают существующим [checkpoint
toolkit](../workflows/checkpoint-recovery.md#полная-копия-для-облачных-агентов): репозиторий с
`.git`, конфигурация, все постоянные БД и авторские материалы. Внешние настроенные БД должны быть
явно включены в переносимую поставку вместе с описанием отображения путей; инструмент не должен
угадывать их расположение и заменять более новые файлы. Остановить writers на время снимка; не
представлять разные моменты нескольких БД как одну распределённую транзакцию.

Локальная разработка не требует создания переносимых архивов или проверки
их восстановления без отдельного прямого поручения пользователя.

Для Gmail используют [prepare → отправку → полное обратное получение →
confirm](../workflows/checkpoint-recovery.md#полные-резервные-копии-в-gmail-при-непрерывной-разработке).
Успешная отправка или список имён вложений не заменяют восстановление байтов. `delivery_verified:
false` внутри подготовленного манифеста корректен: факт доставки подтверждает последующий отдельный
receipt.

Восстанавливать только в новый каталог. Проверить transport/archive SHA-256, файлы манифеста, Git
refs и целостность/FK каждой SQLite-базы, затем применить явное сопоставление путей. Исторические
или дублирующие базы нельзя удалять только из-за одинакового имени; их роль и происхождение должны
быть установлены отдельно. Утверждение о целостности снимка не является повторным запуском тестов
продукта.
