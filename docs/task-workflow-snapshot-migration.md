# Явная миграция Task workflow snapshot

Обновлено: **2026-10-13**. Исторические схемы ниже относятся к указанным точечным
операциям. Отдельный текущий контракт описан в разделе
[миграции типов и критериев этапов](#миграция-типов-и-критериев-этапов).

`task-workflow-migrate` — публичная одноразовая операция для сохранённых Task workflow
snapshots, созданных до обязательного поля `worktree_required`. Это не compatibility read,
не fallback и не общий редактор metadata. Оператор запускает её только по прямому
разрешению пользователя для точного набора Task:

1. `0077`;
2. `0081`;
3. `0079`;
4. `0078`;
5. `0074`;
6. `0063`.

Порядок входит в intent запроса. Подмножество, надмножество, замена, повтор ID или иной
порядок отклоняются. Это узкое расширение первоначального плана Task 0084 прямым
разрешением пользователя; оно не разрешает менять остальные требования или другие Task.

## Подготовка

Явно выберите `PROJECT_JSON`. Остановите всех writers Task DB, затем создайте публичную
резервную копию:

```bash
poise backup create --config PROJECT_JSON
```

Сохраните выданное имя файла. Проверьте его наличие через `poise backup list --config
PROJECT_JSON`. Не копируйте и не заменяйте SQLite-файл вручную. Целевые Task должны
существовать, не быть terminal и содержать совместимый workflow без поля
`worktree_required`. Их неизменяемый `goal_type` должен ссылаться на настроенный workflow.
Существующий claim не нужно предварительно освобождать: операция сохраняет его точное
значение и не принимает решений о liveness, передаче или замене владельца. При этом сам
владелец не должен писать в Task DB во время backup и миграции.

## Запрос

Передайте один JSON document в stdin. Поля и их набор точные:

```json
{
  "schema": "task-workflow-migration-1",
  "request_id": "migrate-authorized-six-workflows-1",
  "backup_name": "tasks-backup-20260913T120000000000Z.sqlite",
  "task_ids": ["0077", "0081", "0079", "0078", "0074", "0063"],
  "authorization": "User explicitly authorized this exact Task workflow migration."
}
```

Запуск:

```bash
poise task-workflow-migrate --config PROJECT_JSON <<'JSON'
{
  "schema": "task-workflow-migration-1",
  "request_id": "migrate-authorized-six-workflows-1",
  "backup_name": "BACKUP_NAME",
  "task_ids": ["0077", "0081", "0079", "0078", "0074", "0063"],
  "authorization": "User explicitly authorized this exact Task workflow migration."
}
JSON
```

Операция проверяет целиком названную копию и рабочую DB, все цели и lifecycle,
workflow shape и соответствие `goal_type`. Значение `worktree_required` выводится из
настроенного workflow definition. После внешнего preflight состояние повторно сверяется
под writer lock. Все шесть snapshots записываются **одной транзакцией** либо не меняется
ни один. Task IDs, lifecycle, прочее содержимое workflow, history, submissions, evidence,
dependencies, claims, results и artifacts сохраняются. Стабильный existing claim допустим;
его создание, снятие или замена после названного backup либо после preflight считается
drift и отклоняет весь пакет.

## Receipt, повтор и восстановление работы

Успех возвращает статус `migrated`, `request_id`, `backup_name`, ordered Task summaries,
старый и новый digest каждого workflow и общий `receipt`. Тот же точный запрос можно
повторить: валидированный audit вернёт тот же receipt с `replayed: true`. Тот же
`request_id` с другим intent отклоняется. Повреждённый audit, несовпадение backup/live DB
или drift также отклоняются, без частичной записи. Audit UTC получается только через
обязательный `Clock`; production использует явно предоставленный `SystemClock`.

После успеха сохраните backup и оба JSON receipt, сравните публичные read-only проекции
до и после, затем выполните native bootstrap целевых Task. Успешный bootstrap доказывает,
что runtime читает новый обязательный contract без fallback.

## Точечное восстановление Task 0082

`task-workflow-migration-2` — отдельное прямое разрешение только для Task 0082. Оно принимает
точно `task_ids: ["0082"]` и не расширяет разрешение `task-workflow-migration-1`: смешанный
набор, пустой набор, другой ID или несколько Task отклоняются до изменения данных. Этот путь
добавляет в сохранённый workflow snapshot 0082 только отсутствующий boolean
`worktree_required`, взятый из настроенного workflow того же immutable `goal_type`. Уже выданный
старый receipt schema 2 остаётся точно replayable; этот опубликованный контракт не меняется.

Корректирующая `task-workflow-migration-3` принимает только `0082`. Если schema 2 уже
добавила совпадающий boolean, schema 3 сохраняет workflow без изменений; если boolean ещё нет,
она добавляет его, не заменяя остальные поля старого snapshot актуальным workflow целиком.
Та же атомарная операция инициализирует отсутствующий `stage_contracts` в Task contract. Она
создаёт один contract на каждый сохранённый workflow stage в исходном порядке, переносит
его `allowed_paths` и назначает entry/exit gates из сохранённых workflow/task content requirements
по их stage и phase. Уже существующий `stage_contracts` либо несовпадающий boolean означает,
что точечный recovery неприменим, и весь запрос отклоняется. Обе правки выполняются одним
metadata update без изменения lifecycle columns, Task version и released handoff.

До вызова создайте публичную резервную копию через `poise backup create --config PROJECT_JSON`
в период без writers и передайте её точное имя в `backup_name`:

```json
{
  "schema": "task-workflow-migration-3",
  "request_id": "migrate-task-0082-stage-contracts-2",
  "backup_name": "BACKUP_NAME",
  "task_ids": ["0082"],
  "authorization": "User authorized workflow snapshot recovery for Task 0082."
}
```

Успех должен вернуть `receipt`; точный повтор того же запроса возвращает тот же receipt и
`replayed: true`. Миграция сохраняет lifecycle, verified result, stage, iteration, content,
feedback, evidence, history, ownership, Git binding и config identity. Summary также фиксирует,
был ли добавлен workflow boolean, факт инициализации stage contracts и
old/new digests обоих изменяемых snapshots. После сравнения публичных
проекций передайте сохранённую released Task назначенному проверяющему и выполните native bootstrap
Task `0082`. Ожидаемый восстановленный контекст — исходная verified итерация
`test_remediation`, а не новая Task и не пустой результат.

## Восстановление текущей задачи планирования

`task-workflow-migration-4` — одноразовая точечная операция только для
`ERP-HARNESS-COMPARISON-PLAN`. Она исправляет legacy Task, которой не хватает
`stage_contracts`, без restart: сохраняет ID, lifecycle, текущие stage/iteration, историю,
ownership, worktree, branch и WIP. Контракты выводятся исключительно из сохранённых workflow и
content snapshots этой Task: для каждого stage сохраняется его `allowed_paths`, а entry/exit
gates строятся по сохранённым requirements и их phase. Процесс не подменяется текущим
конфигом проекта.

Перед запуском остановите writers и создайте public backup. Запрос имеет точную форму:

```json
{
  "schema": "task-workflow-migration-4",
  "request_id": "migrate-current-task-stage-contracts-1",
  "backup_name": "BACKUP_NAME",
  "task_ids": ["ERP-HARNESS-COMPARISON-PLAN"],
  "authorization": "User authorized recovery of the current unfinished planning Task."
}
```

Успешный receipt фиксирует old/new digests workflow и contract, а затем native `bootstrap`
должен вернуть сохранённый этап `framing`. Другая Task, повторный другой intent, уже
инициализированный contract или drift базы отклоняются до записи.

Для отката прекратите все
writes и используйте только `poise backup restore --config PROJECT_JSON BACKUP_NAME` по
[контракту резервных копий](task-db-backups.md); восстановление является отдельным
разрушительным решением и не подразумевается самой миграцией.

## Миграция типов и критериев этапов

Для сохранённых задач старой установки, где определение процесса записано
в поле metadata `process`, явно выберите схему
`task-stage-criteria-process-migration-1`. Она использует тот же публичный
вход, mapping, владельца публикации и резервную копию. В рамках переноса
поле `process` заменяется на `workflow`, после чего применяется общий
механизм переноса критериев. Обычное чтение задач старый формат не принимает.
История, требования, результаты, версии и владельцы задач сохраняются;
исторические вложенные снимки не переписываются. Постановка без выбранного
процесса сохраняет исходный текст metadata. Для задач, уже использующих
`workflow`, используется `task-stage-criteria-migration-1`.
При явном выборе `--project-settings` источником переноса process-формата
служат зарегистрированный manifest и его наблюдённая редакция. Архивная
квитанция создания проекта не требуется: отсутствие такой квитанции не
мешает определить проект и переносимые данные. Запись, pending и новую
квитанцию результата выполняет существующий владелец обновления проекта.
Формат архивного результата `readiness` создания проекта не определяет
возможность переноса этапов и не является условием допуска миграции.
Настроенные процессы могут быть уже обновлены независимо от старых Task.
Для process-переноса такой процесс сохраняется без перезаписи файла, если
все назначения, полномочия, состав и порядок этапов совпадают с mapping.
Полностью историческое определение получает явно заданные назначения.
Допустима установка, где часть определений уже обновлена. Неполные или
противоречивые аннотации внутри одного определения требуют исправления
исходных данных; перенос не выбирает значения вместо оператора.

`task-stage-criteria-migration-1` — отдельная схема того же публичного
`poise task-workflow-migrate --config PROJECT_JSON`. Она не является пятой версией
исторических точечных схем выше и не расширяет их списки Task.
Операция требует прямой авторизации, исключительного окна без writers и публичной
резервной копии всей выбранной Task DB. Она классифицирует сохранённые этапы
явно, без угадывания по роли, имени или handler.

### Выбор владельца публикации

Выберите владельца, который опубликовал настроенные процессы проекта.
Без `--project-settings` операция использует настроенный редактор каталога:
каждый workflow должен совпадать с его зарегистрированным target и managed head.
Если процессы созданы владельцем подготовки проекта и находятся в его отдельном
пакете, передайте путь к действующим setup settings:

```bash
poise task-workflow-migrate \
  --config PROJECT_JSON \
  --project-settings PROJECT_SETUP_SETTINGS < MIGRATION_JSON
```

`PROJECT_JSON` — текущий manifest выбранного проекта; `PROJECT_SETUP_SETTINGS` —
существующий документ схемы `project-setup-settings-1`, использованный его
владельцем; `MIGRATION_JSON` — файл согласованного запроса, описанного ниже.
Это пути к реальным файлам установки, а не новые конфигурации для обхода отказа.
Настройки должны связывать manifest с каталогом установки, реестром проектов,
квитанцией подготовки и project lock. Manifest находится в отдельном пакете
проекта под настроенным root. Создавать редактор каталога или перепривязывать
его targets ради этой миграции не требуется.

Выбор явный: операция не переключается между владельцами после отказа.
`--project-settings` применим только к `task-stage-criteria-migration-1`;
исторические точечные схемы выше его не принимают. Все обязательства по
авторизации, полному mapping, backup и остановке writers сохраняются.

### Запрос и инвентаризация

Запрос содержит ровно пять полей: `schema`, `request_id`, `backup_name`,
`mapping`, `authorization`. `backup_name` — реальное имя проверенной копии
в штатном каталоге backups, не путь к произвольному файлу.
`mapping` непуст и покрывает **все** настроенные определения процессов и
**все** незавершённые Task, включая newborn. Подмножество не является частичной
активацией. Инвентаризацию, сравнение с backup и проверку привязок выполняет
владелец операции до записи intent; отдельный публичный preflight endpoint
этим контрактом не вводится.

| `kind` ресурса | Поля, кроме `kind` и `stages` |
|---|---|
| `workflow_definition` | `goal_type`, `expected_revision` — точная revision редактора каталога либо digest исходного workflow при выбранных project settings |
| `executable_task` | `task_id`, `expected_version` — целое число, `expected_workflow_digest` |
| `newborn_task` — с договорами этапов | `task_id`, `expected_revision` — целое число, `expected_workflow_digest` |
| `newborn_draft` — до подготовки договоров этапов | `task_id`, `expected_revision`, `expected_metadata_digest` |

В `stages` каждый исторический этап указан ровно один раз в исходном порядке.
Для workflow definition элемент содержит ровно `stage_id`, `purpose`,
`criteria_authority`. Для Task с существующими договорами этапов добавляются
`criteria` и `execution`. Для `newborn_draft` применяются
[правила переноса постановки](#постановки-без-договоров-этапов).
Формы назначения, полномочий и критериев описаны в
[основном протоколе](workflows/stage-criteria.md#договор-и-критерии).
Отсутствующие исходные значения не заменяются скрытыми defaults.

`execution` содержит ровно `state`, `source_revision`, `source_refs`.
Исторический источник без редакций критериев требует `source_revision: null`;
положительное число нельзя выдавать за существовавшую редакцию.
`source_refs` — непустой список подлинных ссылок:

- `{"kind":"contract","digest":"OBSERVED-CONTRACT-DIGEST"}`;
- `{"kind":"submission","id":123}`;
- `{"kind":"task_event","id":456}`.

Маркеры и числа здесь иллюстрируют форму, а не существующие записи.
Contract digest должен совпадать с исходным контрактом. Для `started` нужны
подлинные submission или события начала, отправки либо проверки именно этого
этапа. Для `unstarted` нужны события создания newborn или перехода в available
и отсутствие фактического начала/результатов целевого этапа. При недостаточных
сведениях используют `unknown`, а не выдуманную историю. `unknown` не разрешает
менять критерии как ещё не начатые.

Весь запрос подаётся одним JSON в stdin выбранного CLI. Сначала создайте backup
через [его публичного владельца](task-db-backups.md), затем соберите фактический
mapping и авторизацию. Проверка одной JSON-формы не доказывает полноту mapping,
готовность установки или подлинность происхождения.

### Постановки без договоров этапов

`newborn_draft` учитывает новорождённую постановку, у которой в черновике ещё нет
поля `stage_contracts`, а `newborn.ready` равен `false`.
Элемент содержит ровно `kind`, `task_id`,
`expected_revision`, `expected_metadata_digest`, `stages`. Он входит в общий
`mapping` наряду с полными задачами и определениями процессов. Один Task ID
нельзя включать повторно под другим видом ресурса.

`expected_revision` — наблюдённая версия постановки: неотрицательное целое число,
кроме boolean. `expected_metadata_digest` — SHA256 всего исходного объекта
metadata: канонический JSON с отсортированными ключами, без ASCII-экранирования,
с разделителями `,` и `:`, в UTF-8. Значение содержит ровно 64 строчные
шестнадцатеричные цифры. Переданный digest и версия сверяются с текущей строкой;
совпадение базы с backup не заменяет эти проверки.

До выбора типа процесса в metadata отсутствует `workflow`, в черновике отсутствует
`goal_type`, а `stages` явно равен `[]`. Миграция сохраняет исходный текст metadata
без перезаписи, включая его форматирование. Идентичность, версия, владение и
история постановки остаются прежними.

При выбранном процессе `goal_type` черновика совпадает с типом сохранённого
процесса. `stages` перечисляет все его этапы ровно один раз в исходном порядке;
каждый элемент содержит только `stage_id`, `purpose`, `criteria_authority`.
Меняются только назначения и полномочия существующего процесса. Содержимое
черновика и остальные поля metadata сохраняются. Отсутствующие договоры этапов,
критерии, их согласования и состояния исполнения не создаются.

Наличие `stage_contracts` исключает этот вид ресурса: полный исторический договор
новорождённой задачи переносится как `newborn_task`. Исполняемая задача использует
`executable_task`. Явные `null`, массив или повреждённый объект вместо процесса,
повреждённые присутствующие договоры, несовпадающий тип и неполное либо
переставленное перечисление этапов дают структурированный отказ до intent.
Отсутствие будущих данных у законной постановки не является повреждением.

Для задач с существующими договорами допустимы явно пустые списки начальных
критериев, если исторический договор не содержит таких текстов. Общие требования
задачи, DoD и обязательства входа/выхода сохраняются. Этот перенос не выполняет
проектирование будущих этапов.

### Публикация, атомарность и восстановление

До intent проверяются целостность backup, равенство снимка исходной DB,
полнота ресурсов, точные версии, workflow bytes/digests и metadata digests
постановок. При выборе редактора
каталога проверяются его managed heads, зарегистрированные targets и привязки.
При выборе project settings проверяются реестр, квитанция подготовки и
подтверждение исходной project revision в истории её владельца. Перед intent
и последующими эффектами конфигурация перечитывается. Drift не разрешает
переключить владельца или продолжить запись в новое место.

В режиме каталога процессы публикуются через его существующий редактор.
Завершение подтверждается точными receipt, документом, current head и отсутствием
pending-публикации. В режиме project settings владелец сначала получает project
lock, затем координатор получает Task lock. Все процессы публикуются одним полным
кандидатом и одной квитанцией `project-config-receipt-1`. Обычное обновление проекта
сохраняет строгую проверку текущей схемы: исторический вход принадлежит только
явной миграции.

Исходную revision подтверждает проверенная квитанция подготовки
`project-receipt-1` либо квитанция `project-config-receipt-1` обычного обновления
или первой привязки `runtime_resources`. Для первой привязки результат имеет
`schema=project-runtime-resources-bootstrap-result-1` и `status=completed`.
Читатель проверяет точный состав полей, совпадение request ID, непустые строки,
формат digest и revision, равенство `before_revision` с `prior_revision` и
`after_revision` с `revision`, а также различие исходной и опубликованной revision.
Оба сохранённых значения `replayed`, `false` и `true`, допустимы.
Исходную revision можно подтвердить через `revision` или `prior_revision` этой
квитанции; выбирается поле, совпадающее с мигрируемой revision выбранного проекта.

Одного совпадающего поля в произвольном JSON недостаточно. Intent сохраняет путь,
канонический JSON digest и выбранное поле revision конкретной исходной квитанции.
Её содержание повторно проверяется до intent, публикации, при восстановлении и
перед финальной транзакцией Task. Изменение только пробелов JSON сохраняет digest;
изменение значений нарушает привязку. Читатель не переписывает исходные байты.
История другого проекта не входит в эту привязку; собственная новая квитанция
миграции не заменяет исходное подтверждение при повторе. Завершение публикации
миграции подтверждает обычная квитанция обновления с `status=updated` и точной
привязкой к её запросу и кандидату. Квитанция первой привязки подтверждает источник,
но не завершение миграции.

Квитанции подготовки и обычного обновления принимают точные
[формы результата проверки Git](configuration/project-setup.md#подтверждение-проверки-git).
Сохранённый `base_revision` читается без повторной проверки Git. Публикация дочернего
обновления в этой миграции использует `probe_repository=false`; её `readiness`
сообщает `not_checked`, даже если исходная квитанция получена с проверкой Git.
Этот результат не заменяет исходную квитанцию и её привязку к revision.

Project pending содержит точные request ID/digest и component digests до и после
публикации. При прерывании допускается только сочетание исходных процессов и
точного кандидата этого intent. Если durable receipt уже записан, но pending
ещё существует, владелец сверяет квитанцию, полный текущий кандидат и весь pending,
затем удаляет только этот pending. Байты сохранённой квитанции остаются прежними.
Изменённый pending, сторонняя правка процесса или исходной квитанции дают отказ;
повтор не стирает эти данные. Чтение завершённости само pending не удаляет.

Публикация файлов не является частью SQLite-транзакции. Финальные изменения
Task metadata и запись завершённой миграции выполняются одной транзакцией
после повторной проверки исходных строк; сбой откатывает эту транзакцию.
Уже доказанные файловые публикации при последующем drift не стираются и
не подменяются другим владельцем.

У задач с существующими договорами миграция создаёт редакцию критериев `0`
с источником `historical`, исходным
digest и migration receipt, а не фиктивное согласование. Сохраняются ID,
lifecycle, версии Task, владение, текущие этапы/итерации, подлинная история,
результаты, WIP и рабочие деревья. Состояние выполнения сохраняет доказанное
происхождение; разрешение начала восстанавливает общий владелец допуска
по завершённому intent/receipt, а не по одному наличию новых полей.

Результат `migrated` содержит `request_id`, `resources`, `receipt`, `replayed`.
Для каждого `newborn_draft` в `resources` присутствуют ровно `kind`, `task_id`,
`revision`, `old_digest`, `new_digest`. Версия остаётся исходной; digests относятся
ко всему объекту metadata до и после переноса. У постановки без процесса они
совпадают. Результаты постановок выдаются после commit общей транзакции Task.

Точный повтор завершённого запроса возвращает исторический результат с
`replayed: true`; в режиме project settings перед этим сверяются исходный
владелец, подтверждение версии, квитанция и полный опубликованный кандидат.
Это не новая приёмка Task или проверка всей установки.
До intent отказ возвращает `rejected`. Ошибка публикации или финальной транзакции
после intent возвращает `recovery_required` с исходными `request_id`, `receipt`,
reason и только доказанными ресурсами. При допуске повторного запроса конфликт
его идентичности, владельца или исходной квитанции возвращает `rejected`, сохраняя
частично опубликованные данные. CLI завершает `migrated` кодом 0, остальные
исходы — кодом 2. Некорректные вложенные документы квитанций/pending и недоступный
root выбранных настроек дают структурированный отказ; после публикации ошибочная
квитанция сохраняет ответ восстановления с исходной идентичностью.

До commit Task в `resources` ответа восстановления входят только подтверждённые
файловые публикации процессов. Успех переноса постановок ещё не объявляется.
Если квитанция записана, но pending ещё не проверен и не завершён владельцем,
список доказанных ресурсов может быть пустым. Восстановление и завершение
используют ту же идентичность intent и `receipt`; завершённый точный повтор
возвращает тот же `resources` без новых записей.

При `recovery_required` сохраните backup, intent и receipts, остановите writers
и восстанавливайте именно этот intent через владельца операции. Новый request ID,
ручная правка DB, удаление журнала и автоматическое восстановление только DB
после частичной файловой публикации не являются безопасным продолжением.
Удаление backup или откат требует отдельного решения после проверки целостности
всей установки. Эта документация не разрешает live-активацию.
