# Documentation as a maintained contract

## Inputs

The accepted behavior/interface/workflow change, current Task scope, implemented code and real evidence, and affected user/developer/operator scenarios. Locate existing canonical owners from the selected Poise project profile and target-worktree facts. Obtain managed Task content through [poise-workflow](../poise/SKILL.md); historical reports are execution provenance, not current product truth.

## Procedure

1. Identify one canonical owner for each requirement, rule, interface, architecture decision and procedure. Read only the affected product, developer, test, runtime, migration, operator and agent-instruction surfaces. The [impact checklist](references/doc-impact-checklist.md) is a decision aid, not a registry.
2. Co-deliver affected instructions, examples, links and recovery guidance with the behavior change. Include failure modes, setup/version/runtime prerequisites and irreversible operations where actually relevant. An independently useful documentation Task may be separate; it must not conceal missing mandatory co-delivery.
3. Describe implemented, checked behavior as such. Mark proposals, unresolved dependencies and planned capabilities explicitly; a design document or instruction alone does not implement a runtime hook, router, guard or automation. Do not copy volatile Task/Sprint status into canonical product documentation.
4. Verify commands, paths, payloads, versions and recovery steps against actual code/configuration/evidence. Distinguish syntax/link checks from execution. Never document an unavailable tool or fabricated success as tested; use the real selected project runtime rather than copied ERP command examples.
5. Resolve contradictions at the canonical owner and point other documents there. Remove stale present-tense descriptions of removed behavior while retaining historical provenance in historical material. Preserve agent-facing/human-facing language and layout rules of the current repository.
6. Record each affected path, owner, reason and validation in existing Poise Task content, not DOC-IMPACT.md or an ERP document registry. If no documentation changes are needed, state the concrete unaffected contract/ownership reason, not a bare N/A.
7. Self-review source fidelity, complete requirements, command accuracy, recovery coverage and direct links, then follow the independent review/handoff route. Non-executable text does not need artificial TDD; changed executable claims require appropriate focused verification. No ordinary full-suite fallback.

## Output

Updated canonical documentation/instructions/examples, precise affected-path decisions including justified no-change outcomes, actual link/path/claim checks, remaining uncertainty and requirement/evidence links in existing Task content. Documentation completion grants neither implementation authority for a proposal nor acceptance/publication of the result.
