# Пакетный редактор конфигурации типа цели — DDD-04A

Обновлено: **2026-10-08**. API реализован, не проект будущих команд.

## Назначение и DDD
`GoalTypeDefinition` — чистый владелец полного process-конфига. `GoalConfigCommands.apply_batch` строит один кандидат через порт и публикует его. `FileGoalConfigRepository` реализует ожидаемую revision, журнал операции в SQLite и атомарную замену одного JSON. `FileTemplates` читает только явно зарегистрированный шаблон и проверяет version/digest. `exclusive_lock` переиспользуется редактором и Task store. Domain/Application не делают I/O.

Редактор и обычный `load_config` используют **один** `GoalTypeDefinition.parse`. Нет двух расходящихся наборов правил. Это не универсальный raw JSON/SQL/file editor: допустимы предметные операции по ID.

## Один прямой вызов
```bash
export PYTHONPATH="$PWD/src"
python -m poise goal-config --settings config/goal-editor.json < examples/goal_config_create.json
```
Это готовый пример create `generated_notes`. Вход JSON можно передать прямо через stdin в том же tool call; предварительно создавать/редактировать request-файл не требуется. Project config и caller identity для конфигурирования не нужны: Task store не открывается и task не создаётся. В API: `goal_config_tools(settings_path).apply_batch(request)`.

`--settings` — явный installation-конфиг редактора. Он задаёт root, разрешённые target paths, шаблоны, лимиты, форматирование, права создаваемого файла и выходные коды. Нет автопоиска settings по cwd, неявного шаблона или имени `origin`.

## Пакет
Обязательны `schema`, `request_id`, `mode`, `goal_type`, `expected_revision`, `template`, `changes`.

- `schema` = `goal-config-batch-1`.
- `create`: `expected_revision: null`, template с точными `id/version/digest`. Полный шаблон копируется и дальнейшее изменение независимо от него. Идентичность goal_type берётся из явного запроса.
- `update`: exact `expected_revision`, `template: null`. Неперечисленные **известные** значения текущего конфига сохраняются. Отсутствующие обязательные значения не подставляются.
- `request_id` идентифицирует логическую операцию; повтор с другим содержимым отклоняется. Полный запрос одинаковой операции должен совпадать; перестановка записей с тем же ID не обещается как transport replay, хотя независимый порядок даёт одинаковый конечный конфиг.
- `changes` всегда явно заданный список. Пустой create допустим с полноценным шаблоном; пустой update не создаёт новую content revision.

## Предметные изменения
| Операция | Вход |
|---|---|
| `put_stage` | `value`: полный этап с id |
| `patch_stage` | `id`, `set`: известные меняемые поля этапа |
| `remove_stage` | `id` |
| `patch_route` | `set`: entry и/или явные budgets |
| `put_section`, `remove_section` | Полное дополнительное определение секции либо id |
| `put_trace_route`, `remove_trace_route` | Полная цепочка с точками либо id |
| `put_requirement`, `remove_requirement` | Полное обязательство содержимого либо id |

Форма put: `{ "op":"put_section", "value": { ... } }`. Remove: `{ "op":"remove_section", "id":"rollback" }`. Patch: `{ "op":"patch_stage", "id":"implementation", "set": { "instruction":"..." } }`.

Полные stage-объекты включают обязательную `role` (непустую строку), переходы, инструкции, read-only/allowed paths, нормализацию, стандартные секции и требования к артефактам. Правки этих полей не требуют специального обработчика на каждое имя секции. Точки трассировки изменяются заменой соответствующего route-объекта; их смысловой порядок сохраняется.

Объявление секции и обязательство, ссылающееся на неё, могут идти в любом порядке пакета. Проверяется финальный кандидат. Две конкурирующие записи одного свойства, put и remove одного объекта — ошибка, без неявного last-write-wins. Несколько patch разных свойств одного этапа разрешены.

## Роли процесса и совместимость

`role` задаётся явно на каждом этапе. `patch_stage` может изменить её тем же публичным
редактором, например `{"op":"patch_stage","id":"test_review","set":{"role":"executor"}}`.
Одинаковая роль на produce и inspect разрешает самопроверку одной сессией. Разные роли
требуют разных effective actors для производства и осмотра. Произвольные непустые имена
ролей допустимы; handler не выбирает роль. В current-Task workflow projection возвращается
роль текущего этапа.

Роль входит в замороженный process snapshot задачи. Изменение исходного process-файла
не меняет старую задачу. Конфиги и сохранённые snapshots 044A без `role` несовместимы
с новым обязательным полем; скрытого восстановления роли по handler нет. Они требуют
явно согласованной подготовки своим владельцем, а не ручного UPDATE Task DB. Для активных
задач нужен отдельный разрешённый маршрут миграции/перезапуска; данный patch его не добавляет.
Рабочую установку с такими snapshots нельзя обновлять одним копированием нового кода.

## Проверки
Точная форма; обязательные поля и типы; уникальные IDs; известные handlers/outcomes; ссылки графа, достижимость, путь к завершению и бюджеты; read-only inspect; обязательный inspect после revise; стандартные и дополнительные sections; внутренние content/trace references; ограничения количества артефактов. Для каждого нового trace-требования хотя бы один его `stage` должен входить в `write_stages` указанной точки; недостижимое расписание отклоняется вместе со всем кандидатом до публикации файла.

Редактор возвращает несколько независимых обнаружимых ошибок пакета с путями. Проверка зависимого объекта может остановиться на его первой структурной ошибке; полный перечень всех возможных ошибок повреждённого дерева не обещается.

В текущем формате `evidence_plan`, конкретные command methods и task requirement IDs принадлежат **конкретной задаче**, не process pack. Редактор не добавляет неиспользуемые псевдополя в конфиг; эти ссылки проверяются при создании Task. Истинность логического аргумента и инженерная разумность процесса машинной проверкой не объявляются.

## Публикация, повторы и ошибки
1. Короткий внешний Linux lock.
2. Чтение исходного файла и exact revision; сверка с уже управляемым head.
3. Применение пакета в памяти; общая validation.
4. Запись pending operation с полным кандидатом, исходной revision, назначением и template provenance.
5. Запись временного файла в том же каталоге, flush/fsync и atomic replace.
6. Короткая транзакция completion receipt/head.

SQLite не объявляется атомарной транзакцией filesystem. Повтор продолжает известный pending только если адрес назначения и текущее содержимое соответствуют прежнему либо новому состоянию. Неизвестное внешнее изменение блокирует запись; оно не присваивается текущему агенту. Crash после replace до receipt не создаёт второго результата. Старый повтор после более нового update возвращает прежний receipt вместе с текущей revision и **не откатывает файл**.

Конфигурационная ошибка не публикует частичный пакет. Чрезмерно маленький output budget отклоняется до публикации. Ошибка записи после сохранения намерения возвращается как pending; следующий вызов выясняет/продолжает состояние, а не требует правки БД агентом.

## Представление ответа

При действительных settings CLI сохраняет полный структурированный результат в
настроенный `responses`, затем использует [общий агентский
envelope](../workflows/batch-work.md#представление-ответа-агенту) с `output_chars`.
Это тот же владелец представления, что у Work, hook transport и catalogue; отдельного
алгоритма усечения editor JSON нет. Внутренний `GoalConfigCommands` возвращает полный
результат. Профиль shell-команды для standalone editor JSON не требуется.

Если полный envelope помещается, выдаётся весь результат с `response_path`. Иначе
сохраняются `status` и адрес полного JSON; revision и прочие метаданные, `error_count`
и начальная часть `issues` включаются по доступному бюджету. Полный файл содержит
все исходные issues и вложенные поля, даже когда краткий ответ их не вместил. Статус
не выводится из текста preview и не заменяет фактический исход вложенной команды.

Если запись полного response не удалась, CLI возвращает `response_storage_error`
с исходным `business_status` и настроенным pending exit code, без ложной ссылки на
полный результат. Если минимальные `status` и `response_path` не помещаются, этот
editor возвращает pending exit code без JSON; полный файл уже сохранён. При ошибке
самих settings настройки лимитов/выходных кодов недоступны, поэтому действует
отдельный bootstrap error. Эти ответы не подтверждают успешную публикацию; её
фактическое состояние выясняется через сохранённую операцию и штатный повтор. Catalogue
переиспользует общий envelope, сохраняя собственные settings, persistence и exit policy.

## Сверка управляемой revision с live-конфигурацией

Редактор — единственный владелец своей managed-head revision. Другой разрешённый механизм
может атомарно заменить тот же process-файл, но такая замена не становится новой managed
head молча и не должна затираться прежним содержимым редактора. Для диагностики и явного
принятия уже опубликованного валидного файла служат две схемы того же публичного CLI:

- `goal-config-status-1` принимает `schema` и `goal_type`. Это строго read-only операция:
  она возвращает target, managed revision, наблюдаемую live revision, признак совпадения и
  известный `pending_request`, не продолжая и не завершая pending-публикацию.
- `goal-config-reconcile-1` принимает `schema`, уникальный `request_id`, `goal_type`, точные
  `expected_managed_revision` и `expected_live_revision`, а также непустые `reason` и
  `authorization`. Операция полностью разбирает live process общим валидатором и принимает
  его только при совпадении обеих revisions.

Успешная сверка меняет только ownership metadata и audit редактора. Process-файл и snapshots
существующих Task не переписываются. Receipt связывает предыдущую managed revision, принятую
и валидированную live revision, target path, причину и основание полномочий; точный повтор
того же запроса возвращает этот receipt. Конфликтующий drift, устаревшая managed revision,
другой payload с тем же `request_id` и любая неоднозначная pending-операция дают отказ без
изменений.

Диагностику и сверку вызывают через действующий installation settings, например:

```bash
python -m poise goal-config --settings config/goal-editor.json <<'JSON'
{"schema":"goal-config-status-1","goal_type":"development"}
JSON

python -m poise goal-config --settings config/goal-editor.json <<'JSON'
{"schema":"goal-config-reconcile-1","request_id":"adopt-development-1","goal_type":"development","expected_managed_revision":"<exact-managed-revision>","expected_live_revision":"<exact-live-revision>","reason":"adopt an authorized external publication","authorization":"user-approved repair"}
JSON
```

Расхождение нельзя обходить, создавая новую БД редактора: это теряет цепочку владения и
аудит, но не доказывает происхождение live-конфигурации. Сначала получают read-only status,
проверяют источник изменения и затем либо выполняют точную публичную сверку, либо устраняют
неправомерную замену отдельным авторизованным действием.

## Результат
Один компактный JSON: status, request/goal IDs, новая и предыдущая revisions, changed/replayed, число изменений, путь полученного конфига и полного ответа. Размер inline и выходные коды заданы settings. Подробные ошибки сохраняются автоматически в configured response root.

Редактор создаёт только заранее разрешённый target текущего registry. Произвольное добавление проектов/путей и интерактивный installation wizard не включены в этот срез. Рабочий `config/goal-editor.json` не хранится в Git; [goal-editor.example.json](../../config/goal-editor.example.json) показывает форму заполнения, но его значения не являются literals домена или универсальными для всех установок.

## Активные задачи
Задача хранит свой process snapshot. Редактирование process-файла не меняет этот snapshot и не блокирует его исполнение только из-за digest соседних process definitions. Новая задача получает новый pack. Изменение валидного **project execution config** не перезапускает и не инвалидирует текущую задачу: следующие операции используют текущую конфигурацию вместе с сохранёнными неизменными Task contracts и exact methods. Новый формат project `ddd-goal-config-5`, Task DB `user_version=6`; старый store отвергается без миграции. Editor DB имеет отдельный `user_version=1`.

## Что ещё не реализовано
Прямой batch результата Task, ArtifactFactory и message events — DDD-04B. Sprint API — DDD-05. Все 13 нормативных packs, внешние hooks/MCP/Gmail и полная экономика не объявляются готовыми. Данный срез редактирует все поля **реально исполняемого** process-формата; он не материализует весь прежний нормативный каталог автоматически.
