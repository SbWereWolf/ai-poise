# AI poise

AI poise — локальное приложение для работы AI-агентов над задачами и
спринтами. Оно ведёт состояние задач, выдаёт инструкции текущего
этапа, запускает заданные проверки и сохраняет результаты. Размещение
работы в отдельном Git worktree или в настроенном checkout
определяется явной политикой процесса `worktree_required`;
см. [правила размещения](docs/governance/development-rules.md#размещение-task-worktree).

Этот репозиторий называется **ai-poise**, команда приложения — **
`poise`**. Проектная конфигурация задаёт процессы, проверки и
расположение рабочих данных.

## Запуск

Требуется **Python 3.13** (`>=3.13,<3.14`). Команды ниже рассчитаны на
существующую локальную установку ai-poise: окружение `.venv/` с
установленным AI poise и опубликованная конфигурация проекта уже
должны быть подготовлены.

```bash
cd /home/sbwerewolf/workdata/ai-poise
.venv/bin/poise --help

```

Текущая установка работает только через источник `runtime_event`: хуки
Codex передают агенту путь к сессионному `work.sh`. Агент вызывает его
через Bash; launcher задаёт обязательные runtime-переменные
`POISE_CONFIG` и `POISE_SESSION`, выбирая конфигурацию и нативную
сессию. Если путь не получен, сначала нужно проверить обнаружение,
разрешение и исполнение хуков. Самостоятельная генерация сессии и
ручная регистрация сообщений не заменяют подключение.

Для подготовки нового проекта
см. [настройку проекта](docs/configuration/project-setup.md), для этой
установки — [локальные пути и команды](docs/configuration/project-setup.md#локальный-проект-ai-poise).
Повторно создавать конфигурацию или запускать seed для уже
настроенного ai-poise не требуется.

Автономные учебные сценарии без remote и подключения живой IDE описаны
в
[примерах](docs/workflows/runnable-examples.md#запуск-в-новом-каталоге).

## Работа с задачами

`bootstrap` начинает или возобновляет работу, `verify` проверяет
результат текущего этапа. Это JSON-операции команды `poise work`.

Минимальный пример чтения **без формальной задачи**. Задайте
`AI_POISE_WORK` точным путём из нативного hook-контекста; не копируйте
launcher другой сессии:

```bash
bash "${AI_POISE_WORK:?Set the launcher path supplied by the native hook}" <<'JSON'
{"operation":"bootstrap","input":{"task":null,"decision":null,"feedback":null,"rework_stage":null},"messages":[]}
JSON

bash "${AI_POISE_WORK:?Set the launcher path supplied by the native hook}" <<'JSON'
{"operation":"verify","input":{"result":null,"artifacts":[]},"messages":[]}
JSON
```

Ожидаемые статусы — `read_only` и `read_only_verified`. Последний
означает завершение сессии чтения, а не проверку содержательных
результатов.

Для формальной задачи передайте её ID в `bootstrap`, работайте в
выданном контексте репозитория и заполните полученный
`result_template` для `verify`. Уже разрешённые этапы своей роли
продолжайте через [публичный
`advance`](docs/workflows/batch-work.md#продвижение-к-этапу); на
границе роли сохраните и передайте результат. Проверка, принятие,
публикация и интеграция остаются отдельными действиями со своими
полномочиями. Форматы пакетов описаны
в [API работы](docs/workflows/batch-work.md), выбор задач и
зависимости — в [API спринтов](docs/workflows/sprints.md).

## Структура проекта

| Путь                                     | Назначение                                                                                                                                      |
|------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------|
| `src/`                                   | Реализация AI poise                                                                                                                             |
| `config/`                                | Настройки инструментов, шаблоны и конфигурации процессов; рабочий проект — `config/projects/ai-poise/`                                          |
| `projects/ai-poise/`                     | Разрешённое рабочее состояние этой установки: Task DB, материалы `standalone/` и `sprint/`, runtime-данные; расположение worktree задаётся явно |
| `docs/`                                  | Текущие руководства и спецификации; датированные проектные материалы сохраняются как история                                                    |
| `examples/`                              | Примеры API и входных данных                                                                                                                    |
| `.agents/skills/`, `.agents/references/` | Инструкции агентам и ссылки на соответствующие разделы документации                                                                             |
| `tests/`                                 | Проверки приложения                                                                                                                             |
| `recovery-tools/`                        | Восстановление и безопасное слияние полных копий для облачных агентов                                                                           |
| `tools/`                                 | Вспомогательные команды разработки и настройки                                                                                                  |
| `delivery/`                              | Состояние поставки и перенос канонических баз без повторной инициализации задач                                                                 |

В корне также находятся `pyproject.toml` с метаданными и требованиями
Python, `requirements-dev.txt`, `.gitignore` и
правила [AGENTS.md](AGENTS.md).

Для этой установки конфигурация и рабочие данные разделены:
`config/projects/ai-poise/` и `projects/ai-poise/`. Отдельная
Requirements DB уже используется: она хранит канонические
System/Application требования, а Task DB — согласованные цепочки и
исторические снимки Task. Обязательные пути задаются в конфигурации,
без скрытого переноса существующих данных.
См. [владельцев, версии и границы хранилищ](docs/architecture/storage-lifecycle.md#владельцы-и-версии).

## Восстановление для облачных агентов

[Recovery toolkit](recovery-tools/README.md#назначение-и-границы)
сохраняет полный
проект с Git и БД, восстанавливает бинарный архив или его читаемый
Gmail transport
и готовит cloud/local merge в новом каталоге. Для конфликтующих Task
IDs предусмотрен
проверяемый SQL-план, а не автоматическое отождествление записей.
После распаковки
сначала прочитайте приложенный корневой HANDOFF.md; он намеренно не
входит в Git history.

Постановка задач с полными цепочками
требований: [реестр требований](docs/workflows/requirements-registry.md#декларативный-api-и-согласование).
