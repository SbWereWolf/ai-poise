## Что произошло со старыми отказами

В PILOT-01 было 7 FAIL и 34 случая модуля без terminal XML. Все они прошли внутри одного
полного контрольного запуска, не адресной подборкой зелёных результатов. Прежние 96 test-
файлов и 127 Python-файлов runtime не изменялись. Это НЕ доказывает задним числом причину
каждого отказа. В трёх исходных отказах был явный subprocess timeout, один целый модуль
превысил внешний предел; причины четырёх отрицательных assertions не восстановлены.

Внутренние лимиты и ожидаемые результаты тестов не повышались. Внешнему супервизору явно
передан бюджет **900 секунд на pytest-модуль**. Максимум базового запуска —
**220.200 с**, ниже прежних внешних 600 с.
Это не основание приписать старые отказы только CPU. Полная исходная диагностика там была
утрачена старой процедурой удаления временных папок; новые отказы сохраняются.

## Подтверждённые дефекты вспомогательного runner

`runner-before-after.json` фиксирует настоящие subprocess на одинаковых fixtures:

1. Обычный падающий pytest создал diagnostic-result.json. Старый инструмент удалил файл;
   новый сохранил его, итог остался честным неуспехом.
2. Pytest plugin выставил code=0 при failing testcase. Старый runner вернул success=true
   при 0 прошедших тестов. Новый вернул failure и сохранил исходный JUnit/workspace.

Это дефекты development-инструмента проверки, а не доказанная причина прежних семи failures.

## Воспроизведение

```bash
export PYTHONPATH="$PWD/src"
python tools/run_test_packages.py --root "$PWD" \
  --output /tmp/harness-pilot02-checks-new --workers 2 --timeout 900 \
  --success-workspaces delete
python -m pytest tests/test_package_execution.py tests/test_project_execution.py -q
```

Все значения внешнего запуска явные. Старые, red и mutation-прогоны не перезаписываются
последующими зелёными. Scripts в evidence/reproduce отражают реальные абсолютные пути
этой среды; переносимый вызов выше и штатный пример описаны в docs/pilot02.md.
