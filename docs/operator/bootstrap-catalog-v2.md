# Bootstrap и каталог catalog/v2

Обновлено: 2026-10-14. Это руководство относится к корневому
`bootstrap` AI poise, а не к действующему маршруту `poise infra/deps/check` с
профилем `requirements/v1`. Подготовка Bootstrap сама не переключает установленного
оператора. Эксплуатационный каталог и выбор профиля для AI poise остаются за
отдельной поставкой прикладного каталога и явным решением об активации.

## Граница приложений и происхождение

AI poise владеет только корневым `bootstrap`, транспортным адаптером
`apps/bootstrap/application.py` и lock-файлом `apps/bootstrap/component.json`.
Отдельное приложение `environment-maintenance` владеет schema
`environment-maintenance/catalog/v2`, параметрами, разрешённым окружением,
выполнением действий, состояниями и повторной проверкой. Его исходники и generic
engine не копируются в AI poise.

Lock фиксирует `schema=ai-poise/bootstrap-component/v1`, дистрибутив
`environment-maintenance`, версию `0.2.0`, принятый commit
`a980fcd54d0958e0a491efb385ede406453d6899`, SHA-256 сохранённого wheel
`c3551a4ed17af48b3a03840fd76a10ec395dda00415a51b224b93bdf62b31b69`
и SHA-256 delivery manifest
`2b1ed295527193e817cd91f40ce63b6ab8123d842ac2cb5c710405a6a1287610`.
Эти digest проверяются при подготовке поставки по сохранённым файлам.
При запуске Bootstrap проверяет lock, установленную версию дистрибутива и
доступность модуля в том же изолированном Python, который выполнит действие.
Проверка установленной версии не восстанавливает digest исходного wheel.

Комплект поставки содержит шесть файлов:

| Файл | Назначение |
|---|---|
| `environment_maintenance-0.2.0-py3-none-any.whl` | Те же проверенные байты устанавливаемого компонента. |
| `source.bundle` | Принятые исходники, SHA-256 `42c113c71b04cee01acb9be78ff9749ee1af47b935beed0024f2dcfa2d7c7e28`. |
| `build-record.json` | Исходная запись сборки: commit, digest исходников и wheel, backend, команда, код выхода и digest потоков. |
| `build.stdout` | Полный stdout исходной сборки. |
| `build.stderr` | Полный stderr исходной сборки, включая предупреждения. |
| `manifest.json` | Запись выбранной поставки, чей digest зафиксирован в lock. |

`manifest.json` содержит ровно восемь полей: `distribution`, `version`,
`requires_python`, `source_commit`, `source_bundle_sha256`, `wheel`, `wheel_sha256`,
`build`. Значение `build` совпадает с объектом `build-record.json`. Его исходное
описание кандидатной сборки и пути команды сохранены как история происхождения;
они не являются текущим адресом файлов поставки. Повторная сборка при продвижении
проверенного wheel не выполняется. Файл wheel расположен рядом с manifest под
именем из поля `wheel`.

Оператор получает комплект из согласованного места поставки. Рабочие материалы Task
не заменяют постоянную поставку после её завершения и удаления служебных материалов.

## Подготовка и безопасная проверка

Проверенная среда потребителя — Python 3.13 с установленным ровно
`environment-maintenance` 0.2.0. Метаданные самого компонента объявляют Python
`>=3.11`; это не означает, что потребитель здесь испытан на каждой такой версии.
Оператор заранее предоставляет комплект поставки и каталог v2 с `catalog.json`; Bootstrap
не выбирает каталог по умолчанию. Следующие пути предполагают существующий
родитель `/srv/poise` и новую отдельную venv; это пример площадки, а не
встроенные значения AI poise:

```bash
BOOTSTRAP_ROOT=/srv/poise/release
PACKAGES_ROOT=/srv/poise/packages
BOOTSTRAP_PYTHON=/srv/poise/bootstrap-venv/bin/python
CATALOG_ROOT=/srv/poise/catalog-v2

sha256sum "$PACKAGES_ROOT/environment_maintenance-0.2.0-py3-none-any.whl"
sha256sum "$PACKAGES_ROOT/manifest.json"
sha256sum "$PACKAGES_ROOT/source.bundle" "$PACKAGES_ROOT/build-record.json" \
  "$PACKAGES_ROOT/build.stdout" "$PACKAGES_ROOT/build.stderr"
```

До установки сравните первые два SHA-256 с
`$BOOTSTRAP_ROOT/apps/bootstrap/component.json`. Сверьте имя, версию, исходный commit
и digest wheel с `manifest.json`, digest `source.bundle` — с
`source_bundle_sha256`, содержимое `build-record.json` — с `build`, digest потоков —
с `build.stdout_sha256` и `build.stderr_sha256`. Сам digest `build-record.json`
выводится для сохранения наблюдения; отдельного поля для него в manifest нет.
Любое отсутствие или расхождение сначала устраняют восстановлением оригинального
комплекта из согласованной поставки. Продолжать установку до согласования файлов
нельзя. Пересборка создаёт другие байты и требует собственной проверки происхождения.

После успешного сравнения создайте новую отдельную среду и установите выбранный wheel:

```bash
python3.13 -m venv /srv/poise/bootstrap-venv
"$BOOTSTRAP_PYTHON" -m pip install --no-index --no-deps \
  "$PACKAGES_ROOT/environment_maintenance-0.2.0-py3-none-any.whl"

"$BOOTSTRAP_PYTHON" -I -B "$BOOTSTRAP_ROOT/bootstrap" check \
  --catalog-dir "$CATALOG_ROOT"
"$BOOTSTRAP_PYTHON" -I -B "$BOOTSTRAP_ROOT/bootstrap" infra \
  --catalog-dir "$CATALOG_ROOT" --dry-run
"$BOOTSTRAP_PYTHON" -I -B "$BOOTSTRAP_ROOT/bootstrap" deps \
  --catalog-dir "$CATALOG_ROOT" --dry-run
```

Wheel должен быть установлен именно в `BOOTSTRAP_PYTHON`; одного
файла на диске недостаточно. `bootstrap` запускается вместе с соседним каталогом
`apps/bootstrap/` из той же проверенной копии AI poise. Корневой entrypoint,
`application.py` и `component.json` поставляются вместе; `POISE_CONFIG`, Task
и сессия harness самому Bootstrap не нужны.

После выбора настоящего каталога `infra` и `deps` разрешены как изменяющие
операции. Оба имени передаются внешнему приложению как `run`; различие задаёт
только явно выбранный каталог. `check` передаётся как `check`.
`infra/deps --dry-run` передаются как `run --dry-run`.
Bootstrap сохраняет порядок всех аргументов после публичного имени, включая
повторяемые `--values` и `--set`. `check` и `--dry-run` не вызывают `install` или
`repair`. Секреты не следует передавать через `--set`: argv доступен системе.

Повторяемые `--values` читаются слева направо. Приоритет параметров:
значения каталога → файлы values → явно объявленные переменные окружения → `--set`.
Неизвестные, отсутствующие обязательные и неверно типизированные параметры
отклоняются до запуска действий. Подстановка параметров выполняется за один проход;
значение с буквальным `${name}` не разворачивается повторно. Выбранный v2-каталог
использует `catalog.json`; соседние `requirements.json` или `repairs.json` его
не подменяют. Старые опции `--repairs`, команда `apply` и старые поля маршрутизации
не являются входами этого интерфейса.

## Результаты и ошибки

После успешного preflight Bootstrap запускает один процесс
`python -I -B -m environment_maintenance` с отображённой командой. Для обычного
завершения он передаёт stdout, stderr и код выхода без разбора или замены JSON.
Если вход принят и внешний `execute` вернул результат со schema
`environment-maintenance/result/v2`, код `0` означает `ready`, `2` —
`action_required`, `3` — `unavailable`, `4` — `failed`. Ошибка контракта входа
(каталог, `--values` или `--set`) возникает до сериализации результата: код `2`,
пустой stdout и обычный текст в stderr, без JSON `result/v2`. Поэтому один код
`2` сам по себе не означает наличие структурированного результата. Для
`missing` обычный `run` выбирает `install`, для `invalid` — `repair`; после каждой
попытки изменения, включая неуспешную, внешний компонент повторяет `check`.
`unavailable` содержит причину и рекомендации без изменения среды.

Ошибка, созданная самим Bootstrap после разбора публичной команды, выводится
одним компактным UTF-8 JSON-объектом и завершающим LF в stdout, без stderr.
Её отдельная schema — `ai-poise/bootstrap-error/v1`. Поля:
`schema`, `source=bootstrap`, `status=error`, `code`, `command`, непустая `cause`,
непустой массив `recommendations`, `exit_code`. `command` — полученное публичное
имя `infra`, `deps` или `check`. Bootstrap не выдаёт эту ошибку за внешний
`environment-maintenance/result/v2`.

| Ситуация | `code` Bootstrap | Код выхода | Действие оператора |
|---|---|---:|---|
| Lock отсутствует, недоступен или повреждён | `component_lock_missing`, `component_lock_unreadable`, `component_lock_invalid` | 2 | Восстановить проверенный lock из той же поставки; не исправлять его поля наугад. |
| Дистрибутив или модуль не виден изолированному Python | `component_missing` | 3 | Установить принятый wheel в выбранный интерпретатор и повторить безопасный `check`. |
| Установленная версия отличается от lock | `component_version_mismatch` | 3 | Установить ровно указанную в lock версию. |
| Не запустился probe/action или probe завершился неожиданно | `component_spawn_failed` | 4 | Проверить интерпретатор и установку компонента; сохранить диагностику до повтора. |
| Action завершился сигналом | `component_signaled` | 4 | Изучить номер сигнала в `cause` и последствия действия до нового изменяющего запуска. |

Неизвестная публичная команда, отсутствующий или пустой `--catalog-dir` отклоняются
`argparse` до probe/action: код `2`, сообщение в stderr, без Bootstrap JSON.
Повреждённый lock, включая повторные/неизвестные поля, неверный UTF-8,
экранированный NUL, одиночный surrogate и чрезмерную глубину JSON, не запускает
компонент. При пустом stdout и текстовом stderr проверьте каталог, файлы
`--values` и переопределения `--set`: полей результата в этой ветке нет.
В структурированном `result/v2` строки `unavailable` содержат `cause` и
`recommendations`; при отказе действия или протокола смотрите соответствующие
`initial_check`, `mutation` и `final_check`, если они есть, а внутри них —
`invocation`, `error`, `timed_out`, `capture_complete` и сохранённые потоки.
Bootstrap эти внешние ошибки не исправляет и автоматически не повторяет
изменяющие действия.

Неправильный UTF-8, нарушенный протокол дочернего действия, превышение лимита
вывода или времени дают `status=protocol_failure` внутри действия; состояние
строки требования и итогового результата — `failed`, код CLI — `4`.
Лимит вывода относится отдельно к stdout и stderr. При переполнении смотрите
`capture_complete=false`, при превышении времени — `timed_out=true`; ни одно
из этих наблюдений не означает готовность ресурса. После попытки изменения
исходный `check` выполняется повторно, поэтому частичный эффект оценивается по
`final_check`, а не только по коду действия изменения. Для уже готового или
недоступного ресурса `install` и `repair` не выбираются.

## Откат и пределы поставки

Само подключение Bootstrap не меняет текущий release pointer оператора,
проектный конфиг или базы. Явно выбранное действие `infra/deps` может изменить
окружение по каталогу. Для отказа от пути прекратите его вызовы и сохраните выбранные
каталог, lock, вывод и код выхода. Возврат к прежней установленной поставке
проводится её отдельным управляемым lifecycle; Bootstrap не выполняет миграцию
профиля v1 и не удаляет результаты уже совершённых `install` или `repair`.
После частичного изменения сначала диагностируйте состояние по каталогу и
рекомендациям компонента, затем примите отдельное решение о восстановлении.

При недоступном или несовпадающем комплекте восстановите проверенные файлы
и повторите сравнение до установки. При `component_missing` или
`component_version_mismatch` проверьте выбранный изолированный Python и установите
в него ровно проверенный wheel, затем выполните `check`. Не исправляйте lock
под случайно установленный пакет. После тайм-аута, сигнала или частичного изменения
сохраните полный вывод и сначала выполните диагностический `check` с теми же
каталогом и параметрами; повторное изменяющее действие требует понимания фактического
состояния ресурса.

Реальные проверки `tests/maintenance/test_generic_v2_consumer.py` устанавливают
выбранный wheel в отдельную среду Python 3.13 и проверяют состояния, выбор действий,
повторный check, диагностику, параметры и границы вывода/времени/протокола.
`tests/architecture/test_bootstrap.py` отдельно проверяет транспортную границу
с контролируемым компонентом; один этот тест не доказывает поведение настоящего engine.
`tests/maintenance/test_generic_v2_supply.py` сверяет исходники, wheel, запись
сборки, manifest и lock. Поддерживаемый `tests/smoke.sh` охватывает шесть выбранных
сценариев harness. Эти проверки не доказывают работу произвольного прикладного
каталога, постоянную поставку или переключение эксплуатационного оператора.
