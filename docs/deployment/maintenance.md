# Развёртывание и обслуживание Poise

Обновлено: 2026-09-23. Контракт профиля: `environment-maintenance/requirements/v1`.

## Граница приложений

`poise infra`, `poise deps` и `poise check` передают аргументы самостоятельному
приложению `environment-maintenance`, сохраняя его stdout, stderr и код выхода.
Для этой маршрутизации не нужны `POISE_CONFIG`, текущая Task или сессия harness.
Основной интерфейс `poise work` сохраняется. Само maintenance-ядро не импортирует
Poise. Пакет `poise_environment` принадлежит поставке Poise: здесь находятся только
прикладные профили и адаптеры существующих владельцев конфигурации и баз данных.

Нужны Python 3.13, доступный Git и две совместимые поставки Python: `ai-poise` и
`environment-maintenance`. У обеих нет внешних runtime-зависимостей. Установщик
wheel не скачивает пакеты при использовании `--no-index --no-deps`.

## Подготовка профиля

Пример ниже предполагает распакованные исходники Poise в `$POISE_SOURCE`, уже
установленные wheel-пакеты, существующий родитель `/srv/poise` и настоящий целевой
Git-репозиторий с веткой `main`. Значения задаёт оператор; это не значения по
умолчанию для произвольного проекта. Образцовая development DB не используется.

```bash
python -m poise_environment.profile \
  --source "$POISE_SOURCE" \
  --output /srv/poise/profile \
  --state /srv/poise/state \
  --repository /srv/project \
  --project production \
  --base-ref main \
  --author-name 'Poise Operator' \
  --author-email 'poise@example.invalid'

poise deps --catalog /srv/poise/profile/requirements.json \
  --repairs /srv/poise/profile/repairs.json
poise infra --catalog /srv/poise/profile/requirements.json \
  --repairs /srv/poise/profile/repairs.json
poise check --catalog /srv/poise/profile/requirements.json \
  --repairs /srv/poise/profile/repairs.json
```

Профиль копирует только проверенные по digest шаблоны из поставки. Он не копирует
Task, execution, telemetry или историю разработки. Новый реестр проектов сначала
пуст. Сам генератор профиля не создаёт базы; это делает `infra` через владельцев
Poise. Существующий каталог профиля не перезаписывается.

В первой версии шаблоны берутся из явно указанного распакованного дерева поставки
`--source`. Наличие одного wheel без этих шаблонов недостаточно для создания
профиля. `--module-path` предусмотрен только для явного запуска из исходников;
при проверенной wheel-установке он пуст, импорты не зависят от исходной среды.

## Требования и ремонт

Исходные каталоги `config/maintenance/requirements.json` и `repairs.json`
версионируются в поставке; генератор не содержит второго перечня требований.
Он переносит каталог и подставляет только исходные значения параметров.
Дополнительное требование из конфига сохраняется без изменения кода генератора.

Профиль содержит 14 требований: интерпретатор и Git (`deps`), репозиторий и семь каталогов,
конфигурацию проекта и три собственные базы (`infra`). В каждой записи обязательны
`id`, `kind`, `check`, `apply`, `recommendation`. Требования выполняются в порядке
каталога. Команды выражены `argv`, а не неявным shell-скриптом.

| Прикладной модуль | Владелец, которому делегировано создание |
|---|---|
| `poise_environment.repairs.repository` | Только чтение локального Git через общую библиотеку запуска |
| `poise_environment.repairs.project_config` | `ProjectCommands` / `FileProjectSetup` |
| `poise_environment.repairs.task_database` | `Database` |
| `poise_environment.repairs.requirements_database` | `RequirementsStore` |
| `poise_environment.repairs.telemetry_database` | `TelemetryDatabase` |

У каждого модуля свои коды и шаблоны рекомендаций. Общая механика файлов,
процессов, протокола и проверки SQLite используется из общих библиотек. Схема
сравнения получается через того же владельца в отдельном временном каталоге;
ручной копии DDL и параллельной системы миграций нет.

`infra` создаёт только отсутствующий объект. Каждый адаптер БД перед действием сверяет выбранный `state_root` с конфигом
и не разрешает перенаправить создание базы за его пределы. Существующая повреждённая база,
неизвестная версия, несовместимая схема или невалидная конфигурация приводят к
`action_required`, а не к замене файла. Автоматического `DROP`, переноса истории,
сброса Task, рекурсивного `chown` и повышения привилегий нет. Перед обслуживанием
оператор останавливает конкурирующие записи. SQLite sidecar-файлы означают
необходимость штатного завершения/checkpoint владельцем, не разрешение удалить их.

## Переопределение и диагностика

```bash
poise infra --catalog /srv/poise/profile/requirements.json \
  --repairs /srv/poise/profile/repairs.json --dry-run \
  --set state_root=/srv/poise/alternate-state
```

Одинаковые `--values` и `--set` нужно передавать всем трём командам. Приоритет:
значения каталога → файлы values слева направо → явно объявленные environment
параметры → CLI-переопределения. Неразрешённые параметры и неверные типы
отклоняются до действий. Переопределение не означает разрешения переписать уже
опубликованную конфигурацию: расхождение требует её управляемой ревизии.

`check` и оба `--dry-run` не вызывают `apply`. Они не изменяют проверяемую
конфигурацию и базы. Временные файлы захвата и эталонной схемы создаются вне
проверяемой установки. Это не ядро sandbox: сам каталог является доверенной
программой оператора, поэтому явно объявленные check-команды также должны быть
диагностическими.

Коды результата общего исполнителя: `0` — выполненные требования; `2` — неверный
вход; `3` — требуется действие оператора; `4` — ошибка исполнения. `ready` означает
готовность среды по каталогу, но не успешность жизненного цикла Task.

## Граница приёмки

Проверки развёртывания находятся в `tests/maintenance/test_deployment.py`. Они
готовят собственные Git-репозитории и профили и вызывают публичные команды.
Полная ПМИ, ПСИ Task/Sprint/rework/crash и переключение на новую эксплуатационную
установку — отдельные следующие пункты плана. Успешный `check` их не заменяет.
