# Поэтапные требования к содержимому задачи

Обновлено: 2026-09-14T00:00:00+05:00.

## Реализованный контракт DDD-02

Task владеет ContentPolicy, ContentSnapshot и CheckRegistry. Чистая библиотека `modules/content_requirements` не знает имён goal types, не читает файлы, не запускает команды, не меняет Task/Sprint. Она принимает снимок и возвращает Assessment. Проверенные пути в наблюдения превращает существующий filesystem adapter. Переход `verified` принадлежит Task и повторно проверяет gates — runner не может ограничиться выставлением статуса.

Два источника предикатов: `process.content_contract` (минимумы типа цели) и `task.content_contract` (решения планировщика конкретной задачи). Оба обязательны в формате, даже если каждый содержит три явно пустых списка. Process packs не наследуют друг друга. Слои объединяют каталог неизменяемых определений: повтор неизменного определения идемпотентен, замена существующего запрещена. Какие из этих предикатов являются gates конкретной Task, задаёт `stage_contracts`.

## Точный StageContract Task

Новая Task обязательно содержит `stage_contracts`: по одному объекту на каждый route stage в том же порядке. Объект имеет точные поля `stage_id`, `allowed_paths`, `entry_requirements` и `exit_requirements`. Read-only stage не может иметь writable scope. Ссылка gate обязана указывать на существующий предикат с теми же stage и phase: `pre` для entry, `post` для exit. Списки refs — явное подмножество каталога ContentPolicy, а не неявно все правила phase.

`allowed_paths` из process stage задаёт шаблон при планировании, но в runtime действует точный `allowed_paths` из Task StageContract. Перед submit, материализацией artifacts и любым action runtime повторно проверяет entry gates и текущий Git scope. Отказ не создаёт submission и не меняет Task. После внешнего `apply_plan` scope проверяется ещё раз; action с внешними путями не может завершить stage. Exit gates проверяются после получения outputs и checks и ещё раз в Task перед `verified`.

Новый artifact-предикат обязан явно объявить `source`: `{"kind":"preexisting"}`, `{"kind":"stage_output","producer_stage":"..."}` или `{"kind":"declared_arrival","arrival_stage":"..."}`. Для активного `stage_output` producer обязан доминировать consumer на обычном и rework маршруте, иметь покрывающий writable scope и независимый exit gate на тот же output. `declared_arrival` не может удовлетворять более ранний entry gate.

Добавленные через `content_additions` предикаты не активируются скрыто: сохранённый StageContract повторно валидируется, а новый ID становится gate только после явной reviewer-ревизии. Переходная операция `initialize_stage_contracts` единожды инициализирует прежнюю persisted Task; до неё start, acquire, context и submit отклоняются. `revise_stage_contract` доступна только текущему владельцу на inspection stage с точной авторизацией `{"role":"reviewer"}`. Обе операции сохраняют old/new, reason, authorization, actor, `expected_version` и `request_id`; точный replay идемпотентен, а изменённое intent с тем же ID конфликтует.

## Четыре вида механических требований

| kind | Что проверяется |
|---|---|
| `section` | объявленная секция имеет одно из явно заданных состояний empty/template/populated |
| `trace` | конкретная точка конкретной цепочки заполнена; при необходимости поля равны заданным значениям |
| `coverage` | каждое требование задачи представлено хотя бы одной цепочкой; optional явно перечисленные общие точки этой цепочки заполнены |
| `artifact` | количество уникальных проверенных файлов в scope с соответствующим path pattern находится в заданном интервале |

Каждое правило обязательно содержит `id`, `kind`, непустой список `stages`, `phase` (`pre` или `post`) и поля своего вида. Никаких guessed/default stages. Чтобы обязать «начиная с tests», планировщик явно перечисляет tests и последующие нужные этапы. Ветвящийся runner не будет выводить сроки по числовому индексу.

`coverage` — покрытие требований задачи, не доказательство корректности. Две цепочки для одного требования могут иметь разные сроки остальных точек. Каждая такая точка проверяется своим `trace`-правилом.

## Дополнительные секции

Определение: `id`, `template`, `normalization` (exact/strip), `write_stages`. Для заполнения передаётся текст в `sections`. Необъявленная секция отклоняется; объявить и заполнить её можно одним result packet. Обязательность задаётся отдельным правилом — описание секции само по себе не делает её обязательной на всех этапах.

Стандартные секции текущего этапа сохраняют свой исходный контракт. Дополнительные секции живут на уровне задачи: ранее заполненное содержимое доступно следующим этапам и не требуется повторно посылать. Bootstrap помещает в шаблон только дополнительные секции, разрешённые для записи на текущем этапе, и возвращает каталог остальных с текущими данными.

## Трассировка

Цепочка задаёт `id`, явные `requirements` из задачи и упорядоченный список `points`. Точка имеет `id`, `kind`, `fields`, `write_stages`.

- `text`: непустой текст; `fields={}`.
- `method`: ID уже зарегистрированного точного метода; `fields={}`. Метод можно зарегистрировать тем же пакетом до обработки точки.
- `record`: структурированные текстовые поля. `fields` отображает имя поля в явный список допустимых значений; `[]` означает любой непустой текст. Все перечисленные поля нужны для полной точки. Неполный record можно сохранить, но он не пройдёт требование заполненности на нужном этапе.

### Достижимость срока trace-требования

Каждое новое правило `kind=trace` обязано иметь хотя бы один общий этап между
собственным `stages` и `write_stages` указанной точки. Дополнительно учитывается
фаза и порядок этапов процесса: для `phase=pre` хотя бы один объявленный этап
записи должен находиться строго раньше самого раннего обязательного этапа
(`earliest required stage`), а для `phase=post` допустима запись на самом раннем
обязательном этапе. Поэтому same-stage запись удовлетворяет `phase=post`, но не
может впервые наполнить точку до entry gate `phase=pre`.

Ошибка пригодна для исправления контракта и называет ID требования, маршрут,
точку, `phase`, её `write_stages`, все `due_stages` и `earliest required stage`.
Порядок берётся из явного списка этапов сохранённого процесса, а не из строковой
сортировки идентификаторов или скрытого workflow-графа.

Один доменный валидатор проверяет весь новый кандидат goal type, прямое создание
Task, перевод standalone newborn Task в ready и публикацию Sprint. Для активной
Task он проверяет только действительно новые требования из `content_additions`.
Отказ происходит до создания Task/worktree, освобождения newborn Task, публикации
участников Sprint либо сохранения submission соответственно.

Уже сохранённый контракт восстанавливается структурно через отдельный read-path
без применения нового правила: история остаётся читаемой и не переписывается.
Миграция прежних process snapshots не выполняется. Это исключение не разрешает
добавить к сохранённому контракту новое недостижимое trace-требование.

`stages` перечисляет все этапы обязательности, а не только последний срок. Если
доказательство впервые создаётся на этапе, его первоначальный gate на этом этапе
должен быть `phase=post`; последующие этапы могут потреблять уже созданную точку
через `phase=pre`. Расширять `write_stages` на поздние этапы только ради формального
пересечения нельзя. Это правило проверяет лишь доступность записи к первому сроку;
ветвящийся маршрут и фактические gates по-прежнему задаются явно.

Известный словарь record не захардкожен. Например, проект определяет поля `state=[planned,documented]`, `reference=[]`. На раннем этапе planned допустим; позже правило `field_equals={state: documented}` требует смены состояния. Это не проверка существования документа. Физическое существование нужно проверять путём артефакта или точной командой проекта. Будущая документация не обязана существовать на старте.

Для логического аргумента config может задать facts/assumptions/inference/conclusion. Для verdict — result/basis с нужным словарём. Наличие отрицательного verdict может быть достаточным для review/verification; наличие и удовлетворённость — разные требования. Политика `field_equals` явно определяет, требуется ли положительный исход. Истинность аргумента и достаточность основания оценивает агент на осмотре.

Изменение ранней точки очищает актуальность только последующих точек этой же явно упорядоченной цепочки. В БД записываются новые слои/tombstones; прежние доказательства не исчезают. Другая цепочка не затрагивается. Это реализованная локальная модель, не полный граф инвалидации всего продукта.

## Пакет результата агента

Все поля обязательны; отсутствие данных выражается явными пустыми коллекциями:

```json
{
  "sections": {"report": "Содержательный итог текущего этапа"},
  "artifact_paths": [],
  "commit_message": "",
  "content_additions": {"sections": [], "routes": [], "requirements": []},
  "trace": {},
  "method_additions": []
}
```

`content_additions` позволяет зарегистрировать секции, цепочки и дополнительные обязательства. `trace` — изменения точек вида `{route: {point: value}}`; для осмысленной очистки разрешён null. Snapshot и declared contract получаются самим AI poise. Агент не передаёт status/version/task_id/Git diff/hashes.

`method_additions`: список `{method: <точный метод>, stages: [<этапы исполнения>]}`. Поля метода: id, argv, cwd, environment, expected_exit_code, stdout_contains, stderr_contains. Verification method не задаёт таймаут: после запуска AI poise ждёт конечный результат процесса. Метод имеет неизменное определение; другой способ/ожидание получает новый ID. Такой метод сразу включается в checks указанных этапов. Пустое расписание допускается явно, например для метода, который нужен только automatic mapping; AI poise не угадывает его назначение.

## Последовательность verify

1. Проверить форму пакета, текущие entry gates и `allowed_paths` до материализации artifacts, action и любой мутации Task. Если уже существующее входное требование нарушено, отказ не создаёт submission, artifacts, command evidence или Git-кандидата.
2. Зарегистрировать допустимые добавления в кандидатной Task, применить изменения секций/точек, повторно провалидировать StageContract и сохранить один submission со всеми слоями транзакционно. Регистрация предиката сама по себе не меняет активные refs.
3. Получить Git/проверенные path-only artifacts. Выполнить `pre`-Assessment по активным entry refs. При нехватке данных вернуть `content_requirements_failed`, точные обязательства и текущий контекст; не запускать команды. Сохранённый содержательный кандидат остаётся доступен для доработки.
4. Подготовить локальный Git candidate commit до запуска checks. Каждый receipt относится к этому точному commit/tree, а не к исходному HEAD до подготовки.
5. Выполнить task checks + явные project mappings, включая методы из текущего result packet; сохранить receipts.
6. Выполнить `post`-Assessment. При отказе сохранить локальный candidate commit и результаты команд, но не переводить Task в `verified` и не принимать её результат. Существование локального коммита не означает прохождение gate, приёмку или публикацию.
7. Перед публикацией перепроверить текущие path observations и gates. `Task.mark_verified` также проверяет оба набора требований и не позволяет обойти неудовлетворённый активный gate.
8. При успехе сохранить проверенный результат, очистить runtime и дать доклад. Принятие/continue выполняются отдельно в рамках пользовательского полномочия. Git push не является побочным эффектом `verify` и здесь запрещён.

Повтор того же payload не создаёт второй содержательный слой. Изменённый код может проверяться повторно, даже если payload прежний. Для content failure CLI возвращает exit 1 (штатный отказ требований), а не exit 0 и не AI poise Incident. Cancel обходит обязательность содержимого и не запускает проверки.

## Артефакты

Агент продолжает передавать только пути. Допустимые области — текущие runtime/task/sprint. Тип файла для простого счётчика задаётся scope + pattern. Повтор одного физического пути не увеличивает количество. Счётчик файлов не доказывает число test cases внутри файла. Для точного количества тестов нужен проектный executable check.

В этом срезе artifact_paths должны существовать при подаче пакета. Автоматически генерируемые позже внешние artifacts и их promotion будут подключены через executor/runner на следующем соответствующем маршруте; пока не предусмотрен скрытый режим принятия несуществующих путей.

## Границы

Работает последовательный runner существующего прототипа и rework последнего предъявленного этапа. Механика проверки не зависит от goal_type и отдельно проверена на произвольных stage IDs. Общий runner семи семейств, возврат на произвольный ранний этап, полноценные evidence/resolution aggregates, Sprint planner, 13 производственных конфигураций и scoped waiver пока не реализованы. Ожидание этих возможностей не блокирует использование описанного пути.
Новые методы в исходном контракте Task и в `method_additions` содержат
`verification_plan`. Его матрица проверяется вместе с расписанием, route и
`allowed_paths` до сохранения содержимого, регистрации метода и любых побочных
эффектов. Ошибка не оставляет частично созданную Task или частично применённый
пакет результата.
