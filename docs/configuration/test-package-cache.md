# Кэш тестовых пакетов AI poise

Этот механизм существует только для тестовых пакетов собственной кодовой базы AI poise.
Он не является адаптером кэша для репозиториев, которыми Poise помогает управлять.

## Расположение

Для конкретной проверяемой копии AI poise кэш хранится в `.poise-test-cache/` в этой
копии. Пути в records/evidence относительны этой папке. Перенос checkout не направляет
этот кэш в mutable state Poise.

## Идентичность кэша

Текущая реализация вычисляет SHA-256 всех байтов каждого объявленного входа
ровно в трёх категориях: `source`, `tests`, `fixtures`. Отдельной категории
`support` в каталоге и fingerprint больше нет: исполняемый/helper-код относится
к `source`, а неисполняемые конфигурационные и data-входы — к `fixtures`.

```text
content[group] = [{path: relative_path, sha256: SHA256(file_bytes)}, ...]
  group in (source, tests, fixtures); paths sorted
input_fingerprint = SHA256(canonical_JSON({membership, content}))
record_address = .poise-test-cache/records/<package_id>/<input_fingerprint>.json
```

В fingerprint намеренно не входят environment, Python/runtime version, runner
configuration, timeout policy, lock-файлы сами по себе или абсолютное расположение
checkout. Файл влияет на fingerprint, если он включён в membership конкретного
пакета. Это принятая семантика C018.

## Хеши байтов по группам входов

Пользователь потребовал раздельно учитывать хэши содержимого **проверяемых
исходников, тестов и фикстур**. Имя файла или набора проверок выбирает вход, но
не доказывает его неизменность. Для каждого файла считается SHA-256 его полных
байтов, а не имени, размера или mtime. Фикстуры учитывают код подготовки и данные.

Перед повторным использованием заново определяется состав этих входов и
пересчитываются хэши их байтов. Изменение содержимого между запусками должно
менять ключ; старый результат не подходит новому содержимому.

Четвёртой группы вспомогательных входов нет. `support` не хэшируется и не входит
в cache membership; бывшие такие входы классифицированы как `source` или `fixtures`
по их роли.

## Состав целевого ключа и сохраняемого манифеста

Логический состав ключа по согласованному требованию: идентичность файла/набора
проверок и раздельные хэши содержимого исходников, тестов, фикстур.

```text
набор проверок
  + хэши содержимого проверяемых исходников
  + хэши содержимого тестов
  + хэши содержимого фикстур
```

Это не предписание новой JSON-схемы, названий полей или отдельной миграции.
Текущие группированные списки `{path, sha256}` уже различают содержимое групп
при вычислении общего fingerprint. В нынешнем `result.json` сохраняются
`membership` и общий `input_fingerprint`; пофайловый `content` используется при
вычислении, но не записывается. Отсутствие отдельных агрегатных полей само по себе
не объявляется дефектом и не требует дополнительного этапа разработки.

Каталог должен перечислять проверяемые исходники, тесты и фикстуры данного пакета:
необъявленный файл не попадает в вычисление его ключа. Состав каталога проверяется
отдельно от правильности SHA-256. Неизменный checkout при переносе сохраняет ключ.

## Обычный режим выполнения тестов

Исходники, тесты и фикстуры не редактируются между началом и окончанием одного
запуска. Агент заканчивает правки, запускает проверку и продолжает редактирование
после её завершения. Следующий запуск заново хэширует текущие байты.

Защита от намеренной подмены файлов агентом с последующим возвратом исходного
содержимого **не входит в задачу кэша**. Для неё не требуются неизменяемые копии
checkout, слежение за каждой записью или доказательство неизменности за весь
интервал теста. Такой сценарий не служит блокером, критерием приёмки или основанием
усложнять harness. Прежнее замечание обзора RV2-01 снято из действующей очереди,
а не объявлено исправленным продуктовым изменением.

## Монопольная запись через владение

Рабочее дерево принадлежит одной сессии по [общему правилу владения](../governance/development-rules.md#владение-task-и-worktree).
Входы, тесты и `.poise-test-cache` берутся из этой же проверяемой копии; разные
рабочие деревья не используют общий индекс. Агент завершает один запуск перед следующим.

По уточнению пользователя после обзора `61151e5` конкурентные писатели одного кэша
не рассматриваются как практически значимый штатный сценарий. Прежнее требование
отдельного межпроцессного cache-lock, собственного учёта владельцев и обязательных
конкурентных проверок снято. Не добавлять эту обвязку и не превращать её отсутствие
в блокер. Это решение об области работы, а не утверждение, что блокировка реализована.

### Смерть или зависание владельца

Используется существующий жизненный цикл владения Task/worktree и выполнения команд.
Перехват не разрешает одновременно продолжать старую операцию. Отдельный протокол
восстановления владельца кэша, watchdog или новое хранилище блокировок не вводятся.

### Публикация при сбое записи

Нынешняя запись индекса остаётся неатомарной: обычный сбой записи может оставить
неполный JSON. Это [известное ограничение RV2-02](../operations/known-bugs.md#rv2-02--прерванная-запись-индекса-кэша),
а не доказательство конкуренции сессий и не поручение реализовать новую подсистему.
Для повреждённого record уже существует явный `--fresh`; первичные журналы не удаляются.

## Статус выполнения контракта

Хэширование полных байтов `source/tests/fixtures`, локальность checkout и проверка
первичных доказательств реализованы. Для `runtime-services` явно объявлен
`src/poise/application/check_attempts.py`; регрессия проверяет membership, impact,
изменение ключа при изменении локального файла и неизменность ключа другой копии.

Запись индекса не объявляется атомарной. Отдельное владение cache resource не требуется
в согласованной модели одной сессии на рабочее дерево. Снятые требования и RV2-01
не возвращаются через тесты или критерии приёмки. Cache hit не является новым запуском.

## Reuse и provenance

Успешный fresh run сохраняет terminal evidence и cache record с `package_id`, `input_fingerprint`, `origin_run_id`, относительным `evidence_path` и digest evidence. Cache hit не создаёт вымышленный новый запуск: результат возвращается с `reused=true`, `executed=false` и тем же `origin_run_id`.

Cache schema `ai-poise-test-package-cache-2` сохраняет в result.json manifest
`ai-poise-primary-evidence-1`: относительный путь, размер и SHA-256 каждого
stdout/stderr/JUnit. stdout и stderr обязательны даже при нулевой длине. Обычный
hit проверяет весь комплект, provenance origin и terminal JUnit, а не только
сохранённое поле passed. Symlink-компоненты и ссылки на другой run запрещены.

Повреждённый/исчезнувший первичный файл или несовместимый старый record дают
контролируемую ошибку с указанием `--fresh`, без автоматического повторного запуска
и без удаления прошлого record. Только отсутствие самого record является обычным
cache miss. Неуспешный, прерванный или incomplete-capture запуск сохраняет диагностику,
но reusable record не создаёт. Новая версия record не меняет content fingerprint.

Проверка устанавливает целостность на момент чтения, не гарантирует последующее
существование файлов и не является подписью против субъекта, способного изменить
record вместе с evidence. Полный reuse не подтверждает новую среду исполнения:
для проверки другой Python/environment требуется `--fresh`.

[Решение о полноте evidence](../architecture/cache-evidence-completeness-design.md).

`--fresh` в `tools/run_ai_poise_test_package.py` явно обходит reuse и выполняет пакет повторно; успешный новый запуск становится новым origin для того же content fingerprint.
