# Постоянный журнал сбоев и обходов harness

## Постоянное хранилище

[Порядок записи и проверки](#запись-и-проверка) применяется по мере работы,
до завершения задачи и до удаления единственного источника диагностики.

Общий корень действующей операторской установки:

```text
/home/sbwerewolf/workdata/poise-project-data/poise-op-operation-journal
```

Его `README.md` — общая точка входа для всех проектов установки. Хранилище находится
вне Git-репозиториев, Task-root и runtime-сессий. Существующие F01–F08 сохраняются.
Для новой работы выбирается свободный каталог с ID спринта или самостоятельной
задачи; проект и Task ID записываются в журнале. Для общей работы без Task
используется явно названный каталог операции. Существующий журнал продолжают
на его месте, сохраняя прежние записи.

В каталоге находятся `incidents.md`, `manual-corrections.md` и необходимые отдельные
исходные ответы/доказательства с индексом постоянных путей и SHA-256.
Это рабочие данные, не копия рабочей области, архив Task DB или новый реестр
статусов. Их не добавляют в Git, в том числе при интеграции. Отдельный сервис
автоматической регистрации этим правилом не вводится: агент действительно
сохраняет и проверяет записи доступными владельцами. Для другой установки
оператор явно определяет постоянный корень вне удаляемых материалов и записывает
его в эксплуатационной инструкции.

## Запись и проверка

1. Сразу записать отказ: время, проект/Task/Sprint, точное действие, фактический
   ответ, эффекты либо их неизвестность, причину, повторяемость и решение.
   Ошибка агента и ожидаемый защитный отказ обозначаются именно так; отказ
   не доказывает дефект Poise. Обычный RED предметного теста остаётся его evidence.
2. До ручного изменения записать полномочие, исходные данные, точную границу,
   способ, альтернативы и проверку. После действия дополнить фактический исход,
   неудачные попытки и откат. Предложенный способ отличать от выполненного.
3. Сохранить необходимые полные ответы, входы и результаты отдельными постоянными
   файлами, указать их SHA-256. Временные пути оставить только как происхождение:
   единственная ссылка на удаляемый Task/runtime-файл не является постоянной записью.
   Секреты не копировать.
4. Прочитать постоянные файлы обратно, сверить SHA-256 и полноту ссылок журнала,
   сохранить результат проверки. Для публикации можно использовать существующий
   `BinaryFilePublisher`, без нового копирующего сервиса. Недоступность `artifacts`
   на newborn не задерживает запись: отсутствие native-регистрации указать явно.
5. До accept, завершения, отмены или интеграционной очистки убедиться, что все
   возникшие отказы и обходы уже представлены здесь. Документы Sprint/Task
   ссылаются на постоянные файлы и не остаются единственной копией истории.

Индекс и контрольные суммы обновляются после изменения рабочих записей.
Для уже сохранённого журнала ENV-MAINTENANCE-2.0 проверка выполняется так:

```bash
cd /home/sbwerewolf/workdata/poise-project-data/poise-op-operation-journal/ENV-MAINTENANCE-2.0
test -r incidents.md
test -r manual-corrections.md
sha256sum --check SHA256SUMS
```

Эта проверка подтверждает сохранённые байты, не исправность продукта или native
приёмку. Классификация причин и полномочия принадлежат
[правилу восстановления](../governance/development-rules.md#сбой-harness-и-ручной-обход).

## Известные баги и контроль версий

[Реестр известных багов](known-bugs.md#ведение-реестра) отслеживается Git.
Он содержит актуальную проблему, условия повторения, подтверждённую причину либо
неопределённость, допустимый способ продолжения и ссылку на постоянный журнал.
Полные рабочие логи, установка-зависимые конфиги и сырые ответы остаются вне Git.
Для повторяемой проблемы используется один существующий или новый repair draft
через публичного владельца; незарегистрированный текстовый черновик обозначается
как таковой. После проверенного исправления активная запись удаляется либо
сужается в той же поставке. История остаётся в Git и постоянном журнале.
Ручной обход не закрывает кодовый баг.

## Немедленная поставка общего правила

Общие изменения порядка регистрации сбоев и обходов фиксируются в канонической
документации и кратких правилах агентов сразу после принятия, не в конце предметной
задачи. По прямому поручению пользователя от 21.10.2026 эта общая правка выполняется
непосредственно в `master` операторского репозитория с проверкой ссылок, содержания
и независимым осмотром; рабочие журналы не коммитятся. Это не общее разрешение
править продуктовый код в основном checkout или менять другие ветки и установки.
