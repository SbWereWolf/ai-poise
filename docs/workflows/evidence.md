# Доказательства и наблюдения — контракт DDD-04

Обновлено: **2026-10-22**. Текущий договор файловых доказательств и машинных наблюдений.

## Владение и цель
`CheckRegistry` (verification) хранит точные команды и расписание. `EvidencePlan` определяет роль
результатов и обязательные аргументы/осмотры. `EvidenceBook` хранит неизменные наблюдения,
текущие метаданные файловых доказательств, решения и прежнюю историю. Task композиционно владеет планом/книгой и фазой; runner не правит доменные
поля. Правило одинаково для всех goal types.

## Явный evidence_plan задачи
Для каждого stage нужен объект `subject_methods`, `arguments`, `review_arguments`; даже отсутствие
обязанностей задаётся явно тремя пустыми коллекциями. Пример двух этапов:

```json
{
  "measure": {
    "subject_methods": {
      "M": {"exit_codes": [0, 1], "stdout_contains": ["VALUE="], "stderr_contains": []}
    },
    "arguments": [
      {"id": "A", "kind": "logical", "phase": "continue", "observation_methods": ["M"]}
    ],
    "review_arguments": []
  },
  "audit": {"subject_methods": {}, "arguments": [], "review_arguments": ["A"]}
}
```

Числа/строки выше — пример конкретной задачи, не defaults runtime. M обязан существовать в methods и
расписании measure. Каждая команда содержит полный argv, cwd относительно task worktree, явное
окружение, expected_exit_code и признаки ожидаемого stdout/stderr. Verification method не
ограничивает время исполнения: после запуска AI poise ждёт конечный результат. AI poise ничего не
узнаёт о способе запуска проекта самостоятельно.

Каждый новый verification method дополнительно содержит обязательный `source_under_test`.
Для исходников репозитория это `{"kind":"repository","bindings":[...]}` с одним или
несколькими явными binding: `cwd` меняет рабочий каталог на путь внутри текущего task
worktree, `environment` связывает названную переменную с таким путём. Существующий ключ
окружения нельзя молча заменить binding. Команда без репозиторного исходника использует
`{"kind":"external","reason":"..."}` с содержательной причиной. Пути абсолютные, с `..`,
отсутствующие или выходящие из worktree отклоняются до subprocess.

`CheckRegistry` отклоняет методы с одинаковой полной семантикой, даже если их ID различны,
а на одном этапе — один вызов с разными ожиданиями или разной декларацией provenance.
Разные source bindings образуют разные вызовы. Для nonzero expectation нужен явный
stdout/stderr marker: RED считается связанным только при совпадении failure predicate и
успешном разрешении `source_under_test`.

### Два разных результата команды
1. **Наблюдение распознано**: процесс завершён без timeout/signal, код и признаки результата
   соответствуют явному observation rule. Поле receipt `interpretable`.
2. **Критерий выполнен**: actual exit и признаки совпали с expected contract метода. Поле receipt
   `passed`.

У `observe` отрицательный критерий остаётся наблюдением, outcome=complete. У `check` он даёт
not_satisfied, а не ошибку AI poise. Неопознанный вывод, сбой запуска, timeout/signal не дают
ложного опровержения продукта. Проектные automatic checks всегда guard: включение их ID в subjects
не снимает блокировку. Прочие task checks тоже guards.

У check outcomes: satisfied / not_satisfied / inconclusive. Наличие отрицательного аргумента/subject
даёт not_satisfied; при отсутствии отрицания inconclusive аргумент даёт inconclusive. Это
протокольные результаты семейства; конкретные переходы выбираются явным route config. Статус этапа
verified означает корректность проведения работы, не положительность предметного результата.

## Один пакет результата
В существующий stage result добавлено обязательное поле:

```json
{"evidence_work": {"phase": "prepare", "arguments": [], "decisions": []}}
```

Остальные поля
sections/artifact_paths/commit_message/content_additions/trace/method_additions/stage_work остаются.
Agent не передаёт exit_code, tree hash или receipts; они приходят от адаптера.

При [выбранной сдаче результата](batch-work.md#выбранная-сдача-результата)
автор явно передаёт содержательные секции и при необходимости полное поле
`metadata.evidence_work`; непереданное поле берётся из актуального шаблона этапа.
Эта форма меняет способ подготовки того же результата. `selection.files`
создаёт обычные артефакты и само по себе не создаёт argument, claim, verdict
или решение осмотра. Содержание аргумента, достаточность и независимый осмотр
сохраняют своих владельцев и описанный ниже договор отдельного файла.

Автор предварительно создаёт отдельный файл внутри фактического `task_root` выбранной Task.
В нём находятся факты, допущения и рассуждение, необходимые для проверки утверждения.
Формат выбирает автор: Markdown не обязателен, расширение соответствует содержимому.
Каталог `proofs` в примерах — выбор примера, а не требование приложения.

Предъявление содержит ровно восемь полей:

| Поле | Значение |
|---|---|
| `id` | Непустой устойчивый идентификатор доказательства |
| `kind` | `logical` или `inspection` |
| `claim` | Непустое проверяемое утверждение |
| `path` | Абсолютный путь к отдельному существующему обычному файлу выбранной Task |
| `covers` | Непустой список уникальных действующих `requirements[N]` или `definition_of_done[N]`, индексы с нуля |
| `verdict` | Авторский вывод `proved`, `disproved` или `inconclusive` |
| `observation_ids` | Явный список уникальных действительных наблюдений; может быть пустым |
| `correction` | При первом предъявлении `null`; при исправлении объект `kind`/`reason` |

Например, элемент `evidence_work.arguments` для логического доказательства без командных
наблюдений имеет вид ниже. `/actual/task/root` заменяют полученным `task_root`, а файл
создают до `verify`. Это фрагмент полного stage result, не самостоятельный work packet.

```json
{
  "id": "A",
  "kind": "logical",
  "claim": "Разобранный сценарий удовлетворяет первому требованию задачи.",
  "path": "/actual/task/root/proofs/scenario.txt",
  "covers": ["requirements[0]"],
  "verdict": "proved",
  "observation_ids": [],
  "correction": null
}
```

Обязательные ID, виды, фазы и observation methods задаёт `evidence_plan`. Дополнительные
доказательства можно предъявить под собственными ID без изменения этого плана; они
не заменяют его обязательства. Каждый ID сохраняет один путь, а путь относится к одному ID.
Для второго доказательства создают отдельный файл и второй элемент списка, например `B`.

Решение содержит ровно `argument_id`, `decision` (`accepted`/`rejected`) и непустой `reason`.
Его выдаёт отдельно разрешённый inspect после чтения нынешнего файла:

```json
{"argument_id":"A","decision":"accepted","reason":"Прочитанное обоснование подтверждает заявленный сценарий."}
```

`verdict` автора не означает приёмку. Обязательные `review_arguments` требуют явных решений;
решение о дополнительном существующем доказательстве тоже передаётся явно. Сам `clear`
этапа не принимает все остальные файлы автоматически.

## Текущие файлы и история

Перед предъявлением различайте три вида материала:

| Материал | Владелец |
|---|---|
| Текущее авторское доказательство | `evidence_work.arguments`: отдельный файл со стабильным ID и путём; нынешние байты читает `proof_file`, исправление описано ниже. |
| Зарегистрированный артефакт | [Артефакты и приёмочные черновики](batch-work.md#редактируемые-приёмочные-черновики): обычная регистрация защищает неизменные байты, редактируемый рабочий путь имеет свой явный lifecycle. |
| Машинная квитанция или захваченный результат | Владелец исполнения и сохранённого результата: происхождение и записанные байты сохраняются; это не авторский редактируемый текст. |

`show` с `kind:evidence` возвращает план, assessment, компактные observations, текущие
`arguments`/`decisions` и `historical_arguments`/`historical_decisions`. У текущего файлового
аргумента ровно двенадцать полей: восемь полей предъявления и `state`, `stage`, `iteration`,
`tree`. `state` — `presented`, `accepted` или `rejected`; `tree` относится к исходнику.
Порядок списка соответствует первому предъявлению ID. Исправление заменяет текущую запись
того же ID на прежней позиции, сохраняя остальные доказательства. Решения сохраняют
свой действительный stage/iteration/tree.

Прежние inline-записи с `body`/`revision` остаются историей и не удовлетворяют текущие
файловые обязанности. Новый вход не принимает `facts`/`assumptions`/`inference`/`conclusion`
вместо файла или `revision` в решении. Содержимое файла не помещается в EvidenceBook;
для него нет обязательного хэша, версии, снимка или finalize. Сохранённый полный ответ
прежнего чтения остаётся свидетельством именно того чтения.

Машинные receipts, stdout/stderr, managed runs и обычные зарегистрированные artifacts
сохраняют свои правила неизменности и происхождения. Их нельзя предъявить как авторское
изменяемое доказательство. Такой файл не регистрируют через `artifacts` или
`result.artifact_paths`: его предъявляют только полем `path` аргумента. Незарегистрированный
авторский файл может находиться в допустимой части Task, в том числе внутри её artifacts
каталога; весь этот каталог не запрещён. Отдельный договор
[приёмочных черновиков](batch-work.md#редактируемые-приёмочные-черновики) сохраняется.

## Чтение нынешнего содержимого

После получения ID из `evidence` проверяющий читает его через публичный `show`:

```json
{"operation":"show","input":{"queries":[{"id":"read-a","kind":"proof_file","argument_id":"A","representation":"text"}]},"messages":[]}
```

Query имеет ровно `id`, `kind`, `argument_id`, `representation`. Представление указывают
явно: `text` или `base64`. Значение ответа содержит ровно `status`, `task`, `argument_id`,
`path`, `representation`, `content`, `size_bytes`; `status` равно `read_only`.
Каждый запрос заново читает фактические байты, включая изменение файла до следующего
предъявления. Текст читается строгим UTF-8 с сохранением CRLF и NUL. `base64` возвращает
все байты с обычным padding; `size_bytes` — размер исходных байтов. Пустой файл читается.
При ошибке UTF-8 следует явно запросить `base64`; автоматического переключения нет.

Несколько известных ID читают одним `show.queries` с разными query ID. Полный машинный
ответ сохраняется общим владельцем вывода; ограниченный агентский preview не означает
обрезку прочитанного файла. Для решения используют полный сохранённый ответ, а не один
preview. Отдельного лимита обрезки proof_file нет; общие input/batch ограничения действуют.
Выбранная Task обязательна для этого чтения; остальные taskless инструменты сохраняются.

## Исправление на прежнем пути

Для действительной коррекции автор переписывает тот же файл и предъявляет тот же ID/путь
с непустой причиной. `reviewer_rejected` требует настоящего текущего отказа проверяющего;
`author_unreliable` выражает признание автором недостоверности прежнего доказательства.
Пример значения `correction`:

```json
{"kind":"reviewer_rejected","reason":"Исправлено обоснование случая, указанного проверяющим."}
```

При признании ошибки автором выбирают `kind:author_unreliable` и описывают конкретную
причину. После исправления состояние этого ID становится `presented`, проверяющий
снова читает нынешние байты и выносит новое решение. Неизменённый `B` можно повторно
передать с прежними полями и `correction:null`; его состояние сохраняется.

В следующем законном цикле допускается повторная явная коррекция с теми же восемью
полями, той же строкой причины и тем же исходником: учитывается настоящая стадия/итерация
предъявления. После нового реального отказа допустима следующая `reviewer_rejected`.
Старый отказ не разрешает такую коррекцию после приёмки без нового отказа. Точный повтор
уже применённого предъявления в том же контексте не создаёт нового бизнес-результата.
Чтение изменённого файла само по себе не объявляет коррекцию и не меняет приёмку.

## Отказы и продолжение

| Причина | Действие |
|---|---|
| `proof_argument_invalid`, `proof_argument_duplicate` | Исправить точные поля, вид, вердикт и уникальность ID/списков |
| `proof_file_missing`, `proof_file_not_regular` | Подготовить обычный файл по предъявленному пути |
| `proof_file_foreign_task` | Выбрать абсолютный путь внутри текущей Task |
| `proof_file_path_changed`, `proof_file_path_conflict` | Сохранить прежний путь ID и отдельное расположение каждого доказательства |
| `proof_file_ordinary_artifact`, `proof_file_managed_material` | Подготовить отдельный авторский файл, сохраняя материалы у их владельцев |
| `proof_requirement_unknown` | Исправить ссылки `covers` по действующим требованиям/DoD |
| `proof_observation_invalid` | Получить допустимые наблюдения по текущему методу, фазе и исходнику |
| `proof_correction_required`, `proof_correction_invalid` | Указать реальную допустимую причину; не выдумывать отказ проверяющего |
| `proof_argument_unknown` | Получить текущий ID через evidence; предъявить отсутствующее доказательство разрешённым авторским этапом |
| `proof_task_required` | Выбрать Task штатным bootstrap перед чтением |
| `proof_file_representation_invalid`, `proof_file_decode_error` | Явно выбрать text/base64; для не-UTF8 выбрать base64 |
| `proof_file_read_error` | Устранить указанную причину доступа к фактическому файлу и повторить чтение |

Проверки предъявления выполняются до семантической записи и запуска команд; относящиеся
к результату файлы повторно проверяются после внешних действий. Это не транзакция ОС
и SQLite. Если после команд обнаружен отказ, сохраняют настоящие command receipts и
следуют указанному продолжению. Отказ сам по себе не меняет бизнес-результат, решения,
чужие файлы и машинную историю; допустимый аудит попытки сохраняется. Не исправляйте
Task DB вручную и не повторяйте мутацию только ради получения её полного вывода.

## Фазы
PREPARE принимает готовый аргумент по известным фактам. Обязательное отсутствие такого аргумента
блокирует дорогие команды. Он может ссылаться на предусмотренные наблюдения прежнего этапа того же
дерева, но не на будущие текущие.

Для аргумента CONTINUE сначала выполняются методы текущего этапа. AI poise сохраняет batch и
возвращает `awaiting_continuation` с receipts/контекстом. Агент сохраняет остальные поля
исходного результата, меняет `evidence_work.phase` на `continue`, готовит файл и добавляет
его аргумент с настоящими observation IDs, затем снова вызывает verify. Независимого
пользовательского этапа и нового claim нет.

Повтор ожидания с незаполненным аргументом не запускает команду заново. CONTINUE принимает только
наблюдения соответствующей задачи, этапа, итерации и текущего batch. Ссылки на другое/устаревшее
наблюдение отклоняются. Изменение дерева или явно переданной среды даёт observations_stale, а не
тихую подстановку старого результата. Агент возвращает phase=prepare, удаляет неподтверждённый
continue-аргумент и получает новое наблюдение. Это инженерное исправление, не автоматическая выдумка
evidence.

## Переиспользование evidence и артефактов

Evidence и полезные артефакты разрешено переиспользовать между Task/ветками, когда их provenance
действительно совпадает. Для repository evidence обязательная идентичность включает **точный hash
commit, на котором доказательство получено**. Совпадение commit hash — необходимое условие reuse
такого evidence; дополнительно должны быть совместимы проверяемое требование/метод, source
provenance и неизменяемые входы конкретного evidence kind. Совпавший hash не превращает
доказательство другого смысла в подходящее.

Если проверяемый commit hash изменился хотя бы на один commit, прежнее repository evidence больше не
доказывает новый результат и требуемое доказательство выполняется заново. Нельзя переносить PASS
только потому, что diff кажется несвязанным или artifact bytes совпали. Артефакты как данные могут
переиспользоваться по их собственным owner/path/digest правилам; receipt доказательства их
корректности остаётся привязан к commit hash и своему контракту.

При [автоматической промотке после restart](batch-work.md#автоматическая-промотка-после-перезапуска)
каждый достигнутый этап проверяется как текущий на сохранённом текущем коммите.
Переключения на исторический commit нет; прежний PASS не заменяет новое выполнение.
До проверки применяется текущий договор и совместимость методов/ожиданий/расписания
и плана доказательств. Несовместимость останавливает продвижение, не подменяя договор.
Новые квитанции сохраняет существующий runner; исторические остаются происхождением.
Обычные обязательные зарегистрированные файлы должны сохранить идентичность и байты;
историческая неполнота не освобождает от обязательных текущих файлов.

### Конфигурационные наборы и повторные проверки

Необязательный `check_runner.systems`, если задан, явно объявляет обе системы —
AI poise и обслуживаемый проект: абсолютный repository и непустой список абсолютных
configs каждой. Известный неполный раздел отклоняется; отсутствующий раздел даёт
пустой набор companions. Требуемые inputs конкретного метода остаются обязательными.
Повторная проверка использует текущие системы без отката к историческим commit IDs;
сохранённые условия объясняют различие результатов.

Перед запуском фиксируются bytes объявленных конфигов, пути, digests и копии
`captured_path` в порядке конфигурационного списка. Недостающий/изменённый обязательный
набор препятствует созданию или повторному использованию proof по его договору.
Scoped копирование между участниками удалено: полный вывод и обязательные текущие
материалы остаются у своих владельцев. Проверки выполняются в текущей работе либо
на разрешённых достигнутых этапах перемотки.

При [интеграции принятого результата](batch-work.md#интеграция-принятого-результата)
обычные stage receipts не заменяют проверки кандидата публикации. Для него используются
подходящие методы **текущего** реестра завершённой Task и свежая полная партия квитанций
с точными commit/tree, определениями методов и сохранёнными stdout/stderr.
Интеграционная квитанция также сохраняет разрешённую `source_provenance` и
`provenance_digest`. Перед публикацией эти значения и фактический `cwd` сверяются
с повторным разрешением текущего метода для кандидата через общего владельца.
Самосогласованный digest подменённых фактов не подтверждает правильность исходника. Старые
квитанции и событие `checks_passed` без идентичности актуальной партии остаются
аудитом, но требуют нового запуска проверок перед публикацией. Пустой набор допустим
только при действительно пустом подходящем наборе текущего реестра; отсутствие самого
реестра не считается этим случаем.

Целевая реализация должна делать эту привязку и reuse декларативно через владельцев
evidence/artifacts, а не требовать от агента вручную копировать receipts или вычислять hashes.
Текущая реализация reuse в отдельных путях по-прежнему требует локальные проверки и не считается уже
расширенной этим документом; изменение runtime выполняется отдельной Task.

## Актуальность и повтор
Verify и явный rework после `checks_failed` используют один канонический путь построения
invocation и `execution_key`. Invocation содержит точный снимок выбранного метода, включая
ожидания, роли guard/subject и observation rules, разрешённый cwd, фактически переданный env и
разрешённую `source_provenance` с её digest. `execution_key` строится из stage, iteration,
наблюдаемого Git tree и полного списка этих invocations. Отдельного source-less ключа для
поиска failed batch нет.

Исторический batch не заменяется. Повтор без изменения входов использует receipts только после
трёх последовательных проверок: каждый batch receipt полностью совпадает со своей
неизменяемой записью evidence ledger; его method, expectations, cwd, tree и provenance точно
соответствуют текущему каноническому invocation; существующие `stdout`/`stderr` совпадают с
сохранёнными digest. Control-поля receipt имеют строгую форму, завершённый известный exit и не
допускают timeout. Env участвует в `execution_key`, но не записывается целиком в receipt.
Неуспешные guard/transport можно повторить только в рамках явного `verify_attempts`.

До продолжения проверяется существование и digest raw output. При неизвестном исходе прерванного
внешнего процесса сохраняется прежнее безопасное блокирование DDD-03 — recovery runner не
имитируется.

Повтор после неуспешного разрешённого внешнего действия также сверяет execution_key. Изменение env
требует нового запуска; неизменное состояние не запускает тесты повторно. Receipt хранит разрешённую
`source_provenance`, `provenance_digest` и отдельный `expectation_digest`; они входят в identity
исполнения и позволяют отличить проверяемый источник от ожидаемого результата. Git push не является
разрешённым внешним действием.

Изменение Git tree, метода, ожиданий, cwd/env, разрешённой provenance либо любого поля
сохранённого receipt делает batch недоступным для reuse/rework до изменения lifecycle или
execution state. То же относится к отсутствующей ledger-записи и повреждённым либо удалённым
файлам output. Runtime не пробует второй ключ, legacy alias, tolerant reconstruction или
fallback к похожему batch; прежние неканонические данные не переписываются миграцией.

### Замена устаревшего метода наблюдения

Если зарегистрированный предметный метод устарел после изменения репозитория или внешнего
контракта, Task не пересоздаётся и её БД не исправляется вручную. Текущий этап с handler
`observe` может передать в обычном `method_additions` тот же защищённый пакет изменения
реестра, что и этап-владелец `test_registry`: `request_id`, точную `expected_revision`,
непустой список `operations` и полный текущий список `executable_obligations`.

Это узкое делегирование владения разрешает только `replace` метода, который одновременно:

- входит в `evidence_plan.subject_methods` текущего этапа;
- уже существует в current registry;
- сохраняет прежние `method_id`, полный список `stages`, `evidence_kind` и `covers`;
- не меняет `executable_obligations`.

Добавление, удаление, reschedule, замена same-stage guard вне `subject_methods` и изменение
классификации либо покрытия остаются исключительным правом этапа `test_registry`. Весь пакет
сначала проходит обычную проверку revision, idempotency digest, формы метода, provenance и
verification plan. Любой отказ оставляет Task, current/history реестра и журнал без изменений.

Первое успешное применение сохраняет прежний current snapshot в history и привязывает к
request неизменяемый audit receipt: `task`, `actor`, `stage`, `iteration`, `request_id`,
`previous_revision`, `new_revision`, изменённые `methods` и `receipt_id`. Тот же request после
любого числа последующих редакций и после перезапуска возвращает исходные audit-поля и
`receipt_id` с `replayed=true`; событие `verification_registry_changed` второй раз не пишется.
Изменённый payload с тем же request ID отклоняется.

Исторические определения методов, command receipts, их source/expectation provenance,
дерево и execution identity, аргументы и assessments не перезаписываются и не
переинтерпретируются. Следующий `verify` исполняет только новое current-определение. Текущую
revision, current, history, requests и `executable_obligations` перед заменой следует получить
одним `show` query с `kind=verification_registry`; файловая Task DB не является API.

Для разрешённого restart/ready действует тот же авторитетный current registry,
а creation methods остаются историей создания. Независимая правка расписания
валидируется по текущим ID; неизвестная ссылка отклоняет ready атомарно.
Сохранение реестра, отсутствие мутации при семантическом no-op, один audit для
фактического изменения и порядок восстановления описаны в
[реестре после перезапуска Task](batch-work.md#реестр-после-перезапуска-task).
Исторические command receipts сохраняются для осмотра, но не становятся актуальным
доказательством изменённого метода или нового кандидата.

Не заявляется полная идентичность внешней среды: время, состояние внешнего сервиса и ignored файлы
автоматически не fingerprint-ятся. Для таких зависимостей нужны явные команды/наблюдения проекта;
адаптеры и более точные правила актуальности расширяются по реальному использованию.

## Осмотр и обратная связь
Процесс может задать: measure → audit(clear→terminal, changes_requested→measure). Отказ по аргументу
выбирает changes_requested без создания фиктивного исправления или новой задачи. Коррекция
следует [порядку прежнего пути](#исправление-на-прежнем-пути); текущая запись заменяется,
а настоящие решения и машинная история сохраняются. Inspect может одновременно работать с
обычными findings/resolutions DDD-03.

EvidenceBook проверяет метаданные, допустимость ссылок и решений. Истинность утверждения
проверяет агент по нынешнему файлу и действительным наблюдениям. Представленные demo
decisions — fixtures, не независимый peer review.

## Инструменты
`verify` принимает весь пакет; `show` с `kind:evidence` показывает текущий план, assessment,
метаданные, решения, историю и компактные observations. `kind:proof_file` читает нынешний
файл. Полный stdout/stderr — файлы у задачи. `cancel` не
требует заполнить недостающее evidence. Артефакты по-прежнему передаются только путями, без новых
деклараций.
Поставляемые [evidence_demo.py](../../examples/evidence_demo.py) и
[catalogue_walkthrough.py](../../examples/catalogue_walkthrough.py) используют настоящий
файловый договор. Первый принимает `--directory` и `--scenario` со значениями
`command_negative`, `logical`, `mixed`, `observe_feedback`; второй — `--directory`,
`--goal`, `--scenario short|feedback`. Сценарии выполняются в отдельной подготовленной
области; их синтетические роли не заменяют независимого проверяющего.
Для RED поле `verification_plan.red_failure` фиксирует код выхода и полные
`stdout_equals`/`stderr_equals`. Совпадение буквальное: дополнительный сбой или
любой иной дополнительный вывод не подтверждает ожидаемый RED, даже если старые
маркеры присутствуют.


## Сохраняемые входы и приёмочный манифест

Обновлено: **2026-10-08**.

Комплект приёмки находится в папке Task и сохраняется в течение приёмки. Он содержит точные внешние
файлы,
необходимые объявленным проверкам, сведения о производителе и принятом входе, контрольные
суммы, настоящий stdout/stderr, обязательные объявленные файлы результата и манифест.
Передача и очистка временной сессии сохраняют этот комплект. Интеграционная проверка
использует сохранённые байты и реальные receipts. Удаление всего Task-root регулирует
[отдельный договор поставки](terminal-materials.md#договор-и-граница-хранения): необходимые
постоянные
результаты получают согласованное назначение до удаления. Без такого соглашения
Task-root не удаляется.

Файл во временной папке review/runtime сначала копируется в Task через существующего
[владельца артефактов](batch-work.md#создание-файлов). Исходный временный путь не служит
постоянным входом. Папка `runs` **внутри постоянной папки Task** хранит доказательства
команд; она отличается от очищаемого каталога сессии. Пути разрешают настроенные владельцы
Task и артефактов; имя каталога само по себе не определяет его срок хранения.

### Объявление входов метода

`artifact_inputs` — необязательная декларация конкретного метода, с точными полями
`manifest_directory` и `files`. Без неё метод не создаёт приёмочный манифест. Пустой
`files` допустим и всё равно требует проверки явно заданного каталога манифеста.
Зависимости автоматически не обнаруживаются: необходимые файловые входы объявляют в
контракте, а обязательные выходные доказательства — в `outputs`.

Фрагмент метода ниже показывает форму декларации. Digest и commit здесь условные;
подставляются значения принятого входа, а не хеш пересобранного вместо него пакета.
Полный метод дополнительно содержит обычные argv, окружение, source contract и критерии.

```json
{
  "artifact_inputs": {
    "manifest_directory": "artifacts/acceptance",
    "files": [
      {
        "id": "wheel",
        "path": "artifacts/inputs/accepted.whl",
        "digest": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc",
        "producer": {
          "task_id": "PACKAGE-PRODUCER",
          "commit": "dddddddddddddddddddddddddddddddddddddddd"
        },
        "input_ref": "accepted-package",
        "environment": "ACCEPTED_WHEEL"
      }
    ]
  },
  "outputs": [
    {
      "id": "proof",
      "path": "proof/verification.txt",
      "required": true
    }
  ]
}
```

| Поле | Смысл и проверка |
|---|---|
| `manifest_directory` | Путь относительно постоянной папки Task, внутри настроенного Task artifact prefix; путь, равный самому prefix, допустим. |
| `files[].id` | Уникальный безопасный идентификатор входа. |
| `files[].path` | Путь файла относительно папки Task. Для опубликованного `scope:task` файла он включает настроенный artifact prefix. |
| `files[].digest` | SHA-256 точных принятых байтов, 64 строчные шестнадцатеричные цифры. |
| `files[].producer` | Точные поля `task_id` и `commit`; commit — 40 строчных шестнадцатеричных цифр. |
| `files[].input_ref` | Непустая ссылка на объявленный принятый вход. |
| `files[].environment` | Уникальное имя переменной, в которую runner передаст фактический постоянный путь файла. |

Происхождение принятого входа устанавливают при объявлении. Проверка сохранения сверяет
объявленные сведения и точные байты. Идентификаторы, пути и имена переменных не повторяются;
вход не заменяет явную переменную окружения метода. `POISE_RUN_OUTPUT_DIR` зарезервирована
runner. Изменение метода выполняется через существующего владельца текущего реестра и
разрешённый этап, с сохранением исторических definitions и receipts.

Каталог манифеста наблюдается **до** чтения входов и выполнения команды. Symlink в корне
или пути, существующий родитель-файл, неверный тип конечного узла и путь вне настроенного
artifact prefix вызывают отказ. Безопасный ещё не созданный каталог допустим; предварительная
проверка его не создаёт. Проверка файлов включает принадлежность Task, обычный файл и
точное совпадение digest. `verify` проверяет все выбранные методы до submission и
резервирования запуска. Независимая подготовка явно переданных артефактов публичным
пакетом остаётся отдельным файловым действием.

### Форма манифеста и повторная проверка

После настоящей команды и захвата её доказательств владелец публикует манифест,
читает **реально опубликованные** байты с проверкой пути и SHA-256, затем проверяет
их схему и соответствие настоящему receipt, методу и кандидату.

`acceptance-manifest-1` имеет ровно поля `schema`, `task_id`, `method_id`, `commit`,
`tree`, `inputs`, `evidence`, `receipt`. Идентификаторы — непустые строки, commit/tree
содержат 40 строчных hex-цифр; inventories — списки объектов, без неизвестных полей:

- вход: `id`, абсолютный постоянный `path`, `digest`, `producer`, `input_ref`;
- stdout/stderr: `kind`, абсолютный постоянный `path`, `digest`;
- захваченный выход: `kind:output`, `id`, абсолютный постоянный `path`, `digest`;
- receipt: `id`, `actual_exit_code`, `passed`, `definition_digest`.

Вложенный `producer` имеет ровно `task_id` и `commit`; digests содержат 64 строчные
hex-цифры. `actual_exit_code` — JSON integer, `passed` — JSON boolean. Подмена `true`
числом `1`/`1.0`, либо integer `0` значением `false`/`0.0`, отклоняется **до сравнения
значений**. Например, `Acceptance manifest receipt.passed: invalid type` указывает
именно на тип поля. Ошибка digest, отсутствующий файл и ошибка схемы имеют разные причины.

Receipt хранит ссылку на манифест и снимок декларации метода. Проверка комплекта заново
сверяет точный commit/tree/definition, полный инвентарь входов, stdout/stderr и обязательных
захваченных выходов. Отсутствующий или изменённый обязательный файл, неполный inventory,
неверный кандидат и ложные типы не дают признать комплект пригодным. Необязательный
объявленный выход может законно отсутствовать; захваченный необязательный файл проверяется.

[Передача](local-handoff.md#механическая-последовательность) и
[интеграция](batch-work.md#интеграция-принятого-результата) используют того же владельца
комплекта. Интеграция проверяет декларации **всех** выбранных текущих методов до эффектов
кандидата и ещё раз до первого потребителя. Пока рабочие материалы не выведены из обращения,
завершённый replay интеграции и очистка проверяют сохранённые доказательства без создания
удалённого worktree и без повторного потребителя. После подтверждённого владельцем поставки
начала удаления точный повтор завершённой интеграции и запрос её состояния возвращают историю
без чтения удалённых входов, манифестов и proof. Такие ответы не публикуют
`acceptance_manifests` как текущую проверку комплекта. Само отсутствие файлов не подтверждает
удаление: потеря живого комплекта по-прежнему вызывает отказ. См.
[исторический повтор после
удаления](terminal-materials.md#чтение-и-повторное-использование-после-удаления).

### Повторная проверка после перезапуска

После законного restart и ready [автоматическая
промотка](batch-work.md#автоматическая-промотка-после-перезапуска)
повторяет принятую проверку на текущем `start_commit/current_tree` при совместимом
действующем договоре. Принятый исторический commit остаётся происхождением; прежний PASS
не переносится на новый код.
Потребитель получает сохранённый постоянный вход Task; исходный файл во временной
review/runtime-папке к этому моменту может отсутствовать. Новый запуск создаёт настоящую
квитанцию, stdout/stderr, захваченные выходы и новый приёмочный манифест в постоянной папке
Task. Прежняя квитанция и все байты исходного принятого комплекта остаются неизменными.

Декларация `artifact_inputs` входит в идентичность ожиданий метода при её наличии.
Изменённый допустимый digest или `input_ref` не наследует прежний успех: несовместимый
текущий договор останавливает промотку с `proof_contract_changed` до потребителя.
Некорректная декларация отклоняется при допуске договора. Потеря или изменение принятого
входа, манифеста либо обязательного доказательства даёт `evidence_missing` или
`evidence_changed` до повторного выполнения. Отказ не восстанавливает повреждённый файл
и не меняет остальные доверенные доказательства. Необязательные отсутствующие выходы
остаются допустимыми по своему объявленному контракту.

### Отказ и восстановление комплекта

До запуска исправьте неверную декларацию через её существующего владельца на разрешённом
этапе; неизменяемый контракт корректируется законным restart, если он действительно необходим.
После дефекта производителя/схемы выполните разрешённую доработку и получите новый настоящий
результат проверки. Обычные зарегистрированные файлы не правятся на месте; правила
[черновиков](batch-work.md#редактируемые-приёмочные-черновики) применяются только к заранее
объявленным редактируемым приёмочным материалам.

Если сохранённый обязательный файл потерян или изменён, остановите приёмку, сохраните
диагностику и восстановите точные байты из доступного доверенного источника.
Если для этой среды подготовлена контрольная точка, примените её
[контракт восстановления](checkpoint-recovery.md#контрольная-точка-и-восстановление).
Локальная работа сама по себе не требует создания архива или отправки по почте.
Затем используйте подходящий публичный шаг восстановления/повтора с исходной идентичностью
пакета. Неизвестный исход команды не разрешает запускать её повторно вслепую.

Пересборка с другим SHA-256 является другим входом и требует явного решения о его принятии.
Сохранность при штатной очистке и повторная диагностика реализованы. Восстановление после
произвольного внешнего удаления без доверенных сохранённых байтов не гарантируется;
предварительная проверка не является общей транзакцией filesystem и Task DB.

## Удалённые рабочие доказательства

Полные файлы наблюдений, stdout/stderr и промежуточные артефакты в Task-root
подчиняются [договору
удаления](terminal-materials.md#чтение-и-повторное-использование-после-удаления).
Исторические определения, результаты и provenance остаются у владельцев в DB;
удаление raw proof не требует скрытого файлового архива. Terminal read и точный
completed replay показывают историю без новых checks и без восстановления папки.
Для нового доказательства нужны действительные текущие байты, точный commit и
совместимый метод; отсутствие удалённых файлов не превращается в свежий PASS.
Если proof-файл сам является результатом, его отдельное постоянное назначение
согласуют до terminal handling. Registry receipt не заменяет эти байты.
