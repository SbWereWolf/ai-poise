# Правила разработки AI poise

Обновлено: **2026-09-13**.

## Инварианты
1. Домен не импортирует I/O, SQLite, filesystem, CLI, subprocess или clock. Application использует domain/ports, infrastructure реализует ports; composition связывает явно.
2. Владельцы Task/Sprint/GoalTypeDefinition/ArtifactRegistry принимают только свои изменения. CLI/runner/hooks не присваивают статусы, не обходят repositories и не изменяют snapshot активной задачи через конфиг.
3. Все предметные этапы, секции, шаблоны, команды, output policies и лимиты — явные данные. Разрешены внутренние константы структуры; запрещены hidden defaults/fallback и наследование бизнес-процессов.
4. **Все инструменты AI poise пакетные и декларативные.** Одна инженерная правка множества объектов принимается одним envelope. Нельзя вводить процесс, который требует по вызову на каждый элемент, ручного редактирования DB/config или контроля промежуточной механики агентом.
5. **Генерация обслуживаемых артефактов — обязанность инструмента.** При осмысленном шаблоне он выбран явно; иначе инструмент создаёт файл из готового содержания. Путь, ID, hash, регистрация и создание каталогов автоматические. Path-only регистрация существующего артефакта сохранена.
6. Репозиторий не делает отдельный commit: UoW атомарно сохраняет связанные business изменения. Долгие проверки, Git и внешние операции не держат DB lock. Для файлов и внешних эффектов receipt/явный статус вместо обещания общей SQL-атомарности.
7. Секции и обязательства принимаются в кандидат до pre-gates. ContentPolicy объединяет minima цели и task additions без скрытого ослабления. Для каждого нового trace-требования его этапы обязательности пересекаются с `write_stages` указанной точки; сохранённые контракты читаются без ретроактивной проверки, но новые недостижимые additions запрещены. Каждая цепочка имеет собственные сроки и поля. Наличие evidence не доказывает истинность.
8. Общая механика переиспользуется композиционно. Не создавать отдельные engines по goal_type, универсальный BaseTask с I/O или raw-table editor. Нативные инструменты target codebase не заменяются AI poise ради единообразия.
9. Старые DB/форматы не мигрировать без явного поручения. Действующий store отклоняет неподдерживаемую schema, а не «чинит» её по догадке.
10. Значения токенов/сообщений/времени имеют источник и полноту. Сообщение пользователя считается событием, не tool call. Повторы и handoff не умножают затраты.
11. Длительность и порядок accounting-операций определяются только сопоставимыми монотонными наблюдениями через обязательный `Clock`; UTC используется для аудита и календарной проекции. Production roots явно передают `SystemClock`, тесты — детерминированный `FakeClock`. Смена области сравнения, обратный отсчёт или недоступный стабильный boot ID дают явный отказ либо unmeasured-результат по документированному контракту; wall-clock clamp и скрытый fallback запрещены.
12. Каждый новый verification method явно объявляет `source_under_test`. Repository binding разрешается только внутри текущего task worktree и не перезаписывает переданное окружение; внешний источник требует причины. Семантические дубликаты и конфликтующие ожидания отклоняются до subprocess.
13. Verification methods и команды declarative action не объявляют таймаут исполнения. После запуска AI poise ждёт конечный результат процесса; таймауты capability probes, хуков и другой ограниченной инфраструктуры остаются отдельными явными контрактами.

## Владение Task и worktree

Обновлено: 2026-09-13. Источник: требования задачи 0076;
продолжение ролей и прямая передача — принятые решения 0072/0073.

Сессия владеет не более чем одной Task и одним worktree. Поддерживаются четыре комбинации:
ни одним ресурсом, только Task, только worktree, обоими. Это независимые claims, а не
смена текущего каталога. Обязательный boolean `worktree_required` в process snapshot
типа Task определяет, нужен ли ей зависимый worktree; агент не выбирает этот флаг при захвате.

Захват предварительно проверяет весь требуемый набор, узнаёт собственное владение и
автоматически заменяет прежнее владение ресурсом того же вида. Повторная проверка и
публикация полного набора выполняются атомарно: при конфликте или сбое частичный захват
не остаётся. Чужой живой владелец запрещает захват. Неопределённое состояние владельца
также запрещает перехват; отсутствие PID, давность или отсутствие hook-записи не доказывают
смерть сессии. В нативном пути подтверждённый `SessionEnd` позволяет освободить устаревший
набор при следующем захвате; без авторитетного источника liveness остаётся неопределённой.

Освобождение Task освобождает её зависимый worktree, но сохраняет независимый worktree.
Захват, замена и освобождение claims не меняют cwd, launch roots, HEAD, index или WIP,
не создают коммитов и не удаляют файлы. Они не подменяют сохранение результата, публичный
handoff, терминальную уборку либо отдельно разрешённую интеграцию. Перед сменой предметной
задачи агент сохраняет и завершает либо передаёт текущую работу; атомарная замена claims
сама по себе не разрешает бросить незавершённое поручение.

Task без worktree проходит проверки из настроенного repository и сохраняет результат и
evidence без создания ветки или фиктивного Git delta. Изменение исходников по-прежнему
требует выделенного worktree. Не следует объявлять любую Git-зависимую action пригодной
для Task без worktree только на основании поддержки такого владения.

Newborn Task — это раннее состояние той же Task с постоянным ID и историей, а не временное
вложенное определение. До выбора `goal_type` у неё нет route entry; после выбора применяется
type-specific process snapshot, а переход в `available` разрешён только после полной проверки
готовности. Создатель и последующий редактор используют общий ownership API: освобождённую
Task можно получить автоматически, запись при чужом живом владельце запрещена, независимый
worktree не освобождается. Sprint materialization сохраняет частичные правки, историю,
членство и граф в реальных newborn Task. Legacy embedded definitions переводятся явно, без
массовой миграции; historical replacement relations сохраняют traceability от source Task. Если
DoD недостижим или следующий DoR сломан, Task получает явный outcome `broken` и либо reviewer
исправляет локальный stage contract, либо authorized `restart` возвращает ту же незавершённую
неинтегрированную Task в newborn с сохранением identity, history, Sprint membership, worktree и WIP.
Публичный Sprint action `replace_task` для такого исправления не используется. Это правило реализует
согласованные результаты 0072, 0073 и 0079 и не отменяет прямое создание полной `available` Task.

## TDD и осмотр
До implementation определить owner, вход/выход и полный happy path с явным feedback. Написать проверки и сохранить честный RED. RED допустим только при совпадении заранее объявленного failure predicate и подтверждённой provenance проверяемого исходника; ошибка импорта, чужой checkout или иной несвязанный отказ не являются ожидаемым RED. Осмотреть тесты: реальный результат вместо проверок собственных mocks, batch с несколькими связанными элементами, отказ без частичного применения. Реализовать через API владельцев, выполнить GREEN. Затем осмотреть код и исправления, обновить API/границы/статус/отчёт с временем и упаковать срез.

Полный набор тестов запрещено запускать в процессе работы над задачей, в том числе автоматически на границе поставки. На каждом этапе запускаются только узкие целевые проверки действующей задачи и поддерживаемый быстрый дымный набор `tests/smoke.sh`. Дымный набор содержит конечный явный список test node IDs, принимает путь к Python обязательным аргументом и не заменяет доказательство полного regression-покрытия. Если отдельной задаче действительно требуется более широкий запуск, его состав должен быть явно ограничен и принят в её проверочный контракт; неограниченный repository-wide test discovery не регистрируется.

Архитектурные тесты должны проверять отсутствие SQL/I/O в доменах, наличие единого пакетного прикладного маршрута и отсутствие обязательных ручных правок обслуживаемых файлов. Точные технические тесты формируются по мере реализации, не объявляются пройденными из описания.

## Размер среза
Один срез реализует законченное действие на работающем маршруте. DDD-04A — конфиги, DDD-04B — результаты/артефакты/первичный message event. Не добавлять сотни схем/таблиц и все 13 packs до работоспособного первого пути. Неimplemented API явно остаётся planned.

## Наблюдения и циклы
Graph задаётся явно. Inspect read-only, revise предлагает исправление, следующий inspect решает. Observe/check и PREPARE/CONTINUE не создают новый пользовательский этап. Командное распознавание, predicate и принятие аргумента раздельны. Проверять freshness перед повтором и перед переходом; изменение дерева не скрывается при publication retry.

Route определяет `entry`, outcomes, targets и разрешённые rework-переходы, но не ограничивает количество переходов или посещений этапа. Счётчики visits/transitions принадлежат истории, identity и аудиту. Запрещено вводить эквивалентный предел под другим именем, через глубину маршрута, watchdog, timeout или ограничение рекурсии. Конечная проверка достижимости графа допустима только при валидации структуры и не является пределом исполнения.

## Шаблоны и код инструмента
Явный шаблон содержит принятые значения; его выбор фиксируется. Это не разрешение взять отсутствующее поле из случайного global config. Правка исходного кода и шаблонов самого инструмента идёт coding tools по этому же TDD. После поставки инструментов рабочие config/task/artifact данные обслуживаются ими, а не ручными shell/Python/SQL рецептами.

См. [декларативный контракт](../architecture/declarative-tools.md), [учёт сообщений](../operations/user-message-metrics.md) и [статус реализации](../architecture/implementation-status.md).


## Общие правила агентов

Эти правила адаптированы из независимых от проекта положений `erp/AGENTS.md` по поручению пользователя от 2026-09-10. Этот раздел — канонический источник; корневой `AGENTS.md` содержит его английскую проекцию.

1. Ответы людям и пользовательская документация — на русском. Файлы для агентов (`AGENTS.md`, `.agents/**`, `.codex/**`, управляемые артефакты задач) — на английском. Идентификаторы и синтаксис сохраняют исходный язык.
2. Постоянные правила определяются актуальной человекочитаемой документацией. Навыки, конфигурации, скрипты и инструкции агентов применяют её. Исторические планы и отчёты не дают новых полномочий. Изменения поведения, конфигурации и процесса сопровождаются изменениями соответствующих документов в той же работе.
3. Перед работой с областью прочитать применимые вложенные правила. Частные правила действуют в рамках корневых ограничений с учётом приоритета платформы и пользователя. Загружать только навыки и разделы, необходимые текущему этапу.
4. Продолжать разрешённую работу до согласованного результата, не расширяя область. Делегирование субагентам требует явного разрешения пользователя в текущем запросе. Уточнять только действительно блокирующие решения, учитывая уже выданное разрешение.
5. Перед первой записью проверить Git. Сохранять чужие изменения. Если принадлежность изменённого или неотслеживаемого файла не установлена, получить явное решение пользователя до его изменения. Не сбрасывать, не восстанавливать, не индексировать и не коммитить посторонние файлы.
6. Новая папка верхнего уровня требует явного разрешения с её путём и назначением. Временные файлы и управляемые доказательства задач/спринтов размещать по конфигурации AI poise, по явному контракту расположения проекта. Для локального ai-poise пользователь разрешил `projects/ai-poise/` внутри репозитория; каталог исключён из Git.
7. Расширение файла соответствует назначению и содержимому. Шаблон окружения оканчивается на `.env` и содержит `example`, например `app.example.env`. Параллельные списки оформлять вертикально для устойчивых различий. Репозиторные `.sh` запускать явно через Bash.
8. Значения, влияющие на продукт и его результат, задаются явной конфигурацией. Внутренние константы допустимы лишь без такого влияния. Скрытые значения, резервные пути, старые псевдонимы, двойное чтение/запись и адаптеры совместимости не добавляются без требования. Согласованная замена удаляет прежний путь в пределах работы; отсутствие обязательного входа вызывает явную ошибку.
9. Перед реализацией искать существующее поведение и его предметного владельца. Переиспользовать API владельца или выделить общую реализацию; потребителям оставить композицию и транспорт. Раздельные реализации обосновывать различием семантики или владельцев.
10. Для исполняемого поведения сохраняется TDD. После последних существенных изменений выполнять целевые проверки и осмотр всей правки. Полный набор тестов во время задачи не запускать; использовать только узкие проверки задачи и быстрый конечный `tests/smoke.sh`. Для документации проверять содержание, ссылки и исполняемые утверждения без выдуманной красной фазы. Самопроверка не является независимым осмотром; устаревшее, отсутствующее или неуспешное доказательство не является PASS.
11. Текущий реестр проверок изменять одним guarded-пакетом только на этапе, владеющем `test_registry`. Creation и каждая мутация явно задают `executable_obligations`; скрытой классификации нет. Исторические definitions/receipts не переписывать. Выход из test-inspection требует непустого текущего GREEN executable-набора с полным совокупным покрытием объявленных исполняемых обязательств, но не устаревших методов или полного repository-wide suite.
12. Использовать штатные инструменты и настроенные проверки. Причины ошибок и таймаутов исследовать по доказательствам, не обходить неуспешную проверку и не увеличивать время ради сокрытия зависания. Сохранять диагностические данные ошибок. Не выдумывать метрики расхода или доступность инструментов.
13. Ошибка для пользователя объясняет сбой, установленную причину либо неопределённость и действие восстановления в пределах его полномочий. Не раскрывать секреты и не подменять гипотезу установленной причиной.
14. Разрушительные миграции требуют явного разрешения с объектами и действием. Push запрещён. Коммиты, необходимые по документированному рабочему процессу явно порученной задачи, разрешены без повторного подтверждения: в том числе необходимый базовый коммит и коммиты результата. Включать только файлы этой работы или явно согласованный состав; посторонние коммиты требуют отдельного поручения. Использовать публичные инструменты жизненного цикла AI poise, когда они доступны.
15. При любом терминальном исходе задачи ответственный агент завершает работу уборкой принадлежащих именно этой задаче worktree, локальной ветки, временных файлов и временных резервных копий. Основной checkout, чужие ресурсы, постоянная история и артефакты задачи, операторские резервные копии и данные восстановления незавершённых операций сохраняются.
16. Правило: судьба коммитов требует отдельного явного решения. Правило уборки само по себе не разрешает ни публикацию в `master`, ни уничтожение уникальных коммитов и не предписывает merge или discard. Для успешно принятой работы уборка выполняется только после завершения отдельно разрешённой интеграции. При отмене задачи до удаления ресурса, которое уничтожит уникальные коммиты, должно быть отдельно записано решение об их судьбе.
17. Эти правила устанавливают ручную обязанность агента. При этом автоматизация уборки не является реализацией этой документационной работы и не заявляется как её результат; существующая возможность публичной интеграции описана отдельно ниже.
18. Итог содержит результат, покрытие требований, фактически выполненные проверки, ошибки или недоступные проверки и оставшуюся неопределённость. Проверка этапа сама по себе не является пользовательским принятием. Штатные переходы исполнения, проверки и исправления разрешены поручением запустить задачу; новое обязательное решение и отдельно регулируемые приёмка, публикация или интеграция требуют собственного полномочия.
19. Запуск задачи пользователем разрешает её исполнителю и проверяющему самостоятельно продолжать работу в пределах ворот AI poise и пользовательских ограничений, без отдельной команды на каждую проверку. Если они известны друг другу, в обе стороны сначала сохранить результат и подтвердить освобождение задачи публичным API, затем отправить прямое сообщение получателю; тот захватывает задачу до работы. Следовать [правилу прямой передачи](../workflows/local-handoff.md#прямая-передача-между-исполнителем-и-проверяющим). Сообщение не заменяет владение или независимую проверку.

### Роли этапов и непрерывность поручения

Каждый настроенный этап имеет ровно одну роль — `executor` (исполнитель) или `reviewer`
(ревьюер). Каноническая классификация находится в [карте исполняемого
каталога](../configuration/catalogue-stage-map.md). Роль не выводится из обработчика, статуса
Task, `read_only` или наличия теста: `observe`, `check`, `inspect`, `publish` и другие
обработчики описывают действие этапа, а роль определяет, кто вправе его выполнять.

Явное поручение выполнить Task назначает агента исполнителем и разрешает ему без повторных
команд «дальше» проходить последовательные этапы `executor`, включая предусмотренные ими
тесты, проверки, исправления и повторные реальные проверки. Исполнитель на каждом этапе
по-прежнему выполняет `bootstrap`/`verify`, соблюдает gates, findings, evidence, разрешённые
пути и исходную область задачи. Реальный блокер, недостаток полномочий или новое обязательное
решение пользователя останавливают работу. Агент не создаёт фиктивные пользовательские
сообщения, не правит Task DB или счётчики этапов напрямую и не подменяет evidence.

Поручение пользователя запустить задачу разрешает её назначенному ревьюеру проходить
этапы `reviewer`, включая повторные циклы после исправлений, без отдельной команды на каждое
ревью. Явное ограничение поручения одним этапом или иным объёмом сохраняет силу.
Исполнитель перед границей роли докладывает проверенный результат, выполняет публичный
`handoff`, подтверждает освобождение Task и прекращает её изменять. Затем он отправляет
известному ревьюеру прямое сообщение по [правилу передачи](../workflows/local-handoff.md#прямая-передача-между-исполнителем-и-проверяющим).
Исполнитель не изображает независимый осмотр и не продолжает ревьюерский этап как самопроверку.

Ревьюер получает Task обычным `bootstrap` после освобождения ownership, сохраняет findings и
не исправляет результат на исполнительском этапе. Если нужны исправления, он передаёт Task
обратно тем же публичным `handoff`, проверяет release и прекращает изменения. Назначенный
исполнитель через `bootstrap` выполняет непрерывный участок remediation и снова освобождает
Task и уведомляет известного ревьюера о следующем осмотре без новой команды пользователя.
Сообщение в чате без успешного `handoff` не
является передачей; неуспешный release докладывается как отказ, а прежний владелец не заявляет
передачу завершённой.

Полученные поручения сохраняются в рабочем плане до выполнения, отмены или явной передачи
ответственности, включая контрольные записи и контекст после сжатия переписки. Новое сообщение
дополняет план, если явно не меняет поручение; прочтение или подтверждение не означает выполнения.
После сохранения результата, подтверждённого освобождения Task и уведомления получателя агент
сразу продолжает доступные полученные поручения или разрешённую цепочку этапов и задач в том же
ходе. Финальный ответ допустим только при отсутствии доступной порученной работы: агент сверяет
оставшиеся обязательства и указывает препятствие для каждого. Блокер одной задачи не останавливает
другую доступную работу при соблюдении правил владения. Собственные запущенные операции доводятся
до определённого исхода. Сверка собственных поручений обязательна; опрос статуса другого агента,
чтение его переписки ради прогресса и фоновое наблюдение не нужны. Подробности — в
[правиле передачи](../workflows/local-handoff.md#прямая-передача-между-исполнителем-и-проверяющим).

Свободный проверяющий начинает проверку по полученной передаче без дополнительной команды
пользователя. При нескольких передачах он сначала завершает начатую проверку, сохраняет
результат, освобождает Task и уведомляет исполнителя, затем берёт следующую задачу.
Новое сообщение не прерывает текущую проверку. Следующая уже поступившая доступная передача
обрабатывается сразу в том же ходе, без повторного сообщения или команды «дальше».

`self_inspection` вне goal type `review` — самопроверка исполнителя, а не независимое ревью.
Проверки `check` также остаются работой исполнителя. Этап `publish` классифицирован как
исполнительский, но роль сама по себе не выдаёт полномочие на приёмку, публикацию или
интеграцию: применяются их отдельные пользовательские решения и публичный lifecycle.

Каждая actionable-находка независимого review связывает подтверждённое пропущенное
обязательство, его producer stage, поздний gate и конкретную воспроизводимую проверку. Причина
классифицируется по evidence как дефект AI poise runtime/task contract, пропуск исполнителя, пропуск
проверяющего, штатный защитный отказ либо unresolved; один reject или исторический исправленный
инцидент не доказывает текущий дефект. Канонический порядок и incident-derived checklist:
[проверка по доказательствам](../workflows/evidence-based-review.md).

Публичный `advance` сохраняет явно запрошенный целевой stage и последовательно применяет
обычные переходы Task на непрерывном участке одной роли. Он останавливается на реальной работе,
непройденных воротах, границе ролей или достигнутой цели и идемпотентно продолжается тем же
request после restart либо correction. `verify` по-прежнему только сохраняет результат этапа;
`advance` не выполняет работу за агента и не создаёт скрытого autoaccept.
Обычный переход сохраняет report в `verified`, записывает `stage_progressed`, а не
`user_accept*`. Перед `publish` продвижение останавливается со статусом
`user_acceptance_required`; только отдельное публичное решение пользователя открывает этап.

На границе ролей `advance` не меняет stage или ownership. Отправитель выполняет публичный
`handoff`, затем напрямую уведомляет известного получателя. Получатель захватывает ту же Task
через `bootstrap` и повторяет точный progression request; переход разрешён только после
подтверждённой передачи в другую сессию. Сообщение остаётся внешней координацией и не заменяется
runtime-механизмом.

Обычные маршруты применения правила:

| Сценарий | Обязательный результат |
|---|---|
| Последовательные исполнительские этапы | Исполнитель после успешного `verify` повторяет сохранённый `advance` и продолжает следующий `executor` без новой команды «дальше». |
| Тест или validation внутри исполнения | Исполнитель запускает требуемую проверку, сохраняет фактическое evidence и исправляет допустимый сбой в своём исполнительском участке. |
| Исполнитель → ревьюер | Исполнитель сохраняет результат, успешно освобождает Task через `handoff`, прекращает изменения и напрямую уведомляет известного ревьюера. |
| Ревью запущенной задачи | Назначенный ревьюер получает освобождённую Task через `bootstrap` и проходит reviewer-участок без новой команды пользователя, соблюдая ограничения поручения. |
| Ревьюер → исправление → новое ревью | Ревьюер сохраняет findings, освобождает Task и уведомляет исполнителя; тот захватывает её, исправляет и тем же порядком передаёт обратно. Новые команды на каждый цикл не нужны. |
| Неуспешное освобождение | Отправитель сохраняет ownership, докладывает отказ и не утверждает, что передача состоялась; получатель не начинает изменения. |

ERP-специфичные пути, роли приложений, `preflight`, `taskctl`, `verify_final`, MCP-runner, политики кэша, статусы задач, предположение об отсутствии производственных данных и автоматические коммиты не перенесены. Их наличие в ERP не доказывает наличие соответствующей инфраструктуры в AI poise.

## Начало и завершение работы

Перед содержательной работой явно выбрать рабочую конфигурацию проекта и идентичность сессии, затем выполнить `bootstrap` публичным work API AI poise. До этого допускается только подготовительное чтение для обнаружения или настройки точки входа. Использовать возвращённый контекст задачи, этапа, возможностей и шаблон результата. Не выдумывать идентификаторы, состояние или worktree. Продолжение работы также выполняется штатным API.

Перед сообщением об успешном завершении выполнить `verify` тем же API с актуальным результатом этапа и артефактами. Проверить итоговый статус и обязательные доказательства; выполнить требуемое продолжение в пределах разрешённого этапа. Нулевой код выхода, промежуточный статус и receipt сами по себе не доказывают успех. Штатные этапы `executor` и `reviewer` разрешены поручением запустить задачу; отдельно регулируемые приёмка, публикация и интеграция сохраняют свои требования к полномочиям.

Для штатных переходов исполнения, проверки и исправления таким разрешением служит поручение пользователя запустить задачу; повторное «дальше» не требуется. Оно не отменяет явное поручение только одного этапа, ворота AI poise, отдельные полномочия или независимость проверяющего. При смене роли известные друг другу агенты используют [прямую передачу с освобождением задачи](../workflows/local-handoff.md#прямая-передача-между-исполнителем-и-проверяющим).

### Интеграция завершённого результата

После неизменяемого принятия результата его commit считается `accepted commit` и больше не переписывается. Для подготовки к публикации завершитель использует уже существующие ветку и worktree принятой Task. В этой ветке он создаёт последующие commits изменяемого `integration head`: включает текущий `master`, оставляет conflict state и выполняет проверки. Отдельные integration branch и integration worktree не создаются. Основной checkout не используется для редактирования или разрешения конфликтов.

При конфликте автоматическая часть останавливается со статусом ожидания. Агент разрешает конфликт именно в существующем task worktree, после чего завершитель выполняет объявленные проверки на полученном `integration head`. Непосредственно перед публикацией он под общим для target lock повторно читает `master`: если ветка ушла вперёд, прежний проверенный integration head не публикуется, а цикл update, агентского разрешения конфликтов и проверок автоматически повторяется. Стабильный кандидат публикуется в основном checkout только командой `git merge --ff-only <task-branch>`; прямое обновление target ref и force update запрещены.

Состояние основного checkout и чужой WIP не изменяется подготовительными действиями завершителя: над ними запрещены `stash`, `reset`, `restore`, `checkout`, `clean`, staging, commit, удаление и разрешение конфликтов. Однако грязное или незавершённое состояние может штатно заблокировать `merge --ff-only`. При таком отказе завершитель обязан доказать совпадение до и после для `HEAD`, branch binding, index, tracked/untracked paths, содержимого, типов, режимов файлов и Git operation state; при отсутствии этого доказательства безопасный отказ не заявляется.

Операция восстанавливаема после сбоя и идемпотентна: persisted state различает неизменяемый `accepted commit`, изменяемый `integration head`, наблюдавшийся target head, ожидающие конфликты, результаты проверок, публикацию и каждый шаг уборки. Повтор незавершённой интеграции продолжает только подтверждённую фазу, не переписывает accepted commit и не повторяет уже подтверждённый внешний эффект вслепую.

После подтверждённого fast-forward или доказанного terminal no-op тот же завершитель удаляет task worktree, task branch и все зарегистрированные временные резервные копии этой интеграции; несуществующих integration-ресурсов в уборке нет. Удаление owned-ветки не зависит от `HEAD` основного checkout: завершитель проверяет её commit относительно текущего target и удаляет только всё ещё наблюдаемый ref. Если target после подтверждённой публикации продвинулся к потомку опубликованного integration head, уборка продолжается; переписанная или посторонняя история останавливает её с сохранением recovery state. Временные копии разрешены только в task/integration-scoped каталоге внутри настроенного runtime root; статус успешного завершения недоступен, пока каталог не очищен. Предсуществующие, чужие и долговременные операторские backup-файлы не принадлежат этой уборке и не удаляются. Backup, объявленный результатом задачи либо необходимый для восстановления незавершённой интеграции, сохраняется до отдельного терминального решения.

Публичный `integrate` реализует этот цикл из текущего установленного исходного кода AI poise, а не из accepted commit завершаемой Task. Сохранённое точное legacy-состояние blocked-запроса `integrate-0048-1` восстанавливается в новый цикл без переписывания accepted commit и прежней истории; другие старые формы автоматически не адаптируются. Точный контракт входа, состояний и повторов определён в [пакетной интеграции результата](../workflows/batch-work.md#интеграция-принятого-результата). Проверенное локальное поведение не доказывает push, удалённую публикацию или multi-codebase integration.

Для чтения без задачи `bootstrap` принимает `task=null`, `decision=null`, `feedback=null`, `rework_stage=null`; завершающий `verify` — `result=null`, `artifacts=[]`. Проверять, что получен именно контекст без задачи: сессия может уже владеть работой. `read_only_verified` завершает runtime и возвращает пустой список проверок; правильность ответа проверяется отдельно. Постоянный результат задачи требует формальной задачи и управляемого API артефактов.

Если рабочая конфигурация, runtime или операция недоступны, указать конкретное препятствие и требуемое восстановление. Не подставлять демонстрационный конфиг, эталонную БД или выдуманный успешный статус. До выполнения обязательной операции завершение не считается проверенным через AI poise. Текстовые инструкции устанавливают обязанность, но сами по себе не создают автоматический hook контроля.

Контракт пакетов и статусов: [пакетный инструмент](../workflows/batch-work.md#verify). Настройка проекта: [подготовка проекта](../configuration/project-setup.md). Расположение состояния: [локальная установка](../configuration/wsl-local-delivery.md#пути-project-local-storage).


### Точка входа локальной установки

Для ai-poise используются `.venv/bin/poise work` и `config/projects/ai-poise/project.json`; `bootstrap`/`verify` — операции JSON-пакета, а не отдельные скиллы. Полные команды, передача идентичности сессии и ограничения Git описаны в [настройке ai-poise](../configuration/project-setup.md#локальный-проект-ai-poise). Рабочие данные размещаются в `projects/ai-poise/` внутри проекта по явному поручению пользователя. До появления первого коммита taskless-проверка не подтверждает готовность работы через Git worktree.

## Матрица плана проверки

Каждый новый метод проверки объявляет точный `verification_plan`: непустую
`responsibility`, явную `change_surface`, списки `red_stages` и `green_stages`, а
также `red_failure`. Расписание метода обязано совпадать с объединением RED- и
GREEN-этапов. До сохранения Task или `method_additions` реестр проверяет по
настроенному графу процесса, что на каждом пути к требуемому GREEN каждая часть
поверхности покрыта `allowed_paths` текущего или предшествующего этапа.

RED задаёт точные `stdout_equals` и `stderr_equals`: любая дополнительная ошибка
делает доказательство непригодным. Зависимости pytest рекурсивно не выводятся —
матрица является явным договором. Сохранённые методы без матрицы читаются без
миграции, но новые и изменяемые методы обязаны использовать новый договор.

Например, поверхность `docs/**`, `AGENTS.md`, `.agents/**` нельзя объявлять
подготовленной этапом, чей `allowed_paths` покрывает только `docs/**`.
