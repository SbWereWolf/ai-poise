# Перенос сохранённой работы между хранилищами

Обновлено: **2026-10-09**. Формат компактного пакета: `poise-recovery-1`.

## Назначение и граница

Перенос восстанавливает состояние выбранной работы и её текущую позицию в
подготовленной среде. Архив содержит состояние, необходимые материалы и диффы;
исходные версии кода должны быть доступны через явно настроенный репозиторий.
Развёртывание проверяет читаемость и валидность задачи, сохраняя исходную работу
и чужие материалы. Оно не запускает проверки этапов, переходы или перемотку.

Поддерживаются самостоятельные Task одним пакетом либо **целый опубликованный
Sprint** со всеми участниками. Частичная выборка участников Sprint запрещена.
Неначатые, завершённые, отменённые и сохранённые через handoff участники сохраняют
своё состояние. Чужой активный владелец не освобождается автоматически.
Незавершённое внешнее выполнение сначала разрешают через его владельца;
полностью завершённые `task_cleanup` и `result_integration` допускаются как
сохранённое состояние, а не разрешение повторить их эффекты.

Импорт создаёт отсутствующих владельцев. Совпадение ID Task/Sprint, занятого пути
или ветки означает конфликт, а не merge/замену. Возврат в исходное хранилище с уже
существующим ID также не поддерживается. Миграция схемы, частичная синхронизация и
внешняя доставка не выполняются. Создание новой Task вручную не подменяет импорт
истории и не создаёт квитанции прошлых этапов.

[Проверка назначения интеграции](batch-work.md#ранняя-проверка-назначения-интеграции)
не отменяет эти условия. Идентичность проекта и совместимость политики проверяются
отдельно от Git-привязки; manifest и БД пакета вручную не исправляют.

## Пакетный API

Выберите настроенный проект и передайте один пакет `poise work` через его launcher.
Нативная идентичность вызывающего агента сохраняется, `messages` остаётся пустым.

Экспорт освобождённых самостоятельных задач:

```json
{"operation":"transfer","input":{"action":"export","request_id":"export-01","task_ids":["T1","T2"],"sprint_id":null,"handoff":null},"messages":[]}
```

Экспорт текущей работы с её сохранением:

```json
{"operation":"transfer","input":{"action":"export","request_id":"export-02","task_ids":null,"sprint_id":null,"handoff":{"request_id":"checkpoint-02","reason":"Продолжить в другой среде","result":null,"commit_message":"Preserve work for another environment","artifact_paths":[]}},"messages":[]}
```

`handoff` использует существующего владельца локальной передачи. `result` содержит
разрешённый незавершённый результат либо `null`; verified-результат не заменяют.
Изменённый код сохраняют с допустимым содержательным сообщением коммита.

Для полного Sprint задают `sprint_id`, а `task_ids` — `null`. Если вместе с экспортом
сохраняется текущая Task, она должна принадлежать этому Sprint; остальных активных
участников освобождают заранее.

Успех экспорта: `status=exported`, `success=true`, `package_path`, `package_digest`,
`task_ids`, `sprint_ids`, `steps`, `replayed`. `delivery=local_package_only` означает
создание локального пакета, а не отправку в Gmail или другой сервис.

Импорт в заранее настроенную принимающую среду:

```json
{"operation":"transfer","input":{"action":"import","request_id":"import-01","package_path":"/absolute/input/work.tar.gz","package_digest":"<точный SHA-256 из результата экспорта>"},"messages":[]}
```

Успешный импорт возвращает `status=imported`, `success=true`, выбранные ID,
фактические `steps`, `reason`, `placement_decision` и сведения доставки. После этого
обычный `bootstrap` выбранного ID получает сохранённую позицию. Импорт не меняет
уже активную независимую Task принимающего агента. Точный повтор принятого пакета
возвращает receipt, сохраняя дальнейший прогресс, без повторного размещения.

## Конфигурация

Полный `runtime_services.transfer` обязателен. Начальный обезличенный образец —
[runtime.example.json](../../config/runtime.example.json). Оператор подставляет
реальные пути и полные конфигурационные наборы; `/example/...` не является рабочей
установкой. Настройка выполняется через [владельца проекта](../configuration/project-setup.md#назначение),
а не ручной записью управляемого manifest. Примеры не создают скрытых defaults.

| Поле transfer | Назначение |
|---|---|
| `directory` | Каталог операций относительно настроенного state root. |
| `archive`, `manifest`, `database` | Раздельные имена архива, manifest и scoped SQLite; пример архива — `work.tar.gz`. Поля `bundles_directory` в текущем формате нет. |
| `files_directory` | Обязательное безопасное имя в политике transfer; в текущем компактном формате оно не выбирает состав/размещение материалов: их определяют mapping и manifest, а transport-пути используют `materials/`. |
| `max_tasks`, `max_files`, `max_file_bytes`, `max_total_bytes` | Явные положительные пределы выбранной работы и файлов. |
| `chunk_bytes`, `file_mode` | Размер блока копирования и режим создаваемых файлов. |
| `recovery` | Полный контракт ниже, используемый при создании и развёртывании. |

| Поле recovery | Назначение |
|---|---|
| `format` | Поддерживаемый формат `poise-recovery-1`. |
| `tool_argv` | Непустой массив точных аргументов запуска установленного `workspace-recover`, включая выбранную среду исполнения. |
| `mapping` | Версия и явно классифицированные материалы; см. [размещение](#версия-и-размещение-материалов). |
| `systems.poise`, `systems.project` | Для каждой системы абсолютный `repository` и непустой упорядоченный массив абсолютных путей `configs`, реально используемых при проверках. |
| `repositories.task` | Явный доступный локальный Git-репозиторий с сохранёнными коммитами кода Task. Он требуется даже при наличии объекта в принимающем репозитории; источник не угадывается. |
| `paths.staging`, `paths.create_session`, `paths.restore_session` | Раздельные относительные пути подготовки и сессий инструмента внутри каталога операции. |
| `placement_decisions` | Явные решения совместимого размещения при несовпадении версий mapping. |
| `create_flow`, `restore_flow` | Непустые определения `workspace-recover/flow/v3`; см. [конвейер](#конвейер-доставки). |
| `component_steps` | Явный массив шагов подготовки компонентов задачи в том же формате flow. Пустой массив означает, что дополнительных шагов не задано. |

Принимающая среда использует свой конфиг и установленный инструмент. Исторические
наборы конфигов сохраняются как происхождение проверок, а не устанавливаются поверх
текущей системы. Process snapshot Task сохраняется без замены новым шаблоном.
Точные команды проверок и их параметры не переписываются под новую машину.
Нужные interpreter, внешние сервисы и источники оператор подготавливает явно.

### Версия и размещение материалов

Назначение материала задаётся явно в `mapping.materials`, размещение — относительно
корня Task. Имена файлов и каталогов не определяют роль. При несовпадении версий
агент выбирает совместимое размещение и сохраняет решение через конфигурацию;
инструмент применяет его, сохраняя логическую идентичность материала.

Каждая запись содержит `id`, непустую произвольную строку `role`, относительный
`source`, булев `include` и `destination`. При `include=true` destination — безопасный
относительный путь; при `include=false` — строго `null`. Роль `configuration` допустима
и для обычного материала: она не превращает его в служебный конфигурационный companion.

```json
{
  "version": "task-materials-1",
  "materials": [
    {"id":"notes","role":"task-material","source":"artifacts/notes","destination":"notes","include":true},
    {"id":"generated","role":"reproducible","source":"generated","destination":null,"include":false}
  ]
}
```

Включённые материалы перечисляются из Task roots; все файлы Sprint автоматически
не обходятся. Структурное состояние полного Sprint и разрешённые пропуски его
исторических артефактов сохраняются. Необъявленный обязательный зарегистрированный
материал не разрешается молча потерять: неполный пакет отвергается.

При одинаковой версии применяется размещение из сохранённой схемы. При разных
версиях без подходящего решения возвращается `placement_decision_required` с
`success=false`, без публикации Task. Решение покрывает все включённые ID:

```json
{
  "source_version": "task-materials-1",
  "target_version": "task-materials-2",
  "reason": "Материалы размещаются по действующей схеме проекта",
  "destinations": {"notes":"documents/notes"}
}
```

Пути проверяются на выход из корня и ссылки. Физическое переназначение не создаёт
новый artifact ID. Сохранённые привязки позволяют повторно экспортировать уже
развёрнутую Task с её фактического места без доступа к прежней папке задачи.

### Конвейер доставки

Создание и развёртывание выполняет один настроенный инструмент по явным flow.
Развёртывание включает распаковку, размещение, подготовку компонентов и проверку
читаемости/валидности доставленного состояния. Эти проверки готовности отделены
от проверок выполнения этапов Task.

Образец `create_flow` архивирует подготовленное содержимое. Образец `restore_flow`
выполняет `extract`, затем команды `place`, `components` и `validate`. Poise передаёт
`${variables.workspace}`, `${variables.staging}`, `${variables.package}` и массивы
`${variables.place_argv}`, `${variables.components_argv}`, `${variables.validate_argv}`.
`task_root` доступен как единственный корень, когда выбран ровно один owner root;
для нескольких корней значение `null` нельзя использовать как строковый путь.
Целая переменная сохраняет тип, поэтому `argv` принимает массив, а не shell-строку.
Неизвестная переменная — ошибка. Изменённый flow также не может обойти обязательную
финальную проверку файлов, SQLite и Git-состояния перед публикацией владельцев.

Установленные зависимости, воспроизводимые компоненты, прежние backup и временные
материалы исключаются явной классификацией. Нужные компоненты задачи готовятся
через `component_steps`: генерацией, копированием совместимого установленного
компонента или явной установкой. Восстановление одной задачи не требует
переустановки зависимостей всей системы. Шаги и проверки готовности определяются
при работе над задачей; инструмент не придумывает их по именам каталогов.

Архив, staging и сессии располагаются вне выбранных Task/Sprint roots, worktrees и
включённых источников, не пересекаются друг с другом. Выходы упаковки не входят
обратно в пакет. Архивирование/распаковка передаются инструменту, копирование файлов
в staging выполняется блоками `chunk_bytes`; Base64 всего пакета в памяти не строится.

## Содержимое пакета

- SQLite текущей схемы: только выбранные Task/Sprint, договор, позиция, история,
  методы, findings/resolutions, receipts, сообщения и структурные связи.
- Commit/base/branch/tree для начатого кода и binary-aware diff рабочего состояния.
  Полные исходники и история Git, включая локальный handoff `source.bundle`, в
  компактный пакет не входят. Сохранённые коммиты должны быть доступны в явном источнике.
- Явно включённые Task-материалы, полные сохранённые конфиги обеих систем для
  каждого proof и manifest состава/размещения/контрольных сумм.

Активные сессии, внешние runtime bindings/cursors и независимые владельцы не
переносятся. Исторические stdout/stderr, полные выводы и воспроизводимые файлы
проверок не упаковываются; нужные конфиги и происхождение остаются.

Каждый присутствующий зарегистрированный файл должен совпадать с исходным digest.
Отсутствие исторического артефакта разрешено только по проверенному импортному
контексту того же scope/owner с точным `id/scope/owner/path/digest` и сохранением
допустимости пропуска по текущей явной классификации. Это действует и для полного
Sprint. Новый отсутствующий файл, повреждённый присутствующий файл, обязательный
материал или несовпавший контекст вызывают отказ. Полные необходимые конфиги proof
всегда обязательны. Успешный первый импорт не создаёт общего разрешения на пропуски
при следующих экспорт/импорт.

Пакет не зашифрован; конфиги содержат выбранные оператором реальные значения.
Файловая целостность не удаляет секреты. Внешняя доставка отдельно разрешается и
выполняется выбранным транспортом; `transfer` сам её не отправляет.

## Возобновление и актуальность

После развёртывания сохраняется текущая позиция Task. Прошлые receipts остаются
историей исходной среды. Проверки выполняются при разрешённой работе над текущим
этапом; при разрешённой перемотке каждый достигнутый этап проверяется как текущий.
Развёртывание не запускает эту работу вместо агента.

### Конфиги и версии проверяемых систем

Каждый proof сохраняет полные конфигурационные наборы `poise` и `project` и коммиты
обеих систем. Повторная проверка использует текущие версии без отката к записанным
коммитам. Старые идентификаторы и конфиги позволяют объяснить различие результатов;
старый PASS не заменяет новое выполнение.

Проверка до запуска команды фиксирует реально объявленные config bytes, их digest
и `captured_path`, исходные `path` и коммиты. Списки `systems.*.configs` задаются явно
и сохраняют порядок. При переносе сохранённые config bytes остаются обязательными,
даже когда исторический вывод проверки исключён. Это не отменяет
[точную привязку repository evidence к коммиту](evidence.md#переиспользование-evidence-и-артефактов).

Сохраняются `restart_history`, native Task events, `action_runs`/`action_events`
и их происхождение. Текущую привязку действий определяет Task audit, а не последняя
строка с совпавшими stage/iteration. Точный повтор завершённого действия не
повторяет эффект: действует [контракт текущего цикла](actions.md#текущий-цикл-task-и-неизменность-плана).
Все сохранённые действия начатого рабочего дерева должны быть complete;
перезапуск не превращает прежний prepared/failed/blocked в завершённый исход.

Читающий адаптер разрешает подтверждённые физические привязки, сохраняя текст,
идентичность и происхождение. Импорт не переносит активный source claim и не
обнуляет счётчики итераций/лимиты. Submission IDs могут локально переназначаться
с FK; стабильные task/finding/argument/receipt IDs и message identities сохраняются.
Новые квитанции текущего этапа и [перемотки](batch-work.md#автоматическая-промотка-после-перезапуска)
создаются существующими владельцами, без выдачи прежних результатов за свежие.

## Согласованность и ошибки

Успех сообщается только после подтверждённого завершения обязательных фаз и
финальной проверки доставленной Task. При failed/unknown сообщаются фактические
шаги и причина; решение о дальнейших действиях принимает конечный пользователь.
Ошибка не выдаётся за успешно развёрнутую работу.

| Ситуация | Результат и граница |
|---|---|
| Недоступен `repositories.task` или сохранённый commit | Неуспех `source_unavailable`; код из другого неявного источника не подставляется. |
| Дифф неприменим | Неуспех `diff_inapplicable`; существующее дерево не сбрасывается. |
| Нет решения версии mapping | `placement_decision_required`, `success=false`; публикации нет. |
| Занятый owner ID, корень, ветка или чужое содержимое | Отказ/`destination_occupied`; merge и перезапись не выполняются. |
| Изменённый архив/digest, опасный путь/ссылка, неполный snapshot или обязательный файл | Отказ до принятия неполного состояния. |
| Ошибка компонентов либо финальной проверки | Неуспех с фактическими фазами; успешный шаг не равен завершённому импорту. |
| Неизвестен исход внешней операции | `unknown`; тот же запрос не запускает эффект заново. |

Перед внешним запуском записывается намерение; после ожидания процесса — его
terminal-результат и проверяемые факты stdout/stderr/tool state. Незавершённый запуск,
пропавший или повреждённый журнал, отсутствие достоверного terminal proof не дают
права повторить команду. Завершённый повтор использует сохранённый исход. Не удаляйте
сессии/журналы и не меняйте request ID ради обхода неизвестного эффекта.

Перед упаковкой повторно проверяются выбранное состояние и файлы. Импорт проверяет
архив и scoped SQLite текущей схемы/FK, сохраняет намерение, подготавливает пути
без перезаписи и публикует владельцев одной транзакцией. Ошибка SQL не оставляет
частично видимую Task/граф; подготовленные файлы могут остаться. Общей атомарности
Git, filesystem, внешнего инструмента и SQLite не заявляется.

Сбой упаковки после handoff может оставить уже сохранённую освобождённую работу
без готового архива. Это не потеря работы: исходное состояние сохраняется.
Независимые копии БД не образуют распределённую блокировку; одновременную запись
одной задачи в две копии пользователь не разрешает автоматически.

## Основания реализации

Scoped SQLite формируется существующими Task/Sprint repositories. Старые схемы
не преобразуются. Код Task разворачивается из сохранённого коммита через явный
источник и дифф; исторические коммиты систем проверки служат происхождением.
Состав владельцев и границы адаптеров: [библиотечный API](../architecture/library-api.md#ddd-07b-перенос-сохранённой-работы).

Пример и проверки локальны. Их успех не объявляет живые ChatGPT hooks, JetBrains
или Gmail подключёнными.
