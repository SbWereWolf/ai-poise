# Наблюдаемая работа hooks и runtime

Обновлено: **2026-09-16**. Владелец явной операции — `HookDiagnostics`; данные остаются у
`HookRegistry`, `SourceReader`, `InteractionStore`, `SqliteEvidenceRepository` и
`TelemetrySpool`. Операция не запускается автоматически перед работой и не является
общим наблюдателем соблюдения правил.

## Диагностика фактических эффектов hooks

`poise runtime-config --settings /absolute/path/to/existing-settings.json` принимает
операцию `diagnose` через stdin. Она различает **установленную регистрацию**, **записанное
нативное событие** и **сопоставленный результат конкретного владельца**. Наличие JSON
конфигурации не доказывает доверие хоста, доставку события или действие обработчика.

Пример запроса одной проверки:

```json
{
  "operation": "diagnose",
  "input": {
    "definition_path": "/absolute/path/to/installed-definition.json",
    "session_id": "existing-bound-session-id",
    "event": "SessionStart",
    "event_id": null,
    "run_ids": [],
    "probe_cwd": null
  }
}
```

`session_id` — точный внутренний ID существующей привязки сессии, не произвольный путь
и не внешний conversation ID. `definition_path` указывает существующее определение.
`event_id` выбирает положительный ID записи именно этой сессии и типа события;
`null` выбирает последнюю запись этого типа. Все поля задаются явно.

Пакет проверок использует тот же `input` в форме
`{"queries":[{"id":"start","request":{...}},{"id":"end","request":{...}}]}`.
В `request` находится полный одиночный запрос, показанный выше. Допускаются 1–32 запроса
с уникальными ID; вся структура проверяется **до любого явно заказанного probe**.
Операционная ошибка одного запроса не скрывает результаты остальных.

### Какие свидетельства сопоставляются

| Событие | Что операция действительно может подтвердить |
|---|---|
| `SessionStart` | Сохранённое поколение SourceReader: `event_id=hook-event:<ID>` и `reason`, совпадающий с native `source`. Это не доказывает, что агент помнит текст, прочитал все инструкции или что router завершился. |
| `UserPromptSubmit` | Наличие исходного receipt сообщения в прежнем `InteractionStore` для точных project/source/conversation/turn. Текст сообщения не возвращается и повторно не регистрируется. |
| `SessionEnd` | Отмену конкретных запусков из `run_ids`, если их прежний immutable evidence receipt содержит native cancellation и корреляцию с выбранными сессией и событием. Без `run_ids` эффект не считается подтверждённым. |
| `Stop` | Запись native события. Доставка возвращённого hook-ответа не имеет отдельного устойчивого receipt, поэтому эффект остаётся `not_recorded`. Это не отмена проверок и не приёмка Task. |

C031 дополняет результат **существующего** RegisteredCheckRunner полем
`cancellation_observation`, когда нативная отмена реально замечена его прежним callback.
Там находятся `session_id`, `start_event_id`, `end_event_id`. Поле сохраняется тем же
владельцем evidence; второго runner, реестра PID или журнала сообщений нет. Старые
receipts не мигрируются: отсутствие корреляции возвращает `not_correlated`, даже если
в старом receipt написано `cancelled=true`. Дополнительно проверяются завершение процесса сигналом и отсутствие timeout. Receipt — локальное свидетельство владельца,
а не криптографическое доказательство подлинности внешнего события.

Проверяется соответствие установленной собственной группы hooks, binding и launcher
текущим settings и definition. Изменённая группа или launcher дают `changed`; чужие
неизменяющие её группы не являются дефектом. Диагностика ничего не переустанавливает.

### Статусы и ограничения наблюдения

`diagnosed` означает, что запрошенная локальная корреляция установлена, либо конкретный
необязательный эффект явно `not_configured`. Это **не общий PASS системы**, не факт
пользовательского trust и не завершение Task. `host_trust` всегда `not_observed`:
эта операция его не измеряет. `recorded_at` — время записи HookRegistry, не выдуманное
время возникновения события на стороне источника.

Недоступное событие — `unsupported`; отсутствующая запись — `not_observed`; другой
эпизод или старый receipt — `not_correlated`; повреждённое/недоступное хранилище —
`unavailable`. Неизвестная версия registry не мигрируется. Итог таких неполных запросов —
`inconclusive`. Ошибочный запрос отклоняется. Exit codes берутся из существующих
settings: `success` для `diagnosed`, `incomplete` для `inconclusive`, `rejected` для
ошибки запроса. В пакетном ответе сохраняется результат каждого запроса.

Чтения разных владельцев — независимые снимки, не единая транзакция. Результат может
устареть при последующих событиях. При расхождении следует выбрать точный event ID и
повторить явную диагностику, а не запускать постоянный polling.

### Чтение без изменения работы и явно активные probes

Без `probe_cwd` операция читает только существующие данные. Она не создаёт Task или
reader state, не захватывает claim, не вызывает restore_context, не повторяет сообщения,
не выполняет telemetry replay и не устанавливает hooks. SQLite открывается read-only с чтением последнего committed WAL-снимка;
служебные файлы читаются с ограничением размера, FIFO и неподдержанные типы отвергаются.
CLI может записать **сам отчёт** в прежний каталог observations, если он превышает
настроенный output budget; вместо обрезки выдаётся `response_path`.

Ненулевой `probe_cwd` — **явный заказ активных capability probes**, объявленных в выбранном
определении. Значение — конкретный абсолютный либо относительный к текущему cwd путь
существующей директории. Отсутствующий аргумент не выводится из native cwd или Task.
Применяется прежний bounded executor; он сохраняет обычные probe receipts. Это не
разрешение исполнять произвольный код из диагностики и не смена инструментов на код
проверяемой копии. Политика разрешения путей работающего Poise не меняется.

Блок `runtime` описывает текущий процесс: executable интерпретатора, Python version и
местоположение импортированного пакета. Эти сведения — provenance, не входы выбора
другого экземпляра Poise и не доказательство того, какой процесс исторически выполнил
hook. Живая IDE или хост пользователя не считаются проверенными по локальному fixture.

Блок `telemetry_delivery` читает ограниченную сводку прежнего spool, без payload и replay.
Он относится к **настроенной очереди целиком**, не к выбранному событию hook. Ошибка
необязательной телеметрии не заменяет результат подтверждённого эффекта. Пустая очередь
не доказывает полную доставку: сохраняется
[окно потери до асинхронного сохранения](telemetry-delivery.md#асинхронная-доставка-без-блокирования-работы).
