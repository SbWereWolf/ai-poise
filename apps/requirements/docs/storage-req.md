# Самостоятельное хранилище Requirements

Обновлено: **2026-10-17**.

## Реализованный формат

Приложение создаёт собственную SQLite-базу формата 1: `PRAGMA user_version=1`,
единственная строка `requirements_meta(revision=0,schema_version=1)` и 20 таблиц.
Исполнимая схема находится в [schema.sql](../schema.sql).

| Таблицы модели | Назначение |
| --- | --- |
| `requirements_meta` | Общая ревизия хранилища и номер его схемы. |
| `requirements`, `requirement_revisions` | Идентичность System/Application и указатель на текущую версию; сохранённые тексты, статусы, происхождение и ревизии. |
| `application_purposes`, `application_purpose_revisions` | Назначение Application и его сохранённые редакции. |
| `system_application_versions` | Периоды связей System/Application; текущая связь имеет `valid_to IS NULL`. |
| `task_identities`, `task_creation_requests` | Идентичность Task и сохранённое намерение её создания. |
| `task_statements`, `task_requirement_keys`, `task_requirement_versions` | Редакции постановок, устойчивые ключи и версии требований Task. |
| `application_task_links` | Основания требований конкретной редакции Task в Application. |
| `task_snapshots`, `requirement_outcomes` | Снимки постановок и связанные результаты. |
| `requirement_requests` | Намерение и ответ запроса в пространстве протокола. |

Это 15 таблиц основной модели. Ещё пять таблиц содержат предметный каталог:
`domain_areas`, `domain_entities`, `domain_actions`, `requirement_entities`,
`requirement_actions`.

При повторном открытии выбранного самостоятельного формата проверяются его
номер и обязательная общая ревизия. Существующая модель из 15 таблиц поддерживает
свои запросы без добавления пяти таблиц каталога. Необходимые данные используются
владельцем конкретной операции; общей проверки всех таблиц при запуске нет.

## Текущие значения и ревизии

Чтение System/Application соединяет `requirements.current_revision` с соответствующей
строкой `requirement_revisions`. Запросы связей читают открытые периоды
`system_application_versions`. Типизированные страницы используют временные
представления текущих значений в одном соединении; файл схемы при чтении сохраняется.
Запросы реестра, сущностей и связей можно сочетать в одном пакете.

`apply` последовательно применяет операции к реестру и сохраняет итоговое состояние.
Каждое изменённое требование получает следующую локальную ревизию; прежние строки
сохраняются. Новые связи получают `valid_from` общей ревизии этого изменения.
Удаление верхней связи через `unlink` закрывает её период общей ревизией;
повторное добавление создаёт новый период. Общая ревизия, данные и сохранённый ответ
фиксируются одной транзакцией.

`revise_task` сохраняет полную следующую постановку известной Task, её упорядоченные
требования и связи с Application, затем обновляет текущий указатель. Снятые из новой
постановки keys сохраняются в постоянном наборе и прежних версиях. Публичные
`task_history` и `history_requirement` читают сохранённые редакции; `snapshot`
возвращает выбранный полный payload. Позднее изменение графа сохраняет старые
постановки, origins и снимки. Эти значения доступны после повторного открытия.

Отдельные `put_requirement` и `link` изменяют реестр и верхние связи. Текущий состав
Task меняет явный `revise_task`, добавляющий новую редакцию и её нижние связи.
Исторический `task_chain` читает выбранные Task-текст и нижние связи, а значения
Application берёт из актуального реестра. Сохранённый `snapshot` имеет собственную
`statement_revision`; указатель последнего снимка и структурный `basis_ready`
описывают свои данные отдельно от факта выполнения изменённого требования.
Правильная последовательность приведена в
[руководстве текущих и будущих обязательств](graph-req.md#текущее-обязательство-и-будущая-потребность).

Текущий CLI предоставляет `create_task`, `apply`, `query`, `import_bootstrap`.
Создание Task, graph-операции и правильные пакеты описаны в
[руководстве графа](graph-req.md#создание-task-и-канонический-id). Выдача ID и запись
первой постановки используют существующую схему. Purpose-aware публикация и outcomes
остаются будущими возможностями; их подготовленные таблицы сохраняют имеющиеся значения.

`create_task` одной короткой транзакцией сохраняет identity, постановку 1,
её ключи/требования/связи, следующую общую ревизию и первоначальный результат.
`task_creation_requests` содержит `creation_request_id`, полный JSON `intent`,
`task_id` и полный JSON `response`. Этот журнал независим от `requirement_requests`;
одинаковая строка request ID может обозначать отдельные запросы двух операций.
При точном повторе возвращается первоначальный результат с `replayed:true`;
сохранённый ответ сохраняет `replayed:false`. Существующая текущая постановка
может иметь более позднюю ревизию. Поле `work_choice` хранится как часть исходного
намерения. Запись ограничена собственным хранилищем Requirements.

`task_creation` читает исходное создание, `get_task` — текущую постановку,
`task_basis` — полноту оснований её применимых требований. Выбранный JSON
декодируется для соответствующего чтения. Отказ создания откатывает identity,
постановку, ревизию и receipt вместе; следующий правильный запрос использует
свободное пространство IDs. Публикация и исполнение принадлежат своим операциям.

## Повтор запроса

`requirement_requests` хранит `protocol_namespace`, `request_id`, JSON object
`intent` и JSON object `response`. Для `apply` пространство — `registry.apply`.

Равенство намерения определяется по каноническому JSON сохранённого пакета с
сохранением типов значений. Порядок
операций сохраняется; порядок ключей объектов не меняет намерение. Для нового
изменения используйте новый `request_id` и актуальный `expected_revision`.
Повтор исходного пакета возвращает его сохранённую ревизию и `replayed:true`,
включая повтор после последующих изменений реестра. Новая композиция хранит
полное намерение вместо хэша.

Читаемые сохранённые объекты необходимы конкретному повтору. Неуспешное чтение
такого объекта возвращает описанный отказ и сохраняет исходные записи.
Восстановление данных принадлежит отдельному инструменту оператора.

## Публичная композиция и транзакции

[Приложение storage.py](../storage.py) предоставляет фабрику
`RequirementsStore(database,lock,lock_seconds,poll_seconds)`. Она создаёт backend
собственного формата и вызывает публичный
`poise.infrastructure.requirements_registry.RequirementsStore.standalone(...)`
с явным `registry_type=RequirementsGraph`. Shell передаёт полученный store общему
`RequirementsCommands`.

Общий владелец выполняет проверку внешнего запроса, сравнение повторов, выбор
заявленной модели и границу транзакции. `RequirementsGraph` владеет трёхуровневым
графом и применимостью, используя публичную двухуровневую модель для прежних правил.
Backend приложения получает соединение и обычные структуры данных, владеет SQL
собственной схемы и её сохранением. `SavedRevisions` передаёт отсоединённые значения
истории: JSON декодируется при запросе выбранного record, без живого соединения
в домене. Ошибка выбранного JSON описывается как `PoiseError`; остальные читаемые
записи продолжают использоваться. Проверки контрольных сумм при запуске и чтении
этой композиции не выполняются.
Подробные сигнатуры определены в
[библиотечном API](../../../docs/architecture/library-api.md#самостоятельное-хранилище-requirements).

Подготовка и запись используют локальную границу хранилища и
`BEGIN IMMEDIATE`/`COMMIT`. Ошибка до фиксации откатывает изменения этой
транзакции. SQLite/filesystem ошибки новой композиции переводятся в `PoiseError`
после выхода из транзакции и становятся описанным JSON-отказом CLI.
Backend использует только переданное соединение; транзакцией управляет общий
владелец.

## Практическое использование

Для новой установки и повторного открытия выполняйте
[инструкцию запуска](shell-req.md#создание-и-повторное-открытие) с одной выбранной
конфигурацией. Поддерживаемое окружение, заполнение параметров и команды проверок
описаны там же. Публикация пакета и специализированные Task-операции — отдельные
результаты; этот документ описывает фактически реализованный срез исходников.
