# Поставка результата и удаление материалов Task

## Договор и граница хранения

Папка Task — удаляемая рабочая область, а не постоянное место результата.
До завершения или отмены явно согласуйте весь сохраняемый результат через
`delivery/agree`: точный Git-коммит и ref в настроенном репозитории, отдельный
файл, игнорируемую рабочую конфигурацию либо передачу заказчику. Если результата
нет, явно укажите `no_result` с пустым `outputs`; это не способ скрыть обязательную
поставку. Правило действует для standalone Task и участников Sprint.

Удаление материалов не удаляет Task из реестра или её DB-историю. Договор,
минимальные подтверждения, идентичность, прежние результаты и история остаются
у существующих владельцев. Полные потоки проверок, доказательства-файлы,
временные артефакты, handoff-файлы, локальные checkpoint и остальные файлы
внутри Task-root удаляются вместе с ним, без скрытого архива. Нужный заказчику
файл сначала объявляется самостоятельным результатом и поставляется наружу.
Общие материалы Sprint, файлы других Task, основные checkout, операторские
резервы и данные незавершённых операций не становятся материалами этой Task.

## Публичный договор поставки

Пакет передаётся выбранному проекту существующим `poise work`, с нативной
идентичностью caller и `messages=[]`. Пример формы для файлового результата:

```json
{
  "operation": "delivery",
  "input": {
    "action": "agree",
    "request_id": "result-delivery-1",
    "task_id": "EXPLICIT-TASK-ID",
    "expected_version": 42,
    "authorization": "Согласованная поставка результата",
    "declaration": {
      "disposition": "deliver",
      "outputs": [
        {
          "id": "result-file",
          "kind": "file",
          "source": "/absolute/task-root/artifacts/result.bin",
          "destination": "/absolute/agreed-location/result.bin",
          "digest": "<точный SHA-256 содержимого>"
        }
      ]
    }
  },
  "messages": []
}
```

Пути, digest и `42` в примере заменяются фактическими значениями. Для newborn
`expected_version` берётся из публичного `revision`, для остальных состояний —
из `version`. `request_id` стабилен для точного повторения того же пакета.
Смена намерения требует разрешённого restart до терминального исхода и начала
удаления; terminal/начатое удаление не допускают изменения договора.

| kind | Поля одного output помимо уникального `id` и `kind` | Подтверждение |
|---|---|---|
| `git` | `repository`, `target_ref`, `commit` | Точный commit существует и является предком согласованного ref в настроенном репозитории |
| `file` | `source`, `destination`, `digest` | Отдельный постоянный файл имеет согласованный SHA-256 |
| `ignored_configuration` | `source`, `destination`, `digest` | Файл имеет согласованные байты, находится в настроенном репозитории, ignored и не tracked |
| `customer` | `source`, `destination`, `digest`, `acknowledgement` | Полученный файл и отдельное подтверждение заказчика совпадают с договором |

`acknowledgement` содержит ровно `path` и `receiver`; файл подтверждения вне
Task state содержит JSON с точными `receiver`, `digest`, `received_path`.
`received_path` равен `destination`. Сам инструмент не отправляет письмо и не
создаёт подтверждение заказчика. Для `file` и `ignored_configuration` отсутствующий
файл публикуется общим файловым владельцем; совпавшие байты принимаются,
конфликтующие не перезаписываются. Пути абсолютные, без `.`/`..` и symlink.
Файловые источники принадлежат Task-root; постоянное назначение находится вне защищённых
state/runtime/config-путей. Рабочие конфиги не помещаются в Git.

## Завершение и продолжение

`accept`, `cancel`, `cleanup` и `integrate` вызывают settlement согласованной
поставки для возвращённой Task. При отмене Sprint либо после снятия блокировки
используйте явный `settle` для каждой Task. Уже существующим Task договор
автоматически не придумывается: отсутствие договора не удаляет материалы.
Согласование не даёт полномочий на приёмку, интеграцию или судьбу уникальных
коммитов. Эти решения сохраняют собственные gates.

```json
{"operation":"delivery","input":{"action":"settle","request_id":"result-settlement-1","task_id":"EXPLICIT-TASK-ID"},"messages":[]}
```

Чтение состояния не требует захвата Task:

```json
{"operation":"show","input":{"queries":[{"id":"delivery","kind":"task_delivery","task_id":"EXPLICIT-TASK-ID"}]},"messages":[]}
```

`delivery_agreed` означает сохранённое намерение; `delivery_pending` — выполняемую
поставку; `delivery_partial` — зафиксированное разрешение удаления после всех
подтверждений. При существующем договоре `delivery_blocked` содержит `reason`
и описание `recovery`. Без договора отдельный ответ `delivery_blocked` содержит
`reason: agreement_required`, но не содержит `recovery`: недостающий договор
задаётся через `delivery/agree`, после чего продолжают `delivery/settle`.
`delivery_complete` означает проверенное фактическое отсутствие Task-root.
Исключение удаления не объявляет успех: durable-состояние сохраняет возможность
продолжить частичную уборку. Системный сбой не превращается в фиктивный PASS.

| Причина | Продолжение через владельца |
|---|---|
| `agreement_required` | `recovery` отсутствует; задать действительный договор через `delivery/agree` до завершения |
| `task_not_terminal` | Завершить либо санкционированно отменить Task |
| `integration_required`, `resource_cleanup_pending` | Завершить разрешённую интеграцию либо cleanup с явной судьбой коммитов |
| `checks_pending`, `external_operation_pending` | Разрешить исходную незавершённую внешнюю операцию |
| `artifact_draft_open`, `handoff_pending`, `artifact_consumer_pending` | Закрыть исходный draft/передачу/потребителя через его API |
| `transfer_pending` | Продолжить исходный export с теми же actor/request до независимого пакета |
| `source_integrity_failed` | Восстановить согласованный исходник до начала удаления |
| `destination_unavailable`, `destination_conflict` | Восстановить согласованное назначение/доступ/ignore-контракт, не перезаписывая чужие байты |
| `customer_acknowledgement_required`, `customer_acknowledgement_invalid` | Получить действительное подтверждение и согласованные полученные байты |

После устранения причины повторяется исходный settlement; `recovery` не является
готовым work-пакетом без `input`, `messages` и `request_id`. Перед продолжением
незавершённого удаления заново наблюдаются все постоянные подтверждения и
обязательные потребители. Удалённые источники не перечитываются, поставка не
повторяется, внешние данные автоматически не ремонтируются. Это действует и
при уже отсутствующем каталоге до сохранения окончательного complete.
Завершённый исторический replay возвращает прежний результат без нового аудита.

## Владение каталогом и намеренная замена

Каталог по настроенному Task-пути может быть намеренно заменён оператором обычным
каталогом. Сохранённые device/inode — начальное наблюдение для аудита, а не запрет
продолжения. Отдельная защита от намеренной подмены корня, quarantine и закрепление
inode не входят в договор. При замене оператор сохраняет правильную принадлежность
содержимого. Остаются проверки владельца, настроенного пути, обычного типа каталога,
символических ссылок и чужих/общих материалов; разрешение замены не разрешает
удалять произвольный путь.

## Чтение и повторное использование после удаления

Terminal inspection и точные завершённые публичные повторы возвращают сохранённую
историю без захвата Task, восстановления Task-root и raw proof. Недоступные файлы
доказательств отмечаются как удалённые, а не как новые проверки или повреждение
ещё живого материала. Исторический PASS не сертифицирует другой commit.

Зарегистрированный файл после удаления доступен потребителю только через
единственное согласованное постоянное назначение с тем же исходным путём и digest.
Логическая identity регистрации сохраняется; общий material resolver выбирает
физические байты. Отсутствие такого назначения либо конфликт не исправляются
копированием receipt. Accepted duplicate reuse сохраняет проверки семейства,
локальной доступности и самостоятельной приёмки; удалённые raw outputs не
становятся свежими evidence. Новый export удалённых рабочих материалов не
поддерживается; заранее подготовленный пакет и его точный replay самостоятельны.

## Владельцы механики

`TaskDeliveryCommands` владеет договором и журналом подтверждений/удаления;
`RuntimeTaskDelivery` наблюдает Git/filesystem, потребителей и удаляет Task-root.
Lifecycle Task, ресурсный cleanup, интеграция, export и публикация файлов остаются
у своих владельцев. `ArtifactMaterialResolver` выбирает постоянные байты без
перезаписи регистрации. Общий material lock сериализует зависимые операции,
но не превращает filesystem и DB в одну атомарную транзакцию.

Checkpoint, экспорт или handoff не являются неявным бессрочным резервом папки
Task. Если архив нужен как самостоятельный результат, его назначение согласуется
и подтверждается до удаления; локально архив без отдельного поручения не создаётся.
