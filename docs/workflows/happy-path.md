# Happy path и внутреннее устройство

Обновлено: 2026-09-06T14:30:44+05:00.

## Пользовательский цикл

`bootstrap` выбирает/возобновляет задачу, при необходимости по process snapshot создаёт изолированный worktree, возвращает цель, требования, DoD, root AGENTS целевой codebase, разрешённый следующий этап, roots артефактов и один result file. Агент читает AGENTS приложения и работает его нативными инструментами.

Агент заполняет только содержательный результат, сообщение коммита и пути своих артефактов. Он не записывает Git status, timestamps, hashes или test exit codes. `verify` использует кандидатный результат, механически проверяет его, сам запускает точные tests, сохраняет evidence, создаёт commit при Git-изменениях и выполняет только явно настроенную и разрешённую публикацию, очищает runtime и возвращает доклад. Статус verified сам по себе не начинает следующий этап.

`accept` соответствует «принял, остановись». `bootstrap --decision continue` объединяет принятие с подготовкой ровно одного следующего этапа. Для последовательных этапов роли `executor` основанием каждого такого вызова служит действующее поручение исполнителю; отдельное новое сообщение «дальше» не требуется. Граница `reviewer` требует публичной передачи отдельному проверяющему в рамках начала Task; отдельно регулируемые решения требуют соответствующего разрешения по [канонической политике ролей](../governance/development-rules.md#роли-этапов-и-непрерывность-поручения). `bootstrap --decision rework --feedback ...` открывает новую iteration того же этапа. `cancel` требует содержательной инструкции пользователя и не запускает acceptance checks.

## Владение рабочим набором

Обновлено: 2026-09-13. По [правилу владения](../governance/development-rules.md#владение-task-и-worktree)
сессия независимо владеет не более чем одной Task и одним worktree. `bootstrap` создаёт
или возобновляет зависимый worktree только если process snapshot требует
`worktree_required=true`; Task с `false` работает без ветки и Git delta. Это не разрешает
менять код в main.

Захват всего набора автоматически заменяет прежнее владение того же вида, проверяет
чужих владельцев и публикует новый набор атомарно. При отказе сохраняется прежний набор.
Освобождение Task снимает зависимый claim worktree, но не независимый; файлы, WIP,
cwd и launch roots остаются прежними. Проверки и сохранение результата — отдельные
операции жизненного цикла, а не побочный эффект владения.

Начало Task разрешает обычные этапы обеих ролей согласно принятой политике 0072/0073:
на границе ролей отправитель сохраняет результат, публично освобождает Task и напрямую
уведомляет известного коллегу. Получатель захватывает её через bootstrap до изменений.
Это заменяет прежнее требование новой команды на каждое ревью;
приёмка и интеграция сохраняют отдельное разрешение. См. [прямую передачу](local-handoff.md#прямая-передача-между-исполнителем-и-проверяющим).

## Данные

SQLite: task contract, process snapshot, session binding, stage/iteration, submissions с текстовыми sections, execution evidence, id/path артефактов и внутренние digests, append-only operational journal. Долгие команды запускаются вне внешнего DB-lock.

Filesystem под state root: runtime/session; tasks/task-id; sprints/sprint-id; worktrees/task-id. Только первые три являются допустимыми roots для agent artifacts. Code/test deliverables внутри worktree учитываются через Git, а не artifact_paths.

## Модули

`common.py` — явная конфигурация и проверка точных методов. `storage.py` — SQLite и внешний flock. `artifacts.py` — только пути, ID, confinement и количества. `execution.py` — конечный запуск процесса и file-backed output. `runtime.py` — простой последовательный happy path. `__main__.py` — тонкий CLI и краткий вывод с адресом полного ответа.

## Пример требования к файлам

```json
{"scope":"task","pattern":"*.json","minimum":2,"maximum":2}
```

Это требование двух уникальных зарегистрированных JSON-файлов в текущей task, а не двух JSON-объектов или двух тест-кейсов. Проверка содержания должна быть отдельной точной командой проекта. Значения — пример конфигурации, не значения по умолчанию в коде.

## Правило повторов

FAILED tests → исправление → verify: новая execution attempt, даже при прежнем semantic payload. Успешный verify без изменений → сохранённый report. Commit уже существует → повторно не создавать; Git push запрещён. Изменения после предъявленного verified требуют явного rework. Неизвестный исход прерванной внешней операции не запускается второй раз автоматически.
