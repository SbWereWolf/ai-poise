# Локальные профили Bootstrap

Эта страница описывает реализованный срез T026: выбор локальных целей и
проверку файлов профиля без изменения среды. Полный целевой интерфейс описан
в [контракте Bootstrap](contract-bst.md); [страница оболочки T022](shell-bst.md)
сохранена как описание её исходной основы.

**Корректный непустой профиль пока даёт `action_required`, код 3 и
`maintenance_unavailable`. Это не `ready` и не результат ремонта.**
Выполнение `environment-maintenance`, разрешение параметров и действия
относятся к T027; публичные адаптеры ремонта владельцев — к T028.

## Запуск и выбор цели

Вызов не требует Task, Session или конфигурации соседних приложений. Оболочка
использует стандартную библиотеку Python и POSIX-дескрипторы каталогов с
`O_NOFOLLOW`; проверенный контур — Linux и Python 3.13.5. Работа на Windows
этим срезом не подтверждается. `PYTHON` в примере — интерпретатор выбранной
установки; `CHECKOUT` и `BOOTSTRAP_CONFIG` задаёт оператор, это не встроенные пути.

```bash
PYTHON=/absolute/path/to/installed/python
CHECKOUT=/absolute/path/to/checkout
BOOTSTRAP_CONFIG=/absolute/path/to/bootstrap.json

"$PYTHON" -B "$CHECKOUT/apps/bootstrap/bin/bootstrap" --config "$BOOTSTRAP_CONFIG" check --target alpha
"$PYTHON" -B "$CHECKOUT/apps/bootstrap/bin/bootstrap" --config "$BOOTSTRAP_CONFIG" infra --target all --dry-run
"$PYTHON" -B "$CHECKOUT/apps/bootstrap/bin/bootstrap" --config "$BOOTSTRAP_CONFIG" deps
```

`--config PATH` обязателен и расположен перед командой. Поддерживаются только
`infra`, `deps`, `check`; у всех один механизм выбора. Явный `--target TARGET`
имеет приоритет над переменной, названной в `target_env`; при отсутствии такой
переменной используется `default_target`. При `target_env: null` окружение
не участвует в выборе. Явный аргумент перекрывает даже пустую или некорректную
переменную окружения. Присутствующая пустая переменная без аргумента — ошибка
`invalid_selector`, а не повод перейти к настройке по умолчанию.

`all` выбирает все обнаруженные профили; другой ID выбирает только свой файл.
Добавление корректного профиля не требует изменения кода или списка приложений.
Повторный `--target`, неизвестный флаг, лишний позиционный аргумент, отсутствие
значения и повторный `--dry-run` отклоняются. `--set NAME=VALUE` допускается
синтаксически и сохраняет порядок аргументов, но в T026 значения не разрешаются,
не подставляются и не передаются движку. `--dry-run` отражается в результате;
и с ним, и без него T026 не выполняет действий.

ID не может быть пустым, равняться `.` или `..`, содержать `/`, `\`, NUL,
символы U+0000–U+001F и U+007F или символы, не кодируемые в UTF-8. `all` зарезервирован
как селектор и не допускается в качестве ID файла профиля.

## Конфигурация и операционный каталог

[Поставляемый конфиг](../config/bootstrap.json) содержит ровно пять полей:
`schema`, `projects_root`, `default_target`, `target_env`, `limits`. Его схема —
`stride-bootstrap-config/v1`. В примере поставки `projects_root` равен `projects`,
`default_target` равен `all`, а `target_env` равен `null`. Это значения файла,
не неявные значения реализации: пропуск обязательного поля — ошибка.

Относительный `projects_root` разрешается от каталога конфигурационного файла,
а не от текущего рабочего каталога вызова. Корень должен уже существовать и быть
доступным каталогом без символических ссылок в его компонентах. Bootstrap
не создаёт его, не сканирует чужие хранилища и не восстанавливает конфиги из
шаблонов автоматически. Отсутствующий или недоступный корень —
`projects_unavailable`, а не успешный пустой набор.

При `all` рассматриваются непосредственные имена `<id>.json`, отсортированные
по кодовым точкам Unicode. Обычные подкаталоги и другие расширения игнорируются.
Выбранная символическая ссылка или специальный файл с расширением `.json`
отклоняются, а не открываются и не исчезают из отчёта незаметно. Список целей
фиксируется для одного вызова. Явная цель не заставляет читать остальные
профили: повреждённый соседний профиль не мешает работе с выбранным корректным.
Неизвестный ID не заменяется на `all`.

Локальное правило [`.gitignore`](../.gitignore) исключает
`apps/bootstrap/config/projects/` из Git. Оно не распространяется на любой
произвольный путь из внешнего конфига: такой операционный каталог также должен
находиться вне версионируемых данных. [Шаблоны `examples/projects/`](../examples/projects/alpha.json)
поставляются отдельно. Они инертны; размещение их копий в операционном каталоге
требует явного решения оператора и не должно перезаписывать его существующие
файлы. Обновление приложения не означает обновление рабочих профилей.

## Формат профиля и файлов

Файл `alpha.json` содержит ровно шесть обязательных полей:

```json
{
  "schema": "stride-bootstrap-project/v1",
  "id": "alpha",
  "catalog": "alpha-assets/requirements.json",
  "repairs": null,
  "values": {},
  "parameter_values_files": []
}
```

`schema` должен точно совпадать, `id` — совпадать с именем файла без `.json`.
`catalog` — непустой относительный путь; `repairs` — такой путь или явно `null`.
`values` — JSON-объект. `parameter_values_files` — упорядоченный список непустых
относительных путей; пустой список разрешён. Неизвестные поля, пропуски и
неправильные типы дают ошибку профиля до каких-либо действий.

Все ссылки на файлы разрешаются относительно `projects_root`. Абсолютные пути,
пустые компоненты, `.`, `..`, NUL, обратная косая черта и символические ссылки
в любом компоненте отвергаются. Финальный вход должен быть обычным файлом:
каталог, FIFO, устройство и символическая ссылка не читаются. Дескриптор
проверяется до и после чтения; обнаруженная смена имени, типа, размера или
метаданных не признаётся успешным чтением.

Каталог требований — JSON-объект со `schema` равным
`environment-maintenance/requirements/v1`, объектом `parameters` и массивом
`requirements`. Пример находится в [файле требований шаблона](../examples/projects/alpha-assets/requirements.json).
При наличии `repairs` его объект должен иметь схему
`environment-maintenance/repairs/v1` и массив `repairs`. Каждый файл значений
параметров должен содержать JSON-объект.

**Здесь проверяются передача JSON, заголовки и типы контейнеров, но не полная
семантика требований, действий и параметров движка.** Неизвестные параметры,
последнее значение повторного `--set`, подстановки и выбор ремонтного адаптера
должен оценивать существующий владелец `environment-maintenance` в T027/T028.
T026 не объявляет произвольный каталог допустимым для выполнения только потому,
что его контейнеры прочитаны.

Для всех JSON-входов отвергаются повторные ключи, BOM, неверный UTF-8,
непарные суррогаты, `NaN`, бесконечности и переполнение экспоненты до
бесконечности. Чрезмерная вложенность также отвергается; защитная константа
парсера `JSON_DEPTH_LIMIT` равна 128. Диагностика не копирует содержимое входа,
его частные ключи или значения в текст ошибки.

## Ограничения и снимок входов

В `limits` обязательны ровно пять положительных значений. Для счётчиков и
размеров требуется целое число, не `bool`; время задаётся конечным числом.

| Поле | Реализованное значение ограничения |
| --- | --- |
| `max_targets` | Максимум выбранных целей; при `all` перечисление прекращается после обнаружения превышения. Явная одна цель не зависит от числа посторонних профилей. |
| `max_target_bytes` | Общий бюджет исходных байтов профиля и всех прочитанных по его ссылкам файлов, отдельно для каждой цели. Повторное чтение ссылки также расходует бюджет. |
| `max_output_bytes` | Размер полного обычного отчёта в байтах UTF-8, включая завершающий перевод строки, проверяется перед публикацией. JSON не обрезается. |
| `target_timeout_seconds` | Проверяется как положительное конечное значение; выполнение и контроль времени цели относятся к T027. |
| `run_timeout_seconds` | Проверяется как положительное конечное значение; выполнение и общий срок запуска относятся к T027. |

Сам конфигурационный файл Bootstrap ограничен 1 МиБ. Чтение профиля и файлов
ограничено дескриптором и оставшимся байтовым бюджетом; это не обещание жёсткого
предела всей памяти процесса или длительности файловых операций. Слишком
большой вход цели получает `target_input_unavailable`, остальные выбранные цели
сохраняют свои результаты.

Если полный обычный отчёт не помещается в `max_output_bytes`, возвращается
глобальная ошибка `limit_exceeded` без частичного списка целей. Небольшой
фиксированный JSON ошибки может превышать заведомо слишком маленький лимит,
например 1 байт. Это отдельный канал отказа, не успешно ограниченный отчёт;
никакие действия до него не выполнялись.

Для корректной цели снимок состоит из прочитанных объектов
`{project, catalog, repairs, values_files}`; порядок файлов значений сохраняется.
`config_digest` — SHA-256 его JSON-представления с `sort_keys=True`,
`ensure_ascii=False`, разделителями `(',', ':')`, без `NaN`, в UTF-8 и без
завершающего перевода строки. Перестановка ключей и форматирование входного JSON
не меняют digest, порядок `values_files` входит в снимок. Это digest прочитанных
входов, не digest результата разрешения параметров или команды `--set`.

Для вычисления digest каждое объявление в `catalog.parameters` должно быть
объектом с точным логическим `secret: false`. При `secret: true`, отсутствии
этого признака или непонятной форме хотя бы одного объявления возвращается
`config_digest: null`. При ошибке входа digest также `null`. Значения параметров
и содержимое файлов не выводятся. Это правило классификации объявленных
параметров, а не автоматическое обнаружение любого возможного секрета во входе.

Каждый файл читается с проверкой наблюдаемой стабильности. Набор нескольких
файлов и каталог не заблокирован одной транзакцией: глобальная атомарность
файлового снимка не обещается. Не изменяйте операционные входы во время вызова,
который должен описывать один согласованный набор файлов.

## Результаты и отказ

Нормальный ответ имеет схему `stride-bootstrap/v1`, поля `command`, `dry_run`,
`selection` (`requested`, `source`, `resolved`), общий `status`, `exit_code` и
массив `targets`. `source` равен `argument`, `environment` или `configuration`.
Порядок `targets` совпадает с фиксированным `resolved`.

Строка цели содержит `target`, `config_digest`, `status`, `exit_code`,
`effects`, `core`, `error`. В T026 всегда `effects: "none"` и `core: null`:
оболочка не запускает команды каталога, не ремонтирует БД и не читает хранилище
соседнего приложения скрытым вызовом. Глобальный отказ содержит только
`schema`, `status`, `exit_code`, `error`, `targets: []`, без полей выбора цели.

| Ситуация | Статус и код процесса |
| --- | --- |
| Доступный пустой набор `all` | `not_required`, 0. Это отсутствие выбранных работ, не проверка готовности среды. |
| Все выбранные входы корректны и набор непуст | `action_required`, 3; у каждой цели ошибка `maintenance_unavailable`. |
| Хотя бы одна цель имеет повреждённый или недоступный вход | `failed`, 4; строки остальных целей сохраняются. |
| Ошибка вызова, конфигурации, выбора, корня или общего лимита | `rejected`, 2; обычный отчёт целей не публикуется. |

Глобальные коды: `invalid_request`, `invalid_bootstrap_config`,
`invalid_selector`, `target_not_found`, `projects_unavailable`, `limit_exceeded`.
Коды входов отдельной цели: `invalid_target_config`, `unsafe_target_config`,
`target_input_unavailable`, `invalid_target_catalogue`, `invalid_target_parameters`.
В этих диагностических ответах `retryable` равен `false`; повторение без
исправления входа не является ремонтом. Ни одна ошибка не переводится в `ready`.

Ответ — один объект JSON и `\n`, явно записанные в UTF-8. Настройка
`PYTHONIOENCODING=ascii` или `latin-1` не меняет протокольные байты. При
принудительном прекращении процесса полный ответ не гарантируется: caller
проверяет настоящий код завершения и полноту JSON, а не только его префикс.

## Резервирование и продолжение работы

Полный набор операционных входов включает сам конфиг Bootstrap, всё содержимое
указанного `projects_root`, файлы профилей и все их каталоги, ремонты и файлы
значений. Одних путей к ним или поставляемых examples недостаточно. Сохраняйте
права, типы файлов и связи относительных путей; произвольный внешний
`projects_root` должен быть явно включён в манифест вашей системы резервирования.

При переносе сначала восстановите этот набор и соответствующие корневые пути,
не заменяя действующие профили шаблонами. Текущий Bootstrap не имеет команды
импорта/экспорта, не копирует файлы и не делает резервную копию вместо оператора.
Повторный вызов при неизменных входах повторяет диагностику без побочных действий;
это не выполнение будущего ремонта T027. Для восстановления рабочей среды
проекта используется отдельный [комплект восстановления](../../../recovery-tools/README.md),
а не ручная подмена состояния Task или чужой БД.

## Узкие проверки

Проверки выполняются из корня поставки с её выбранным интерпретатором.
`PYTEST_ROOT` ниже — каталог закреплённых тестовых зависимостей установки,
содержащий pytest 9.0.2; приложение для обычного выбора профилей pytest не требует.

```bash
PYTEST_ROOT=/absolute/path/to/pinned/pytest-9.0.2
cd "$CHECKOUT"
export LANG=C.UTF-8
export PYTHONDONTWRITEBYTECODE=1
export PYTEST_DISABLE_PLUGIN_AUTOLOAD=1
export PYTEST_ADDOPTS="-p no:cacheprovider"
export PYTHONPATH="$CHECKOUT/src:$PYTEST_ROOT"

"$PYTHON" -B apps/bootstrap/tests/test_profiles.py --suite behavior
"$PYTHON" -B apps/bootstrap/tests/test_shell.py --suite behavior
"$PYTHON" -B apps/bootstrap/tests/test_profiles.py --suite documentation
bash tests/smoke.sh "$PYTHON"
```

Первый набор содержит 20 постоянных групп поведения, второй — 8 исходных групп
совместимости оболочки, третий — 4 группы документации. Последний вызывает
только поддерживаемый smoke из шести явно перечисленных тестов. Документационный
набор использует существующий `tools/check_documentation.py` для страницы,
ссылок и якорей, а не отдельную реализацию проверяющего инструмента. В обычной
задаче запуск всех тестов репозитория не требуется. Историческую RED-проверку
`--suite red` после принятого RED не используют для повторного прохождения этапа.
