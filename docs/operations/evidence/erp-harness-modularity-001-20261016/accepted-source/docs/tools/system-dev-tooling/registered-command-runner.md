# Запуск зарегистрированных команд

## Назначение

Registered command runner уменьшает объём вывода проверок в контексте
AI-агента и не позволяет выбирать произвольный штатный timeout. Он
используется для неинтерактивных tests, static analysis, build и других
repository checks, которым назначен стабильный command profile.

Canonical profiles находятся в:

```text
ai-assistant/checks/command-profiles.toml
```

Текущая сгенерированная таблица лимитов и связанные contracts:

- [лимиты выполнения команд](../../agents/command-runtime-limits.md);
- [durable evidence зарегистрированных
  проверок](registered-check-evidence.md);
- [repository checks MCP](repository-checks-mcp.md).

## Контракт запуска

### Владельцы возможностей

| Модуль | Ответственность |
|---|---|
| `command_profile_lib.py` | Модели профилей, проверка конфигурации, чтение и запись TOML, построение таблицы лимитов, атомарная запись текста |
| `check_configuration.py` | Выбор корня конфигурации и сохранение признака явного выбора |
| `registered_check_service.py` | Общая операция выбора профиля и запуска зарегистрированной команды |
| `check_runner_lib.py` | Процессы, зависимости, timeout, кэш, ledger и доказательства исполнения |
| `run_check.py`, `repo-checks-server.py` | Разбор запросов CLI и MCP, сборка вызова, владение запросом и отображение результата |

Файлы Python находятся в `ai-assistant/checks/`; MCP transport находится
в `ai-assistant/mcp/`. Генератор лимитов использует модуль профилей
самостоятельно. Для чтения, проверки или записи профиля не требуются
SQLite, запуск процессов, реестр тестовых пакетов или регистрация
временных артефактов.

`CheckConfiguration.select(repository_root, configured_root)` фиксирует
корень и признак `explicit` на границе запроса. Отсутствующий аргумент
выбирает корень репозитория; явно переданный относительный путь, включая
пустую строку, разрешается от каталога запуска. Выбор пути не читает
реестры. `load_profiles()` читает выбранный файл при обращении.

`RegisteredCheckService(configuration)` загружает профили один раз для
запроса. CLI и MCP вызывают его `run()` и получают выбранный профиль,
полную запись и результат. Корень исполнения и каталог ledger передаются
отдельными аргументами. Контекст конфигурации явно проходит дальше в
проверку зависимостей, выбор реестра пакетов, кэш и область доказательств;
повторного выбора корня внутри этих операций нет.

Неизвестные параметры игнорируются на всех уровнях конфигурации.
Обязательные известные параметры, их типы, допустимые значения и версия
контракта проверяются явно. `schema_version` имеет целочисленный тип и
поддерживаемое значение `1`; логическое `true` ему не соответствует.
Таблица `cache`, её поля `enabled`, `input_paths`, `environment`, все
три поля `prerequisites`, а также `stall_timeout_seconds` и
`observed_max_progress_gap_seconds` обязательны. Отключение задаётся
явными `false`, `0` и пустыми массивами; отсутствие поля вызывает отказ.
Схема JSON проверяет заявленные структурные ограничения. Расчётные и
межполевые правила, включая согласованность прогресса и лимитов,
принадлежат моделям профилей.

### Вызов команды

Codex использует один MCP tool call:

```text
mcp__repo_checks__run
```

с input:

```json
{
  "command_id": "<registered-command-id>"
}
```

MCP server вызывает тот же repository runner и ждёт terminal result
внутри tool execution. Project `PreToolUse` dispatcher блокирует exact
registered argv и shell-wrapped варианты до Bash-выполнения и возвращает
точный MCP payload. Похожая, но неэквивалентная команда не заменяется
молча: она получает только candidate notice.

Прямой CLI остаётся для человека. Codex использует его только после
реального отказа MCP и передаёт одну machine-readable причину:

```bash
bash ai-assistant/bootstrap/python-runtime.sh \
  ai-assistant/checks/run_check.py \
  --command-id <registered-command-id> \
  --fallback-reason mcp-server-unhealthy \
  --json
```

Допустимые причины: `mcp-tool-unavailable`, `mcp-server-unhealthy`,
`mcp-call-failed` и `mcp-project-untrusted`. Fallback должен быть одной
foreground-командой без redirect, pipeline, background или monitor-loop.
Dispatcher добавляет `--json`, если агент его пропустил. Metadata
operations `--list` и `--describe` можно выполнять напрямую.

Runner:

1. выбирает profile для текущей платформы;
2. проверяет executable, files и environment prerequisites;
3. запускает фиксированный `argv` в заданном `cwd`;
4. сохраняет полный объединённый stdout/stderr;
5. наблюдает общий timeout и, при наличии, монотонный progress;
6. завершает process tree при timeout или stall;
7. разбирает terminal log выбранным parser;
8. при объявленном `evidence_id` проверяет и атомарно сохраняет declared
   artifacts;
9. записывает JSON record и SQLite ledger;
10. возвращает bounded model-facing result.

Произвольные аргументы команды через runner или MCP не передаются. Новая
вариация нагрузки или runtime оформляется отдельным профилем, чтобы её
история выполнения не смешивалась с другой нагрузкой. Repository-local
STDIO MCP server не возвращает process session и не предоставляет
status-polling tool: одна команда создаёт один model tool call и один
bounded terminal response. Это ответ на ожидающий RPC, а не отдельное
уведомление о завершении фонового процесса. В одном session/subagent
scope dispatcher разрешает только одну активную зарегистрированную
проверку. Он блокирует второй запуск и обнаруживаемый мониторинг
активного лога; независимая работа допустима, если она не меняет
зафиксированные входы проверки, конфигурацию или данные БД, не создаёт
конфликт ресурсов и не мешает завершению принадлежащего runner процесса.
Ответ Bash с `session_id` и без `exit_code` сохраняет владение
проверкой:
это выдача управления, а не завершение. Освобождение выполняет terminal
cleanup runner либо окончательный ответ инструмента.

### Граница проверки Bash

Dispatcher различает обнаруженное наблюдение (`detected_observer`),
неопределённый контекст конкретного наблюдения
(`unresolved_execution_context`) и отсутствие обнаруженного наблюдения.
Последнее не является доказательством безопасности произвольного Bash.

Поддерживаемые формы включают прямые команды и их аргументы,
перенаправления, кавычки и подстановки, буквальные присваивания и
экспорт,
`env -S`, известный статус `true`/`false`/`:`, логические связки,
выбранные ветки `if` и области переменных в subshell/pipeline.
Буквальное определение функции не исполняет её тело; проверки наличия
функции используют отдельное пространство имён. Исполнение функции или
условие, зависящее от внешних файлов, нельзя считать вычисленным по
тексту команды.

Для доступного исполняемого файла с аргументом активного ресурса
неизвестная роль аргумента требует разрешения контекста. Доступность
определяется по окружению hook и переданному `cwd`, без чтения активного
лога. После `eval`, `source`, изменения alias или настроек Bash прежние
предположения о пространстве команд и экспортированных значениях не
считаются доказанными. Запрет возникает при последующей конкретной
зависимости от активного ресурса; сам модификатор не запрещает команду.
Изменение `PATH` или рабочего каталога не позволяет считать неизвестный
обработчик отсутствующим по исходному окружению hook. Известная команда,
которая только печатает литерал, сохраняет определённую роль аргумента.
При запуске через `env` или `exec` одноимённый внешний файл не считается
встроенной командой Bash. После изменения пути поиска его роль требует
разрешения контекста; явный проверенный путь сохраняет свою роль.

Известное буквальное значение переменной связывается с аргументом
читателя только при реальной подстановке. Простые подстановки в правой
части присваивания сохраняют значение через вторую переменную и
составление пути, включая вызываемую функцию. Правая часть присваивания
не разделяется на поля. Присваивания перед командой вычисляются
последовательно; аргументы `export` и `readonly` используют снимок
значений до выполнения встроенной команды. Одинарные кавычки, печать
значения и использование его как шаблона поиска не превращают значение
в читаемый файл. Простая подстановка без кавычек учитывает разделение
по пробелу, табуляции и переводу строки: после шаблона может появиться
отдельный файловый аргумент. В `env -S` сначала применяется подстановка
внешнего Bash, затем разбор GNU `env`; неэкспортированная переменная
доступна первому этапу. Файловый аргумент `bash`/`sh` читается как
скрипт,
а аргументы после `-c` сохраняют роль данных. Для такой зависимости hook
требует определённый
аргумент. Подстановка команды получает снимок контекста в момент её
выбора; известные значения вызывающей области доступны при проверке
тела выбранной функции. Возможные значения активного ресурса после
вызова функции сохраняются как неопределённые зависимости, без
заявления о полном вычислении её исполнения и изменений состояния.

При анализе `bash -c` и `sh -c` дочерняя область получает снимок
экспортированных переменных и временных присваиваний перед командой.
Неэкспортированные переменные не наследуются; `env -i` и `env -u`
изменяют этот снимок. Формы `-u NAME`, `-uNAME` и `--unset=NAME`
одинаково удаляют переменную из дочерней среды.
Присваивания GNU `env` являются аргументами: кавычки вокруг
`NAME=value` не отменяют их роль. Подстановки и разделение на поля
используют снимок вызывающего Bash до изменения среды `env`.
Известная простая подстановка имени команды
сохраняет её роль: динамический `printf` не становится читателем.
Подстановка `${NAME}` внутри GNU `env -S` использует среду самого
`env` до применения `-i` и `-u` к дочерней команде. Временные
присваивания перед вызовом функции доступны её телу; после вызова
значение вызывающей области восстанавливается. Статус модификатора
без исполняемой команды не считается заведомо успешным: следующая
ветка проверяется при конкретной зависимости от активного ресурса.
Дочерний Bash получает явно экспортированные функции с учётом снятия
экспорта и удаления соответствующей записи `BASH_FUNC_*%%` через
`env -u`. Обычные функции родительской области не наследуются.
Внешний запуск через `env`/`exec` и выбор через `command` не вызывают
одноимённую функцию родительского Bash.

Цель перенаправления также получает известное значение переменной;
чтение или запись активного лога через такой путь блокируются. Символ
перенаправления в кавычках остаётся аргументом данных. Файл `--rcfile`
у Bash учитывается при явно интерактивном запуске вне POSIX-режима;
обычный `-c` не превращает этот параметр в чтение файла инициализации.
Для выбранного дочернего shell учитываются и файлы из его среды:
`BASH_ENV` у обычного неинтерактивного Bash и `ENV` у интерактивного
`sh` либо Bash в POSIX-режиме. У Bash режим выбирается через
`--posix`, `-o posix`, наличие `POSIXLY_CORRECT` или `posix` в
дочернем `SHELLOPTS`; `+o posix` отключает его. Явный
привилегированный режим `-p` либо `-o privileged` подавляет эти
входы; отключение режима учитывается тем же владельцем опций.
Привилегированный режим, унаследованный через `SHELLOPTS`, подавляет
чтение этих входов при запуске даже при последующем `+o privileged`
или `+p`. Опция `--norc` подавляет обычный `rcfile`, но не
`ENV` в POSIX-режиме.
Простые `$NAME` и `${NAME}` в значении файла инициализации
вычисляются в выбранной дочерней среде тем же владельцем подстановок,
без разделения на поля и повторной подстановки полученного значения.
Сложные параметры и подстановка команды в этих значениях не
вычисляются как произвольный shell. При конкретной зависимости от
активного ресурса они сохраняют неопределённый контекст и запрет до
исполнения. Исполняемый код подстановки проверяет существующий
владелец команд и дочерней области; зависимости берутся из выбранных
аргументов и значений параметров. Нейтральная подстановка без такой
зависимости и вход, подавленный режимом запуска, запрета не создают.
Путь учитывается как имя файла; буквальные кавычки не становятся
синтаксисом shell. При известном cwd путь нормализуется относительно
него; неопределённый контекст с зависимостью от активного ресурса
сохраняет запрет до разрешения контекста.
Неэкспортированная, удалённая или очищенная переменная не создаёт
чтение; обычный файловый путь вне активного ресурса не блокируется.

Если неопределённый выбор команды или ветки связан с доступом к
активному логу либо наблюдением runner, hook возвращает
`permissionDecision=deny` до исполнения. Причина называет неизвестный
выбор и ресурс. Агент разрешает контекст независимым чтением, не читая
активный лог и не наблюдая процесс, затем отправляет определённую
команду в том же checkout и active scope с неизменными входами проверки.
Если подтверждено наблюдение, повтор остаётся запрещённым до terminal
result. Разрешение оператора для обычного разрешения контекста не нужно.

Неопределённый синтаксис без конкретной зависимости от активного
наблюдения не создаёт запрета. Строковый литерал у известной команды,
которая не читает файл, неисполняемое определение и пропущенная ветка
также не создают наблюдение. При отсутствии активной проверки эта
защита не применяется. Это ограниченная проверка наблюдаемых
зависимостей,
а не sandbox и не гарантия против произвольных скрытых обращений.

[Исполняемый
контракт](../../../ai-assistant/tests/checks/registered-command-adoption.py)
проверяет полный hook, отсутствие запуска побочного эффекта при отказе
и определённый повтор с неизменным source/active scope. Его transport
adapter моделирует порядок исполнения fixture; сам по себе он не
доказывает порядок native Codex host.

MCP runner открывает artifact-policy session по adoption scope запроса.
Если transport не передал такой scope, server детерминированно выводит
request-local technical session из JSON-RPC request ID; это сохраняет
тот же policy gate до первой artifact write и не меняет profile или
result contract проверки.

## Adoption telemetry

Append-only telemetry dispatcher-а хранится в:

```text
ai-assistant/analytics/data/registered-command-adoption.ndjson
```

Запись содержит session/turn/tool identifiers, candidate profile,
selected transport, MCP availability, fallback reason, rewrite/bypass
flags, terminal status и SHA-256/размер входа. Raw Bash command и полный
tool input не сохраняются. Текущее active-state находится только в
`.runtime/registered-command-adoption/**` и может быть удалено вместе с
runtime state. Изменённый project hook начинает действовать после
повторного trust/review конфигурации Codex.

## Результаты и журналы

Временные данные активного процесса:

```text
.runtime/checks/<check-id>/
├── staging/
└── result/
```

Retained metadata между запусками:

```text
ai-assistant/checks/data/
└── ledger.sqlite3
var/ai-assistant-check-cache.sqlite3
```

Во время исполнения command log и progress находятся в
`.runtime/checks/<check-id>/staging/`. После terminal outcome полный
log,
progress, JSON record и evidence tree атомарно переносятся в
`.runtime/checks/<check-id>/result/`. Затем удаляется только staging;
результат и данные других проверок сохраняются. Прежние квитанции,
журналы и evidence не перемещаются и не удаляются. Кэш использует
сохранённый `source_record_path`, проверяя хэш квитанции и evidence;
поиска альтернативных путей нет. Полный log не печатается обратно в
контекст.
Если command profile ссылается на именованный evidence contract, runner
передаёт private staging path через `REPO_CHECK_EVIDENCE_DIR`, проверяет
required artifacts, budgets и filesystem safety, затем создаёт
`evidence-manifest.json` в current-run root. Green command без
обязательного evidence
получает `unconfirmed`. Полный контракт, cache reuse и status semantics
описаны в [durable evidence зарегистрированных
проверок](registered-check-evidence.md).

### Известное ограничение native FAST

При доставке `ERP-STORAGE-REQUIREMENTS-001` подтверждено
рассогласование путей: runner передаёт private
`staging/evidence`, а native-потребитель JUnit ожидает путь без
`staging`. Проверка отклоняет допустимый путь до запуска тестов.
Это дефект взаимодействия инструментов ERP, не схемы БД Poise.
Черновик ремонта: `ERP-NATIVE-FAST-EVIDENCE-CONTRACT-001`.

Для этого случая отдельно согласован ручной способ получения
доказательств: неизменённый полный FAST, временное снятие привязки
evidence только в конфигурации дочернего процесса, сохранение
фактических JUnit и журнала, точное восстановление конфигурации.
Такой запуск не получает штатную приёмку evidence: при успешном
процессе квитанция остаётся `unconfirmed`, а
`verified_success` — `false`. Ручная независимая приёмка не меняет
эти значения и не означает исправления дефекта.

Способ не является общим разрешением обходить dispatcher или
выбирать часть именованного пакета. Для покрывающего поверхность
пакета обязателен полный штатный запуск. В указанной задаче
дополнительно выполнен весь `component.system-admin`; отдельный
диагностический запуск файла не заменяет этот пакет.

При проверке многопоточного результата сверяют не только число
тестов и аргументы команды, но и требуемые классы и методы в
сохранённых доказательствах. Отсутствие класса в JUnit само по себе
не устанавливает причину потери доказательства и не доказывает,
что класс не запускался.

Сбои, нерабочие попытки и ручные исправления регистрируются по
[контракту сбоя
harness](../../agents/agent-workflow-contract.md#сбой-harness)
в рабочих материалах спринта. После исправления дефекта эту
активную запись следует удалить или сузить; история останется в
журнале и Git.

Для точечной диагностики используйте
`ai-assistant/agent/command-output.py` с конкретным pattern или
диапазоном строк.

## Эмпирический timeout

Профиль калибруется только по `verified_success` с совпадающими:

```text
command_id
workload_class
runtime_class
```

Execution timeout равен 110% самого долгого подтверждённого успешного
запуска. Для профиля с монотонным progress probe stall timeout равен
110% самого долгого подтверждённого интервала между последовательными
progress events; подготовка до первого event в этот baseline не входит.
Timeout, stall, cancellation, dependency failure, environment failure,
hang и loop не входят в baseline.

Перед каждым запуском runner читает durable ledger и автоматически
применяет новый эмпирический максимум. После более долгого verified
success следующий запуск уже использует `ceil(1.10 × maximum)`; модель
не запускает отдельную команду и не редактирует profile вручную.

`calibrate_timeout.py` предназначен только для
maintenance-материализации
ledger history в version-controlled profile snapshot и generated
documentation. Он не входит в обычный workflow задачи.

Если зарегистрированного лимита не хватило, агент сначала исследует
saved evidence. Один увеличенный diagnostic rerun разрешён только с
`--timeout-evidence` и текстовой причиной. Сам timeout не изменяет
profile.

## Принудительная отмена

Активный зарегистрированный запуск отменяется только через
`mcp__repo_checks__cancel`. Control tool не принимает PID или
shell-команду:
доверенный hook привязывает его к текущему session scope. Сначала runner
получает обычный cancellation event; если bounded cleanup не завершён,
MCP
server завершает принадлежащее runner дерево процессов и освобождает
stale
adoption lock. Отмена сохраняет terminal evidence и никогда не считается
успешной проверкой.

`progress = unavailable` означает, что runner видит process liveness и
terminal timeout, но не умеет доказать предметное продвижение.

`progress = regex` извлекает монотонный completed counter, optional
total и stage из stdout/stderr. Stall clock запускается только после
первого подтверждённого progress event: длительная подготовительная
стадия ограничивается общим empirical timeout и не считается stall сама
по себе. Повтор того же значения не сбрасывает stall clock. Уменьшение
counter или противоречивый total фиксируются как anomaly.

Output offsets и время последнего stdout/stderr сохраняются как
диагностическая activity, но сами по себе не сбрасывают stall clock.

Даже при probe универсально доказать отсутствие любого бесконечного
цикла невозможно. Empirical timeout остаётся конечной safety boundary,
а process-tree snapshot и полный log сохраняются для расследования.
Явная отмена также завершает process tree, сохраняет evidence и
возвращает `cancelled`, но не участвует в calibration baseline.

## Парсеры

Runner содержит отдельные bounded parsers для:

- generic text;
- PHPUnit;
- Vitest;
- Playwright;
- PHPStan;
- Deptrac;
- build output.

Статус команды всегда зависит от exit code. Для профиля с
`require_parser_confirmation = true` нулевой exit code без узнаваемого
success summary получает `unconfirmed`, а не `passed`.
