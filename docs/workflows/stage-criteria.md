## Назначение этапа

У каждого этапа явно заданы `purpose` и `criteria_authority`:

| `purpose` | Смысл | Полномочия относительно будущего выполнения |
|---|---|---|
| `design` | Проектирование | Предлагает редакцию для целей из `propose` |
| `execution` | Выполнение | При начале закрепляет действующую редакцию |
| `observation` | Наблюдение результата, в том числе согласование проекта | Принимает решения для целей из `decide` |
| `other` | Другое пользовательское назначение | Использует явно заданные `propose` и `decide` |

`criteria_authority` содержит ровно два списка уникальных ID: `propose` и `decide`.
Каждый ID ссылается на существующий этап с `purpose: "execution"`. Пустые списки
означают отсутствие соответствующего полномочия. Сам тип `other` полномочия не выдаёт.

Назначение не заменяет `handler`, `role`, `instruction`, переходы и ограничения
записи. Имена ролей произвольны. Например, `observation` может использовать `produce`
в одноролевом процессе либо `inspect` с независимой ролью. Во втором случае действуют
обычные проверки независимости автора и проверяющего. Система не добавляет обязательную
роль или универсальную последовательность этапов.

## Новые проекты и старые снимки

Поставляемые `config/catalogue/processes` явно задают `purpose` каждого этапа
и `criteria_authority` с пустыми `propose`/`decide`. Назначение выбирается по
содержанию работы, а не автоматически по handler или роли. Например, написание
детального проекта — `execution`, проверка альтернативных выводов — `observation`,
механическая публикация уже принятого результата — `other`.

Пустые списки не дают планировщику или проверяющему скрытого права менять критерии
следующих этапов. Планировщик может явно настроить task-owned starter до его
замораживания; применяются действующие правила Task, а не автоматический grant
по имени этапа. Обновление blueprint и его process-source digest относится только
к будущему созданию проекта. Существующие process snapshots, маршруты и Task
не переписываются: их миграция — отдельная авторизованная операция.

Порядок выбора совместимой поставки и создания конфигурации описан в
[схеме нового проекта](../configuration/storage-layout.md#новый-проект-шаблоны-и-заполнение).

## Договор и критерии

В каждом элементе Task `stage_contracts` явно присутствуют:

```json
{
  "stage_id": "build",
  "allowed_paths": ["src/**"],
  "entry_requirements": [],
  "exit_requirements": [],
  "criteria": {
    "requirements": ["Возвращается удвоенное входное целое число."],
    "definition_of_ready": ["Входные данные и ожидаемый результат определены."],
    "definition_of_done": ["Согласованные проверки доказывают результат."]
  }
}
```

Три списка в `criteria` содержат уникальные непустые строки; явные пустые списки
допустимы. `entry_requirements` и `exit_requirements` — ID обязательств содержимого,
а не текст DoR/DoD. Их ссылки проверяет общий владелец Task-контракта.

Цель и верхнеуровневые требования задачи не подменяются критериями отдельного этапа.
`ready` фиксирует исходный Task-контракт. Это не запрещает уточнять критерии будущего
выполнения через описанный ниже протокол. `allowed_paths`, граф и прочие поля Task
этот протокол не редактирует.

Начальная редакция имеет источник `initial`, связанный с исходным контрактом и
подлинным снимком требований. Процесс может начинаться непосредственно с выполнения:
ради этого не создаются фиктивные проектирование или согласование. Источник `proposal`
связывает принятую редакцию с точным предложением и решением; `historical` — с исходным
состоянием и квитанцией явной миграции.

## Чтение

После захвата своей Task передайте существующему native launcher:

```json
{
  "operation": "show",
  "input": {"queries": [
    {"id": "task", "kind": "task"},
    {"id": "build-criteria", "kind": "stage_criteria", "stage_id": "build"}
  ]},
  "messages": []
}
```

Ответ сопоставляют по ID запроса, не по позиции. `stage_criteria` возвращает `task`,
`stage_id`, `purpose`, `revision`, `criteria`, `entry_requirements`, `exit_requirements`,
`source`, `execution`, `proposals`, `history`. Внутренний полный список `revisions`
не входит в эту проекцию. `execution` содержит `state`, `epoch`, `bound_revision`.
Публичная `version` Task берётся из `show` или `bootstrap`, без пересчёта; она отличается
от `revision` критериев. Чтение не создаёт предложения, решение или начало выполнения.

## Предложение редакции

На текущем разрешённом этапе добавьте `criteria_work` в **реальный**
`result.stage_work` обычного пакета `verify`. Остальные поля `result` берутся из
актуального шаблона; обязательные поля обычного handler сохраняются.

Ниже только значение `criteria_work`, не самостоятельная операция. Числа `42` и `0`
нужно заменить текущими наблюдёнными версиями Task и целевого этапа:

```json
{
  "request_id": "design-build-criteria-1",
  "expected_version": 42,
  "proposals": [{
    "stage_id": "build",
    "expected_criteria_revision": 0,
    "criteria": {
      "requirements": ["Для любого входного целого числа возвращается его удвоенное значение."],
      "definition_of_ready": ["Входные данные и ожидаемый результат определены."],
      "definition_of_done": ["Согласованные проверки доказывают результат."]
    },
    "entry_requirements": [],
    "exit_requirements": []
  }],
  "decisions": []
}
```

Объект содержит ровно `request_id`, `expected_version`, `proposals`, `decisions`.
Ровно один список операций непуст. Boolean не является допустимой числовой версией.
В пакете предложений каждый целевой этап встречается один раз.

Предлагать можно на `design` или на явно уполномоченном `other`, только для целевого
выполнения со `state: "unstarted"`. Готовность Task и результаты других этапов этого
права не отменяют. Приём предложения связан с успешно проверенным результатом текущего
этапа. Предложение само по себе не заменяет действующие критерии. В сохранённом
предложении есть `proposal_id`, `proposal_digest` и происхождение: этап, итерация,
submission автора. Эти значения получают чтением, не вычисляют вручную.

## Согласование

На разрешённом `observation` или `other` передаётся решение о точном предложении:

```json
{
  "request_id": "agree-build-criteria-1",
  "expected_version": 47,
  "proposals": [],
  "decisions": [{
    "proposal_id": "OBSERVED-PROPOSAL-ID",
    "proposal_digest": "OBSERVED-PROPOSAL-DIGEST",
    "decision": "accepted",
    "reason": "The proposed criteria describe the agreed result."
  }]
}
```

Маркеры ID/digest и число `47` — места подстановки из текущего публичного чтения,
а не пригодные для отправки идентичности. `decision` — `accepted` или `rejected`;
`reason` непуст. Для `inspect` сохраняют также его обычные `coverage`, `findings`
и `resolution_decisions`: критерии не заменяют независимый осмотр результата.

После успешной проверки результата `accepted` активирует предложенную редакцию,
увеличивает её номер и сохраняет предыдущую. `rejected` сохраняет действующую редакцию
и записывает решение. Цель должна оставаться не начатой, исходная revision — актуальной.
Повтор одного предложения и решения по разным предложениям одного целевого этапа
в одном пакете отклоняются. Ошибка одного элемента не применяет остальные элементы.

## Начало выполнения

При фактическом допуске к `execution` приложение закрепляет действующую редакцию:
`execution.state` становится `started`, `bound_revision` указывает на неё. Проверки
версии, источника редакции, владения, входных условий и зависимостей действуют вместе.
Конкурирующие согласование и начало не создают двух действующих закреплений.

Handoff, resume и повторное посещение сохраняют закрепление; это не новое право
изменить критерии. Уточнение другого, ещё не начатого выполнения сохраняет критерии,
результаты и доказательства остальных этапов, в том числе при общих требованиях.
Сохранённые доказательства не превращаются в свежие PASS для другого коммита.

## Перезапуск и история

Изменение закреплённых критериев проходит согласованный публичный
[restart](batch-work.md#жизненный-цикл-newborn-task), разрешённую ревизию
`stage_contracts` в newborn и `ready`. Перезапуск сохраняет Task ID, рабочее дерево,
WIP, результаты и историю; его авторизация определяет разрешённые поля пересмотра.
Сам restart не означает, что все критерии автоматически стали редактируемыми.

При реальном изменении критериев целевого этапа после restart создаётся следующая
редакция, увеличивается `epoch`, закрепление открывается как `unstarted`. Неизменённые
критерии и закрепления других этапов сохраняются. Изменение назначения этапа этим
протоколом не поддерживается. Историческая классификация имеет отдельный контракт
миграции; она не является общим редактором назначения действующей Task.

История связывает авторов, решения, редакции, начало выполнения и основание restart.
Предложения сохраняют происхождение проверенного результата. Служебная
[автоматическая промотка](batch-work.md#автоматическая-промотка-после-перезапуска)
не требует выдуманной смены роли, но повторяет только разрешённые действия и проверки.
Это не единая новая команда `restart → revision → ready → продолжение`.

## Отказы и восстановление

| Наблюдение | Действие |
|---|---|
| `criteria_authority_denied` | Проверить текущий тип этапа и явный grant целевого ID; не переименовывать caller |
| `criteria_work task version conflict` / `criteria revision conflict` | Прочитать актуальное состояние и оценить, применим ли прежний проект |
| `target_started_requires_restart` | Согласовать restart вместо скрытого редактирования |
| `proposal_identity_mismatch` | Использовать точные ID/digest сохранённого предложения |
| `duplicate_proposal_target`, `duplicate_proposal_decision`, `overlapping_decision_targets` | Исправить состав пакета, сохраняя смысл решения |
| `stage criteria migration required` | Выполнить отдельно разрешённый переход состояния; не добавлять поля SQL-запросом |

Точный повтор уже успешно предъявленного `verify` обслуживает существующий владелец
пакета. Повторное использование `criteria_work.request_id` как новой работы отвергается;
другой payload не становится повтором старого результата. При неизвестном исходе сначала
используют существующий recovery-протокол, а не новый ID для обхода неопределённости.

Историческое `execution.state: "unknown"` не трактуется как `unstarted`; оно не даёт
права уточнять критерии или выдумывать начало. Продолжение сохранённого исторического
состояния использует его подлинное происхождение и обычные guards. Доказательство
допустимого начала мигрированной available Task получает общий владелец допуска
из точного завершённого intent/receipt, а не из одного наличия новых полей.

Неизвестные исторические поля execution сохраняются существующим владельцем записи.
Переданные значения неизменны с учётом JSON-типа: `1` и `true` различны, в том числе
внутри контейнеров. Изменение отклоняется до UPDATE с сохранением исходной строки
и версии. Пропуск такого поля сохраняет его прежнее значение; обычные текущие поля
продолжают обновляться с optimistic version.

## Пример и проверка

[Полный process](stage-criteria-process.example.json) — отдельный учебный JSON,
не рабочая конфигурация установки. Он показывает четыре назначения и произвольную
роль `author`; для независимого процесса задают действительные разные роли и actors.
Task-контракт, Requirements snapshot и текущий `result_template` получают отдельно.
Пример не является полной командой создания Task или разрешением на её запуск.

Из проверяемого checkout с выбранным Python можно проверить process без записи:

```bash
PYTHONPATH=src python -B - <<'PY'
import json
from pathlib import Path
from poise.modules.goal_config.domain import GoalTypeDefinition
document = json.loads(Path('docs/workflows/stage-criteria-process.example.json').read_text())
GoalTypeDefinition.from_configuration(document)
print('process example: valid')
PY
```

Эта проверка подтверждает форму process, не выполнение workflow, миграцию или приёмку.
Локальные ссылки и входящие anchors проверяет
[существующий checker](documentation-checks.md#проверка-ссылок-и-точных-заголовков).
