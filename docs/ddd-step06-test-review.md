## Требуемые маршруты до реализации
1. Два точных source commits, один конфликтующий файл: получить конфликт → native исправление → CONTINUE без повторного merge → тесты → own commit/push → inspect → явная публикация target.
2. Бесконфликтный и no-op варианты без искусственных commits/операций.
3. Неуспех combined tests → новая правка текущего дерева → новый verify, без повторного применения source-плана.
4. Замечание inspect → revise → отклонённое исправление → новый revise → принятие → publish. История находится в исходной Task.
5. Exact commands-план: probe → apply → probe, несколько шагов, остановка на отказе; корректировка через тот же apply_plan и FeedbackBook.
6. Read-only/unknown/обычные пользовательские сообщения учитываются на активной задаче; повтор message ID не увеличивает стоимость.
7. Read-only publish требует clear inspect и новой пользовательской инструкции, ожидаемый target ref проверяется.

Тестовые контракты отдельно закоммичены до появления нового API. Начальный `red.log` — отсутствие модуля, не утверждение о runtime-дефекте. Domain assertions затем проверяют реальные переходы, ограничения и неизменность планов.

Используются реальные Git worktrees, локальные bare remotes, subprocess, SQLite и stdin CLI. Изменения кода при конфликте и решения пользователя/осмотра в примерах задаются fixture, не моделью. Интерпретатор/пути конкретны в исполняемых fixtures. Внешний интернет и реальные privileged изменения среды не нужны.

## Обычные отрицательные проверки
Dirty worktree не сбрасывается; чужой target drift не перезаписывается; неопределённый probe не вызывает apply; исход неизвестного действия сначала проверяется; отсутствующий required artifact не позволяет выполнить target publication; прямой Task.mark_verified без action receipt запрещён.

После появления механического publish добавлен отдельный numeric regression: 4 содержательных узла графа, из них 2 пройденных, publish не увеличивает количество. Прежний код воспроизвёл ошибку 5 вместо 4.

Это законченные очевидные маршруты текущего среза, а не перебор невероятных комбинаций. Более широкие процедуры интеграции и изменения среды уточняются после реального использования.
