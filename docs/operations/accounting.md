# DDD-08 — фактические затраты и конечный результат

Редакция: **2026-09-12T00:25:00+05:00**. Владелец: библиотека Accounting. Это описание работающего среза, не обещание полноты внешней телеметрии.

## Граница модели

Task/Sprint отвечают за выполнение и приёмку. Accounting наблюдает их состояния и считает затраты/конечный payload, но не завершает задачи, не снимает claims и не меняет findings. Нет отдельного обязательного инструмента «учесть каждый запуск»: telemetry входит в существующий WorkTools.invoke, отчёт получается через batch show.

Измеряем три независимые группы: фактические tokens/time/messages; конечные изменения выбранных файлов/секций; явную стоимость поздних исправлений. Строки и байты — объём конечного результата, не доказательство бизнес-ценности. Расход железа, цена кредита и гипотетическая экономия не считаются.

## Явная конфигурация

Project schema — `ddd-accounting-12`, SQLite — `user_version=12`. Обязателен `accounting` со всеми полями из [исходного примера](../../config/accounting.example.json): timezone, week_start, max_events, max_files, max_blob_bytes, time_mode, causes, sources, path_categories, tokenizer и `storage` с отдельными относительными путями `database`/`lock`. Schema 11 не поддерживается и не мигрируется: до этого изменения рабочий вариант schema 12 не публиковался. Пример задаёт конкретные значения, не является неявной подстановкой.

В schema 12 необязательная телеметрия записывается в отдельную SQLite-БД под отдельным внешним lock. Её writer не обращается к authoritative Task DB и не участвует в транзакции результата работы. Захваченный `TelemetryEnvelope` обрабатывается асинхронно; заполненность очереди, ошибка или удерживаемый optional lock дают частичное покрытие, но не задерживают и не заменяют успешный ответ WorkTools. Accounting read объединяет authoritative Task/message/workflow/cycle projection с последним доступным committed snapshot optional-БД; чтение optional snapshot не берёт writer flock, а при недоступном SQLite snapshot немедленно использует последний ранее успешно прочитанный optional snapshot. Совпадающие факты двух хранилищ учитываются один раз: usage определяется также по `(source, stream, sequence)`, остальные наблюдения — по стабильному `id`. При различающемся содержимом authoritative-факт имеет приоритет, конфликт не суммируется, а отчёт получает `telemetry.projection_conflicts` и частичное покрытие. Текущая terminal benefit projection вычисляется при чтении и не создаёт обратную запись из optional processor в Task DB. Время envelope содержит `ClockObservation`; длительность вычисляется только внутри общей `comparison_domain`.

У каждого process обязательное `benefit`: `git_categories` и `sections`. Пустые списки допустимы только явно. Редактор goal-config поддерживает `set_benefit` в том же пакете с изменениями этапов и секций. Неизвестная категория при начале работы отклоняется.

Accounting path categories не расширяют автоматический выбор тестов. В частности, добавление категории documentation для метрик не означает, что документация стала четвёртым автоматическим impact-классом приложения.

Для development конфиги выбирают code/documentation как полезные категории; tests/fixtures видны в объёмах, но в пользу не входят. У конфигурации задачи на тесты можно явно выбрать tests/fixtures. Никакого ветвления доменного кода по goal_type нет. Полные 13 нормативных конфигураций остаются отдельным DDD-09.

## Пакет наблюдённой телеметрии

Обычный объект work допускает ключ `telemetry`. Его отсутствие означает отсутствие переданных фактов, не нулевой расход. Присутствующий объект имеет строго заданные четыре поля:

```json
{
  "usage": [{
    "source": "test", "stream": "actor-stream", "event_id": "response-42",
    "sequence": 1, "mode": "delta", "occurred_at": "2026-09-07T00:00:00+00:00",
    "counters": {"input_tokens": 1000, "output_tokens": 200, "total_tokens": 1200,
                 "cached_input_tokens": 300, "reasoning_tokens": 50}
  }],
  "intervals": [], "cause": "initial", "finding_targets": []
}
```

Это синтетические данные для формы запроса, не счётчик текущего разговора. Реальный источник обязан передать свои наблюдённые counters. Source должен быть объявлен в policy как observed/reported; новая запись получает известные task/sprint/stage/iteration от текущей работы. При повторе её исходная привязка сохраняется.

`mode=delta` — отдельная порция. `baseline` — исходный накопительный счётчик, который не начисляет предысторию в задачу. `cumulative` — разность со своим предыдущим baseline/cumulative в том же source/stream. Без baseline отказ; падение счётчика требует нового явно обозначенного потока. В одном пакете события сортируются по sequence, поздний неизвестный исторический элемент не пристраивается угадыванием.

Идентичность source/stream/event_id дедуплицируется. Иной payload под прежней идентичностью или повтор sequence с иной идентичностью отклоняется. Новые записи пакета откатываются вместе при ошибке. `total=input+output`; cached — часть input, reasoning — часть output. Детали не прибавляются к total второй раз; неизвестная деталь задаётся null.

`response_usage(...)` — адаптер уже полученного Responses usage object. Он не вызывает API и не получает скрытую статистику ChatGPT. Отсутствующее optional detail остаётся null.

## Время и границы наблюдения

`time_mode=tool_cycle`: bootstrap активной задачи открывает интервал; verified/accept/cancel/handoff закрывает его. Период включает инструментальную работу и необходимые ожидания проверок. Обычные действия внутри этапа не создают второй одновременно открытый цикл.

Время цикла поступает через обязательный порт `Clock` на границе композиции `Poise`/`RuntimeAccounting`. Наблюдение содержит три независимых значения: `audit_utc` — timezone-aware UTC для аудита и календарной проекции, `monotonic_ns` — неотрицательный монотонный отсчёт для порядка и длительности, `comparison_domain` — непустую область, внутри которой отсчёты сопоставимы. Production composition roots явно создают `SystemClock`; прямые API-тесты используют детерминированный `FakeClock`, а CLI subprocess получает собственную последовательность fake-наблюдений. Скрытого production fallback нет.

`SystemClock` использует `time.monotonic_ns()` и стабильный Linux boot ID из `/proc/sys/kernel/random/boot_id`. Если boot ID нельзя прочитать или он пуст, адаптер возвращает понятную ошибку вместо process-local идентификатора. Два сохранённых отсчёта сравниваются только при одинаковом `comparison_domain`. Смена boot domain или неполная форма открытого цикла закрывает его со статусом `unmeasured_clock_discontinuity`: длительность не выдумывается. Состояние, где `last_monotonic_ns < started_monotonic_ns`, и новое наблюдение меньше последнего сохранённого отсчёта отклоняются без изменения accounting row.

Новые tool-cycle записи используют timing version 2: начало, последний/конечный монотонный отсчёт, область сравнения, `elapsed_microseconds` и явный status. Поле `seconds` для них не записывается. Закрытая legacy-запись без timing остаётся читаемой по уже сохранённому числовому `seconds`; автоматической миграции или dual-write нет. В отчёте измеренный version-2 интервал восстанавливается как `audit_utc` начала плюс `elapsed_microseconds`, ограничивается half-open периодом запроса и делится по фактическим локальным полуночам. Несопоставимые циклы учитываются как unmeasured, а не как нулевая длительность.

Если после неуспешного verify поступает новое пользовательское сообщение с другим ID, прежний незавершённый интервал закрывается временем последнего наблюдённого результата, а не временем нового сообщения. Поэтому ночное ожидание пользователя не становится рабочим временем. Без событий пользовательских ходов такую границу невозможно достоверно восстановить — coverage partial. Открытые/crashed интервалы показываются отдельно и не экстраполируются до текущего времени.

`time_mode=reported`: источник передаёт массив закрытых интервалов с source,stream,event_id,started_at,ended_at. Они дедуплицируются; перекрытие внутри одного источника/потока отклоняется. Этот режим исключает параллельное автоматическое начисление tool_cycle. Перекрывающаяся работа разных агентов разрешена: active_seconds суммируется, wall_active_seconds — длина объединения наблюдённых интервалов.

Не измеряются автоматически размышление до первого инструментального старта и генерация финального ответа после последнего tool-result. Доставка человеку не утверждается: сохранённая граница — `tool_result_returned`.

## Конечная польза

Accounting baseline закрепляется при первом начале задачи: исходный Git commit, выбранные разделы результата и конкретная policy. Rework и transfer его не обнуляют. Внутри одного active store изменение измерительной policy не применяется молча к существующей задаче.

После completed берётся baseline→последний проверенный commit. Не суммируются промежуточные commits и переписывания. Для обычных UTF-8 Git-файлов сравнение построчное, с исходными окончаниями строк; заменённая строка считается удалённой плюс добавленной. И добавления, и удаления полезных категорий входят в результат.

Эталон `a=1\n → a=2\n`: added_lines=1, removed_lines=1, added_bytes=4, removed_bytes=4, итог changed_lines=2, changed_bytes=8. CRLF занимает свои фактические байты. Сопоставление путей буквальное; эвристическое обнаружение rename и вычитание чужих rebase-изменений не заявляются. Предполагается собственный worktree от фиксированного task base. Integration process может явно иметь пустые полезные категории, не удваивая исходную разработку.

В результате по каждой измеренной категории сохраняются added/removed lines/bytes; `useful` определяет её включение. Для выбранных секций SQLite читается только последний populated layer, а не сумма всех итераций и не весь technical report. Начальная authored section новой задачи считается пустой; работа должна входить через bootstrap до подачи содержательных sections.

Binary, non-UTF8, symlink/submodule и файлы сверх явно заданного бюджета не выдаются за ноль текста: у результата есть список unmeasured и partial coverage, если затронута полезная категория. Неизвестный вне configured categories путь не входит в объявленную область измерения. Двойное включение одного текста и как Git deliverable, и как section не устраняется семантически — process должен явно выбрать свою область.

При completed создаётся зачёт, при reopen/cancel он отзывается. Повтор принятия не добавляет новый зачёт; повторное завершение меняет прежний итог на новый. Например 3 → reopen 0 → completed 4 даёт 4, не 7. Отменённая задача имеет нулевую полезную длину/байты; её наблюдённые затраты сохраняются.

## Измерительные токены

Полезные payload tokens и фактический model usage — разные значения. Если tokenizer.kind=`unavailable`, changed_tokens=null. Это не нулевая польза, а недоступный измеритель.

Для `command` обязательны argv/cwd/environment/timeout/output budget и идентичность измерителя. В stdin поступает JSON `texts` из двух потоков: добавленный и удалённый полезный текст в стабильном порядке путей, затем выбранные секции. Ответ — `counts` той же длины. Код не выбирает tokenizer по имени текущей LLM. Изменение инструмента требует явного решения; старые measurements сохраняют идентичность и payload digest.

Ошибка этого инструмента оставляет известные lines/bytes и возвращает tokenizer_error. Сбой общего измерения сохраняется как unavailable measurement и диагностическое событие; он не превращает принятую задачу обратно в неуспешную.

В комплекте есть опциональный адаптер [tokenize_payload.py](../../tools/tokenize_payload.py) для явно установленной версии tiktoken и выбранного encoding. Пакет tiktoken здесь не установлен; этот production-инструмент не объявляется проверенным. Контракт проверен внешним синтетическим codepoint-измерителем. Это не модельный tokenizer и не способ оценить скрытый usage.

## Находки и стоимость исправления

Причина работы передаётся явно из configured causes либо null. Код не выводит дефект из слова «дальше», имени handler или номера iteration. `finding_targets` связывает имеющийся finding с конкретной прежней предъявленной stage/iteration. Запись самопроверки того же подхода не может быть выдана за поздний дефект.

При исправлении группы F1/F2 одна стоимость относится ко всей группе. Отчёт remediation_groups не делит её искусственно между находками. Ошибочная ссылка на finding/непредъявленный результат отклоняет telemetry-пакет. Неразмеченные записи осмотра остаются unclassified, не автоматическими quality findings. Отдельно видны предложения исправлений и отвергнутые решения.

## Один пакет чтения

```json
{
  "operation": "show",
  "messages": [],
  "input": {"queries": [{
    "id": "economics", "kind": "accounting",
    "scope": {"kind": "all", "id": null},
    "group_by": ["goal_type", "week"],
    "from": null, "to": null
  }]}
}
```

scope: all/project/task/sprint; у all id=null, иначе точный ID. Доступные группировки: task/sprint/project/goal_type/day/week. Период half-open `[from,to)`; у границ ISO timestamp с timezone. Calendar zone и начало недели берутся только из обязательной policy. Интервалы делятся по настоящим локальным полуночам; в DST сутки не предполагаются всегда 24 часа.

Область применяется к optional `TelemetryEnvelope` до подсчёта длительности, группировки,
стоимости исправлений и неполного покрытия времени. Выбирается `after_binding`, если
в нём есть Task; иначе сохраняется `before_binding`. Событие чужой Task/Sprint или
запрос другой project не даёт ни времени, ни группы, ни `partial` из-за несопоставимых
часов. События без Task и read-only наблюдения без исходной Task исключаются до этой
оценки. `all` по-прежнему охватывает все допустимые события текущего store; фильтр не
переписывает исходные факты. Проверка через public CLI:
[tests/accounting/test_telemetry_scope.py](../../tests/accounting/test_telemetry_scope.py).

Без периода totals.benefit — текущий зачёт задач. В периоде/по дням — сумма событий зачёта и отзыва в этот период; отрицательный delta после reopen нормален. Исторические затраты отменённой впоследствии задачи выделяются по её текущему исходу. Поэтому отчёт с датой периода может уточниться после отмены, это не immutable бухгалтерская ведомость «как было известно тогда».

Нет наблюдённых usage/time/messages — основной показатель null и coverage unavailable. Наблюдённый subtotal может быть 0; отсутствие событий не даёт права назвать полное потребление нулём. Coverage остаётся partial, даже при валидности всех полученных событий. Количественные коэффициенты вычисляются только при доступных ненулевых знаменателях. CPU, диск, биллинг и «сэкономленные токены» не включены.

## Transfer

Существующая scoped transfer сохраняет accounting accounts, usage, закрытые интервалы, credits и связи findings. Handoff закрывает свой цикл до снимка. Повтор импорта не начисляет расходы заново. Open cycle или совпадающий event identity в целевом store не объединяются автоматически.

«Вся работа» означает текущий store и явно выбранный project context; несинхронизированные stores не федеративно суммируются. Межмашинная подмена путей Git обрабатывается существующим transfer; измерительная policy не переписывается по догадке.

## Не реализовано этим срезом

Автоматическое чтение скрытых counters ChatGPT, полный live usage-feed Codex, цена кредитов, полная длительность ответа модели, отдельный first-pass quality score, стоимость по каждой находке внутри неделимого общего подхода, provenance строк через произвольные rebase/merge, все 13 продукционных benefit-конфигураций. Первый практический путь работает на поддержанных input-событиях и текущих process examples.

## Привязка поздних замечаний в отдельном хранилище телеметрии

Для `finding_targets` перед отправкой события захватываются минимальные
неизменяемые сведения из принадлежащего Task хранилища: идентификатор задачи,
этап/итерация замечания и факт доставки адресуемого результата. Фоновый
обработчик проверяет этот внутренний контекст, а не читает Task DB.
Неизвестное замечание, недоставленная итерация или ссылка на собственную
итерацию осмотра отклоняют весь telemetry batch; работа Task не откатывается.
Принятые привязки объединяются в read-only проекции отчёта. Теневые Task-строки
в optional DB и обратная запись классификации замечаний в Task DB не создаются.
Повтор идентичного события не удваивает затраты; группа замечаний разделяет
одну наблюдаемую стоимость, а не делит её произвольно между замечаниями.
