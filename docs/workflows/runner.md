# Runner и фазы DDD-04

Обновлено: **2026-09-14**. Срез **POISE-DDD-04**.

Пять реализованных семейств: produce, inspect, revise, observe, check. `apply_plan` выполняет типизированные действия, а Git publication handler отклоняет remote publication. Финализация write-stage создаёт только локальный commit; `git push` запрещён.

Route содержит только явный `entry`; переходы задаются `outcomes→targets`, а пользовательский возврат — `rework_targets`. Порядок списка stages не имеет семантики исполнения. Поддержаны короткие пути и циклы DDD-03. Счётчики переходов и посещений сохраняются только как история и не ограничивают исполнение.

`verify`:
1. Установить session/task/stage и наблюдаемое дерево.
2. Принять один полный result: секции, trace, новые методы, paths, stage_work и evidence_work.
3. Проверить content pre и required PREPARE evidence.
4. Выбрать task checks + project auto guards, сформировать точный execution key.
5. Использовать пригодный batch или выполнить команды без lock; записать receipts.
6. Убедиться, что предмет не изменился при проверках.
7. Оценить evidence; при CONTINUE вернуть факты и остановить механику этого вызова.
8. После аргумента — использовать те же наблюдения, оценить predicate/аргумент, проверить content post.
9. Согласовать commit tree и сохранить verified result. Git push не выполняется; принятый результат позже проходит отдельную локальную `integrate` с `merge --ff-only`.
10. Очистить runtime, вернуть доклад. Следующий этап ждёт пользовательского решения.

Если предыдущий вызов успел сохранить полный набор terminal receipts, но его execution-marker
остался `pending=checks`, точный повтор того же `verify` восстанавливает выполнение без нового
запуска команд. Runner повторно строит текущие tree, invocation и execution key, сверяет
submission digest, полноту receipts, ledger provenance и digest сохранённых output. Затем один
application UoW записывает доменное событие восстановления и очищает только `pending`; уже
неуспешный batch снова даёт `checks_failed`, а успешный продолжает обычную оценку evidence.
Неполный, изменённый, дублированный либо повреждённый batch остаётся неизвестным исходом:
повтор не запускается вслепую и состояние не меняется.

Незаполненная ручная часть до команды — evidence_requirements_failed. После новых фактов — awaiting_continuation. Неизвестные ссылки/невалидный формат — входная ошибка. Сбой или нераспознанный результат команды — checks_failed. Негативный predicate subject внутри check — нормальный not_satisfied, если процедура выполнена корректно. Guard failures никогда не становятся нормальным негативным subject.

После `checks_failed` активный submitted этап не требуется отменять или пересоздавать. Только новый явный пользовательский `bootstrap(decision=rework, feedback, rework_stage)` может провести ту же Task через объявленный `rework_targets`, если сохранился точный доступный failed batch текущих stage, iteration, submission, tree и execution key и нет неизвестного `pending`. Цель `revise` без открытых findings отклоняется до изменения состояния. Переход сохраняет contracts, worktree, историю и receipts, применяет семантические правила route и scope целевого этапа и очищает только заброшенное retry-состояние. Полные условия и пакет запроса определены в [пакетном контракте](batch-work.md#явный-rework-после-checks_failed).

Следующий inspect решает accepted/rejected для конкретной revision аргумента. Rejected направляет route в явно заданный changes_requested edge. Исправление проходит новую iteration и снова проверяется; старые revisions/decisions не теряются. Командные и логические evidence не подменяют друг друга.

## Нативное завершение сессии и зарегистрированные проверки

C020 использует существующую цепочку `hook → HookRegistry → RegisteredCheckRunner`.
`SessionEnd` сохраняет наблюдение о завершении **своей** сессии в существующем
операционном журнале hooks. Сам hook не посылает сигналы процессам и не меняет Task.
При `hook-work verify` runner получает read-only проверку этого журнала, привязанную
к наблюдённому `SessionStart`. Перед запуском и при опросе процесса runner проверяет,
не закончилась ли сессия. При завершении он отменяет только собственную process group,
записывает `cancelled=true`, `cancellation_reason=native_session_end`, освобождает слот
и оставляет полный stdout/stderr в evidence. Закрытая сессия отклоняет новый запуск
**до** создания процесса; отсутствие наблюдённого `SessionStart` тоже даёт отказ.

Поздний `SessionStart` после resume открывает новую последовательность наблюдений
для новых вызовов, но не стирает `SessionEnd`, относящийся к уже работающему запуску.
Чужая сессия не отменяет этот процесс. `Stop` означает конец хода и **не** отменяет
проверки, не принимает Task и не вызывает дополнительный ход. Если чтение журнала
или захват вывода ломается, runner освобождает свою группу/слот и возвращает ошибку,
не успешное evidence. Повторный `run_id` отклоняется до запуска и до очистки логов.

Семантика протокола сверена 2026-09-15 с официальной [документацией Codex hooks](https://developers.openai.com/codex/hooks/):
`SessionEnd` относится к завершению главного потока, advisory, имеет короткий
timeout до трёх секунд; `Stop` относится к ходу. C020 не добавляет новые события,
перехват Bash/MCP или распознавание shell-строк. Код/конфиг работающего Poise
не подменяются содержимым проверяемой копии; запуск проверки получает конкретный `cwd`.

Проверены настоящий subprocess runner и доставка JSON другим процессом через
сгенерированную команду hook. Доставка события живым экземпляром Codex после
пользовательского trust/deployment в этой среде **не наблюдалась**. Отсутствующий hook,
принудительное убийство самого runner ОС или уход потомка в новую независимую сессию
не покрываются этим advisory-каналом: нет обещания перехвата всех сторонних процессов.
Тайм-аут C033 и явная отмена C015 остаются независимыми механизмами самого runner.

## Среда исполнения и точные команды AI poise

Обновлено: **2026-09-15**, C025. Для собственной разработки AI-poise переиспользуются
`RegisteredCheckRunner`, `LocalProbeExecutor`, `AiPoiseTestPackages` и прежний output
store. Отдельные ERP runtime helpers, PHP/Composer entrypoints, второй runner или
общая runtime policy для чужих репозиториев не нужны.

Команда — точный argv, без shell-интерполяции. Environment передаётся явно, не
подменяется другим набором переменных. `cwd` — конкретный файловый путь, абсолютный
или относительный по обычной семантике процесса; передача пути не изменяет cwd
самого Poise. Executable ищется обычным способом выбранного процесса, а не в task
worktree по скрытому правилу. Отсутствующий executable даёт явную ошибку с его именем
и освобождает владение запуском. Вывод сохраняется только в переданные пути evidence.

Проверенная платформа запуска — Linux, включая Linux-процесс WSL. Нужны POSIX process
groups: их отсутствие отклоняется до создания логов и subprocess. Native Windows
здесь не поддерживается и не эмулируется. Другие POSIX hosts отдельно не проверены.
Сам WSL host в этом контейнере не наблюдался; тестировалась Linux-механика процесса.

Временные файлы recovery создаёт существующий `work_checkpoint`, а логи и declared
outputs — существующие runner/evidence owners. Нового глобального временного каталога,
политики tool paths или зависимости от ERP окружения C025 не вводит.

## Полный вывод и preview

Общее правило для всех инструментов: **preview служит только отображению; решения,
машинный разбор и полные списки строятся по полным данным**. Лимит отображения не может
изменять содержательный результат. Не вводить исключения для отдельных команд, числа
конфликтов или длины пути и не лечить ошибку увеличением `preview_chars`.

`RegisteredCheckRunner` сохраняет stdout/stderr в файлы: поля `stdout` и `stderr`
содержат пути, а `stdout_preview` и `stderr_preview` — краткие представления. Агент
читает полные сохранённые файлы штатным файловым инструментом. При `capture_complete=false`
вывод не становится полным от чтения preview; неполнота остаётся явно обозначенной.

Ошибка файлового чтения необязательного preview не отменяет факты завершения runner:
неудавшееся представление возвращается пустым, а `preview_errors` содержит имя потока
и класс ошибки, без текста исключения. Это диагностическое отображение, не замена
stdout/stderr и не признак успешной проверки. Целостность полных файлов, digest,
полнота capture и ожидаемый код завершения проверяются отдельно.

Новая попытка `check_attempt` версии 2 сохраняет связанные с Task/run факты реального
владельца: ожидание завершения ребёнка, остановку его группы и полноту capture.
Runtime записывает их до fallible сохранения receipt и представления результата.
Отсутствующий receipt по-прежнему запрещает повтор команды; доказательство остановки
позволяет передать попытку другому проверяющему и архивировать её при явном restart.
Историческая попытка v1 с полным подлинным набором отрицательных receipts может
финализироваться как `checks_failed`; started-попытка без receipt и без доказательства
остановки не получает proof задним числом. Остановка не означает GREEN или приёмку.

Явный `RunnerTimeoutPolicy.select(..., workload_contract=...)` поддерживает режим
`non_streaming` с конечными положительными `inner_budget_seconds` и
`teardown_seconds`: сумма должна помещаться в выбранный внешний deadline; progress-gap
учитывает эту сумму. Это API контракта, не автоматическое подключение поля к native
конфигурации методов. Живые лимиты и обычный streaming-маршрут этим изменением не
переключаются. Ручная диагностика использует тот же явно выбранный PATH/HOME и
методный PYTHONPATH, без переноса caller identity из полного родительского окружения.

Если нужные полные данные доступны обычной read-only командой или штатным чтением,
агент получает их этим способом в своём рабочем дереве, без отдельной обвязки. Не нужно
заново запускать изменяющую состояние команду только ради повторного вывода. Новое
чтение — наблюдение текущего состояния, а не замена истории прежнего запуска.

Известное отклонение текущего адаптера интеграции описано в
[RV2-07](../operations/known-bugs.md#rv2-07--усечение-машинных-данных-в-адаптере-интеграции).
Правило не выдаётся за уже выполненное исправление этого адаптера.
