# Хранение действий — DDD-06

Обновлено: **2026-09-06T22:58:21+05:00**. `project.schema=ddd-actions-8`, SQLite `user_version=9`. Требуется новая пустая БД. Миграций и чтения прежних схем нет.

## Таблицы
- `action_runs`: ключ `(task_id, stage, iteration)`, версия, сериализованный ActionRun. FK на Task; весь план и current cursor закреплены за итерацией.
- `action_events`: последовательные snapshots изменения операции, соответствующая версия, время. Внешний receipt не хранится исключительно в техническом stdout.
- Task содержит `action_assessment`: последнее подтверждение законченного плана, привязанное к текущему submission digest и дереву. Только оно разрешает handler outcome complete; одного агентского заявления недостаточно.
- `interaction_reports`: существующая таблица; механическая публикация не записывается как предъявленный содержательный этап.

`SqliteActionRepository` — единственный writer action-таблиц. Создание/обновление run и его события происходят в одной транзакции. Optimistic version предотвращает незаметную подмену. Тест SQLite trigger подтверждает откат run, если событие записать не удалось.

## Границы внешней операции
1. В короткой UoW сохранить намерение/состояние running.
2. Освободить lock; выполнить Git/точную команду и сохранить raw output в task runs.
3. Короткой UoW записать факт, cursor и событие.
4. Через Task API принять assessment только для текущей итерации.

Git/файлы/remote не являются частью SQLite-транзакции. Неизвестный исход обозначается running/blocked и проверяется перед повтором. Проверенные recovery-сценарии — pending merge собственной операции, промежуточный checkpoint, выполненная command с подтверждающим probe, target push. Произвольное восстановление любого внешнего эффекта не заявляется.

Raw command output находится только у текущей Task; технические имена из configured paths. Командный plan snapshot неизменен, completed prefix сохраняется. Предыдущие action_runs при rework не удаляются. Историческое сохранение плана не означает, что внешнее состояние навсегда неизменно; новая обязательная проверка должна явно измерить необходимые внешние условия.

Сессии разных задач могут одновременно исполнять планы. Общий OS lock защищает короткие записи, а не удерживается на всё время исполнения. Реальные Sprint/worktree регрессии прошлого среза повторяются.
