## 0035 — проверка выполнилась не над подтверждённым task source

- Статус: исправлено task 0037.
- Evidence: `projects/ai-poise/task/0035/runs/192bad99-7384-4fd0-85f5-b56b4ba05f2b/response.json`.
- Наблюдение: в одном ответе implementation-проверки `CLOCK_GREEN` завершилась с exit 0 и
  `7 passed`, но `T0035_CLOCK_GREEN` и `T0035_ACCOUNTING` завершились с exit 1; полный
  accounting-набор сообщил `7 failed, 50 passed`.
- Причина: verification method не содержал обязательной provenance проверяемого исходника.
  Среда запуска могла разрешить импорт из другого checkout, поэтому зелёный результат узкой
  команды не был связан с task worktree. Реестр также не запрещал некоторые дублирующие или
  конфликтующие методы до выполнения.
- Воздействие: этап не был ошибочно подтверждён, потому что остальные guards отказали, но
  отдельный PASS и ранее допустимый RED нельзя было считать доказательством task change.
- Исправление: новые методы требуют `source_under_test`; runtime разрешает repository bindings
  внутри текущего worktree, фиксирует `provenance_digest` и `expectation_digest`, отклоняет
  коллизии/неразрешимые пути до subprocess, а `CheckRegistry` запрещает semantic duplicates и
  конфликтующие ожидания. RED дополнительно требует явный nonzero failure marker.
- Ограничение: исторический response остаётся неизменным доказательством события; он не
  переписывается и не переименовывается в успешный запуск после исправления.

## 2026-10-04 — чтение истории после принятого ready

- Идентификатор: `REGISTRY-HISTORY-CURRENT-STAGES-001`; категория: код;
  повторяется при согласованной смене процесса с удалением исторических этапов.
- Task: `AIP-CHECK-OUTCOME-RECOVERY-001`, request
  `aip-delivery-ready-20261004`. Ответ сообщил неизвестный исторический
  `test_implementation`, хотя переход уже сохранил `available`, revision `244`
  и освободил владельца. Реестр имел revision `5` и пустой current; новые проверки
  не запускались. Независимый проверяющий подтвердил сохранённый action receipt.
- Причина: `CheckRegistry.restore_state` проверял каждый старый снимок против
  нового текущего процесса. Ошибка возникала в публичной проекции после принятия
  транзакции, а не в подготовке или валидации кандидата `ready`.
- Первичные материалы в configured project runtime:
  `aip-historical-registry-load-incident-20261004.json`,
  `aip-historical-registry-load-diagnostic-20261004.json`,
  `analyst03-ready-history-load-20261004/review.json`.
- Отдельные ошибки подготовки были исправлены до этого вызова: будущие входы
  не существовали в исходном base, а удаление `test_inspection` нарушало владельца
  сохранённых findings. Они не объясняют отказ чтения после принятого перехода.
- Выбранное исправление: владелец `RegistrySnapshot` восстанавливает исторический
  контекст из сохранённых расписаний и планов; существующие проверки формата,
  повторов и согласованности остаются. Текущие этапы не получают новых разрешений.
  Реальные RED-сценарии включают публичный persisted restart → ready → reload,
  текущий формат и старый формат исторического метода.
- Альтернативы отклонены: удаление истории, ручная смена DB/base/claim, возврат
  старого процесса и повтор нового `ready` скрыли бы причину или изменили договор.
  Применён разрешённый пользователем ручной маршрут в существующем Task worktree
  с независимой проверкой «Аналитик03», без подделки native stage evidence.
- Восстановление после установки исправления: прочитать состояние через владельца
  и точно повторить сохранённый request, подтвердив исходный receipt и отсутствие
  повторного запуска. Ранее проверенный `e950e82` остаётся историческим evidence;
  новый исходник требует свежих проверок и согласованной коррекции закреплённой
  source instruction перед следующим native этапом.


## 2026-10-03 — интеграционный runner не разрешал объявленные исходники

- Task исправления: `AIP-INTEGRATION-SOURCE-PROVENANCE-001`.
- Причина: путь интеграционных проверок собирал cwd и окружение самостоятельно,
  обходя существующий `resolve_source_under_test`. Объявленный repository binding
  не применялся к реальному subprocess; receipts не сохраняли разрешённые факты
  происхождения и их digest для повторной проверки перед публикацией.
- Воспроизведение: независимо проверенный RED на commit
  `cd2ffdd1eaf7f149a4148aece68c81c8ac27027e`, run
  `9345facd-c287-419f-a9e8-da8ed91e4992`: импорт выбрал стандартный модуль вместо
  одноимённого исходника кандидата. Это проверка фактического выбора исходника,
  а не только успешного завершения команды.
- Исправление в Task-ветке: общий resolver для подготовки запуска и сверки
  provenance текущего кандидата; непригодная свежая партия блокирует публикацию.
  Наличие исправления в ветке не означает его интеграцию в установленный оператор.
