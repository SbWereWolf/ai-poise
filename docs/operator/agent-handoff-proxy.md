# Прокси передачи результата

## Назначение и границы

`handoff-proxy` передаёт подготовленный результат назначенному напарнику одним
вызовом. Инструмент запускает существующий native `handoff`, дожидается процесса,
читает полный ответ, проверяет фактическое продолжение и освобождение владения,
затем вызывает установленный `send_message_to_thread`. Возвращается единый итог.

Агент заранее готовит содержательный результат, доказательства, сообщение и
авторизованного получателя. Решение проверяющего сохраняется в исходном пакете.
Получатель продолжает свою работу через собственный native launcher по
[договору передачи](../workflows/local-handoff.md#прямая-передача-между-исполнителем-и-проверяющим).
Приёмка Task, публикация и интеграция сохраняют своих владельцев и полномочия.

## Подготовка и настройки

Нужны Ubuntu/Linux, выбранный Python 3.15.x этой поставки Poise, native caller и
настроенный MCP stdio транспорт приложения с `send_message_to_thread`.
`CODEX_THREAD_ID` или `CODEX_SESSION_ID` поступают от настоящего host; при наличии
обоих значения совпадают. Используется native-сценарий без `POISE_CALLER_BINDING`.

Для запуска из явно выбранных исходников оператор задаёт:

| Значение | Источник |
|---|---|
| `poise_root`, `poise_python` | Выбранные исходники и интерпретатор действующей установки. |
| `project_id` | Точный ID настроенного проекта, выбранного для native handoff. |
| `native_launcher` | `work.sh`, доставленный текущему caller настоящим native hook. |
| `proxy_settings` | Абсолютный путь заполненных настроек данного инструмента вне Git. |
| `native_packet` | Подготовленный полный `handoff` Work-пакет текущего этапа с `messages=[]`. |
| `proxy_packet` | Абсолютный путь будущего `deliver` JSON внутри рабочей области Task. |
| `recipient_thread`, `message` | Согласованное назначение пары и содержательное сообщение агента. |

Потребитель установленного пакета выбирает версию, содержащую `handoff-proxy`,
через свой пакетный менеджер. Его `python -I -B -m poise` и запуск из выбранных
исходников могут обращаться к разным копиям. Интеграция исходников и обновление
отдельного установленного потребителя — самостоятельные действия по
[правилу поставки](../configuration/stride-launcher.md#библиотечные-потребители-и-версии).

Заполните все значения образца реальными путями и ID из указанных источников:

```json
{
  "schema": "poise-agent-handoff-proxy-settings-1",
  "project": "PROJECT_ID",
  "launcher": ["bash", "/absolute/native/work.sh"],
  "notification": {
    "command": ["/absolute/selected/node", "/absolute/installed/server.mjs"]
  },
  "state_root": "/absolute/Task-root/handoff-proxy"
}
```

| Поле | Договор заполнения |
|---|---|
| `schema` | Точно `poise-agent-handoff-proxy-settings-1`. |
| `project` | Непустой ID выбранного проекта; прокси добавляет `--project` и это значение к launcher argv. |
| `launcher` | Непустой argv существующего native входа данного caller. Executable доступен в выбранной среде. |
| `notification.command` | Непустой argv уже установленного MCP stdio сервера приложения. Это выбранный транспорт, способный уведомить назначенный чат. |
| `state_root` | Абсолютный путь временных материалов этой Task, сохраняемый до завершения обязательных потребителей и разрешённых повторов. |

`proxy_settings` отличается от project manifest и настроек native hooks.
Рабочие значения заполняются оператором; инструмент читает этот файл, а технические
операции Task делегирует прежнему launcher. Cwd и окружение наследуются от вызова.

Для Codex desktop используйте argv и среду действующей установки
`codex-app-tools`. В WSL установленный транспорт может использовать Windows Node
напрямую через interoperability. Сохраните предусмотренную этой установкой передачу
`CODEX_APP_TOOLS_PIPE_PATH` через `WSLENV`. Прокси получает готовый argv/environment;
выбор runtime, преобразование путей и установка транспорта принадлежат оператору.

Журнал и raw logs — временные Task-owned материалы. Держите `state_root` вместе с
рабочими материалами Task до завершения проверки/продолжения. Затем их удаляет
существующий владелец [retirement](../workflows/terminal-materials.md#владельцы-механики).
Постоянный результат и его потребителей согласуют отдельно. Повтор работает в
сохранённом контексте операции; её удаление выполняют после окончания использования.

## Пакет и один вызов

Вход — один UTF-8 JSON с ровно `operation` и `input`.

| Поле `deliver.input` | Содержимое |
|---|---|
| `handoff` | Полный native Work envelope: `operation="handoff"`, `input` по действующему договору, `messages=[]`. |
| `recipient` | Объект с непустым `thread_id`; необязательный `host_id` передаётся, если выбран явно. |
| `message` | Непустое содержательное сообщение; передаётся с добавленным машинным контекстом. |

`request_id` берётся из `handoff.input.request_id`. Один ID связывает исходные
result/artifacts, сообщение и получателя. Готовый native пакет создаётся по
[актуальному шаблону результата](../workflows/batch-work.md#передача-результата-одной-командой)
его этапа. Пакет содержит собственные инженерные выводы и reviewer decision.

До передачи соберите `deliver` из этого готового файла:

```bash
"$poise_python" -B - "$native_packet" "$proxy_packet" "$recipient_thread" "$message" <<'PY'
import json
import sys
from pathlib import Path

source, destination, recipient, message = sys.argv[1:]
packet = {
    "operation": "deliver",
    "input": {
        "handoff": json.loads(Path(source).read_text(encoding="utf-8")),
        "recipient": {"thread_id": recipient},
        "message": message,
    },
}
Path(destination).write_text(json.dumps(packet, ensure_ascii=False), encoding="utf-8")
PY
```

Здесь готовится исходный смысловой вход. Сама передача выполняется одним вызовом
постоянного инструмента из выбранной копии:

```bash
env PYTHONPATH="$poise_root/src:$poise_root" \
  "$poise_python" -P -B -m poise handoff-proxy \
  --settings "$proxy_settings" < "$proxy_packet"
```

`--settings` — обязательный абсолютный путь. Команда сама ожидает native процесс,
читает его `response_path`, проверяет полный результат и уведомляет получателя.
Между запуском и итогом агенту не требуется переносить версии, paths или статусы.

Вызовите команду через execution host, возвращающий её terminal результат в том же
обращении. В проверенном Codex-сценарии выбранное ожидание команды позволило получить
итог одним внешним вызовом без промежуточного модельного `write_stdin`.
Настройки времени ожидания внешнего execution host остаются у этого host.

## Результат и частичные исходы

Stdout содержит один JSON; `exit 0` соответствует `delivered`, `exit 2` —
подтверждённому препятствию или неизвестному исходу. Полный ответ также сохраняется
по возвращённому `response_path`, когда рабочая область операции доступна.

| Поле результата | Значение |
|---|---|
| `schema` | `poise-agent-handoff-proxy-result-1`. |
| `status`, `phase` | `delivered`, `blocked` или `unknown`; фактическая граница `admission`, `handoff`, `notification` либо `complete`. |
| `request_id`, `task` | Исходная операция и Task; при раннем непригодном входе доступна только установленная часть этих сведений. |
| `handoff` | Фактически полученный native result, его `response_path`, известный exit и доступные полные stdout/stderr/runner references; либо null до запуска. |
| `notification` | Собственный статус, получатель, полный MCP response и transport references; либо null до отправки. |
| `error` | `code`, диагностическое `message` и применимое `continuation`; null при подтверждённой доставке. |
| `replayed` | Признак возврата сохранённого исхода для соответствующего повтора; факты внешних эффектов определяются отдельными подтверждениями. |
| `response_path` | Полный сохранённый результат прокси; при недоступной ранней конфигурации может быть null. |

`handoff.result` равен null, когда пригодный полный ответ получить не удалось.
При ошибке сохранения используйте `error` и фактически доступные raw references;
наличие адреса само по себе не подтверждает новые сохранённые bytes.

Native успешная передача освобождает Task и её зависимый worktree. Прежний
независимый worktree сохраняется с тем же ID в `release.before/after`.
Фактическая `progression`, source commit/tree и native receipt добавляются к
сообщению после `Контекст передачи:`. Остановка `task_acceptance_required`
сохраняет отдельную приёмку её владельцем.

Если native ответ недоступен, невалиден или относится к другому Task/request,
прокси сохраняет доступные raw facts и конкретное продолжение. Полный native
`handoff_blocked` сохраняет собственную диагностику. Непригодная форма `blocked`
даёт структурированный неизвестный исход с сохранением фактического ответа.

Отдельный неизвестный исход уведомления возможен после подтверждённого release.
Обрыв транспорта, недостоверный JSON/RPC/content, другой получатель и `isError`
сохраняют `unknown` и диагностику. В notification transport references доступны
полные отправленные frames, stdout/stderr и terminal receipt процесса.

## Продолжение и явное подтверждение

Повтор выполняет исходный caller с тем же `request_id` и неизменным `deliver`.
После подтверждённого complete возвращается сохранённый исход. Потерянное native
подтверждение восстанавливается тем же handoff request через существующего
идемпотентного владельца, сохраняя ранее выполненные действия и чужое владение.

Для неизвестного уведомления получите фактическое подтверждение у назначенного
получателя и передайте его основание через `resolve_notification`.
После независимого подтверждения полученного сообщения корректный пакет имеет вид:

```json
{
  "operation": "resolve_notification",
  "input": {
    "request_id": "handoff-review-1",
    "outcome": "delivered",
    "evidence": "Назначенный получатель подтвердил сообщение по сохранённой квитанции."
  }
}
```

После независимого подтверждения отсутствия доставки используйте:

```json
{
  "operation": "resolve_notification",
  "input": {
    "request_id": "handoff-review-1",
    "outcome": "not_delivered",
    "evidence": "Получатель и владелец транспорта подтвердили отсутствие отправленного сообщения."
  }
}
```

Подставьте исходный request ID и фактическое основание проверки, сохраните пакет
в рабочей области и выполните тот же CLI-вызов с ним на stdin.
`delivered` сохраняет ручное основание в `notification.resolution`, с
`notification.response=null`. `not_delivered` разрешает только недостающий send;
новый успешный MCP response сохраняется отдельно от этого решения.
Повтор того же resolution использует сохранённый факт его применения.

Если до dispatch недоступна выбранная конфигурация, восстановите её через
операторский owner и продолжите тот же intent. Подтверждённый native результат
остаётся сохранённым. Адресное `continuation` различает native rework/release,
проверку исходной Task и разрешение неизвестного уведомления.

## Проверка поставки и текущие условия

Реализован native-сценарий с явно выбранными CLI source/runtime и существующим
MCP stdio транспортом. Потребитель обеспечивает доступность команды и среды;
код использует их существующие владельцы. Scope настройки охватывает данную
операцию и её разрешённые повторы под исходным caller.

При проверке поставки наблюдают один внешний вызов, raw native/MCP операции,
фактическую release receipt, acknowledgement именно назначенного threadId и
реально полученное сообщение. Независимый проверяющий сверяет эти результаты.
Правильность JSON и ссылок проверяется отдельно от такой доставки.

Границы слоёв и материалов закреплены в
[архитектурном договоре](../architecture/boundaries.md#прокси-передачи-результата-между-агентами).
