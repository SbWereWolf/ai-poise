# Реестр требований

Обновлено: **2026-10-29**.

## SQL-миграции требований

Для изменения реестра используются два существующих маршрута:

1. `work.operation=requirements` создаёт полную пару буквальных SQL-файлов
   в рабочем дереве активной Task, затем применяет её штатным `yoyo-migrations`.
   Добавление, изменение и связи используют прежние пакеты `command` или `apply`.
2. Штатное завершение Task автоматически откатывает её исполненные миграции,
   склеивает последовательные DML-сегменты и проверяет итоговый накат, откат и
   повторный накат. Отдельное ручное вычисление итоговых INSERT/UPDATE не нужно.

Версионируются SQL и соответствующие `*.rollback.sql`, а не рабочая SQLite-база.
Миграции содержат прямые SQL-литералы и обычные метаданные yoyo: без импорта
приложения, ORM, Python callbacks и чтения старой БД при применении. Схема и данные
разделены уже в начальных `0001_requirements_schema` и `0002_requirements_data`.
В одной паре не смешивают DDL и DML верхнего уровня;
комментарии и пустые `;` этому не мешают. Не включайте BEGIN/COMMIT/ROLLBACK в тела
и не отключайте транзакции: каждым прямым и обратным телом управляет обычный yoyo.

Настройки задаются явно в project configuration. Пример фрагмента для проекта
Poise, а не значения по умолчанию:

```json
{"requirements_migrations":{"schema":"requirements-sql-1","schema_directory":"src/requirements-migrations/schema","data_directory":"src/requirements-migrations/data","initial_directory":"/absolute/poise/src/poise/infrastructure/requirements_sql"}}
```

`schema_directory` и `data_directory` — разные непересекающиеся относительные пути
внутри фактического Task worktree; они должны входить в разрешённую область этапа.
`initial_directory` задаётся отдельно: абсолютным путём либо относительно worktree.
Рабочие DB/lock берутся из `paths.requirements_database` и `paths.requirements_lock`.
Отсутствующая настройка или выход из области дают отказ до предметной записи.
Настройте маршрут до нового явного входа в Task; не подменяйте захваченную
конфигурацию посреди исполнения. Пустую БД сначала создают обычным yoyo из начальных
SQL-пар: открытие `RequirementsStore` само схему не создаёт.

Для явно выбранной пустой БД задайте `REQUIREMENTS_DATABASE_URL` и `INITIAL_SQL`
(каталог начальных пар), затем выполните выбранным yoyo:

```bash
yoyo --no-config-file --batch apply --database "$REQUIREMENTS_DATABASE_URL" "$INITIAL_SQL"
```

URL должен указывать на выбранный абсолютный DB-путь; специальные символы пути
кодируются по правилам URL. Это явная инициализация, не команда для существующей
legacy-БД.

Пакеты ниже отправляются через настроенный проектный
[work-вход](batch-work.md#ответственность). Пример добавления требования;
revision и выбранные ID должны соответствовать фактически прочитанному состоянию:

```json
{"operation":"requirements","input":{"request":{"operation":"command","input":{"request_id":"requirements-add-example","expected_revision":7,"operations":[{"id":"add","kind":"create","table":"requirements","row":{"id":"APP-EXAMPLE","level":"application","status":"current","text":"Приложение показывает источник результата расчёта."}}]}}},"messages":[]}
```

Изменение существующего требования использует тот же маршрут и `kind:update` из
[контракта CRUD](#command-и-количество-строк). Полный исходный SQL и обратная пара
публикуются до применения к рабочей БД. Чтение и точный повтор нормально завершённого
запроса не создают новую миграцию. Прежний standalone CLI сохраняет чтение, но
отклоняет запись, включая `command`, `apply`, `migrate` и `import_bootstrap`.

### Перенос из старой БД

Генератор `export` читает отдельный согласованный снимок каждой выбранной source/target,
включая WAL, и записывает самодостаточную DML-пару в data-каталог текущей Task.
Ни одна предметная БД при генерации не изменяется. Пример выбранного переноса:

```json
{"operation":"requirements","input":{"request":{"operation":"export","input":{"request_id":"transfer-example","source":"/absolute/legacy/requirements.sqlite","target":"/absolute/new/requirements.sqlite","mode":"selected","requirement_ids":["APP-EXAMPLE"],"output_directory":"/absolute/current-task/src/requirements-migrations/data"}}},"messages":[]}
```

`selected` переносит выбранные требования и необходимые зависимости: одинаковые
записи переиспользуются, отсутствующие вставляются, отличающиеся записи с тем же
ключом дают конфликт. История target сохраняется, его revision повышается и
добавляется квитанция переноса; полностью совпавший набор возвращает `unchanged`.
`full` требует `requirement_ids:[]` и пустую совместимую инициализированную target;
он переносит весь реестр, revision и историю запросов источника. Таблицы учёта yoyo
не копируются. Точный повтор использует прежнюю пару только при неизменном снимке
источника и ожидаемом состоянии target до/после; другое намерение или снимок
отклоняются. Существующие выходные пары не перезаписываются.

Генерация не означает применение. Для применения в настроенную рабочую БД
используется `request.operation:migrations` с `action:apply`, точными
`migration_ids`, `expected_revision` и `expected_state`. Сначала получите статус:

```json
{"operation":"requirements","input":{"request":{"operation":"migrations","input":{"action":"status"}}},"messages":[]}
```

В apply передаются `expected_revision` из `revision` и `expected_state` из `state`
этого свежего ответа.
Захваченный target должен совпасть с фактической БД; иной target требует отдельного
явного принятия поставки. Неисполненная экспортная пара остаётся поставляемым
артефактом и не выдаётся за пройденный цикл на другой БД.

В ERP старый `docs/foundations/requirements.sqlite`, его строки и разрешённые старые
записи физически сохраняются, пока агенты переносят требования этой командой.
Безопасное снятие Git tracking не удаляет рабочий файл. Физическое удаление
возможно только после прекращения всех старых writers и сверки оставшихся данных.

### Склейка и завершение Task

Порядок `DML1 → DML2 → DDL3 → DML4` становится
`DML1+2 → DDL3 → DML4`. Склеиваются исходные SQL-тела, без вычисления конечного
состояния и замены последовательности на итоговые INSERT/UPDATE. DDL-пары вместе
с метаданными зависимостей остаются побайтно неизменными. Дополнительные границы
сохраняют исходные ID, на которые ссылаются оставляемые DDL или чужие миграции.
Поэтому итоговых DML-пар может быть несколько даже внутри одного типа.
Обратные SQL-тела и порядок миграций идут строго в обратной последовательности.

Завершение автоматически выполняет original-down → final-up → final-down → final-up.
На успешных границах сравниваются реальные начальное/конечное состояния схемы,
ограничений, user_version, строк, revision, квитанций и штатных применённых ID.
Task завершается только после подтверждённого последнего наката; чужие миграции
и история не переписываются. Само чередование DDL/DML не является причиной отказа.

### Ошибка записи статуса yoyo

Тело SQL и регистрация применённого статуса могут фиксироваться раздельно.
Ошибка после COMMIT не доказывает откат тела. Сохраните диагностику, остановите
конкурирующих writers и сравните реальные данные/квитанции с SQL и учётом yoyo.
Не повторяйте неизвестный эффект вслепую и не удаляйте БД или служебные таблицы.

Следующие переменные должны быть явно заполнены для выбранной установки:
`REQUIREMENTS_DATABASE_URL`, `INITIAL_SQL`, `SCHEMA_SQL`, `DATA_SQL`, `MIGRATION_ID`.
Пути указывают на начальные и фактические Task-каталоги, ID — на проверяемую
миграцию. Команды существующего yoyo:

```bash
yoyo --no-config-file list --database "$REQUIREMENTS_DATABASE_URL" "$INITIAL_SQL" "$SCHEMA_SQL" "$DATA_SQL"
yoyo --no-config-file mark --database "$REQUIREMENTS_DATABASE_URL" --revision "$MIGRATION_ID" "$INITIAL_SQL" "$SCHEMA_SQL" "$DATA_SQL"
yoyo --no-config-file unmark --database "$REQUIREMENTS_DATABASE_URL" --revision "$MIGRATION_ID" "$INITIAL_SQL" "$SCHEMA_SQL" "$DATA_SQL"
```

`mark` допустим только после доказанного полного прямого эффекта при отсутствующем
статусе; `unmark` — после доказанного полного обратного эффекта при оставшемся
статусе. До подтверждения проверьте выбранный yoyo набор зависимостей. Эти команды
меняют учёт без исполнения SQL-тел. После ремонта снова проверьте реальное состояние
и штатный статус. Неизвестный исход остаётся неизвестным до установления фактов;
общая атомарность данных и ledger, автоматический ремонт и exactly-once через
этот разрыв не обещаются.

## Владение и явные пути

Версии, допустимое создание и границы backup собраны в [матрице
хранилищ](../architecture/storage-lifecycle.md#владельцы-и-версии); переносимая поставка и
настроенные абсолютные пути различаются
[явно](../architecture/storage-lifecycle.md#явные-пути-и-переносимая-поставка).

Requirements Registry хранит канонические System и Application требования и связи
System → Application в отдельной SQLite-базе. Требования Task, утверждённые цепочки
System → Application → Task и их исторический снимок принадлежат Task DB.

Каждое System или Application требование занимает отдельную строку `requirements`
с собственными `id`, `level`, `status`, `text`. Уровень различается полем `level`,
а не объединением нескольких требований в одном тексте. Каждая связь родителей
и приложений занимает отдельную строку `requirement_links`.

В конфигурации проекта явно заданы `paths.requirements_database` и
`paths.requirements_lock`. Относительный `paths.state` разрешается от каталога
окончательного project manifest; относительные Requirements-пути — от `paths.state`,
а не Git checkout. Абсолютные значения используются точно. Отсутствующие поля
отклоняются: скрытых значений по умолчанию и автоматического переноса данных нет.
Шаблоны новых проектов содержат оба поля.

Requirements DB допускается вне обслуживаемого репозитория или внутри него,
если DB/lock и сопутствующие mutable-файлы исключены из Git и не отслеживаются им.
В истории хранятся [SQL-пары](#sql-миграции-требований), а не бинарная рабочая БД.
У существующего legacy-файла tracking снимается с сохранением физического файла
и данных; это не разрешает его удаление.

Оба пути проверяются до создания или изменения Requirements-хранилища.
DB и lock должны отличаться друг от друга и от Task DB и lock как разрешёнными
путями, так и идентичностью существующих физических файлов. Сохраняется отделение
от хранилища telemetry.

Пример фрагмента явно выбранных путей, а не полный конфиг или значения по умолчанию:

```text
served repository           = /srv/app
final project manifest      = /srv/app/projects/demo/project.json
paths.state                 = state
paths.requirements_database = requirements.sqlite
paths.requirements_lock     = requirements.lock
```

Итоговые пути — `/srv/app/projects/demo/state/requirements.sqlite` и
`/srv/app/projects/demo/state/requirements.lock`. Во время подготовки проекта или
его обновления проверяются эти окончательные пути, а не временный каталог кандидата.

При отказе исправить явно заданные пути и устранить указанные пересечения хранилищ
через поддерживаемую настройку проекта. Обычные `manifest_edits` не разрешают менять
`paths.requirements_database` и `paths.requirements_lock`; отказ не даёт права
вручную менять managed config или переносить рабочую базу. Перенос `paths.state`
и изменение `paths.worktrees` принадлежат отдельным документированным операциям
с собственными условиями допуска. Порядок подготовки и ограничения обновления описаны в
[настройке проекта](../configuration/project-setup.md#назначение).

В доставленной конфигурации ai-poise Task-хранилище остаётся в `projects/ai-poise`,
а новая Requirements DB настроена отдельно:
`/home/sbwerewolf/workdata/poise-project-data/ai-poise/requirements.sqlite` и соседний
`requirements.lock`. Это конкретная внешняя настройка новой базы, не перенос Task DB
и не обязательное расположение для всех проектов.

## Предметные области и миграция схемы

Requirements DB использует schema 2. Новая пустая база инициализируется отдельными
буквальными DDL/DML-парами через обычный yoyo, не при открытии реестра.
Обычное открытие schema 1 отклоняется: автоматического обновления нет.
Task DB и исторические снимки требований Task этой миграцией не изменяются.
Для поддерживаемого исторического перехода пакет `migrate` с пустым input
передаётся через активную Task в [work-обёртке](#sql-миграции-требований).

Добавлены пять таблиц: `domain_areas`, `domain_entities`, `domain_actions`,
`requirement_entities`, `requirement_actions`. Область содержит стабильный `id`,
уникальное бизнес-имя и определение. Сущность и действие содержат стабильный `id`,
обязательную область `domain_id`, бизнес-имя, имя для кода и определение.
Идентичность имени не зависит от изменяемого написания; бизнес-имя и имя для кода
уникальны внутри области, но могут совпадать в разных областях. Регистр значим.
Идентификаторы и имена не допускают окружающих пробелов; обязательные строки
не могут быть пустыми или состоять только из пробельных символов.

Связь требования с сущностью или действием содержит требование, область и имя.
Составной внешний ключ запрещает указать имя из другой области. Повтор одной
связи запрещён; отсутствующие родители и удаление используемого родителя
отклоняются сразу. Одно System или Application требование может использовать
имена нескольких областей. Привязки необязательны: требование может не иметь
имён, область — имён, имя — связей с требованиями. Принадлежность имени области
обязательна. Миграция оставляет все пять таблиц пустыми и ничего не угадывает.
CRUD словаря и операции со связями доступны через [пакетный CRUD](#пакетный-crud).

Явная миграция существующей базы выполняется через настроенный work-вход
активной Task с выбранной Requirements DB:

```json
{"operation":"requirements","input":{"request":{"operation":"migrate","input":{}}},"messages":[]}
```

Использовать настроенный интерпретатор и установленный код Poise. `input` должен
быть пустым объектом; ошибочный ввод и отсутствующая база не создают новую БД.
Известная schema 1 обновляется в schema 2, ответ:
`{"status":"migrated","from_version":1,"to_version":2,"changed":true}`.
Повтор на schema 2 возвращает `from_version: 2`, `changed: false` без изменения
данных. Другие версии отклоняются. Поддержка work-записи внешними прокси,
включая `req-ctl`, проверяется по их отдельному контракту.
Номер версии сам по себе не подтверждает принадлежность файла: до DDL
проверяются таблицы, колонки, ключи и внешние связи поддержанной schema 1;
до успешного повтора — структуры schema 2. Посторонний, повреждённый или
неполный файл отклоняется без изменения схемы, версии и данных. Дополнительные
посторонние таблицы и представления корректной базы сохраняются. Проверка
пяти новых таблиц сопоставляет определения с историческим DDL этой версии,
включая CHECK и collation. На таблицах Requirements проверяются все уникальные
индексы: допустимы исторические сигнатуры ключей, без частичных условий и
выражений, с `BINARY`. Дополнительные ограничения уникальности на этих таблицах
не считаются посторонними объектами и отклоняются; объекты других таблиц
не изменяются.
Для этого замкнутого DDL допускаются различия пробелов и регистра синтаксиса,
но не произвольные переписанные выражения или варианты с quoted identifiers.
Это не общий анализатор эквивалентности SQL. Проверка
структуры не является полным аудитом содержимого либо защитой от намеренной
подмены файла; автоматического ремонта нет. При отказе проверить правильность
выбранного manifest и его DB-пути, не удалять базу или lock-файлы.

Владелец использует настроенные DB/lock, проверяет захваченное исходное состояние
и публикует отдельную буквальную DDL-пару исторического перехода в schema-каталог
Task. Её тело исполняет обычный yoyo. Четыре прежние таблицы, требования, связи,
revision и исторические квитанции сохраняются. Ошибка внутри транзакции DDL
откатывает структуры и номер версии вместе; раздельная ошибка записи статуса
имеет [собственный порядок восстановления](#ошибка-записи-статуса-yoyo).

При обновлении нескольких проектов сначала установить проверенный код, затем
выполнить миграцию каждого явно выбранного manifest. До обновления конкретной
базы обычные запросы к её schema 1 отклоняются; это не поставка без простоя.
Каждая база — отдельная транзакция, общего атомарного обновления нескольких
SQLite-файлов нет. Сравнивать прежние таблицы в согласованных read snapshots,
учитывая возможные независимые записи. После каждого перехода проверить версию,
сохранность данных, пустоту новых таблиц, integrity/FK и повторный запуск.
При отказе сохранить список успешно обновлённых и оставшихся баз, устранить
причину и продолжить через тот же API. Возврат старого Git commit сам по себе
не возвращает совместимость уже обновлённой базы; обратной миграции нет.

## Статусы и полнота связей

Требования имеют ровно три предметных уровня: **System → Application → Task**. Дополнительные уровни
иерархии не вводятся. Любые тематические, продуктовые, компонентные или организационные подборки
являются виртуальной группировкой (tags/views/collections) и не меняют эту сквозную цепочку.
Требование Task может обнаружить необходимость нового Application или System requirement: discovery
снизу вверх допустим, но сохранённая связь всё равно строится через все три уровня. Если агент не
может обоснованно состыковать требование с существующей цепочкой или понять, какой новый предок
нужен, он не выдумывает смысл и задаёт вопрос.

`current` означает действующее требование; `future` участвует в анализе и планировании, но не
добавляется автоматически к проверкам текущего соответствия. В целевой модели `future` может
использоваться как **проектируемое требование**. Для проектируемой цепочки допускается явно
типизированное пустое звено **любого из трёх уровней** там, где соответствующая формулировка ещё не
создана или возможность ещё не разработана. Например, проектируемый System requirement может быть
связан через пустые Application/Task звенья, а Task requirement — через пустой Application/System
предок. Пустое Task-звено не создаёт исполняемую Task. Такое пустое требование — не четвёртый
уровень и не доказательство выполнения: это адресуемый placeholder конкретного уровня, который
сохраняет сквозную связь `System → Application → Task` и показывает незакрытый gap. Исполнимый
формат описан в разделе [явных пустых проектируемых звеньев](#явные-пустые-проектируемые-звенья):
`status: "future"`, `text: ""` и прежний типизированный ID. Используется публичный владелец
Requirements, не ручная запись БД.

`obsolete` сохраняется исторически, исключается из нового покрытия и не может быть основанием новой
Task. Изменение текста или статуса не переписывает старые снимки. Когда проектируемый placeholder
позже получает содержательное требование, новая revision/chain не переписывает исторический Task
snapshot.

Связи System → Application имеют кратность многие-ко-многим. Для `current` цепочек каждый
Application обязан иметь содержательного неустаревшего System-родителя, а каждый используемый Task
requirement — содержательную Application-связь. Проектируемая цепочка может явно содержать
placeholder на любом отсутствующем уровне; такой placeholder отображается как gap и не засчитывается
как current coverage. Каждый неустаревший содержательный System должен быть распределён хотя бы в
один Application либо явно оставаться проектируемым gap. `coverage` и `gaps` показывают обе стороны
разрывов. `coverage` с `mode: "current"` учитывает только действующие содержательные узлы; обычный
анализ включает также `future` и проектируемые placeholders в исполнимом API.

## Декларативный API и согласование

Команда `python -m poise requirements --config /absolute/project.json` читает один
JSON-пакет из stdin. Формат: `{"operation": "query", "input": {"queries": [...]}}`.
Каждый запрос имеет уникальный `id` и `kind`: `registry`, `coverage`, `gaps`, `chain`
(с `requirement_id`) или `plan_task` (с `task_requirements`). Число запросов и
требований плана ограничено конфигурационным `batch.max_items`.

Пример планирования без изменения реестра:

```json
{"operation":"query","input":{"queries":[{"id":"plan","kind":"plan_task","task_requirements":[{"text":"Сохранить результат задачи с происхождением требований.","applications":["APP-TRACE"]}]},{"id":"coverage","kind":"coverage","mode":"current"}]}}
```

План возвращает `status`, `gaps`, `chains` и `snapshot`. При отсутствующем Application/System он
предлагает явный текст недостающего требования, но сам не утверждает и не записывает его. Если
планирование обнаруживает ещё не сформулированное звено любого уровня, API позволяет явно выбрать
typed placeholder соответствующего уровня вместо выдуманной формулировки. Для действующего
(`current`) обязательства placeholder не заменяет требование; для явно проектируемого (`future`)
обязательства он сохраняет сквозную цепочку и видимый gap. При **новом** согласовании цепочки
показать пользователю все содержательные тексты, статусы и пустые проектируемые звенья System →
Application → Task, а не только идентификаторы. Уже данное точное согласие сохраняется в
`requirements_agreement` Task и не требует нового решения пользователя на каждом обычном этапе или
при согласованном исполнителем и независимым проверяющим restart без изменения этих цепочек. `ready`
у плана означает структурную полноту допустимой цепочки, а не согласие пользователя и не реализацию
проектируемого требования.

Изменения отправляются одним `apply` внутри [work-обёртки](#sql-миграции-требований)
с `request_id`, `expected_revision` и
`operations`. Операции: `put_requirement` с точными `id`, `level`, `status`, `text`
и `link` с `system`, `application`. Весь пакет применяется атомарно; конфликт
revision требует нового чтения. Точный повтор request_id возвращает сохранённый
результат, изменённый пакет с тем же идентификатором отклоняется. Прямое редактирование
таблиц, вторая каноническая JSON-копия и автоматические согласования не допускаются.

Запись построчная: новое требование вставляется, изменённое требование обновляется
с сохранением его идентичности, новая связь добавляется отдельно. Неизменённые
требования и существующие связи не перезаписываются; удаления и пересоздания
реестра для этих операций нет. Валидация всего пакета предшествует записи.
SQL-ошибка откатывает изменения строк, revision и receipt вместе. Новый допустимый
запрос, включая пакет с прежними значениями, увеличивает revision и сохраняет
receipt; точный повтор уже принятого запроса возвращает исторический результат
без новой записи и изменения revision.

## Публикация и исторический снимок

В публикуемую Task передаётся `requirements_snapshot` из структурно допустимого
плана. Дополнительное решение пользователя — самостоятельный факт: отсутствие
`requirements_agreement` или значение `null` означает, что такого решения нет,
а не отказ пользователя. Само отсутствие не блокирует подготовленную Task и не
заменяется выдуманным согласием. Переданный ненулевой объект
`requirements_agreement: {"accepted": true, "chains": [...]}` проверяется по точным
полным цепочкам. Неверный тип, неполный объект, отказ или несовпадение цепочек
отклоняются; ложные значения не приравниваются к отсутствию.

Requirements gate проверяет снимок независимо от дополнительного решения; Task
сохраняет оба факта в metadata в той же транзакции, что и публикацию. Обычная Task
и пакет Sprint проходят одну границу проверки: отсутствующий, устаревший или
структурно неверный снимок отклоняется до записи Task. Отдельная явная операция
публикации согласования по-прежнему требует действительного подтверждения полных
цепочек и не допускает перезаписи уже опубликованного снимка. Готовность Task не
даёт полномочий на пересмотр требований, приёмку или интеграцию результата.

Поздняя правка живого реестра не меняет смысл опубликованной Task. Точный повтор создания использует
сохранённую идентичность запроса. Обычное исполнение использует замороженный requirements
snapshot/agreement. Если исполнитель доказывает, что текущие требования делают успешное продолжение
невозможным или обход неадекватен, он согласует restart с независимым проверяющим. Авторизованный
restart может сформировать новый согласованный requirements snapshot: policy задаёт поля по
умолчанию, а иной точный набор Task-полей проверяющий фиксирует в решении. Старое согласие и старые
chains остаются историей и не выдаются за актуальные. Изменение project/harness rules требует
отдельного согласия пользователя. Существующие исторические Task без снимка не дополняются
выдуманной цепочкой автоматически.

При повторном `ready` после разрешённого restart Task сравнивает свой текущий
snapshot/agreement с сохранённым. Совпадение направляет проверку в исторический
контекст: последующий дрейф живого Registry не переопределяет Task. Изменённый
контекст, в том числе у Task без `planning_revision`, проходит планирование и
проверку полных цепочек против живого Registry; отсутствующее дополнительное
решение остаётся отсутствующим, а переданное решение проверяется строго. Перед публикацией
проверяется, что реестр не изменился после подготовки. При обнаруженном дрейфе
Task остаётся в прежнем newborn-состоянии, а независимое изменение Registry не
откатывается. При успехе прежний snapshot/agreement сохраняется в истории restart,
текущий контекст заменяется в той же Task-транзакции, что и промоция; отсутствующее
или несогласованное поле не заменяется историческим значением молча.

Выбор существующей Task объектом только с `id` — продолжение сохранённого состояния,
не новое предложение договора. Текущая проекция методов может законно отличаться
от первоначального договора. Она не подставляется в повторную проверку полного
контракта; проверка явно переданного full/canonical договора остаётся строгой.
[Публичный выбор Task](batch-work.md#выбор-существующей-задачи-по-id).

## Однократный импорт утверждённой поставки

Утверждённый документ схемы `requirements-bootstrap-1` импортируется операцией
`import_bootstrap` с точными `path` и `request_id` в первоначально пустой реестр,
через [work-обёртку активной Task](#sql-миграции-требований).
Повтор того же запроса идемпотентен. Текст, статусы `future` и связи сохраняются;
импорт не объявляет будущие требования реализованными. После проверки чтением из
Requirements DB временный документ удаляется в рамках завершения этой операции.
В этой поставке импорт уже завершён: 6 требований и 4 связи сохранены в ревизии 1;
точный повтор и полное чтение проверены перед удалением временных файлов в задаче `0067`.
Реестр, история запросов и квитанция импорта входят в полную резервную копию.

Исторический переносимый архив этой поставки содержал снимок
`projects/ai-poise/database/requirements.sqlite`; это описание прежней поставки.
Текущий маршрут создаёт явно выбранную новую БД начальными SQL-парами и переносит
данные [самодостаточной миграцией](#перенос-из-старой-бд), сохраняя старый файл.
Рабочая БД не версионируется. Оба Requirements-пути задаются явно при поддерживаемой
настройке проекта; обычные `manifest_edits` не меняют
`paths.requirements_database` и `paths.requirements_lock`. Документированный перенос
`paths.state` сохраняет собственные условия допуска.
Восстановление архива само по себе не является разрешением перезаписи рабочей базы:
назначение должно быть новым, контрольная сумма проверена. Не создавать пустой
реестр вместо импортированного снимка. Квитанция импорта хранится в материалах `0106`.

## Конкурентная запись

Query читает согласованный транзакционный snapshot. Для записи активная Task
захватывает реальное состояние, готовит буквальную SQL-пару и проверяет revision
и состояние перед штатным применением yoyo. Project fence и настроенный
Requirements lock ограничивают конкурирующую запись; они не объединяют Task DB,
предметную БД и служебный учёт yoyo в одну транзакцию.

Предметные строки, revision и квитанция запроса входят в одно SQL-тело и его
обычную транзакцию. Применённый статус yoyo может фиксироваться отдельно.
Для нормально завершённого запроса точный replay возвращает исторический
response без новых файлов и эффекта. Он сохраняет весь исходный пакет:
request ID, expected revision и операции. Иной intent с тем же ID отклоняется;
новый запрос с устаревшей revision требует нового чтения и согласования.

Ошибка до COMMIT откатывает SQL-тело. Отказ после подтверждённого COMMIT не
означает отсутствие эффекта и не разрешает слепой повтор: сначала восстановите
известное состояние через [обычные средства yoyo](#ошибка-записи-статуса-yoyo).
Удаление DB/lock/квитанций не является восстановлением. Формат предметных
CRUD-ошибок описан [отдельно](#ошибки-crud-и-восстановление).

Перед публикацией Task native `SqliteRegistrySnapshotProvider` сравнивает семантическую
идентичность всего захваченного канонического реестра: `id/level/status/text` требований
и связи System/Application. Одна лишь новая CRUD revision из-за правок представления
не становится veto создания Task; семантические изменения реестра могут дать отказ,
даже если изменённое требование не названо в цепочке этой Task. Provider выбран явно
в runtime; библиотечный pure callable backend — отдельный явный способ композиции.
Он не подставляется скрыто вместо native SQL provider.

Task DB хранит собственный исторический snapshot/agreement, а Requirements DB — живой
реестр. Их сверка не создаёт общей распределённой транзакции и не гарантирует единый
момент записи двух файлов. Исторические replay/restart подчиняются владельцу
[опубликованного снимка](#публикация-и-исторический-снимок).

## Явные пустые проектируемые звенья

System/Application placeholder создаётся обычным `put_requirement`: прежние `id`,
`level`, `status: "future"`, `text: ""`. Нового уровня и отдельного placeholder ID
нет. Связи задаются прежним `link`. `plan_task` дополнительно допускает у элемента
`task_requirements` явное `status: "future"` и пустой `text`; такой элемент —
проектируемый узел snapshot, а не созданная исполнимая Task.

Каждый пустой узел виден как `projected_placeholder` с уровнем; plan возвращает
`status: "gaps"` даже при полной связности. `gaps` реестра показывает и связанные
пустые System/Application. Пустой current или текст из одних пробелов отклоняется.
Заполнение текста и смена статуса используют тот же ID, поэтому связи не теряются.
Старые сохранённые snapshots не меняются от последующего заполнения live реестра.

## Пакетный CRUD

Standalone вход для чтения — выбранный интерпретатор с установленным Poise:
`python -B -m poise requirements --config /absolute/project.json`.
stdin содержит один UTF-8 JSON-пакет, stdout — один JSON и перевод строки.
Успех имеет exit 0, отказ — exit 2. Query не требует владения Task или bootstrap.
Command отправляется внутри [work-обёртки](#sql-миграции-требований) активной
Task и создаёт/применяет SQL-пару; standalone запись отклоняется.
Используются явно настроенные Requirements DB/lock, schema 2,
`batch.max_input_bytes` и `batch.max_items`, а не новый профиль.
Лимит `M = batch.max_items` ограничивает длину пакета (1…M), списка `in` (0…M)
и размер страницы (1…M). Лимит байтов применяется к полному входу.
Булевы значения не заменяют целые числа; строки должны содержать Unicode scalars,
не отдельные surrogate code points. Неизвестные поля этих пакетов отклоняются.

CRUD относится только к следующим сущностям и публичным колонкам:

| Таблица | Колонки |
|---|---|
| `requirements` | `id`, `level`, `status`, `text` |
| `domain_areas` | `id`, `business_name`, `definition` |
| `domain_entities` | `id`, `domain_id`, `business_name`, `code_name`, `definition` |
| `domain_actions` | `id`, `domain_id`, `business_name`, `code_name`, `definition` |

Все значения колонок — строки. `id` неизменяем; у требования неизменяем также
`level` (`system` или `application`). Статусы: `current`, `future`, `obsolete`.
Пустой `text` допустим только для `future`; пробельный текст не допустим.
ID требования не состоит только из пробелов, не содержит `/`, `\`, NUL
и не равен `.` или `..`.
Для словаря ID, имена и `domain_id` непусты без окружающих Unicode-пробелов;
`definition` не состоит только из пробелов, но может иметь их по краям.
Бизнес-имя области уникально; бизнес-имя и code name сущности/действия уникальны
внутри области, отдельно для каждого вида. Сравнение `BINARY`, регистр значим.
Область у имени обязательна. Связи имён и требований необязательны.

Service tables, история квитанций и Task snapshots через CRUD недоступны.
Специализированные `query` (`coverage`, `registry`, `gaps`, `chain`, `plan_task`),
`apply`, `migrate` и импорт сохраняют собственные контракты, не являются aliases CRUD.

### Query и фильтры

```json
{"operation":"query","input":{"queries":[{"id":"q","kind":"entities","table":"domain_areas","filter":{},"page":{"limit":2,"after":null}}]}}
```

Поля entity Query ровно `id`, `kind`, `table`, `filter`, `page`.
`id` — непустая строка, уникальная в пакете, не ID записи.
Фильтр — AND по публичным колонкам: `{"id":{"eq":"D1"}}` или
`{"id":{"in":["D1","D2"]}}`. Для каждой колонки ровно один оператор;
значения — строки, список `in` не содержит повторов. `{}` выбирает все строки,
`{"id":{"in":[]}}` — ни одной. Это действует и для изменений: пустой фильтр
не означает отказ или безопасный no-op. SQL, выражения и произвольная сортировка
не поддерживаются.

Ответ: `{"status":"read_only","revision":7,"results":[{"id":"q","value":{"rows":[],"next":null}}]}`.
Все Query, включая смешанные специализированные, читают один snapshot.
Ошибка любого элемента отклоняет весь пакет без частичного `results` и записей.

`page` имеет ровно `limit` и `after`. Первая страница: `after: null`.
Следующая: передать полученный `next` без изменения. Строки упорядочены по
физическому первичному ключу (`BINARY`); offset не используется. `next` содержит
ключ последней возвращённой строки только при наличии следующей строки.
Курсор имеет ровно `revision`, `selection`, `key` (массив строк PK).
Selection включает `kind`, `table`, `filter` либо `a`, `b`; не включает ID Query
и размер страницы. Порядок ключей объекта и значений `in` незначим, но `eq` не
равен одноэлементному `in`; направление A/B значимо. Пропущенный фильтр B
нормализуется в `{}`. После проверки формы/Unicode/revision курсора устаревшая
revision имеет приоритет перед проверкой selection/key. В текущей revision
проверяются selection, длина/типы ключа и наличие ключа в выбранных строках.
Изменить размер страницы допустимо; продолжить старую revision — нет.

### Связи и операнды

| Таблица | Endpoints | Колонки и порядок PK |
|---|---|---|
| `requirement_links` | `system`, `application` | `system_id`, `application_id` |
| `requirement_entities` | `requirement`, `entity` | `requirement_id`, `domain_id`, `entity_id` |
| `requirement_actions` | `requirement`, `action` | `requirement_id`, `domain_id`, `action_id` |

A и B обозначают разные endpoints одной таблицы; разрешены оба направления.
Endpoint `system`/`application` автоматически ограничивает уровень требования.
A имеет ровно `endpoint`, `filter` и обязан выбрать **ровно одну** сущность,
даже когда B пуст. B имеет `endpoint` и необязательный `filter`: отсутствие
фильтра выбирает все допустимые сущности B; `null` не заменяет отсутствие.
B может выбрать 0, 1 или N строк. Каждая операция — 1:1 или 1:N, не N:M;
это не запрет разных сохранённых связей между несколькими требованиями и именами.
`domain_id` связи берётся из выбранного имени, не угадывается из требования.

```json
{"operation":"query","input":{"queries":[{"id":"links","kind":"relations","table":"requirement_entities","a":{"endpoint":"requirement","filter":{"id":{"eq":"A3"}}},"b":{"endpoint":"entity"},"page":{"limit":2,"after":null}}]}}
```

Relation Query имеет ровно `id`, `kind`, `table`, `a`, `b`, `page` и возвращает
сохранённые связи, не кандидатов для связывания. Порядок PK не меняется при
перестановке endpoints.

### Command и количество строк

```json
{"operation":"command","input":{"request_id":"example-create-1","expected_revision":7,"operations":[{"id":"create","kind":"create","table":"domain_areas","row":{"id":"D9","business_name":"Shipping","definition":"Shipping domain."}}]}}
```

`input` имеет ровно `request_id`, `expected_revision`, `operations`.
Непустой request_id определяет intent, expected_revision — наблюдённое целое >= 0.
Виды операций и их точные поля:

- `create`: `id`, `kind`, `table`, `row`; row содержит все публичные колонки сущности.
- `update`: `id`, `kind`, `table`, `filter`, `changes`; changes — непустое подмножество колонок без
  `id`.
- `delete`: `id`, `kind`, `table`, `filter`.
- `link` / `unlink`: `id`, `kind`, `table`, `a`, `b` с указанными выше операндами.

Примеры отдельных элементов `operations`, не самостоятельные пакеты.
Связи предполагают существующие требование A3 и сущность E9; D9 создаётся
предыдущим примером. Revision 7 и эти ID иллюстративны: для рабочего пакета
нужны фактически прочитанная revision и явно выбранные существующие записи.

```json
[
  {"id":"edit","kind":"update","table":"domain_areas","filter":{"id":{"eq":"D9"}},"changes":{"definition":"Updated shipping domain."}},
  {"id":"link","kind":"link","table":"requirement_entities","a":{"endpoint":"requirement","filter":{"id":{"eq":"A3"}}},"b":{"endpoint":"entity","filter":{"id":{"eq":"E9"}}}},
  {"id":"unlink","kind":"unlink","table":"requirement_entities","a":{"endpoint":"requirement","filter":{"id":{"eq":"A3"}}},"b":{"endpoint":"entity","filter":{"id":{"eq":"E9"}}}},
  {"id":"remove","kind":"delete","table":"domain_areas","filter":{"id":{"eq":"D9"}}}
]
```

Пакет исполняется по порядку в одной транзакции: следующий элемент видит предыдущий.
Форма всех элементов проверяется до эффектов, state/integrity — при исполнении.
Update проверяет полную итоговую строку. Удаление используемого родителя отклоняется;
сначала явно unlink/delete зависимых строк. Неявных cascade, replace или усечения
числа выбранных изменений до M нет. Отказ до подтверждённого COMMIT откатывает
весь пакет и его receipt/revision; исключение cleanup описано ниже.

Ответ:
`{"status":"applied","revision":8,"replayed":false,"results":[{"id":"create","affected_rows":1}]}`.
Результаты следуют исходному порядку. Считаются только реальные предметные изменения:
вставки, изменённые строки, удаления, новые связи и удалённые существующие связи.
Повторное связывание, отсутствующая связь и update без изменения дают 0.
Первый успешный пакет повышает revision **один раз**, даже если все counts равны 0.

Точный повтор известного request_id возвращает исходные revision/counts с
`replayed: true` без исполнения, даже после последующих изменений базы.
Replay проверяется до сравнения expected_revision с текущим состоянием.
Другой intent с тем же ID даёт `request_conflict`, включая конфликт с `apply`.
Новый ID с устаревшей revision даёт `revision_conflict`: требуется новое чтение
и решение, а не автоматическая замена revision в старом намерении.

### Ошибки CRUD и восстановление

```json
{"status":"rejected","reason":"Invalid Requirements CRUD item.","error":{"code":"invalid_item","item_index":0,"item_id":"bad"}}
```

Коды: `invalid_packet` (пакет, границы, IDs), `invalid_item` (форма/строка/таблица),
`invalid_filter`, `invalid_cursor`, `stale_cursor`, `operand_cardinality`,
`immutable_field`, `integrity_conflict`, `revision_conflict`, `request_conflict`,
`store_error`. Индекс элемента нулевой; контекст конкретного элемента заполняется
при его проверке/исполнении. Для общей ошибки пакета/revision/request/хранилища
вне элемента оба поля контекста `null`. Ответ не раскрывает SQL или внутренние пути.
Admission-ошибки CLI/config и старые специализированные запросы сохраняют прежний
формат `status`/`reason`; structured error не обещается для всех отказов Poise.

`store_error` описывает предметный storage-отказ; admission и ошибки применения
миграций могут иметь другой `status`/`reason`. После подтверждённого COMMIT данные
и receipt могут сохраниться несмотря на отказ cleanup или записи статуса yoyo.
Сначала установите фактический эффект и восстановите согласованный учёт через
[обычные средства](#ошибка-записи-статуса-yoyo); точный повтор не обещается как
автоматический ремонт этого разрыва. До COMMIT транзакционная ошибка не публикует
частичный пакет. Не удаляйте DB/locks/receipts ради повторного запуска.

### Пример чтение-анализ-изменение

Запустить следующий Python-фрагмент выбранным интерпретатором, передав аргументы:
абсолютный путь того же интерпретатора, абсолютный manifest, ID существующей области,
явно выбранное новое определение и уникальный request_id. Пример только читает
реестр и выводит work-пакет изменения выбранной области после анализа значения.
Он не отправляет этот пакет и не выполняет запись. Для применения передайте
выведенный пакет в настроенный work-вход того же проекта с активной Task и
полномочием на изменение, как описано в [SQL-маршруте](#sql-миграции-требований).

```python
import json
import subprocess
import sys

python, config, domain_id, definition, request_id = sys.argv[1:]

def query(packet):
    run = subprocess.run(
        [python, "-B", "-m", "poise", "requirements", "--config", config],
        input=json.dumps(packet, ensure_ascii=False), text=True,
        encoding="utf-8", capture_output=True, check=False,
    )
    result = json.loads(run.stdout)
    if run.returncode != 0:
        raise SystemExit(json.dumps(result, ensure_ascii=False))
    return result

selected = {"id": {"eq": domain_id}}
read = query({"operation": "query", "input": {"queries": [{
    "id": "domain", "kind": "entities", "table": "domain_areas",
    "filter": selected, "page": {"limit": 1, "after": None},
}]}})
rows = read["results"][0]["value"]["rows"]
if len(rows) != 1:
    raise SystemExit("Expected exactly one selected domain.")
if rows[0]["definition"] == definition:
    print(json.dumps({"status": "unchanged", "revision": read["revision"]}))
else:
    packet = {"operation": "command", "input": {
        "request_id": request_id, "expected_revision": read["revision"],
        "operations": [{"id": "edit", "kind": "update", "table": "domain_areas",
                        "filter": selected, "changes": {"definition": definition}}],
    }}
    print(json.dumps({"operation": "requirements", "input": {"request": packet},
                      "messages": []}, ensure_ascii=False))
```

Отказ чтения завершает пример без скрытого retry. Перед отдельной отправкой
сохраните исходный выведенный work-пакет в материалах операции. Отказ применения
восстанавливается по [фактическому состоянию](#ошибка-записи-статуса-yoyo);
повторный запуск всего сценария чтение/анализ не является точным replay.
