# Собственное состояние Poise

Актуально: 2026-10-28.

`bin/poise-state` подготавливает и читает собственное SQLite-хранилище Poise.
Поставка содержит самодостаточную миграцию пустого формата `0` в формат `1`.
Повторная подготовка готового формата сохраняет данные и возвращает пустой список
применённых версий. Хранилища задач и установленные соседние приложения для этих
операций не требуются.

Вход использует стандартную библиотеку CPython 3.13 с SQLite. Проверенная среда:
CPython 3.13.15, SQLite 3.53.1. Выберите исполняемый файл этого Python явно.
Переменная `POISE_PYTHON` ниже принадлежит примеру запуска; приложение получает
конфигурацию только через `--config PATH`.

## Подготовка и чтение

Из корня поставки, в Bash, с выбранным `POISE_PYTHON`:

```bash
poise_python="${POISE_PYTHON:?Select the CPython 3.13 executable}"
poise_app="$(pwd)/apps/poise"
poise_example_root="$(mktemp -d)"
mkdir -p "$poise_example_root/config"
cp "$poise_app/config/state.example.json" "$poise_example_root/config/state.json"
cd "$poise_example_root"
for operation in prepare status prepare; do
  printf '{"schema":"poise-state/v1","operation":"%s","input":{}}\n' "$operation" |
    "$poise_python" -I -S -B "$poise_app/bin/poise-state" \
      --config "$poise_example_root/config/state.json"
done
printf 'State directory: %s\n' "$poise_example_root"
```

Все три вызова завершаются кодом `0`, `status="ok"`, `version=1` и пустым
stderr. `applied_versions` последовательно равен `[1]`, `[]`, `[]`. Рабочая база
находится в `state/sessions.sqlite` внутри показанного временного каталога.
Этот каталог сохраняет результаты примера; для постоянной работы подготовьте
такой же собственный конфиг в выбранном оператором каталоге.

Поставка приложения включает `bin`, `state.py`, `domain`, `application`,
`infrastructure` и `migrations`. [Пример настроек](../config/state.example.json)
служит исходным материалом собственного рабочего конфига. Пути приложения и
конфига передаются явно, поэтому вызывающий может работать из своего каталога.

## Конфигурация

Конфиг — один UTF-8 JSON-объект. Все перечисленные поля обязательны:

| Поле | Тип и значение |
| --- | --- |
| `schema` | Строка `poise-state-config/v1` |
| `database` | Непустая строка пути собственной базы без NUL |
| `target_version` | Целое число `1` |
| `limits.packet_bytes` | Положительное целое число; сырой предел входного пакета в байтах |
| `limits.sqlite_timeout_seconds` | Конечное число не меньше нуля; время ожидания необходимой операции SQLite |

Булевы значения отделены от чисел. Значение таймаута `0` допустимо. Пример
задаёт `packet_bytes=65536` и `sqlite_timeout_seconds=0`.

Относительный `PATH` аргумента `--config` относится к каталогу вызова.
Относительный `database` относится к каталогу конфигурации; абсолютный путь
используется непосредственно. Результат сообщает разрешённый абсолютный путь.
При `prepare` создаются необходимые родительские каталоги базы. `status` открывает
существующую базу только для чтения. Неизвестные настройки игнорируются при
исполнении; исходный конфигурационный файл сохраняется целиком.

## Пакеты и результаты

Вызывающий отправляет один UTF-8 JSON-объект на stdin и закрывает поток.
Пакет содержит ровно `schema`, `operation`, `input`:

```json
{"schema":"poise-state/v1","operation":"prepare","input":{}}
```

Операция `status` имеет такой же пустой `input`. Ограничение `packet_bytes`
считает исходные байты вместе с пробелами и завершающим переводом строки.
Пакет ровно на границе допускается. Проверка пакета предшествует открытию базы.

Ответ — один JSON-объект в UTF-8 с завершающим LF, ровно с пятью полями:

| Поле | Содержание |
| --- | --- |
| `schema` | `poise-state/v1` |
| `status` | `ok`, `unavailable` или `rejected` |
| `result` | При успехе объект `database`, `version`, `applied_versions`; при отказе `null` |
| `error` | При успехе `null`; при отказе объект `code`, `details`, `action` |
| `evidence` | Пустой массив для этих операций |

`ok` соответствует exit code `0`, `unavailable` — `1`, `rejected` — `2`.
Обработанные исходы оставляют stderr пустым. `version` — наблюдённое целое число,
`applied_versions` — список фактически применённых целых версий.

## Версии и обычное продолжение

| Состояние собственной базы | `prepare` | `status` |
| --- | --- | --- |
| Путь ещё не создан | Создаёт пустую схему `1`, `applied_versions=[1]` | `state_not_found`, путь остаётся отсутствующим |
| Пустой собственный формат `0` | Атомарно подготавливает `1`, `applied_versions=[1]` | `state_not_prepared`, версия остаётся `0` |
| Готовый формат `1` | Сохраняет факты, `applied_versions=[]` | Возвращает версию `1`, `applied_versions=[]` |
| Другая версия собственного состояния | `state_incompatible` с фактической версией | `state_incompatible` с фактической версией |

Исторический [артефакт `v1.prepare(connection)`](../migrations/v1.py) содержит
собственные определения схемы и исполняется независимо от текущих классов
приложения. Вызывающий завершает свою транзакцию перед подготовкой. Для перехода
`0 → 1` артефакт начинает короткую `BEGIN IMMEDIATE`, повторно читает версию,
выполняет отдельные DDL-операции и фиксирует схему вместе с `user_version=1`.
Если другой вызов уже подготовил `1`, повтор сохраняет готовое состояние.
При ошибке в собственной транзакции выполняется откат. После устранения причины
тот же `prepare` подготавливает состояние заново.

На готовой версии `1` чтение и повторная подготовка обходятся без транзакции
писателя; они проверены при другом соединении с `BEGIN IMMEDIATE`. Ожидание SQLite
нужно только для операций, которым действительно необходим соответствующий доступ.

| `error.code` | Существенные `details` | Правильное продолжение, `action` |
| --- | --- | --- |
| `state_not_found` | `database` | Подготовить выбранное собственное состояние: `prepare:state` |
| `state_not_prepared` | `version=0` | Выполнить `prepare`: `prepare:state` |
| `state_incompatible` | Фактическая `version` | Выбрать собственное поддержанное состояние: `select:state` |
| `state_busy` | `database` | После завершения мешающей операции повторить вызов: `retry:state` |
| `state_io` | Непустая `reason` | Обеспечить доступный путь собственной базы: `configure:state` |
| `invalid_config` | Указатель `path` на конфиг или известное поле | Подготовить конфиг по справочнику: `correct:config` |
| `invalid_json` | Пустой объект | Передать один UTF-8 JSON-пакет: `provide:json` |
| `invalid_request` | Указатель `path` | Передать точные поля пакета и операции: `correct:request` |
| `unsupported_schema` | Строковая `schema` или `null` | Выбрать схему `poise-state/v1`: `select:schema` |
| `packet_limit` | `limit="packet_bytes"` | Уложить пакет в выбранный предел: `reduce:packet` |

## Сохранённые факты и владельцы

Формат `1` использует семь таблиц:

| Таблица | Принадлежащие ей факты |
| --- | --- |
| `poise_sessions` | `id`, происхождение `native`/`generated`, статус `open`/`closed`, ревизия не меньше `1` |
| `poise_bindings` | Уникальный ключ caller, единственный владелец Session и переданный JSON inventory |
| `poise_role_assignments` | Одно первое назначение роли Session и переданный JSON происхождения решения |
| `poise_hook_bindings` | Идентификатор привязки, Session и её данные |
| `poise_hook_events` | Последовательность событий; уникальность пары привязка/идентификатор события |
| `poise_reader_state` | Контекст, последнее событие, квитанции и ACK самостоятельного reader каждой Session |
| `poise_cursors` | Переданные данные позиции по паре Session/путь |

Обязательные поля имеют `NOT NULL`; связи с Session и hook binding имеют внешние
ключи. Соединения приложения включают `foreign_keys`. Первое назначение роли
занимает единственную запись Session; неизвестная роль представлена отсутствием
такой записи. Это инвариант данных. Один и тот же путь reader может независимо
принадлежать разным Session. Подготовка схемы создаёт пустые таблицы; факты
появляются через предназначенные для них операции владельцев. Повтор подготовки
сохраняет уже записанные значения и порядок истории событий.

Текущий вход предоставляет подготовку и чтение версии состояния. Установление Session,
первое назначение роли и её статус доступны через `bin/poise` и описаны в
[действующем руководстве Session](shell-poi.md). Транспорт событий и внешние вызовы
имеют [действующее руководство hooks](hooks-poi.md). Порционное чтение через тот же
`bin/poise` описано в [действующем договоре reader/2](poi-file-contract.md). Его
метаданные принадлежат `poise_reader_state`; курсор передаётся клиентом в каждом
продолжении. Существующие значения таблицы `poise_cursors` сохраняются за своим
владельцем. Общие контекст, навыки, проверки возможностей и навигация имеют
[собственный вход](generic-poi.md).

## Проверка поставки

Из корня checkout, с выбранным CPython 3.13:

```bash
"$POISE_PYTHON" -B apps/poise/tests/test_state.py --suite behavior \
  --output-root "$POISE_STATE_CHECK_OUTPUT"
"$POISE_PYTHON" -B apps/poise/tests/test_shell.py --suite behavior \
  --output-root "$POISE_STATE_CHECK_OUTPUT/shell"
```

Выберите собственный `POISE_STATE_CHECK_OUTPUT` для полного отчёта
`state-details.json`. Пять групп проверяют lifecycle, факты и SQL-инварианты,
изоляцию конфигураций, отдельный исторический артефакт с откатом и обычные исходы
публичной границы. Успех — `status="passed"`, `groups=5`, `executed=5`,
`errors=0`, `failures=0`. Smoke оболочки выполняет восемь проверок.
