# Владение после аварийного восстановления

Обновлено: **2026-09-21**.

## Причина и граница

Авария облачного агента может не оставить `SessionEnd`. Без native lifecycle
`UnobservedSessionLiveness` возвращает `UNCERTAIN`; старая запись `SessionStart`
также не доказывает, что процесс продолжает работать. Обычный `bootstrap` не должен
автоматически перехватывать такое владение. Однако восстановленная задача не должна
оставаться в бесконечном отказе из-за отсутствующего события завершения.

Для подтверждённой аварии существует **режим `after_crash` существующей операции
`recover_ownership`**. Он записывает решение пользователя об отзыве выбранных claims,
а не выдумывает факт смерти сессии. Режим согласования конфликтов старой схемы v12
сохраняет прежний формат и правила; это другой сценарий той же операции.

## Штатная последовательность

Сначала восстановить проверенный [checkpoint](checkpoint-recovery.md) в новый
каталог. Установить, что прежние писатели не могут менять выбранные ресурсы:
остановить их штатным способом либо работать в действительно изолированной копии.
Не считать отсутствие PID, давность файла или неопределённый hook достаточным
подтверждением. Перед сбросом сохранить закрытый снимок БД и существующий WIP.
Не удалять lock, SQLite WAL, незавершённые receipts или файлы рабочего дерева.

Из своей настоящей сессии запросить выбранные задачи одним пакетом:

```json
{
  "operation": "show",
  "input": {"queries": [{
    "id": "recovery",
    "kind": "ownership_recovery",
    "task_ids": ["0162"]
  }]},
  "messages": []
}
```

Ответ содержит задачи и их версии, связанные worktree claims, сохранённое execution,
наблюдение liveness, список отзываемых связей и `recovery_template` — готовый пакет
для `recover_ownership`. Инструмент сам вычисляет `expected_snapshot`, подставляет
Task IDs и идентификатор запроса. Агенту не требуется читать SQLite, вычислять hash
или собирать внутренние связи. В шаблоне `reason` и `authorization.decision` пусты,
`writers_stopped` равен `false`: инструмент не придумывает пользовательское разрешение.

После реального решения пользователя заполнить причину, текст решения
`authorization: {"role": "user", "decision": "..."}` и подтвердить
`writers_stopped: true`. Отправить этот пакет через тот же `poise work`.
Результат — `ownership_recovered`. Шаблон без заполненного решения и подтверждения
отклоняется. Это осознанная операторская операция, не универсальный `force`.

При изменении снимка ни одна задача пакета не освобождается. Повторить чтение,
сверить изменившуюся область с разрешением и отправить новый согласованный пакет;
не повторять старый сброс вслепую. Повтор точного уже применённого запроса возвращает
исторический receipt и **не сбрасывает нового владельца**. Изменённый запрос с прежним
`request_id` отклоняется как конфликт.

После освобождения выполнить обычный `bootstrap` той же Task. При необходимости
пересмотра задачи использовать [авторизованный `task/restart`](task-planning.md#решение-о-restart-и-пересмотре),
затем `edit` и `ready`. Сброс владения сам по себе не требует изменения контракта.

## Сохранность и запрет устаревшего повторного захвата

Освобождение Task, связанных с выбранными Task worktree claims и запись решения
в `ownership.crash_recovered` выполняются в одной существующей SQLite unit of work.
При сбое записи журнала вся операция откатывается. Используются текущие таблицы,
без новой схемы, миграции, фонового наблюдателя или второго lock-механизма.

Сохраняются ID, статус, этап, итерация, draft/контракт, requirements, история,
submissions, proofs, артефакты, Git HEAD/index, рабочее дерево и WIP. Меняется только
владение и версия освобождённой Task; добавляются события освобождения и аудита.
Независимый worktree прежнего владельца, относящийся к другой Task, не затрагивается.


Состояние `available` само по себе не подтверждает отсутствие владельца worktree.
Проверять нужно обе оси через `ownership_recovery`. Если сохранился только claim
рабочего дерева выбранной Task, операция отзывает только его: статус, версия и
история этапов самой задачи не изменяются.

Отозванная сессия не может повторно захватить эти Task/worktree, возобновить их или
обойти запрет прямым редактированием свободного newborn. Отзыв хранится в существующем
журнале и переживает закрытие процесса и восстановление БД. Исторические receipts
можно читать; они не дают нового владения. Продолжение использует новую настоящую
сессию, не подменённый идентификатор или скопированный старый caller binding.

## Что операция не делает

`writers_stopped` и текст решения — сохранённые подтверждения оператора. API не
аутентифицирует человека внешним удостоверением и не умеет останавливать удалённый
процесс; оператор отвечает за фактическую изоляцию. Изолированная копия не должна
позднее подменять более новую рабочую БД без сверки состояния.

Обычные автоматические захваты по-прежнему освобождают чужое владение только при
авторитетном `DEAD`. Только явный `after_crash` допускает отзыв при сохранённом
`UNCERTAIN` или устаревшем `LIVE`, без изменения этого наблюдения и без fake `SessionEnd`.
Собственные claims освобождаются обычной операцией; terminal Task передаётся своим
операциям результата/cleanup, а не перезапускается сбросом владения.

Неизвестные исходы checks, actions, handoff, публикации и cleanup остаются в execution
и своих журналах. Получение владения не означает разрешения слепо повторить внешнюю
операцию и не превращает неизвестный результат в успех. При утраченном рабочем
дереве применяется существующий `recover_missing_worktree`; этот режим не пересоздаёт
Git-каталоги. Если продолжение невозможно, агент представляет проверяющему или
пользователю основание для обычного `restart` и изменения правил, не требует ручного
редактирования БД как штатного шага.
