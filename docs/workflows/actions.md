# ApplyPlan / Publish — общий инструмент внешних изменений

Обновлено: **2026-09-06T22:58:21+05:00**. Реализовано в POISE-DDD-06. Это контракт существующего среза, не заявление о выполнении всего нормативного ТЗ.

## 1. Один пакет и два семейства обработчиков
`poise work` по-прежнему принимает JSON через stdin: `operation`, `input`, `messages`. Выбор обработчика задан графом процесса, не названием типа цели. В результате этапа `stage_work` содержит план либо намерение публикации. Все прочие секции, трассировка, доказательства и пути остаются в том же пакете.

`apply_plan` выполняет заданный план, фиксирует наблюдаемые действия и при необходимости возвращает продолжение тому же агенту. `publish` изменяет точный целевой Git ref после принятого осмотра. Они используют Task/Feedback/ContentPolicy, общий executor, внешние порты и короткий SQLite UnitOfWork. Прямой SQL или присваивание lifecycle из handler запрещены.

## 2. План интеграции
```json
{
  "plan": {
    "kind": "git_merge",
    "base_commit": "<точный полный SHA базового коммита>",
    "sources": [
      {"commit": "<точный SHA первого источника>", "checkpoint_message": "WIP: integrate first source"},
      {"commit": "<точный SHA второго источника>", "checkpoint_message": "WIP: integrate second source"}
    ]
  },
  "phase": "prepare",
  "resolutions": [],
  "finding_resolutions": []
}
```
Это содержимое `stage_work`, не самостоятельный envelope. SHA-маркеры в документации должны быть заменены фактическими SHA; они не допустимы для запуска. Полностью исполняемый пример — `examples/actions_demo.py`.

Источники должны существовать в текущей codebase; remote, Git identity, шаблон ветки, правила сообщений и timeout берутся из явной конфигурации. Начальное дерево должно быть чистым, HEAD должен совпадать с заданной базой. Неизвестные изменения не сбрасываются. Предварительная проверка охватывает весь список источников, лимит числа действий и требуемое сообщение окончательного коммита.

Источники объединяются в заданном порядке `git merge --no-ff --no-commit`. Для перехода от промежуточного источника к следующему необходим локальный checkpoint-коммит. Он использует явно заданное сообщение, сохраняется в receipt как **UNVERIFIED**, не является успешным доказательством и не обновляет целевую ветку. Последнее объединённое дерево проходит обычные проверки и только затем получает проверенный коммит и публикацию в собственной ветке задачи.

### Конфликт и CONTINUE
Ответ `awaiting_action_continuation` содержит наблюдённые конфликтующие пути и актуальный `result_template`. Агент меняет исходники нативным IDE/patch-инструментом и возвращает в том же пакете `phase: continue` и `resolutions: [{"path": "src/file.py", "reason": "Почему решение сохраняет требования источников"}]`.

AI poise проверяет точный набор путей, принадлежность MERGE_HEAD текущему плану, отсутствие конфликтных маркеров и незавершённых записей index. Затем сам выполняет Git stage и продолжает план. Повторный merge уже обработанного источника не запускается. Объяснение разрешения сохраняется в action receipt; Git-конфликт сам по себе не является дефектом исходной задачи.

Если объединённые тесты не прошли, агент исправляет код и повторяет `verify` той же итерации. Новое дерево получает новые проверки; план источников не воспроизводится заново. Содержимое начатого плана неизменно. Для нового плана нужно явное разрешённое rework, а не незаметная замена списка источников.

## 3. Осмотр и целевая публикация
Нормальный маршрут: `apply_plan → inspect → publish`; при находках: `inspect → revise → inspect → publish`. Сначала заканчивается проверка текущего этапа и возвращается доклад. Ни одно семейство не начинает следующий содержательный этап само: агент открывает его новым `bootstrap`. Действующее поручение исполнителю покрывает последовательные `executor`-этапы, но перед `reviewer` и отдельно разрешаемой публикацией нужна соответствующая явная команда по [канонической политике ролей](../governance/development-rules.md#роли-этапов-и-непрерывность-поручения).

В графе `publish` не может быть начальным этапом или обходиться прямым входом из `produce/apply_plan`. Каждый обычный предшественник — clear-ветка `inspect`; rework shortcut в publish запрещён. Повторный осмотр исправления также может быть таким предшественником.

Пакет `stage_work` публикации:
```json
{
  "target_ref": "refs/heads/main",
  "expected_commit": "<точный полный SHA ожидаемого старого target>",
  "authorization": "Пользователь принял осмотр и поручил публикацию результата."
}
```
Текст authorization — интерпретация прямой инструкции агентом, не автоматическое доказательство или NLP-парсер полномочий. Публикация требует чистого принятого кандидата и всех текущих pre/post/content/artifact-условий. Exact candidate берётся из HEAD текущей задачи, а не из пользовательского произвольного пути.

Проверяются ancestry ожидаемого target и наблюдаемый remote ref. Обновление использует exact old-ref lease; общей команды `--force` нет. Этот lease — защита сравни-и-замени, **не разрешение удалить историю**: ожидаемый target сначала обязан быть предком кандидата. Если remote уже равен кандидату, факт подтверждается без нового эффекта. При drift возвращается `action_blocked/target_changed`; чужой ref не затирается.

Private task branch и target branch различаются. Remote — заданный проектом, не автоматически `origin`. Если target push не подтверждён, повтор сначала читает remote: при прежнем expected ref может ограниченно повторить только доставку, не повторяя неизменные тесты. Если результат уже на remote, receipt восстанавливается. При другом target требуется новое осмысленное решение.

Нет необходимости искусственно создавать коммит для no-op. Target publication обновляет remote ref, не checkout локального `main` пользователя.

## 4. Изменения среды через тот же apply_plan
```json
{
  "plan": {
    "kind": "commands",
    "steps": [{
      "id": "install-runtime",
      "apply": "<полный exact method object>",
      "probe": "<полный exact method object>",
      "probe_false_exit_codes": [1]
    }]
  },
  "phase": "prepare",
  "resolutions": [],
  "finding_resolutions": []
}
```
`apply` и `probe` в реальном пакете — не строки, а полностью заданные объекты метода: id, argv, cwd, environment, expected_exit_code, stdout_contains, stderr_contains. Эти команды не задают таймаут: после запуска AI poise ждёт их конечный результат. Документационная запись сокращена только ради чтения; исполнитель таких сокращений не принимает. Пример исполняемых объектов есть в CLI demo.

Перед эффектом выполняется read-only probe. Если desired state уже подтверждено, изменение не повторяется. Только явно перечисленные `probe_false_exit_codes` означают «состояние не достигнуто, действие допустимо». Signal, другой exit либо неверный ожидаемый вывод не выдаются за нормальное FALSE. После apply снова исполняется probe; успешным считается завершённое действие с подтверждённым состоянием.

Каждый шаг имеет before-probe, apply/probe receipts и исходные stdout/stderr в task storage. Следующий шаг не запускается после failed/blocked. При неизвестном исходе незавершённого действия повтор использует probe и не исполняет побочный эффект вслепую.

Для correction этап может снова иметь handler `apply_plan`, вместе с `finding_resolutions` общего FeedbackBook. Затем отдельный inspect принимает или отклоняет предложение. Это тот же механизм feedback, не environment-specific runner.

## 5. Состояния операции и возвраты
| Состояние | Поведение |
|---|---|
| prepared | Следующий известный шаг ещё не начат |
| running | Намерение сохранено, исход внешнего шага ещё требует receipt/probe |
| awaiting_resolution | Наблюдаемое Git-объединение ожидает решения агента |
| complete | План закончен; это ещё не заменяет тесты/осмотр/приёмку Task |
| failed | Известный результат не достиг условий; хвост не выполняется |
| blocked | Продолжение не определено безопасно; повтор эффекта не угадывается |

Для известного failed/blocked action явный `bootstrap` с `decision: rework`, причиной и допустимым target stage создаёт новую итерацию. Pending MERGE_HEAD сначала требует разрешения/санкционированного прекращения; скрытого reset нет. Все этапные и общие limits сохраняются. Snapshot action адресуется в контексте, повторные task ID не требуются.

## 6. Границы DDD-06
Поддерживается последовательное merge точных существующих коммитов **одной configured codebase**. Rebase/cherry-pick, автоматическое объединение любых predecessor refs, создание произвольных targets и полный multi-codebase resolver не реализованы. Результаты DDD-05 с несколькими result-ветками по-прежнему требуют явной integration-задачи.

Commands-план — исполнитель явно разрешённой процедуры, не универсальный установщик пакетов и не автоматическая rollback-система. Тест среды использует контролируемый файл-состояние, не реальную установку в WSL. Нет имитации sudo/секретов/удалённых сервисов. При необходимости нового решения исполнитель сохраняет факты и останавливается.

Полноценные parser adapters, durable process supervisor, hooks, IDE MCP, Gmail и message capture остаются DDD-07. Наличие семи семейств handler не означает готовность всех 13 нормативных конфигураций (DDD-09).
