# Исходные данные первоначального спринта

Здесь остались определения задач и требований, которые читает [seed-инструмент](../tools/seed_wsl_tasks.py). Его работу проверяет [тест поставки](../tests/delivery/test_wsl_seed.py).

| Файл | Назначение |
|---|---|
| `task-definitions/harness/0001.json` | Требования к Requirements DB и связям требований |
| `task-definitions/harness/0002.json` | Обнаружение возможностей IDE MCP |
| `task-definitions/harness/0003.json` | Исследование JetBrains MCP и правила работы агентов |
| `requirements-bootstrap.json` | Исходные будущие требования для Requirements DB |

В проекте ai-poise эти задачи уже созданы в `SPRINT-0001`. Исходные JSON также сохранены в артефактах спринта. Рабочие задачи и их состояние читаются через AI poise; редактирование файлов здесь не изменяет опубликованные задачи.

Для текущего ai-poise повторный seed не требуется. Определения оставлены, до выполнения предпосылок задачи `0067`; новые публикации используют действующий контракт. После отдельной доработки этих зависимостей каталог можно удалить полностью.

Исторические отчёты поставки, её отдельный план и проверочная SQLite-база удалены. Рабочая база проекта — `projects/ai-poise/database/tasks.sqlite`; эталонная база не использовалась для её создания. Настройка и команды приведены в [инструкции локального проекта](../docs/configuration/project-setup.md#локальный-проект-ai-poise).

## Исправление baseline-контракта первоначальной поставки

`BASELINE` в определениях `0001` и `0002` проверяет существующий код до изменений:
`checks.baseline = ["BASELINE"]`, `checks.test_inspection = []`,
`verification_plan.green_stages = ["baseline"]`, `change_surface = []`.
В `evidence_plan.baseline.subject_methods.BASELINE` явно задано успешное завершение:
`exit_codes = [0]`, пустые списки `stdout_contains` и `stderr_contains`.
Это baseline guard, а не проверка создаваемого результата. При интеграции выбираются
текущие produced GREEN методы, а не пустой schedule терминального этапа и не BASELINE.
Порядок повторов после изменения кандидата описан в
[правилах интеграции](../docs/workflows/batch-work.md#исправление-кандидата-после-checks_failed).

Seed содержит явную decomposition для каждого этапа по действующей политике проекта.
Trace-методы планируются в `verification_planning` и требуются с `phase=pre` только
перед `test_implementation`/`implementation`, а не перед собственным созданием.
`write_stages` точки включает планирование и её этап-потребитель: это удовлетворяет
действующему правилу writable due stage; входной gate всё равно требует уже
сохранённую точку до написания кода. Валидатор достижимости не отключается.

Для новой чистой установки seed публикуется через обычные Sprint/Task owners;
предварительное редактирование SQLite не нужно. Для уже опубликованной установки
изменение этих JSON не исправляет сохранённый контракт. Сначала сохранить checkpoint,
проверить точный Task ID, версию, состояние и договорённости о сохранении результатов.
Для незавершённого контракта использовать существующий санкционированный restart
и вновь подготовить определение с указанными schedule/evidence/trace, не заменяя
исходные submissions. Отменённые или завершённые исторические `0001`/`0002` и `0114`
не переписывать; работать с их актуальными преемниками. Повторять seed в рабочем
проекте ради исправления истории не следует.
