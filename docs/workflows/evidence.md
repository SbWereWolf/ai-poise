# Доказательства и наблюдения — контракт DDD-04

Обновлено: **2026-09-20**. Срез **POISE-DDD-04 / tasks 0037, 0052, 0094**.

## Владение и цель
`CheckRegistry` (verification) хранит точные команды и расписание. `EvidencePlan` определяет роль
результатов и обязательные аргументы/осмотры. `EvidenceBook` хранит неизменные наблюдения, ревизии
аргументов и решения. Task композиционно владеет планом/книгой и фазой; runner не правит доменные
поля. Правило одинаково для всех goal types.

## Явный evidence_plan задачи
Для каждого stage нужен объект `subject_methods`, `arguments`, `review_arguments`; даже отсутствие
обязанностей задаётся явно тремя пустыми коллекциями. Пример двух этапов:

```json
{
  "measure": {
    "subject_methods": {
      "M": {"exit_codes": [0, 1], "stdout_contains": ["VALUE="], "stderr_contains": []}
    },
    "arguments": [
      {"id": "A", "kind": "logical", "phase": "continue", "observation_methods": ["M"]}
    ],
    "review_arguments": []
  },
  "audit": {"subject_methods": {}, "arguments": [], "review_arguments": ["A"]}
}
```

Числа/строки выше — пример конкретной задачи, не defaults runtime. M обязан существовать в methods и
расписании measure. Каждая команда содержит полный argv, cwd относительно task worktree, явное
окружение, expected_exit_code и признаки ожидаемого stdout/stderr. Verification method не
ограничивает время исполнения: после запуска AI poise ждёт конечный результат. AI poise ничего не
узнаёт о способе запуска проекта самостоятельно.

Каждый новый verification method дополнительно содержит обязательный `source_under_test`.
Для исходников репозитория это `{"kind":"repository","bindings":[...]}` с одним или
несколькими явными binding: `cwd` меняет рабочий каталог на путь внутри текущего task
worktree, `environment` связывает названную переменную с таким путём. Существующий ключ
окружения нельзя молча заменить binding. Команда без репозиторного исходника использует
`{"kind":"external","reason":"..."}` с содержательной причиной. Пути абсолютные, с `..`,
отсутствующие или выходящие из worktree отклоняются до subprocess.

`CheckRegistry` отклоняет методы с одинаковой полной семантикой, даже если их ID различны,
а на одном этапе — один вызов с разными ожиданиями или разной декларацией provenance.
Разные source bindings образуют разные вызовы. Для nonzero expectation нужен явный
stdout/stderr marker: RED считается связанным только при совпадении failure predicate и
успешном разрешении `source_under_test`.

### Два разных результата команды
1. **Наблюдение распознано**: процесс завершён без timeout/signal, код и признаки результата
   соответствуют явному observation rule. Поле receipt `interpretable`.
2. **Критерий выполнен**: actual exit и признаки совпали с expected contract метода. Поле receipt
   `passed`.

У `observe` отрицательный критерий остаётся наблюдением, outcome=complete. У `check` он даёт
not_satisfied, а не ошибку AI poise. Неопознанный вывод, сбой запуска, timeout/signal не дают
ложного опровержения продукта. Проектные automatic checks всегда guard: включение их ID в subjects
не снимает блокировку. Прочие task checks тоже guards.

У check outcomes: satisfied / not_satisfied / inconclusive. Наличие отрицательного аргумента/subject
даёт not_satisfied; при отсутствии отрицания inconclusive аргумент даёт inconclusive. Это
протокольные результаты семейства; конкретные переходы выбираются явным route config. Статус этапа
verified означает корректность проведения работы, не положительность предметного результата.

## Один пакет результата
В существующий stage result добавлено обязательное поле:

```json
{"evidence_work": {"phase": "prepare", "arguments": [], "decisions": []}}
```

Остальные поля
sections/artifact_paths/commit_message/content_additions/trace/method_additions/stage_work остаются.
Agent не передаёт exit_code, tree hash или receipts; они приходят от адаптера.

Аргумент: `id`, `kind` (logical/inspection), непустые `facts`, явный список `assumptions` (может
быть пуст), `inference`, `conclusion`, `verdict` (proved/disproved/inconclusive), `observation_ids`.

Решение: `argument_id`, точная `revision`, `decision` (accepted/rejected), `reason`. Revision
копируется из предъявленного предмета осмотра как ссылка. Решение допускается только в отдельно
объявленном inspect. Аргумент сам себе verdict acceptance не назначает. Собственный `verdict`
аргумента — его вывод о критерии, не признание аргумента достаточным.

## Фазы
PREPARE принимает готовый аргумент по известным фактам. Обязательное отсутствие такого аргумента
блокирует дорогие команды. Он может ссылаться на предусмотренные наблюдения прежнего этапа того же
дерева, но не на будущие текущие.

Для аргумента CONTINUE сначала выполняются методы текущего этапа. AI poise сохраняет batch и
возвращает `awaiting_continuation` с receipts/контекстом. В result file меняется только
evidence_work.phase. Агент добавляет аргумент и снова вызывает verify. Независимого
пользовательского этапа и нового claim нет.

Повтор ожидания с незаполненным аргументом не запускает команду заново. CONTINUE принимает только
наблюдения соответствующей задачи, этапа, итерации и текущего batch. Ссылки на другое/устаревшее
наблюдение отклоняются. Изменение дерева или явно переданной среды даёт observations_stale, а не
тихую подстановку старого результата. Агент возвращает phase=prepare, удаляет неподтверждённый
continue-аргумент и получает новое наблюдение. Это инженерное исправление, не автоматическая выдумка
evidence.

## Переиспользование evidence и артефактов

Evidence и полезные артефакты разрешено переиспользовать между Task/ветками, когда их provenance
действительно совпадает. Для repository evidence обязательная идентичность включает **точный hash
commit, на котором доказательство получено**. Совпадение commit hash — необходимое условие reuse
такого evidence; дополнительно должны быть совместимы проверяемое требование/метод, source
provenance и неизменяемые входы конкретного evidence kind. Совпавший hash не превращает
доказательство другого смысла в подходящее.

Если проверяемый commit hash изменился хотя бы на один commit, прежнее repository evidence больше не
доказывает новый результат и требуемое доказательство выполняется заново. Нельзя переносить PASS
только потому, что diff кажется несвязанным или artifact bytes совпали. Артефакты как данные могут
переиспользоваться по их собственным owner/path/digest правилам; receipt доказательства их
корректности остаётся привязан к commit hash и своему контракту.

При [интеграции принятого результата](batch-work.md#интеграция-принятого-результата)
обычные stage receipts не заменяют проверки кандидата публикации. Для него используются
подходящие методы **текущего** реестра завершённой Task и свежая полная партия квитанций
с точными commit/tree, определениями методов и сохранёнными stdout/stderr.
Интеграционная квитанция также сохраняет разрешённую `source_provenance` и
`provenance_digest`. Перед публикацией эти значения и фактический `cwd` сверяются
с повторным разрешением текущего метода для кандидата через общего владельца.
Самосогласованный digest подменённых фактов не подтверждает правильность исходника. Старые
квитанции и событие `checks_passed` без идентичности актуальной партии остаются
аудитом, но требуют нового запуска проверок перед публикацией. Пустой набор допустим
только при действительно пустом подходящем наборе текущего реестра; отсутствие самого
реестра не считается этим случаем.

Целевая реализация должна делать эту привязку и reuse декларативно через владельцев
evidence/artifacts, а не требовать от агента вручную копировать receipts или вычислять hashes.
Текущая реализация reuse в отдельных путях по-прежнему требует локальные проверки и не считается уже
расширенной этим документом; изменение runtime выполняется отдельной Task.

## Актуальность и повтор
Verify и явный rework после `checks_failed` используют один канонический путь построения
invocation и `execution_key`. Invocation содержит точный снимок выбранного метода, включая
ожидания, роли guard/subject и observation rules, разрешённый cwd, фактически переданный env и
разрешённую `source_provenance` с её digest. `execution_key` строится из stage, iteration,
наблюдаемого Git tree и полного списка этих invocations. Отдельного source-less ключа для
поиска failed batch нет.

Исторический batch не заменяется. Повтор без изменения входов использует receipts только после
трёх последовательных проверок: каждый batch receipt полностью совпадает со своей
неизменяемой записью evidence ledger; его method, expectations, cwd, tree и provenance точно
соответствуют текущему каноническому invocation; существующие `stdout`/`stderr` совпадают с
сохранёнными digest. Control-поля receipt имеют строгую форму, завершённый известный exit и не
допускают timeout. Env участвует в `execution_key`, но не записывается целиком в receipt.
Неуспешные guard/transport можно повторить только в рамках явного `verify_attempts`.

До продолжения проверяется существование и digest raw output. При неизвестном исходе прерванного
внешнего процесса сохраняется прежнее безопасное блокирование DDD-03 — recovery runner не
имитируется.

Повтор после неуспешного разрешённого внешнего действия также сверяет execution_key. Изменение env
требует нового запуска; неизменное состояние не запускает тесты повторно. Receipt хранит разрешённую
`source_provenance`, `provenance_digest` и отдельный `expectation_digest`; они входят в identity
исполнения и позволяют отличить проверяемый источник от ожидаемого результата. Git push не является
разрешённым внешним действием.

Изменение Git tree, метода, ожиданий, cwd/env, разрешённой provenance либо любого поля
сохранённого receipt делает batch недоступным для reuse/rework до изменения lifecycle или
execution state. То же относится к отсутствующей ledger-записи и повреждённым либо удалённым
файлам output. Runtime не пробует второй ключ, legacy alias, tolerant reconstruction или
fallback к похожему batch; прежние неканонические данные не переписываются миграцией.

### Замена устаревшего метода наблюдения

Если зарегистрированный предметный метод устарел после изменения репозитория или внешнего
контракта, Task не пересоздаётся и её БД не исправляется вручную. Текущий этап с handler
`observe` может передать в обычном `method_additions` тот же защищённый пакет изменения
реестра, что и этап-владелец `test_registry`: `request_id`, точную `expected_revision`,
непустой список `operations` и полный текущий список `executable_obligations`.

Это узкое делегирование владения разрешает только `replace` метода, который одновременно:

- входит в `evidence_plan.subject_methods` текущего этапа;
- уже существует в current registry;
- сохраняет прежние `method_id`, полный список `stages`, `evidence_kind` и `covers`;
- не меняет `executable_obligations`.

Добавление, удаление, reschedule, замена same-stage guard вне `subject_methods` и изменение
классификации либо покрытия остаются исключительным правом этапа `test_registry`. Весь пакет
сначала проходит обычную проверку revision, idempotency digest, формы метода, provenance и
verification plan. Любой отказ оставляет Task, current/history реестра и журнал без изменений.

Первое успешное применение сохраняет прежний current snapshot в history и привязывает к
request неизменяемый audit receipt: `task`, `actor`, `stage`, `iteration`, `request_id`,
`previous_revision`, `new_revision`, изменённые `methods` и `receipt_id`. Тот же request после
любого числа последующих редакций и после перезапуска возвращает исходные audit-поля и
`receipt_id` с `replayed=true`; событие `verification_registry_changed` второй раз не пишется.
Изменённый payload с тем же request ID отклоняется.

Исторические определения методов, command receipts, их source/expectation provenance,
дерево и execution identity, аргументы и assessments не перезаписываются и не
переинтерпретируются. Следующий `verify` исполняет только новое current-определение. Текущую
revision, current, history, requests и `executable_obligations` перед заменой следует получить
одним `show` query с `kind=verification_registry`; файловая Task DB не является API.

Для разрешённого restart/ready действует тот же авторитетный current registry,
а creation methods остаются историей создания. Независимая правка расписания
валидируется по текущим ID; неизвестная ссылка отклоняет ready атомарно.
Сохранение реестра, отсутствие мутации при семантическом no-op, один audit для
фактического изменения и порядок восстановления описаны в
[реестре после перезапуска Task](batch-work.md#реестр-после-перезапуска-task).
Исторические command receipts сохраняются для осмотра, но не становятся актуальным
доказательством изменённого метода или нового кандидата.

Не заявляется полная идентичность внешней среды: время, состояние внешнего сервиса и ignored файлы
автоматически не fingerprint-ятся. Для таких зависимостей нужны явные команды/наблюдения проекта;
адаптеры и более точные правила актуальности расширяются по реальному использованию.

## Осмотр и обратная связь
Процесс может задать: measure → audit(clear→terminal, changes_requested→measure). Отказ по аргументу
выбирает changes_requested без создания фиктивного исправления или новой задачи. Новый подход
создаёт новую revision; старый аргумент и отказ сохраняются. Inspect может одновременно работать с
обычными findings/resolutions DDD-03.

EvidenceBook обеспечивает наличие фактов/структуры/ссылок, но не истинность текста. Она проверяется
агентом. Представленные demo decisions — fixtures, не независимый peer review.

## Инструменты
`verify` принимает весь пакет; `show --evidence` показывает текущий план, assessment, сохранённые
аргументы/решения и компактные observations. Полный stdout/stderr — файлы у задачи. `cancel` не
требует заполнить недостающее evidence. Артефакты по-прежнему передаются только путями, без новых
деклараций.
Для RED поле `verification_plan.red_failure` фиксирует код выхода и полные
`stdout_equals`/`stderr_equals`. Совпадение буквальное: дополнительный сбой или
любой иной дополнительный вывод не подтверждает ожидаемый RED, даже если старые
маркеры присутствуют.
