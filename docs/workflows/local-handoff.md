# Локальная передача работы

Обновлено: **2026-11-03**. Участники продолжают одну Task в её существующей рабочей области.
Готовый результат передаётся одной командой
[`handoff`](batch-work.md#передача-результата-одной-командой): проверка результата,
допустимое продвижение и обычное освобождение владения. Сам native `handoff`
сохраняет отдельный шаг сообщения. Настроенный
[прокси](../operator/agent-handoff-proxy.md#пакет-и-один-вызов) объединяет техническую
передачу и уведомление одним вызовом; получатель приобретает Task своим входом.
Scoped transport, `transfer`,
bundle и копирование материалов между участниками не возвращаются.

## Прямая передача между исполнителем и проверяющим

Поручение пользователя выполнить Task разрешает исполнителю и проверяющему проходить свои
штатные этапы, проверки и исправления без новой команды на каждый осмотр. Явные ограничения
пользователя и отдельные полномочия на приёмку, публикацию и интеграцию сохраняются.

При настроенном прокси агент передаёт ему готовый native пакет, содержательное
сообщение и назначенного получателя. Прокси выполняет технические шаги сохранения,
допустимого продвижения, release и уведомления; получатель продолжает по пункту 4
ниже. [Настройка](../operator/agent-handoff-proxy.md#подготовка-и-настройки) и
[неизвестный исход уведомления](../operator/agent-handoff-proxy.md#продолжение-и-явное-подтверждение)
имеют собственного операторского владельца. Прямой native маршрут описан ниже.

Успешный release освобождает Task и её зависимый worktree. Независимый worktree
сохраняется с тем же ID в `before/after`; это поддержанный результат передачи.

1. Подготовить полный результат текущего этапа, evidence и findings через его владельцев.
   Выполнить `handoff` по [точному договору](batch-work.md#передача-результата-одной-командой)
   с полным текущим result template и артефактами. Команда выполняет штатные проверки,
   допустимое продвижение и release, сохраняя собственное сообщение коммита этапа.
2. Прочитать полные `verification`, `progression`, `release`, фактическое состояние и
   `blocked.continuation`. Подтвердить освобождение до передачи. Для незавершённых материалов
   сохранить их честно и использовать отдельный [release](#пакет), без ложного GREEN.
3. Прекратить изменения Task и её дерева. Напрямую уведомить известного получателя:
   project/Task ID, его этап и роль, source commit/tree, ссылки на результат, evidence,
   release receipt, findings и следующее действие. Указать действующие request_id/target_stage
   продвижения; для maximum progression target отсутствует.
4. Получатель своим native launcher вызывает `bootstrap` с тем же Task ID, проверяет
   фактический этап, scope, findings и существующий worktree. После захвата он продолжает
   в той же области и повторяет точный действующий `advance`, если это разрешено воротами.

Сообщение в чате не снимает claim и не заменяет независимый осмотр. При подтверждённом
отказе до release владение остаётся у отправителя. При потерянном подтверждении после
release `handoff_blocked`/`release:null` не доказывают владение: получатель уже мог захватить
Task. Установите фактический исход через ownership/исходную receipt и повторите точный
handoff, без нового release или захвата обратно. Recovery сохраняет claim получателя.
После успешного освобождения
ошибка уведомления допускает повтор сообщения о том же сохранённом результате, а не повтор
работы или молчаливый захват обратно. При неизвестном получателе сохраняют точное препятствие,
не рассылают поручение посторонним агентам.

Полученное поручение остаётся обязательством до выполнения, отмены или явной передачи.
Новые сообщения дополняют рабочий план, если явно не меняют поручение. После сохранения,
освобождения и уведомления агент продолжает уже порученную доступную работу в том же ходе.
Собственные запущенные операции доводятся до определённого исхода. Чтение чужого чата ради
прогресса, опрос статуса и фоновое наблюдение не применяются. Если проверяющий занят, он
сначала завершает начатую проверку, затем берёт следующую полученную передачу; второй Task
или worktree одновременно не захватывает.

## Завершение хода после передачи

После сохранения результата, подтверждённого освобождения владения и успешного уведомления
получателя отправитель сверяет собственные поручения. Дальнейшее действие определяется
фактической доступностью работы:

| Ситуация | Действие участника |
|---|---|
| Своей доступной порученной работы нет; продолжение зависит от ответа напарника | Завершить текущий ход, сохранив в результате ожидаемое решение и следующее действие. Входящее сообщение о готовом результате возобновляет работу. |
| Есть собственное доступное поручение | Продолжить его в том же ходе с соблюдением границ владения. |
| Получено сообщение о передаче | Прочитать сохранённый результат, получить Task своим штатным `bootstrap` и продолжить назначенный этап. Занятый проверяющий сначала завершает текущую проверку. |
| Уведомление после освобождения завершилось ошибкой | Сохранить фактический исход; повторить только уведомление о том же результате либо сообщить конкретное препятствие. После исчерпания доступного продолжения завершить ход с сохранённым препятствием. |
| Собственная операция уже запущена | Довести её до определённого исхода через владельца операции, прочитать результат и затем снова определить доступную работу. |

Ожидание ответа напарника — сохранённая зависимость, а не выполняемая работа. Оно не требует
удерживать ход, повторять обращения модели, читать чужой чат ради прогресса, опрашивать статус,
запускать таймер или фоновое наблюдение. Возобновление по входящему сообщению совместимо
с обязанностью сохранять незавершённые поручения. Ожидание результата собственной запущенной
команды остаётся частью выполнения этой команды.

Доставляйте сообщение назначенному участнику доступным прямым инструментом связи. В Codex
при доступном `send_message_to_thread` укажите ID назначенного чата и сохранённый результат;
проверьте ответ самого вызова отправки. Успех отправки подтверждает передачу сообщения
инструменту, но не прочтение или завершение работы получателем. Передача на осмотр завершается
после подтверждения отправки; ждать решения принимающего внутри того же хода не требуется.
Если инструмент или адресат недоступен, сохраните препятствие по
[процедуре прямой передачи](#прямая-передача-между-исполнителем-и-проверяющим).
Это порядок использования доступной связи; автоматическая доставка и возобновление зависят
от возможностей среды и не создаются текстом инструкции.

## Назначение ролей и идентичность участников

Пользователь назначает агентам роли. Одному агенту могут быть поручены обе роли —
исполнителя и проверяющего. Он выполняет их раздельно по этапам: план, проверка плана,
исполнение, проверка результата. Если пользователь назначил роли разным участникам,
они передают работу друг другу. Доступ к Task не назначает агенту новую роль.
См. [каноническое правило](../governance/development-rules.md#роли-этапов-и-непрерывность-поручения).

Идентичность служит учёту фактических авторов и владения. Она не является условием,
что проверяющий обязан быть другим агентом или другой сессией. Автор результата
сохраняется в событии `verified`; поле `review_identity` описывает происхождение,
а различие actors само по себе не доказывает качество проверки. Native caller сохраняется;
подмена binding или hook events запрещена.

История обычных `ownership_released`/`ownership_acquired` подтверждает продолжение
проверенного результата при неизменных stage/iteration/tree и остальных воротах.
Если обе роли поручены одному агенту, он может законно получить Task после своего
освобождения и перейти к следующей роли. Это не создаёт результата проверяющего:
его работу и решение ещё требуется выполнить и сохранить на своём этапе.
См. [продолжение verified результата](batch-work.md#продолжение-проверенного-результата-после-освобождения).

## Пакет

Сначала прочитайте текущую версию Task. Значение `expected_version` ниже условное; используйте
фактическую версию своего claim. Отправляется один пакет выбранного проекта через собственный
native launcher, с `messages=[]`:

```json
{"operation":"release","input":{"task_id":"T1","request_id":"release-T1-review-1","expected_version":17,"reason":"Результат сохранён для независимого осмотра"},"messages":[]}
```

Пакет возвращает `status=ownership_released`, Task/request_id, `before`/`after` ownership
snapshots и `replayed`. Освобождение закрывает собственный accounting interval в той же UoW
после допуска и до снятия claim. Зависимый worktree binding освобождается вместе с Task;
независимая рабочая область остаётся за сессией. Физические файлы и рабочее состояние сохраняются.

`release` не принимает `result`, `commit_message` или `artifact_paths`: сохраните их до вызова
через реальные владельцы. Операция не создаёт commit, bundle, транспортную квитанцию или копию;
не исполняет проверки, не меняет lifecycle outcome и не разрешает приёмку либо очистку.
Полный контракт: [обычное освобождение владения](batch-work.md#обычное-освобождение-владения).

## Незавершённые материалы исправления

На этапе `revise` непустой `result.stage_work.resolutions` означает действительные
предложения исправлений открытых findings. Когда выполнены только новые тесты и
настоящий RED для независимого осмотра до кода, такое предложение ещё отсутствует.
Частичный stage result с пустыми resolutions не является допустимым revise result.

Сохраните отчёт/полные доказательства отдельной публичной `artifacts`-операцией,
а затем освободите владение обычным `release`, сохранив WIP без коммита.
Например, создание неизменяемого снимка:

```json
{
  "operation": "artifacts",
  "input": {
    "items": [
      {
        "scope": "task",
        "path": "handoff/test-review/report.md",
        "source": {"kind": "text", "text": "Фактические тесты, RED, происхождение и ограничения."}
      }
    ]
  },
  "messages": []
}
```

Для готовых полных файлов используйте существующий
[file source с фактическим digest](batch-work.md#создание-файлов), сохраняя исходник.
`text` source принимает ключ `text`, а не `content`. Обычный зарегистрированный
снимок неизменяем; заранее требуемое редактирование проходит отдельный
[artifact drafts lifecycle](batch-work.md#редактируемые-приёмочные-черновики).

Сохраните реальные пути, возвращённые владельцем, в сообщении проверяющему.
Прочитайте фактическую текущую версию и выполните обычный `release` по
[точному пакету](#пакет). Проверьте `ownership_released`, прежние HEAD/index/WIP,
текущий незавершённый stage и фактическое освобождение владения. `release` не
создаёт submission, коммит, bundle или фиктивное исправление.

После освобождения прямо сообщите известному проверяющему; получатель захватывает
ту же Task до работы. Независимое решение по тестам сохраняется через владельца
материалов. Это проверка конкретного промежуточного результата внутри незавершённого
этапа, а не native verify всего исправления, приёмка либо закрытие исходного finding.
Исполнитель получает Task обратно перед изменением кода и доводит исправление
через обычный gate. Зарегистрированные снимки остаются неизменяемыми.

## Передача после перезапуска

Перезапуск сохраняет ту же Task, историю и существующий WIP; новая роль не получает доказательств
текущего этапа из одной старой submission. Авторизованный restart и законная коррекция frozen
договора имеют собственные owners. После них отправитель сохраняет фактический контекст,
освобождает свой claim, затем уведомляет получателя. Получатель проверяет actual bootstrap:
старый этап, target или GREEN нельзя считать действующими без подтверждения.

## Механическая последовательность

Готовый результат → `handoff` (verify → advance → release) → подтверждение исхода →
прямое сообщение → `bootstrap` той же Task → законное продолжение. Для незавершённых
материалов: сохранение через владельцев → отдельный `release` → тот же прямой протокол.
Task-owned рабочая область не пересоздаётся и не копируется. `advance` останавливается
на реальной работе, границе ролей и отдельных полномочиях; он не выполняет работу
этапа, уведомление, приёмку или публикацию.

### Постоянный комплект при передаче

Дополнительные proof, снимки и полные потоки публикуйте через artifact owner во
время ACTIVE до `verify`, пока запись артефактов разрешена. Сохраняйте ссылки
на Task-owned пути в результате. После `verify` и `advance` runtime может быть
очищен; его файлы не являются постоянным комплектом следующей передачи.
Полные native receipts уже принадлежат сохранённому исходу операции: используйте
их пути, не запускайте проверку повторно только ради производного отчёта.
Производный файл, подготовленный после VERIFIED, остаётся рабочим материалом до
следующего действительного ACTIVE владельца; это не основание для restart или
фиктивной записи артефакта. Отдельные постоянные результаты заранее согласуются
через [delivery](terminal-materials.md#публичный-договор-поставки).

Принятые постоянные результаты сохраняются владельцем артефактов до terminal retirement;
служебные файлы остаются служебными. Передача ссылки на уже сохранённый комплект не означает
создание новой копии между участниками и не заменяет его проверку владельцем.
См. [комплект приёмки](evidence.md#сохраняемые-входы-и-приёмочный-манифест).

## Продолжение

Освобождённая Task остаётся на текущем этапе и с тем же WIP. Новый участник явно выбирает
этот ID через `bootstrap`; контекст возвращает фактические требования, scope, проверки,
findings и worktree. Claim только разрешает работу, а не подтверждает её готовность.
Отказ о чужом или неопределённо живом владельце разрешается через
[восстановление после сбоя](crash-ownership-recovery.md), не присвоением чужого caller.

## Передача между исполнителем и ревьюером

Обе стороны соблюдают один [прямой протокол](#прямая-передача-между-исполнителем-и-проверяющим).
Исполнитель сохраняет результат и проверки, проверяющий — решение и findings; каждый
освобождает собственный claim перед уведомлением. Получатель захватывает до записи.
[Политика ролей](../governance/development-rules.md#роли-этапов-и-непрерывность-поручения)
не зависит от имени обработчика и не допускает выдавать самопроверку за независимую.

## Повтор и отказ

Точный повтор `release` тем же caller возвращает исходный receipt без новых эффектов, включая
случай последующего захвата другой сессией. Тот же ID с изменённым intent или actor отклоняется.
При stale version прочитайте актуальный контекст и создавайте новое намерение только при
сохранившемся собственном claim. Отказ записи откатывает release и receipt одной транзакцией.
Receipt старого освобождения не снимает новое владение и не доказывает завершение Task.

## Освобождение при неизвестном исходе проверки

Обычный `release` сохраняет pending/unknown check attempt. Сначала сохраните точные сведения
и существующие полные outputs через их владельцев. Освобождение не превращает неизвестный
исход в успех, не перезапускает процесс и не снимает ворота проверки. Получатель диагностирует
текущий исход до продолжения. Применяется
[протокол checks_failed](batch-work.md#явный-rework-после-checks_failed) и
[порядок восстановления harness](../governance/development-rules.md#сбой-harness-и-ручной-обход).
Локальный архив не создаётся без отдельного поручения; облачные условия принадлежат
[checkpoint recovery](checkpoint-recovery.md#контрольная-точка-и-восстановление).

## Что сохраняет receipt

Ownership receipt фиксирует intent, настоящего actor и снимки владения до/после. Источники,
stage result, checks и accounting сохраняются у их существующих владельцев. Полные ответы
читаются из сохранённых файлов, сокращённое представление не заменяет машинные данные.
Исторические handoff receipts остаются историей, не действующим механизмом продолжения.

## Сохранение незавершённого newborn

Черновик сохраняют через публичного Task owner. Обычный `release` допускает свой newborn,
сохраняет draft и состояние, не требует фиктивной submission или коммита. Получатель выбирает
тот же ID и продолжает черновик. Обязательства готовности не объявляются выполненными.
Read-only newborn registry отделяет исторический реестр от ещё неактивного текущего договора.

При выборе newborn текущие draft и revision принадлежат Task owner. Последующие
разрешённые изменения и `restart` сохраняют прежнюю историю, не восстанавливая
устаревший снимок. Старые transport rows и receipts остаются историческими.

Участник неопубликованного Sprint после `ready` остаётся newborn. Последовательность
разрешённое редактирование → `ready` → освобождение → `bootstrap` сохраняет его
текущую готовность. Приобретение сохраняет цель, draft, метаданные, принадлежность
к Sprint, файлы в той же рабочей области и прежнюю историю; добавляется событие
приобретения владения.

Наблюдаемая revision и claims повторно проверяются владельцем при приобретении.
Изменение версии или чужой claim вызывает отказ до записи; текущая постановка,
работа другого участника и зависимый worktree сохраняются. Получение само по себе
не коммитит WIP, не создаёт bundle и не подтверждает готовность или исполнение.
Проверки целостности источников при начале исполнения сохраняют свой договор.
См. [восстановление harness](../governance/development-rules.md#сбой-harness-и-ручной-обход).

### Снимок готового участника возвращённого Sprint

При unpublish Sprint участник сохраняет прежнюю историю и WIP в той же области; исполнение
после новой подготовки подчиняется актуальному договору. Старые снимки и receipts не
перезаписываются и сами по себе не являются текущим GREEN. Экспорт staged-tree для смены
участника удалён. См. [правила Sprint](sprints.md).

### Восстановление после отказа native caller

Чужой launcher не предоставляет identity отправителя. Получатель использует собственную
настоящую native session; отсутствующие или конфликтующие session variables и смешение
binding не исправляются придуманным ID или записью в Task DB. Отправитель освобождает
Task обычным `release`, получатель захватывает тот же ID своим `bootstrap`.
См. [изоляцию caller](../configuration/runtime-hooks.md#изоляция-native-caller-и-передача-делегату).

## Передача до удаления рабочих материалов

Смена участника сохраняет WIP до terminal retirement и не даёт права удалять его. После
доставки постоянного результата существующие integration/delivery/TaskCleanup owners
освобождают ресурсы по своему договору. Dirty worktree блокирует удаление даже при
`discard_authorized`; используются обычное удаление Git без force, проверка идентичности
ресурса и compare-and-delete. [Хранение terminal материалов](terminal-materials.md#договор-и-граница-хранения).
