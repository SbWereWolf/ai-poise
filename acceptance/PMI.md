# ПМИ AI Poise: программа и методика испытаний

Версия программы: `POISE-PMI-1.0`. Машинная последовательность:
[`pmi/pmi-v1.json`](pmi/pmi-v1.json). Испытания:
[`ПСИ: Arrange → Act → Assert`](PSI.md).

## Назначение и границы

ПМИ задаёт **окружение, порядок запуска ПСИ и оформление результатов**.
Действия и утверждения отдельных испытаний принадлежат ПСИ, а не дублируются
в программе. Приёмка выполняется над установленными пакетами, без импорта
внутренних владельцев вместо публичного CLI и без старой базы разработки.

Протокол распространяется только на указанные commit, wheel-хэши, версию ПМИ,
профиль ОС и Python. Успех на Debian не подтверждает испытания на Ubuntu.

## 1. Испытательная среда

Поддерживаемые программой профили: `ubuntu-24.04` и `debian-13`; Python 3.13,
Git, POSIX-файловая система. Исполнитель испытаний — обычный пользователь,
не root. Зависимости **методики сборки**: pip и setuptools из build-system
поставки. Runtime-зависимости обоих приложений определены их пакетами и
каталогом среды. Интернет для установки подготовленных wheels не требуется.

Пути исходников и результатов должны быть разными. Каждый ПСИ получает
собственный пустой каталог, новый Git-репозиторий, конфиги и базы. Между ПСИ
не переносятся Task, Sprint, ownership, результаты или состояние предыдущего
испытания. Не требуется чистить историческую рабочую базу.

## 2. Подготовка поставки

Из корня поставки с соседними `poise/` и `environment-maintenance/`:

```bash
python3.13 poise/acceptance/prepare.py \
  --source "$PWD/poise" \
  --core "$PWD/environment-maintenance" \
  --output /absolute/new-delivery
```

Подготовка создаёт wheels и virtualenv вне исходников, устанавливает оба пакета
без сети и сохраняет `delivery.json` с SHA-256 исходных файлов, установленных модулей и wheels и `prepare-log.json`. ПСИ используют
только `/absolute/new-delivery/venv/bin/python` и установленный `poise`.
Не подставлять `PYTHONPATH` как замену отсутствующей установленной зависимости.

## 3. Запуск

Обычным пользователем с правом создавать каталог результатов:

```bash
python3.13 poise/acceptance/run_pmi.py \
  --manifest poise/acceptance/pmi/pmi-v1.json \
  --profile ubuntu-24.04 \
  --python /absolute/new-delivery/venv/bin/python \
  --source /absolute/poise \
  --workspace /absolute/new-psi-run
```

Для фактической Debian 13 явно выбрать `--profile debian-13`. Неподходящая ОС,
версия Python или root дают `BLOCKED` до первого ПСИ. Название профиля не
подменяет наблюдение `/etc/os-release`.

Порядок берётся из манифеста: инфраструктура, защитные проверки, taskless,
standalone, Sprint, integration, restart, rework, crash recovery, cancellation.
После неуспеха текущий запуск останавливается; последующие случаи не заявляются
проверенными. Порядок не зашит во второй список внутри исполнителя.

## 4. Ограниченные запуски и продолжение

```bash
# Завершить не более трёх ПСИ, сохранить протокол и вернуть код 3.
python3.13 poise/acceptance/run_pmi.py ... --limit 3
# Продолжить ту же программу с теми же аргументами и каталогом.
python3.13 poise/acceptance/run_pmi.py ... --resume --limit 3
```

Завершённые ПСИ не повторяются. При продолжении сверяются входные fingerprint
и хэши сохранённых результатов/stdout/stderr. Изменение программы, среды,
исходников или доказательств требует нового протокола. Незавершённый `RUNNING`
с неизвестным внешним исходом не повторяется автоматически. После `FAIL`
исправление испытывается новым запуском, старый протокол сохраняется.

Для каждого ПСИ установлен явный timeout в манифесте. При превышении завершается
его группа процессов, фиксируется код 124 и `FAIL`, а не успешный результат.

## 5. Формат и критерий результатов

`protocol.json` — первичный протокол; `protocol.md` — читаемая сводка.
Каждый ПСИ пишет `result.json`, исходные JSON-запросы, полные stdout/stderr,
возвратные коды и SHA-256. Краткий ответ Poise раскрывается через его собственный
`response_path`, а не обрезанный preview.

`PASS` требует одновременно: все объявленные ПСИ исполнены, каждый процесс
завершился с 0, каждый `result.json` содержит PASS. Код 0 без результата или
при `FAIL` в результате не принимается. Незавершённая программа — `RUNNING`,
неподходящая среда — `BLOCKED`, отказ утверждения/таймаут — `FAIL`.
Коды исполнителя: 0 PASS; 1 FAIL; 2 неправильный запуск; 3 BLOCKED/RUNNING.

## 6. Эксплуатационная установка

После успешного ПСИ для соответствующей среды создаётся **другая**, пустая
эксплуатационная установка через `profile → deps → infra → check`.
Испытательные Task/Sprint не копируются в неё. Историческая development DB
также не импортируется. Результат `check` — готовность инфраструктуры, не
замена полного протокола ПСИ.

Резервное копирование и проверка восстановления выполняются на каждом значимом
этапе по постоянному манифесту агента; отдельной «финальной очистки истории» нет.

## 7. Создание пустой эксплуатационной установки

После PASS (не после RUNNING/BLOCKED) используется отдельная команда.
Она проверяет принадлежность полного протокола текущим исходникам,
установленным пакетам, ОС и версии ПМИ; существующий каталог не заменяется.
Целевой Git-репозиторий указывается явно. История задач не копируется.

```bash
python3.13 poise/acceptance/create_installation.py \
  --protocol /absolute/new-psi-run/protocol.json \
  --manifest /absolute/poise/acceptance/pmi/pmi-v1.json \
  --python /absolute/new-delivery/venv/bin/python \
  --source /absolute/poise \
  --repository /absolute/target-repository \
  --destination /absolute/new-installation \
  --project production --base-ref main \
  --author-name 'Project operator' --author-email operator@example.invalid
```

Сохраняются `INSTALLATION.json`, журналы публичных команд и `environment.sh`.
Проверка готовности и чистые базы не означают развёртывание на другом хосте.
Результаты испытаний остаются вне эксплуатационного каталога.
