# Реестр требований проекта

## Владение и явные пути

Выбранное приложение владеет собственным реестром канонических System/Application требований,
предметным словарём и связями; API Poise обслуживает этот реестр по его явной конфигурации.
Изменение требований выполняется через создание файла DML-миграции и применение этого файла.
История требований хранится в Git как SQL-миграции; рабочая SQLite-БД и её sidecar-файлы
размещаются в путях данных приложения вне Git. Task DB хранит собственные неизменяемые снимки,
а не второй изменяемый реестр требований.

Обязательные настройки `paths` явно разделяют хранилище и исходные файлы:

| Поле | Назначение |
|---|---|
| `requirements_database` | Рабочая SQLite-БД требований; абсолютный путь либо путь от `paths.state`. |
| `requirements_lock` | Отдельный lock реестра; абсолютный путь либо путь от `paths.state`. |
| `requirements_schema_migrations` | История DDL в исходниках приложения управления задачами. |
| `requirements_data_migrations` | История DML в документации проекта. |
| `requirements_schema_file` | Единственный актуальный SQL-сценарий создания схемы рядом с документацией. |

DB/lock отличаются между собой и от Task/telemetry DB/lock. Три пути миграций обязательны:
пропуск не подменяется значением по умолчанию. Относительные пути миграций разрешаются от
каталога загруженного файла конфигурации проекта. Примеры конфигурации используют явно подставленные абсолютные пути:

```json
{
  "requirements_schema_migrations": "/srv/poise/config/migrations/requirements",
  "requirements_data_migrations": "/srv/project/docs/requirements/data",
  "requirements_schema_file": "/srv/project/docs/requirements/schema.sql"
}
```

Это фрагмент объекта `paths`, а не полный manifest. Подготовка и публикация конфигурации принадлежат
[настройке проекта](../configuration/project-setup.md#назначение).
Обычный редактор `manifest_edits` не меняет эти пути: его отказ не разрешает ручное изменение
managed config. Не переносить рабочие данные простым редактированием пути.

Операции `command`, `apply`, `rollback`, `squash`, `rebase` и `export` работают с явно выбранным
приложением без создания или захвата Task. Существование, статус, владелец, этап и ветка
посторонней Task не определяют право записи реестра; текущий каталог не обязан быть её worktree.
Используется конфигурация выбранного приложения и его действующая привязка к проекту.
Пути DML и bootstrap берутся из неё без перенаправления в worktree; создаваемые, заменяемые и
удаляемые файлы проверяются относительно настроенных ресурсов требований. DDL читается из
отдельно настроенного каталога. Данные, журналы применения и файлы других приложений сохраняются; их реестры и истории
не объединяются.
Независимый API не открывает и не создаёт Task DB. Read-only `query` также не создаёт БД
требований. При отсутствии хранилища нужна его явная инициализация, описанная ниже.

Требования являются источником для Task: при подготовке исполняемой Task её требования связывают
с соответствующими Application/System требованиями реестра и публикуют согласованный снимок.
Независимая запись реестра сохраняет обязательность этой цепочки и исторических снимков,
описанных в [правиле публикации](#публикация-и-исторический-снимок).

## Предметные области и миграция схемы

Предметный словарь хранится в `domain_areas`, `domain_entities`, `domain_actions`.
Связи требований с именами и действиями хранятся в `requirement_entities` и
`requirement_actions`; System/Application связи — в `requirement_links`.
Данные, `requirements_meta` и `requirement_requests` воспроизводятся DML-историей.

Схема — инфраструктура Poise. Её история принадлежит
[config/migrations/requirements](../../config/migrations/requirements).
`docs/requirements/schema.sql` содержит один актуальный bootstrap, соответствующий конечной схеме;
история DDL не переносится в документацию требований. Имена начальных файлов приложения:
`0001.sql` и `0001.rollback.sql`. SQL-откат лежит рядом с прямым SQL.

Истории схемы и данных управляются стандартным `yoyo-migrations 9.0.0`.
Отдельные таблицы yoyo `_poise_requirements_schema` и `_poise_requirements_data`
(со своими `_log` и `_version`) учитывают применение к конкретной БД; используется стандартный
`yoyo_lock`. Это служебное состояние исполнения, не версия требований вместо файлов.

В новой БД сначала применяют историю `schema`, затем `data`. Пустой каталог DDL не создаёт
хранилище. Инициализация отсутствующего хранилища через инфраструктурного владельца требует обе
непустые истории; существующий файл не перезаписывается. Открытие реестра для чтения ничего
не создаёт и не мигрирует. Сначала откатывают `data`, затем `schema`: применённая история
данных блокирует откат схемы. Возврат Git-коммита сам по себе не откатывает БД.

При изменении схемы устаревшую DML-историю заменяют полной миграцией данных для новой структуры,
а bootstrap обновляют до этой структуры. Для этого служит `rebase`; склейка обычных изменений
схему не меняет. До замены сверяют все требования, связи и служебные значения; после —
восстановление,
откат и повторный накат. В DML никогда не добавляют `CREATE`, `ALTER`, `DROP` или иной DDL.

## Статусы и полнота связей

Требования имеют ровно три предметных уровня: **System → Application → Task**. Дополнительные уровни
иерархии не вводятся. Любые тематические, продуктовые, компонентные или организационные подборки
являются виртуальной группировкой (tags/views/collections) и не меняют эту сквозную цепочку.
Требование Task может обнаружить необходимость нового Application или System requirement: discovery
снизу вверх допустим, но сохранённая связь всё равно строится через все три уровня. Если агент не
может обоснованно состыковать требование с существующей цепочкой или понять, какой новый предок
нужен, он не выдумывает смысл и задаёт вопрос.

`current` означает действующее требование; `future` участвует в анализе и планировании, но не
добавляется автоматически к проверкам текущего соответствия. В целевой модели `future` может
использоваться как **проектируемое требование**. Для проектируемой цепочки допускается явно
типизированное пустое звено **любого из трёх уровней** там, где соответствующая формулировка ещё не
создана или возможность ещё не разработана. Например, проектируемый System requirement может быть
связан через пустые Application/Task звенья, а Task requirement — через пустой Application/System
предок. Пустое Task-звено не создаёт исполняемую Task. Такое пустое требование — не четвёртый
уровень и не доказательство выполнения: это адресуемый placeholder конкретного уровня, который
сохраняет сквозную связь `System → Application → Task` и показывает незакрытый gap. Исполнимый
формат описан в разделе [явных пустых проектируемых звеньев](#явные-пустые-проектируемые-звенья):
`status: "future"`, `text: ""` и прежний типизированный ID. Используется публичный владелец
Requirements, не ручная запись БД.

`obsolete` сохраняется исторически, исключается из нового покрытия и не может быть основанием новой
Task. Изменение текста или статуса не переписывает старые снимки. Когда проектируемый placeholder
позже получает содержательное требование, новая revision/chain не переписывает исторический Task
snapshot.

Связи System → Application имеют кратность многие-ко-многим. Для `current` цепочек каждый
Application обязан иметь содержательного неустаревшего System-родителя, а каждый используемый Task
requirement — содержательную Application-связь. Проектируемая цепочка может явно содержать
placeholder на любом отсутствующем уровне; такой placeholder отображается как gap и не засчитывается
как current coverage. Каждый неустаревший содержательный System должен быть распределён хотя бы в
один Application либо явно оставаться проектируемым gap. `coverage` и `gaps` показывают обе стороны
разрывов. `coverage` с `mode: "current"` учитывает только действующие содержательные узлы; обычный
анализ включает также `future` и проектируемые placeholders в исполнимом API.

## Декларативный API и согласование

Публичный вход — выбранный интерпретатор с установленным Poise:
`python -B -m poise requirements --config /absolute/project.json`.
stdin содержит один UTF-8 JSON-пакет ровно с полями `operation` и `input`.
stdout — один JSON и перевод строки; успех имеет exit 0, отказ — exit 2.
Ограничение полного входа задаёт `batch.max_input_bytes`, запросов/страниц — `batch.max_items`.

| Операция | Точные поля `input` | Результат |
|---|---|---|
| `query` | `queries` | Read-only снимок без постоянной записи. |
| `command` | `name`, `sql`, `rollback_sql` | Создать DML-файл и применить ожидающие миграции данных. |
| `apply` | `kind`: `schema` или `data` | Применить ожидающие файлы выбранной истории. |
| `rollback` | `kind`: `schema` или `data` | Откатить применённые файлы выбранной истории. |
| `squash` | `name`, `migrations` | Склеить указанные DML-миграции с проверкой полного результата. |
| `rebase` | `name` | Заменить историю данных полным снимком для текущей схемы. |
| `export` | `source`, `requirements`, `name` | Сгенерировать DML из существующей БД, без применения. |

`name` начинается с буквы или цифры, содержит только ASCII-буквы, цифры, `_`, `-`.
Имя не включает расширение; повтор существующего имени отклоняется.
`migrations` — непустой список уникальных ID исходных файлов без расширений.
`export.requirements` — `null` для полного экспорта либо непустой список уникальных ID требований.

Успешный `query` возвращает `status: "read_only"`, `export` — `status: "generated"`
и `migration` с путём файла. Остальные операции возвращают `status: "applied"`;
для применения/отката `migrations` перечисляет реально выбранные ID.
Это статус операции; он не означает завершение или приёмку Task.

Планирование без записи:

```json
{"operation":"query","input":{"queries":[{"id":"plan","kind":"plan_task","task_requirements":[{"text":"Сохранить результат задачи с происхождением требований.","applications":["APP-TRACE"]}]},{"id":"coverage","kind":"coverage","mode":"current"}]}}
```

Специализированные `kind`: `registry`, `coverage`, `gaps`, `chain` с `requirement_id`,
`plan_task` с `task_requirements`. План возвращает `status`, `gaps`, `chains` и `snapshot`;
сам он не утверждает и не записывает требования. `ready` означает структурную полноту цепочки,
а не согласие пользователя или реализацию проектируемого требования. При новом согласовании
показывают содержательные тексты, статусы и пустые звенья всех уровней System → Application → Task.
Ранее данное точное согласие сохраняется в `requirements_agreement` Task.

## Публикация и исторический снимок

В публикуемую Task передаётся `requirements_snapshot` из структурно допустимого
плана. Дополнительное решение пользователя — самостоятельный факт: отсутствие
`requirements_agreement` или значение `null` означает, что такого решения нет,
а не отказ пользователя. Само отсутствие не блокирует подготовленную Task и не
заменяется выдуманным согласием. Переданный ненулевой объект
`requirements_agreement: {"accepted": true, "chains": [...]}` проверяется по точным
полным цепочкам. Неверный тип, неполный объект, отказ или несовпадение цепочек
отклоняются; ложные значения не приравниваются к отсутствию.

Requirements gate проверяет снимок независимо от дополнительного решения; Task
сохраняет оба факта в metadata в той же транзакции, что и публикацию. Обычная Task
и пакет Sprint проходят одну границу проверки: отсутствующий, устаревший или
структурно неверный снимок отклоняется до записи Task. Отдельная явная операция
публикации согласования по-прежнему требует действительного подтверждения полных
цепочек и не допускает перезаписи уже опубликованного снимка. Готовность Task не
даёт полномочий на пересмотр требований, приёмку или интеграцию результата.

Поздняя правка живого реестра не меняет смысл опубликованной Task. Точный повтор создания использует
сохранённую идентичность запроса. Обычное исполнение использует замороженный requirements
snapshot/agreement. Если исполнитель доказывает, что текущие требования делают успешное продолжение
невозможным или обход неадекватен, он согласует restart с независимым проверяющим. Авторизованный
restart может сформировать новый согласованный requirements snapshot: policy задаёт поля по
умолчанию, а иной точный набор Task-полей проверяющий фиксирует в решении. Старое согласие и старые
chains остаются историей и не выдаются за актуальные. Изменение project/harness rules требует
отдельного согласия пользователя. Существующие исторические Task без снимка не дополняются
выдуманной цепочкой автоматически.

При повторном `ready` после разрешённого restart Task сравнивает свой текущий
snapshot/agreement с сохранённым. Совпадение направляет проверку в исторический
контекст: последующий дрейф живого Registry не переопределяет Task. Изменённый
контекст, в том числе у Task без `planning_revision`, проходит планирование и
проверку полных цепочек против живого Registry; отсутствующее дополнительное
решение остаётся отсутствующим, а переданное решение проверяется строго. Перед публикацией
проверяется, что реестр не изменился после подготовки. Повторная проверка читает
реестр в согласованной read-only SQLite-транзакции, сохраняя его данные.
При обнаруженном дрейфе Task остаётся в прежнем newborn-состоянии, а независимое
изменение Registry не откатывается. При успехе прежний snapshot/agreement сохраняется в истории
restart,
текущий контекст заменяется в той же Task-транзакции, что и промоция; отсутствующее
или несогласованное поле не заменяется историческим значением молча.

Выбор существующей Task объектом только с `id` — продолжение сохранённого состояния,
не новое предложение договора. Текущая проекция методов может законно отличаться
от первоначального договора. Она не подставляется в повторную проверку полного
контракта; проверка явно переданного full/canonical договора остаётся строгой.
[Публичный выбор Task](batch-work.md#выбор-существующей-задачи-по-id).

## Явные пустые проектируемые звенья

System/Application placeholder записывается через DML-миграцию с прежними `id`,
`level`, `status: "future"`, `text: ""`. Нового уровня и отдельного placeholder ID
нет. Связи записываются SQL в соответствующую таблицу связей. `plan_task` дополнительно допускает у
элемента
`task_requirements` явное `status: "future"` и пустой `text`; такой элемент —
проектируемый узел snapshot, а не созданная исполнимая Task.

Каждый пустой узел виден как `projected_placeholder` с уровнем; plan возвращает
`status: "gaps"` даже при полной связности. `gaps` реестра показывает и связанные
пустые System/Application. Пустой current или текст из одних пробелов отклоняется.
Заполнение текста и смена статуса используют тот же ID, поэтому связи не теряются.
Старые сохранённые snapshots не меняются от последующего заполнения live реестра.

## Query и фильтры

```json
{"operation":"query","input":{"queries":[{"id":"q","kind":"entities","table":"domain_areas","filter":{},"page":{"limit":2,"after":null}}]}}
```

Поля entity Query ровно `id`, `kind`, `table`, `filter`, `page`.

| Таблица entity Query | Публичные колонки |
|---|---|
| `requirements` | `id`, `level`, `status`, `text` |
| `domain_areas` | `id`, `business_name`, `definition` |
| `domain_entities` | `id`, `domain_id`, `business_name`, `code_name`, `definition` |
| `domain_actions` | `id`, `domain_id`, `business_name`, `code_name`, `definition` |

Значения публичных колонок — строки. Для `page.limit` допустимы целые значения
от 1 до `batch.max_items`; для списка `in` — от 0 до того же лимита.
Булевы значения не заменяют целые; неизвестные поля отклоняются.

`id` — непустая строка, уникальная в пакете, не ID записи.
Фильтр — AND по публичным колонкам: `{"id":{"eq":"D1"}}` или
`{"id":{"in":["D1","D2"]}}`. Для каждой колонки ровно один оператор;
значения — строки, список `in` не содержит повторов. `{}` выбирает все строки,
`{"id":{"in":[]}}` — ни одной. В query не поддерживаются SQL, выражения и произвольная сортировка.

Ответ: `{"status":"read_only","revision":7,"results":[{"id":"q","value":{"rows":[],"next":null}}]}`.
Все Query, включая смешанные специализированные, читают один snapshot.
Ошибка любого элемента отклоняет весь пакет без частичного `results` и записей.

`page` имеет ровно `limit` и `after`. Первая страница: `after: null`.
Следующая: передать полученный `next` без изменения. Строки упорядочены по
физическому первичному ключу (`BINARY`); offset не используется. `next` содержит
ключ последней возвращённой строки только при наличии следующей строки.
Курсор имеет ровно `revision`, `selection`, `key` (массив строк PK).
Selection включает `kind`, `table`, `filter` либо `a`, `b`; не включает ID Query
и размер страницы. Порядок ключей объекта и значений `in` незначим, но `eq` не
равен одноэлементному `in`; направление A/B значимо. Пропущенный фильтр B
нормализуется в `{}`. После проверки формы/Unicode/revision курсора устаревшая
revision имеет приоритет перед проверкой selection/key. В текущей revision
проверяются selection, длина/типы ключа и наличие ключа в выбранных строках.
Изменить размер страницы допустимо; продолжить старую revision — нет.

## Связи и операнды

| Таблица | Endpoints | Колонки и порядок PK |
|---|---|---|
| `requirement_links` | `system`, `application` | `system_id`, `application_id` |
| `requirement_entities` | `requirement`, `entity` | `requirement_id`, `domain_id`, `entity_id` |
| `requirement_actions` | `requirement`, `action` | `requirement_id`, `domain_id`, `action_id` |

A и B обозначают разные endpoints одной таблицы; разрешены оба направления.
Endpoint `system`/`application` автоматически ограничивает уровень требования.
A имеет ровно `endpoint`, `filter` и обязан выбрать **ровно одну** сущность,
даже когда B пуст. B имеет `endpoint` и необязательный `filter`: отсутствие
фильтра выбирает все допустимые сущности B; `null` не заменяет отсутствие.
B может выбрать 0, 1 или N строк. Каждая операция — 1:1 или 1:N, не N:M;
это не запрет разных сохранённых связей между несколькими требованиями и именами.
`domain_id` связи берётся из выбранного имени, не угадывается из требования.

```json
{"operation":"query","input":{"queries":[{"id":"links","kind":"relations","table":"requirement_entities","a":{"endpoint":"requirement","filter":{"id":{"eq":"A3"}}},"b":{"endpoint":"entity"},"page":{"limit":2,"after":null}}]}}
```

Relation Query имеет ровно `id`, `kind`, `table`, `a`, `b`, `page` и возвращает
сохранённые связи, не кандидатов для связывания. Порядок PK не меняется при
перестановке endpoints.

## Изменение требований через миграции

Сначала прочитать нужные требования и связи через `query`. Затем подготовить прямой SQL
изменения и точный SQL отката. Каждое постоянное изменение, включая связь или удаление,
проходит `command`: API сначала создаёт файл в настроенном каталоге DML приложения, затем применяет
ожидающую историю данных. Отдельной постоянной CRUD-записи нет.

Пример для предварительно прочитанной revision 53 (ID, текст и точные числа сверяют с постановкой
и фактическими данными):

```json
{"operation":"command","input":{"name":"0002_add_system_requirement","sql":"INSERT INTO requirements(id,level,status,text) VALUES ('SYS-EXAMPLE','system','future','Сохранять согласованный результат.'); UPDATE requirements_meta SET revision=54;","rollback_sql":"UPDATE requirements_meta SET revision=53; DELETE FROM requirements WHERE id='SYS-EXAMPLE';"}}
```

`sql` и `rollback_sql` — непустые SQL-строки. Для данных допустимы `INSERT`, `UPDATE`,
`DELETE`. DDL, Python-вычисления, импорт кода приложения, условные обходы и управление
транзакцией из SQL запрещены. Приложение создаёт обычный yoyo-файл `name.py` с
литеральными `step(sql, rollback_sql)` и зависимостями. Допустим также стандартный SQL-формат
`name.sql` с обязательным `name.rollback.sql`. Транзакцией управляет yoyo;
не добавлять `BEGIN`, `COMMIT`, `ROLLBACK` или `SAVEPOINT`.

Изменение существующего текста — обычный `UPDATE requirements ... WHERE id=...`;
откат содержит прежний точный текст. Связь — `INSERT`/ `DELETE` в таблице связи с обратным SQL.
Для удаления сначала сохраняют точные значения восстанавливаемых строк и учитывают FK-порядок.
Ревизия реестра также является данными: если изменение должно инвалидировать курсоры и планы,
соответствующий `UPDATE requirements_meta` и его откат явно включают в миграцию.
API не подставляет бизнес-операции или скрытые изменения revision вместо переданного SQL.

Файл миграции — версионируемый источник истории приложения независимо от Task. Ошибка применения
не означает, что файл
не был создан: перед исправлением проверить файл, фактические данные и историю yoyo.
Не повторять `command` с тем же именем вслепую. Исправленную неприменённую миграцию применяют
через `apply`; уже применённый опубликованный файл не переписывают ради нового изменения.

### Пример записи без Task

Общий [JSON-пакет](../examples/requirements-taskless-command.json) содержит буквальный SQL для
`SYS-TASKLESS` → `APP-TASKLESS` и явное изменение revision. Выполнять этот демонстрационный
пакет на отдельном настроенном приложении с инициализированной схемой, пустой историей `data`,
revision 0, отсутствующими демонстрационными ID и свободным именем `0100-taskless`.
Task DB для примера не требуется. Рабочий реестр CE или Poise для демонстрации не используется.
В реальном приложении сначала читают фактические строки, revision и историю, согласуют значения
и выбирают свободное имя миграции.

Из корня исходников или установленного пакета выбрать доступный интерпретатор Poise;
`project_json` — абсолютный путь конфигурации демонстрационного приложения,
`packet_json` — абсолютный путь к указанному общему JSON-файлу:

```bash
"$python" -B -m poise requirements --config "$project_json" < "$packet_json"
```

Ожидается `status: "applied"`, `migrations: ["0100-taskless"]`. Запрос
`{"operation":"query","input":{"queries":[{"id":"registry","kind":"registry"}]}}`
возвращает ровно два требования и связь из пакета, revision 1. До команды он возвращает
пустой реестр и revision 0. Публичный `rollback` с `kind: "data"` возвращает пустые требования
и связи с revision 0; `apply` с тем же `kind` восстанавливает те же строки, связь и revision 1.
Все пакеты подаются на stdin той же CLI с той же конфигурацией. Task DB остаётся отсутствующей.
Этот пример не является инициализатором реестра и не подходит для слепого повторения поверх
существующей истории.

## Применение и откат

```json
{"operation":"apply","input":{"kind":"schema"}}
```

```json
{"operation":"apply","input":{"kind":"data"}}
```

Каждая миграция выполняется собственной стандартной транзакцией yoyo с включёнными FK.
При ошибке откатывается текущая миграция; ранее успешно применённые миграции остаются в истории.
Для возврата данных используют тот же API:

```json
{"operation":"rollback","input":{"kind":"data"}}
```

`rollback` выбирает все применённые файлы настроенной истории, а не только последний.
После отката данных можно явно вызвать `rollback` с `kind: "schema"`.
Повторный накат выполняется через `apply` с тем же `kind`. В штатном ходе учёт применения
ведёт yoyo; пометка «применено» не заменяет фактическое исполнение SQL.
Редкое операторское восстановление описано в [правиле ошибок](#ошибки-и-восстановление).

## Склейка миграций задачи

```json
{"operation":"squash","input":{"name":"0003_combined","migrations":["0002_a","0002_b"]}}
```

Публичный `squash` выбирает настроенную историю приложения без Task.
Poise определяет порядок по истории и зависимостям yoyo, откатывает выбранные применённые
миграции в обратном порядке, склеивает исходный прямой SQL в порядке применения, а обратный —
в порядке отката. Внешние зависимости сохраняются; невыбранные файлы не переписываются.
Итог действительно применяется, откатывается и применяется повторно. Сравнивается полное
логическое содержимое хранилища, а не число затронутых строк. Это последовательная склейка,
а не вычисление итогового набора `INSERT`/`UPDATE`.

Отдельный адаптер завершения фактической Task сохраняет проверки её контекста, владельца,
worktree, изменяемого этапа и `allowed_paths`; DML/bootstrap для этой процедуры отображаются
в её рабочую копию. Это граница завершения Task, а не условие публичной записи реестра.
Перед замораживанием исходников на завершении изменяемого этапа Poise автоматически готовит
DML, добавленные данной Task относительно её базового Git-дерева. Несколько файлов объединяются;
единственный также проходит проверку отката и повторного наката. Неприменённый единственный
файл блокирует завершение до исполнения SQL. Если Task не добавляла DML, новый файл не создаётся.
Точная граница завершения — в
[договоре исполнения](task-execution-contract.md#требования-и-конфигурация).

## Замена истории после изменения схемы

```json
{"operation":"rebase","input":{"name":"0001_current_schema_data"}}
```

`rebase` сохраняет полное текущее содержимое в новой DML-миграции, обновляет единственный
bootstrap до новой схемы и удаляет заменяемые исходные файлы DML. Устаревший SQL, рассчитанный
на прежние колонки, не исполняется. В штатном API только для этой операции учёт старой истории
заменяется
на учёт новой; новая миграция реально проходит накат, откат и повторный накат с полной сверкой.
Проверка сохраняет административные строки начальной схемы, а не предполагает пустоту всех таблиц.
DDL остаётся в инфраструктурной истории приложения. Использовать `squash` для замены схемы нельзя.

## Экспорт и восстановление данных

```json
{"operation":"export","input":{"source":"/absolute/existing-requirements.sqlite","requirements":null,"name":"0001"}}
```

Источник открывается только для чтения. Полный экспорт переносит все таблицы приложения,
требования, связи и служебные значения; таблицы исполнения yoyo не являются данными требований.
Экспорт сверяет таблицы и колонки с применённой инфраструктурной схемой, требует одну строку
метаданных и проверяет SQL в отдельной временной БД стандартным yoyo. Он только создаёт DML-файл;
затем его надо применить. Источник не удаляется и не изменяется.

Для переноса выбранных требований передать их ID в `requirements`. Экспорт добавляет
необходимых предков, словарные записи и связи, исключает уже имеющиеся точные строки.
Несовпадение данных при том же PK, нарушение UNIQUE или FK отклоняются до публикации итогового
файла;
проверяются реальные ограничения целевой схемы, а не только Python-сравнение ID.

### Однократный импорт утверждённой поставки

Для первого переноса согласованного существующего реестра выполнить полный `export`,
проверить созданную DML-миграцию и восстановить из неё новое хранилище вместе с DDL-историей.
Импортировать именно согласованный полный исходный снимок, а не демонстрационные записи.
Существующий более новый реестр не заменяется повторным импортом без отдельного решения.

БД должна полностью создаваться из исходных историй. Начальная инфраструктурная DDL-миграция
создаёт схему, начальная DML-миграция в документации восстанавливает данные. Единственный
bootstrap документации описывает текущую схему, но не заменяет её историю и журнал yoyo.
Проверка переноса в отдельную БД включает все строки и структуры, `integrity_check`,
`foreign_key_check`, откат и повторный накат через тот же инструмент.

При переключении работающего хранилища сохраняют исходный файл только как временную страховку.
До копирования фиксируют риск потери данных, условие восстановления и срок жизни: успешная
полная сверка восстановленной БД, проверка действующего API и прекращение записи прежним способом.
После выполнения этих условий резервную копию удаляют. Переключение не подтверждается одним
успешным тестом на другой БД; нужен результат для явно выбранного работающего экземпляра.

## Конкурентная запись

Каждая публичная изменяющая операция удерживает настроенный файловый `requirements_lock`
один раз на весь вызов под project fence выбранного приложения. Внутренние шаги используют
стандартный backend yoyo и его блокировку для выбранной истории schema/data. Используются настроенные бюджеты ожидания SQLite/lock; второй собственный журнал
или движок миграций не создаётся. Проверка и применение DDL/DML не образуют одну распределённую
транзакцию с Task DB. Read-only запросы читают согласованный снимок.

Миграция должна явно выражать точные значения и обратное изменение. При конкурентном изменении
повторно прочитать действующие данные и фактическую историю; не перезаписывать чужой результат.
Повторное применение выбирает ожидающие ID истории yoyo. Имя нового файла не является
идемпотентным request receipt: конфликт существующего имени требует проверки фактического состояния.

## Ошибки и восстановление

Отказ возвращает `status: "rejected"`, причину и действие восстановления; формат отдельных
read-only ошибок следует их query-контракту. Отсутствующие пути — исправить явно выбранный профиль
через владельца конфигурации; отсутствующее хранилище явно инициализировать по его историям.
Ошибка пути записи — сверить настроенные DML/bootstrap и целевой файл. Ошибки Task/ветки/области
относятся к отдельному адаптеру завершения: продолжить фактическую Task и разрешённый этап
из её managed worktree. Отсутствующий адаптер не считается успешной подготовкой: возвращается
`requirements_migration_failed` с причиной. Ошибка SQL/ограничения — проверить исходные строки, исправить
неприменённый файл и повторить `apply`. Блокировка — дождаться её владельца и повторить операцию.

При редком подтверждённом расхождении фактических данных и журнала yoyo допустимо ручное
операторское исправление данных или журнала через стандартные средства инструмента.
До исправления остановить запись, зафиксировать фактические данные, применённые ID и причину
расхождения; действовать в пределах явного полномочия на конкретные объекты и действия.
Обеспечить исключение
других писателей и необходимую конечную резервную копию с условием восстановления и удаления.
Действия записать в журнал, после них сверить данные и историю, целостность и возможность
воспроизведения миграций. Не выдавать неподтверждённое исправление за успешное применение.

Это исключение относится к хранилищу требований и журналу yoyo, а не к Task DB, lifecycle,
claims или verification records. Оно не разрешает неутверждённое разрушение данных.
Штатная запись остаётся миграционной; отдельный движок восстановления, автоматическое
примирение, обходной CRUD и режим совместимости не добавляются.

## Сопровождение и происхождение изменения

Публичный composition строит контекст выбранного приложения, его store и project fence без
полного Task runtime. Временные ресурсы миграций размещаются в `requirements` под
настроенным `paths.state` / `paths.runtime`. `RequirementsMigrations` обслуживает настроенные ресурсы;
`TaskRequirementsMigrations` отдельно сохраняет контекст, область файлов и подготовленный
источник фактического завершения Task. `RequirementsCommands` передаёт публичную операцию
под одну блокировку, а подготовку завершения — настоящему адаптеру Task.

Порядок, зависимости и применённую историю определяет yoyo. Внутренний помощник удаления
только перечисляет физические файлы миграций и соседние `.rollback.sql`; это не новый
публичный API и не второй реестр истории. При сопровождении `squash`/`rebase` сохраняют
порядок эффектов, пары SQL/откат, невыбранные файлы, полную сверку данных и повторный накат.

Текущий независимый договор записи реализован исправлением
`POISE-REQUIREMENTS-INDEPENDENT-WRITE-20261117`: устранён цикл подготовки
`AIP-REQUIREMENTS-PREREADY-WRITE-001`, при котором запись нужных требований зависела от ready
задачи, а ready — от уже сохранённого снимка. История дефекта и доказательств сохраняется
в Git и материалах исправления. Английская проекция для агентов:
[Requirements registry](../../.agents/references/requirements-registry.md).
