# Сравнение ограниченного чтения файлов

## Решение и его область

Для Poise выбрано повторное использование существующего владельца `SourceReader`,
развиваемого из версии 044A. Его основа — явные диапазоны, идентичность всего файла,
подтверждение получения результата, поколения контекста и общая транзакция квитанций
для пакета чтений. Потребители обращаются к одному владельцу этого поведения.

ERP `content-read` решает связанную задачу учёта уже показанного текста. Его cache
сохраняет другую семантику идентичности и подтверждения. Перенос этого cache как
замены `SourceReader` не выбран.

Выбор относится к поведению и ответственности владельца. Самостоятельная поставка
провайдера Poise, его зависимости и расширение чтения байтами и продолжением требуют
собственной проверки на границе реальных производителя и потребителя. Данная
сравнительная работа не создаёт нового reader и не подтверждает готовность этих
расширений.

## Семь различий договора

| Ось | SourceReader 044A и исследованная текущая основа | ERP content-read | Основание |
| --- | --- | --- | --- |
| Диапазоны | Включительные номера строк от 1; явный ограниченный пакет диапазонов. Запрошенный конец за EOF отклоняется. | Один явно указанный файл; включительный диапазон строк либо полное чтение. Конец диапазона нормализуется до фактически прочитанной строки. | Разбор запросов и функции чтения; реальные ограниченные чтения ERP. Проверка ERP EOF в runtime не выполнялась. |
| Байты и кодировка | Читаются исходные байты, проверяется UTF-8, возвращаются выбранные строки с сохранением окончаний. `text_bytes` считает UTF-8 возвращённого текста. | Ограниченное чтение сохраняет окончания строк через `newline=""`, считает UTF-8 выбранного текста. Полное `read_text` нормализует окончания строк. | Код обоих производителей; для реального ERP диапазона 1–40 подтверждены 40 строк и 3783 байта. |
| Продолжение | Квитанция содержит `start` и `end`; схема результата не содержит `next` или EOF cursor. | Возвращаются нормализованный диапазон и количество строк; схема также не содержит `next` или EOF cursor. | Проверены схемы и формирование результата. Номера строк не объявляются байтовыми смещениями. |
| Версия файла | SHA-256 относится ко всем исходным байтам файла. Идентичность квитанции связывает путь, полный SHA, диапазон и поколение; чтение проверяет наблюдаемое состояние файла до и после. | Для ограниченного чтения SHA относится к выбранному тексту. Cache связывает его с диапазоном, сессией, epoch и reader kind. Полное чтение хэширует нормализованный текст. | Код `SourceFiles.read`/`receipt`, `_read_lines`/`_read_complete` и регистрация cache. Конкурентное изменение файла в runtime не проверялось. |
| Подтверждение получения | Совпавший результат подавляется после явного ACK известной квитанции в том же поколении. Регистрация и возврат текста сами по себе не доказывают получение клиентом. | Cache key регистрируется до возврата результата. Точный повтор может вернуть `unchanged` без отдельного ACK от потребителя. | Существующие проверки SourceReader и реальные первые/повторные вызовы ERP CLI двумя независимыми исполнителями. Доставка через native PostToolUse этим не доказана. |
| Поколения и повтор события | `reset` меняет поколение и очищает квитанции; повтор последнего `event_id` с той же причиной идемпотентен. Чтение принимает текущее поколение. | Compaction учитывается по сессии и `turn_id`; текущий epoch определяется из сохранённых событий. В наблюдавшихся чтениях возвращён epoch 0. | Код владельцев состояния и результат CLI. Native compaction events в этом исследовании не имитировались. |
| Пакет и ошибки | Весь пакет и общий объём текста проверяются до сохранения квитанций и ACK в одной транзакции. | CLI принимает один файл; проверяет диапазон, размер и границу вывода до регистрации результата. Единого входа для атомарного пакета нескольких файлов нет. | Код и узкие проверки. Отказ SourceReader по output budget сохранил байты receipt state. |

Проверенная граница изменения файла относится к обычному чтению поддержанного
файла. Из неё не выводится всеобъемлющая гарантия изоляции операционной системы.

## Производители и потребители

Путь SourceReader:

1. Клиент передаёт явные `cwd`, диапазоны, поколение и IDs подтверждённых квитанций.
2. Владелец проверяет пакет и выполняет чтения в общей транзакции метаданных.
3. Файловый адаптер получает текст, полный SHA файла и точный диапазон.
4. Владелец возвращает текст либо метаданные подтверждённого совпадения.
5. После получения текста клиент использует IDs квитанций в последующем ACK.

Каждый результат `unchanged` здесь должен объясняться тем же путём, полным SHA,
диапазоном, поколением и подтверждением известной квитанции. `text_bytes`
объясняется фактически возвращённым UTF-8 текстом.

Путь ERP:

1. Агент вызывает CLI для одного файла и конечного диапазона через настроенное окружение.
2. Библиотека получает выбранный текст, его SHA и метаданные диапазона.
3. После проверок вывода владелец регистрирует cache key текущей сессии и epoch.
4. CLI возвращает `content` либо `unchanged` по состоянию регистрации.

Для ERP `unchanged` объясняется совпадением зарегистрированной экспозиции текста.
Этот факт не заменяет ACK-договор SourceReader. Совпадение слова `generation`
также не делает одинаковыми правила повторного события.

## Основание повторного использования

Существующий SourceReader уже владеет поведением, необходимым для подтверждённого
ограниченного чтения: полная идентичность файла, явный ACK, поколения и атомарность
пакета. Это соответствует направлению [публичного договора Poise](contract-poi.md#6-tool-descriptor-and-generic-boundary-examples).

Перенос ERP cache не добавляет байтовые диапазоны или продолжение и одновременно
меняет смысл подтверждения. Повторный импорт всего архива 044A также не сохраняет
принятый текущий разбор неизвестных параметров конфигурации. Поэтому основой выбран
текущий владелец SourceReader; ERP остаётся источником сравнения ответственности.

При подключении самостоятельного Poise транспорт и зависимости должны сохранять
одного владельца поведения. Фактическая доступность без Task runtime доказывается
проверкой готового провайдера в поддержанном окружении. Исследование не определяет
будущие классы, размещение пакетов или новое wire schema.

Следующее проектирование расширенного чтения должно явно определить единицы
диапазона, UTF-8 границы, идентичность исходного файла, смысл `next`/EOF и связь
продолжения с ACK и поколением. Исследованные интерфейсы не считаются уже готовой
реализацией этого расширения.

## Правильное использование существующих интерфейсов

Для текущего SourceReader используйте его [действующую инструкцию](../../../docs/workflows/source-reader.md#прямой-инструмент)
с явными политикой и отдельным состоянием контекста клиента. Получите текущее
поколение, передайте конечные диапазоны и подтверждайте действительно полученные
квитанции. После восстановления контекста выполните предусмотренный `reset` и
получите нужные тексты в новом поколении.

Для ERP используйте его установленный `ai-assistant/agent/content-read.py` через
настроенный repository Python launcher с явными `--path` и `--lines START:END`.
Ограничение строк и ограничение байтов проверяются вместе. Наблюдавшиеся 8192 байта
были значением локальной политики исследования, а не общим пределом будущего Poise.
Подготовка окружения и конфигурация принадлежат инструкции самого ERP.

Рабочие параметры и хранилища остаются у своих владельцев. Данный документ не
вводит новую конфигурацию или команду.

## Проверенные наблюдения и пределы

Подтверждены исходный архив и его manifest, карта пяти совпадений и трёх изменений,
конкретные ERP источники, реальные ограниченные чтения и повтор без отдельного ACK.
На исследованном текущем Poise выполнены девять выбранных существующих проверок
reader и шесть поддерживаемых smoke-проверок. Дополнительная узкая проверка
подтвердила сохранение receipt state при превышении общего output budget.

Runtime архива 044A не запускался. Для ERP не выполнены runtime-сценарии EOF,
конкурентного изменения файла, различий newline, compaction и прерывания доставки.
Кодовые выводы по этим вопросам отмечены отдельно от исполненных проверок.
Полная квалификация нового провайдера и расширенного протокола остаётся отдельной
работой по их действительным договорам.
