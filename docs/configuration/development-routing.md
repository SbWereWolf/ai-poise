# Маршрутизация разработки самой AI poise

Обновлено: **2026-09-16**.

## Декларативные условия выбора skills

`config/development/skill-selection.json` — метаданные C003, а не ERP profile-документ
и не обязательная схема чужого репозитория. Источник identity/purpose/class —
существующий [SkillCatalog](skill-catalog.md). Инструкции и команды не копируются.

Формат `ai-poise-skill-selection-1` явно ограничен `subject=ai-poise`:
`facts` перечисляет допустимые факты; `rules` содержит уникальный `id`, числовой
`priority`, список `skills` и `when`. Условие состоит из `stages` (точные ID этапов),
`paths_any` (относительные glob-пути), `facts_all` (все перечисленные факты).
Пустое условие не ограничивает соответствующую ось; непустые оси соединяются через AND.
Порядок приоритетов возрастающий, затем ID; дубликаты выбранных skills удаляются.
Факт `review`, `recovery`, `release` и т. п. сообщает вызывающая операция, а не
угадывает классификатор из текста запроса или имени ветки.

Каждый skill каталога либо упомянут в selection rules, либо явно указан в `excluded`
с причиной. Исключение из автоматического выбора **не удаляет skill**. Например,
Laravel/Vue/Vitest/PHPUnit остаются поставленными инструкциями, но не выбираются для
текущей Python-кодовой базы AI-poise. Нет автоматического наследования технологий ERP
или переноса этой конфигурации на произвольное разрабатываемое приложение.

`SkillSelection` проверяет неизвестные skills/facts, дубли и некорректные пути, но
сам не выполняет routing. Единственный потребитель условий и владелец выбора — C004.
Загрузка metadata сама по себе не означает запуск проверок, загрузку всех references
или изменение lifecycle. Факты и неизвестные пути должны оставаться видимыми в результате.

## Единый router и прямой вызов

`DevelopmentRouting` — единственная композиция выбора. Доменные `SkillSelection`
и `RoutingPolicy` проверяют декларации и сопоставляют факты; файловый адаптер читает
метаданные, scoped AGENTS и выбранные SKILL.md. Ни инструкции, ни команды проверок
не переписываются в routing policy.

Прямой инструмент `tools/route_development.py` получает через stdin точный объект:

```json
{
  "checkout": "/absolute/path/to/an-ai-poise-copy",
  "stage": "implementation",
  "handler": "produce",
  "scope_paths": ["src/poise/modules/skills/**"],
  "changed_paths": ["src/poise/modules/skills/catalog.py"],
  "facts": [],
  "required_methods": [],
  "registered_methods": [],
  "result_contract": {"sections": ["report"]}
}
```

Параметры `--catalog`, `--selection`, `--policy`, `--packages` задают конкретные пути
к `.agents/skill-catalog.json`, `config/development/skill-selection.json`,
`config/development/routing.json`, `config/testing/test-packages.json` работающего
экземпляра. Относительные CLI-пути вычисляются обычным способом от cwd процесса.
`checkout` — только проверяемая копия **AI-poise**, подтверждённая `project.name`;
это не место поиска executable, hook или operational configuration. Из копии читаются
только применимые `AGENTS.md` и выбранные `SKILL.md`, не все справочники. Для glob scope
читаются AGENTS предков его буквального префикса, а не все вложенные документы.

`known_paths` описывает распознаваемые области; `handler_facts` декларативно добавляет
факты для обработчика; `checks` сопоставляет пути с ID **существующих** тестовых
пакетов AI-poise. Неизвестные packages отклоняют конфигурацию до чтения копии.
Неизвестные факты, пути, обработчик, отсутствующие обязательные методы или skills
попадают в `missing_inputs`. Не возникает fallback на full suite.

`ready`/exit 0 означает, что выбор получен без перечисленных пропусков, **не** что
код проверен. `needs_inputs`/exit 1 сохраняет частичный результат и диагностику;
ошибка формы/config/path даёт `rejected`/exit 2. `required_methods` никогда не теряются
и не заменяются `suggested_packages`; обе коллекции содержат разные виды ID.
`checks.executed` всегда false. Рекомендация пакета не доказывает полноту тестов:
исполнитель выбирает минимальные task-specific проверки и штатный bounded smoke.

## Подключение к bootstrap и обновлению контекста

Необязательный раздел `development_routing` существующего project manifest содержит
ровно `catalog`, `selection`, `policy`, `packages`: непустые конкретные файловые пути.
Пути относительно manifest разрешаются существующим способом, абсолютные остаются
абсолютными. Настройка относится только к разработке AI-poise. Без раздела остальные
проекты работают как прежде; никакой общей миграции конфигурации нет. Для установки
раздела использовать существующий [редактор проекта](project-setup.md#обновление-действующего-проекта), не ручное
изменение managed-файла. Единственное новое поле разрешено добавить целиком через
`manifest_edits` с `path=["development_routing"]`; revision, quiescent-project и
атомарная публикация остаются прежними. Редактор валидирует форму раздела; доступность
метаданных проверяет загрузка router. Подключение следует проверить прямым вызовом
до bootstrap. Это не разрешение добавлять произвольные отсутствующие поля. Поставленный персональный project manifest автоматически
не изменяется: его пути и окружение здесь не установлены и не проверены.

После явного подключения bootstrap возвращает `development_route` через того же
владельца, что прямой инструмент. Он использует фактический текущий этап, его
`allowed_paths`, накопленный Git diff от исходного `base` Task (staged/unstaged,
переименования как удаление/добавление) и untracked-файлы. Проверки поступают из
существующего `_select_checks`, включая автоматические обязательства, а не из второго
реестра методов. Без dedicated worktree используется **уже существующее** поведение:
конкретный настроенный checkout проекта. Размещение worktree не меняется.

Обновить результат после изменения файлов или для дополнительных явных фактов можно
через тот же публичный work packet:

```json
{"operation":"routing","input":{"facts":["self_review"]},"messages":[]}
```

Текущая Task должна принадлежать этой сессии. Операция не изменяет её version, stage,
claim, acceptance или submission. Явные дополнительные facts относятся к одному
вызову; следующий bootstrap заново выводит факты из своего контекста, не наследует
скрыто старые overrides. Без configured router запрос отклоняется.

## Производный снимок и воспроизведение

Результат содержит исходные факты, IDs/пути/SHA-256 правил и skills, digest четырёх
конфигураций, форму результата этапа и `route_digest`. Одинаковые факты и байты дают
одинаковый результат. Время, имя сессии и случайный ID в digest не добавляются.

`--snapshot /concrete/path/route.json` явно сохраняет атомарный снимок с mode 0600;
bootstrap/refresh заменяет один `development-routing.json` в существующем runtime
каталоге своей сессии. Это **не ledger и не новый lifecycle**. Возвращённый route
можно сохранить вместе с обычным handoff/checkpoint; временный файл сам по себе не
обещает пережить очистку runtime. Прямой вызов без `--snapshot` ничего не записывает.

`read_snapshot` проверяет schema и digest исторического результата; это контроль
целостности, не криптографическая подпись. Он не объявляет старый снимок актуальным
для нового содержимого: для этого нужно повторно вызвать router. После загрузки
операционная конфигурация фиксируется в экземпляре сервиса; её изменение требует
нового экземпляра. Снимок не обеспечивает транзакционное чтение всех файлов при
параллельном редактировании; не следует выполнять refresh одновременно с записью
проверяемых правил. Пути и scope не меняют разрешение кода работающего Poise.

## Выбор проверок по входам тестовых пакетов

Обновлено: **2026-09-16**, C017. Тот же `DevelopmentRouting` дополняет маршрут
`test_impact`, полученным от существующего `AiPoiseTestPackages`. Вход — **конкретные
относительные пути diff** в явно указанной копии AI-poise; `scope_paths` остаётся
плановой областью и может содержать glob, `changed_paths` — только файлы, без glob.
Переименование передаётся двумя путями (старый/новый); удалённый файл сопоставляется
с декларацией даже после исчезновения с диска. Symlink за пределы проверяемой папки
отклоняется. Метаданные инструментов по-прежнему берутся из явно переданных конфигураций,
а не ищутся заново в рабочей копии.

Сопоставляются три категории каталога test packages: `source`, `tests`, `fixtures`. `*` не пересекает каталог, `**` допускает ноль или больше каталогов.
`direct_packages` перечисляет непосредственных владельцев изменённого входа;
`integration_packages` — их явно объявленные соседние границы **одного шага**.
Рекурсивное подтягивание всего графа отсутствует. Общая фикстура затрагивает все
пакеты, которые её действительно объявили. `reasons` сохраняет файл, пакет,
владельца, категорию и совпавший pattern; `integration_reasons` сохраняет источник
добавления соседнего пакета.

`checks.suggested_packages` — объединение impact и существующих routing-деклараций.
`checks.required_methods` содержит прежние обязательные методы Task, включая методы
для нового поведения. Impact не отменяет их, не регистрирует команд и не выдаёт
рекомендацию за покрытие требований. Неизвестный в package map путь даёт
`unmapped_test_input:<path>` и `needs_inputs`, даже внутри известного `src/**`.
Это требует уточнения существующего каталога/точного Task check, а не запуска full suite.

Результат пересчитывается каждым direct/refresh/bootstrap-вызовом по актуальным
фактам; при изменении operational metadata создаётся новый экземпляр router.
Исторический route snapshot не подтверждает новые байты. Для **явно выбранного**
пакета используется прежний `tools/run_ai_poise_test_package.py --root /concrete/path
--package <id> --timeout <seconds> --fresh`, за которым остаются прежние cache и
`RegisteredCheckRunner`. Прямой routing сам ничего не запускает и не создаёт кэш.
Этот протокол не навязывается приложениям, которые разрабатываются через Poise.


## Авторский архитектурный gate

C029.4 использует тот же `DevelopmentRouting`, не второй router. Необязательное поле
operational routing policy `authoring_boundary_gate` содержит конкретный `policy` и
явные `handlers`. Поставленная конфигурация выбирает Python boundary rules AI-poise
для `produce`. Отсутствующая регистрация не объявляется пройденной проверкой; отсутствующий
сам policy-файл или неверная регистрация отклоняют загрузку, а не выключают gate молча.

Gate запускается перед авторским submission, не при выборе маршрута. Ошибка не меняет
Task/claim/stage и исправляется повтором той же сдачи. Проверяемая рабочая папка не
подменяет operational configuration. Подробный контракт, точные исходы и ограничения:
[проверка архитектуры перед авторской сдачей](../workflows/architecture-boundaries.md#проверка-архитектуры-перед-авторской-сдачей).
