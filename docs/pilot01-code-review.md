# Осмотр кода и исправлений HARNESS-PILOT-01

Обновлено: **2026-09-07T14:15:55+05:00**.

## Ответственность

ProjectBlueprint/Survey — чистый домен; ProjectCommands использует порт. FileProjectSetup
выполняет пути, snapshots, локальный Git probe, lock и публикацию. Task/Sprint tables не
используются. Финальная проверка полного проекта — тот же load_config, что в runtime.

## Найденные и воспроизведённые дефекты

1. Первая реализация обращалась к Git до полной проверки проекта. Тест с неверным limits
и запрещённым probe показал нарушение порядка. Теперь сначала staged load_config, затем probe.
2. `base_ref` списком и `remote` числом приводили к TypeError, не понятному отказу. В общем
validator добавлены проверки обязательных строк Git; повторные тесты дают HarnessError.
3. `paths.state=project.json` публиковался, хотя следующий запуск не мог создать state.
Запрещено пересечение mutable state с manifest/process/receipt. Правило применяется и runtime.
4. Первая версия self-pilot не описывала subject method будущего check stage. Штатный
creation validator правильно отклонил задачу. Исправлен пример, а не ослаблена EvidencePolicy.

## Проверенные границы

Повтор не перечитывает новый шаблон поверх опубликованного snapshot и не перезаписывает
изменённый working config. Индекс БД не создаётся генератором. Git probe не контактирует remote;
настроенный remote не называется доступным. Atomic directory publication относится только
к локальному новому каталогу, не к Git/SQLite/network общей транзакцией.

## Известные ограничения

Create-only: изменять действующий manifest этим инструментом нельзя. Один репозиторий на
runtime пока сохраняется. Не реализован универсальный questionnaire UI; текстовый интерфейс
достаточен для WSL и batch-драйвера. Живой Codex/IDE/Gmail не проверяется этим пилотом.
Полный регрессионный отчёт содержит и первоначальные неуспехи, не только удачные повторы.
