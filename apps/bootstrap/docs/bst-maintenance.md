# Обслуживание среды через Bootstrap

Эта страница описывает реализацию T027: самостоятельная оболочка Bootstrap
передаёт обслуживание существующему `environment-maintenance==0.1.1`.
Единственный владелец последовательности действий —
`environment_maintenance.engine.execute`; Bootstrap выбирает цели, фиксирует
входы, ограничивает выполнение и формирует общий отчёт. Он не копирует ядро,
не создаёт Task или Session и не принимает результаты разработки.

[Целевой контракт Bootstrap](contract-bst.md) задаёт публичную границу.
[Описание профилей T026](bst-profiles.md) и [основа оболочки T022](shell-bst.md)
сохраняют исторические срезы. Их прежнее утверждение о неизбежном
`maintenance_unavailable` для непустого профиля больше не описывает текущий
исполнитель: при доступном ядре запускается обслуживание. Отсутствующее или
неподходящее ядро по-прежнему даёт `action_required`, код 3, а не ложный успех.
Публичные адаптеры ремонта хранилищ соседних приложений остаются границей T028.

## Установка и вызов

Подтверждённый контур — Linux и Python 3.13.5. Надзор за процессами требует
доступных `/proc`, libc `pidfd_open` / `pidfd_send_signal` и `prctl` для
subreaper. Работа на Windows и замена этих средств сигналами по неподтверждённым
PID не заявляются. Отсутствие пригодного надзора до старта worker диагностируется
как `maintenance_unavailable` у выбранной цели.

Используется именно выбранный интерпретатор. Зависимость объявлена в
[requirements.txt](../requirements.txt); worker проверяет версию `0.1.1`,
не ищет другую установку и сохраняет политику `-S` / `-s` вызывающего Python.
Загрузка Bootstrap не требует импорта Poise, его runtime или соседнего приложения.

Ниже `PYTHON`, `CHECKOUT` и `BOOTSTRAP_CONFIG` — явные значения оператора,
а не встроенные пути или обязательные переменные Bootstrap. Первая команда
устанавливает зависимость в выбранную среду и выполняется отдельно от диагностики;
сам Bootstrap её не запускает. Примеры предполагают уже подготовленные
операционные профили и квалифицированные команды владельцев.

```bash
PYTHON=/absolute/path/to/installed/python
CHECKOUT=/absolute/path/to/checkout
BOOTSTRAP_CONFIG=/absolute/path/to/bootstrap.json

"$PYTHON" -m pip install -r "$CHECKOUT/apps/bootstrap/requirements.txt"
"$PYTHON" -B "$CHECKOUT/apps/bootstrap/bin/bootstrap" --config "$BOOTSTRAP_CONFIG" check --target alpha
"$PYTHON" -B "$CHECKOUT/apps/bootstrap/bin/bootstrap" --config "$BOOTSTRAP_CONFIG" infra --target all --dry-run
"$PYTHON" -B "$CHECKOUT/apps/bootstrap/bin/bootstrap" --config "$BOOTSTRAP_CONFIG" deps --target alpha --set python=/absolute/path/to/python
```

`--config PATH` обязателен и расположен перед `infra`, `deps` или `check`.
После команды допустимы один `--target TARGET`, один `--dry-run` и повторяемый
`--set NAME=VALUE`. `--set` сохраняет порядок; последнее значение одного имени
имеет приоритет. Неизвестные аргументы, повтор одиночного флага или пропущенное
значение отклоняются. Нет флагов `--catalog`, `--repairs` и `--values` прежнего
одиночного интерфейса Poise: ссылки и значения задаются профилем. Публичный stdin
не является JSON-интерфейсом; внутренний worker-протокол не предназначен для caller.

## Конфигурация и операционные профили

[Поставляемый Bootstrap config](../config/bootstrap.json) содержит ровно
`schema`, `projects_root`, `default_target`, `target_env`, `limits`.
Версия — `stride-bootstrap-config/v1`. Относительный `projects_root` разрешается
относительно файла этого конфига, не cwd вызывающего процесса. Обязательные
пределы: `max_targets`, `max_target_bytes`, `max_output_bytes`,
`target_timeout_seconds`, `run_timeout_seconds`. Counts/bytes — положительные
целые, durations — положительные конечные числа; bool не подменяет число.
Значения поставляемого примера не являются скрытыми значениями по умолчанию.

Общий для трёх команд приоритет выбора:

```text
явный --target > присутствующая переменная target_env > default_target
```

При `target_env: null` источник environment отключён. Пустое присутствующее
значение переменной — ошибка, не повод перейти к default. Явная цель важнее
даже неподходящего env. `all` раскрывается в непосредственные `<id>.json`
выбранного корня, отсортированные по ID; подкаталоги и другие расширения не цели.
Ссылка или специальный файл с выбранным JSON-именем не пропускается молча:
он получает ошибку квалификации. Новый корректный профиль входит в следующий
`all` без изменения исходников. Неизвестный ID не заменяется на `all`.

Каждый `stride-bootstrap-project/v1` имеет ровно шесть полей:

| Поле | Значение |
| --- | --- |
| `schema` | `stride-bootstrap-project/v1` |
| `id` | ID, совпадающий с именем файла; `all` зарезервирован |
| `catalog` | Обязательный относительный путь к каталогу требований |
| `repairs` | Относительный путь к таблице ремонта либо явный `null` |
| `values` | Объект значений объявленных параметров |
| `parameter_values_files` | Упорядоченный массив относительных путей к JSON-объектам значений |

Пути assets разрешаются от `projects_root`, допускают подкаталоги, но не
абсолютные пути, `..`, пустые компоненты, обратную косую черту или symlink.
Файлы читаются как обычные файлы без следования ссылкам; FIFO/устройства не
принимаются. Размер записи вместе со всеми считанными assets ограничен
`max_target_bytes` каждой цели. Повторное чтение одного asset также расходует
бюджет. JSON должен быть UTF-8 без повторяющихся ключей, нечисловых констант и
неконечных чисел; допускается только ограниченная глубина структуры.

Рабочий `config/projects/` не отслеживается Git. Отдельные
[пример профиля](../examples/maintenance/alpha.json) и
[пример каталога](../examples/maintenance/alpha-assets/requirements.json)
не копируются автоматически и не заменяют конфигурацию установки.
В примере marker и интерпретатор требуют явной настройки. Его `apply`
преднамеренно завершается ошибкой до настройки публичной команды владельца;
это не готовый ремонт и не команда создания чужой БД.

## Каталог требований и таблица ремонта

Каталог `environment-maintenance/requirements/v1` содержит `parameters`,
массив `requirements` и, при необходимости, `inherit_env`.
Требование задаёт уникальный `id`, `kind` (`infra` или `deps`), `check`,
`apply`, `recommendation`; `description` необязателен. Действие задаётся
массивом `argv` и явным `timeout`; допустимы также `cwd`, `env`,
`max_output_bytes`. Shell-строка не заменяет `argv` и не исполняется оболочкой.
Доверенный оператор может сам указать shell executable: это уже ответственность
квалифицированной команды, не безопасная интерпретация произвольного ввода.

Перед первой командой конкретной цели ядро валидирует весь её каталог и все
repair routes, включая требования другой категории. Некорректный параметр,
каталог или маршрут не разрешает частично начать эту цель. Ошибка одной цели
не отменяет остальные выбранные цели и не превращает обход в общую транзакцию.

**`repairs` внутри `environment-maintenance/repairs/v1` — объект
`requirement_id → command`, не массив.** Это существенное уточнение относительно
первой квалификации T026. Ссылка действия имеет вид `{"repair":"owner-readiness"}`;
её ID должен совпадать с ID требования. Таблица обязана содержать этот маршрут.
Рекурсивная ссылка `repair` внутри таблицы запрещена. Рекомендация — непустой текст
либо обращение к repair-модулю этого же требования, а не произвольная другая команда.

Публичный `RepairRouter` ядра передаёт adapter запрос
`environment-maintenance/repair-request/v1` с `requirement_id`, режимом
`check`, `apply` или `recommend`, параметрами и наблюдаемым отказом.
Ответ — `environment-maintenance/repair-result/v1` с теми же ID/режимом и
согласованным status. Успешный код процесса не заменяет проверку domain-ответа.
Bootstrap не разбирает чужую схему БД и не добавляет собственный repair verb.

## Snapshot, параметры и cwd

До первого действия фиксируются имена всех выбранных целей и прочитанные
project/catalog/repairs/value-file объекты. Этот `snapshot` передаётся worker
через приватный ввод; изменение файлов после freeze не меняет текущие входы
и учитывается только следующим вызовом. Проверяются наблюдаемые изменения
идентичности/размера файла при чтении. Это не атомарная межфайловая транзакция:
публикация операционных файлов остаётся обязанностью их владельца.

`config_digest` — SHA-256 канонического UTF-8 JSON
`{project, catalog, repairs, values_files}`: ключи объектов отсортированы,
пробелов нет, массив value-files сохраняет порядок, `repairs: null` сохранён.
Digest отражает прочитанные входы, не разрешённые CLI/env-значения.
Он выводится только если у каждого catalogue parameter явно `secret: false`;
`secret: true` или отсутствие явной классификации подавляет digest до `null`.
При ошибках квалификации/параметров/каталога он также может быть `null`.

Значения `values` дополняются `parameter_values_files` слева направо;
затем существующий resolver ядра применяет приоритет:

```text
catalogue default < merged target values < declared environment < last explicit --set
```

Поддерживаются `string`, `integer`, `boolean`, `number`. Числа и boolean в CLI/env
разбираются как JSON, строки остаются строками. Неизвестные, отсутствующие или
неподходящие по типу параметры дают `invalid_target_parameters` именно этой цели.
При `all` один override не становится автоматически допустимым в чужом каталоге.
Подстановка `${name}` однопроходная: результат подстановки не раскрывается повторно.

Host environment копируется один раз при входе в оболочку. Binding параметра
через `env` и разрешение наследования команды через `inherit_env` — разные вещи.
Ядро передаёт subprocess только перечисленные `inherit_env` и явный `env`
действия; оно не наследует всё окружение скрыто. Для разрешения executable через
PATH требуется осознанная конфигурация, абсолютный `argv[0]` исключает эту зависимость.

Без `cwd` обычное действие исполняется из исходного каталога требований;
относительный `cwd` разрешается от него. Для repair-команды базой служит исходный
каталог repair-файла, а не временная директория snapshot. Worker сохраняет эту
семантику через приватный cwd alias; абсолютный cwd и буквальные `${...}` после
однократной подстановки не раскрываются снова. Заморожены конфигурационные
объекты, но не содержимое внешних executable и не состояние обслуживаемых ресурсов.

Ядро выполняет редактирование секретов в видимом report по своим объявлениям
`secret`; оболочка не выводит приватный snapshot или текст исключения с параметрами.
Это не универсальный фильтр любых секретов: незадекларированные чувствительные
данные, внешние логи и видимость argv в ОС требуют политики владельца adapter.
Секретные операционные assets нельзя помещать в открытый handoff.

## Check, apply и повторный check

Все выбранные цели обрабатываются последовательно. Внутри цели порядок требований
и алгоритм check/apply/recheck сохраняются за `engine.execute`.

| Вызов | Категории | Действия после непрошедшего initial check |
| --- | --- | --- |
| `check`, включая `--dry-run` | `infra` и `deps` | Рекомендация; `apply` не вызывается |
| `infra --dry-run` | `infra` | `planned_apply` и рекомендация без `apply` |
| `deps --dry-run` | `deps` | То же для `deps` |
| `infra` | `infra` | `apply`, затем повторный check |
| `deps` | `deps` | То же для `deps` |

Прошедший initial check даёт требованию `satisfied`, без ремонта. При разрешённом
ремонте final check выполняется и после завершившегося неуспешного `apply`.
`repaired` возможен только при успешных **обоих** наблюдениях:

| Apply | Final check | Итог требования |
| --- | --- | --- |
| passed | passed | `repaired` |
| passed | failed | `failed` |
| failed | passed | `failed` |
| failed | failed | `failed` |

Успешный `apply` без успешного recheck не означает готовую среду. Отчёт ядра
сохраняет `initial_check`, `apply`, `final_check`, рекомендацию и причину отказа,
если соответствующие действия были выполнены. В `check`/dry-run выполнение
`apply` запрещено. Сами check/recommend-команды обязаны быть read-only по
публичному контракту adapter; имя команды и нулевой счётчик apply не доказывают
безопасность произвольного executable.

## Результат и неопределённые эффекты

Обычный ответ — один UTF-8 JSON `stride-bootstrap/v1` с завершающим переводом
строки. Его поля: `schema`, `command`, `dry_run`, `selection`, `status`,
`exit_code`, `targets`. `selection` содержит `requested`, `source`, `resolved`;
на каждый выбранный ID приходится ровно одна строка в том же порядке.

Строка цели содержит `target`, `config_digest`, `status`, `exit_code`, `effects`,
`core`, `error`. При достоверном результате `core` сохраняет полный
`environment-maintenance/result/v1`, включая action stdout/stderr и поля ядра;
это не его сокращённая проекция. При ошибке входов, отсутствии ядра или
недостоверном worker-ответе `core: null`. Ошибка каталога от публичного loader
попадает в `invalid_target_catalogue`, без выдуманного CLI-отчёта ядра.
`error` — `null` либо объект `code`, `message`, `retryable`.

| Effects | Что утверждается |
| --- | --- |
| `none` | Apply не вызывался: read-only режим либо подтверждённый отказ до него |
| `applied` | Есть завершённая попытка apply; её ненулевой код не отменяет факт попытки и не обещает успех |
| `unknown` | Apply мог начаться, но завершение/эффекты не подтверждены; автоматический повтор запрещён |

Для записей apply таймаут, отрицательный exit code, отсутствующий или неверно
типизированный exit code либо неполная запись дают `unknown`, а не `applied`.
Полный report с неуспешным final check сохраняется и при этом исходе.
Отсутствие успешного результата нельзя использовать как доказательство `none`.
`effects` описывает попытки apply, а не атомарность ремонта и не отсутствие
произвольных побочных эффектов неправильно настроенной диагностической команды.

Приоритет общего результата вычисляется по всем строкам:

```text
failed или not_started > action_required > repaired > ready > not_required
```

`failed` соответствует process exit 4, `action_required` — 3,
`ready`, `repaired`, `not_required` — 0. Пустой выбранный набор или отсутствие
требований нужной категории даёт `not_required`. Частичный `all` не скрывает
ошибку одной цели успехом другой. Общий status не является приёмкой Task.

Глобальный отказ до запуска worker имеет отдельную форму: `schema`,
`status: rejected`, `exit_code: 2`, `error`, `targets: []`.
Коды `invalid_request`, `invalid_bootstrap_config`, `invalid_selector`,
`target_not_found`, `projects_unavailable`, `limit_exceeded` не означают
частичного ремонта. Неполный stdout, закрытый transport или внешнее принудительное
завершение нельзя считать полноценным JSON-отчётом и успехом.

## Пределы времени, вывода и времени жизни процессов

Ядро применяет явный `timeout` действия: положительное число до 3600 секунд.
Action `max_output_bytes` при указании — целое от 1 до 16777216; без него ядро
использует 262144 байта для захвата каждого stdout/stderr. Усечённый action output
помечается `capture_complete: false`, действие не считается passed. Это сохранённое
поведение ядра, а не молчаливое усечение внешнего JSON оболочкой.

Bootstrap дополнительно ограничивает worker через `target_timeout_seconds` и
оставшееся `run_timeout_seconds`. Общий deadline относится к последовательной
фазе выполнения после freeze, не является обещанием точного wall-clock предела
чтения файлов и cleanup. По истечении target deadline цель получает
`failed/4`, `target_timeout`; последующие цели запускаются, пока остаётся время.
Для ещё не начатых целей после общего deadline создаются `not_started/4`,
`run_deadline_exceeded`, `effects: none`; итог run — `failed`.

До первого worker резервируется место под полный безопасный результат каждой
выбранной цели. Если `max_output_bytes` не вмещает этот резерв, возникает
глобальный `limit_exceeded/2` до эффектов. Диагностический rejected-ответ
остаётся целым даже при пределе меньше его собственной длины.
Во время исполнения ограничен захват worker output и размер собираемого
UTF-8 envelope с переводом строки. Не помещающийся полный report заменяется
ограниченной строкой `failed/4`, `output_limit_exceeded`, `core: null`, а не
обрезанным JSON и не post-effect `rejected/2`. Резерв для оставшихся целей сохраняется.

При timeout/недостоверном transport/переполнении `check` и dry-run сохраняют
`effects: none`; mutating-вызов после старта worker консервативно получает
`unknown`. Никакого автоматического повторного apply нет. Для восстановления
после неопределённого исхода сначала нужна диагностика фактических ресурсов
и решение их публичного владельца.

При аварийном завершении надзор прекращает принадлежащие worker дочерние процессы,
включая обнаруженные новые сессии и усыновлённых сирот; PID identity закрепляется
pidfd. При **нормальном полном возврате ядра** надзор закрывает дескрипторы и
восстанавливает режим subreaper, но не уничтожает разрешённую дочернюю работу.
Нормальный ответ не обещает, что все созданные adapter фоновые процессы завершены.
Надзор не является sandbox для намеренно ускользающего кода и не вводит общей
блокировки между разными вызовами Bootstrap; блокировки принадлежат владельцам ресурсов.

## Диагностика, восстановление и границы ответственности

`error.code` — машинный признак; текст `message` не служит протоколом.
Ошибки квалификации `unsafe_target_config`, `invalid_target_config`,
`invalid_target_catalogue`, `invalid_target_parameters`, `target_input_unavailable`
дают failed-строку без apply. Остальные цели продолжаются в рамках deadline.
`maintenance_unavailable` означает отсутствие подходящего ядра/надзора до старта;
`maintenance_failed` — достоверный failed report ядра; `worker_failed` — недостоверное
завершение/протокол worker. `retryable` не разрешает повтор неизвестного ремонта.

Резервная копия операционной установки должна включать Bootstrap config и
**фактические** project records, каталоги, repairs и value files либо явные
защищённые ссылки на секреты, а не только examples. Для данных нужны относительные
пути, размеры, SHA-256 и политика доступа. Восстановление проверяет inventory,
выбирает явный destination и не заменяет отличающиеся действующие конфиги скрыто.
Затем владелец квалифицирует зависимости и выполняет check; наличие архива
не доказывает готовность обслуживаемой среды. Сам CLI не добавляет backup-команду.

T028 должен предоставить адаптеры предметных владельцев. Здесь нет чтения private
store соседнего приложения, копии его DDL, удаления повреждённой БД под видом
ремонта, Session/Task admission, распределённой транзакции или exactly-once гарантии.
Наличие generic RepairRouter не означает, что конкретный foreign-owner adapter уже
поставлен или проверен. Legacy одиночные команды Poise не преобразуются скрыто в `all`.

## Узкие проверки

Команды выполняются из корня проверяемого checkout выбранным интерпретатором,
который содержит закреплённое ядро. Они перечислены для воспроизведения; установка
зависимости и примеры настоящих repairs не выполняются проверкой документации.

```bash
cd "$CHECKOUT"
"$PYTHON" -B apps/bootstrap/tests/test_maintenance.py --suite behavior
"$PYTHON" -B apps/bootstrap/tests/test_profiles.py --suite behavior
"$PYTHON" -B apps/bootstrap/tests/test_shell.py --suite behavior
"$PYTHON" -B apps/bootstrap/tests/test_maintenance.py --suite documentation
```

Это 32 группы maintenance, 20 групп профилей, 8 групп оболочки и 4 документационные
проверки. Первая группа maintenance остаётся тем же внешним CLI-сценарием, который
доказывает отсутствие исполнения до реализации; для обычного продолжения RED
повторно не запускается. Подтверждаются счётчики check/apply/recheck, четыре исхода
ремонта, partial all, параметры/cwd/freeze, отсутствие запрещённого apply,
таймауты/вывод, неопределённые эффекты, различие нормального и аварийного завершения
потомков и граница единственного executor.

Документационный набор использует существующий
[проверяющий инструмент ссылок](../../../tools/check_documentation.py)
с `--checkout` и `--changed apps/bootstrap/docs/bst-maintenance.md`, включая
входящие ссылки из неизменённых страниц. Он проверяет локальные пути и anchors,
не выполняет ссылки или установочные команды и не подтверждает внешние URL.
Поддерживаемый smoke — `bash tests/smoke.sh "$PYTHON"` с зависимостями и окружением
выбранного профиля проверки, только когда он назначен этапом. Полная регрессия
не подменяет эти целевые проверки и не запускается как обычная приёмка задачи.
