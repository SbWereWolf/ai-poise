# Контракт общего runner и библиотечных обработчиков

Создано: **2026-09-06T15:39:15+05:00**.

Статус: **предлагаемая декомпозиция для реализации; код Harness и исходные маршруты не изменены**.

## 1. Минимальная граница ответственности

Runner читает узел из независимого route config и выбирает handler по **явной ссылке**. Обработчик не выбирается по goal_type, имени этапа или расширению файла. В ядре не нужны условные ветви `если development / если profiling`.

Контекст содержит привязанную сессию, текущую задачу, этап и итерацию, источник конфигурации, уже разрешённые inputs, проверяемый объект, сохранённые receipts и входной результат агента. Служебные идентификаторы модель не переписывает.

Обработчик возвращает смысловой исход: нужен результат агента; нужны наблюдения; нужно продолжение по новым наблюдениям; готово к общей финализации; проверка не удовлетворена; требуется внешнее действие; обнаружен Incident. Конкретные коды/формат вывода определяются контрактом конфигурации, а не зашиты как бизнес-литералы в реализацию.

Ни один handler не должен самостоятельно закрывать задачу, переходить в соседний этап или начинать повторный пользовательский цикл. Это делает runner после предусмотренного решения пользователя и проверки route conditions.

## 2. Что обязан задать узел маршрута

| Область | Обязательная явная информация |
|---|---|
| Идентичность | ID этапа, ссылка на handler, содержательный или механический узел |
| Вход | Источники контекста, inline/on-demand sections, зафиксированный объект работы |
| Работа агента | Инструкция/skill, writable scope, schema результата и фазы его подачи |
| Наблюдения | Явные observation procedures либо явное отсутствие; точные methods разрешаются до запуска |
| Проверки | Методы и predicates, обязательные manual/command evidence, pre/post validators |
| Исправление | Набор находок, источник решения о возврате, body produce/apply_plan либо неприменимость |
| Фиксация | Правила Git commit/push, artifact roots/path-only input, сохранение результатов и отчёт |
| Управление | Условия и цели переходов, authority, локальный и общий бюджет повторов |

Все списки могут быть пустыми только явно и когда schema разрешает это. Числа, paths, команды, критерии, названия output-файлов берутся из указанной конфигурации. Ссылки на schema/instructions внутри pack не являются наследованием другого goal_type.

## 3. Пример переиспользования inspect

Это **фрагмент предполагаемого конфига для объяснения**, не готовый runtime config. Связанные schema и refs должны быть определены при реализации; отсутствующие поля не получают defaults.

```yaml
# Фрагмент независимого development pack
stage_id: implementation_inspection
handler: inspect
subject: current_implementation_result
criteria: development_local_inspection_criteria
result_contract: development_local_inspection_result
execution_methods: []
reviewed_subject_mutation: forbidden
finish: report_and_wait_user
transitions_after_user_instruction:
  no_blocking_findings: documentation_or_completion_by_explicit_contract
  blocking_findings: implementation_remediation
```

```yaml
# Фрагмент независимого documentation pack
stage_id: inspection
handler: inspect
subject: current_documentation_result
criteria: documentation_local_inspection_criteria
result_contract: documentation_local_inspection_result
execution_methods: []
reviewed_subject_mutation: forbidden
finish: report_and_wait_user
transitions_after_user_instruction:
  no_blocking_findings: completion
  blocking_findings: remediation
```

Код inspect один; schema и критерии не общие. `execution_methods: []` в этих фрагментах не запрещает configured readiness/consistency checks runner. У реального этапа могут быть собственные точные методы, если он их требует.

## 4. Фазы, не новые пользовательские этапы

```text
ENTER
  runner разрешает один этап, готовит контекст и входной шаблон

PREPARE
  принимает результат агента, если требуется
  строит кандидатное состояние
  проверяет обязательные входы

OBSERVE / APPLY
  handler через executor получает факты/эффект
  receipts и позиция сохраняются

CONTINUE, только если требуется содержательное решение
  агент получает новые факты в ответе текущего вызова
  подаёт предусмотренный результат того же этапа

VERIFY + FINALIZE
  общая проверка обязательств, изменений и доказательств
  фиксация, private commit/push где требуется, отчёт

WAIT USER
  остановка перед следующим содержательным этапом
```

Ненужные фазы пропускаются по явному контракту. Одни стадии требуют только агентского результата; другие могут быть чисто исполнительными. Логическое evidence по уже имеющимся фактам не требует выдумывать OBSERVE. При unknown external outcome автоматический повтор не подменяет восстановление.

## 5. Псевдокод, не реализация

```text
на bootstrap или verify:
    разрешить текущие session/project/task/iteration
    загрузить явный node и его handler
    применить однозначную пользовательскую инструкцию в её области
    проверить оставшийся бюджет и сохранённую позицию

    если получен semantic result:
        сохранить кандидатный слой без дубликата
        проверить новую, а не прежнюю проекцию

    продолжать только механические шаги разрешённой фазы:
        outcome = handler.advance(контекст, контракт, сохранённые receipts)

        если outcome требует рассуждения:
            вернуть нужные факты + контракт результата той же стадии

        если outcome является обычной блокировкой/неуспехом:
            сохранить факты и вернуть текущую работу/необходимое действие

        если outcome готов к финализации:
            выполнить общий configured completion pipeline
            сохранить verified result и подготовленную следующую ветвь
            вернуть доклад; не начинать следующий содержательный этап

    межэтапный переход:
        только после соответствующей пользовательской инструкции
        применить edge из конфига, создать/возобновить нужную итерацию
        выдать её рабочий контекст одним bootstrap
```

## 6. revise как специализация, не второй runner

`revise` добавляет selection активных находок, requirements affected и обязательность resolution evidence. Затем вызывает тело produce либо apply_plan через тот же текущий контекст. Он не открывает вложенную сессию, не запускает новый workflow loop и не создаёт новую задачу.

Следующий inspect самостоятельно принимает/отклоняет предложение исправления. Reviewer здесь может быть тот же агент в следующем подходе либо другой агент по пользовательской оркестрации; библиотека не назначает моделей.

## 7. Общая библиотека ниже обработчиков

| Группа | Ответственность | Что не переносим в неё |
|---|---|---|
| Состояние и содержательные слои | SQLite sections, iterations, findings/resolutions, decisions, receipts | Смысл выводов и разрешение пользователя по догадке |
| Validators | Наличие/структура полей, refs, точные методы, graph/coverage relations, predicates | Истинность логического аргумента по факту непустоты строки |
| Executor | Точная команда, cwd, env, лимиты, output capture, parser, outcome | Выбор команды проекта без явного определения |
| Workspace | Worktree, stage-entry/current state, Git diff, привязка IDE | Фиксация каждого native edit агентом |
| Evidence | Привязка наблюдения к методу/объекту, пригодность reuse, structured summary | Переписывание test FAIL в Harness Incident |
| Artifacts | Только path input, допустимые roots, ID, configured count/pattern, durable refs | Назначение/тип/hash, придуманные моделью для регистрации |
| Publication backends | Task/sprint atomic publish либо Git target publish с receipt | Автоматическое разрешение публикации следующей пользовательской стадии |
| Output/hooks/observability | Primary + prepared details, ограничение выдачи, async policy, journal, incidents, metrics | Скрытая критичная mutation из async hook |

## 8. Обычные ошибки переиспользуются тоже

| Источник | Общая реакция | Результат для handler |
|---|---|---|
| Не хватает обязательного поля/команды | Остановить до дорогого исполнения, указать недостающее | Тот же кандидатный результат можно исправить |
| Нет среды/IDE/доступа | Сохранить состояние, подготовить требуемое действие пользователя | Не считать тест прошедшим или task отменённой автоматически |
| Проверка не совпала с ожиданием | Сохранить actual outcome, вернуть предметную проблему | Повтор текущего verify или предложенный route rework |
| Evidence устарело | Проверить актуальный объект согласно методам | Не превращать любой повтор payload в replay |
| Операция имеет неизвестный исход | Проверить saved receipt/probe или остановиться | Никакого безусловного повторного side effect |
| Свой баг/несогласованность Harness | Incident и сохранённое состояние | Инцидент включён в доклад независимо от восстановления |

Эти ответы не требуют отдельного ErrorHandler для каждого типа цели. Детали конкретного метода и безопасного восстановления остаются у соответствующего адаптера.
