# Инвариант DDD для проектирования и разработки

Создано: **2026-09-06T16:04:53+05:00**.

Статус: **проект следующей реализации, не выполненный refactoring**.

## Нормативный текст для документации Harness

Проектирование и разработка Harness выполняются с применением DDD. Для каждой бизнес-операции определяются предметный термин, владелец правил, агрегат или доменный сервис и публичный контракт изменения. Инварианты состояния проверяются владельцем, а не случайно распределяются между CLI, runner и SQL.

Task и Sprint реализуются отдельными библиотеками. Механика секций, версий, ссылок, путей артефактов, командного pipeline и коротких транзакций переиспользуется композиционно. Повторение технического алгоритма между goal types не допускается, если отличие выражается параметрами явного контракта.

Семь handler-семейств являются прикладными стратегиями и используют доменные библиотеки. Они не изменяют строки БД напрямую, не присваивают статусы Task/Sprint, не объявляют собственное исправление принятым и не начинают следующую содержательную стадию без предусмотренного решения пользователя.

Бизнес-правила процесса, обязательные поля, команды, лимиты, имена пользовательских представлений и пути берутся из явно заданной конфигурации. В домене допустимы собственные технические Value Objects, enum и инварианты идентичности/целостности. Отсутствующая настройка не восполняется default/fallback, а версия старого формата не поддерживается скрытым adapter.

Все точки входа используют одну application library инструментов. Запросы отделены от изменения бизнес-состояния. Repositories инкапсулируют запись агрегатов, Query API выдаёт адресные проекции, UnitOfWork определяет короткую SQL-транзакцию. Внешние действия имеют явные receipts и не объявляются частью общей ACID-транзакции БД.

Архитектура проверяется на реальных коротких/полных маршрутах и на границах импортов/владения данными. DDD не является основанием добавлять сервисы, абстрактные слои или обязательные вызовы агента, которые не нужны исполняемому процессу.

## Короткая формулировка для корневого AGENTS.md

> При изменении кода Harness соблюдай документированную DDD-архитектуру. Бизнес-правило помещай в библиотеку-владельца домена; Task и Sprint изменяй только через их API. Не записывай их состояние напрямую из CLI, runner, hooks или SQL-кода чужого модуля. Переиспользуй общие content/verification/artifact/transaction компоненты; не размножай реализацию по goal_type. Доменные модели не выполняют I/O и не получают скрытые defaults. Сверяй изменения с архитектурными ограничениями и одним реальным маршрутом с обратной связью.

Это дополнение к существующим meta-правилам worktree, пользовательских исключений и порядка работы, а не замена этих правил. В данном комплекте корневой AGENTS.md прототипа не изменён; текст подготовлен для включения при начале соответствующей работы над кодом.
