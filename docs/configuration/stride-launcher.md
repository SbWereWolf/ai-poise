# Запуск операций проекта через Stride

## Имена и владельцы

**Stride** — имя системы управления задачами. **Poise** — harness для агентов.
Версионируемая точка запуска операций проекта — `stride.sh` в корне приложения.
Общий механизм входит в Python-пакет `ai-poise`; независимые репозитории
подключают его через пакетный менеджер и самостоятельно выбирают версию.
Копирование исходников общей библиотеки между потребителями не является способом поставки.

`stride.sh` выбирает действующую конфигурацию проекта и запускает заданную команду.
Нативную идентичность сессии и обработку событий по-прежнему обеспечивают
[runtime hooks](runtime-hooks.md). Для агентской работы используется выданный
хуком сессионный `work.sh`; Stride не создаёт другую идентичность.

## Установка и выбор версии

Нужен явно выбранный Python **3.13** (`>=3.13,<3.14`). Исходники инструмента,
шаблоны и `stride.sh` хранятся в Git. Рабочие настройки и данные имеют отдельные пути.
Установка пакета является явным действием оператора; запуск операции ничего не устанавливает.

Пакет можно собрать из выбранной ревизии другого репозитория. Переменные ниже
оператор задаёт абсолютными путями: `stride_source` — checkout этой ревизии,
`stride_python` — интерпретатор потребителя, `stride_wheels` — каталог выходных wheel.
Для сборки без изоляции в выбранной среде должен быть установлен `setuptools>=80.9.0`.

```bash
"${stride_python:?}" -m pip wheel --no-build-isolation --no-deps \
  --wheel-dir "${stride_wheels:?}" "${stride_source:?}"
```

После выбора точного полученного файла `stride_wheel`:

```bash
"${stride_python:?}" -m pip install --no-index --no-deps "${stride_wheel:?}"
"${stride_python:?}" -I -B -c \
  'from importlib.metadata import version; print(version("ai-poise"))'
```

В манифесте зависимостей потребителя фиксируют `ai-poise==1.0.2`.
При использовании индекса пакетов его адрес задаётся настройкой пакетного менеджера;
публикация версии в публичный индекс этим руководством не предполагается.
Для локальной поставки выбирают конкретный wheel этой версии и сохраняют выбор
версии в зависимостях потребителя. Каталог сборки — временный выход установки,
а не архив задач или резервная копия данных.

Каждый потребитель имеет свою установленную зависимость. Изменение исходников
общего репозитория или выпуск новой версии не меняет уже установленный пакет.
Обновление — изменение выбранной версии и явная установка у нужного потребителя.
Общий пакет не импортируется из checkout через `PYTHONPATH` и не устанавливается
в editable-режиме. Установленная версия определяет общий механизм запуска;
состав команд и пути задаются рабочей конфигурацией.

## Настройки запуска

Обезличенные примеры:
[stride.example.env](../../config/stride.example.env) и
[stride-launcher.example.json](../../config/stride-launcher.example.json).
Рабочие `config/stride.env` и `config/stride-launcher.json` исключены из Git.
При другом расположении рабочие файлы также остаются вне коммитов.

Первый аргумент `stride.sh` — существующий абсолютный путь к доверенному Bash-файлу
настроек `.env`. Он выполняется через `source`, поэтому его содержимое должно
контролироваться оператором. Обязательны оба явно заданных значения:

| Переменная | Значение |
|---|---|
| `STRIDE_PYTHON` | Абсолютный путь к исполняемому Python с установленной выбранной версией пакета. |
| `STRIDE_CONFIG` | Абсолютный путь к существующему JSON настроек запуска. |

Одноимённые унаследованные переменные перед чтением файла очищаются.
JSON читается заново при каждой операции:

| Поле | Контракт |
|---|---|
| `schema` | Ровно `stride-launcher-1`. |
| `poise_root` | Существующий абсолютный каталог инструментов и конфигурации Poise. |
| `data_root` | Существующий абсолютный каталог рабочих данных. |
| `project_id` | Непустой идентификатор проекта из реестра. |
| `project_setup` | Непустой путь к настройкам владельца реестра; относительный путь разрешается от `poise_root`. Настроенный там `root` должен совпадать с `poise_root`. |
| `command` | Непустой массив непустых строк — префикс команды по умолчанию. |
| `overrides` | Обязательный объект: непустое имя операции → непустой массив строк префикса. Пустой объект допустим. |
| `exit_codes.rejected` | Обязательное целое от 1 до 255, кроме булевых значений; код отказа после успешного чтения настроек. |

Строки обязательных настроек не содержат NUL. Неизвестные опции игнорируются;
исходный JSON не переписывается. Пропущенные и непригодные известные значения
приводят к объяснённому отказу.

`project_setup` использует существующий
[владелец настройки проекта](project-setup.md#назначение).
Его `registry` определяет файл реестра. Реестр сопоставляет идентификатор проекта
с `config_path` его manifest. При следующей операции заново читаются адрес
manifest и его настройки. Относительные ссылки внутри manifest, в том числе
на process JSON, разрешаются по правилам владельца конфигурации от каталога
manifest; при переносе нужны и соответствующие материалы.

## Независимые корни

`poise_root` задаёт размещение инструментов и настроек реестра. `data_root`
независимо задаёт размещение данных. Для локальной установки это отдельно
настраиваемые каталоги `/home/sbwerewolf/workdata/poise-op/app` и
`/home/sbwerewolf/workdata/poise-project-data`; код не содержит этих значений.

До запуска команды проверяется, что выбранный manifest размещает внутри
`data_root` следующие ресурсы:

- `paths.state`;
- `paths.database` и `paths.lock`;
- `paths.requirements_database` и `paths.requirements_lock`;
- `accounting.storage.database` и `accounting.storage.lock`.

Остальные пути manifest проверяет существующий владелец конфигурации.
Task worktree задаётся `paths.worktrees` по
[правилам размещения](../governance/development-rules.md#размещение-task-worktree).
Для размещения `projects/poise-op/worktrees` под корнем приложения в manifest
задают абсолютный путь к этому каталогу. Относительное значение
`paths.worktrees` существующий владелец разрешает от `paths.state`;
оно не означает путь от корня инструментов.

Изменение одного корня не подменяет другой. Запуск только проверяет размещение;
он не переносит хранилища и не создаёт недостающий каталог данных. Смена пути
в настройках сама по себе не является миграцией БД. Перенос выполняется
[публичным владельцем состояния](project-setup.md#активные-задачи-и-перенос-state)
после проверки писателей и внешних ссылок. Поддержанное удаление источника —
`source_disposition=delete_after_publish` после подтверждения потребителей и повторной
проверки исходника и native authority; `remove` не является значением этого API.
Резервные копии и архивы запуском не создаются.

Для переноса действующего проекта нужны явная `runtime_resources` association с setup
owner и существующими установками хуков, освобождённые Task writers и реальное `DEAD`
переносимых native bindings. `LIVE` или `UNCERTAIN` дают отказ независимо от Task status.
Первую association публикует отдельно установленный поддерживающий её producer через
[bootstrap проекта](project-setup.md#привязка-владельцев-ресурсов). Запуск Stride не создаёт
эту связь и не подменяет [native
identity](runtime-hooks.md#разрешение-source-root-для-native-launcher).
Материалы, зарегистрированные пути и hooks переключаются их владельцами до удаления source;
одной правки `data_root` для этого недостаточно.

## Выполнение команды

Оператор задаёт `stride_entry` и `stride_bootstrap` абсолютными путями к
версионируемому скрипту и рабочему `.env`:

```bash
bash "${stride_entry:?}" "${stride_bootstrap:?}" --help
bash "${stride_entry:?}" "${stride_bootstrap:?}" next
```

Первый пример передаёт `--help` команде по умолчанию. Второй использует override
`next` из примера JSON: его префикс уже содержит `next` и явный `--settings`.
Для `check`, `deps`, `infra` и других операций оператор задаёт префиксы
реальных инструментов в `overrides`; сам launcher не назначает им семантику.

Если первый аргумент после `.env` совпал с ключом `overrides`, он заменяется
на соответствующий префикс; остальные аргументы добавляются буквально.
Иначе все аргументы добавляются к `command`. Строки аргументов не выполняются
как shell-код. Пустой список аргументов запускает только `command`.

Процесс получает `POISE_CONFIG` с точным выбранным manifest, исходные cwd,
stdin, stdout и stderr. `exec` сохраняет код завершения и сигналы дочерней
команды. Общая библиотека загружается выбранным Python с `-I -B`: пакет из cwd
или унаследованного `PYTHONPATH` не заменяет установленную версию.
Префиксы дочерних команд задаёт оператор; пример для установленного Poise
также явно содержит `-I -B`. Изоляция импорта произвольного дочернего инструмента
определяется его собственным префиксом.

## Отказ и восстановление

Отсутствующий или не абсолютный путь bootstrap и недопустимые обязательные
переменные отклоняются с кодом 2 и адресной причиной. Ошибки выполнения самого
доверенного `.env` подчиняются Bash и его `set -euo pipefail`.
Ошибка чтения или разбора JSON до получения полного набора настроек также
использует код протокола 2. После успешного разбора отказ выбора проекта,
размещения данных или запуска команды использует `exit_codes.rejected`.
Код завершения уже запущенной команды передаётся без замены.

При отсутствующем установленном пакете Python сообщает причину; launcher
не переключается на исходники. Оператор проверяет выбранный интерпретатор
и явно устанавливает нужную версию. При ошибке реестра или manifest исправляют
конфигурацию через её владельца; при несовместимом размещении данных сначала
завершают перенос и проверяют ссылки. Предварительный отказ не изменяет
рабочие данные. Действия успешно запущенного инструмента подчиняются его контракту.

При прерванном переносе используют
[точный повтор сохранённого намерения](project-setup.md#прерывание-и-точный-повтор),
сохраняя исходные request ID и пакет. До первой опубликованной копии владелец может допустить
актуальный исходник под writer fences; после публикации конфликт исходной истории или
скопированных байтов сохраняет обе копии и даёт отказ. Завершённый receipt возвращает
исторический результат и не заменяет свежую проверку доступности материалов.
Код отказа вызываемого `project-config` берётся из его setup settings; резервное `2`
используется при невозможности их создать. Это отдельная настройка от кода отказа launcher.

Подготовка к поставке включает проверку выбранной версии, рабочего реестра,
обоих корней и чтение проекта через установленный пакет. Проверка кандидата
в отдельной среде не подтверждает установку в действующую среду. Приёмка,
интеграция и фактический перенос данных имеют отдельные полномочия и результаты.
