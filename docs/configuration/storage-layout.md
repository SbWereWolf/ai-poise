# Размещение ресурсов установки и проектов

## Назначение и состояние

Документ определяет согласованную схему размещения и порядок её внедрения.
Рекомендуемые имена каталогов не являются жёсткими ограничениями: поддерживаемые
параметры конфигурации могут задавать другое размещение. Разделение данных проектов,
сохранность нужных данных и проверка потребителей обязательны независимо от пути.

Документ сам по себе не переносит данные, не изменяет рабочие конфигурации и не доказывает
завершение миграции. Ниже разделены датированный срез установки, целевые рекомендации и
поддержанный [перенос state](#перенос-дерева-state-и-независимые-ресурсы). Наличие проверенного
кода переноса не доказывает его установку или выполнение на конкретном проекте.
Неподдерживаемое пока решение нельзя выдавать за готовый параметр запуска.

## Язык предметной области

| Бизнес-имя | Определение |
|---|---|
| Storage Resource | Постоянный или временный ресурс, который читает либо записывает установка или подключённый проект. |
| Poise Installation | Установка инструментария оператора, обслуживающая независимо настроенные проекты. |
| Project | Независимо настроенный проект с собственными задачами, требованиями и рабочими данными. |
| Configuration | Настройки конкретной установки или подключения проекта; не исходный шаблон продукта. |
| Task Store | Хранилище задач, их состояния, связей, истории и сведений о сеансах проекта. |
| Requirements Store | Хранилище требований проекта и их связей; для ERP является частью документации. |
| Hook Registry | Проектный реестр установки обработчиков, привязок сеансов, событий и операций хуков. |
| Task Materials | Рабочие материалы одной задачи. |
| Sprint Shared Materials | Материалы спринта, необходимые нескольким его задачам. |
| Agent Session Resources | Временные файлы одного фактического сеанса агента. |
| Storage Migration | Проверенный перенос нужных данных с переключением всех действующих потребителей. |

Имена относятся к соответствующей предметной области; одинаковое написание
в другой области не доказывает тождество понятий. Требования используют бизнес-имена
и определения. Конкретные пути, технические имена и команды относятся к постановке
и документации реализации, а не подменяют производственные требования.

## Границы хранения

В примерах `O` означает `/home/sbwerewolf/workdata/poise-op`, `E` —
`/home/sbwerewolf/workdata/erp`, `D` — выбранный корень данных проекта.
Рекомендуемый `D`: `/home/sbwerewolf/workdata/poise-project-data/<project-slug>`.
Ресурсы разных проектов не смешиваются. Общие редакторы установки не становятся
проектными только потому, что редактируют определения, используемые проектами.

| Ресурс | Потребитель и назначение | Целевое размещение | Настройка и срок хранения |
|---|---|---|---|
| Task Store | Публичный `work`: задачи, спринты, история, сеансы | `D/tasks/tasks.sqlite` | `paths.state`, `paths.database`; постоянное, отдельно для проекта. |
| Requirements Store | Публичный `requirements`, согласование и связи требований | `D/requirements/requirements.sqlite`; для ERP — `E/docs/foundations/requirements.sqlite` | `paths.requirements_database`; постоянное, выбор версионирования за пользователем. |
| Телеметрия | Учёт наблюдённых событий, если включён | `D/telemetry/events.sqlite` | `accounting.storage.database`; необязательна, срок хранения задаёт её политика. |
| Hook Registry | Обработчик `poise hook`, регистрации и операции хуков проекта | `D/codex-hook/sessions-runtime.sqlite` | `database` и `state` в настройках хуков; не отдельная БД каждого агента. |
| Редактор этапов | Редактирование маршрута задачи, этапов и связей | `O/storage/workflow-stages/` | `database` в настройках редактора конфигурации целей; один экземпляр установки. |
| Редактор схем | Редактирование каталога процессов и шаблонов | `O/storage/workflow-schemas/` | `database` в настройках редактора каталога; один экземпляр установки. |
| Снимок переноса | Экспорт и импорт выбранных задач и их материалов | `D/task-transfers/<transfer-id>/` | `runtime_services.transfer`; получатель явно задаёт конечный файл передачи. |
| Резервная копия | Явная операция оператора, не автоматическая очистка | `D/tasks/backup/` рядом с Task Store | Настраиваемые команды `workspace-recover`; хранение по решению оператора. |
| Реестр чтений документов | Инструменты чтения документов агента, не Task Store | `D/runtime/<session-id>/document-intake/session-registry.sqlite3` | Настройки владельца document-intake; удаляется вместе с сеансом. |

Отдельная БД сеансов Task сейчас не вводится: сведения остаются в Task Store.
Hook Registry и реестр чтений решают разные задачи и не объединяются по сходству
имён файлов. SQLite WAL/SHM и принадлежащие БД lock-файлы располагаются рядом с БД;
не надо переносить их отдельно от работающего владельца.

## Новый проект: шаблоны и заполнение

Краткая агентская [инструкция подключения](../../.agents/references/project-storage-setup.md#project-storage-setup)
ссылается на этот полный справочник. Скиллы дают маршрут к инструкции, а не
дублируют настройки. Настройка генератора и пакет публикации принадлежат
[владельцу проекта](project-setup.md#пакетный-путь-для-агента).

Корень данных `D` — непосредственно каталог проекта, например
`/srv/poise-project-data/demo`, без дополнительного `state`. Конфигурация, исходники
и Task worktrees имеют независимо выбранные корни. В поставляемой схеме:

```text
poise-project-data/demo/
  tasks/tasks.sqlite
  requirements/requirements.sqlite
  telemetry/events.sqlite
  codex-hook/sessions-runtime.sqlite
```

Сопутствующие SQLite-файлы и locks принадлежат своей БД. Каталоги материалов,
спринтов, сеансов и передач задаются отдельными существующими настройками: эта
схема не переименовывает их неявно. Пример `demo` — заменяемое значение оператора.
Иные явные поддерживаемые пути допустимы; автоматической нормализации нет.

### Комплект примеров

| Файл под Git | Для чего | Что заполнить |
|---|---|---|
| [project-registry.example.json](../../config/project-registry.example.json) | Начальный реестр | Пустой `projects`; генератор регистрирует опубликованный manifest. |
| [project-setup.example.json](../../config/project-setup.example.json) | Настройки генератора | `root`, registry, внешний setup lock и точные выбранные template ID/version/digest. |
| [linux-reference.json](../../config/project-templates/linux-reference.json), [wsl-poise.json](../../config/project-templates/wsl-poise.json) | Полные blueprint нового проекта | Все вопросы, включая абсолютные корни данных и worktrees; не править blueprint ради одной установки. |
| [project.example.json](../../config/project.example.json) | Обезличенный полный manifest и справочный образец значений | Project ID, репозиторий, наблюдённая ветка, автор, политика публикации и корни. Для создания использовать генератор. |
| [hook-settings.example.json](../../config/hook-settings.example.json) | Отдельные настройки Hook Registry | Общий файловый `root`, выбранные Python/source root, project config, native hooks, definitions и проектный hook state. |
| [stride.example.env](../../config/stride.example.env), [stride-launcher.example.json](../../config/stride-launcher.example.json) | Запуск выбранного проекта | Явный интерпретатор установленного пакета, registry settings, ID проекта и независимые tool/data roots. |

Рабочие копии примеров остаются вне Git. Выбранные версия и digest blueprint
должны совпадать с фактическим файлом; `process_sources` фиксирует реальные
поставляемые процессы. Обновление примеров не обновляет уже заполненные настройки
оператора и не обновляет установленный пакет. Для другой версии инструмента
совместимость проверяют отдельно; сведения о [выборе версии](stride-launcher.md#установка-и-выбор-версии)
не заменяются импортом checkout.

### Значения manifest и hook settings

| Параметр | Значение поставляемой схемы и корень разрешения |
|---|---|
| `paths.state` | Явный абсолютный `D`, например `/srv/poise-project-data/demo`. |
| `paths.database`, `paths.lock` | `tasks/tasks.sqlite`, `tasks/tasks.lock` относительно `D`. |
| `paths.requirements_database`, `paths.requirements_lock` | `requirements/requirements.sqlite`, `requirements/requirements.lock` относительно `D`; явные абсолютные пути также поддержаны. |
| `accounting.storage.database`, `accounting.storage.lock` | `telemetry/events.sqlite`, `telemetry/events.lock` относительно `D`. |
| `paths.worktrees` | Явный абсолютный каталог внутри обслуживаемого репозитория; относительный путь разрешился бы от `D`. |
| Hook `root` | Явный общий файловый предок tools, данных и native hooks; образец использует `/srv`. Это не `paths.state`. |
| Hook `state` | `poise-project-data/demo/codex-hook` относительно hook `root`. |
| Hook `database` | `sessions-runtime.sqlite` относительно hook `state`. |
| Hook `lock` | `poise-project-data/demo/codex-hook/sessions-runtime.lock` относительно hook `root`. |
| Hook `bindings`, `observations` | `bindings`, `probes` относительно hook `state`; привязки сеансов создаёт настоящий native event. |

Остальные опции hook settings, их типы, лимиты, режимы файлов и коды отказа
описаны в [справочнике хуков](runtime-hooks.md#настройки-установки). Опции генератора и manifest —
в [настройке проекта](project-setup.md); launcher — в [контракте Stride](stride-launcher.md).
Секреты и действующие идентичности сеансов в примеры не записывают.

Процессы новых проектов содержат явные назначения этапов и пустые полномочия
на изменение критериев. Это дополнение поставляемых snapshot для текущей схемы,
а не миграция существующих Task или рабочих process files. Полный договор —
[новые проекты и старые снимки](../workflows/stage-criteria.md#новые-проекты-и-старые-снимки).

Для обоих blueprint обязательные ответы передаются через `edits`: `project`,
`git.repository`, `git.base_ref`, `git.remote`, `git.author_name`, `git.author_email`,
`git.push_required`, `paths.state`, `paths.worktrees`, `environment_names`.
Типы и prompts находятся в `questions`; остальные значения берутся из полного
выбранного blueprint. Готовый операторский пакет передают без выбора скрытого root:

```bash
/srv/poise/app/tools/.venv/bin/python -I -B -m poise project \
  --settings /srv/poise/app/config/project-setup.json \
  < /srv/poise/app/config/create-demo.json
```

Все пути в команде — заменяемые явные значения оператора; файл запроса должен
лежать вне создаваемого `destination`. Полная форма запроса и ответы инструмента —
в [пакетном контракте](project-setup.md#пакетный-путь-для-агента).
Поддержка назначения этапов определяется выбранной установленной версией: само
наличие новых metadata в JSON не доказывает работу нового runtime договора.

### Порядок подключения и проверка

1. Выбрать существующий primary checkout и прочитать его ветку по
   [инструкции выбора](project-setup.md#выбор-ветки-основного-checkout-для-интеграции).
   Задать отдельные абсолютные `D` и worktrees. Подготовить рабочий registry и
   generator settings из примеров, сверив все template pins с выбранной поставкой.
2. Передать полный `project-setup-1` через
   [публичный пакет](project-setup.md#пакетный-путь-для-агента), заполнив все вопросы.
   Публикация создаёт manifest, process snapshots, receipt и запись registry;
   она не создаёт Task DB, Requirements DB, worktree, native binding или архив.
3. Прочитать manifest и разрешённые пути. Выполнить
   [проектную проверку](project-setup.md#проверка-согласованности-проекта)
   с точными settings/config/project selectors. Она не заменяет создание БД
   их владельцами и не означает получения Task claim.
4. Перед изменяющим runtime опубликовать
   [ресурсную связь](project-setup.md#привязка-владельцев-ресурсов) через
   `project-runtime-resources-bootstrap-1`; для проекта без хуков список `hooks` пуст.
   Если нужны native hooks, явно выбрать совместимый `batch.message_source` с режимом
   `runtime_event` и тем же ID, что в definition. Для первой установки после пустой
   связи обычный `project-config` публикует `runtime_resources.hooks` и message source,
   затем `runtime-setup` с заполненными hook settings устанавливает определение.
   Использовать текущую revision и явные пакеты из
   [контракта обновления](project-setup.md#обновление-действующего-проекта) и
   [владельца хуков](runtime-hooks.md#интерфейсы). Проверить native groups и реестр;
   настоящий SessionStart даёт собственный launcher. Шаблон сам hooks не включает.
5. Проверить Stride и выбранные потребители. Для существующего проекта изменение
   пути не переносит данные: сначала определить фактические исходники, писателей
   и способы восстановления, затем сверить данные и удалить согласованный исходник.

Штатный `state_relocation` запрещает пересечение исходника и назначения, в том
числе перенос `D/state` в его родительский `D`. Такую коррекцию нельзя выдавать
за штатный перенос: применим только отдельно разрешённый проверяемый маршрут
[ручного восстановления](../governance/development-rules.md#сбой-harness-и-ручной-обход).
При операционном переносе также учитывать начальное создание session registry
прямым CLI до runtime fence: исключить такие команды на время переключения,
проверить реальные открытые БД и уведомить владельцев о новых путях. Блокировка
проекта сама по себе не доказывает остановку всех внешних запусков.

Точный действующий путь реестра чтений, перечень всех его потребителей и состояние
очистки устанавливаются отдельно: это ресурсы инструментария ERP, а не автоматически
настраиваемые поля Poise. Не объявлять их уже перенесёнными.

Указатели `state-erp` сейчас используются приведёнными ERP-потребителями; удалять
каталог до переключения этих потребителей нельзя. Имена `ai-poise`, `poise-op`
и `profile` здесь являются наблюдёнными именами, а не доводом о том, какое хранилище
«старое» или «новое». Решение о замене требует проверки данных и владельцев.

## Конфигурации и подключение проекта

Целевой комплект подключения: `O/projects/<project-slug>/config/`.
Настройки генератора называются `project-generator.json`. Сейчас генератор
использует `config/project-setup.json`; переименование не выполнено этим документом.
Реестр проектов — конфигурация установки, а не общая БД проектных задач.

Рабочие настройки уникальны для установки и не ведутся в Git. Для каждого
рабочего формата в Git нужен актуальный файл с `example` в имени, инструкция
заполнения, справочник всех опций и допустимых значений. Справочник ссылается
на инструкцию; правила разработки и соответствующий скилл — на справочник.
Примеры не содержат действующих сеансов, секретов и установочных значений,
которые нельзя переносить между установками.

Порядок настройки:

1. Определить проект, его основной checkout, корень данных и общий комплект
   конфигураций установки. Не выбирать хранилище по имени случайно найденной БД.
2. Взять актуальные примеры из [справочника
   подключения](project-setup.md#рабочие-конфигурации-вне-git),
   заполнить необходимые известные параметры и проверить их владельцем конфигурации.
3. Создать или обновить manifest публичным генератором. Проверить разрешённые
   абсолютные пути, выбранный проект, рабочую ветку и действующие потребители.
4. Подключить нативные хуки через [владельца установки](runtime-hooks.md).
   `.codex/hooks.json` остаётся там, где его читает Codex; команды указывают
   на выбранный комплект. Не сохранять сеанс конкретного запуска в общем конфиге.
5. Проверить ERP-прокси с фактическим сеансом вызывающего агента. Прокси ERP
   остаются ERP-прокси; установка Poise и выбранный управляемый проект — разные вещи.

[Контракт Requirements Store](../workflows/requirements-registry.md#владение-и-явные-пути)
допускает БД внутри репозитория независимо от Git-игнорирования и отслеживания.
Версионирование БД выбирает пользователь; отдельный разрешительный механизм не нужен.
Целевой ERP-путь в `docs/foundations` остаётся выбранным размещением. Снятие запрета
само по себе не переносит БД и не подтверждает переключение действующих потребителей.

## Материалы, сеансы и рабочие деревья

| Материал | Целевой путь относительно `D` | Время жизни |
|---|---|---|
| Материалы самостоятельной задачи | `standalones/<task-code>/` | До согласованной постоянной поставки и терминальной очистки. |
| Материалы задачи спринта | `sprints/<sprint-code>/<task-code>/` | До поставки и завершения необходимых потребителей. |
| Общие материалы спринта | `sprints/<sprint-code>/share/` | Пока нужны задачам спринта или постоянному потребителю. |
| Ответы команд, журналы и временные файлы агента | `runtime/<actual-session-id>/` | До завершения сеанса с проверяемой очисткой. |
| Снимки, архивы и манифесты переноса | `task-transfers/<transfer-id>/` | Пока нужен незавершённый перенос или явно согласованный результат. |

`task-code` и `sprint-code` — человекочитаемые символьные идентификаторы,
не UUID. Имена task-specific файлов переноса включают код задачи.
Рабочие деревья рекомендуются в `<master-checkout>/worktrees/`; точный путь
задаёт конфигурация. Нельзя вручную передвигать зарегистрированное активное дерево.

Чистый шаблон БД чтений заранее создаётся из миграций; при создании сеанса
копируется готовый файл, а не выполняется полный цикл миграций при каждом открытии.
Удаление каталога сеанса удаляет его реестр чтений. Реализация и проверка hook
завершения и восстановления после пропущенного завершения — отдельная задача,
а не уже существующая гарантия этой схемы. Очистка не должна зависеть от нового
сообщения пользователя и не должна превращать временные файлы в постоянный архив.

## Резервные копии и перенос

Для резервного копирования и восстановления используется `workspace-recover`,
не новый внутренний движок Poise. Целевая конфигурация содержит шаблоны обеих
команд, обрабатываемые общепринятым шаблонизатором: агент передаёт имя файла копии,
расположение Task Store известно из конфигурации. Копия создаётся без архивации
рядом с Task Store в `backup/` и проверяется на работоспособность. Перед
восстановлением проверяется копия; вытесняемая исходная БД сохраняется под именем
с временной меткой. Операция выполняется в согласованное окно без пишущих владельцев.

Это целевой контракт. До реализации шаблонов использовать только реально
поддерживаемую [публичную операцию резервного копирования](../task-db-backups.md),
не выдумывать флаги и команды. Явная резервная копия оператора и сохраняющий архив
при терминальной очистке — разные действия; очистка не разрешает делать второй.

Резервное копирование — отдельная явно запрошенная операция оператора. Локальная разработка,
перенос state и терминальная очистка сами по себе не создают checkpoints или копии «на всякий
случай». Нативный `handoff` сохраняет свой `source.bundle` как служебный материал передачи
результата по [существующему договору](../workflows/local-handoff.md#пакет), а не как резервную
копию БД. Его дальнейшим хранением и удалением владеет lifecycle задачи.

Перенос — не резервная копия. Получатель явно выбирает конечный файл пакета;
служебные снимки и манифесты относятся к конкретной операции переноса.
Использовать [публичный API переноса](../workflows/transfer.md), не сливать
управляемые SQLite произвольными SQL-операциями.

### Перенос дерева state и независимые ресурсы

Смена размещения всего состояния проекта выполняется
[публичным владельцем project-config](project-setup.md#активные-задачи-и-перенос-state).
Это отдельная операция от передачи выбранной Task между хранилищами. Она копирует state
вместе с существующими Task/Sprint records и историей, публикует зарегистрированные
физические пути материалов, связанные установки хуков и manifest, проверяет потребителей
и только затем обслуживает выбранное удаление исходника. При конфликте данные сохраняются;
слияние произвольных поздних SQLite изменений не обещается.

`runtime_resources` связывает manifest с setup owner и Hook Registry; project writer fence
находится вне переносимых корней. Освобождение Task и остановка native session — разные
условия. Переносимая native установка требует фактического `DEAD`; первоначальная привязка
и точный повтор описаны у владельца переноса, без ручной правки рабочих JSON или БД.

Корни инструментов и данных выбираются независимо через
[Stride](stride-launcher.md#независимые-корни). Относительные storage paths следуют своему
настроенному корню. Абсолютные `paths.requirements_database`, `paths.requirements_lock` и
`paths.worktrees` сохраняют заданное значение при смене state: операция не переносит внешний
Requirements Store или зарегистрированное Git worktree. Если абсолютный путь указывает
внутрь удаляемого source, его потребителя нужно отдельно согласовать и проверить перед
удалением; сама смена `paths.state` не исправляет такие ссылки. Приёмка конкретного размещения
включает проверку каждого действующего потребителя, а не только смену пути в manifest.

Путь worktrees задают по [его
правилам](../governance/development-rules.md#размещение-task-worktree).
Для каталога `projects/poise-op/worktrees` под корнем приложения используют явный абсолютный
путь в `paths.worktrees`. Относительное значение разрешается от `paths.state`, поэтому
одинаковая строка без указания владельца корня не определяет то же размещение.
Будущие рекомендуемые пути не подставляются вместо фактически проверенных настроек.

## Приёмка миграции и очистки

1. Составить карту всех исходных и целевых ресурсов, их настроек, читателей
   и писателей. Зафиксировать, какие данные сохраняются и почему.
2. Перенести незавершённые самостоятельные задачи. Для незавершённого спринта
   перенести всех участников, включая завершённые задачи, а также материалы,
   связи и необходимую историю. Коллизия локального ID не означает тождество задач.
3. Свести полный реестр требований ERP с канонической документацией; частичный
   набор из одной найденной БД не считается полнотой. Сверить коды, тексты,
   статусы, связи и явно разрешённые исключения, а не только число записей.
4. Проверить целостность целевых данных и работоспособность публичных операций.
   Переключить каждый действующий потребитель на один согласованный комплект.
5. Повторно проверить конфигурации, запуск и отсутствие обращений к заменённым
   путям. До этого исходное размещение не удалять. Не оставлять два комплекта,
   каждый из которых обслуживает только часть функций.
6. Удалить подтверждённо ненужные прежние ресурсы. Оставить только данные
   с действующим назначением, не архив «на всякий случай».

Производственные требования описывают постоянное поведение системы и приложения.
Полнота конкретного переноса и проверка переключения — критерии обслуживания;
они сохраняются в задаче, без выдуманных производственных предков. Сама схема
размещения не доказывает, что данные уже мигрировали или что очистка выполнена.

Терминальная очистка следует [договору постоянной поставки](../workflows/terminal-materials.md):
сначала результат доставлен и интегрирован, нужные потребители закрыты, затем
удаляются принадлежащие задаче дерево, ветка и временные материалы. Постоянные
результаты, общие ещё нужные материалы, рабочие данные и чужие ресурсы сохраняются.
