# Bootstrap и внешнее обслуживание

Корневой `bootstrap` исполняет явно выбранную команду и передаёт полный результат
настроенному обработчику. Рабочий профиль собственного экземпляра подготовьте по
[инструкции развёртывания](maintenance-profile-v2.md#развёртывание-из-примера).

## Граница приложений и происхождение

Poise владеет CLI, настройками команды, стандартной подстановкой аргументов,
запуском процесса и интерфейсом `ResultHandler`. Выбранный плагин разбирает результат,
оценивает успех и разрешённое исправление. Самостоятельное приложение
`environment-maintenance` читает свои конфиги и исполняет объявленные цепочки;
предметные эффекты Poise остаются у владельцев проекта, каталогов и баз данных.
Исходники внешнего приложения в Poise не копируются.

Версии пакетов выбирает пакетный менеджер. Команды и расположение установки заданы
конфигом. Для Poise требуется его собственный Python `>=3.15,<3.16`; интерпретатор
внешнего приложения выбирается отдельно. Подготовка профиля сама не переключает
действующую установку, её launcher или hooks.

## Проверенная поставка универсального компонента

Собственный operation-профиль использует интерфейсы конфигурации, подготовки,
проверки и запуска приложения `environment-maintenance` 2.0. Пакет с этими
интерфейсами устанавливают отдельно; номер версии при выполнении Bootstrap
не сравнивает. Проверки выполнялись с выбранным npm-артефактом, отдельной установкой
SDK и независимыми обслуживаемыми репозиториями в Ubuntu/WSL.

Существующие потребители `catalog/v2`, ERP и подготовки Task-worktree сохраняют
собственные конфиги команды и входы. Их прежние проверки поставок, включая wheel
`0.2.1`, относятся к тем выбранным поставкам; они не означают установку или
публикацию текущего npm-пакета. Принимаемую поставку и её происхождение хранит
её владелец. Маршруты разделены в [справочнике](poise-command-reference.md#обслуживание-окружения).

### Установка выбранного wheel

Для отдельно сохранённого каталожного потребителя установите его принятый wheel
в выбранное окружение пакетным менеджером. Например, при заранее выбранных
`tool_python` и `accepted_wheel`:

```bash
"$tool_python" -I -B -m pip install --no-index --no-deps "$accepted_wheel"
```

Его рабочие каталог, параметры и команда должны соответствовать именно этой
поставке. Установка нового operation-профиля через npm описана в
[основной инструкции](maintenance-profile-v2.md#развёртывание-из-примера).

## Настройка команды и рабочего файла

Материализатор нового профиля создаёт игнорируемые `operator/profile/bootstrap.json`
и `parameters.json` внутри выбранного репозитория Poise. Команды и заполнение
описаны в [инструкции](maintenance-profile-v2.md#развёртывание-из-примера).
Отслеживаются [общий пример команды](../../config/bootstrap.example.json) и
[спецификация профиля](../../config/maintenance/start-app/profile.example.json).
Рабочие файлы установки остаются вне Git.

В `bootstrap.json` параметр `python` выбирает Python установленного внешнего SDK;
в `parameters.json` параметр `python` выбирает Python обслуживаемого Poise.
Профиль сохраняет эти две роли раздельно. Его конфиги `infra.json`, `deps.json`,
`check.json`, `run.json` читает внешний инструмент. При замене инструмента
измените рабочую команду и выберите совместимый обработчик по интерфейсу ниже.

### Конфигурация команды

`--config` выбирает JSON со следующими обязательными полями:

| Поле | Значение |
|---|---|
| `parameters` | Строковые значения подстановок команды. |
| `commands` | Имена команд и непустые массивы строковых argv. |
| `handler.callable` | Импортируемый `module:callable`, реализующий `ResultHandler`. |
| `handler.options` | Явный JSON-объект настроек выбранного плагина. |

Каждый argv-токен обрабатывается стандартным `string.Template.substitute`:
`$name`, `${name}`, `$$`. Применяется одна подстановка из `parameters` и явного
контекста. Для `--base-dir` контекстный `base_dir` — абсолютный выбранный каталог;
он же cwd дочерней команды. Для `--catalog-dir` добавляется `catalog_dir`, а cwd
остаётся cwd вызова. Контекстный ключ имеет приоритет над одноимённым параметром.
Значения файлов SDK подставляет сам SDK, не Bootstrap. Недостающий placeholder
вызывает диагностируемую ошибку.

Пример операции из заполненного профиля: настроенный `env` задаёт явный
`PYTHONPATH` обслуживаемого репозитория, выбранный Python SDK выполняет
`-P -s -B -m environment_maintenance infra --config ... --parameters ...
--base-dir ... --requirements all`. `deps` и `run` также имеют явный
`--requirements all`; `check` использует свои правила чтения ресурсов.
Это argv с `shell=False`, без собственного shell-рендера или скрытого пути инструмента.

### Настройки встроенного обработчика

В примере выбран `apps.bootstrap.environment_result:handle`:

| Опция | Назначение собственного operation-профиля |
|---|---|
| `schema` | `null`: SDK не объявляет верхнеуровневое поле schema. |
| `status_exit_codes` | `succeeded: 0`, `failed: 1`; статус сверяется с exit процесса SDK. |
| `success_statuses` | Список статусов подтверждённого успеха; здесь `succeeded`. |
| `repairable_statuses` | Распознанные результаты для разрешённого исправления; здесь `failed`. |
| `repair_operations` | Явно разрешённые исходные операции; здесь `infra`, `deps`. |
| `repair_command` | Имя команды исправления из `commands`; здесь `repair`. |
| `verification_command` | Имя последующей проверки; здесь `verify`. |
| `failure_exit_code` | Ненулевой целый код ошибки Bootstrap; в примере `4`. |

В заполненном примере `repair` выполняет инфраструктурную цепочку, `verify` —
проверку ресурсов. Оператор задаёт применимую команду и разрешённые операции
по своему процессу. При ошибке зависимостей этот конкретный ремонт может оказаться
недостаточным: полный результат передаётся агенту после одной попытки и проверки.
Другой обработчик определяет собственные `options` и результат по тому же интерфейсу.

## Подготовка и безопасная проверка

После [публикации и заполнения](maintenance-profile-v2.md#развёртывание-из-примера)
используйте выбранные `poise_source`, `poise_python`, `repository`, `profile`:

```bash
"$poise_python" -I -B "$poise_source/bootstrap" infra --config "$profile/bootstrap.json" --base-dir "$repository"
"$poise_python" -I -B "$poise_source/bootstrap" deps --config "$profile/bootstrap.json" --base-dir "$repository"
"$poise_python" -I -B "$poise_source/bootstrap" check --config "$profile/bootstrap.json" --base-dir "$repository"
"$poise_python" -I -B "$poise_source/bootstrap" run --config "$profile/bootstrap.json" --base-dir "$repository"
```

Каждая строка выполняет свою выбранную операцию. `run` самостоятельно выполняет
только настроенную цепочку запуска. Этот профиль запускает `poise project list`;
подготовку выполняют предыдущие отдельные команды. `check` проверяет presence и
объявленную availability ресурсов из `infra`/`deps`, затем дополнительные проверки
своего конфига. Сам `check` не создаёт обслуживаемые ресурсы.

| Аргумент Bootstrap | Назначение |
|---|---|
| `infra`, `deps`, `check`, `run` | Выбранное имя операции. |
| `--config PATH` | Обязательный JSON команды Bootstrap. |
| `--base-dir PATH` | Один из двух обязательных вариантов контекста: непустой каталог выбранного экземпляра; явный `.` допустим. |
| `--catalog-dir PATH` | Другой вариант: непустой контекст отдельного каталожного потребителя. |
| `--values PATH` | Повторяемый передаваемый аргумент выбранного внешнего контракта. |
| `--set NAME=VALUE` | Повторяемое передаваемое переопределение. |
| `--dry-run` | Передаваемый флаг; встроенный обработчик при нём не исправляет. |
| `-h`, `--help` | Справка argparse без запуска инструмента. |

Два контекста взаимоисключающие. Нулевое строковое значение контекста отклоняется
до запуска процесса. Пути с пробелами и Unicode передаются отдельными argv-токенами.
`--values`, `--set`, `--dry-run` добавляются к argv в исходном порядке. Применяйте
их там, где они поддерживаются выбранным внешним контрактом: operation-профиль SDK
принимает свои `--config`/`--parameters`/`--base-dir`, а значения старого каталога
передаются его собственными аргументами. Необязательные флаги не означают наличие
соответствующего режима у любого внешнего приложения.

## Входы универсального каталога

Отдельный сохранённый каталог имеет `catalog.json` со schema
`environment-maintenance/catalog/v2`, строковыми `parameters`, `inherit_env`
и упорядоченными `requirements`. Действия ресурса — `check`, `install`, `repair`;
их протокол Poise — `poise/maintenance-action/v2`. Такой профиль выбирает свою
совместимую поставку consumer и JSON команды с `${catalog_dir}`; например,
внешний `check --catalog-dir ... --values ...`. Поля статусов и коды его обработчика
задаются под этот результат. Текущий `config/bootstrap.example.json` описывает
operation-маршрут; действующие каталожные рабочие конфиги выбираются отдельно.

Материализатор с явным `--profile-spec config/maintenance/profile.example.json`
сохраняет этот самостоятельный контракт. ERP выбирает свою
[спецификацию и конфиги](maintenance-profile-v2.md#профиль-erp), Task-подготовка —
[свой владелец](worktree-preparation.md#подготовка-рабочей-области).
Смена одного cwd не меняет repository, уже сохранённый в рабочем профиле.

## Состояния и повторная проверка

Успех исходной команды возвращается без ремонта. Неразбираемый результат,
несовпадение схемы или противоречие статуса и exit передаются агенту с диагностикой.
Распознанная ошибка запускает исправление только при разрешении в `repair_operations`
и применимом настроенном статусе. Затем выполняется одна проверка. Линейная
последовательность `initial → repair → verification` не входит в исправление повторно.
После ошибки исправления проверка также сохраняет своё фактическое наблюдение.
Готовность подтверждается только при успехе и исправления, и проверки.

Это один локальный вызов обработчика: отдельное хранилище счётчика попыток не нужно.
Неизвестную или последующую ошибку решает агент. Для каждой следующей самостоятельной
команды создаётся новый вызов, без автоматического скрытого повторения предыдущей.

Внутри SDK настроенный `MaintenanceResult` проверяет schema, реальный exit и
`state=satisfied` либо `outcome=completed` предметного ответа. Отрицательный state
при exit0 остаётся ошибкой ресурса. `ExitResult` сравнивает exit с явным `accept`.
`ProjectListResult` выбран только для запуска этого собственного профиля: требует
корректные списки `projects` и `errors`, минимум один проект и пустые ошибки;
имена полей, минимум и допустимые exit заданы в `interpreter.options`.
Сам публичный `poise project list` по-прежнему может успешно вернуть пустой реестр;
профиль интерпретирует такой результат как неготовый выбранный экземпляр.
Все интерпретаторы возвращают `success`, `value`, `error`, а SDK сохраняет сырой
результат процесса без изменения.

## Интерфейс подключаемого обработчика

`apps.bootstrap.contracts.ResultHandler` принимает
`initial: CompletedProcess[bytes]`, `invoke: Callable[[str], CompletedProcess[bytes]]`,
`options: Mapping[str, object]`, `context` с `operation` и `dry_run`.
Он возвращает сериализуемый JSON-объект с целым `exit_code`.
`invoke(name)` исполняет настроенную команду с тем же контекстом и передаваемыми
аргументами. Подменяемый плагин выбирается через `handler.callable`, приложение
зависит от протокола, а не от класса конкретного обработчика.

SDK-интерпретаторы являются отдельным интерфейсом `interpret(raw, options)`.
Их `module` и `attribute` задаёт `app.interpreters`; ресурсная команда выбирает
имя и настройки. `raw` содержит полный `exit_code`, `stdout`, `stderr`.
`success` — bool; успешный `error` равен null, неуспешный — непустая строка.

## Результаты и ошибки

Встроенный обработчик выводит `status=ready`, `exit_code=0` либо `status=error`
и настроенный код ошибки. `actions` содержит реально запрошенные имена ремонта
и проверки; `observations` — исходный и фактически выполненные последующие
`stage`, `stdout`, `stderr`, `exit_code`. При ошибке добавляется `reason`.
UTF-8 потоки сохраняются полностью; нетекстовые bytes представлены обратимым
`repr(bytes)`. SDK передаёт вложенные потоки команд в полном base64-представлении.
Preview не заменяет полный результат и не используется для решения об успехе.

Ошибка загрузки команды/плагина, подстановки или нарушение интерфейса обработчика
возвращает JSON `status=error`, `exit_code=4`, `reason` и доступное исходное наблюдение.
Если команда ещё не запускалась, такого наблюдения нет. Ошибки синтаксиса CLI и
справка используют стандартный argparse, а не этот JSON. Подменяемый обработчик
может вернуть свой целый код; реальный exit внешнего процесса остаётся диагностикой.

## Диагностика и восстановление

Прочитайте полный результат и фактическое состояние указанного ресурса. Для
распознанного разрешённого результата уже выполнены максимум один настроенный ремонт
и проверка; следующую проблему решает агент. При ошибке настройки исправьте выбранный
рабочий конфиг согласно его примеру и повторите нужную команду. Неполные обязательные
настройки ремонта диагностируются до его запуска. Для проверки ресурсов используйте
самостоятельную `check`, для запуска — `run`.

Протокол предметных адаптеров сохраняет причину и рекомендации. Действующие базы
обслуживают их исходные владельцы; действия не пересоздают существующие неисправные
или занятые БД. Публикация профиля не является разрешением на миграцию данных.

## Проверки и границы доказательств

`tests/maintenance/test_self_service_boundary.py` подтверждает реальные argv/cwd,
смену обработчиков, полный большой/нетекстовый вывод и одну разрешённую попытку.
`test_self_service_profile.py` использует настоящий установленный SDK, раздельные
исходник/репозиторий/профиль/runtime/data, реальные три БД и зависимость; проверяет
подготовку, ресурсы и запуск, включая отсутствие эффектов при неподготовленном run.
Старые отдельные потребители имеют адресные регрессионные проверки.

Ссылки/оформление не заменяют исполнение сценария. Для точной ревизии применяются
целевые методы и поддерживаемый быстрый smoke; это не новая приёмка hooks, всех
платформ или пользовательских бизнес-сценариев ERP.

## Откат и пределы поставки

Публикация нового профиля и выбор команды у действующей установки — отдельные
операторские действия. Для явного выбора и возврата используйте
[процедуру владельца](maintenance-profile-v2.md#переход-на-новый-маршрут-и-возврат).
Смена команды не откатывает уже выполненные изменения ресурсов. Служебные материалы
проверки размещают в своей Task/сессии, рабочие настройки установки — в её ignored
профиле; исходные примеры и эта инструкция остаются под VCS.
