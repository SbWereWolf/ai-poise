# Bootstrap и каталог catalog/v2

Руководство описывает корневой `bootstrap` из этой поставки AI poise.
Он запускает выбранный инструмент по конфигурации и передаёт полный
результат
подключаемому обработчику. `poise infra/deps/check` — отдельный
маршрут
делегирования; текущий материализатор готовит v2-профиль. Фактическую
совместимую
поставку установленного оператора выбирают отдельно: подготовка
Bootstrap сама
не переключает
его. [Исторический маршрут и зависимость от
исходников](../deployment/maintenance.md#исторический-маршрут-requirementsv1)
описаны отдельно.
[Справочник команд](poise-command-reference.md#обслуживание-окружения)
разделяет эти маршруты.
Полный каталог Poise подготовьте по [инструкции рабочего
профиля](maintenance-profile-v2.md#развёртывание-из-примера).
Автоматическое применение выбранных команд к новой Task-worktree, полные входы,
квитанции и повтор описаны в [подготовке рабочей области](worktree-preparation.md#подготовка-рабочей-области).
Этот маршрут использует те же интерфейсы команды и обработчика; standalone запуск
ниже остаётся самостоятельной операцией.
Для Task используйте [отдельный профиль с её repository](worktree-preparation.md#профиль-конкретной-задачи).
Standalone профиль сохраняет выбранный при материализации checkout; смена cwd
команды не меняет repository в его values и каталоге.

## Граница приложений и происхождение

Poise владеет CLI, чтением конфигурации, стандартным рендером
аргументов,
запуском процесса и интерфейсом обработчика. Выбранный обработчик
владеет
разбором результата, оценкой готовности, решением об исправлении и
проверкой.
Внешнее приложение владеет каталогом, его параметрами и действиями
обслуживания.
Исходники внешнего инструмента не копируются в Poise.

Версии внешних пакетов выбирают при установке пакетным менеджером.
Bootstrap
использует указанные оператором команды. Собственная версия Poise
принадлежит
его поставке. Метаданные этой поставки Poise задают Python
`>=3.15,<3.16`;
этот диапазон относится и к корневому Bootstrap. Интерпретатор
внешнего
приложения выбирается отдельно согласно его требованиям.

## Проверенная поставка универсального компонента

Для описанных сценариев проверен независимый пакет
`environment-maintenance` версии
`0.2.1`, исходная ревизия `482b11417f8e74d9bcc1d885767bb16837f3284a`.
Получите комплект из подтверждённой поставки компонента; папку
комплекта выбирает
оператор. В неё входят следующие неизменяемые материалы:

| Файл                                             | SHA-256                                                            |
|--------------------------------------------------|--------------------------------------------------------------------|
| `environment_maintenance-0.2.1-py3-none-any.whl` | `01932116ea61f7da6f6f613ce910bd978a5b46fb91ab1d14b74b9c6ad78e3ba7` |
| `manifest.json`                                  | `e8a8a9d398c022a00267737f9847c842418b5da6892e4bdebc1215accab1341b` |
| `source.bundle`                                  | `ad742873b12521979c5c6d824a8082c00e11194e3bf42b842d1cd822d406b250` |
| `build-record.json`                              | `e5d13db9baae94b92e756ac2f4aa82a8d1a62bbf120b772e5731a61af5643213` |
| `build.stdout`                                   | `66abc3aa34e3d907c9781742f2ae2851095dd33db8f8582d8f24f747373107fd` |
| `build.stderr`                                   | `8995e8cc62d964b7fedcbe7e25c28a9639531d076bc4981c73e741bf687c51eb` |

До установки вычислите SHA-256 всех шести файлов и сравните с
таблицей.
В `manifest.json` и `build-record.json` должны совпасть имя
wheel,
исходная ревизия, digest wheel и `source.bundle`; digest обоих потоков
сборки
должны совпасть с её файлами. Версия указана в manifest и метаданных
wheel;
build-record связывает wheel с исходниками и результатом сборки.
Непустой
`build.stderr` сам по себе не означает неуспех: сохранённый exit
сборки равен 0.
`source.bundle` и материалы сборки подтверждают происхождение; CLI
обслуживания
читает выбранный каталог, а не эти файлы.

Метаданные внешнего пакета разрешают Python `>=3.11`. Фактически
совместная
работа пакета и Bootstrap проверена в Ubuntu 24.04 под WSL на Python
3.13.15:
отдельное окружение, установка выбранного wheel без сети и
зависимостей,
метаданные версии/путь импорта и совпадение семи установленных модулей
с wheel.
Этот результат подтверждает указанную среду; метаданные не являются
проверкой
каждой версии Python или другой ОС.

### Установка выбранного wheel

Пути ниже — значения выбранной установки. Подготовьте отдельное
окружение
совместимым интерпретатором; `$tool_python` указывает его Python.
После сверки
комплекта установите именно полученный wheel:

```bash
supply_dir=/srv/poise/supply/environment-maintenance/0.2.1
tool_python=/srv/poise/tool-venv/bin/python
sha256sum "$supply_dir/environment_maintenance-0.2.1-py3-none-any.whl" \
  "$supply_dir/manifest.json" "$supply_dir/source.bundle" \
  "$supply_dir/build-record.json" "$supply_dir/build.stdout" "$supply_dir/build.stderr"
"$tool_python" -I -B -m pip install --no-index --no-deps \
  "$supply_dir/environment_maintenance-0.2.1-py3-none-any.whl"
"$tool_python" -I -B -c 'import importlib.metadata as m, environment_maintenance as e; print(m.version("environment-maintenance")); print(e.__file__)'
```

Ожидаемая версия — `0.2.1`, путь импорта — внутри выбранного
окружения.
При расхождении остановите подготовку и исправьте выбор
комплекта/интерпретатора.
Bootstrap использует фактический путь `$tool_python` из рабочего JSON;
встроенного
выбора версии или автоматической установки у него нет. Полный
прикладной каталог
Poise готовится отдельно
по [инструкции профиля](maintenance-profile-v2.md#развёртывание-из-примера).

## Настройка команды и рабочего файла

Выберите корень установленной копии Poise, каталог обслуживания и
интерпретаторы.
Установите выбранный внешний инструмент в его окружение пакетным
менеджером.
Корневой `bootstrap` поставляется вместе с соседним `apps/bootstrap/`;
ему не нужны Task, сессия harness или `POISE_CONFIG`.

В следующем примере `/srv/poise/app` — выбранная оператором копия, а
не
встроенное значение программы. Из её корня подготовьте рабочие файлы:

```bash
poise_root=/srv/poise/app
bootstrap_python=/srv/poise/bootstrap-venv/bin/python
catalog_dir=/srv/poise/catalog-v2
cd "$poise_root"
cp config/bootstrap.example.json config/bootstrap.json
cp config/environment-maintenance.example.json config/environment-maintenance.json
```

Заполните оба рабочих файла значениями своей установки. Рабочие
`config/bootstrap.json` и `config/environment-maintenance.json`
находятся
внутри папки Poise и исключены из Git. Отслеживаются заполненные
примеры
[команды](../../config/bootstrap.example.json) и
[параметров внешнего инструмента](../../config/environment-maintenance.example.json).
В sanitized примере `python` содержит `${PYTHON_EXECUTABLE}`; в
рабочем файле
замените его фактическим путём выбранного интерпретатора. Также
замените
`${POISE_SOURCE_ROOT}` в параметре `tool_config` фактическим корнем.
Эти значения
не подставляются автоматически из переменных окружения: стандартный
рендер
обрабатывает аргументы команды один раз, используя уже заполненные
`parameters`.
Состав этого файла определяется внешним каталогом: Bootstrap передаёт
его
через команду как файл значений, а не интерпретирует его содержимое.
Ключи
файла должны быть объявлены выбранным каталогом; пример с `python`
применим,
когда каталог объявляет этот параметр. Для иного каталога заполните
его
собственные параметры, иначе внешний инструмент отклонит неизвестное
значение.

### Конфигурация команды

`--config` выбирает JSON-объект со следующими полями:

| Поле               | Значение                                                             |
|--------------------|----------------------------------------------------------------------|
| `parameters`       | Объект строковых параметров шаблона: имена и значения — строки.      |
| `commands`         | Непустой объект имён команд и непустых списков строковых аргументов. |
| `handler.callable` | Импортируемый обработчик в формате `module:callable`.                |
| `handler.options`  | Явный JSON-объект настроек выбранного обработчика.                   |

Каждый аргумент независимо рендерится стандартным Python
`string.Template.substitute`.
Доступны `$name`, `${name}` и `$$` для буквального доллара.
Значения берутся из `parameters`; `catalog_dir` берётся из
обязательного
`--catalog-dir` и имеет приоритет над одноимённым параметром.

Команда — список argv, например `["${python}", "-m", "environment_maintenance",
"check", "--catalog-dir", "${catalog_dir}"]`. Исполняемый файл и
параметры
полностью задаются конфигурацией. Процесс запускается без shell;
относительные
пути относятся к текущему рабочему каталогу запуска Bootstrap. Для
приведённых
примеров это явно выбранный `poise_root`.

Поставленный пример сначала вызывает внешний `check` для всех трёх
операций.
При разрешённом исправлении обработчик вызывает команду `repair`,
которая
в примере запускает внешний `run`, затем `verify` с внешним `check`.
Так первоначальное наблюдение предшествует решению об изменении
окружения.

### Настройки встроенного обработчика

Пример выбирает `apps.bootstrap.environment_result:handle`.
Его `handler.options` содержит:

| Поле                   | Назначение и значение примера                                                             |
|------------------------|-------------------------------------------------------------------------------------------|
| `schema`               | Ожидаемая schema JSON-результата: `environment-maintenance/result/v2`.                    |
| `status_exit_codes`    | Соответствие статуса реальному exit: ready=0, action_required=2, unavailable=3, failed=4. |
| `success_statuses`     | Статусы готовности: `["ready"]`.                                                          |
| `repairable_statuses`  | Статусы, допускающие исправление: `["action_required"]`.                                  |
| `repair_operations`    | Публичные операции с разрешением исправления: `["infra", "deps"]`.                        |
| `repair_command`       | Имя команды исправления из `commands`: `repair`.                                          |
| `verification_command` | Имя последующей проверки: `verify`.                                                       |
| `failure_exit_code`    | Ненулевое целое для ошибки обработчика: `4`.                                              |

Эти поля принадлежат именно встроенному обработчику. Другой
подключаемый
обработчик определяет собственные настройки через тот же интерфейс.

## Подготовка и безопасная проверка

После заполнения файлов выполните команды из выбранного корня:

```bash
"$bootstrap_python" -I -B "$poise_root/bootstrap" check \
  --config "$poise_root/config/bootstrap.json" --catalog-dir "$catalog_dir"
"$bootstrap_python" -I -B "$poise_root/bootstrap" infra \
  --config "$poise_root/config/bootstrap.json" --catalog-dir "$catalog_dir" --dry-run
"$bootstrap_python" -I -B "$poise_root/bootstrap" deps \
  --config "$poise_root/config/bootstrap.json" --catalog-dir "$catalog_dir" --dry-run
```

В поставленном примере `check` только наблюдает. Для применения
разрешённого
обслуживания используйте `infra` или `deps` с теми же настройками.
Названия не выбирают каталог автоматически: оператор явно передаёт
нужный каталог.

| Аргумент                 | Назначение                                                                  |
|--------------------------|-----------------------------------------------------------------------------|
| `infra`, `deps`, `check` | Публичная операция и имя первоначальной команды в конфигурации.             |
| `--config PATH`          | Обязательный путь JSON-конфигурации Bootstrap.                              |
| `--catalog-dir PATH`     | Обязательное непустое значение параметра каталога.                          |
| `--values PATH`          | Повторяемый аргумент внешнего инструмента с файлом значений.                |
| `--set NAME=VALUE`       | Повторяемое переопределение внешнего инструмента.                           |
| `--dry-run`              | Передаётся внешней команде; встроенный обработчик не выполняет исправление. |
| `-h`, `--help`           | Справка без запуска инструмента.                                            |

Дополнительные `--values`, `--set` и `--dry-run` добавляются после
аргументов
шаблона с сохранением порядка и передаются также последующим командам.
Например, для каталога, определяющего строковый параметр `python`:

```bash
"$bootstrap_python" -I -B "$poise_root/bootstrap" deps \
  --config "$poise_root/config/bootstrap.json" --catalog-dir "$catalog_dir" \
  --values "$poise_root/config/environment-maintenance.json" \
  --set python=/srv/poise/tool-venv/bin/python --dry-run
```

## Входы универсального каталога

Компонент `0.2.1` читает `catalog.json` из явно выбранной
`--catalog-dir`.
Корневой объект содержит `schema: environment-maintenance/catalog/v2`,
`parameters`, `inherit_env` и `requirements`. Каждое требование задаёт
уникальный
`id` и самостоятельные `check`, `install`, `repair`. Каждое действие
содержит
явные `argv`, `cwd`, `env`, `output.schema`, `max_output_bytes` и
`execution_bound_seconds`. Действия получают разрешённые переменные из
`inherit_env` и явно заданные значения своего `env`; выбор каталога
определяет
весь набор требований. Файлы прежних requirements/repairs, опция
`--repairs`
и команда `apply` не являются входами этого CLI. Соседний старый
профиль
не подменяет выбранный v2-каталог.

Параметры имеют объявленные типы `string`, `integer`, `number`,
`boolean`.
Приоритет от меньшего к большему: default → файлы `--values` →
объявленная
переменная `env` → `--set`. Более поздний values-файл заменяет
одноимённое
значение раннего. Неизвестное имя или повтор одного имени в `--set`
отклоняется;
сохранение порядка аргументов Bootstrap не означает разрешения
повторных CLI-ключей.
Обязательный параметр должен получить значение согласованного типа.
`${name}` в аргументах/рабочем каталоге/окружении действия
раскрывается один раз;
подставленный текст повторно как шаблон не обрабатывается.

Для каждого действия `max_output_bytes` — целое от 1 до 16777216,
предел
отдельно для stdout и stderr. `execution_bound_seconds` — конечное
число
строго больше 0 и не больше 3600. Переполнение или превышение времени
дают
неуспех и диагностику; после остановки процесса второй поток может
быть
захвачен не полностью. Оценивайте `capture_complete` и `timed_out`
вместе
со статусом, а не принимайте частичный вывод за успешный ответ.

Некорректные каталог, значения, типы, чрезмерная структурная глубина
JSON,
непригодные argv/cwd/env и числовые ограничения отклоняются до запуска
действий:
внешний CLI возвращает exit 2 с причиной в stderr. Фиксированный
предел глубины
не заявляется. Строка, похожая на вложенный JSON, остаётся обычной
строкой,
когда её параметр объявлен строковым.

Результат компонента сериализуется в валидный UTF-8 JSON с сохранением
текстовых
значений, включая экранированные одиночные суррогаты. В проверенной
POSIX-среде
путь с байтом `ff` сохраняется через файловое представление Python.
Это
отличается от передачи значения операционной системе: NUL и
непредставимые
в её кодировке значения argv/cwd/env, включая полученные после
подстановки,
отклоняются до действий. Неправильный UTF-8 или чрезмерно глубокий
JSON-ответ
действия — ошибка протокола, а не готовность.

## Состояния и повторная проверка

Состояние ресурса и итоговый статус обслуживания — разные поля
результата:

| Исходное состояние | `check` или dry-run                      | Разрешённый `run`                           |
|--------------------|------------------------------------------|---------------------------------------------|
| `satisfied`        | Подтверждает готовность                  | Завершается без install/repair              |
| `missing`          | Показывает отсутствие и рекомендации     | Выполняет install, затем исходный check     |
| `invalid`          | Показывает некорректность и рекомендации | Выполняет repair, затем исходный check      |
| `unavailable`      | Сохраняет причину и рекомендации         | Возвращает недоступность без install/repair |

Внешний `environment_maintenance` возвращает `ready`/0,
`action_required`/2, `unavailable`/3 или `failed`/4.
`check` и dry-run сохраняют ресурсы. В разрешённом `run` итог действия
подтверждает тот же исходный check с теми же argv/cwd/env. Он
выполняется
и после ошибки install/repair, включая ошибку разбора ответа глубокой
структуры.
Неуспех изменения остаётся `failed`/4, даже если действие успело
привести ресурс
в `satisfied`, а повторная проверка это подтвердила.

У встроенного обработчика Bootstrap отдельные внешние статусы `ready`
/0 и
`error`/4. Вложенный результат и его реальный код находятся в
`observations`.
Первоначальный check, запускаемый обработчиком `repair` (в примере
внешний run)
и последующий `verification` (внешний check) — отдельные наблюдения.
Проверка
внутри внешнего run не заменяется этой последующей проверкой
обработчика.

## Интерфейс подключаемого обработчика

Обработчик импортируется стандартным `importlib` по `module:callable`.
Это импортируемая функция или callable-объект с контрактом
`apps.bootstrap.contracts.ResultHandler`:

```python
def handle(initial, invoke, options, context):
    ...
    return {"exit_code": 0}
```

`initial` — `subprocess.CompletedProcess[bytes]` с полными
stdout/stderr
и реальным returncode. `invoke(name)` запускает именованную команду
с теми же добавленными аргументами и возвращает такой же полный
результат.
`options` — настройки обработчика; `context` содержит `operation` и
`dry_run`.
Результат — JSON-сериализуемый dict с целым `exit_code`; остальные
поля
определяет обработчик. Общий CLI выводит полный JSON и возвращает этот
код.
Замена обработчика производится через конфигурацию без зависимости
транспорта
от конкретной реализации. Обработчик сохраняет диагностику собственных
действий.

## Результаты и ошибки

Встроенный обработчик сопоставляет JSON schema, status и реальный
exit.
Результат содержит:

| Поле           | Значение                                                                        |
|----------------|---------------------------------------------------------------------------------|
| `status`       | `ready` либо `error`.                                                           |
| `exit_code`    | 0 при готовности, иначе настроенный `failure_exit_code`.                        |
| `observations` | Упорядоченные результаты initial, repair и verification, когда они выполнялись. |
| `actions`      | Имена последующих команд, попытки вызова которых действительно предприняты.     |
| `reason`       | Причина ошибки при `status=error`.                                              |

Наблюдение содержит `stage`, полные `stdout`, `stderr` и реальный
`exit_code`.
Корректный UTF-8 сохраняется как текст без усечения. Невалидные байты
показываются однозначным Python repr; такой результат не признаётся
готовностью.
При ошибке вызова последующей команды наблюдение содержит диагностику
и
`exit_code: null`, поскольку код дочернего процесса не получен.

Готовый исходный результат сразу возвращается агенту. Неизвестная
ошибка,
неисправимый статус или отсутствие разрешения также сразу возвращаются
агенту
с доступной диагностикой. Для распознанной разрешённой ошибки
встроенный
обработчик выполняет одну попытку исправления и последующую проверку,
включая проверку после неуспешного исправления. Успех требует
готовности обоих
результатов. Ошибка исправления или проверки возвращается агенту
вместе
с исходными и последующими наблюдениями; второй попытки в этом запуске
нет.
Состояние попытки локально этому вызову, следующий запуск
самостоятельный.

Необходимое имя команды последующей проверки читается в выбранной
ветви
до изменяющего исправления. Готовность, неизвестная ошибка,
отключённое
исправление и dry-run завершаются прежде этой ветви.

Исключение конфигурации, транспорта или обработчика общий CLI
представляет
JSON-ошибкой с exit=4, reason, actions=[] и доступным исходным
результатом;
его потоки представлены полными bytes repr. Это не восстанавливает
внутреннюю
диагностику произвольно сломанного стороннего обработчика.
Ошибки синтаксиса CLI обрабатывает argparse: exit=2 и сообщение в
stderr.

Сохраните полный JSON, код завершения и реально выполненные действия.
Агент принимает решение по исходной и последующей диагностике;
оператор
применяет необходимые изменения установки или настроек. После этого
выполните
явный `check` с выбранными рабочими файлами.

## Диагностика и восстановление

1. Сохраните полный JSON Bootstrap, реальный exit и все `observations`
   вместе
   с исходной диагностикой и рекомендациями внешнего компонента. При
   входном
   отказе внешнего CLI изучите его stderr/exit 2 внутри наблюдения,
   даже когда
   внешний обработчик Bootstrap вернул `error`/4.
2. Сверьте выбранные каталог, параметры, разрешённое окружение,
   интерпретатор
   и версию установленного пакета. Для недоступного ресурса
   используйте его
   причину и рекомендации; для ошибочного входа исправьте объявленные
   значения.
3. После неуспешного install/repair проверьте фактическое состояние
   ресурса
   и сохранённый исходный final check. Действие могло изменить ресурс
   до ошибки
   ответа, тайм-аута или переполнения. Автоматического отката здесь
   нет.
4. Исправьте подтверждённую причину в принадлежащем оператору
   каталоге/настройках
   или действии. Выполните явный диагностический `check` с теми же
   выбранными
   файлами. Следующее изменение выполняйте только в разрешённом
   режиме;
   повторный запуск является новой попыткой, а не продолжением старого
   успеха.

## Проверки и границы доказательств

`tests/maintenance/test_generic_v2_consumer.py` проверяет настоящий
отдельно
установленный компонент: состояния, параметры, разрешённые действия,
исходный
recheck, диагностическую сохранность, UTF-8/OS-входы, глубину,
числовые и процессные
границы. `tests/architecture/test_bootstrap_v2_supply.py` проверяет
композицию
с фактическим Bootstrap и заполненной копией поставленного примера
конфигурации.
Существующие адресные Bootstrap-тесты проверяют транспорт и
обработчик;
`tests/smoke.sh` содержит поддерживаемый быстрый набор из шести явных
сценариев.
Это разные области проверки; проверка полного прикладного профиля
описана в
[руководстве профиля](maintenance-profile-v2.md#границы-проверенной-поставки).

`tests/maintenance/test_generic_v2_supply.py` проверяет неизменяемый
комплект.
Для воспроизведения адресных проверок явно задайте пути к шести его
файлам:
`AIP_GENERIC_WHEEL`, `AIP_GENERIC_DELIVERY`,
`AIP_GENERIC_SOURCE`,
`AIP_GENERIC_BUILD`, `AIP_GENERIC_BUILD_STDOUT`,
`AIP_GENERIC_BUILD_STDERR`.
Все они относятся к одной выбранной поставке. Выполните
supply-проверку отдельным
Python-скриптом, consumer/Bootstrap — адресным pytest-набором, smoke —
через Bash
с явным тестовым Python. Сохраняйте полный вывод и точный commit
проверяемой копии;
изменение commit требует доказательств для новой ревизии. Проверка
ссылок проверяет
достижимость документации, а не исполнимость установки или готовность
оператора.

## Откат и пределы поставки

Сам Bootstrap не меняет release pointer оператора, проектные профили
или базы.
Явно разрешённые внешние действия могут изменить окружение по
каталогу.
Для перехода к иной поставке используйте её процедуру установки и
выбранные
пакетным менеджером зависимости. Сохраните каталог, настройки и полный
результат
уже выполненного обслуживания; восстановление окружения принадлежит
внешнему
инструменту и оператору. Переключение действующего профиля и
эксплуатационные
каталоги поставляются отдельно от описанного интерфейса.
