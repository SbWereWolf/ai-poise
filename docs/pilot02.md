# HARNESS-PILOT-02: исполнение проверки реальных исходников

Срез начат: **2026-09-07T14:42:55+05:00**. Документ сохранён: **2026-09-07T15:04:48+05:00**.

## Цель, требования, DoD

Получить проверенный результат следующего этапа ранее опубликованной программы проверки
настройки проекта. Исполнять точную команду, не менять проверяемые исходники и не переходить
к анализу/осмотру без следующей инструкции пользователя. Сохранить не только доклад, но
и переносимый Task checkpoint с секциями, evidence и кодом. Дополнительно закрыть два
наблюдаемых недостатка инструмента общего прогона: потерю диагностики и ложный success.

Доказательства: реальные команды на Git snapshot Harness; отсутствие изменений дерева;
повтор verify без второго запуска; экспорт через штатный transfer; тест восстановления
в другом репозитории после исчезновения исходного store; полный независимый регрессионный
прогон; адресные RED/GREEN и отрицательные мутации проверяющей механики.

## Что было доступно при начале

Из HARNESS-PILOT-01 поставлены отчёты и исходники, но не его рабочая SQLite с живой
привязкой сессии. Старая БД не объявляется восстановленной из отчёта и не реконструируется
SQL-правками. Через существующие Project/Catalogue/WorkTools создана новая пилотная задача
`HARNESS-SELF-VERIFY-02` с той же точной программой. Planning воспроизведён штатно; текущая
инструкция пользователя «дальше» использована для перехода к execution.

Это новая локальная сущность по прежней программе, а не продолжение идентичности старого
store. Чтобы следующему шагу это повторение не потребовалось, результат теперь содержит
полный переносимый checkpoint, а не только текстовый JSON-отчёт.

## Проверяемый код

Объект — точный snapshot действительных закоммиченных исходников Harness, его тестов,
конфигураций, примеров, инструментов, правил и документации. Исключены прежние большие
архивы evidence и история Git; вместо них snapshot фиксирует исходный commit и побайтовые
хэши. Никакая учебная функция вместо приложения не подставлялась.

Это не проверка пользовательского ERP и не live-проверка JetBrains/Codex/Gmail.
Сопоставление файлов находится в `evidence/pilot02/real-pilot/source-snapshot.json`.

## Один разрешённый этап

Инструмент-пример `examples/project_execution.py` работает через существующий WorkTools:

```text
Разрешить ранее проверенную planning-задачу
→ явное continue предыдущего этапа
→ исполнить exact VERIFY
→ сохранить observations/отчёт
→ повтор verify проверяет идемпотентность
→ handoff + transfer одним пакетом
→ остановиться
```

Команда данного пилота — `python -m pytest tests/projects -q` с явным interpreter из
зарегистрированного метода. Отрицательный исход не подменяется успешным; образ результата
подготовлен до наблюдения и не утверждает заранее, что тесты прошли.

Пример вызывается для уже подготовленной задачи:

```bash
export PYTHONPATH="$PWD/src"
python examples/project_execution.py \
  --config /absolute/generated-project/project.json \
  --session CURRENT_SESSION \
  --task-id PLANNED_VERIFICATION_TASK \
  --user-decision continue \
  --export-request-id EXECUTION-CHECKPOINT-1
```

Это конкретный пример для процесса verification, не новый общий route engine. Он отказывает
попытке самостоятельно продвинуться из analysis или другого этапа. Публикация в Git remote
не нужна: проект пилота явно read-only и push выключен явно в выбранных значениях настройки.

## Сохранённый результат

`evidence/pilot02/real-pilot/task-checkpoint.zip` — результат штатного экспорта: SQLite,
файлы evidence, Git bundle. `execution.json` содержит сохранённые фактические paths и digest
исходной среды; пути не переписаны задним числом. Копии stdout/stderr даны рядом для чтения.

На момент handoff результат execution был `verified`, но НЕ принят пользователем. Владелец
освобождён. При штатном импорте и bootstrap восстанавливается проверенный execution той же
итерации, а не автоматически запускается analysis. Для начала analysis нужна следующая
инструкция пользователя; её этот срез не создаёт.

Пакет — локальная переносимая копия, не отправка Gmail. Import по-прежнему разрешён только
для отсутствующего владельца. Runtime/store-настройки получателя задаются существующим
project-инструментом. Сама библиотека переноса перепривязывает физические пути. Нельзя
восстановить это состояние редактированием таблиц вручную.

## Проверка передачи

`tests/test_project_execution.py` проходит штатный export/import между разными store и
репозиториями. Перед import исходный store становится недоступен. Проверяются статус и
итерация, отсутствие дополнительной приёмки, сохранение exact command и чтение полного
вывода через обычный `show`. Решение `continue` в тесте — fixture; в реальном пилоте — текущая
инструкция пользователя. Token usage и пользовательские события не выдумываются.
