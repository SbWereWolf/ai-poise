# Случаи приёмки пакетных инструментов и метрики сообщений

Обновлено: **2026-09-06T21:26:17+05:00**. BATCH-01…04 сохраняют прежний статус. Основная механика BATCH-05…08/MSG-01…02/06 реализована и проверена в DDD-04B; полная экономика и delivery adapters не объявлены выполненными.

Каноническое описание случаев: [JSON](planning-data/batch-tools-cases.json). Числа в примерах — тестовые данные, не defaults runtime.

## BATCH-01. Создание конфига из явного шаблона

Срез: **DDD-04A**.

**Исходные условия:** Выбран существующий самодостаточный шаблон с зафиксированной revision; переданы новые ID/значения.

**Действие:** Один apply_batch создаёт тип цели.

**Ожидается:** Полный независимый pack проходит действующие graph/content валидаторы исполняемого process-формата; точные methods/EvidencePlan конкретной задачи проверяются при Task creation.

**Запрещено:** Не запрашивать ручную правку файлов; не добавлять отсутствующую политику default-значением.

## BATCH-02. Согласованное изменение нескольких объектов

Срез: **DDD-04A**.

**Исходные условия:** Есть валидный pack с известной revision.

**Действие:** Одним пакетом создать секцию, её pre-gate, новую стадию и переход к ней, расположив записи в разном порядке.

**Ожидается:** Итоговый кандидат одинаков и валиден; проверены финальные ссылки, опубликована одна редакция.

**Запрещено:** Не отклонять пакет лишь из-за промежуточной ссылки на ещё не применённый элемент; не требовать отдельных вызовов.

## BATCH-03. Ошибка пакета не публикует половину

Срез: **DDD-04A**.

**Исходные условия:** Есть неизменный исходный pack; пакет содержит корректную секцию и неизвестный handler/target.

**Действие:** Применить пакет.

**Ожидается:** Опубликованный pack побайтно прежний; ошибки адресуют конкретные элементы; staged результат не объявлен рабочим.

**Запрещено:** Не сохранять корректную половину как успешный полный результат; не пропускать неправильный элемент.

## BATCH-04. Повтор и независимость процессов

Срез: **DDD-04A**.

**Исходные условия:** Два независимых goal-type pack; активная задача имеет собственный snapshot.

**Действие:** Изменить один pack и повторить идентичный запрос с тем же ключом операции.

**Ожидается:** Одна новая редакция; второй pack и snapshot задачи прежние; повтор возвращает receipt.

**Запрещено:** Не мигрировать task, не наследовать соседний pack и не создавать дубликат публикации.

## BATCH-05. Содержательный пакет без файла, созданного агентом

Срез: **DDD-04B**.

**Исходные условия:** Текущий этап разрешает дополнительную секцию, метод проверки и запись точки трассировки.

**Действие:** Передать всё вместе прямым входом verify.

**Ожидается:** Кандидат содержит все записи до prechecks; точный новый метод выбран в текущем verify; инструмент сам сохраняет представление.

**Запрещено:** Не требовать предварительного редактирования result_path или трёх register-вызовов.

## BATCH-06. Генерация артефактов и path-only регистрация

Срез: **DDD-04B**.

**Исходные условия:** Task/sprint binding известен; шаблон отчёта выбран явно; есть файл другого инструмента в разрешённом root.

**Действие:** Один пакет: создать файл по шаблону, другой из готового содержания, зарегистрировать существующий путь.

**Ожидается:** Файлы созданы в правильных roots; каждому назначен ID; технические свойства получены инструментом; регистрация требует только путь.

**Запрещено:** Не возвращать смысловые декларации артефакта и ручные hash/ID; не терять файл после cleanup.

## BATCH-07. Границы и повторы артефактов

Срез: **DDD-04B**.

**Исходные условия:** В пакете есть runtime/task/sprint paths; один путь выходит через symlink за разрешённый root.

**Действие:** Применить; затем исправить путь и повторить успешный пакет.

**Ожидается:** Недопустимый путь отклонён до регистрации; корректный повтор не создаёт новые IDs для того же результата.

**Запрещено:** Не писать вне roots и не подменять содержимое по ранее зафиксированному evidence ID.

## BATCH-08. Чтение коллекции и reasoning boundary

Срез: **DDD-04B**.

**Исходные условия:** Несколько секций известной задачи; observe/check ожидает аргумент после команды.

**Действие:** Прочитать секции одним read_batch; продолжить этап одним CONTINUE с новым аргументом.

**Ожидается:** Единый краткий ответ с деталями; команда наблюдения не повторяется; следующий пользовательский этап не начинается.

**Запрещено:** Не предлагать вызов по каждой секции и не соединять будущие решения пользователя в автоматический цикл.

## MSG-01. Один пользовательский turn, много инструментов

Срез: **DDD-04B**.

**Исходные условия:** Одно сообщение пользователя начинает задачу.

**Действие:** Bootstrap, submission, два verify, CONTINUE и повторная доставка события используют тот же turn.

**Ожидается:** user_messages_count = 1; event зарегистрирован один раз, без отдельного обязательного record-message call.

**Запрещено:** Не считать tool calls или retries пользовательскими сообщениями.

## MSG-02. Несколько сообщений, возврат и отмена

Срез: **DDD-04B**.

**Исходные условия:** Задача имеет начальное поручение и последующее «дальше».

**Действие:** Добавить замечание после доклада и сообщение отмены; повторить импорт одного из них.

**Ожидается:** Для четырёх различных сообщений count = 4; при отмене count не обнуляется, benefit = 0; дубль не добавлен.

**Запрещено:** Не объявлять каждое сообщение находкой; не удалять затраты отменённой работы.

## MSG-03. Явный источник и ограниченное покрытие

Срез: **DDD-07**.

**Исходные условия:** Один runtime предоставляет поток message events, другой настроен на agent_reported.

**Действие:** Наблюдать видимые сообщения; для недоступного интервала построить отчёт.

**Ожидается:** Source/coverage сохранены; неизвестные сообщения не превращаются в 0; reported не объявлен полным автоматическим capture.

**Запрещено:** Не оценивать tokens по количеству сообщений и не переключать режим молча.

## MSG-04. Привязка и агрегаты без двойного зачёта

Срез: **DDD-08**.

**Исходные условия:** Одно поручение пришло в sprint scope до выбора task; после выбора получило основной task binding. Есть второй независимый sprint-only message.

**Действие:** Построить task/sprint/type/day/week/all отчёты; повторить импорт.

**Ожидается:** Task учитывает первое событие один раз; sprint/all = 2; ссылки на другие сущности не добавляют события; повтор не меняет суммы.

**Запрещено:** Не суммировать related references как дополнительные сообщения.

## MSG-05. Handoff и поздний импорт

Срез: **DDD-08**.

**Исходные условия:** Одна task работала в двух runtime; сообщение с надёжным source timestamp доставлено позже.

**Действие:** Объединить наблюдения с дедупликацией.

**Ожидается:** Count задачи объединяет разные события; периоды используют source time и явную timezone; неполнота прошлой истории указана.

**Запрещено:** Не сбрасывать счётчик новой session; не выдавать received_at за надёжное время источника.

## MSG-06. Сообщение получает контекст без повторного ввода IDs

Срез: **DDD-04B**.

**Исходные условия:** Есть активная задача с известными goal_type, stage и iteration; в общем входе передан один user event.

**Действие:** Обработать событие в bootstrap/submit, выполнить verify и повторную доставку с тем же ключом.

**Ожидается:** Событие связано с известной работой автоматически; user_messages_count = 1; повтор не создаёт новую итерацию. Если известной причины нет, она остаётся неклассифицированной.

**Запрещено:** Не требовать ручного заполнения известных IDs и отдельного вызова регистрации; не выводить причину из количества инструментов.

## MSG-07. Обычная поэтапная работа не выдаётся за дефекты

Срез: **DDD-08**.

**Исходные условия:** У документационной задачи три применимых содержательных этапа. Наблюдаются четыре сообщения: начальное поручение, два «дальше» и финальное принятие; замечаний нет.

**Действие:** Завершить и предъявить три разные итерации трёх этапов, сформировать отчёт.

**Ожидается:** goal_type=documentation; user_messages_count=4; planned_content_stages_count=3; delivered_stages_count=3; delivered_iterations_count=3; сообщений о недостатках=0. Источник и покрытие указаны.

**Запрещено:** Не считать четыре сообщения четырьмя дефектами; не штрафовать штатную приёмку и не переводить сообщения в токены.

## MSG-08. Позднее замечание, новое требование и неизвестная причина разделены

Срез: **DDD-08**.

**Исходные условия:** Есть ранее предъявленный результат. Три новых уникальных сообщения имеют соответственно: подтверждённое замечание к нему; явное новое требование; недостаточно контекста для классификации.

**Действие:** Записать события обычным пакетным входом и построить общий и тематические отчёты.

**Ожидается:** Общий расход увеличивается на 3; известные замечания к прежнему результату — на 1; новое требование — отдельный срез; неклассифицированный остаток — 1. Известная ссылка на прежний результат сохранена.

**Запрещено:** Не превращать новое требование или неизвестную причину в дефект; не считать число сообщений числом находок.

## MSG-09. Повторный подход увеличивает итерации, но не число уникальных этапов

Срез: **DDD-08**.

**Исходные условия:** Одна задача имеет два содержательных этапа; выполнены и предъявлены stage-A#1, stage-A#2 после замечания и stage-B#1. Внутри stage-A#2 было два verify и CONTINUE.

**Действие:** Построить отчёт и повторить импорт прежних событий; отдельно предъявить view с неполной историей.

**Ожидается:** Для полного наблюдения delivered_stages_count=2 и delivered_iterations_count=3; вызовы verify/CONTINUE и повторы событий чисел не меняют. Для неполной истории coverage указан явно; отсутствующее не превращено в ноль.

**Запрещено:** Не смешивать количество stages, iterations, messages и tool calls; не объявлять неполное наблюдение полным.
