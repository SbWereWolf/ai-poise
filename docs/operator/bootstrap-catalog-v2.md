# Bootstrap и каталог catalog/v2

Руководство описывает корневой `bootstrap` из этой поставки AI poise.
Он запускает выбранный инструмент по конфигурации и передаёт полный результат
подключаемому обработчику. Действующий `poise infra/deps/check` — отдельный маршрут
с профилем `requirements/v1`; подготовка Bootstrap сама не переключает оператора.
[Справочник команд](poise-command-reference.md#обслуживание-окружения) разделяет эти маршруты.

## Граница приложений и происхождение

Poise владеет CLI, чтением конфигурации, стандартным рендером аргументов,
запуском процесса и интерфейсом обработчика. Выбранный обработчик владеет
разбором результата, оценкой готовности, решением об исправлении и проверкой.
Внешнее приложение владеет каталогом, его параметрами и действиями обслуживания.
Исходники внешнего инструмента не копируются в Poise.

Версии внешних пакетов выбирают при установке пакетным менеджером. Bootstrap
использует указанные оператором команды. Собственная версия Poise принадлежит
его поставке. Описанный Python-код Poise требует Python 3.13; интерпретатор
внешнего приложения выбирается отдельно согласно его требованиям.

## Настройка команды и рабочего файла

Выберите корень установленной копии Poise, каталог обслуживания и интерпретаторы.
Установите выбранный внешний инструмент в его окружение пакетным менеджером.
Корневой `bootstrap` поставляется вместе с соседним `apps/bootstrap/`;
ему не нужны Task, сессия harness или `POISE_CONFIG`.

В следующем примере `/srv/poise/app` — выбранная оператором копия, а не
встроенное значение программы. Из её корня подготовьте рабочие файлы:

```bash
poise_root=/srv/poise/app
bootstrap_python=/srv/poise/bootstrap-venv/bin/python
catalog_dir=/srv/poise/catalog-v2
cd "$poise_root"
cp config/bootstrap.example.json config/bootstrap.json
cp config/environment-maintenance.example.json config/environment-maintenance.json
```

Заполните оба рабочих файла значениями своей установки. Рабочие
`config/bootstrap.json` и `config/environment-maintenance.json` находятся
внутри папки Poise и исключены из Git. Отслеживаются заполненные примеры
[команды](../../config/bootstrap.example.json) и
[параметров внешнего инструмента](../../config/environment-maintenance.example.json).
В примере параметров `python` указывает реальный выбранный интерпретатор.
Состав этого файла определяется внешним каталогом: Bootstrap передаёт его
через команду как файл значений, а не интерпретирует его содержимое.

### Конфигурация команды

`--config` выбирает JSON-объект со следующими полями:

| Поле | Значение |
|---|---|
| `parameters` | Объект строковых параметров шаблона: имена и значения — строки. |
| `commands` | Непустой объект имён команд и непустых списков строковых аргументов. |
| `handler.callable` | Импортируемый обработчик в формате `module:callable`. |
| `handler.options` | Явный JSON-объект настроек выбранного обработчика. |

Каждый аргумент независимо рендерится стандартным Python `string.Template.substitute`.
Доступны `$name`, `${name}` и `$$` для буквального доллара.
Значения берутся из `parameters`; `catalog_dir` берётся из обязательного
`--catalog-dir` и имеет приоритет над одноимённым параметром.

Команда — список argv, например `["${python}", "-m", "environment_maintenance",
"check", "--catalog-dir", "${catalog_dir}"]`. Исполняемый файл и параметры
полностью задаются конфигурацией. Процесс запускается без shell; относительные
пути относятся к текущему рабочему каталогу запуска Bootstrap. Для приведённых
примеров это явно выбранный `poise_root`.

Поставленный пример сначала вызывает внешний `check` для всех трёх операций.
При разрешённом исправлении обработчик вызывает команду `repair`, которая
в примере запускает внешний `run`, затем `verify` с внешним `check`.
Так первоначальное наблюдение предшествует решению об изменении окружения.

### Настройки встроенного обработчика

Пример выбирает `apps.bootstrap.environment_result:handle`.
Его `handler.options` содержит:

| Поле | Назначение и значение примера |
|---|---|
| `schema` | Ожидаемая schema JSON-результата: `environment-maintenance/result/v2`. |
| `status_exit_codes` | Соответствие статуса реальному exit: ready=0, action_required=2, unavailable=3, failed=4. |
| `success_statuses` | Статусы готовности: `["ready"]`. |
| `repairable_statuses` | Статусы, допускающие исправление: `["action_required"]`. |
| `repair_operations` | Публичные операции с разрешением исправления: `["infra", "deps"]`. |
| `repair_command` | Имя команды исправления из `commands`: `repair`. |
| `verification_command` | Имя последующей проверки: `verify`. |
| `failure_exit_code` | Ненулевое целое для ошибки обработчика: `4`. |

Эти поля принадлежат именно встроенному обработчику. Другой подключаемый
обработчик определяет собственные настройки через тот же интерфейс.

## Подготовка и безопасная проверка

После заполнения файлов выполните команды из выбранного корня:

```bash
"$bootstrap_python" -I -B "$poise_root/bootstrap" check \
  --config "$poise_root/config/bootstrap.json" --catalog-dir "$catalog_dir"
"$bootstrap_python" -I -B "$poise_root/bootstrap" infra \
  --config "$poise_root/config/bootstrap.json" --catalog-dir "$catalog_dir" --dry-run
"$bootstrap_python" -I -B "$poise_root/bootstrap" deps \
  --config "$poise_root/config/bootstrap.json" --catalog-dir "$catalog_dir" --dry-run
```

В поставленном примере `check` только наблюдает. Для применения разрешённого
обслуживания используйте `infra` или `deps` с теми же настройками.
Названия не выбирают каталог автоматически: оператор явно передаёт нужный каталог.

| Аргумент | Назначение |
|---|---|
| `infra`, `deps`, `check` | Публичная операция и имя первоначальной команды в конфигурации. |
| `--config PATH` | Обязательный путь JSON-конфигурации Bootstrap. |
| `--catalog-dir PATH` | Обязательное непустое значение параметра каталога. |
| `--values PATH` | Повторяемый аргумент внешнего инструмента с файлом значений. |
| `--set NAME=VALUE` | Повторяемое переопределение внешнего инструмента. |
| `--dry-run` | Передаётся внешней команде; встроенный обработчик не выполняет исправление. |
| `-h`, `--help` | Справка без запуска инструмента. |

Дополнительные `--values`, `--set` и `--dry-run` добавляются после аргументов
шаблона с сохранением порядка и передаются также последующим командам.
Например, для каталога, определяющего строковый параметр `python`:

```bash
"$bootstrap_python" -I -B "$poise_root/bootstrap" deps \
  --config "$poise_root/config/bootstrap.json" --catalog-dir "$catalog_dir" \
  --values "$poise_root/config/environment-maintenance.json" \
  --set python=/srv/poise/tool-venv/bin/python --dry-run
```

## Интерфейс подключаемого обработчика

Обработчик импортируется стандартным `importlib` по `module:callable`.
Это импортируемая функция или callable-объект с контрактом
`apps.bootstrap.contracts.ResultHandler`:

```python
def handle(initial, invoke, options, context):
    ...
    return {"exit_code": 0}
```

`initial` — `subprocess.CompletedProcess[bytes]` с полными stdout/stderr
и реальным returncode. `invoke(name)` запускает именованную команду
с теми же добавленными аргументами и возвращает такой же полный результат.
`options` — настройки обработчика; `context` содержит `operation` и `dry_run`.
Результат — JSON-сериализуемый dict с целым `exit_code`; остальные поля
определяет обработчик. Общий CLI выводит полный JSON и возвращает этот код.
Замена обработчика производится через конфигурацию без зависимости транспорта
от конкретной реализации. Обработчик сохраняет диагностику собственных действий.

## Результаты и ошибки

Встроенный обработчик сопоставляет JSON schema, status и реальный exit.
Результат содержит:

| Поле | Значение |
|---|---|
| `status` | `ready` либо `error`. |
| `exit_code` | 0 при готовности, иначе настроенный `failure_exit_code`. |
| `observations` | Упорядоченные результаты initial, repair и verification, когда они выполнялись. |
| `actions` | Имена последующих команд, попытки вызова которых действительно предприняты. |
| `reason` | Причина ошибки при `status=error`. |

Наблюдение содержит `stage`, полные `stdout`, `stderr` и реальный `exit_code`.
Корректный UTF-8 сохраняется как текст без усечения. Невалидные байты
показываются однозначным Python repr; такой результат не признаётся готовностью.
При ошибке вызова последующей команды наблюдение содержит диагностику и
`exit_code: null`, поскольку код дочернего процесса не получен.

Готовый исходный результат сразу возвращается агенту. Неизвестная ошибка,
неисправимый статус или отсутствие разрешения также сразу возвращаются агенту
с доступной диагностикой. Для распознанной разрешённой ошибки встроенный
обработчик выполняет одну попытку исправления и последующую проверку,
включая проверку после неуспешного исправления. Успех требует готовности обоих
результатов. Ошибка исправления или проверки возвращается агенту вместе
с исходными и последующими наблюдениями; второй попытки в этом запуске нет.
Состояние попытки локально этому вызову, следующий запуск самостоятельный.

Необходимое имя команды последующей проверки читается в выбранной ветви
до изменяющего исправления. Готовность, неизвестная ошибка, отключённое
исправление и dry-run завершаются прежде этой ветви.

Исключение конфигурации, транспорта или обработчика общий CLI представляет
JSON-ошибкой с exit=4, reason, actions=[] и доступным исходным результатом;
его потоки представлены полными bytes repr. Это не восстанавливает внутреннюю
диагностику произвольно сломанного стороннего обработчика.
Ошибки синтаксиса CLI обрабатывает argparse: exit=2 и сообщение в stderr.

Сохраните полный JSON, код завершения и реально выполненные действия.
Агент принимает решение по исходной и последующей диагностике; оператор
применяет необходимые изменения установки или настроек. После этого выполните
явный `check` с выбранными рабочими файлами.

## Откат и пределы поставки

Сам Bootstrap не меняет release pointer оператора, проектные профили или базы.
Явно разрешённые внешние действия могут изменить окружение по каталогу.
Для перехода к иной поставке используйте её процедуру установки и выбранные
пакетным менеджером зависимости. Сохраните каталог, настройки и полный результат
уже выполненного обслуживания; восстановление окружения принадлежит внешнему
инструменту и оператору. Переключение действующего профиля и эксплуатационные
каталоги поставляются отдельно от описанного интерфейса.
