## Goal and cause

Remove the rule that the mere existence of any unfinished Task prevents every manifest edit.
An explicit correction of `git.commit_pattern` must remain possible with available or active
Tasks. Use effect-specific guards for actual storage/lock or repository rebinding instead.

The guard was introduced by commit `67da88cff2baa8a19c7459d275c22f1792d626d6`,
`feat: update live project configuration safely`, dated 2026-09-12 00:19:42 +05:00.
Git records author `SbWereWolf`; that metadata alone does not identify who chose the policy
or prove that the user required it. It began in `src/harness/infrastructure/project_config.py`
and now lives in [the project configuration owner](../../../src/poise/infrastructure/project_config.py).

The current `_active_work` query treats every status other than `completed` or `cancelled`
as active. The publisher applies this predicate to any `manifest_edits`, even a harmless
validation-policy correction. This is excessive: Task status is not the effect of an edit.

T011 exposed a deadlock: `git.commit_pattern = ".+"` is matched against the complete message
without DOTALL, while [the project policy](../../workflows/commit-messages.md#продуктовый-смысл-и-формат-5070)
requires a title, blank line and body. Explicit `(?s).+` accepts multiline text, but the
configuration editor refuses that correction while the Task is unfinished.
Do not silently change regex semantics or weaken the 50/70 documentation policy.

## Reproduction and expected result

2. Create an available Task, or start a Task in its own worktree.
3. Request only `git.commit_pattern` from `.+` to `(?s).+` at the exact known project revision.
4. Before the fix, observe `Manifest or state relocation requires quiescent project; active work exists`.
5. After the fix, publication succeeds and exact retry replays. A fresh runtime reads the new policy;

## Requirements and acceptance criteria

- R1: Ordinary manifest edits, including commit validation, Git author metadata, bounded limits
  and future process settings, do not require every Task to become terminal.
- R2: Decisions use the actual before/after values, not the presence of an edit entry. A no-op
  resource edit must not impose a false relocation gate.
- R3: Actual state/lock and preserved-artifact binding changes keep their integrity guard;
  repository rebinding keeps the existing allocated-worktree guard. No unknown directories
  are removed, no databases are rewritten, and no histories are migrated implicitly.
- R4: Keep exact known revisions, lock serialization, full candidate validation, pending receipts,
  atomic publication, exact replay and stale/conflicting request rejection.
- R5: Fresh invocation can resume the same Task after an ordinary policy update. The update itself
  must not alter any Task state/version, process snapshot, ownership, stored provenance or WIP.
- R6: Update the normative documentation and agent rule projection with the same change.
- R7: Persist red tests, implementation, green evidence and local commits separately; do not push.

## Implementation result — 2026-09-27

The blanket guard has been removed from the source and normative rules. The existing
configuration owner now validates the full candidate and compares actual before/after
bindings. Ordinary policy edits and no-op bindings do not use the unfinished-Task gate.
Real storage rebinding retains its check; Git resource rebinding reuses the allocated
execution/worktree check. This is not an unconditional deletion of data-integrity guards.

Before implementation, 15 test cases failed with the exact obsolete rejection and 10
protection cases passed. The final focused set passes all 65 tests, including all 25 new
regressions. The maintained smoke set passes 6 tests. Canonical documentation checks and
`git diff --check` pass. An intermediate run exposed a test-oracle field error and an
unbound child-interpreter import path; both were corrected, with the failed output retained.

The source correction does not automatically deploy a new operator, modify the live
`git.commit_pattern`, grant independent approval or advance T011's stored lifecycle.
For further user-authorized source work, the documented native-tool path is available.
