# Реестр требований

## Владение и явные пути

Версии, допустимое создание и границы backup собраны в [матрице хранилищ](../architecture/storage-lifecycle.md#владельцы-и-версии); переносимая поставка и настроенные абсолютные пути различаются [явно](../architecture/storage-lifecycle.md#явные-пути-и-переносимая-поставка).

Requirements Registry хранит канонические System и Application требования и связи
System → Application в отдельной SQLite-базе. Требования Task, утверждённые цепочки
System → Application → Task и их исторический снимок принадлежат Task DB.

В конфигурации проекта явно заданы `paths.requirements_database` и
`paths.requirements_lock`; относительные значения разрешаются относительно явного `paths.state`, а не Git
checkout. Абсолютные значения используются точно. У самого AI-poise старое
авторизованное Task-хранилище остаётся в `projects/ai-poise`, а новая Requirements DB
настроена отдельно: `/home/sbwerewolf/workdata/poise-project-data/ai-poise/requirements.sqlite`
и соседний `requirements.lock`. Это новая база, не перенос существующей Task DB. Постоянные данные проекта размещаются вне обслуживаемой кодовой
базы. Пути и физические файлы не должны совпадать с Task DB или хранилищем telemetry.
Отсутствующие поля отклоняются: скрытых значений по умолчанию и автоматического
переноса существующих данных нет. Шаблоны новых проектов содержат оба поля.

## Статусы и полнота связей

Требования имеют ровно три предметных уровня: **System → Application → Task**. Дополнительные уровни иерархии не вводятся. Любые тематические, продуктовые, компонентные или организационные подборки являются виртуальной группировкой (tags/views/collections) и не меняют эту сквозную цепочку. Требование Task может обнаружить необходимость нового Application или System requirement: discovery снизу вверх допустим, но сохранённая связь всё равно строится через все три уровня. Если агент не может обоснованно состыковать требование с существующей цепочкой или понять, какой новый предок нужен, он не выдумывает смысл и задаёт вопрос.

`current` означает действующее требование; `future` участвует в анализе и планировании, но не добавляется автоматически к проверкам текущего соответствия. В целевой модели `future` может использоваться как **проектируемое требование**. Для проектируемой цепочки допускается явно типизированное пустое звено **любого из трёх уровней** там, где соответствующая формулировка ещё не создана или возможность ещё не разработана. Например, проектируемый System requirement может быть связан через пустые Application/Task звенья, а Task requirement — через пустой Application/System предок. Пустое Task-звено не создаёт исполняемую Task. Такое пустое требование — не четвёртый уровень и не доказательство выполнения: это адресуемый placeholder конкретного уровня, который сохраняет сквозную связь `System → Application → Task` и показывает незакрытый gap. Исполнимый формат описан в разделе [явных пустых проектируемых звеньев](#явные-пустые-проектируемые-звенья): `status: "future"`, `text: ""` и прежний типизированный ID. Используется публичный владелец Requirements, не ручная запись БД.

`obsolete` сохраняется исторически, исключается из нового покрытия и не может быть основанием новой Task. Изменение текста или статуса не переписывает старые снимки. Когда проектируемый placeholder позже получает содержательное требование, новая revision/chain не переписывает исторический Task snapshot.

Связи System → Application имеют кратность многие-ко-многим. Для `current` цепочек каждый Application обязан иметь содержательного неустаревшего System-родителя, а каждый используемый Task requirement — содержательную Application-связь. Проектируемая цепочка может явно содержать placeholder на любом отсутствующем уровне; такой placeholder отображается как gap и не засчитывается как current coverage. Каждый неустаревший содержательный System должен быть распределён хотя бы в один Application либо явно оставаться проектируемым gap. `coverage` и `gaps` показывают обе стороны разрывов. `coverage` с `mode: "current"` учитывает только действующие содержательные узлы; обычный анализ включает также `future` и проектируемые placeholders в исполнимом API.

## Декларативный API и согласование

Команда `python -m poise requirements --config /absolute/project.json` читает один
JSON-пакет из stdin. Формат: `{"operation": "query", "input": {"queries": [...]}}`.
Каждый запрос имеет уникальный `id` и `kind`: `registry`, `coverage`, `gaps`, `chain`
(с `requirement_id`) или `plan_task` (с `task_requirements`). Число запросов и
требований плана ограничено конфигурационным `batch.max_items`.

Пример планирования без изменения реестра:

```json
{"operation":"query","input":{"queries":[{"id":"plan","kind":"plan_task","task_requirements":[{"text":"Сохранить результат задачи с происхождением требований.","applications":["APP-TRACE"]}]},{"id":"coverage","kind":"coverage","mode":"current"}]}}
```

План возвращает `status`, `gaps`, `chains` и `snapshot`. При отсутствующем Application/System он
предлагает явный текст недостающего требования, но сам не утверждает и не записывает его. Если
планирование обнаруживает ещё не сформулированное звено любого уровня, API позволяет явно выбрать
typed placeholder соответствующего уровня вместо выдуманной формулировки. Для действующего
(`current`) обязательства placeholder не заменяет требование; для явно проектируемого (`future`)
обязательства он сохраняет сквозную цепочку и видимый gap. При **новом** согласовании цепочки
показать пользователю все содержательные тексты, статусы и пустые проектируемые звенья System →
Application → Task, а не только идентификаторы. Уже данное точное согласие сохраняется в
`requirements_agreement` Task и не требует нового решения пользователя на каждом обычном этапе или
при согласованном исполнителем и независимым проверяющим restart без изменения этих цепочек. `ready`
у плана означает структурную полноту допустимой цепочки, а не согласие пользователя и не реализацию
проектируемого требования.

Изменения отправляются одним `apply` с `request_id`, `expected_revision` и
`operations`. Операции: `put_requirement` с точными `id`, `level`, `status`, `text`
и `link` с `system`, `application`. Весь пакет применяется атомарно; конфликт
revision требует нового чтения. Точный повтор request_id возвращает сохранённый
результат, изменённый пакет с тем же идентификатором отклоняется. Прямое редактирование
таблиц, вторая каноническая JSON-копия и автоматические согласования не допускаются.

## Публикация и исторический снимок

В публикуемую Task передаются `requirements_snapshot` из согласованного плана и
`requirements_agreement: {"accepted": true, "chains": [...]}` с точными полными
цепочками. Эти поля потребляет Requirements gate; Task сохраняет контекст в своих
metadata в той же транзакции, что и публикацию. Обычная Task и пакет Sprint проходят
одну границу проверки; отсутствующий, устаревший или неподтверждённый контекст
отклоняется до записи Task.

Поздняя правка живого реестра не меняет смысл опубликованной Task. Точный повтор создания использует сохранённую идентичность запроса. Обычное исполнение использует замороженный requirements snapshot/agreement. Если исполнитель доказывает, что текущие требования делают успешное продолжение невозможным или обход неадекватен, он согласует restart с независимым проверяющим. Авторизованный restart может сформировать новый согласованный requirements snapshot: policy задаёт поля по умолчанию, а иной точный набор Task-полей проверяющий фиксирует в решении. Старое согласие и старые chains остаются историей и не выдаются за актуальные. Изменение project/harness rules требует отдельного согласия пользователя. Существующие исторические Task без снимка не дополняются выдуманной цепочкой автоматически.

При повторном `ready` после разрешённого restart Task сравнивает свой текущий
snapshot/agreement с сохранённым. Совпадение направляет проверку в исторический
контекст: последующий дрейф живого Registry не переопределяет Task. Изменённый
контекст, в том числе у Task без `planning_revision`, проходит планирование и
проверку согласованных полных цепочек против живого Registry. Перед публикацией
проверяется, что реестр не изменился после подготовки. При обнаруженном дрейфе
Task остаётся в прежнем newborn-состоянии, а независимое изменение Registry не
откатывается. При успехе прежний snapshot/agreement сохраняется в истории restart,
текущий контекст заменяется в той же Task-транзакции, что и промоция; отсутствующее
или несогласованное поле не заменяется историческим значением молча.

Выбор существующей Task объектом только с `id` — продолжение сохранённого состояния,
не новое предложение договора. Текущая проекция методов может законно отличаться
от первоначального договора. Она не подставляется в повторную проверку полного
контракта; проверка явно переданного full/canonical договора остаётся строгой.
[Публичный выбор Task](batch-work.md#выбор-существующей-задачи-по-id).

## Однократный импорт утверждённой поставки

Утверждённый документ схемы `requirements-bootstrap-1` импортируется операцией
`import_bootstrap` с точными `path` и `request_id` в первоначально пустой реестр.
Повтор того же запроса идемпотентен. Текст, статусы `future` и связи сохраняются;
импорт не объявляет будущие требования реализованными. После проверки чтением из
Requirements DB временный документ удаляется по отдельной задаче очистки.
В этой поставке импорт уже завершён: 6 требований и 4 связи сохранены в ревизии 1;
точный повтор и полное чтение проверены перед удалением временных файлов в задаче `0067`.
Реестр, история запросов и квитанция импорта входят в полную резервную копию.

В переносимом архиве этой поставки снимок новой базы находится в
`projects/ai-poise/database/requirements.sqlite`. Перед запуском на целевой машине
скопировать этот файл в **явно выбранный** `paths.requirements_database` вне Git
checkout либо явно изменить оба Requirements-пути через настройку проекта.
Восстановление архива само по себе не является разрешением перезаписи рабочей базы:
назначение должно быть новым, контрольная сумма проверена. Не создавать пустой
реестр вместо импортированного снимка. Квитанция импорта хранится в материалах `0106`.

## Конкурентная запись

RequirementsStore получает write reservation до чтения revision и request digest через общий `write_transaction`. Краткий независимый SQLite writer пережидается на `BEGIN IMMEDIATE`; краткий читатель — на `COMMIT`. Тело изменения не повторяется. Исчерпанный бюджет даёт диагностическую ошибку с путём БД и SQL-границей, а транзакция откатывается без частичного изменения требований, связей и request response. Удалять lock-файлы или базу для устранения блокировки нельзя. `lock_seconds` ограничивает каждое ожидание отдельно, не весь запрос. Политика и отрицательные сценарии описаны в [проектировании общей границы](../architecture/sqlite-write-boundary-design.md).

## Явные пустые проектируемые звенья

System/Application placeholder создаётся обычным `put_requirement`: прежние `id`,
`level`, `status: "future"`, `text: ""`. Нового уровня и отдельного placeholder ID
нет. Связи задаются прежним `link`. `plan_task` дополнительно допускает у элемента
`task_requirements` явное `status: "future"` и пустой `text`; такой элемент —
проектируемый узел snapshot, а не созданная исполнимая Task.

Каждый пустой узел виден как `projected_placeholder` с уровнем; plan возвращает
`status: "gaps"` даже при полной связности. `gaps` реестра показывает и связанные
пустые System/Application. Пустой current или текст из одних пробелов отклоняется.
Заполнение текста и смена статуса используют тот же ID, поэтому связи не теряются.
Старые сохранённые snapshots не меняются от последующего заполнения live реестра.
