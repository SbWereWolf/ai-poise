# ApplyPlan / Publish — общий инструмент внешних изменений

Обновлено: **2026-10-08**. Контракт существующих действий и их
привязки к текущему циклу Task. Описанное поведение требует установки
соответствующей версии AI poise; проверка рабочей копии сама по себе
не обновляет установленный оператор.

## 1. Один пакет и два семейства обработчиков
`poise work` по-прежнему принимает JSON через stdin: `operation`, `input`, `messages`. Выбор обработчика задан графом процесса, не названием типа цели. В результате этапа `stage_work` содержит план либо намерение публикации. Все прочие секции, трассировка, доказательства и пути остаются в том же пакете.

`apply_plan` выполняет заданный план, фиксирует наблюдаемые действия и при необходимости возвращает продолжение тому же агенту. `publish` поддерживает типизированную data-publication, но любое Git-намерение публикации отклоняет до Git-команды. Они используют Task/Feedback/ContentPolicy, общий executor, внешние порты и короткий SQLite UnitOfWork. Прямой SQL или присваивание lifecycle из handler запрещены.

## 2. План интеграции
```json
{
  "plan": {
    "kind": "git_merge",
    "base_commit": "<точный полный SHA базового коммита>",
    "sources": [
      {"commit": "<точный SHA первого источника>", "checkpoint_message": "WIP: integrate first source"},
      {"commit": "<точный SHA второго источника>", "checkpoint_message": "WIP: integrate second source"}
    ]
  },
  "phase": "prepare",
  "resolutions": [],
  "finding_resolutions": []
}
```
Это содержимое `stage_work`, не самостоятельный envelope. SHA-маркеры в документации должны быть заменены фактическими SHA; они не допустимы для запуска. Полностью исполняемый пример — `examples/actions_demo.py`.

Источники должны существовать в текущей codebase; remote, Git identity, шаблон ветки, правила сообщений и timeout берутся из явной конфигурации. Начальное дерево должно быть чистым, HEAD должен совпадать с заданной базой. Неизвестные изменения не сбрасываются. Предварительная проверка охватывает весь список источников, лимит числа действий и требуемое сообщение окончательного коммита.

Источники объединяются в заданном порядке `git merge --no-ff --no-commit`. Для перехода от промежуточного источника к следующему необходим локальный checkpoint-коммит. Он использует явно заданное сообщение, сохраняется в receipt как **UNVERIFIED**, не является успешным доказательством и не обновляет целевую ветку. Последнее объединённое дерево проходит обычные проверки и только затем получает проверенный коммит и публикацию в собственной ветке задачи.

### Конфликт и CONTINUE
Ответ `awaiting_action_continuation` содержит наблюдённые конфликтующие пути и актуальный `result_template`. Агент меняет исходники нативным IDE/patch-инструментом и возвращает в том же пакете `phase: continue` и `resolutions: [{"path": "src/file.py", "reason": "Почему решение сохраняет требования источников"}]`.

AI poise проверяет точный набор путей, принадлежность MERGE_HEAD текущему плану, отсутствие конфликтных маркеров и незавершённых записей index. Затем сам выполняет Git stage и продолжает план. Повторный merge уже обработанного источника не запускается. Объяснение разрешения сохраняется в action receipt; Git-конфликт сам по себе не является дефектом исходной задачи.

Если объединённые тесты не прошли, агент исправляет код и повторяет
`verify` той же итерации. Новое дерево получает новые проверки; план
источников не воспроизводится заново. Содержимое начатого плана
неизменно. Для нового плана нужен предусмотренный процессом явный
переход к новой работе; допустимые пути описаны
в [контракте текущего цикла](#текущий-цикл-task-и-неизменность-плана).

## 3. Осмотр и локальная интеграция
Нормальный маршрут заканчивает содержательные `apply_plan`/`inspect`/`revise`-этапы, после чего принятие и интеграция выполняются отдельным публичным lifecycle. Сначала заканчивается проверка текущего этапа и возвращается доклад. Ни одно семейство не начинает следующий содержательный этап само. Действующее поручение исполнителю покрывает последовательные `executor`-этапы, но перед `reviewer`, принятием и интеграцией действуют отдельные ворота из [канонической политики ролей](../governance/development-rules.md#роли-этапов-и-непрерывность-поручения).

Git-публикация через `publish` больше не является допустимым эффектом. Любое Git-намерение публикации отклоняется до Git-команды с указанием установить `push_required=false` и использовать локальную операцию `integrate`. `git push` запрещён без исключений, в том числе при пользовательском authorization, внутри Git-адаптеров и в настраиваемых command runner. Data-publication с собственным внешним транспортом остаётся отдельным типизированным действием и не разрешает Git push.

Принятый commit публикуется только локально: `integrate` обновляет существующую ветку задачи от текущего target, повторяет требуемые проверки и под общим target lock выполняет в основном checkout точный `git merge --ff-only <task-branch>`. При drift цикл обновления и проверок повторяется; dirty/unfinished target или невозможность fast-forward блокируют операцию без изменения target. No-op не создаёт искусственный commit. Remote refs не читаются и не изменяются.

## 4. Изменения среды через тот же apply_plan
```json
{
  "plan": {
    "kind": "commands",
    "steps": [{
      "id": "install-runtime",
      "apply": "<полный exact method object>",
      "probe": "<полный exact method object>",
      "probe_false_exit_codes": [1]
    }]
  },
  "phase": "prepare",
  "resolutions": [],
  "finding_resolutions": []
}
```
`apply` и `probe` в реальном пакете — не строки, а полностью заданные объекты метода: id, argv, cwd, environment, expected_exit_code, stdout_contains, stderr_contains. Эти команды не задают таймаут: после запуска AI poise ждёт их конечный результат. Документационная запись сокращена только ради чтения; исполнитель таких сокращений не принимает. Пример исполняемых объектов есть в CLI demo.

Перед эффектом выполняется read-only probe. Если desired state уже подтверждено, изменение не повторяется. Только явно перечисленные `probe_false_exit_codes` означают «состояние не достигнуто, действие допустимо». Signal, другой exit либо неверный ожидаемый вывод не выдаются за нормальное FALSE. После apply снова исполняется probe; успешным считается завершённое действие с подтверждённым состоянием.

Каждый шаг имеет before-probe, apply/probe receipts и исходные stdout/stderr в task storage. Следующий шаг не запускается после failed/blocked. При неизвестном исходе незавершённого действия повтор использует probe и не исполняет побочный эффект вслепую.

Для correction этап может снова иметь handler `apply_plan`, вместе с `finding_resolutions` общего FeedbackBook. Затем отдельный inspect принимает или отклоняет предложение. Это тот же механизм feedback, не environment-specific runner.

## 5. Состояния операции и возвраты
| Состояние | Поведение |
|---|---|
| prepared | Следующий известный шаг ещё не начат |
| running | Намерение сохранено, исход внешнего шага ещё требует receipt/probe |
| awaiting_resolution | Наблюдаемое Git-объединение ожидает решения агента |
| complete | План закончен; это ещё не заменяет тесты/осмотр/приёмку Task |
| failed | Известный результат не достиг условий; хвост не выполняется |
| blocked | Продолжение не определено безопасно; повтор эффекта не угадывается |

Для известного failed/blocked action явный `bootstrap` с `decision: rework`, причиной и допустимым target stage создаёт новую итерацию. Pending MERGE_HEAD сначала требует разрешения/санкционированного прекращения; скрытого reset нет. Все этапные и общие limits сохраняются. Snapshot action адресуется в контексте, повторные task ID не требуются.

## Текущий цикл Task и неизменность плана

Текущее действие определяется задачей, её циклом после последнего
законного `restart`,
этапом и номером итерации. Совпадение этапа и итерации с работой до
перезапуска не
возвращает прежнее действие. Сразу после повторного входа, до
подготовки нового действия,
поле `action` текущего контекста равно `null`. Затем оно показывает
план, состояние и
прогресс именно текущего действия. Отдельного публичного поля
идентификатора цикла нет.

После согласованного перезапуска той же Task можно предъявить
собственный точный план
даже при повторении этапа и итерации. Прежние планы, состояния,
события и receipts
сохраняются; подготовка нового действия не переписывает их и не
повторяет завершённый
старый эффект. Перезапуск сохраняет ID Task и рабочие исходники.
Правила согласования,
проверки версии, владения, незавершённых исходов и terminal boundary
остаются у
[публичного restart](task-planning.md#решение-о-restart-и-пересмотре).

Внутри текущего цикла уже начатый план неизменен. Точный повтор
продолжает сохранённое
действие по его фактическому состоянию; другой план отклоняется до
внешнего эффекта.
Смена сессии, освобождение и повторное приобретение Task, а также
обычное изменение
её версии не создают новый цикл. Сохранённое действие с актуальной
привязкой можно
продолжать после такого возобновления; объект действия из прежнего
цикла нельзя
сохранить поверх текущего. Это правило действует и для локального
намерения публикации,
и для публикации подготовленных дочерних Task/Sprint.

Порядок восстановления зависит от причины:

1. При прерванном текущем действии возобновите сохранённую работу.
   Используются прежние
   receipts и предусмотренный probe; неизвестный внешний эффект не
   повторяется вслепую.
2. Для известного `failed`/`blocked` используйте допустимый явный
   action rework из
   [состояний операции](#5-состояния-операции-и-возвраты). Он создаёт
   новую итерацию,
   а не меняет начатый план той же итерации.
3. Если ошибочен договор Task или нужен согласованный возврат к
   постановке, выполните
   публичный Task `restart`, затем допустимые `edit`/`ready` и обычный
   `bootstrap`.
   Новый план обязан соответствовать фактическим исходникам: для
   `git_merge` требуется
   чистое рабочее дерево и `base_commit`, равный его текущему HEAD.
   Сохранённый после
   перезапуска HEAD не обязан совпадать с базой прежнего плана.

Повреждённый либо противоречивый сохранённый аудит перезапуска
отклоняется с категорией
`Invalid Task lifecycle audit: ` и пояснением причины. Это не
разрешение считать
действие начальным, подменять план или править SQLite. Сохраните
полный отказ и
материалы для восстановления через владельца данных. Корректный
начальный цикл
отличается от перезапуска с границей `from_version=0`; пропуски между
законными
возрастающими границами допустимы. Удалённые без остатка следы
перезапуска инструмент
не восстанавливает предположениями.

Локальная [передача работы](local-handoff.md#передача-после-перезапуска)
сохраняет эту
привязку.
Для [переноса между хранилищами](transfer.md#возобновление-и-актуальность)
действуют дополнительные проверки всего сохранённого набора действий.
Успешное
действие и успешный перенос не заменяют проверки, независимый осмотр
или приёмку Task.

## 6. Границы DDD-06
Поддерживается последовательное merge точных существующих коммитов **одной configured codebase**. Rebase/cherry-pick, автоматическое объединение любых predecessor refs, создание произвольных targets и полный multi-codebase resolver не реализованы. Результаты DDD-05 с несколькими result-ветками по-прежнему требуют явной integration-задачи.

Commands-план — исполнитель явно разрешённой процедуры, не универсальный установщик пакетов и не автоматическая rollback-система. Тест среды использует контролируемый файл-состояние, не реальную установку в WSL. Нет имитации sudo/секретов/удалённых сервисов. При необходимости нового решения исполнитель сохраняет факты и останавливается.

Полноценные parser adapters, durable process supervisor, hooks, IDE MCP, Gmail и message capture остаются DDD-07. Наличие семи семейств handler не означает готовность всех 13 нормативных конфигураций (DDD-09).
