# Гибкое планирование Task

## Исполнимый контракт

AI poise — декларативный harness: типовые механические действия выполняет инструмент,
а смысл работы определяет агент. Выбор `goal_type` материализует зарегистрированный
Task template в newborn. Шаблон сохраняется только как происхождение исходного черновика:
его ID, версия и digest. После materialization задача не перечитывает template при
редактировании того же типа, `ready`, запуске или возобновлении.

Планировщик меняет собственный draft через `task/edit`: goal, requirements, DoD,
methods и method_inputs, checks, artifact_requirements, content_contract, evidence_plan,
executable_obligations, stage_contracts, decomposition и process. Типовая форма не
ограничивает допустимый смысл работы. Необходимые содержательные параметры, которых
нет во входе, не заменяются выдуманными требованиями: соответствующие поля остаются
незаполненными до решения планировщика. В гибком draft поле можно явно удалить через
`remove`; полнота и согласованность проверяются при `ready`.

Идентификатор и принадлежность к Sprint не меняются через patch/remove. Владение,
валидность графа, транзакции и достоверность проверки результата сохраняются.

## Создание по типу цели

Выбранный project manifest явно подключает `task_planning`:

```json
{
  "catalogue": "/absolute/ai-poise/config/catalogue/settings.json",
  "restart_revision_policy": {
    "reviewer": ["goal", "requirements", "requirements_snapshot", "requirements_agreement", "stage_contracts", "process"],
    "user": ["goal", "goal_type", "requirements", "requirements_snapshot", "requirements_agreement", "definition_of_done", "methods", "method_inputs", "checks", "artifact_requirements", "content_contract", "evidence_plan", "executable_obligations", "stage_contracts", "decomposition", "process", "planning"]
  }
}
```

Это пример явного выбора политики, не встроенное разрешение. Подключение выполняется
через существующий `project-config-update-1`, `manifest_edits` с `path: ["task_planning"]`.
Действует обычное требование покоя проекта для изменения manifest. Тестовая или
восстановленная установка может подключить policy до восстановления рабочей Task DB.
Нельзя переписывать manifest/БД вручную или отключать gate ради подключения.

```json
{
  "operation": "task",
  "input": {
    "action": "create",
    "request_id": "plan-fixture-1",
    "task_id": "0159",
    "sprint_id": null,
    "goal_type": "test_development",
    "patch": {"goal": "Исправить подготовку backup-теста без изменения поведения продукта."}
  },
  "messages": []
}
```

Каталог сам разрешает единственный зарегистрированный starter данного типа и проверяет
его ревизию. Механические параметры ID/Sprint заполняются инструментом. Переопределения
`patch` применяются после исходных значений. Повтор точного запроса возвращает receipt,
даже если исходный template уже недоступен. Конфликтующий повтор не создаёт другую Task.

В ответе — draft, process, revision и `planning`. Последний содержит
`schema: "task-planning-1"`, `template` и `restart_revision_policy`. Планировщик может
изменить предложенную политику до `ready`. Для уже существующего untyped newborn
первый `edit` с `goal_type` также материализует отсутствующие типовые поля; ранее
написанный текст сохраняется. Повтор того же goal type не сбрасывает локальные изменения.

Старые проекты без `task_planning` сохраняют прежнее создание пустого newborn. Полный
task-local process можно передать непосредственно в `patch.process`, с явным `planning`
и `template: null`; глобальный goal type и новый reusable template не нужны.

## Process и границы изменений

`patch.process` — полный валидный `GoalTypeDefinition` той же цели.
`patch.process_changes` — существующие именованные операции редактора process,
например `patch_stage`, `put_stage`, `remove_stage`, `patch_route`.
Операции применяются к сохранённому process этой Task, не публикуют глобальную
конфигурацию и проходят обычный graph validator. Явный полный process выбирается
раньше project route. Для типа, которого нет в проекте, каталог может дать свой
зарегистрированный process; это не устанавливает новый глобальный маршрут.

Фактическая файловая граница этапа задаётся `stage_contracts[].allowed_paths`.
`process.stages[].allowed_paths` — предложение process, а не второй whitelist поверх
решения планировщика. Проверка будущих файлов методов также использует Task scope.
При смене набора этапов планировщик согласует checks, evidence_plan, decomposition
и stage_contracts с новым графом. `ready` выявляет оставшиеся несоответствия.
Начальное наблюдение без заявленного изменения исходников (`change_surface: []`)
привязывается к фактическому `route.entry`, а не к зарезервированному имени `baseline`.
Проверка не разрешает выдать последующий этап реализации за начальное наблюдение.

`ready` замораживает resolved contract; обычный `edit` и прежний отдельный
`revise_stage_contract` не изменяют frozen план гибкой Task. Для ready newborn внутри
ещё не опубликованного Sprint действует такая же фиксация.

Ресурсная граница отдельна от template: когда workspace уже выделен, restart сохраняет
его и WIP. `worktree_required` нельзя переключать редактированием draft так, чтобы
оставить прежний каталог без законного владения. Решение о перемещении/замене уже
выделенного ресурса принадлежит существующему владельцу workspace, а не шаблону.
До выделения workspace этот параметр можно выбирать вместе с локальным process.

## Решение о restart и пересмотре

Исполнитель сохраняет доказательства проблемы и предлагает проверяющему либо
пользователю конкретный restart и изменения, когда успех недостижим или обход
неадекватен задаче. Это предложение само по себе не разрешает изменение требований.

Для frozen `task-planning-1` в обычный `task/restart` передаётся:

```json
{"role": "user", "decision": "Пользователь согласовал пересмотр требований этой задачи."}
```

Это поле `authorization`; остальные обязательные поля restart — прежние task_id,
expected_version, request_id и reason. Для решения проверяющего используется
`role: "reviewer"`. Текст фиксирует действительное решение, а не создаёт полномочия
из произвольного заявления. API не аутентифицирует пользователя внешним удостоверением
и не связывается с другим агентом автоматически.

Harness выбирает разрешённые поля из **прежней frozen policy** и сохраняет полный
before_contract/process, digest, актёра и authorization в restart_history. Изменения
вне сохранённого разрешения отклоняются до записи. Повторный restart в newborn может
выбрать пользовательское разрешение вместо более узкого reviewer-разрешения, но
по-прежнему относительно исходного frozen контракта, а не промежуточного draft.
При повторном `ready` сохраняются changed_fields и digest разрешённой ревизии,
в том числе для готовой newborn Task внутри ещё не опубликованного Sprint.

Известный исполнитель не может объявить себя независимым reviewer; используется
сохранённое происхождение произведённого результата либо начала работы. Для другой
сессии предварительно требуется штатная передача владения. `user` означает явно
полученное пользовательское решение. Общие project/harness rules не меняются этим API.

Обычный незавершённый newborn также можно restart, сохранив ID, draft, историю и
Sprint. Это не фиктивное прохождение бизнес-этапа. Старые Task без `planning` сохраняют
существующий формат restart; восстановление не приписывает им новую policy задним числом.

При разрешённом изменении требований новый snapshot/agreement проверяется через
живой Requirements Registry. Если цепочка не меняется, используется собственный
сохранённый исторический контекст. Старые цепочки не переписываются. Пустые проектируемые
звенья сохраняют сквозную связь, но оставляют видимый gap и не заменяют согласованный
содержательный контракт — см. [Requirements Registry](requirements-registry.md).

## Доказательства и границы поставки

Owner-driven доставка постоянных артефактов при reuse и локальный ремонт через restart
сохранены. Гибкое планирование не объявляет старые неуспешные проверки успешными и не
копирует чужой verdict в локальную приёмку.

Обычный `verify` сначала фиксирует допустимое дерево в **локальном commit-кандидате**,
затем запускает проверки именно на этом hash. Кандидат не является принятым результатом:
неуспешная проверка оставляет Task активной, commit/WIP сохраняются, push/merge не выполняются.
Повтор после потери подтверждения Git commit использует уже созданный совпадающий кандидат,
не добавляя пустой commit. Hook, изменивший дерево, не получает фиктивного доказательства.

Hash включён в canonical execution key, invocation и immutable receipt (`commit`).
Receipt также сохраняет `observed_commit_after` и `source_unchanged`: изменение исходников
командой не выдаётся за доказательство неизменного кандидата. Это контекст commit репозитория;
он не заменяет отдельную source provenance внешних inputs. При другом HEAD, даже с тем же
деревом, выполняется новая проверка. Неизвестный исход ранее начатой команды по-прежнему
требует прежнего восстановления receipt либо авторизованного restart, не слепого повтора.

Новый report явно содержит `verification_commit`, совпадающий с `commit`. `verify` replay,
`accept`, `bootstrap/continue` и `advance` не принимают изменённый hash или локальное дерево.
Сохранённый незавершённый legacy report без этого подтверждения направляет к обычному
restart: старую привязку только к дереву нельзя объявлять exact-commit доказательством.
Исторические terminal receipts и собственные артефакты сохраняются; их чтение не является
повторной проверкой текущего кода. При пересмотре требований на прежнем commit сохраняются
также проверки применимости method, inputs и смысла требования.

Путь planning проверен через реальный WorkTools/Poise и изолированные SQLite/Git,
включая отрицательные сценарии. Самопроверка не является независимым inspection.
Прежние пользовательские `0159–0163` перезапускаются теми же ID только через публичный
API и с законным владением, не удалением записей и не SQL-переводом в ready.

## Отмена неисполнявшегося черновика

Владелец standalone Task в состоянии `newborn`, которая ещё не исполнялась,
может вызвать обычную операцию `cancel` с явной причиной пользователя.
Пустые goal, тип, маршрут и content contract не препятствуют отмене: придумывать
их ради закрытия исторической записи нельзя. Перед отменой используется обычное
владение Task; чужой claim не снимается. Исходный draft и история сохраняются,
переход в `cancelled` и событие `newborn_cancelled` записываются одной транзакцией.
Отменённая запись остаётся доступной для исторического чтения, но не для `ready`,
редактирования или получения в работу.

Этот путь не применим к restarted Task с историей исполнения или submission,
а также к члену Sprint: их отмена остаётся у соответствующего владельца.
Неисполнявшийся черновик не создаёт worktree и потому не требует выдуманной
обязанности физической очистки. Независимое владение worktree той же сессии
не изменяется. Отмена не считается выполнением исходной задачи.
