# Отказоустойчивая доставка телеметрии AI-poise

## Асинхронная доставка без блокирования работы

`OptionalTelemetry` передаёт неизменяемый `TelemetryEnvelope` существующему
`AsyncTelemetryDispatcher`. Сохранение spool, ожидание optional SQLite и обработка
наблюдений выполняются **в worker**, не на пути результата Task. Сбой диска, очереди,
получателя или worker не отменяет корректный результат работы. Основная Task DB
не участвует в доставке и не ослабляет свои проверки ради необязательных наблюдений.

`TelemetrySpool` — адаптер доставки для того же dispatcher, а не второй runner,
Task store, источник сообщений или универсальный механизм тестирования приложений.
Единственный получатель `SqliteAccounting.accept_telemetry` сохраняет envelope и
его допустимые проекции **в одной транзакции optional DB**. Неудачная проекция
откатывает и envelope: retry не должен принять недоставленный результат за duplicate.

Подтверждение допуска в оперативную память **не означает fsync**. Между capture
и сохранением worker существует окно потери при аварийном завершении всех процессов.
После атомарного сохранения запись переживает перезапуск, доставка становится
at-least-once; идентичный envelope принимается получателем идемпотентно. Сбой после
commit получателя, но до удаления файла приводит к безопасному повтору, не новому
учёту. Exactly-once и полнота всех наблюдений не заявляются.

## Независимость и порядок

При свободной настроенной ёмкости записи с разными identity и без зависимости
по порядку данных источника обрабатываются независимо. Ожидание завершения одного
capture, его часов или получателя не задерживает уже допущенную другую запись.
Это действует для обычных обработчиков, capture с внедрёнными часами и существующего
Linux detached-исполнения. Один replay обрабатывает выбранные записи параллельно;
несколько consumers также могут доставлять разные записи.

Параллельная обработка не задаёт FIFO между независимыми envelopes. Для событий
упорядоченного source/stream сохраняется [контракт пакета
наблюдений](accounting.md#пакет-наблюдённой-телеметрии):
сортировка и проверка последовательности принадлежат получателю. Разные identity
сами по себе не устраняют зависимость накопительных данных от предшествующих событий.

Первая подготовка optional DB остаётся фоновой и согласует схему существующей
транзакцией хранилища. После успешной подготовки родителем независимая дочерняя
доставка может завершить собственный доступ к БД. Ошибка подготовки отражается
как ошибка optional доставки; после устранения причины доступен обычный повтор.
Основной результат Task не ждёт этой подготовки.

## Подключение и пределы

Необязательный именованный раздел manifest `telemetry_delivery` подключается через
существующий редактор `poise project`. Его значение — объект
[готового примера](../../config/development/telemetry-delivery.json), а не строка
с путём к этому файлу. Без раздела сохраняется прежняя best-effort доставка без
durable spool. Пользовательский manifest автоматически не переписывается.

`directory` — явный путь optional storage: абсолютный используется буквально,
относительный — внутри уже настроенного mutable state. Это не меняет разрешение
путей инструментов, hooks, исходников или рабочей копии. Все численные пределы
задаются явно: количество/байты записей, размер события, число попыток, размер
пакета replay, интервал повтора и ожидание lock. Для retry-метаданных резервируется
ограниченный запас; очередь может отказать до исчерпания физической ёмкости диска.

Допуск dispatcher ограничен существующим `batch.max_items`. Каждая принятая работа
занимает место до завершения: активные обработчики, незавершённые capture и ещё
не собранные detached receipts учитываются вместе. Ожидание `flush` не освобождает
допуск работающего получателя. При исчерпании ёмкости новая работа может получить
отказ с `dropped`, сохраняя результат основной операции.

Локальная память duplicate ограничена; известная dispatcher активная identity
удерживается до завершения обработки. У detached capture identity может формироваться
в дочернем процессе. Постоянная идемпотентность принадлежит получателю optional DB,
а не локальному кэшу dispatcher. Завершённые receipts собираются без ожидания.

Явные `flush` и `close` могут ждать все уже принятые работы, включая незавершённый
capture. `close` сначала закрывает новый допуск, затем дожидается принятого.
Завершение основной Task не требует этого ожидания. Linux detached-исполнение
сохранено; поддержка другого host здесь не добавляется.

## Повтор и явная диагностика

При новом envelope worker выполняет ограниченный replay. Для восстановления
без новой работы есть отдельная явная операция. В примере `poise_python` — заранее
выбранный абсолютный путь к Python установки; пути инструмента и manifest заменяются
на свои. Абсолютный путь инструмента позволяет запускать его из любой папки.

```bash
"${poise_python:?Укажите Python установки}" /path/to/ai-poise/tools/telemetry_delivery.py \
  --config /absolute/project.json status
"${poise_python:?Укажите Python установки}" /path/to/ai-poise/tools/telemetry_delivery.py \
  --config /absolute/project.json replay
```

`status` не создаёт очередь или базу и не меняет Task. Он сообщает pending,
исчерпанные попытки, повреждённые записи, байты и ограниченные метаданные; содержимое
сырого payload и тексты исключений не публикуются. Ошибки отражаются классом
исключения. Это наблюдение очереди, не доказательство полноты телеметрии.
Готовность получателя проверяют отдельно при разборе причины отказа.

`replay` — сознательный I/O, который может ждать в пределах настроенных locks и
получателя. Фоновый бесконечный polling не создаётся. Для каждой записи выполняется
не более одной due-попытки за replay, всего не более `telemetry_delivery.policy.batch_items`.
Размер этого пакета ограничивает и число параллельно обрабатываемых им записей.
Другая запись может завершиться раньше задержанной, но сам вызов replay дожидается
своего пакета.

Каждая запись имеет исключительного владельца на время попытки и подтверждения.
Занятую запись другой consumer пропускает без новой попытки, продолжая отбор других
доступных записей. Наступление `next_attempt_at` не отнимает владение у работающего
получателя: это срок следующего допуска, а не срок аренды. Попытка и время повтора
сохраняются до вызова получателя, поэтому авария worker тоже расходует ограниченный
бюджет. `next_attempt_at` — техническое время повтора, **не время события источника**.

Служебные `queue.lock` и пустые файлы `<hash>.event.json.lock` принадлежат Spool.
Пределы записей и их байтов относятся к событиям с резервом retry-метаданных;
служебные claims не считаются отдельными событиями в `status`. При обычном завершении
владелец освобождает claim и удаляет его файл. После прерванной очистки следующий
`enqueue` или `replay` удаляет только свободные служебные claims без соответствующего
события. Read-only `status` очистку не выполняет.

При fork несвязанная дочерняя работа закрывает только свои унаследованные копии
блокировок очереди и claims. Живой родитель сохраняет исключительное владение;
после утраты владельца несвязанный child не удерживает путь публичного retry.
Если попытка была сохранена, повтор учитывает её бюджет и срок. При прерывании
допуска до сохранения попытки запись сохраняет прежний счётчик. Восстановление
доставки выполняется через тот же replay и идемпотентного получателя.

Обычный порядок диагностики и восстановления:

1. Выполнить `status`, проверить сохранённые попытки, повреждённые записи
   и доступность файлов optional storage.
2. Проверить доступность получателя и устранить установленную причину отказа.
   После наступления срока повтора выполнить `replay`; занятый живым обработчиком
   claim сохраняет своё владение.
3. Повторить `status` и проверить фактическое состояние очереди. Успех основной Task
   или допуск наблюдения в память не заменяют подтверждения доставки.

После `max_attempts` запись остаётся для диагностики, но автоматически не повторяется.
Устранить причину и увеличить явный бюджет доставки можно через редактор конфигурации;
это не сбрасывает уже записанное число попыток. Повреждённые файлы, symlink, неожиданные
файлы и переполнение не очищаются автоматически и не выдаются за успешную доставку.
При заполнении spool новые наблюдения могут быть потеряны; основные операции продолжают
работать, coverage остаётся partial. Отдельный монитор/daemon и живая внешняя API
доставка не заявляются; воспроизводимые сбои проверяются локальными получателями.

## Принятый риск до сохранения события

**Решение пользователя от 2026-09-16:** окно потери между рабочей операцией и
асинхронным сохранением — осознанно принятый риск текущего решения. Его устранение
не блокирует продолжение работы или приёмку миграции само по себе и не входит
в текущие исправления. Нельзя превращать это решение в обещание отсутствия потерь
или скрывать фактически наблюдаемые ошибки доставки.

После получения актуальной пользовательской Task DB при планировании следует
завести отдельную **отложенную** задачу на рассмотрение этого риска; создание
записи не разрешает сразу исполнять её. Реальный Task ID пока не выделен.
Сначала согласовать требуемую гарантию доставки и допустимую цену на рабочем пути,
не нарушая изоляции опциональной телеметрии и не вводя скрытое ожидание fsync.
До отдельного решения сохраняются нынешние гарантии и диагностика partial coverage.
