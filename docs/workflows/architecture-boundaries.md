# Архитектурные проверки самой AI-poise

Обновлено: **2026-09-16**. Capability C029.4; это проверка Python-кода AI-poise,
не анализатор произвольных приложений, разрабатываемых с её помощью.

## Проверка архитектуры перед авторской сдачей

Существующий `DevelopmentRouting` использует явную регистрацию `authoring_boundary_gate`
в operational `config/development/routing.json`. Поставленная регистрация включает
обработчик `produce` и `config/testing/architecture-boundaries.json`. В policy находится
набор именованных правил для объявленных `src/poise/**` поверхностей: запрет I/O и
обратных зависимостей в чистых слоях, прямых записей runtime в Task lifecycle и SQL-таблицы
Task. Обычное разрешение путей работающего Poise не меняется.

Поле регистрации содержит `policy` (конкретный путь) и `handlers` (явные имена из
`handler_facts`). Относительный путь policy вычисляется от уже выбранного operational
routing-файла. Она не ищется в проверяемой рабочей копии. Сама копия передаётся конкретным
filesystem path; возможна выделенная рабочая папка или обычный настроенный checkout.
Подключение `development_routing` остаётся [явным](../configuration/development-routing.md#подключение-к-bootstrap-и-обновлению-контекста).
Личный project manifest автоматически не изменяется.

При `verify` проверка применяется к накопленному diff Task относительно её `base` и
неигнорируемым untracked-файлам. Переименования развёрнуты в удалённый и новый путь.
Удаление подтверждается Git, а не угадывается из неудачного чтения. `AiPoiseArchitectureChecks`
читает только попавшие под policy Python-файлы; `ArchitecturePolicy` анализирует текст через
AST, **не импортирует и не исполняет его**. Результат содержит относительный `file`,
`line`, `rule`, `kind`, `symbol`, SHA-256 проверенных файлов и загруженной policy.

Известное нарушение возвращает `architecture_boundaries_failed` с `architecture.status=failed`.
Синтаксическая ошибка, недоступный файл либо обнаруженное изменение прочитанных байтов
даёт `inconclusive` и также не пропускает сдачу. Отказ происходит **до** `runner.submit`:
не создаёт submission, не меняет claim, Task version, stage, iteration, attempts или history,
не запускает registered checks. Автор исправляет файл и повторяет `verify` в той же Task
и на том же этапе. Сама проверка read-only; нового lifecycle, runner и evidence ledger нет.

Без регистрации результат прямого вызова — `not_configured`, для другого обработчика —
`not_applicable`, в обоих случаях `passed=null`. Это не свидетельство архитектурного PASS.
После успешного gate продолжается обычный путь verify, включая уже назначенные Task методы.
Gate не заменяет эти методы и не делает `inspect` авторской стадией. Bootstrap/refresh
выдают маршрут, не исполняют gate; route digest включает загруженную архитектурную policy.

## Прямой вызов и границы доказательства

Из окружения, где установлен проверяемый инструмент Poise:

```bash
python tools/check_architecture.py --checkout /concrete/ai-poise-copy \
  --policy config/testing/architecture-boundaries.json \
  --path src/poise/modules/tasks/domain.py
```

`--path` повторяется для конкретных файлов, `--deleted` явно объявляет отсутствующую
цель из того же списка. Проверка отвергает path escape, glob вместо файла и checkout
другого приложения. `--all` отдельно выбирает текущие Python-файлы объявленной policy;
это **не** запуск полного тестового набора. CLI возвращает 0 для PASS, 1 для failed или
inconclusive, 2 для неверного запроса/конфигурации. Нет режима автоматического исправления.

Policy проверяет статические imports, их буквальные относительные формы, import aliases,
именованные I/O-вызовы, явные lifecycle assignments/update/pop/setdefault и буквальные SQL
записи. Это не полный data-flow/type analyzer, не гарантия отсутствия динамических обходов
и не доказательство независимости тестового oracle. Динамически построенный SQL и
произвольные runtime aliases не анализируются как вычисления. F-строки/вызовы Python
не выполняются. Допускается чистый код в функциях, который при импорте мог бы завершиться
ошибкой: проверка не импортирует модуль.

Поверхности вне policy перечисляются в `unchecked_paths`; пустой `checked_files` не
означает проверку всего проекта. Удалённые файлы перечислены отдельно. Хэши отражают
наблюдавшиеся байты, повторное чтение ловит наблюдаемую гонку, но не является файловой
транзакцией или блокировкой редактирования. Последующие изменения требуют новой проверки.
При восстановлении результата `verified` действует прежний контракт replay, а не новая
ретроспективная авторская проверка.

Регрессионные проверки принадлежат существующему пакету `verification-runner`:
`tests/verification/test_architecture_gate.py`, интеграции в
`tests/skills/test_development_routing.py` и независимые прежние `tests/ddd/test_architecture.py`.
Запускать выбранные owning tests и bounded smoke, не полный каталог packages.
