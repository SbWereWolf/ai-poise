# Пакетная подготовка проекта и анкета

Обновлено: **2026-09-14T00:00:00+05:00**.

## Назначение

Получить независимый полный конфиг проекта и выбранные process snapshots без ручного
редактирования файлов. Это подготовка окружения, не создание Task/Sprint, не выполнение
бизнес-этапа и не разрешение на изменение целевого приложения.

Источники шаблонов и публикуемые project manifests лежат внутри явно заданного AI poise root.
Настройки самого генератора: `config/project-setup.json`. Корень задан в этих настройках
относительно файла, а не угадан по текущему каталогу. Mutable project state может находиться
вне AI poise root: `paths.state` задаётся явно и может быть абсолютным. Относительное значение
по-прежнему разрешается относительно project manifest. Остальные managed mutable paths
задаются относительно выбранного `paths.state`.

## Доступные задачи во всех проектах

```bash
python -m poise next --settings "$PWD/config/project-setup.json"
python -m poise next --settings "$PWD/config/project-setup.json" --project ERP
```

`next` читает тот же configured-project registry, что и `project list`. Фильтр
`--project` — точный идентификатор, с учётом регистра; префиксы и имена каталогов
не подставляются. Неизвестный идентификатор возвращает явную ошибку. Команда не
читает stdin, не требует текущей Task/native-сессии или `POISE_CONFIG`, не создаёт
launcher, claim, worktree, БД или журнальные записи и не мигрирует старые БД.

Результат содержит `status`, `tasks` и `errors`. Каждый элемент `tasks` содержит
`project`, абсолютный `config_path`, `task`, `sprint` (либо `null`) и `goal`.
Все доступные задачи упорядочены лексикографически по паре `(project, task)`;
это порядок выдачи, а не новая политика приоритета. Пустая очередь — успешный
результат с пустым `tasks`. Ошибки отдельных проектов не скрывают доступные задачи
других проектов: `status=listed_with_errors`, непустой `errors` с идентификатором,
путём и причиной, код завершения CLI `2`. Для неизвестного идентификатора
путь не выдумывается: возвращаются идентификатор, `status=unknown` и причина.
Без ошибок — `listed`, код `0`.
Фильтр ограничивает как задачи, так и диагностику выбранным проектом.

Доступность означает возможность **начать** Task по сохранённому состоянию, а не
возобновить чужую/прерванную работу. Используются владельцы правил Task и Sprint:
статус `available`, отсутствие владельца, корректный начальный маршрут и входной
контент, опубликованный Sprint, его completion/result-зависимости и явные waivers.
Зарегистрированные входные артефакты проверяются по текущим файлам и digest;
утраченные или изменённые файлы не удовлетворяют входным требованиям. Незаконченная
execution-операция исключает задачу; разрешённый restart проверяется тем же правилом,
что и обычный `start`. Newborn, начатые/переданные, заблокированные и терминальные
задачи в эту очередь не входят.

Чтение выполняется отдельной read-only транзакцией каждого проекта. Общего снимка
нескольких БД и резервирования результата нет: после выдачи состояние может
измениться, поэтому обычный `start` заново проверяет условия и атомарно получает
владение. Проверка конфигурации и схемы БД не заменяет проверку доступности runtime,
Git или host в момент запуска. Недоступная, повреждённая или несовместимая БД
попадает в `errors`, а не создаётся или исправляется запросом `next`.

## Интерактивный путь

```bash
export PYTHONPATH="$PWD/src"
python -m poise project-init \
  --settings "$PWD/config/project-setup.json" \
  --template linux-reference \
  --destination config/projects/erp-local \
  --request-id ERP-SETUP-1 \
  --probe-repository yes
```

`linux-reference` — явно выбранный полный шаблон, а не default. Его версия и digest берутся
из выбранной записи registry, проверяются по файлу и фиксируются в receipt. Все прочие
обязательные аргументы явные. Назначение должно быть новым.

Анкета спрашивает идентификатор, существующий Git repository, base ref, неиспользуемое имя remote, имя/email
автора, обязательное `push_required=false`, явный state root (абсолютный либо относительный) и имена наследуемых environment variables. Значение `true` отклоняется до любой Git-команды.
Вопросы, их порядок, типы и подсказки определяются данными шаблона, не условием по имени проекта.

Ответы:

* `set "ERP"` или `set "/home/user/erp"` — задать JSON-строку;
* `set false` — явное отключение push; `set ["PATH","HOME"]` — список;
* `keep` — явно принять показанное значение (из шаблона либо свой прежний ответ);
* `back` — вернуться, сохранив все ранее введённые ответы;
* `abort` или EOF — не публиковать;
* `publish` — доступно на финальном просмотре полного кандидата.

Пустая строка не означает ни согласие, ни default. После возврата изменение ответа попадает
в новый полный кандидат; при публикации повторно проверяются все связанные правила. Число
шагов анкеты ограничено `max_survey_steps`. Обнаруженное значение не подставляется скрыто.
Промпты идут в stderr, один итоговый JSON — в stdout.

## Пакетный путь для агента

```bash
python -m poise project --settings "$PWD/config/project-setup.json"
```

Без позиционного действия команда сохраняет прежний контракт создания и читает один пакет
из stdin. Для чтения настроенных проектов используется действие того же CLI:

```bash
python -m poise project list --settings "$PWD/config/project-setup.json"
```

`list` не читает stdin и не изменяет registry, project manifests, setup lock или каталоги
проектов. Настройки обязаны явно задавать `registry` внутри `root`. Документ registry имеет
схему `configured-project-registry-1`; объект `projects` сопоставляет устойчивый идентификатор
проекта с объектом `{ "config_path": "относительный/путь/project.json" }`. Directory scan,
template registry и скрытый путь по умолчанию не используются.

Результат содержит `status`, `projects` и `errors`. Элементы обоих массивов упорядочены
лексикографически по `project`. Успешный элемент содержит `project` и абсолютный
`config_path`. Отсутствующий manifest попадает только в `errors` со `status=missing`;
невалидный manifest или несовпавший `project` — со `status=invalid`. Каждая ошибка также
содержит абсолютный `config_path` и непустой `reason`; такой проект не выдаётся как пригодный.
При наличии ошибок итоговый status равен `listed_with_errors`, иначе `listed`; пустой registry
возвращает два пустых массива. Невалидная схема или структура самого registry отклоняет всю
операцию через обычный CLI error contract.

Успешная публикация через `project` или `project-init` регистрирует тот же manifest под его
полем `project`, пока удерживается общий setup lock. Существующий идентификатор нельзя
перепривязать к другому пути. Если каталог проекта уже опубликован, а запись registry не
сохранилась, точный повтор исходного `request_id` проверяет receipt и файлы и завершает
регистрацию; новый запрос или ручная перезапись не являются recovery.

На stdin один объект `project-setup-1` с полями:

| Поле | Значение |
|---|---|
| `schema` | `project-setup-1` |
| `request_id` | Идентичность этого намерения создания |
| `destination` | Новый относительный каталог внутри AI poise root |
| `template` | Явные `id`, `version`, `digest` из registry |
| `edits` | Список `{path: [имена полей], value: точное значение}` |
| `probe_repository` | Явное true/false |

`path` адресует поле выбранного project definition, не файл или таблицу. Каждый путь должен
существовать в полном шаблоне. Список/подобъект заменяется целиком. Дубликаты и одновременная
правка родителя и потомка отклоняются; порядок пакета не выбирает победителя. Поля вопросов
обязаны быть явно переданы. Остальные значения берутся из выбранного полного шаблона,
не из встроенных defaults. Изменение `automatic_checks` передаёт точные правила проекта;
редактор не читает команды из prose AGENTS и не изобретает их.

### Политика Task ID

Automatic Task creation доступен только при явном поле `task_ids` полного project config:

```json
{
  "task_ids": {
    "namespace": {"minimum": 1, "maximum": 9999},
    "width": 4,
    "progression": {"first": 1, "step": 1}
  }
}
```

Значения выше — пример политики, не default. `minimum` и `maximum` задают включительный
неотрицательный namespace; `width` обязан представлять `maximum`; `first` входит в namespace;
`step` — положительный. Кандидаты имеют decimal-представление с ведущими нулями до `width`.
Invalid policy отклоняет загрузку конфигурации. Отсутствующая policy сохраняет чтение и
explicit-ID creation существующих проектов, но automatic intent завершается явной ошибкой.

Project templates и уже опубликованные project configs не получают `task_ids` автоматически.
Этот срез не выбирает за пользователя числовой диапазон. Чтобы проект поддерживал automatic
allocation, выбранный полный template должен уже содержать принятую policy. `project-config`
изменяет только существующие manifest fields и не добавляет отсутствующий `task_ids`; ручная
правка managed manifest не является поддержанным обходом.

### Каталог поставленных skills

Метаданные ID/path, назначения и специализации, а также прямой интерфейс чтения описаны
в [контракте каталога skills](skill-catalog.md). Каталог не копирует инструкции и не
меняет выбранную project policy автоматически.

### Маршрутизация декомпозиции Task

task_decomposition хранит project-specific routing навыков и областей ответственности.
В `skills` каждый известный skill получает уникальный `id`, класс `meta`, `general` или
`narrow` и `responsibility`; у `meta` и `general` она равна `null`, у `narrow` — непустая.
В `areas` каждый project-specific glob связывается с одной responsibility. Дубликаты и
неверная форма отклоняют загрузку полного project config.

Для установленного общего каталога доступна альтернативная явная форма:
`catalog` (полный snapshot metadata), `skill_ids` (выбор проекта), `areas`.
Её строит read-only операция `poise skills` / `policy`, описанная в
[контракте каталога](skill-catalog.md#политика-проекта-и-проверка-пакета-без-harness).
Она принимается тем же `load_config`; классы и responsibilities берутся из общего
владельца metadata, а не переопределяются рядом. Смешивать `skills` с `catalog`
нельзя. Экспорт политики не является её публикацией и не изменяет конфигурацию проекта.

При создании и переводе Task в ready неизвестный skill или неразмеченная area отклоняют план.
Та же политика применяется к материализации и публикации Sprint, поэтому сохранённое деление
фаз не может обойти проверку фокуса. Area, связанная в политике с narrow responsibility,
проверяется в каждой фазе и должна соответствовать responsibility объявленного в этой фазе narrow skill;
area с responsibility, которой не владеет ни один narrow skill политики, не становится narrow
только из-за соседства с таким skill. Конфигурация является маршрутом проверки декларации, а
не доказательством её фактической полноты.

Переносимые примеры AI poise показывают только форму контракта. ERP inventory и его классификация принадлежат конфигурации ERP, а не AI poise; пример
`config/examples/erp-task-decomposition.example.json` фиксирует явный кандидат миграции,
который должен быть принят владельцем ERP перед публикацией в целевой проект.
Этот исторический пример и `erp-migrated-skills.json` не являются инвентарём
поставленных skills; актуальная поставка перечислена в `.agents/skill-catalog.json`.

Перед публикацией инструмент проверяет весь кандидат штатным `load_config`, в том числе
каждый process через общий GoalTypeDefinition. При `push_required=true` кандидат отклоняется до Git.
При `push_required=false` выполняются только локальные Git-проверки: repository root,
разрешимость base ref и имя ветки. Ни remote probe, fetch/push, установка пакетов, ни изменение
trust не выполняются; readiness remote равен `not_required`.

## Обновление действующего проекта

### Рабочие деревья внутри репозитория

`paths.worktrees` принимает явный абсолютный путь к дочернему каталогу
`git.repository`. Корень репозитория, его `.git`, выход наружу и symlink в пути
отклоняются. Уже заданные относительные пути по-прежнему относятся к `paths.state`.
Каталог рабочих деревьев внутри репозитория должен исключаться из Git.

Исправление пути у восстановленного проекта выполняет тот же `project-config`
пакетом `project-worktree-root-1`: поля как у `project-config-update-1`, плюс
непустые `reason` и `authorization`. Допускается ровно одна `manifest_edits`
для `["paths", "worktrees"]`; `process_updates=[]`, `state_relocation=null`.
`expected_revision` — точный digest текущего manifest и process snapshots.
Этот узкий операторский путь также фиксирует текущую revision после восстановления,
когда исходная setup-квитанция относится к прежнему расположению установки.
Остальные параметры и process snapshots не изменяются.

Под общим state lock проверяется отсутствие активного исполнения, выделенных
Task worktrees/веток и незавершённых внешних действий. Не начатые задачи и
задача, возвращённая в newborn без выделенного дерева, не требуют отмены или
пересоздания. Существующие рабочие деревья этот API не перемещает.
Сохраняются проверка точной revision, квитанция намерения и восстановление
прерванной публикации; точный повтор не меняет историю задач.

Один публичный пакет обновляет существующий project manifest и его process snapshots без
удаления и повторного создания проекта:

```bash
python -m poise project-config --settings "$PWD/config/project-setup.json"
```

На stdin передаётся ровно один bounded JSON-объект `project-config-update-1`:

```json
{
  "schema": "project-config-update-1",
  "request_id": "ERP-CONFIG-2",
  "config_path": "/absolute/poise/root/config/projects/erp-local/project.json",
  "expected_revision": "known-project-revision",
  "manifest_edits": [
    {"path": ["git", "push_required"], "value": false}
  ],
  "process_updates": [
    {"goal_type": "development", "expected_revision": "known-process-revision", "changes": []}
  ],
  "state_relocation": null,
  "probe_repository": false,
  "receipt_path": "operations/ERP-CONFIG-2.json"
}
```

`config_path` выбирает существующий managed manifest внутри root из settings.
`expected_revision` — digest полного действующего project manifest вместе со всеми process
snapshots; операция принимает только revision, ранее зафиксированную setup/update receipt.
Каждый process update дополнительно содержит digest выбранного process и декларативные
`changes` контракта `GoalTypeDefinition`. Изменения одного process публикуются полным
валидированным snapshot, а не правкой JSON-файла на месте.

`manifest_edits` адресует существующие поля по логическому пути. Корни `project`, `schema`,
`processes` и `paths` имеют отдельных владельцев и через generic edit не меняются. Весь
manifest и все process snapshots проверяются общим `load_config` до публикации. Локальный
Git probe выполняется только при `probe_repository=true`; сеть, fetch и push не входят в эту
операцию.

### Revision, receipt и восстановление

`request_id`, содержимое запроса и `receipt_path` образуют неизменное намерение. Receipt
располагается относительно root из setup settings и содержит прежнюю/новую project revision,
readiness и итог операции. Точный повтор возвращает тот же результат с `replayed=true` и не
создаёт вторую revision. Другой пакет с тем же receipt, неизвестная или устаревшая live
revision и посторонняя правка managed файлов завершаются конфликтом без принятия этих данных.

Перед внешними публикациями сохраняется pending receipt с digest каждого компонента до и
после. После прерывания следует повторить тот же пакет: восстановление принимает только
точную комбинацию известных before/after-компонентов, допубликовывает недостающую часть и
создаёт один durable receipt. Неизвестный исход нельзя исправлять новым request ID, ручным
overwrite или удалением проекта.

### Активные задачи и перенос state

Process update не переписывает process snapshot уже созданной Task: она продолжает работать
по сохранённому определению, а новая revision применяется к будущим задачам. Manifest edit и
перенос `paths.state` разрешены только у quiescent проекта без Task в незавершённом состоянии.
Для этой проверки terminal считаются только `completed` и `cancelled`;
сохранённая история заменённой Task не блокирует операцию, а любой другой status блокирует.
Проверка quiescence и публикация защищены тем же state lock, который сериализует создание и
claim Task.

`state_relocation` содержит только `expected_source`, `destination` и `source_disposition`.
Допустимы `retain` и `delete_after_publish`; source должен совпадать с действующим state root,
существовать и не пересекаться с destination как равный, родительский или дочерний путь.
Непустой либо неизвестный destination не перезаписывается. Сначала всё дерево копируется во
временный соседний каталог, публикуется rename и сверяется с source, затем под одновременно
удерживаемыми source/destination locks переключается manifest. Source удаляется только после
успешного переключения при `delete_after_publish`; при `retain` он сохраняется. Повтор после
прерывания распознаёт уже опубликованную точную копию, но не создаёт пустое replacement state
из отсутствующего source.

Временный каталог имеет детерминированное имя `.<destination-name>.project-update`. Если он
уже существует при первом запросе, операция завершается до создания pending receipt и ничего
в нём не удаляет. Очистить частично заполненный staging разрешено только точному повтору
запроса, для которого уже существует matching pending receipt с известными before/after
digests. Новый request ID, изменённый пакет или ручное удаление staging не являются способом
восстановления.

Успешный результат имеет `status=updated`, `changed`, `prior_revision`, `revision`,
`config_path`, `readiness`, `receipt_path` и `replayed`; при переносе добавляется
`state_relocation` с source, destination и фактическим disposition.

## Публикация и повтор

Под общим bounded Linux lock создаётся отдельный кандидат с manifest, process snapshots и
receipt. Он не является действующим проектом. Только после валидации всех файлов и локальных
проверок кандидат публикуется атомарным rename каталога на той же файловой системе. Task DB,
сессия, worktree и код приложения до bootstrap не создаются и не меняются.

Существующий destination не перезаписывается. Повтор того же запроса проверяет receipt и
контрольные суммы опубликованных файлов и возвращает прежний результат. Позднее изменение
файла, другая операция или изменённое намерение приводит к VersionConflict. Источники могут
обновиться после публикации: повтор проверяет сохранённый независимый результат, не подменяет
его актуальным шаблоном. Перед публикацией источники должны совпадать с выбранными digest.

Ошибка до rename не оставляет опубликованной половины проекта. Если ошибка возникла после
rename, повтор того же запроса позволяет проверить сохранённый receipt; запрещён слепой
reset/overwrite. Mutable state и project manifest не могут занимать один файловый путь или вложенные взаимно области.
Пути файлов конфигурации остаются confined к AI poise root; абсолютный `paths.state` допускается
как явно выбранный внешний mutable root и затем ограничивает database/runtime/task/sprint/worktree paths.

## Результат

`status`, `project`, `config_path`, `revision`, `process_count`, `readiness`, `replayed`.
Один небольшой результат заменяет последовательность copy/edit/validate/register.
Выходной лимит проверяется до публикации. Все настройки механики явно определены в settings.
Коды успеха/отказа/отмены анкеты также задаются settings; ошибка загрузки settings использует
существующий базовый CLI error contract.

Необходимый для порученной задачи коммит разрешён рабочим процессом; включать только согласованные файлы проекта. Публикация конфигурации и taskless-цикл не создают коммит. Remote `origin` указан как явное неиспользуемое имя: `push_required=false`; remote в репозитории не создаётся.

`automatic_checks` у выбранного шаблона пуст: эта установка не объявляет автоматическое покрытие тестами. Конкретные проверки формальных задач должны быть заданы их действующим контрактом. Исходный bootstrap-комплект спринта и эталонная БД здесь не импортируются.


### Каталог конфигураций и расположение задач

Рабочие данные находятся в `projects/ai-poise/`, конфигурации — отдельно в `config/projects/ai-poise/`. Основной файл `project.json` соседствует с receipt и подкаталогом `config/processes/` из 13 конфигураций. Имя manifest задаётся в настройках генератора и не является требованием JSON-формата; текущий публичный генератор публикует целый новый каталог. Один файл `config/projects/ai-poise.project.json` не заменяет весь комплект.

Изменение размещения выполнено повторной публикацией нового комплекта штатным инструментом после сохранения исходного комплекта. Рабочих задач в первоначальной базе не было; её проверочные журналы сохранены отдельно, не перенесены как задачи. Текущая база создана runtime в новом месте. Lock генератора находится в `projects/.project-setup.lock` и исключён из Git.

Самостоятельная Task хранит файлы в
`projects/ai-poise/standalone/<task-id>/`. Для Task с сохранённым `sprint_id` единый
владелец путей выбирает `projects/ai-poise/sprint/<sprint-id>/task/<task-id>/`; Sprint-level
артефакты остаются в `projects/ai-poise/sprint/<sprint-id>/`. Конфигурация обязана содержать
`paths.standalone_tasks`; прежнее `paths.tasks` отклоняется без alias, fallback или dual read.
Существующие каталоги прежнего формата не переносятся автоматически. Ответственный агент
перемещает только конкретную мешающую запись по отдельному разрешённому lifecycle и сообщает
об этом; само наличие исторического каталога не включает совместимость.

При публикации изменения самого имени корня действующая установка требует отдельного ручного
cutover. Ответственный агент через публичный inventory фиксирует каждую сохраняемую Task и её
`sprint_id`, сопоставляет этот inventory с каждым каталогом прежнего `task/<task-id>/` и заранее
проверяет отсутствие всех целевых путей. После успешной публикации и доказанного отсутствия
процессов Poise, пишущих рабочие данные, он перемещает каждую запись отдельным атомарным rename:
Task с `sprint_id=null` — в `standalone/<task-id>/`, Task с `sprint_id` — в
`sprint/<sprint-id>/task/<task-id>/`. Статус Task не меняет её owner: завершённые и исторические
записи маршрутизируются по сохранённому `sprint_id`, а неизвестный inventory каталог блокирует
cutover до отдельного решения о его владельце. После перемещения агент проверяет отсутствие
старых путей и наличие каждого ожидаемого нового пути. Переименовывать весь смешанный `task/`,
оставлять одновременно два доступных корня, создавать symlink, копировать данные либо добавлять
runtime fallback запрещено. Если отсутствие писателей или полное однозначное соответствие
источников и целей не доказано, публикация остаётся заблокированной.

### Явное подключение development routing AI-poise

`project-config` допускает один именованный новый раздел `development_routing`,
переданный целиком через `manifest_edits`: `path=["development_routing"]`. Это не
расширение generic editor на неизвестные поля. Полная форма, конкретные пути,
bootstrap/refresh и диагностические ограничения описаны в
[подключении router](development-routing.md#подключение-к-bootstrap-и-обновлению-контекста).
Все проверки revision, отсутствие активной работы и транзакционная публикация
сохраняются; никаких managed manifests автоматически не изменяется.

## Доступные шаблоны поставки

В текущую поставку входят `linux-reference` и `wsl-poise`. Выбор выполняется по
точным `id`, `version` и `digest` из `config/project-setup.json`; изменение шаблона
требует новой версии и digest. Отсутствующий исходник не заменяется похожим
шаблоном и не создаётся автоматически. Неизвестный или изменённый выбор отклоняется
до публикации конфигурации проекта.
