# Sprint API — DDD-05

Обновлено: **2026-09-19**. Исполняемый срез; не заявление о выполнении всех нормативных процессов.

## Владелец и основные гарантии
Sprint владеет планом, принадлежностью задач, внутриспринтовым DAG, решениями об отмене/waiver. Task владеет своим
содержимым и жизненным циклом. `SprintCommands` координирует их в одной короткой UoW. Отдельного процесса/scheduler и
отдельной базы для Sprint нет.

Draft ещё не рабочий Sprint. Неполный дочерний контракт сохраняется с точными ошибками и может быть исправлен следующим
пакетом. При публикации каждый контракт проходит **тот же** `validate_creation`, что и отдельная задача: маршрут,
секции/ContentPolicy, EvidencePlan, реестр точных команд и расписание. Пакет переводит готовые реальные newborn Task в
`available` и публикует весь граф одной транзакцией; worktrees, команды и тесты в ней не запускаются.

Прежние слои планирования хранятся в SQLite. Публикация не переписывает уже существующий task ID. Published process
snapshots не заменяются от редактирования файлов процесса. В этом срезе полный опубликованный план не переписывается;
изменять зависимости можно только для ещё не начатых successors.

Изменение валидной project configuration не инвалидирует и не перезапускает уже созданные задачи. Каждая операция
использует текущую конфигурацию проекта вместе с неизменными Task-owned process/contract/method snapshots. Сохранённый
`config_hash` остаётся диагностическим provenance и не является lifecycle gate. Параллельные задачи изолируются
отдельными worktree, Task ownership, optimistic revisions и короткими resource-scoped locks; общий конфиг на iteration
не замораживается.

## Конфигурация
`project.schema = ddd-actions-8`; обязательное поле `sprint` описывает:
- `max_tasks`, `max_dependencies`: явные пределы;
- `acceptable_terminal_states`: явные допустимые для нормального закрытия состояния;
- `templates`: именованные шаблоны с версией, целью, требованиями, DoD, секциями, задачами и зависимостями;
- `section_rules`: обычные SectionRule (`name`, `template`, `normalization`, `required`).

Образец: `config/sprint.example.json`. Это явные значения примера, не defaults кода. Выбор шаблона обязателен при
создании; при изменении передаётся `template: null`, используется сохранённый контракт. Missing values не изобретаются.

## Пакетные изменения
Один вызов `poise work`, JSON в stdin. Общий envelope: `operation`, `input`, `messages`. Для Sprint — `operation:
sprint`. Структурные имена команд являются протоколом инструмента, а не названием goal type.

### Создать/доработать draft
```json
{
  "operation": "sprint",
  "input": {
    "action": "draft", "sprint_id": "S-1", "request_id": "plan-1",
    "expected_revision": null, "template": {"id": "basic", "version": "1"},
    "changes": [
      {"kind": "purpose", "goal": "Код и инструкция", "requirements": ["R1"], "definition_of_done": ["Результаты приняты"]},
      {"kind": "sections", "values": {"plan": "A создаёт результат, B использует его."}},
      {"kind": "upsert_tasks", "tasks": []},
      {"kind": "dependencies", "items": []}
    ]
  },
  "messages": []
}
```
Этот неполный пример **сохраняет draft, но не проходит публикацию**: список tasks нужно заполнить полными контрактами.
Готовые исполняемые контракты автоматически создаёт пример `examples/sprint_demo.py`; пользователь не обслуживает
файлы/БД вручную.

Поддерживаемые виды changes:

| kind | Данные |
|---|---|
| `purpose` | Полные goal, requirements, definition_of_done |
| `sections` | Пакет текстов `values`; можно добавить именованную дополнительную секцию |
| `upsert_tasks` | Пакет полных creation intents: automatic `{request_id, task без id}` либо поддержанный explicit task; объект заменяет прежнюю draft-редакцию того же alias |
| `adopt_tasks` | Пакет `ids` существующих eligible standalone Task |
| `remove_tasks` | Список `ids`; оставшиеся зависимости проверяются по конечному состоянию |
| `dependencies` | Полный желаемый список `items` |

Один kind в пакете не повторяется: вместо множества однотипных записей используется его список/словарь. Повторные Task
IDs и одновременные remove/upsert отклоняются. Порядок разных kinds не влияет на разрешимость конечного графа. Частичная
активная публикация не допускается.

## Реальные newborn Task в Sprint draft

Sprint draft хранит участников как реальные newborn Task с постоянными ID, собственной
историей и revision, а не только как вложенные определения. Новый участник draft создаётся
без claim: планирующая сессия продолжает владеть только своей текущей Task. Поэтому частичный
контракт можно сохранять и редактировать до выбора типа и полной готовности, не теряя
планирование графа и связь со Sprint. Чужой живой claim блокирует изменение; удаление
участника или отмена draft отсоединяет его от Sprint, сохраняя Task identity и историю.

`materialize_tasks` преобразует legacy embedded definitions текущего draft в такие newborn
Task. Automatic intents получают постоянные ID один раз, сохраняют creation request, а alias
dependencies переписываются на эти ID. Повтор с тем же `request_id` не выделяет новые ID.
Неполный или пока невалидный legacy embedded contract остаётся редактируемым newborn draft;
type-specific readiness проверяется позднее через `ready` или публикацию.

После успешной публикации Sprint plan содержит канонические строковые IDs участников,
newborn Task атомарно становятся `available`, а dependency graph и result projection используют
ту же identity. Отдельная прямая полная creation Task остаётся поддержанным путём и не требует
предварительного Sprint draft.

## Преобразование standalone Task и участника Sprint

Самостоятельная Task не может быть predecessor или successor межзадачной зависимости.
Весь связный компонент зависимостей принадлежит одному Sprint, а этот Sprint владеет всеми
рёбрами: endpoint другого Sprint или standalone endpoint отклоняется до изменения состояния.

### Замкнутость зависимостей и локальные дубли

Sprint используется для реально связанной межзадачной работы. Task, у которой нет ни входящего,
ни исходящего межзадачного ребра, остаётся standalone; размер Sprint не является целью сам по
себе и изолированные задачи не добавляются ради количества или общей темы. Каждый Sprint
содержит все Task-prerequisites, необходимые его участникам, поэтому исполняемый dependency
graph не ссылается на результат участника другого Sprint.

Все участники образуют **одну непрерывную связную цепочку зависимостей**: между
любой парой участников есть путь по реальным рёбрам без учёта направления; направления
сохраняют порядок prerequisites, циклы запрещены. Недостаточно того, что у каждой Task
есть ребро: две несвязанные цепочки также не объединяются в один Sprint. Общая тема,
приоритет, дата или желание запустить задачи вместе зависимостью не являются.
Нельзя добавлять фиктивные рёбра, чтобы обойти это правило.

Если одинаковый смысловой prerequisite нужен в нескольких Sprint, в каждом создаётся
локальная conditional-duplicate Task с уникальным ID; при разбиении длинного Sprint
дублируются необходимые Task **или целые цепочки prerequisites**, с сохранением локальных
рёбер. Дубль нужен для локального графа, а не для параллельной повторной реализации.
Между Sprint dependency edge не создаётся.

#### Задача-Спринта-Дубль: автоматическая проверка семейства

**Исполняемый срез от 2026-09-19: создание дубля, библиотечное чтение семейства и допуск этапа реализованы.**
Harness работает с явным родством, а не с поиском похожих названий, целей или требований.
Агент не обходит задачи/спринты и не поддерживает обратные списки вручную.

##### Две независимые оси

Первая ось — обычная Task или **Задача-Дубль**. Вторая, только для Задачи-Дубля, —
**родительская или дочерняя** роль в семействе. Родительская Задача-Дубль не является
обычной Task с исключением: сам признак дубля включает общий контроль семейства.
При создании первого дочернего дубля исходная Task получает родительскую роль дубля.
Рабочий goal type, требования, процесс, ID, история и lifecycle при этом сохраняются;
дубль не получает новый вводный этап, сдвигающий сравнение.

При штатном создании дочернего дубля указывается родитель. Harness разрешает исходного
родителя, в том числе при копировании дочернего дубля, и в одной транзакции сохраняет
родство и требуемые роли. Достаточно канонической связи «дочерний дубль → исходный
родитель»; родительская роль и обратные списки могут выводиться из этой связи, без
второго вручную поддерживаемого источника истины. Родитель получает весь список детей,
ребёнок — родителя и сестёр. Для копии цепочки родство устанавливается для каждой пары.
История и принятый контракт завершённого родителя не переписываются ради этой проекции.
Родство не является межспринтовым dependency edge.

##### Общий библиотечный метод чтения семейства

Получение семейства — **один библиотечный метод**, вызываемый владельцами контекста и
допуска этапа, а не два алгоритма для родителя и ребёнка и не серия команд агента.
Метод `TaskRepository.read_duplicate_family(task_id)` реализован общим SQLite-адаптером;
`TaskCommands.read_duplicate_family(task_id)` предоставляет библиотечное чтение через UoW.
Внутри одного согласованного чтения БД метод:

1. Определяет исходного родителя: для родительской Задачи-Дубля это сама текущая Task,
   для дочерней — её сохранённый исходный родитель. Только этот шаг зависит от роли.
2. По ID родителя получает **всех** его детей одним общим путём.
3. Формирует уникальный набор `{родитель} ∪ {все дети}`, включая текущую Task.
4. **Пакетно** читает из БД текущие этапы всего набора вместе с сохранённым процессом,
   состоянием, итерацией, ID Sprint, владельцем-сессией и версией записи.

Метод возвращает полное согласованное семейство; не выполняет отдельный `show`/запрос
этапа для каждой Task и не копирует семейный обход в `bootstrap`, resume и старт этапа.
Общий расчёт расстояний и допуска использует этот результат. В ответ агенту затем
отбираются только ближайшие родственники по правилу ниже; пакетное чтение всех членов
не означает выдачу всего семейства. Текущая Task участвует в минимуме ровно один раз,
но не показывается самой себе. Метод не захватывает задачи и не запускает работу.

##### Расстояние до положительного завершения

Для Task `t` расстояние `d(t)` — **число переходов кратчайшего направленного пути от её
текущего этапа до положительного терминального состояния** сохранённого процесса.
Эквивалентное вычисление от терминала выполняется по **обратным рёбрам**: обход от
положительного терминала к текущему этапу, не по прямым рёбрам и не по неориентированному
графу. Если положительных терминалов несколько, берётся минимум расстояний до них.
Каждый переход имеет единичную длину; оценка трудоёмкости или длительности не используется.

Успешное терминальное состояние имеет `d=0`. Отмена или неуспешное прекращение не
превращаются в положительный терминал; отменённые родственники исключаются из отбора.
Для остальных используется текущая позиция, а не максимальный когда-либо достигнутый
этап, количество итераций или `stage_index`. После rework расстояние пересчитывается.
Разные этапы, ветви и названия могут иметь одинаковое расстояние — это равное положение
для данного правила. Порядок элементов JSON на результат не влияет.

Пути берутся из действительных разрешённых переходов сохранённого процесса. Для
готовой к исполнению Task отсутствие пути к положительному завершению является ошибкой
определения расстояния, не разрешением старта; два отсутствующих пути не считаются
равенством. Newborn-родственники ещё не имеют исполняемой позиции и не участвуют в
минимуме до `ready`/публикации. Планирование newborn не является стартом рабочего этапа.
Они видны в полном семействе, но не получают выдуманный этап или нулевое расстояние.

##### Только ближайшие родственники и обязательный допуск этапа

Следующее правило относится к обычной повторной реализации. После проверенного получения
коммита и санкционированного `restart` действует [локальная доработка](#локальная-доработка-через-общий-restart):
родство сохраняется, но чужое расстояние не запрещает исправлять собственную ветку.

Пусть `F` — сравниваемое семейство, включая текущую Task, а
`d_min = min(d(t) for t in F)`; отменённые члены исключены, успешные завершённые имеют `d=0`.
Родственники для ответа: **все и только** задачи с `d=d_min`, кроме самой текущей.

| Положение текущей Task | Решение harness | Родственники в ответе |
|---|---|---|
| `d(current) > d_min`, хотя бы на один переход | **Старт работы на этапе запрещён** | Только все задачи с минимальным расстоянием; не все более продвинутые и не равные текущей отстающие |
| `d(current) = d_min`, среди ближайших менее двух Task с сессиями с учётом запрашиваемого владения | Семейный контроль разрешает старт при обычных требованиях этапа и владения | Только остальные задачи на минимальном расстоянии |
| `d(current) = d_min`, среди ближайших две или более Task с сессиями, флаг отсутствует/false | **Старт запрещён до согласования между агентами** | Только остальные ближайшие задачи, с их сессиями |
| То же равенство и несколько сессий, согласование выполнено, явно передан `force_duplicate_start=true` | Разрешён только этот конфликт равенства; остальные проверки сохраняются | Та же ближайшая группа |
| Текущая Task — единственная ближайшая | Семейный контроль разрешает старт при обычных требованиях | Пустой список родственников-конкурентов |

Если кто-то впереди, задачи на одном расстоянии с отставшей текущей Task не добавляются
в ответ. Если несколько родственников находятся на одном ближайшем этапе **или на разных
равно близких этапах**, возвращаются все они. При равенстве расстояния совпадение имени
этапа не требуется. Для каждой возвращённой Task нужны ID Task и Sprint, фактический
этап, расстояние, состояние, итерация и ID владеющей сессии; отсутствующий владелец
указывается явно, не восстанавливается из имени ветки или последнего автора.

##### Равное расстояние, несколько сессий и явный флаг

Равенство минимума необходимо, **но недостаточно** для старта. Если две или более Task
на этом минимальном расстоянии имеют сессии, harness запрещает старт по умолчанию.
Ответ сообщает причину конфликта и ближайшие Task с ID сессий. Агенты согласуют одного
продолжающего исполнителя; он повторяет запрос с явным `force_duplicate_start=true`.
Флаг `force_duplicate_start` поддержан в `bootstrap` и `advance`; по умолчанию он `false`.
Флаг подтверждает решение агента после согласования, а не выполняет переговоры за него.

Число считается по Task с владельцами в ближайшей группе, не по всем сессиям проекта
и не по отстающим родственникам. При взятии ещё не занятой текущей Task учитывается
также сессия, которая получит её при разрешении данного запроса, **без предварительной
записи claim**: иначе второй агент обойдёт отказ, проверив семейство до своего захвата.
При resume уже записанная текущая сессия учитывается один раз. Чужое владение текущей
Task не подменяется запрашивающей сессией и остаётся обычным отказом владения.
В выдаче сохраняются реальные владельцы БД; предполагаемый claim не выдаётся за записанный.

Флаг снимает **только отказ при равном минимальном расстоянии и нескольких сессиях**.
Он не разрешает старт при `d(current)>d_min` даже на один переход, не обходит отсутствие
валидного пути, требования этапа, владение, завершённость или прочие действующие запреты.
Он относится к одному явному запросу старта/возобновления этапа, не сохраняется как
постоянное разрешение и не переносится автоматически на последующие этапы.
Новый запрос, включая запрос с флагом, заново читает семейство через общий метод и
проверяет расстояния и владельцев до записи владения/старта; прежний ответ не даёт допуска.
Не добавляются автоматическая повторная попытка с флагом, выбор победителя по ID,
отмена/освобождение чужой Task или перехват WIP.

Равенство исходных начальных этапов без нескольких сессий само по себе не конфликт.
Но две или более сессии на равном минимальном расстоянии требуют согласования и флага
**также на начальном этапе**. Если другой дубль ближе, начальный этап отставшего не стартует.
Возврат в `route.entry` после rework не считается ещё не начатой работой.

Это **программный запрет старта отставшего этапа**, а не только предупреждение агенту.
Проверка входит в штатные взятие/возобновление Task и допуск каждого этапа, до выдачи
права работы и запуска его действий; read-only показ заблокированной Task остаётся
доступным. Одного сообщения при создании Task или давно сохранённого разрешения недостаточно.
При обновлении контекста сообщается актуальное решение, а перед фактическим стартом
оно проверяется заново через существующий механизм согласованного состояния/владения.
Отказ не запускает команды этапа, не меняет его состояние и не создаёт рабочее дерево
ради заблокированного старта; существующий WIP сохраняется. Фонового опроса, глобального
worktree lock, автоперехвата чужой сессии и новых terminal-статусов это не требует.

Согласование определяет одного продолжающего исполнителя; harness требует явный флаг
вместо безусловного допуска равных задач с сессиями. Это не автоматическая остановка уже
выполняющихся чужих действий. Отсутствие owner не исключает незавершённый дубль из
сравнения и не означает разрешения перехватить WIP.

Пример: у текущей Task расстояние 4; у родственников — 4, 2, 1 и 1. Старт запрещён
даже с флагом, в ответе только последние две задачи. Для Task с расстоянием 1 ответ
содержит только второго родственника с расстоянием 1. Если обе имеют сессии, обычный
старт запрещён; после согласования выбранный агент использует явный флаг.
Этапы равно близких задач могут называться по-разному.

##### Готовый семейный результат и база ветки

Положительно завершённый родственник с `d=0` прекращает допуск повторной реализации у
незавершённого дубля. Завершение и включение кода в основную ветку — разные факты:
до интеграции дубль ожидает её, не пишет результат повторно. `master` обозначает явно
настроенный `base_ref`, а не новую константу. После интеграции проверяются доступность
результата в локальной ветке и требования; новая ветка для reuse создаётся от актуальной
основной ветки, старое дерево разрешённо обновляется без потери WIP. Resume/handoff
не обновляют базу автоматически.

Для проверки и завершения используется отдельная операция `reuse`, не обычный старт
этапа и не `force_duplicate_start`. Она принимает явный ID завершённого родственника;
никакого поиска похожей работы нет. Поддержаны родитель, ребёнок и сестра как потребители
результата другого члена того же семейства.

```json
{"operation":"reuse","input":{"task_id":"D-1","source_task_id":"P-1","request_id":"reuse-D-1","expected_version":7},"messages":[]}
```

Значения иллюстративны. `expected_version` — точная текущая версия целевой Task из
публичной карточки до первого запроса. Источник должен иметь принятый `completed`-результат
с commit. Harness сравнивает полные сохранённые договоры (кроме ID и Sprint), процесс,
Requirements snapshot/agreement, ContentPolicy и актуальный CheckRegistry. Отсутствие
родства, незавершённый источник или несовпадающий контракт отклоняются. Если целевая Task
входит в Sprint, он должен быть опубликован, а её локальные prerequisites удовлетворены.
Семейный результат не обходит эти рёбра.

Проверяется включение source commit в явно настроенный `base_ref` и в текущий локальный
HEAD. Это проверка доступных Git refs, не автоматический fetch, merge, reset или push.
Новый worktree создаётся от наблюдённой вершины `base_ref` после интеграции. Старый должен
содержать результат уже сейчас; отсутствие кода требует разрешённого обновления, не его
повторной реализации. Рабочее дерево должно быть чистым, без незавершённой Git-операции;
чужое Task/worktree-владение, независимый worktree и pending внешнего действия сохраняются.

`reuse` приобретает только локальную область проверки через существующего владельца и
выполняет зарегистрированные методы, имеющие `verification_plan.green_stages`, в своём
checkout. Используются существующие CheckAttempts, runner, execution identity и EvidenceBook,
не второй движок проверок. Локальные receipts не копируются из источника. Пустой набор
таких методов означает отсутствие исполняемых проверок в договоре, а не автоматическое
доказательство всех смысловых требований; принятие результата остаётся явным.

Успех возвращает `status=reuse_verified`, `completion_kind=duplicate_reuse`, source Task/commit,
наблюдённые base ref/commit, локальные HEAD/tree, execution key и локальные checks.
Task получает состояние `verified`, сохраняя текущий этап и итерацию. В workflow хранится
`duplicate_reuse`; обычные submit/verify/advance/rework не разрешают обходить этот режим.
История не получает фиктивных submissions и событий прохождения невыполненных этапов.

После разрешённого принятия вызывается обычный пакет:

```json
{"operation":"accept","input":{},"messages":[]}
```

Перед принятием заново проверяются родство, source result, договор, prerequisites, интеграция,
локальный HEAD/tree и целостность собственных receipts. Только затем Task записывает
`duplicate_reuse_accepted`, становится `completed` и освобождает зависимое владение.
Локальные result-зависимости получают её собственный принятый result commit.
`reuse_verified` ещё не удовлетворяет зависимость. Источник и чужая история не меняются.

Точный повтор `reuse` сохраняет **исходный пакет**, включая первоначальную `expected_version`:
новая версия не подставляется в уже сохранённый intent. Завершённые попытки не запускаются
повторно; неизвестный исход не выдаётся за успех и не повторяется вслепую. Неуспешная
локальная проверка возвращает `checks_failed`; такой результат принять нельзя. Для смены
сохранённого кандидата используется существующий санкционированный `restart`, не флаг
force и не ручное изменение БД. Ответ `checks_failed` содержит `recovery.action=restart`,
ID Task и актуальную `expected_version`. После перезапуска можно исправлять код локально
по [пути восстановления](#локальная-доработка-через-общий-restart), а не повторять failed reuse
неизменённых входов. Родство и WIP сохраняются.

До принятия replay проверяет актуальные локальные inputs/receipts. После принятия точный
replay возвращает **исторический принятый receipt** с `replayed=true`: не выполняет новую
проверку, не приобретает claim и не пересоздаёт удалённый при штатной уборке worktree.
Последующая отмена Sprint также не отменяет уже принятый результат и его receipt.
Другой request/source/version не считается точным replay.

Для передачи незавершённого reuse применим обычный handoff. Возобновляющий агент повторяет
исходный `reuse`-пакет; проверяются сохранённые Git bundle и факты handoff. Приобретение
нового владения и перевод receipt `released → resumed` выполняются в одной UoW. Повреждённый
bundle и конфликтующая версия не разрешают продолжение. Неизвестный исход запущенной
проверки сначала разрешается её существующим владельцем.

**Локальная доставка артефактов реализована 2026-09-19.** Тот же `reuse`-пакет автоматически
получает только зарегистрированные файлы из принятого результата источника, без списка
ручных команд копирования. Для постоянных областей `task` и `sprint` общий файловый
владелец сохраняет относительные пути и байты, но назначает владельца целевой Task/Sprint
и соответствующие ему идентификаторы. Регистрации и файлы источника не перепривязываются.
Временная область чужой сессии `runtime` не является переносимым результатом; такой
источник отклоняется, а не выдаётся за локальную доставку.

До получения владения проверяется весь набор: регистрация у источника, scope/owner,
идентичность относительного пути, SHA-256, отсутствие symlink и конфликтующих локальных
файлов. Обязательные количества проверяются по договору Task, принятому этапу источника
и привязанным к нему artifact-требованиям ContentPolicy. Предыдущие этапы не симулируются:
их временные условия не становятся новым этапом дубля. Правило с `minimum=0` допускает
пустой набор, если остальные ограничения выполнены. Разные байты в существующем пути
не перезаписываются, а одинаковые могут использоваться повторно.

Доставка использует существующий бинарный publisher восстановления артефактов, не новый
движок. Файлы заново проверяются после доставки, до и после локальных методов, при replay
до принятия и при `accept`. Локальные ссылки регистрируются в одной UoW с `reuse_verified`;
наличие частично опубликованных файлов само по себе не означает принятого результата.
После прерывания точный повтор сохраняет уже доставленные идентичные файлы и допубликует
недостающие. Ошибка регистрации откатывает ссылки и переход в `verified`, сохраняя байты
и собственные receipts для штатного повтора. Чужие receipts не копируются.

Ответ содержит локальные `artifacts` и подтверждение доставки в reuse-кандидате. Источник,
локальные пути/владельцы/хэши и принятый artifact-этап сохраняются при передаче и reuse
результата уже завершённого дубля. После принятия точный replay по-прежнему исторический:
не воссоздаёт удалённые при уборке файлы. Для физического восстановления служит отдельный
штатный `recover_artifacts`; replay не является командой восстановления.
Если reuse не прошёл локальную проверку, уже доставленные файлы сохраняются при обычном
`restart` и могут использоваться в локальной доработке. Если файл источника отсутствует,
после подтверждённого получения его коммита тот же `restart → ready → bootstrap` позволяет
создать корректный локальный артефакт и проверить результат, не ремонтируя чужую задачу.
Существующий конфликтующий файл не перезаписывается автоматически: агент сохраняет WIP
и исправляет локальный результат через обычное выполнение, а не бесконечный reuse.
Незавершённый reuse-кандидат старого формата без описания доставки возвращает управляемый
отказ с указанием `restart`, без миграции или переписывания старых receipts. Точный replay
уже принятого результата остаётся историческим и не требует новых полей доставки.

Нельзя заменить доставку чужими receipts, подделанным `d=0` или автоматической приёмкой.
Расхождение требований запрещает выдать чужой результат за локальное завершение, но не
запрещает локальную доработку: после получения исходного коммита используется тот же
`restart`, разрешённое редактирование контракта и собственная проверка.

##### Локальная доработка через общий restart

Обновлено: 2026-09-19. `restart` — универсальное восстановление той же Task, когда её
текущее состояние не допускает продвижения к успешному терминалу. Отдельной ремонтной
Task, второго lifecycle или универсального force для дублей нет. Не всякий failed check
требует restart: если действующий этап допускает обычную доработку/rework, используется он.

Завершённый родственник требует получить его принятый commit, а не повторять уже сделанное.
Если локальная проверка проходит, достаточно `reuse → accept`. Если она не проходит или
проверенный reuse-кандидат устарел после локальных изменений, путь такой:

**полученный commit → restart → при необходимости edit → ready → bootstrap → локальная
доработка → verify → accept/advance по сохранённому процессу → completed.**

`TaskCommands.restart_newborn` через общий библиотечный метод получает семейство и проверяет
принятый source receipt. Read-only Git-preflight подтверждает включение точного source commit
в HEAD сохранённой Task-ветки; staged, tracked и untracked WIP допускаются и не изменяются.
В `restart_history` записывается факт `local_repair`: source Task/commit, наблюдённые HEAD/tree,
base и идентичность рабочего дерева. Публичного поля для самостоятельной установки этого
факта нет; принадлежность к семейству не удаляется.

Полученный source commit для локальной доработки не обязан предварительно попасть в master:
достаточно его включения в свою уже существующую ветку. Восстановление не выполняет fetch,
merge, cherry-pick, reset или push за агента. Если Task-worktree ещё нет, проверяется основной
checkout, а при последующем старте — точная зарезервированная база нового дерева. Если код
пока не получен, restart не создаёт фиктивного подтверждения импорта и обычный семейный
запрет остаётся: сначала получить результат. Незавершённую Git-операцию надо закончить либо
явно отменить штатным Git с сохранением WIP.

После подтверждённого restart локальная Task получает `duplicate_gate.reason=local_repair`.
Её допуск больше не блокируют расстояние завершённого источника или состояние иных веток:
теперь проверяется и исправляется собственный результат на уже полученной базе. При этом
сохраняются владение, валидность собственного процесса, allowed paths, локальные prerequisites,
требования и собственные checks. Ближайшие родственники остаются в контексте, но не заменяют
локальную приёмку. Флаг `force_duplicate_start` остаётся только подтверждением согласования
равных сессий и не является способом перейти в локальную доработку.

После неуспешной собственной проверки можно исправить код и пройти штатный rework/verify;
при новом тупике повторить общий restart. Сам по себе прежний неуспех не исчерпывает возможность
закончить Task. Проверяющий вправе явно пересмотреть дефектный метод проверки или контракт
через существующие разрешённые операции (`repair_stage_contract` либо `restart → edit → ready`).
Автоматического смягчения проверок, присвоения успеха старым failed receipts или изменения
родительского результата нет. Исполнитель не выдаёт своё желание зелёного теста за решение
проверяющего. Требуются новые локальные доказательства для принятого контракта.

Отдельный случай — запущенный check без устойчивого receipt. Сначала остановить/проверить
фактическое действие. Разрешённый restart архивирует точный `check_attempt` в
`restart_history.abandoned_check_attempt` и очищает текущий pending в той же UoW, что и
перезапуск Task. Он **не** объявляет неизвестный исход успешным, не восстанавливает выдуманный
receipt и не повторяет команду. Следующая проверка получает новую identity. Известный runner
с активным run не разрешает архивирование; отсутствие run в текущем runner не доказывает
отсутствие внешних эффектов — их разбор покрывает явная authorization. Другие pending-протоколы
используют свои существующие recovery-операции. Ошибка любого шага откатывает весь restart.

| Неуспешное условие | Штатное продолжение |
|---|---|
| Источник завершён, его commit ещё не получен | Ответ содержит `result_commit` и `recovery.action=import_then_verify`; получить commit в свою ветку, затем проверить |
| Локальный reuse вернул `checks_failed` | Явный `restart`, сохранить/уточнить контракт, `ready`, исправить код в той же ветке и проверить заново |
| После `reuse_verified` код или receipts изменились | `accept` не проходит; `restart` сохраняет WIP и открывает новую локальную проверку |
| Собственная проверка после restart неуспешна | Обычная доработка/rework; если продолжение невозможно — тот же restart |
| Проверяющий пересмотрел ошибочную проверку | Разрешённая правка контракта; новая собственная проверка и явное принятие, не копирование чужих результатов |
| Исход check неизвестен | Разобрать/остановить действие; явно разрешённый restart архивирует старую попытку, не повторяя её |
| Версия устарела или Task/worktree занят другой сессией | Получить актуальную версию либо штатный handoff; restart не захватывает чужую работу |

Task ID, Sprint membership и рёбра сохраняются. Только собственное успешное завершение
локальной Task удовлетворяет зависимые рёбра; ожидание, failed check, restart и ready сами
по себе их не удовлетворяют. Проверенный сквозной сценарий включает result-зависимую NEXT:
после локального исправления, проверки, принятия и явной интеграции её prerequisites становятся
доступны, NEXT проходит обычный процесс и весь Sprint завершается. Тесты —
`tests/runtime_services/test_restart_local_repair.py`; это не гарантия автоматического решения
любой инфраструктурной аварии, но подтверждённый путь восстановления перечисленных состояний.

##### Исполняемый API и границы

Создание выполняется через обычный `work`, без нового goal type или отдельной базы:

```json
{"operation":"task","input":{"action":"duplicate","request_id":"copy-D-1","task_id":"D-1","parent_id":"P-1","sprint_id":"S-2"},"messages":[]}
```

Здесь `P-1` — существующая Task с сохранённым полным контрактом; `S-2` — существующий
**draft Sprint**, `D-1` — новый ID. При указании дочернего дубля harness разрешает общего
исходного родителя и копирует его контракт, а не историю промежуточной копии. Дубль
создаётся как незахваченный newborn, добавляется в draft и получает родительскую связь
в одной UoW. Повтор того же запроса не создаёт второй Task. Ошибка откатывает все изменения.
Требования, процесс и requirements snapshot/agreement сохраняются; submission, evidence,
worktree, результаты проверок и чужое владение не копируются. Далее используются обычные
`bootstrap` newborn, `ready`, локальные dependencies и публикация draft Sprint.

Обычные карточки возвращают `duplicate`: `kind`, `role`, `parent_id`, а также `children`
у родителя или `siblings` у ребёнка. Для обычной Task это поле отсутствует. Родство
сохраняется через edit, ready, публикацию и restart; родительский контракт и его история
не переписываются. Каноническая ссылка `duplicate_parent_id` хранится в существующей
Task metadata; отдельная миграция SQLite или ручное обновление существующих задач не нужны.

Чтение семейства выполняет три SELECT независимо от числа детей: определение родителя,
список детей, пакет состояний через `json_each`. Оно не меняет Task и не захватывает её.
Перед стартом проверка выполняется в существующей транзакции владения; разрешённый
первый старт дубля сохраняет claim до подготовки worktree. Второй старт видит этот claim,
а не временно свободное семейство. Новая глобальная блокировка кэша/worktree не добавляется.

Запрос выбранного после согласования исполнителя:

```json
{"operation":"bootstrap","input":{"task":{"id":"D-1"},"decision":null,"feedback":null,"rework_stage":null,"force_duplicate_start":true},"messages":[]}
```

Для перехода уже выбранной Task используется обычный `advance` с опциональным тем же
булевым флагом. Не передавать его автоматически. Пример формы запроса:

```json
{"operation":"advance","input":{"request_id":"advance-D-1","task_id":"D-1","target_stage":"implementation","force_duplicate_start":true},"messages":[]}
```

ID и `target_stage` в примерах иллюстративны: используются реальные значения выбранного
процесса. Отказ возвращается как `status=duplicate_start_blocked`, `result_template=null`
и `duplicate_gate` с `parent_id`, `role`, `distance`, `minimum`, `allowed=false`, `reason`
и ближайшими `relatives`. Причины различают `family_ahead`, `duplicate_sessions`,
`foreign_owner`, `invalid_duplicate_distance` и `task_not_executable`. Это незавершённая
работа, не успех и не сбой внешней команды. Read-only карточка/контекст остаются доступны.
Флаг не обходит причины, кроме `duplicate_sessions`.

Проверены публичное создание → ready → публикация → старт, отказ второго владельца,
явный flag/retry, обновление допуска перед записью старта, переход этапа и handoff/resume.
Verification-only завершение по готовому родственнику реализовано через `reuse` и явный
`accept`, включая локальную доставку постоянных Task/Sprint-артефактов. Failed reuse восстанавливается
через общий `restart` и локальную доработку в той же ветке; после подтверждённого импорта
семейный минимум не блокирует эту работу. Без такого restart `family_ahead` сохраняется;
его нельзя обходить флагом или подделкой результата.
Наличие этих библиотечных проверок не означает установленную на внешнем хосте версию.

Это действующее правило планирования, а не обещание нового runtime-валидатора.
`SprintPlan.graph_errors` проверяет endpoints, дубли рёбер, циклы и лимиты, но отдельно
связность всех участников не проверяет. Планировщик обязан соблюдать правило и когда
текущий API принимает более широкий граф. Наличие внутриспринтового DAG не следует
описывать как автоматическую проверку всех этих условий.

Draft-change `adopt_tasks` принимает пакет `ids` уже существующих standalone Task. Каждый
кандидат обязан иметь `status=available, claimed_by=null, worktree=null, pending=null, last_report=null и attempts=0`;
любая начатая execution, worktree, внешний pending, результат, claim или другая Sprint
membership отклоняет весь пакет. identity, immutable history, goal, contract и readiness
сохраняются. В одном draft-пакете можно совместить `adopt_tasks` и полный `dependencies`:
membership, граф, revision и request receipt записываются атомарно либо не меняются вовсе.

```json
{
  "operation": "sprint",
  "input": {
    "action": "draft",
    "sprint_id": "MIGRATION",
    "request_id": "adopt-0097-0098",
    "expected_revision": 1,
    "template": null,
    "changes": [
      {"kind": "adopt_tasks", "ids": ["0097", "0098"]},
      {"kind": "dependencies", "items": [
        {"predecessor": "0097", "successor": "0098", "kind": "result"}
      ]}
    ]
  },
  "messages": []
}
```

Это поддержанный путь миграции Tasks 0097 и 0098 в один Sprint с result-зависимостью
`0097 -> 0098`; после успешного adoption Sprint публикуют обычным `publish` с полученной
revision.

Action `extract_tasks` действует только для published Sprint и принимает непустой уникальный
список `task_ids` и `expected_revision`. Извлекаемая available Task должна удовлетворять той
же eligibility и иметь ноль входящих и исходящих зависимостей; Sprint должен сохранить хотя
бы одного участника. Успех удаляет Task из плана и membership, задаёт `sprint_id=null` и
возвращает её в standalone overview без старта или пересоздания. `remove_tasks` сохраняет
прежний путь удаления draft-newborn и также служит допубликационной коррекцией adoption.
Отмена draft атомарно отсоединяет как newborn, так и adopted участников.

```json
{"operation":"sprint","input":{"action":"extract_tasks","sprint_id":"MIGRATION","request_id":"extract-0098","expected_revision":3,"task_ids":["0098"]},"messages":[]}
```

Любой отказ сохраняет Task states, Sprint plan, membership, граф, revision и request receipt
без изменений; повтор после отказа не считается replay и снова исполняет актуальную
валидацию. Только успешный точный запрос получает неизменяемый replay receipt.

Редактирование: `sprint_id: null` означает выбранный Sprint; `expected_revision` — полученная revision, новый
`request_id`, `template: null`. Полный список ошибок публикационной готовности возвращается вместе с draft. Ошибка draft
ещё не превращается в исполняемые задачи.

### Опубликовать
```json
{"operation":"sprint","input":{"action":"publish","sprint_id":null,"request_id":"publish-1","expected_revision":2},"messages":[]}
```
Одна ошибка дочерней задачи, графа, обязательной секции или конфликт ID отменяет всю публикацию. Действие вызывается
после разрешения пользователя; сам инструмент не проводит смысловую приёмку вместо пользователя.

Для automatic-участника зависимости draft используют его `request_id` как временный alias.
При публикации Task repository атомарно выделяет ID, Sprint plan и все dependency endpoints
переписываются на фактические ID, а ответ содержит массив `allocations`. Полный пакет заранее
резервирует explicit Task IDs и ID создаваемого Sprint, поэтому automatic-кандидат не занимает
их и результат не зависит от порядка automatic/explicit элементов. Ошибка любого участника
откатывает Task-агрегаты, membership, зависимости, Sprint layer и allocation receipt вместе.

```json
{
  "request_id": "member-import-1",
  "task": {
    "sprint_id": "S-1",
    "goal_type": "development",
    "goal": "Добавить импорт.",
    "requirements": ["R1"],
    "definition_of_done": ["D1"],
    "methods": [],
    "checks": {},
    "artifact_requirements": [],
    "content_contract": {"sections": [], "routes": [], "requirements": []},
    "evidence_plan": {}
  }
}
```

Пустые process-зависимые коллекции здесь показывают только форму automatic intent и должны
быть заменены полным контрактом выбранного `goal_type`. После публикации дальнейшие Sprint
операции и `bootstrap` адресуются выданным Task ID, не alias.

`request_id` имеет область Sprint. Тот же ID можно использовать у другого Sprint, но внутри одного ID связан с одним
точным пакетом. Повтор оригинального пакета не повторяет публикацию/слой. Результат содержит свежую проекцию; operation
receipt хранит сам факт применения. Устаревшая revision не перезаписывает новую.

## Выбор работы и один пакет контекста
```json
{"operation":"bootstrap","input":{"task":{"id":"S-1"},"decision":null,"feedback":null,"rework_stage":null},"messages":[]}
```
Поле выбора уже существующего scope принимает **ID**, а не повтор всего task JSON. Registry определяет, задача это или
спринт; имена/префиксы не угадываются. Sprint bootstrap возвращает цель, текущую revision, все eligible IDs, компактные
сведения о задачах, blockers, текущую formal task и `result_provenance`. Для каждого действующего result-ребра эта
проекция содержит ID предшественника и его `result_commit`, включая явный `null` до появления результата. Bootstrap
обзора не выбирает задачу вместо агента, не создаёт worktree и не берёт эксклюзивный claim спринта.

Агент выбирает одну задачу тем же `bootstrap` с её ID. Инструмент начинает её и сразу возвращает обычный stage
context/result_template. В дальнейшем ID не повторяется. После `verify`, `accept` и `cancel` ответ автоматически
включает обновлённую проекцию спринта. Для межпроектного поиска доступных задач есть отдельный [read-only
`next`](../configuration/project-setup.md#доступные-задачи-во-всех-проектах); он не заменяет Sprint bootstrap и не
захватывает работу.

`verified` predecessor ещё не удовлетворяет зависимость: нужен `completed` после пользовательского принятия. При
активной задаче прочитать другой спринт можно; это не переключает formal work. Начать другую task до завершения/передачи
текущей нельзя.

## Два явных вида зависимостей
Каждое ребро: `predecessor`, `successor`, `kind`.

- **completion**: требуется принятый результат предшественника; его commit не включается в специальную result-provenance
  проекцию. Это годится для организационной предпосылки.
- **result**: также требуется завершённый результат предшественника и дополнительно сохраняется его `result_commit` в
  `result_provenance`. Это provenance результата, а не выбор Git ancestry successor.

Каждый **новый** Task worktree — самостоятельный или Sprint-участник — создаётся от commit, наблюдённого на текущей
вершине явно настроенного Git `base_ref`. Наблюдение выполняется после проверки eligibility и до durable Task start;
точный SHA сохраняется в reservation. Поэтому повтор частично выполненного worktree setup использует сохранённый SHA,
даже если `base_ref` уже сдвинулся, а следующая новая Task наблюдает новую вершину. Resume и handoff существующего
worktree не резолвят `base_ref` заново, не сбрасывают и не пересоздают worktree.

У одного successor поддерживаются несколько result-рёбер с одинаковыми или различными result commits: они перечисляются
в `result_provenance`, но не выбирают branch base и не требуют наличия этих Git objects для создания worktree.
Инструмент не переносит и не сливает код предшественников; если successor действительно зависит от их кода, требуемый
код должен быть доставлен в настроенный `base_ref` отдельным явным процессом до старта successor. Точные команды
successor проверяют фактический результат.

Пределы: одна codebase проекта, как в предыдущем runtime; result dependency — Git-result, не общий resolver всех типов
артефактов. Точные команды successor проверяют фактическую работу; чужие tests receipts не становятся его evidence.

## Изменить зависимости, отменить, разрешить зависимую работу
Все действия пакетные; `sprint_id: null` использует текущий scope.

| action | Остальные поля |
|---|---|
| `materialize_tasks` | request_id, expected_revision; превращает legacy embedded definitions в реальные newborn Task |
| `extract_tasks` | request_id, expected_revision, task_ids; возвращает изолированных eligible участников в standalone |
| `dependencies` | request_id, expected_revision, items, reason |
| `cancel_tasks` | request_id, tasks (список ID), mode (`single`/`cascade`), reason |
| `cancel` | request_id, reason |
| `waive_dependencies` | request_id, decisions (predecessor, successor, reason) |

Изменение prerequisites уже начатого successor отклоняется. Cancel одного узла не закрывает siblings/root; cascade
вычисляется по его потомкам. У cancelled predecessor незавершённый successor остаётся blocked до пользовательского
waiver либо отмены ветки. Waiver и исходное ребро остаются в business data, исправление не имитируется.

`cancel_tasks` отменяет **незавершённых** выбранных участников через Task domain; уже
completed/cancelled не переписываются. `cancel` отменяет Sprint целиком: у published Sprint
отменяет всех незавершённых участников, сохраняет completed/cancelled, результаты, историю и
артефакты; у draft отсоединяет newborn и adopted участников без создания Task. Для каждой затронутой Task тот
же владелец создаёт persisted cleanup obligation. Сам terminal-переход не удаляет worktree,
не публикует commit и не выдаёт WIP за проверенный результат.

```json
{"operation":"sprint","input":{"action":"cancel","sprint_id":"S-1","request_id":"cancel-sprint-1","reason":"Пользователь отменил Sprint"},"messages":[]}
```

Отмена standalone Task выполняется её владельцем через `operation: cancel`. Явная
Sprint-команда является полномочием Sprint над собственными участниками и может отменить
активную Task, освободив claim, но не может затронуть задачу другого Sprint. Перед пакетной
отменой все выбранные участники проверяются на pending внешние операции; найденный pending
отклоняет весь пакет без частичного эффекта. Семантическую санкцию пользователя интерпретирует
агент; непустая reason сохраняет это решение, но не является криптографическим удостоверением.
Последующая судьба commit задаётся отдельным `cleanup` для каждой Task; статусы, dirty-worktree
recovery и точная область ресурсов описаны в
[terminal cleanup через native launcher](../configuration/runtime-hooks.md#terminal-cleanup-через-native-launcher).

## Исправить сломанную незавершённую Task

`replace_task` больше не является публичным action. Ошибочный контракт опубликованного
участника исправляется через общий Task lifecycle: `operation: task`, `action: restart` возвращает
ту же незавершённую Task в `newborn`, сохраняя её ID, членство в Sprint, immutable history,
worktree/branch и WIP. После `edit` и `ready` тот же участник снова становится `available`, поэтому
граф, зависимости и provenance не перенаправляются на новый ID.

Restart требует актуальную Task `expected_version`, новый `request_id`, содержательную `reason`
и явную `authorization`. Чужой live owner, pending external outcome и terminal Task отклоняются
до мутации. Идентичный replay возвращает первый receipt; конфликтующий intent с тем же ID
отклоняется. Исторические связи замен сохранены в неизменяемых revision layers и журнале
[явной миграции](../task-status-retirement.md). В текущей проекции нет поля
`replacements`; оставшиеся терминальные состояния — `completed` и `cancelled`.

## Закрытие и чтение
Sprint progress — согласованная проекция из membership и Task states, а не дублируемые вручную счётчики. Нормальное
закрытие определяется явным `acceptable_terminal_states` и отсутствием незавершённой работы/блокировок. Полное
тестирование приложения при закрытии не запускается. Полный future closure process с артефактными post-gates пока не
реализован.

Пакетное чтение:
```json
{"operation":"show","input":{"queries":[{"id":"now","kind":"sprint","sprint_id":null,"view":"current"},{"id":"layers","kind":"sprint","sprint_id":null,"view":"history"}]},"messages":[]}
```
`plan` возвращает сохранённый контракт и snapshots для адресной диагностики. В обычном context они не печатаются
полностью. CLI доклады Sprint сохраняются в configured Sprint root; большой ответ заменяется ограниченным receipt на
полный файл.

### Реестр опубликованных Sprint

Публичный `show` query `kind: work_overview` перечисляет только опубликованные Sprint. Живой draft исключён. Отменённый
Sprint остаётся в реестре, если наличие `sprint_members` подтверждает его предшествующую публикацию; draft, отменённый
через `cancel` до публикации, участников не создаёт и в реестр не попадает. Порядок стабилен по `sprint` ID.

Каждый элемент — обычная owner-проекция `SprintWork.overview`, а не сокращённая реконструкция из строк БД. Поэтому
сохраняются `goal`, `tasks`, `counts`, `eligible`, `active`, `blocked` с причинами зависимостей, `resumable`,
`result_provenance`, `active_task` и остальные поля текущего Sprint overview. `active_task` заполняется только когда
незавершённая текущая Task вызывающей session принадлежит именно этому Sprint; standalone Task или участник другого
Sprint не переносится в чужой DTO.

Статус Sprint вычисляет владелец после проверки зависимостей и наличия завершённых predecessor results:

- `planned` — доступная работа ещё не начиналась;
- `active` — есть активная/продолженная работа либо доступная работа после уже изменившихся состояний участников;
- `completed` — все участники находятся в разрешённых терминальных состояниях;
- `cancelled` — Sprint принудительно закрыт;
- `blocked` — незавершённая работа существует, но доступных или активных участников нет.

Фильтр `sprint_statuses` в `work_overview` применяется к этой готовой проекции и не удаляет сведения
`eligible`/`blocked`. Точный общий пакет, независимый фильтр standalone Task и ограничения выдачи описаны в [пакетном
обзоре работ](batch-work.md#обзор-опубликованных-спринтов-и-самостоятельных-задач).

## Граница метрик
Пользовательские события в Sprint-операциях сохраняются без приписывания чужой активной Task. Task messages/delivery
остаются прежними. Полная атрибуция планирования к Sprint и периодные экономические агрегаты — DDD-08; не заявляются
реализованными.
