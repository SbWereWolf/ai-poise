# Журнал Orchestrator: публикация и порядок чтения

## Статус и граница

Целевой контракт ORC-05, `PS-DEV-002-T076`. Документ определяет будущую
возможность; он не объявляет её реализованной. Исследован исходный код
`000f8ba34f9b73759c809baf84a4db76ecde2144`.

Текущий `apps/orchestrator/shell.py` хранит revision и ответы requests, выполняет
`invoke` и читает каталог commands. Журнала событий и запроса `log_records` в нём
ещё нет. Его существующая транзакция вокруг внешнего процесса не считается
реализацией короткой публикации из этого документа.

Этот документ уточняет журнал из [общего контракта](contract-orc.md#4-ledger-и-внешние-эффекты).
Вызовы, Job, Invocation, Session и разрешения команд сохраняют своих владельцев.
[Query](contract-orc.md#8-query-и-bounded-status) и
[ошибки](contract-orc.md#9-ошибки-и-приоритет) ниже расширяются на уровне целевого
контракта. Соответствие текста этим схемам не доказывает работу будущего провайдера.

Один логический журнал имеет явно настроенный `journal_id`. Orchestrator назначает
места публикации только внутри этого журнала. Общего счётчика всех приложений,
установок или независимых журналов нет. Внешний процесс работает вне короткой
транзакции публикации; испытания приложения также не удерживают её.

## Типы и настройки

`Id` — непустая строка без NUL, как у существующего владельца `_nonempty`.
Все целочисленные поля принимают JSON integer; boolean и дробное число не являются
целым. `position` положителен; `after`, `through`, `monotonic_ns` неотрицательны;
`limit` положителен. `through` допускает также `null` в первом запросе.

Поля координационных объектов перечислены исчерпывающе. Обязательное поле всегда
присутствует; `null` разрешён только там, где это указано. `data` — JSON object,
содержание которого определяет производитель события. Внутри него доступны JSON
строки, boolean, null, конечные числа, объекты и массивы. Повторные ключи и
неконечные числа недопустимы. В отличие от целевой формы, текущий stdin-парсер shell
отклоняет дробные числа; поддержка целевого журнала этим не утверждается.

Используются явно заданные параметры владельца:

| Параметр | Значение и область |
| --- | --- |
| `paths.state`, `paths.database` | Существующее собственное хранилище Orchestrator |
| `batch.max_input_bytes` | Положительный предел UTF-8 bytes входного пакета и представления публикуемой записи; ограничивает также содержащиеся в них Id |
| `batch.max_items` | Положительный предел вложенных элементов `data`: сумма числа членов объектов и элементов массивов на всех уровнях, по существующему определению `_collection_items` |
| `read.max_queries` | Положительный предел числа query items в пакете |
| `log.journal_id` | Явный Id логического журнала |
| `log.max_page_records` | Положительный предел `limit` одной страницы |

Первые параметры существуют в текущем
[примере конфигурации](../config/orchestrator.example.json). `log.*` — новые целевые
настройки. Их значений по умолчанию нет. Это пример фрагмента настроек реализации
целевого журнала, а не новая рабочая конфигурация текущего shell:

```json
{"log":{"journal_id":"orchestrator-main","max_page_records":100}}
```

Текущие конфигурация `stride-orchestrator-config/v1`, executable и working config
этой задачей не изменяются. В реализации журнала оператор явно задаёт его Id и
размер страницы вместе с остальными параметрами владельца. Дополнительного
реестра команд и общей блокировки установки для журнала не требуется.

## Запись и время

`Record` содержит ровно следующие поля:

| Поле | Тип и смысл |
| --- | --- |
| `schema` | Точно `stride-orchestrator-log/v1` |
| `journal_id` | Id журнала |
| `record_id` | Id публикации, уникальный внутри журнала и сохранённый для повтора |
| `position` | Положительное целое место, назначенное владельцем при публикации |
| `job_id` | Id существующего Job |
| `invocation_id` | Id соответствующей Invocation этого Job |
| `event` | Id вида события; смысл принадлежит производителю |
| `observed` | Ровно `{audit_utc,monotonic_ns,comparison_domain}` |
| `data` | JSON object события |

Все поля обязательны, ни одно из них не nullable. Nullable значения внутри `data`
определяет контракт производителя. Изменение обязательной координационной формы
получает новую явную версию schema.

`audit_utc` — ISO datetime с явным нулевым смещением UTC (`Z` или `+00:00`),
соответствующий семантике `ClockObservation`. `monotonic_ns` — неотрицательное
целое; `comparison_domain` — Id области сравнения. Продолжительность определяется
разностью монотонных наблюдений только одной области. UTC служит аудиту и
календарному представлению. Смена области сравнения не мешает читать журнал по
`position`; длительность между разными областями из этих данных не выводится.

Часы не назначают порядок журнала. `position` также отличается от Job.version и
общей coordinator revision. Записи одного журнала читаются по возрастанию position,
включая одинаковое UTC и переставленный физический экспорт.

## Атомарная публикация и повтор

Порт публикации внутренний для владельца Orchestrator. Он получает ровно поля
`record_id,job_id,invocation_id,event,observed,data`; журнал выбирается явной
конфигурацией композиции. `schema`, `journal_id` и `position` формирует владелец.
Ответ порта содержит ровно `{record:Record,replayed:boolean}`. Новый публичный
CLI operation для публикации этим контрактом не добавляется.

В одной короткой транзакции своего store владелец:

1. Находит публикацию по `record_id` выбранного журнала.
2. Для новой публикации назначает position выше прежнего максимума журнала.
3. Сохраняет целую запись вместе с соответствием для повтора.
4. Подтверждает транзакцию и возвращает ответ.

Конкурирующие вызовы сериализуют только эту запись в store. Внешнее выполнение
не входит в транзакцию. Неудача до commit оставляет новую публикацию целиком
отсутствующей. При неизвестном подтверждении вызывающий повторяет исходную
публикацию с тем же Id и теми же значениями, включая исходное наблюдение часов.
Это повтор записи журнала, а не повтор внешней команды.

При совпадении исходного содержимого повтор возвращает прежнюю целую запись,
прежний position и `replayed:true`. Порядок ключей JSON object незначим, порядок
массивов значим; тип и значение сравниваются по исходным JSON-данным. Изменённое
содержимое под занятым Id получает `record_identity_conflict`. Хэши для сравнения
намерения не нужны.

Опубликованные идентичность, содержимое и position неизменны. Новая публикация
имеет position выше максимума уже опубликованных записей. Пропуски позиций
допускаются и не заполняются позднее. Удаление и compaction не вводятся этим
контрактом: записи выбранного префикса остаются доступными для его чтения.

Порядок означает принятие владельцем, а не момент внешнего эффекта. Производитель,
которому нужен порядок «причина перед результатом», сначала публикует причину через
этого же владельца, затем результат. Произвольный граф причинных событий и порядок
между независимыми журналами здесь не определяются.

## Чтение одного префикса страницами

Используется существующий внешний packet `schema=stride-orchestrator/v1`,
`operation=query`. Новый query item имеет ровно:

`id,kind,journal_id,job_id,after,through,limit`, где `kind=log_records`.

Job принадлежит текущей origin Session, а его команды доступны текущим ролям по
существующим правилам общего контракта. Эти правила применяются перед каждым
чтением, следующей страницей, повтором и раскрытием ошибки записи. Порт публикации
сохраняет ту же принадлежность Job/Invocation. Отдельная система ролей не создаётся.

Все items одного query packet читаются в одном согласованном read snapshot.
В нём определяют текущий максимум журнала `M`, для пустого журнала `M=0`:

- `through:null` фиксирует `through=M`;
- явный through принимается при `0 <= through <= M`;
- after принимается при `0 <= after <= through`;
- выбираются записи только указанного Job с `after < position <= through`,
  по возрастанию position, до явно заданного limit.

`limit <= log.max_page_records`. Значения других Job не входят в страницу;
пропуски их позиций не меняют порядка этого Job. Через through выше текущего M
операция не обещает будущий снимок: она возвращает `invalid_log_request` с
`{field:"through",reason:"above_current_maximum"}`.

`value` результата имеет ровно `{journal_id,job_id,through,items,next_after}`.
`items` — массив полных Record. `next_after` — position последней выданной записи,
если в выбранном префиксе остались записи этого Job; иначе `null`.
Следующий запрос сохраняет journal_id/job_id/through, передаёт next_after как after
и задаёт limit явно.

Пустой журнал возвращает through0, items[] и next_after:null. При after==through
страница также пуста и завершена. Граница внутри пропуска допустима и выбирает
только существующие позиции. Поздняя публикация имеет position выше прежнего M,
поэтому не попадает в ранее выбранный префикс.

Это стабильный префикс неизменных записей, а не замороженные права или состояние
Job. Текущая область доступа проверяется заново. Недоступный или неизвестный Job
отклоняет весь query packet; частичных results/items в ошибке нет. Например:

| Условия чтения | Результат |
| --- | --- |
| Session-A владеет Job-A, его команда разрешена | Страница содержит только записи Job-A |
| Job относится к другой origin Session | `origin_mismatch`, details ровно `{job_id:Id}`, retryable:false |
| Текущая роль потеряла разрешение команды Job | `command_denied`, details ровно `{command_id:Id}`, retryable:false |
| Job не найден в области вызывающего | `job_unknown`, details ровно `{job_id:Id}`, retryable:false |

Идентичные публикации повторяются только в разрешённой области Job; повтор не
обходит эти правила. При отказе доступа данные и диагностика записей не выдаются.

Полный закрытый экспорт набора уже принятых записей может иметь физический порядок
C,A,B и логический A,B,C. Это сохранённые position, а не новые append с заданными
вызывающим позициями. При отдельном offline-восстановлении полный закрытый набор
становится доступен до новых публикаций, которые продолжаются выше его максимума.
Инструмент импорта или миграции этой задачей не реализуется.

## Ошибки запрошенной операции

Целевая форма ошибки использует общий контракт: ровно
`{schema:"stride-orchestrator/v1",status:"rejected",error:{code,message,retryable,details}}`,
exit2. `message` — понятный текст для человека, machine discriminator — code.
Ни `results`, ни частичных `items` эта форма не содержит.

| code | Условие | Точные details | retryable |
| --- | --- | --- | --- |
| `invalid_log_request` | Поле или граница запроса/публикации не соответствует договору | `{field:string,reason:string}` | false |
| `journal_not_found` | Выбранный Id не соответствует доступному собственному журналу | `{journal_id:Id}` | false |
| `record_identity_conflict` | Занятый Id публикации имеет другое исходное содержимое | `{journal_id:Id,record_id:Id}` | false |
| `log_record_invalid` | Запрошенная доступная запись не читается или её значения не позволяют определить смысл/порядок | `{journal_id:Id,position:positive integer|null,field:string,reason:string}` | false |
| `log_storage_error` | Собственная операция storage/I/O не завершена или подтверждение неизвестно | `{journal_id:Id,reason:string,outcome:string}` | true только при временной ошибке, которую так классифицирует владелец I/O; иначе false |

У `invalid_log_request` reason принимает ровно `required`, `unknown_field`,
`invalid_type`, `invalid_value`, `limit_exceeded`, `above_current_maximum`,
`after_above_through`. field указывает поле JSON.

У `log_record_invalid` position всегда присутствует: это известная положительная
позиция либо null, если владелец не может её определить. field — путь JSON либо
`$` для всей записи; reason принимает ровно `unreadable_json`, `required`,
`unknown_field`, `invalid_type`, `invalid_value`.

У `log_storage_error` outcome принимает ровно `not_committed`, `unknown`,
`read_failed`; reason содержит понятную фактическую диагностику владельца.
При неизвестном подтверждении повторяется только идентичная публикация журнала.
Атомарное соответствие Id/записи разрешает такой повтор без дубликата; разрешения
на повтор внешнего эффекта этот ответ не даёт.

Обработка ограничена запрошенной операцией. Посторонние записи и журналы на старте
не сканируются. Приложение не восстанавливает смысл данных догадками. Оператор
восстанавливает выбранную корректную копию либо заново получает материал у его
производителя отдельным инструментом.

## Примеры правильного использования

Во всех примерах журнал `orchestrator-main`, Job-A принадлежит Session-A, команда
`requirements.query` ей разрешена. Параметры владельца заданы явно; предел страницы
100, запрос использует limit2. Все три наблюдения имеют одинаковое UTC и область
сравнения boot-A.

Публикация event-B через внутренний порт после event-A:

```json
{"record_id":"event-B","job_id":"job-A","invocation_id":"inv-A","event":"started","observed":{"audit_utc":"2026-10-16T12:00:00+00:00","monotonic_ns":2000000,"comparison_domain":"boot-A"},"data":{"step_id":"step-A-start"}}
```

Ответ новой публикации:

```json
{"record":{"schema":"stride-orchestrator-log/v1","journal_id":"orchestrator-main","record_id":"event-B","position":2,"job_id":"job-A","invocation_id":"inv-A","event":"started","observed":{"audit_utc":"2026-10-16T12:00:00+00:00","monotonic_ns":2000000,"comparison_domain":"boot-A"},"data":{"step_id":"step-A-start"}},"replayed":false}
```

Повтор той же публикации с сохранёнными входными значениями:

```json
{"record":{"schema":"stride-orchestrator-log/v1","journal_id":"orchestrator-main","record_id":"event-B","position":2,"job_id":"job-A","invocation_id":"inv-A","event":"started","observed":{"audit_utc":"2026-10-16T12:00:00+00:00","monotonic_ns":2000000,"comparison_domain":"boot-A"},"data":{"step_id":"step-A-start"}},"replayed":true}
```

После публикаций event-B в позиции2 и event-C в позиции3 первая страница:

```json
{"schema":"stride-orchestrator/v1","operation":"query","input":{"queries":[{"id":"page-1","kind":"log_records","journal_id":"orchestrator-main","job_id":"job-A","after":0,"through":null,"limit":2}]}}
```

Полный ответ:

```json
{"schema":"stride-orchestrator/v1","status":"read_only","revision":9,"results":[{"id":"page-1","value":{"journal_id":"orchestrator-main","job_id":"job-A","through":3,"items":[{"schema":"stride-orchestrator-log/v1","journal_id":"orchestrator-main","record_id":"event-A","position":1,"job_id":"job-A","invocation_id":"inv-A","event":"queued","observed":{"audit_utc":"2026-10-16T12:00:00+00:00","monotonic_ns":1000000,"comparison_domain":"boot-A"},"data":{"command_id":"requirements.query"}},{"schema":"stride-orchestrator-log/v1","journal_id":"orchestrator-main","record_id":"event-B","position":2,"job_id":"job-A","invocation_id":"inv-A","event":"started","observed":{"audit_utc":"2026-10-16T12:00:00+00:00","monotonic_ns":2000000,"comparison_domain":"boot-A"},"data":{"step_id":"step-A-start"}}],"next_after":2}}]}
```

До второй страницы опубликована event-D с position4, coordinator revision стал10.
Потребитель сохраняет through3 и продолжает тот же префикс:

```json
{"schema":"stride-orchestrator/v1","operation":"query","input":{"queries":[{"id":"page-2","kind":"log_records","journal_id":"orchestrator-main","job_id":"job-A","after":2,"through":3,"limit":2}]}}
```

Полный ответ:

```json
{"schema":"stride-orchestrator/v1","status":"read_only","revision":10,"results":[{"id":"page-2","value":{"journal_id":"orchestrator-main","job_id":"job-A","through":3,"items":[{"schema":"stride-orchestrator-log/v1","journal_id":"orchestrator-main","record_id":"event-C","position":3,"job_id":"job-A","invocation_id":"inv-A","event":"returned","observed":{"audit_utc":"2026-10-16T12:00:00+00:00","monotonic_ns":3000000,"comparison_domain":"boot-A"},"data":{"step_id":"step-A-start","exit_code":0}}],"next_after":null}}]}
```

Прочитаны ровно A,B,C. Запись D относится следующему новому чтению. Физический
экспорт C,A,B этих трёх записей даёт тот же логический результат A,B,C: ключом
чтения являются сохранённые position1,2,3. Одинаковое UTC не требует tie-break
по часам или по расположению в файле.

Если при чтении разрешённой страницы владелец сообщает, что сохранённая запись
position2 не читается как JSON, ожидается целиком такой корректный ответ:

```json
{"schema":"stride-orchestrator/v1","status":"rejected","error":{"code":"log_record_invalid","message":"Запись журнала в позиции 2 не читается как JSON.","retryable":false,"details":{"journal_id":"orchestrator-main","position":2,"field":"$","reason":"unreadable_json"}}}
```

Запрос получил определённую причину отказа этой операции. Частичные записи и
результаты в ответ не добавляются; другие операции не объявляются испорченными.

## Соответствие задаче и проверка

| Обязательство | Где определено |
| --- | --- |
| R01 / ORC-05: атомарность, время, идентичность, порядок | Запись и время; атомарная публикация и повтор; чтение префикса |
| DoD: одинаковое время, переставленный физический append, однозначное чтение | Три записи A,B,C; физическое C,A,B; две страницы одного through3 |
| DoD: ошибка повреждённой записи | Точная форма log_record_invalid и корректный JSON ожидаемого отказа position2 |
| DoD: контракт, конфигурация и команда вместе | Типы и настройки; внутренний порт; публичный operation=query/kind=log_records и полные packets |

Проверка этого результата — чтение контракта, синтаксис literal JSON, сопоставление
полей/значений примеров и локальных ссылок. Это проверка проекта. Исполняемый
журнал, его runtime tests, миграция и новая рабочая конфигурация здесь не создаются
и не выдаются за прошедшие проверки реализации.
