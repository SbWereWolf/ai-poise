# Каталог метаданных skills

Обновлено: 2026-09-15. Срез миграции: C005.1 → C012.

## Владелец и состав

`.agents/skill-catalog.json` — явный каталог **поставленных в этой сборке** skills.
Он содержит 33 адаптированных прикладных/методических skill и два собственных skill Poise.
Это не требование переносить весь ERP inventory: `safe-commit` и `system-tests`
исключены решениями миграции; `preflight`, `playwright` и `jetbrains-ide` в эту
поставку не входят. Будущая установка skill должна менять каталог и проверку покрытия
вместе с его файлами. Каталог не объявляет отсутствующий инструмент реализованным.

Чистый доменный владелец `poise.modules.skills.catalog.SkillCatalog` отвечает за
метаданные. Он не читает файлы, не выбирает процесс и не изменяет Task, Sprint или claims.
`poise.infrastructure.skill_catalog.load_skill_catalog` читает один явно переданный
JSON и проверяет существование всех указанных файлов внутри явно выбранного корня.
Тела `SKILL.md`, справочников и документов при этом **не читаются**.

Содержимое skills остаётся в отдельных `SKILL.md` и references. Здесь нет копии
инструкций, описания стадий harness, ERP-топологии или весового бюджета задачи.
Предназначенный для router C004 интерфейс выдаёт дескрипторы и точные пути; сам
автоматический router C004 в этот срез не входит.

## Формат `poise-skill-catalog-1`

Каждая запись имеет ровно поля `id`, `path`, `purpose`, `class`, `level`, `responsibility`:

```json
{
  "id": "vue-best-practices",
  "path": ".agents/skills/vue-best-practices/SKILL.md",
  "purpose": "Implement Vue components with explicit ownership and reactivity.",
  "class": "working",
  "level": 1,
  "responsibility": "vue-frontend"
}
```

`id` — уникальный kebab-case идентификатор; `path` — уникальный канонический
относительный путь к `SKILL.md`. Абсолютные пути, traversal, обратные слеши, шаблоны
и выход через symlink за выбранный корень отклоняются. `purpose` — краткое назначение,
а не копия инструкции. Неизвестные поля, повторные JSON-ключи и неподдержанная schema
являются ошибкой, а не сигналом применить defaults.

`class` принимает `meta`, `common` или `working`. У `meta` и `common` поля `level`
и `responsibility` равны `null`. У `working` `level` — явное положительное целое
значение уровня специализации, а `responsibility` — непустое имя ответственности.
В текущем каталоге рабочие skills находятся на уровне 1. Это **не балл сложности**:
разные номера не разрешают автоматически смешивать несвязанные ответственности,
а связи наследования между уровнями не угадываются.

Для существующего контракта `task_decomposition.skills` владелец предоставляет
единственное отображение: `meta → meta`, `common → general`, `working → narrow`.
Responsibility переносится без вывода по имени skill или пути. Несколько инструментов
одной ответственности допустимы: например, SQL и строгие миграции относятся к `database`.
Разные ответственности требуют отдельных ordinary Tasks; совместное применение
результатов описывается отдельной integration Task.

Каталог поставки — явные исходные метаданные, не автоматическое переопределение
конфигурации любого целевого проекта. Project-specific набор skills и маршруты areas
по-прежнему выбираются явно. Инвентарь приложения не зашит в исходники Poise.

## Чтение без Task и harness

Из корня исходников, с Python проекта:

```bash
printf '%s\n' '{"operation":"list"}' | \
  PYTHONPATH="$PWD/src" python -B -m poise skills \
    --catalog "$PWD/.agents/skill-catalog.json" --root "$PWD"

printf '%s\n' '{"operation":"read","skill_ids":["tdd","vue-best-practices"]}' | \
  PYTHONPATH="$PWD/src" python -B -m poise skills \
    --catalog "$PWD/.agents/skill-catalog.json" --root "$PWD"
```

`list` возвращает весь каталог; `read` — ровно запрошенные записи в порядке ID.
Пустой `skill_ids` означает пустой выбор, а не «все». Неизвестные или повторные IDs
отклоняют запрос целиком. Результат содержит `catalog_digest`, вычисленный из
нормализованных метаданных; перестановка записей его не меняет. Digest не удостоверяет
содержимое инструкций, которое команда не читает.

Успех: exit 0 и JSON `status=ok`; неверный запрос/каталог: exit 2 и `status=rejected`.
Команда не требует `POISE_CONFIG`, `bootstrap`, сессии или Task DB, не выполняет
shell-команды из метаданных и ничего не записывает. Это справочный интерфейс владельца
skills, а не второй жизненный цикл Task и не замена runtime routing.

## Политика проекта и проверка пакета без harness

`operation=policy` принимает явные `skill_ids` и `areas`, возвращает `policy` для
`task_decomposition`. Эта форма содержит ровно `catalog`, `skill_ids`, `areas`:
в `catalog` находится нормализованный снимок **полного** каталога метаданных,
`skill_ids` ограничивает доступный проекту выбор, `areas` задаёт его собственные
относительные glob-пути и responsibilities. Определения классов не повторяются вручную.
Уже поддержанная самостоятельная project-specific форма `skills` + `areas` также
допустима; смешивать обе формы в одной политике нельзя. Это два явных входных контракта,
не неявный fallback и не обращение к файлам из domain-модуля.

```json
{
  "operation": "policy",
  "skill_ids": ["laravel", "php-modernization", "tdd", "documentation"],
  "areas": [
    {"path": "app/**", "responsibility": "laravel-backend"},
    {"path": "docs/**", "responsibility": "documentation"}
  ]
}
```

Пустой выбор для политики ошибочен. Исключение рабочего skill из `skill_ids` не
превращает его известную каталогу ответственность в общую: area такого владельца
по-прежнему требует соответствующий разрешённый рабочий skill. Политика — снимок,
поэтому изменение файла каталога само по себе не меняет конфигурацию уже выбранного
проекта. `policy` ничего не публикует и не записывает в managed manifest.

`operation=validate` принимает те же поля и непустой `tasks`. Каждый элемент имеет
ровно `id`, `stages`, `decomposition`. Это компактная декларация для проверки,
**не** полный creation contract Task. В репозитории есть выполняемый пример с двумя
ordinary Tasks и отдельной integration Task:

```bash
PYTHONPATH="$PWD/src" python -B -m poise skills \
  --catalog "$PWD/.agents/skill-catalog.json" --root "$PWD" \
  < examples/skill-decomposition.json
```

Владелец проверки остаётся `FocusedDecomposition` в модуле Tasks; прямой интерфейс
лишь вызывает его для каждого элемента. Тот же валидатор используется существующими
путями создания/готовности Task и публикации Sprint. `inspect` возвращает все
независимо определимые ошибки внутри декларации; пакет продолжает проверку остальных
Tasks. `require_valid` возвращает декларацию либо `DecompositionError` с теми же
`diagnostics`, а не останавливается на первом дефекте. Для испорченного поля зависимые
от него проверки не выдумываются; известные независимые дефекты всё равно возвращаются.

Результаты содержат `task`, `valid`, `diagnostics`; каждое сообщение — `code`,
`location`, `message`. Результаты сортируются по Task ID, диагностика — по месту,
коду и сообщению. Повторные Task IDs и независимые ошибки остальных элементов
возвращаются в одном пакете. Это пакет деклараций, а не проверка графа зависимостей.

| Исход | `status` | Exit |
|---|---|---:|
| Все декларации согласованы | `valid` | 0 |
| Есть ошибки деклараций | `invalid` | 1 |
| Неверен запрос, каталог или политика | `rejected` | 2 |

### Проверяемые границы

Каждая фаза процесса должна присутствовать ровно один раз и явно объявлять `skills`
и `areas`; пустые списки допустимы как явное отсутствие. Рабочая area требует skill
с той же responsibility **в этой фазе**. Skill из planning не покрывает область
implementation. Обычная Task не соединяет разные рабочие responsibilities ни внутри
фазы, ни через разные фазы; несколько дополняющих skills одного владельца допустимы.
Meta/common не создают самостоятельной причины разделить задачу.

Integration Task может соединять компоненты только при непустых `component_inputs`,
`combined_result`, `integration_checks`, `allowed_paths`. Разрешённые пути должны
покрывать **все** areas фаз, включая общую документацию. Проверка вложения glob
консервативна: равенство, явный `**` или литеральный предок `directory/**`; более
сложные пересечения не угадываются. Абсолютные, неканонические и traversal-пути
отклоняются. `allowed_paths` не расширяет реальные Task-specific stage contracts.

Этот валидатор не доказывает честность или полноту declarations, существование
компонентных результатов и фактическое исполнение integration checks. Task/Sprint
owners по-прежнему проверяют реальные contracts, зависимости, артефакты и права на
изменения. Числовые ERP risk/context weights, привязки к приложениям ERP и обязательные
review-квартеты не перенесены. Автоматический выбор skills по diff/profile (C004)
остаётся отдельной задачей, а не скрытой возможностью команды `skills`.

## Проверки

```bash
python -B -m pytest -q -p no:cacheprovider \
  tests/skills/test_catalog.py tests/skills/test_decomposition.py \
  tests/tasks/test_focused_decomposition.py
bash tests/smoke.sh "$(command -v python)"
```

Точечные проверки охватывают форму, классы, уровни, уникальность, изоляцию входов/выходов,
выбор, снимок политики, ссылки на реальные файлы, отсутствие чтения тел инструкций,
декомпозицию по фазам, integration scope и полную независимую диагностику. Проверка
покрытия сверяет каталог с фактическими `*/SKILL.md`, а не с историческим числом
директорий ERP. Она не доказывает актуальность каждой рекомендации в skill.
