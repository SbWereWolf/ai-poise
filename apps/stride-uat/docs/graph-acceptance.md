# Приёмка выбранного графа Execution

## Назначение и владельцы

Команда [graph_cases.py](../acceptance/graph_cases.py) испытывает выбранный граф
через внешний CLI самостоятельного Execution. Поддержаны создание с нуля (`full`),
создание из выбранного шаблона (`template`) и именованное изменение (`edited`).
Execution владеет графом, исполнением и хранилищем; адаптер проверяет фактические
этапы и переходы; UAT сохраняет свидетельства и вычисляет собственный verdict
по [действующему протоколу](uat-protocol.md).

Приёмка относится к переданному графу, плану и выполненным сценариям. Набор
сценариев конечный: он подтверждает объявленные маршруты и наблюдения.

## Подготовка окружения

Используйте Linux/POSIX, Python 3.13, Git и отдельные доступные тестовые корни.
Настройте публичную команду Execution, профиль UAT, изоляцию и входные файлы по
[руководству UAT](uat-protocol.md#конфигурация-и-явные-зависимости).
Сохраняйте выбранный путь интерпретатора виртуального окружения в argv.

Сопровождаемые проверки этой поставки выполнялись в Ubuntu 24.04 WSL с
CPython 3.13.15. Их тестовое окружение использует `/usr/bin/setpriv`, запуск
под root и отдельную дочернюю идентичность UID 62058 / GID 1000. Файлы приложения,
интерпретатор и входы должны быть доступны этой идентичности для чтения и
прохода по каталогам. Тестовые корни предназначены для записи; отдельный
защищённый корень используется существующей проверкой изоляции.
Эти числовые значения принадлежат поставленным тестовым фикстурам;
развёртывание UAT выбирает собственный явный профиль и изоляцию.

Размер `program_bytes` в тестовой конфигурации равен 67108864 байтам:
этот существующий лимит также применяется при чтении объявленных файлов,
включая фактический исполняемый файл Python. Подберите положительные лимиты
под реальные входы своей установки.

## Входы плана и программы

Подготовьте три отдельных входа: граф, план сценария и программу UAT.
[graphs.json](../tests/fixtures/graph-acceptance/graphs.json) содержит буквальные
графы, а [plans.json](../tests/fixtures/graph-acceptance/plans.json) — соответствующие
планы. Для своего запуска сохраните выбранный объект плана отдельным JSON-файлом.

| Поле плана | Фактическая роль |
| --- | --- |
| `schema` | Метка поставленной фикстуры `execution-graph-case-plan/v1`; адаптер её отдельно не проверяет |
| `execution_config` | Полная конфигурация собственной установки Execution; адаптер задаёт её `verification.repository` и `verification.output_root` путями свежего тестового экземпляра |
| `instance_directory` | Имя каталога свежего экземпляра внутри workspace шага |
| `observation_file` | Относительный путь полного JSONL-журнала внешних вызовов внутри workspace шага |
| `template_id` | Выбор записи `execution_config.process.templates` в сценарии `template` |
| `baseline` | Исходный граф для `edited` и структурного отказного сценария |
| `changes` | Именованные изменения публичного `process/edit` для `edited` |
| `contracts` | Объект контрактов по Task ID; первый явно заданный ID используется для проверки пустого подготовленного экземпляра; выбранные контракты используются при setup исполнения |
| `snapshots` | Снимки требований по тем же Task ID для публичного freeze |
| `actor_id` | Явный участник lifecycle/Gate/attempt/advance, согласованный с конфигурацией Execution |
| `expected_routes` | Объявленные упорядоченные этапы каждого проверяемого исполнения; `edited` задаёт старый и новый Task ID в этом порядке |
| `expected_verdict` | Ожидание независимого теста поставки; адаптер это поле не использует для получения своего результата |
| `expected_rejection_token` | Проверяемый признак структурного отказа в отказном сценарии |

Адаптер читает используемые поля; эта таблица описывает их назначение,
а не отдельный строгий валидатор схемы плана. Задавайте поля и согласованные
значения по выбранному сценарию. Контракт установки, пути и параметры описаны в
[оболочке Execution](../../execution/docs/shell-exe.md),
[process](../../execution/docs/process-exe.md),
[store](../../execution/docs/store-exe.md),
[lifecycle и снимках](../../execution/docs/lifecycle-exe.md),
[Gate](../../execution/docs/gate-exe.md) и
[попытках проверки](../../execution/docs/verification-exe.md).
Адаптер подставляет выбранную ревизию процесса в `contract.process_ref` при setup.

В UAT задайте команду сценария через явный Python и путь `graph_cases.py`.
Её аргументы: `--context`, отдельный элемент `${context}`, `--scenario`, выбранное
имя сценария, `--plan`, абсолютный путь к подготовленному плану. UAT подставляет
путь своего контекста в `${context}`. Контекст передаёт workspace, `public_argv`,
граф и путь результата; адаптер самостоятельно не выбирает установку монолита.

В `commands.source_inputs` объявите самодостаточный файл адаптера, план и
используемые исполняемые входы. В `applications.public_argv` задайте внешний
CLI Execution; в `delivery_inputs` объявите его поставку и зависимости.
Публичный клиент дописывает `--config` с путём собственной тестовой конфигурации.
В `inputs` укажите выбранный граф как файл, а в `program.graphs` свяжите его
с `input_id` и обязательным шагом. Этот же шаг указывает `graph_id` и команду.
Полные формы находятся в [конфигурации](../tests/fixtures/graph-acceptance/uat-config.json)
и [программе](../tests/fixtures/graph-acceptance/program.json) тестов.
Токены вида `@PLAN@` в этих файлах заполняет тестовый helper;
для собственного CLI-запуска сохраните уже заполненные значения по своему профилю.

## Порядок выполнения

1. Подготовьте согласованные граф, план, программу и конфигурацию UAT с отдельными
   корнями данных. Выберите новый `run_id` и полный путь программы.
2. Передайте запрос `run` публичной команде UAT по
   [примеру действующего протокола](uat-protocol.md#run-новый-запуск-или-точное-чтение-прежнего).
   Выберите настроенный `profile_id`; `step_limit: 0` выполняет оставшуюся программу.
3. Адаптер создаёт собственный каталог, Git-репозиторий с начальным коммитом
   и конфигурацию Execution. Первым публичным вызовом он запрашивает заданный
   Task ID в свежем экземпляре. Ответ `execution_not_found` подтверждает ожидаемую
   пустую подготовленную установку.
4. Адаптер создаёт граф напрямую или из шаблона, настраивает исполнение,
   выполняет freeze/enter, Gate, attempt begin/run/finish, present и advance.
   После переходов читает действительное состояние и принятые посещения этапов.
   В `edited` старое исполнение замораживается до изменения графа, новое — после.
5. Прочитайте итог UAT, `protocol_path`, результат шага и сохранённые графовые
   свидетельства. Сопоставьте verdict с выбранной программой и обязательными шагами.

Поставленные положительные проверки наблюдают маршруты:

| Сценарий | Исполнение | Фактически проверяемая последовательность |
| --- | --- | --- |
| `full` | `2042` | `collect-note → seal-note` |
| `template` | `2042` | `capture-note → check-note → publish-note` |
| `edited`, прежний снимок | `2042` | `collect-note → seal-note` |
| `edited`, новый снимок | `2043` | `collect-note → inspect-fragment → seal-note` |

ID и этапы здесь относятся к поставленным фикстурам. Для своего выбранного
графа задайте согласованные контракты, снимки и ожидаемые маршруты.

## Результаты и свидетельства

| Результат случая | Exit | Наблюдение |
| --- | --- | --- |
| `PASS` | 0 | Публичные этапы, переходы и принятые посещения соответствуют выбранному маршруту |
| `FAIL` | 1 | При испытании графа получен структурный отказ или фактический результат расходится с выбранным сценарием |
| `BLOCKED` | 3 | Подготовка установки либо доступ к необходимому окружению завершились отказом до возможности получить требуемое наблюдение |

Явная подготовительная граница преобразует отказ своего первого публичного
запроса в `BLOCKED`. Последующие неожиданные отказы графовых операций дают
`FAIL`. UAT вычисляет общий verdict по всей программе и её обязательным шагам.
В проверках поставки отрицательные контроли ожидают именно фактический `FAIL`
квалификации; успешный тест подтверждает правильное различение результатов.

`calls.jsonl` (либо выбранный `observation_file`) содержит argv, полный вход,
код завершения, stdout и stderr каждого вызова Execution до его интерпретации.
`setup.json` содержит Git-подготовку и исходную версию собственного репозитория.
Graph checks ссылаются на эти файлы; UAT сохраняет их содержимое как evidence.
Для отказа ещё при создании объекта случая используется `preparation.json`.
Результат связывается с текущими `run_id`, `step_id`, `application_id` и выбранным
графом через существующий протокол UAT. Одного exit 0 для приёмки недостаточно.

## Сопровождаемые проверки

Выполняйте команды из корня checkout, выбрав абсолютный путь Python 3.13
и отдельный каталог результатов. Для двух графовых команд под обычным WSL
пользователем тестовый entry сам вызывает существующий Ubuntu root через
`wsl.exe --distribution Ubuntu --user root`; root-entry выполняет проверки напрямую.
Это способ запуска тестов, а не команда продукта.

```bash
"${graph_python:?Absolute Python 3.13 path}" -B apps/stride-uat/tests/test_graph_acceptance.py --suite behavior --output-root "${graph_output:?Absolute result directory}/graphs"
"${graph_python:?Absolute Python 3.13 path}" -B apps/stride-uat/tests/test_graph_preparation.py --suite behavior --output-root "${graph_output:?Absolute result directory}/preparation"
"${graph_python:?Absolute Python 3.13 path}" -B apps/stride-uat/tests/test_shell.py --suite behavior
```

Первая команда выполняет пять реальных групп: новый граф, шаблон, изменение,
структурный отказ и контроль расхождения наблюдаемого этапа. Вторая проверяет
отказ подготовки, `BLOCKED/exit3`, сохранённое evidence и отсутствие успешных
графовых изменений. Третья выполняет восемь поддерживаемых smoke-проверок оболочки.
Подробности первых двух сохраняются в `graph-acceptance-details.json` и
`preparation-details.json` выбранных каталогов. Helper сохраняет полные наблюдения
до удаления собственных временных каталогов тестов.
