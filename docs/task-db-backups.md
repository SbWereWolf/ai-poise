# Резервные копии Task DB и материалов комментариев

Инструмент `poise backup` создаёт, показывает, восстанавливает и удаляет копии Task DB вместе с
постоянными
материалами комментариев выбранного проекта, когда настроен `paths.task_materials`. Текст
комментариев и метаданные вложений находятся в БД, исходные байты вложений — в отдельном хранилище
материалов. Один штатный комплект сохраняет обе части.

Рабочие артефакты самостоятельных Task в `standalone/`, Task-участников в `sprint/<sprint-id>/task/`
и артефакты Sprint в `sprint/` сохраняют через владельцев их поставки. Они находятся вне области
этой команды.

Для полного проекта нужна отдельная [полная копия всех хранилищ и
материалов](architecture/storage-lifecycle.md#резервное-копирование-и-восстановление); эта команда
не резервирует Requirements DB и Git.

## Обязательное условие

Команды `create` и `restore` запускает один оператор после остановки всех записывающих agent,
workflow и экземпляров AI poise для выбранного проекта. На всё время операции остановите запись и в
Task DB, и в материалы комментариев; закройте все соединения с БД. Команда работает в этом
операторском окне, без онлайн-координации писателей.

Используйте обычные файлы и каталоги в namespace материалов выбранного проекта. Сохраняйте выбранную
конфигурацию проекта и исходные пути хранения: записи вложений в БД содержат зарегистрированные
пути, а backup/restore восстанавливает данные по этим путям. Перенос расположения данных выполняется
отдельным владельцем.

Во всех примерах `PROJECT_JSON` — путь к выбранной конфигурации проекта.

## Расположение копий

Путь к рабочей базе берётся из проектной конфигурации. Копии всегда находятся в каталоге `backups/`
рядом с настроенным файлом базы данных. Отдельной настройки пути к резервным копиям нет.

Обычную копию выбирают по точному имени файла. Явное решение о продлённом хранении
владелец связывает с проектом, именем, SHA-256 байтов и конечным сроком в небольшом
соседнем `<имя-копии>.retention.json`. Это метаданные одной копии, не отдельный
архив, база или разрешение на длительное хранение по умолчанию.

## Форматы и область материалов

| Конфигурация проекта | Формат копии | Содержимое |
|---|---|---|
| Настроен `paths.task_materials` | Один файл `.zip` | `task.sqlite` и каталог `task-materials/` с материалами выбранного проекта. |
| Поле `paths.task_materials` отсутствует | SQLite-файл с расширением настроенной БД | Task DB. |

Настройка материалов описана в [конфигурации
проекта](configuration/project-setup.md#постоянные-материалы-комментариев-task).
Относительный `paths.task_materials` разрешается от `paths.state`, абсолютный задаёт точное
расположение.
В общем корне материалов команда использует только namespace, назначенный владельцем материалов
выбранному проекту. Соседние проекты сохраняют свои данные. Пустой или ещё не созданный namespace
записывается как явное пустое состояние; при восстановлении он заменяет более поздние материалы
этого проекта.

Для проекта с настроенными материалами выбирайте комплектную ZIP-копию, созданную в этом режиме.
Команда требует обе части, чтобы восстановить БД и вложения вместе. Копирование одного ZIP-файла
сохраняет весь этот комплект.

## Список

```bash
poise backup list --config PROJECT_JSON
```

Команда возвращает JSON с массивом `backups`. Для каждого обычного файла выдаются только поля `name`
и `created_at`; элементы отсортированы по имени. `created_at` — время файловой системы в UTC,
полученное из `ctime`. В Linux `ctime` означает время последнего изменения метаданных inode, а не
переносимую дату рождения файла.

Пример:

```json
{
  "backups": [
    {
      "name": "tasks-backup-20260912T123456123456Z.zip",
      "created_at": "2026-09-12T12:34:56.123456+00:00"
    }
  ]
}
```

Внутренние файлы `.pending`, метаданные `.retention.json` и каталоги в список
копий не попадают; прежние ограничения выбора файлов сохраняются. `list` не является
отдельной командой проверки разрешения на удаление.

## Создание

```bash
poise backup create --config PROJECT_JSON
```

Инструмент получает снимок настроенной Task DB средствами SQLite и выполняет `PRAGMA
integrity_check`. При настроенных материалах добавляет снимок БД и файлы namespace проекта в ZIP.
Подготовленная копия синхронизируется и публикуется одним переименованием под сгенерированным
именем. При совпадении имени выберите новый запуск с новым временем создания: существующая копия
сохраняется.

Успешный результат содержит имя, признак успеха, размер рабочей SQLite-базы и размер итогового файла
копии в байтах. Пример для ZIP:

```json
{
  "success": true,
  "name": "tasks-backup-20260912T123456123456Z.zip",
  "live_size_bytes": 131072,
  "backup_size_bytes": 12000
}
```

Если ошибка произошла после публикации, сообщение указывает созданный файл и незавершённую
синхронизацию либо очистку. Сохраняйте операторское окно, проверьте имя через `poise backup list`,
завершите указанную очистку и подтвердите пригодность копии штатным восстановлением с последующей
проверкой данных.

## Восстановление

```bash
poise backup restore --config PROJECT_JSON tasks-backup-20260912T123456123456Z.zip
```

Передайте точное имя файла из `backup list`, без каталога. Сохраните выбранный файл в `backups/`
рядом с целевой БД. Целевой файл БД может существовать или отсутствовать: восстановление
поддерживает оба состояния в обоих режимах.

До изменения целей инструмент читает и проверяет копию, включая обязательные части ZIP, целостность
сжатых данных и `PRAGMA integrity_check` SQLite-части. Затем подготавливает новые БД и материалы. В
комплектном режиме прежний namespace временно сохраняется рядом, устанавливаются материалы, а
последним переименованием заменяется БД. В SQLite-режиме заменяется подготовленный файл БД.

При обычной ошибке до замены БД возвращается состояние материалов перед попыткой; прежняя БД либо её
отсутствие сохраняется. Если откат материалов тоже завершился ошибкой, существовавший исходный
namespace сохраняется в указанном `previous`. Держите писателей остановленными, восстановите
исходный namespace из указанного пути либо его прежнее отсутствие по сообщению команды, затем
повторите `backup restore`. Временная исходная копия удаляется после успешной установки либо
успешного отката.

Замена БД и каталога материалов — последовательность файловых операций в остановленной установке.
Она не является общей транзакцией при аварийном завершении процесса или потере питания. После такого
прерывания сохраняйте операторское окно и повторите восстановление из того же целого комплекта.
После проверки восстановленных данных удалите временные каталоги прерванной попытки,
принадлежность которых этому восстановлению подтверждена.

Успешный результат:

```json
{
  "success": true,
  "name": "tasks-backup-20260912T123456123456Z.zip"
}
```

После успешного восстановления выполните SQLite `PRAGMA integrity_check` и `PRAGMA
foreign_key_check`, прочитайте комментарии и вложения через `task_feedback/read` и
`task_feedback/read_attachment`. Текст, идентификаторы вложений и исходные байты восстанавливаются
из копии; исходный файл, использованный при добавлении вложения, для чтения уже не нужен.

Если ошибка произошла после замены БД, команда сообщает, что комплект уже установлен. Сохраняйте
остановку писателей, проверьте SQLite и чтение вложений, затем завершите указанную очистку
временного пути. Материалы после этой точки остаются вместе с установленной БД.

## Срок жизни и удаление

Служебная копия нужна текущему шагу: после использования, проверки миграции или
завершённого восстановления ответственный агент сразу удаляет её через владельца.
[Срок жизни — один шаг](architecture/storage-lifecycle.md#срок-жизни-служебных-копий),
а не ожидание фонового задания. В примерах `PROJECT_JSON` задаёт выбранный проект,
`BACKUP_NAME` — одно точное имя из его каталога `backups`, без пути.

```bash
poise backup remove --config "$PROJECT_JSON" "$BACKUP_NAME"
```

`remove` удаляет только указанную копию; отсутствие после успешного удаления
обрабатывается идемпотентно: `success=true`, `removed=false`. Минимального срока
хранения нет. Действующее разрешение на сохранение защищает копию до своего
конечного срока; команда не предоставляет принудительную отмену такого решения.

```bash
poise backup prune --config "$PROJECT_JSON"
```

`prune` — аварийная страховка пропущенной очистки. Обычная копия, созданная этим
владельцем, становится возрастным кандидатом через **23 часа** по UTC-времени в
сгенерированном имени, включая равенство порогу. `ctime` из списка для этого не
используется. Предельные 24 часа не дают агенту права сохранять уже ненужную копию.
Неизвестное старое имя требует адресного решения владельца, а не догадки по `mtime`.
Отсутствующий каталог обрабатывается без создания копии или нового каталога.

Результат содержит `success`, списки `removed`, `retained`, `rejected`. При
частичном отказе код завершения 2; причина, фактическое наличие архива и
`continuation` относятся к точной копии. Успешно удалённые другие объекты не
восстанавливаются при повторе. Если архив удалён, а очистка его метаданных не
закончилась, повтор завершает только оставшийся допустимый шаг и сообщает,
что самого архива уже нет. Не называйте частичный исход успешной очисткой всего
шага.

Создание, восстановление, удаление, проверка срока и работа с разрешением используют
одного владельца ресурса резервных копий. Публичный потребитель `database_copy`,
включая миграции, удерживает защиту до конца чтения и очистки своей временной
распаковки. `remove` и `prune` ждут освобождения такого потребителя; исходный архив
сохраняется и для SQLite, и для ZIP. Эта защита служебных копий не отменяет
обязательного операторского окна остановки писателей для `create` и `restore`.

## Явное исключение срока хранения

Продление допускается только по действительному отдельному решению пользователя
о конкретной копии и конечном сроке. Оператор заранее располагает этим решением,
а не получает согласие из успешной проверки JSON или из примера ниже.

```bash
poise backup retain --config "$PROJECT_JSON" "$BACKUP_NAME" \
  --until "$VALID_UNTIL" --authorization-ref "$AUTHORIZATION_REF" \
  --expected-digest "$BACKUP_SHA256" --request-id "$REQUEST_ID"
```

| Вход | Что задаёт оператор |
|---|---|
| `VALID_UNTIL` | Конечный будущий момент ISO 8601 с часовым поясом, согласованный пользователем. |
| `AUTHORIZATION_REF` | Ссылку `task-feedback:<Task-ID>:<UUID-комментария>` на реально сохранённый источник решения того же владельца. |
| `BACKUP_SHA256` | Измеренный SHA-256 исходных байтов точной существующей копии. |
| `REQUEST_ID` | Стабильную идентичность одного запроса, сохраняемую при точном повторе. |

Существующий владелец материалов Task читает выбранный комментарий. Его JSON-объект
содержит `role=user`, дословный `text`, `project`, `backup_name`, `sha256` и
`valid_until`, соответствующие фактическому решению и указанным входам. Сама метка
`role=user` и авторская запись агента не создают пользовательского разрешения.
Автор источника и фактический оператор учитываются отдельно. Подмена проекта,
имени, байтов или срока и недоступный источник получают отказ до объявления
разрешения. Создание примера или тестовой fixture никогда не разрешает реальные данные.

Точный повтор сохраняет первоначальный срок, а не отсчитывает новый от часов
повторного запуска. Иные входы конфликтуют с существующим решением. После его
истечения обычная допустимость удаления возвращается с учётом потребителей.
Изменение или досрочная отмена решения требует отдельного законного перехода
владельца; у этого CLI нет `--force` или универсальной команды отмены.

Незавершённый `.<имя-копии>.retention.json.pending`, повреждённое содержимое,
существующий JSON `null`, иной не-объект или несовпадающие байты архива не означают
отсутствие решения: архив сохраняется, результат сообщает отказ. Это не успешное
удержание на неопределённый срок и не завершение шага. Пока исходный допуск ещё
применим, повторяют тот же `retain` с теми же входами для завершения публикации.
При истёкшем сроке, конфликте или неподтверждённом источнике владелец сначала
разрешает точное незавершённое состояние; замена срока, ручное редактирование
sidecar или выдуманная команда `reconcile` не являются штатным продолжением.
Записывают фактическую причину и сохраняют нужные данные до допустимого решения.

## Страхующий запуск по расписанию

Версионированные примеры
[службы](../config/maintenance/backup-retention.service.example) и
[таймера](../config/maintenance/backup-retention.timer.example) обращаются к тому же
`backup prune`. Их установка и изменение принадлежат настроенному внешнему
владельцу обслуживания окружения, включая выбранную версию поставки и каждого
действительного потребителя. Наличие этих файлов ещё не означает запущенный таймер.

Владелец заполняет `@POISE_COMMAND@` сохраняемой установленной командой Poise,
`@PROJECT_CONFIG@` — точным внешним файлом проекта, с корректным экранированием
для `ExecStart`; исходник из удаляемого Task-worktree не выбирают. Рабочие unit-файлы
и конфигурация остаются вне Git. Пример задаёт `Type=oneshot`, `OnCalendar=*:0/15`,
`OnBootSec=1min`, `Persistent=true` и ту же службу для таймера.

После разрешённого развёртывания владелец подтверждает реальный запуск `prune`,
его конечный код и эффект в выбранном проекте, состояние таймера, последний и
следующий запуск. Например, в фактически настроенной пользовательской службе
диагностические чтения включают:

```bash
systemctl --user show backup-retention.timer \
  --property=ActiveState --property=LastTriggerUSec --property=NextElapseUSecRealtime
systemctl --user show backup-retention.service \
  --property=Result --property=ExecMainStatus
```

Выключенный таймер, неуспешный запуск или недоступная среда означают невыполненное
операционное условие. Возобновление расписания не является гарантией работы на
выключенной машине. Даже исправное расписание не заменяет немедленное удаление
копии агентом после её шага.

## Справка

```bash
poise backup help
```

Справка перечисляет `list`, `create`, `restore`, `remove`, `prune`, `retain`,
оба режима хранения и условие остановки писателей.

## Резервная копия перед миграцией workflow snapshot

Операция `task-workflow-migrate` принимает точное `backup_name` ранее созданной публичной
копии. Создайте её через `poise backup create --config PROJECT_JSON`, пока ни один другой
writer не работает с Task DB, и сохраняйте до проверки результата миграции либо завершённого
восстановления. После этого ответственный агент сразу выполняет `backup remove` для точного имени
в рамках того же шага; ожидание фонового `prune` назначение копии не продлевает. Операция до первой
записи и
повторно внутри своей транзакции требует, чтобы полное состояние рабочей базы совпадало с
этой копией. Пошаговый операторский контракт приведён в
[руководстве по миграции](task-workflow-snapshot-migration.md).

Оба маршрута миграции workflow snapshots читают проверенную SQLite-часть через того же владельца
backup. Передавайте имя, полученное от `backup create`, для любого из двух форматов; материалы при
чтении миграционного снимка сохраняются на месте.
