# Маршрутизация разработки самой AI poise

Обновлено: **2026-10-16**.

## Подготовка инструкций по файлам

Общий режим skills/prepare получает инструкции по явно указанным файлам
настроенного проекта. Следующие разделы про SkillSelection и DevelopmentRouting
описывают отдельный специализированный режим разработки AI poise.
Оба режима сосуществуют; общий выбор не заменяет требования навыков этапа Task.

### Настройка и вызов

Нужны установленный Python Poise, явный каталог skills, корень инструкций,
действующий полный project manifest, Git checkout и отдельная policy.
Проект подготавливают или изменяют через
[публичного владельца конфигурации](project-setup.md#обновление-действующего-проекта).
prepare не требует Task, Sprint, bootstrap, caller session или Task DB.
Однако действующий загрузчик проверяет полный manifest, включая его обычную
конфигурацию: это не поддержка произвольного сокращённого manifest без Task plugins.

checkout должен быть корнем настроенного основного Git checkout либо его
зарегистрированным worktree с тем же Git common directory.
Корень checkout содержит применимые AGENTS.md и документы профилей;
отдельный instruction_root из --root содержит файлы навыков по путям каталога.
Сам --catalog задаётся независимо. Относительные CLI пути разрешаются от cwd;
для воспроизводимого вызова задавайте абсолютные пути.

Обезличенный образец:
[project-instructions.example.json](../../config/examples/project-instructions.example.json).
Выберите и заполните свою policy; рабочую конфигурацию храните вне VCS.
Образец не устанавливается автоматически и не является project manifest.

| Поле policy | Значение |
|---|---|
| schema | Ровно poise-project-instruction-policy-1. |
| version | Явная непустая строка версии политики. |
| universal_skills | Уникальные IDs каталога; обязательны для всех переданных файлов. |
| profiles | Явный список профилей, в том числе пустой. |
| profiles[].name | Уникальное непустое имя без двоеточия. |
| profiles[].paths | Непустой уникальный список относительных префиксов каталогов с завершающим /. |
| profiles[].baseline | Уникальные IDs обязательных навыков профиля. |
| profiles[].recommended_skills | Уникальные IDs рекомендованных навыков профиля. |
| profiles[].profile_file | Явный null либо конкретный относительный путь документа профиля в checkout. |

Все известные поля обязательны; пустые списки и null задаются явно.
Скрытых значений по умолчанию нет. Ссылки на skills должны существовать в каталоге.
Неизвестные опции конфигурации игнорируются без переписывания исходных значений,
включая вложенные расширения профилей. policy_sha256 учитывает полные исходные
байты policy, в том числе неизвестные опции. Это не разрешение добавлять поля
в строгие request/previous.

Подготовьте отдельный UTF-8 JSON-файл запроса ровно с шестью полями:

| Поле request | Значение |
|---|---|
| operation | prepare |
| project_config | Абсолютный путь действующего полного project manifest. |
| checkout | Абсолютный путь выбранного Git checkout. |
| policy | Абсолютный путь выбранной policy. |
| paths | Непустой список конкретных относительных файлов. |
| previous | null при первом вызове; полный предыдущий успешный или частичный ответ при обновлении. |

paths использует POSIX-разделитель /. Абсолютные пути, glob, обратная косая черта,
двоеточие, пустые сегменты, . и .. отклоняются. Повторы объединяются,
результат сортируется. Сам рабочий файл может ещё не существовать:
выбор правил предков строится по его пути.

В примере ниже оператор заранее задаёт абсолютные poise_python, skill_catalog,
skill_root и packet; packet содержит заполненные поля из таблицы:

~~~bash
poise=( "${poise_python:?Укажите установленный Python Poise}" -I -B -m poise )
"${poise[@]}" skills --catalog "$skill_catalog" --root "$skill_root" < "$packet"
~~~

Для запуска из исходников явно выберите Python и PYTHONPATH к src этой поставки
без -I; -I игнорирует PYTHONPATH. Не подменяйте установленную поставку каталогом
проверяемого приложения. Команда читает файлы, не исполняет команды из их текста
и не изменяет lifecycle или рабочую конфигурацию.

### Выбор, содержимое и готовность

Универсальные навыки обязательны для всех paths. Профиль совпадает по любому
directory prefix; baseline обязателен, recommended_skills рекомендованы,
ненулевой profile_file обязателен. Для каждого рабочего файла выбираются
существующие AGENTS.md в его каталогах-предках, включая корень.
Отсутствующий необъявленный AGENTS.md не создаёт отдельного обязательства.

Результат имеет schema=poise-project-instructions-1 и поля status, project,
checkout, instruction_root, policy_sha256, paths, materials, diagnostics, delta.
Каждый материал содержит:

| Поля | Смысл |
|---|---|
| kind, id | rule с ID пути AGENTS.md; profile с именем профиля; skill с ID каталога. |
| root, path | checkout для правил/профилей; instructions для skills; конкретный относительный путь. |
| scopes | Рабочие файлы, к которым относится материал. |
| required | Обязательность применения. |
| reasons | Основания выбора. |
| available | Удалось ли прочитать и декодировать материал. |
| sha256, content | SHA-256 исходных байтов и полное UTF-8 содержимое; оба null при недоступности. |

Идентичность материала: kind:id:root:path. Материалы сортируются по
(kind, id, root, path), scopes/reasons — уникальные сортированные списки.
При нескольких совпадениях scopes/reasons объединяются, required становится
true при любом обязательном назначении. Причины: universal,
profile:имя:baseline, profile:имя:recommended, profile:имя для документа профиля,
ancestor:рабочий-путь для правила.

BODY и SHA происходят из одного чтения байтов; CRLF и Unicode сохраняются.
Недоступный выбранный материал остаётся в ответе со своей областью и ролью.
Нет подстановки пустого текста или тела из previous.
Отсутствующие невыбранные файлы навыков не блокируют этот режим.

ready / exit 0 означает доступность обязательных инструкций.
needs_inputs / exit 1 означает отсутствие хотя бы одного обязательного материала.
Недоступная рекомендация сохраняет ready и получает диагностику.
Каждая запись diagnostics содержит code=missing_required_material либо
missing_recommended_material, key=идентичность и action=restore:root:path.
Исправьте указанный материал и повторите запрос.

Агент читает content обязательных материалов и применяет правила в scopes;
рекомендации рассматривает отдельно. ready не подтверждает ознакомление модели,
выполнение проверок, приёмку Task или автоматическое соблюдение инструкции.
Полный машинный stdout содержит один JSON без внутреннего сокращения.
Ограниченное представление для агента и ссылка на полный сохранённый ответ
принадлежат [общему вызывающему владельцу](../workflows/runner.md#три-представления-вывода).

### Обновление и previous

После изменения рабочих paths, policy или инструкций повторите prepare,
передав полный прежний ответ в previous. Данные читаются заново; прежний ответ
нужен только для сравнения. Он должен относиться к тем же project, checkout,
instruction_root и соответствовать строгой схеме, порядку, хешам содержимого,
availability, status и diagnostics. Сокращённое представление агента для этого
не подходит; rejected-ответ также не является previous.

При первом запросе delta=null. Затем delta содержит отсортированные added/removed
идентичности и changed с полями key и fields. Сравниваются available, content,
reasons, required, scopes, sha256, включая рекомендованные материалы.
При неизменных материалах все три списка пусты. policy_sha256 может измениться
из-за расширения конфигурации при пустой delta. Это сравнение материалов,
не журнал Task и не доказательство прочтения агентом.

### Отказы входной границы

Штатный rejected-ответ содержит ровно schema, status=rejected и
error с code, field, action; exit 2. Основные диагностируемые условия:

| Условие | code / field / action |
|---|---|
| Некорректный JSON или форма request | invalid_request / request / provide:request |
| Нет policy либо она null | invalid_request / policy / provide:policy |
| Некорректное обязательное абсолютное поле | invalid_request / имя-поля / provide:имя-поля |
| paths имеет неверный тип | invalid_request / paths / provide:paths |
| Пустые или неканонические paths | invalid_paths / paths / provide:paths |
| Policy не читается | unreadable_policy / policy / restore:policy |
| Неверная policy, ссылки skills или metadata каталога | invalid_policy / policy / correct:policy |
| Manifest не загружается | invalid_project / project_config / provide:project_config |
| Checkout не привязан к настроенному репозиторию | project_binding / checkout / select:checkout |
| previous не соответствует договору | invalid_previous / previous / provide:previous |

Это диагностика перечисленных поддержанных условий, не универсальное перехватывание
всех исключений окружения. Ошибка shell до запуска CLI не является ответом prepare.
У прежних list/read/policy/validate сохраняются собственные metadata envelopes.

### Совместное использование и происхождение

Общий prepare и прежние операции каталога используют существующий
dispatcher команды skills: выбранная операция исполняется один раз.
Legacy list/read/policy/validate сохраняют строгую предварительную проверку файлов
каталога; prepare использует metadata и наблюдает доступность выбранных материалов.
Специализированный DevelopmentRouting вызывается через прежний
route_development.py и остаётся владельцем своих stage/facts/checks. Общий prepare автоматически к native hooks или bootstrap
не подключён; полная миграция Task plugins не заявлена.

Повторно использованы ordered deduplication, reason aggregation, universal/profile
selection, ancestor rules и file delta из ERP
ai-assistant/agent/effective-policy-manifest.py, commit
16c5b906615e57a5b5f89b495c42b79f51eab87e.
Адаптации: явные POSIX file scopes, обязательные/рекомендованные материалы,
каноническая identity и сравнение шести публичных полей.
ERP runtime, Task machinery и рабочие настройки не запускаются и не переносятся.

## Расширения конфигурационных документов

Файловый загрузчик игнорирует неизвестные опции каталога навыков, условий выбора,
маршрутизации, тестовых пакетов и архитектурной политики, включая вложенные
объекты опций. Исходные файлы не переписываются. `configuration_digests` и
`policy_sha256` учитывают полные исходные байты, в том числе неизвестные опции:
неизменное поведение не означает совпадения происхождения конфигурации.

Обязательные известные поля, версия схемы, значения и ссылки на skills, facts,
packages и handlers проверяются как прежде. Динамические имена в `handler_facts`
не являются неизвестными опциями. Строгие доменные `parse` и входные пакеты
инструментов не расширяются; проекция конфигурации выполняется только на границе
её загрузки. Общий контракт —
[опции конфигурации](project-setup.md#удаление-устаревшего-параметра-transfer).

## Декларативные условия выбора skills

`config/development/skill-selection.json` — метаданные C003, а не ERP profile-документ
и не обязательная схема чужого репозитория. Источник identity/purpose/class —
существующий [SkillCatalog](skill-catalog.md). Инструкции и команды не копируются.

Формат `ai-poise-skill-selection-1` явно ограничен `subject=ai-poise`:
`facts` перечисляет допустимые факты; `rules` содержит уникальный `id`, числовой
`priority`, список `skills` и `when`. Условие состоит из `stages` (точные ID этапов),
`paths_any` (относительные glob-пути), `facts_all` (все перечисленные факты).
Пустое условие не ограничивает соответствующую ось; непустые оси соединяются через AND.
Порядок приоритетов возрастающий, затем ID; дубликаты выбранных skills удаляются.
Факт `review`, `recovery`, `release` и т. п. сообщает вызывающая операция, а не
угадывает классификатор из текста запроса или имени ветки.

Каждый skill каталога либо упомянут в selection rules, либо явно указан в `excluded`
с причиной. Исключение из автоматического выбора **не удаляет skill**. Например,
Laravel/Vue/Vitest/PHPUnit остаются поставленными инструкциями, но не выбираются для
текущей Python-кодовой базы AI-poise. Нет автоматического наследования технологий ERP
или переноса этой конфигурации на произвольное разрабатываемое приложение.

Для `config/**` правило выбирает поставленный `project-configuration`, сохраняя
общие foundation skills. В каталоге он объявлен как working уровня 1 с
ответственностью `project-configuration`; проектная декомпозиция использует
соответствующую узкую ответственность. Для иных путей это правило не выбирает
навык. Его инструкции ведут к существующим публичным владельцам настройки проекта.

Уже поставленные `harness-recovery` и `i-have-adhd` явно учтены в `excluded`
автоматического специализированного выбора. Первый применяется при подтверждённом
отказе Poise, мешающем разрешённой работе; обычный факт восстановления сам по себе
этого не доказывает. Второй обязателен по явному `USE` в корневом `AGENTS.md`;
исключение из этого selector не отменяет данную инструкцию.

`SkillSelection` проверяет неизвестные skills/facts, дубли и некорректные пути, но
сам не выполняет routing. Единственный потребитель условий и владелец выбора — C004.
Загрузка metadata сама по себе не означает запуск проверок, загрузку всех references
или изменение lifecycle. Факты и неизвестные пути должны оставаться видимыми в результате.

## Единый router и прямой вызов

`DevelopmentRouting` — единственная композиция выбора. Доменные `SkillSelection`
и `RoutingPolicy` проверяют декларации и сопоставляют факты; файловый адаптер читает
метаданные, scoped AGENTS и выбранные SKILL.md. Ни инструкции, ни команды проверок
не переписываются в routing policy.

Прямой инструмент `tools/route_development.py` получает через stdin точный объект:

```json
{
  "checkout": "/absolute/path/to/an-ai-poise-copy",
  "stage": "implementation",
  "handler": "produce",
  "scope_paths": ["src/poise/modules/skills/**"],
  "changed_paths": ["src/poise/modules/skills/catalog.py"],
  "facts": [],
  "required_methods": [],
  "registered_methods": [],
  "result_contract": {"sections": ["report"]}
}
```

Параметры `--catalog`, `--selection`, `--policy`, `--packages` задают конкретные пути
к `.agents/skill-catalog.json`, `config/development/skill-selection.json`,
`config/development/routing.json`, `config/testing/test-packages.json` работающего
экземпляра. Относительные CLI-пути вычисляются обычным способом от cwd процесса.
`checkout` — только проверяемая копия **AI-poise**, подтверждённая `project.name`;
это не место поиска executable, hook или operational configuration. Из копии читаются
только применимые `AGENTS.md` и выбранные `SKILL.md`, не все справочники. Для glob scope
читаются AGENTS предков его буквального префикса, а не все вложенные документы.

`known_paths` описывает распознаваемые области; `handler_facts` декларативно добавляет
факты для обработчика; `checks` сопоставляет пути с ID **существующих** тестовых
пакетов AI-poise. Неизвестные packages отклоняют конфигурацию до чтения копии.
Неизвестные факты, пути, обработчик, отсутствующие обязательные методы или skills
попадают в `missing_inputs`. Не возникает fallback на full suite.

`ready`/exit 0 означает, что выбор получен без перечисленных пропусков, **не** что
код проверен. `needs_inputs`/exit 1 сохраняет частичный результат и диагностику;
ошибка формы/config/path даёт `rejected`/exit 2. `required_methods` никогда не теряются
и не заменяются `suggested_packages`; обе коллекции содержат разные виды ID.
`checks.executed` всегда false. Рекомендация пакета не доказывает полноту тестов:
исполнитель выбирает минимальные task-specific проверки и штатный bounded smoke.

## Подключение к bootstrap и обновлению контекста

Необязательный раздел `development_routing` существующего project manifest содержит
ровно `catalog`, `selection`, `policy`, `packages`: непустые конкретные файловые пути.
Пути относительно manifest разрешаются существующим способом, абсолютные остаются
абсолютными. Настройка относится только к разработке AI-poise. Без раздела остальные
проекты работают как прежде; никакой общей миграции конфигурации нет. Для установки
раздела использовать существующий [редактор проекта](project-setup.md#обновление-действующего-проекта), не ручное
изменение managed-файла. Единственное новое поле разрешено добавить целиком через
`manifest_edits` с `path=["development_routing"]`; revision, quiescent-project и
атомарная публикация остаются прежними. Редактор валидирует форму раздела; доступность
метаданных проверяет загрузка router. Подключение следует проверить прямым вызовом
до bootstrap. Это не разрешение добавлять произвольные отсутствующие поля. Поставленный персональный project manifest автоматически
не изменяется: его пути и окружение здесь не установлены и не проверены.

После явного подключения bootstrap возвращает `development_route` через того же
владельца, что прямой инструмент. Он использует фактический текущий этап, его
`allowed_paths`, накопленный Git diff от исходного `base` Task (staged/unstaged,
переименования как удаление/добавление) и untracked-файлы. Проверки поступают из
существующего `_select_checks`, включая автоматические обязательства, а не из второго
реестра методов. Без dedicated worktree используется **уже существующее** поведение:
конкретный настроенный checkout проекта. Размещение worktree не меняется.

Обновить результат после изменения файлов или для дополнительных явных фактов можно
через тот же публичный work packet:

```json
{"operation":"routing","input":{"facts":["self_review"]},"messages":[]}
```

Текущая Task должна принадлежать этой сессии. Операция не изменяет её version, stage,
claim, acceptance или submission. Явные дополнительные facts относятся к одному
вызову; следующий bootstrap заново выводит факты из своего контекста, не наследует
скрыто старые overrides. Без configured router запрос отклоняется.

## Производный снимок и воспроизведение

Результат содержит исходные факты, IDs/пути/SHA-256 правил и skills, digest четырёх
конфигураций, форму результата этапа и `route_digest`. Одинаковые факты и байты дают
одинаковый результат. Время, имя сессии и случайный ID в digest не добавляются.

`--snapshot /concrete/path/route.json` явно сохраняет атомарный снимок с mode 0600;
bootstrap/refresh заменяет один `development-routing.json` в существующем runtime
каталоге своей сессии. Это **не ledger и не новый lifecycle**. Возвращённый route
можно сохранить вместе с обычным handoff/checkpoint; временный файл сам по себе не
обещает пережить очистку runtime. Прямой вызов без `--snapshot` ничего не записывает.

`read_snapshot` проверяет schema и digest исторического результата; это контроль
целостности, не криптографическая подпись. Он не объявляет старый снимок актуальным
для нового содержимого: для этого нужно повторно вызвать router. После загрузки
операционная конфигурация фиксируется в экземпляре сервиса; её изменение требует
нового экземпляра. Снимок не обеспечивает транзакционное чтение всех файлов при
параллельном редактировании; не следует выполнять refresh одновременно с записью
проверяемых правил. Пути и scope не меняют разрешение кода работающего Poise.

## Выбор проверок по входам тестовых пакетов

Обновлено: **2026-09-16**, C017. Тот же `DevelopmentRouting` дополняет маршрут
`test_impact`, полученным от существующего `AiPoiseTestPackages`. Вход — **конкретные
относительные пути diff** в явно указанной копии AI-poise; `scope_paths` остаётся
плановой областью и может содержать glob, `changed_paths` — только файлы, без glob.
Переименование передаётся двумя путями (старый/новый); удалённый файл сопоставляется
с декларацией даже после исчезновения с диска. Symlink за пределы проверяемой папки
отклоняется. Метаданные инструментов по-прежнему берутся из явно переданных конфигураций,
а не ищутся заново в рабочей копии.

Сопоставляются три категории каталога test packages: `source`, `tests`, `fixtures`. `*` не пересекает каталог, `**` допускает ноль или больше каталогов.
`direct_packages` перечисляет непосредственных владельцев изменённого входа;
`integration_packages` — их явно объявленные соседние границы **одного шага**.
Рекурсивное подтягивание всего графа отсутствует. Общая фикстура затрагивает все
пакеты, которые её действительно объявили. `reasons` сохраняет файл, пакет,
владельца, категорию и совпавший pattern; `integration_reasons` сохраняет источник
добавления соседнего пакета.

`checks.suggested_packages` — объединение impact и существующих routing-деклараций.
`checks.required_methods` содержит прежние обязательные методы Task, включая методы
для нового поведения. Impact не отменяет их, не регистрирует команд и не выдаёт
рекомендацию за покрытие требований. Неизвестный в package map путь даёт
`unmapped_test_input:<path>` и `needs_inputs`, даже внутри известного `src/**`.
Это требует уточнения существующего каталога/точного Task check, а не запуска full suite.

Результат пересчитывается каждым direct/refresh/bootstrap-вызовом по актуальным
фактам; при изменении operational metadata создаётся новый экземпляр router.
Исторический route snapshot не подтверждает новые байты. Для **явно выбранного**
пакета используется прежний `tools/run_ai_poise_test_package.py --root /concrete/path
--package <id> --timeout <seconds> --fresh`, за которым остаются прежние cache и
`RegisteredCheckRunner`. Прямой routing сам ничего не запускает и не создаёт кэш.
Этот протокол не навязывается приложениям, которые разрабатываются через Poise.


## Авторский архитектурный gate

C029.4 использует тот же `DevelopmentRouting`, не второй router. Необязательное поле
operational routing policy `authoring_boundary_gate` содержит конкретный `policy` и
явные `handlers`. Поставленная конфигурация выбирает Python boundary rules AI-poise
для `produce`. Отсутствующая регистрация не объявляется пройденной проверкой; отсутствующий
сам policy-файл или неверная регистрация отклоняют загрузку, а не выключают gate молча.

Gate запускается перед авторским submission, не при выборе маршрута. Ошибка не меняет
Task/claim/stage и исправляется повтором той же сдачи. Проверяемая рабочая папка не
подменяет operational configuration. Подробный контракт, точные исходы и ограничения:
[проверка архитектуры перед авторской сдачей](../workflows/architecture-boundaries.md#проверка-архитектуры-перед-авторской-сдачей).
