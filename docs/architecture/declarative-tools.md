# Декларативные пакетные инструменты AI poise

Обновлено: **2026-09-06T21:26:17+05:00**.
Статус: принятые требования; config editor и прямой work API реализованы в DDD-04A/04B. Sprint и универсальные runtime adapters остаются следующими срезами.
Основание: пользовательское решение после DDD-04. Документ уточняет интерфейс ввода, но не меняет бизнес-процессы 13 типов целей.

## 1. Архитектурный инвариант
Агент передаёт содержательный результат и желаемые изменения объектов. Инструмент выполняет всю определённую механику: создаёт из шаблонов, рассчитывает пути, валидирует, сохраняет, регистрирует связи, обновляет проекции и формирует ответ. Агент не редактирует обслуживаемые AI poise конфиги, task/sprint/runtime-данные, SQL, технические индексы, hashes или результатные файлы напрямую.

Один логический пакет изменений — один вызов прикладного инструмента, сколько бы секций, точек трассировки, методов или файлов он ни содержал. Одиночный элемент — пакет из одного элемента. Чтение поддерживает коллекцию адресуемых объектов. Это не требование объединить независимые инженерные решения: после нового наблюдения или пользовательской инструкции начинается следующий осмысленный пакет.

Нативные инструменты целевой кодовой базы сохраняются: исходники, тесты и проектная документация изменяются предназначенными для них IDE/patch-инструментами. Их групповое использование предпочтительно там, где оно поддерживается. Новое правило не требует универсального редактора программного кода внутри AI poise и не разрешает обходить AGENTS целевой codebase. Изменения этих файлов AI poise получает через Git. Генерируемые AI poise файлы и рабочая БД обслуживаются только через его API.

Прямой доступ к SQLite запрещён агенту; его выполняет infrastructure repository. Внутри инструмента filesystem/SQL операции допустимы и обязательны. Запрет касается ручного обслуживания представления агентом, а не I/O-реализации инструмента.

## 2. Единственный прикладной вход, разные доменные владельцы
Ниже логические предметные имена; точный исполняемый CLI DDD-04B описан в batch-work.md.

| Прикладной сценарий | Данные агента | Что делает инструмент |
|---|---|---|
| `GoalConfigCommands.apply_batch` | Цель создания/изменения типа, явный шаблон для создания, набор изменений объектов | Строит полный кандидат процесса, проверяет весь граф и ссылки, сериализует и публикует согласованный конфиг |
| `TaskCommands.submit_batch` / общий `verify` | Изменения секций, проверки, трассировка, findings/resolutions, аргументы, сообщения коммита, artifact intents/пути | Принимает один кандидат через Task API; сохраняет и выполняет предусмотренную механику этапа |
| `SprintCommands.apply_batch` | Проект спринта, дочерние контракты, зависимости, секции | Валидирует итоговый набор, публикует/изменяет через владельца Sprint; реализация DDD-05 |
| `ArtifactCommands.apply_batch` | Создать из шаблона; создать из содержания; принять существующий путь | Вычисляет разрешённые пути, создаёт файлы и регистрирует ID, владельца и технические свойства |
| `Queries.read_batch` | Список секций/объектов/диапазонов | Возвращает один компактный ответ и адресуемые подробности |
| Handoff, cancel, accept, project setup | Одно предметное решение и явный scope | Все механические действия остаются внутри сценария, не требуют цепочки вспомогательных вызовов |

Общий `BatchCommandPipeline` отвечает за envelope, привязку к session/work, идентичность операции, проверку формы, общий отчёт и journal. `GoalTypeDefinition`, Task, Sprint, ArtifactRegistry и InteractionLedger владеют своими правилами. Общего метода «изменить любую таблицу/файл» не вводить; SQL не появляется в runner/handlers/CLI.

Детерминированные операции делегируются штатным библиотекам и существующим портам. Декларативность не означает, что LLM-команда превращается в произвольную Python-программу, и не требует собственного языка программирования условий.

## 3. Пакет изменения конфига типа цели
Инструмент обслуживает независимый полный process pack. Пакет содержит выбранный goal type, режим create/change, исходную revision/digest при change и декларативные изменения по устойчивым ID. Рабочий project/session-контекст не вводится повторно, если он уже известен.

Поддерживаются создание/изменение/явное удаление стадий, секций, правил содержимого, точек трассировки, evidence plans, переходов и шаблонов доклада. Допускается полный желаемый объект вместо множества мелких операций. Не требуется JSON Patch по физическим offsets или diff файлов.

Пример содержательного пакета: добавить секцию «план обратного изменения»; сделать её обязательной на implementation; добавить проверку этой секции в pre; добавить к inspection требуемое решение. Это один вызов, а не четыре ручных изменения файлов.

Проверять окончательный кандидат, а не отклонять временно неразрешимые ссылки в середине пакета. Создание этапа и перехода на него допустимо в одном пакете независимо от порядка их перечисления. Конфликтующие изменения одного свойства в одном пакете не получают неявного last-write-wins: возвращается точный конфликт до публикации.

При change неперечисленное поле сохраняет действующее значение исходной revision. Это сохранение известных данных, не default. При create используется только явно выбранный самодостаточный шаблон и явные значения агента. Поле, которого нет ни в этом шаблоне, ни в пакете, остаётся missing и блокирует публикацию. Нет автопоиска шаблона, наследования чужого goal type, подбора defaults или fallback.

В шаблоне могут быть все заранее принятые значения процесса. Его явный выбор означает принятие этих значений; фиксируются ID, revision и digest шаблона. Placeholder не превращается в рабочую политику. Созданный pack полностью материализуется и далее независим от шаблона и других pack. Изменение шаблона не меняет уже созданные задачи.

Сервис проверяет как минимум форму, обязательность значений, handler IDs, ссылки графа, выходы и авторов полей, допустимые циклы/выход и лимиты, требования содержимого. Он не оценивает инженерную разумность нового процесса вместо агента.

Стандартное применение: собрать → проверить → сгенерировать → опубликовать → вернуть diff-summary и новую revision. Отдельные preview/validation доступны по смысловой потребности, но нормальный процесс не требует после каждого update отдельного generate/validate/publish. Ошибки пакета собираются совместно с адресами объектов; нельзя вынуждать LLM исправлять только первую выявленную missing-ссылку сотней вызовов.

При отказе действующий pack не меняется частично. Файлы подготавливаются инструментом в закрытом staging, активируется только полный согласованный результат. Общая атомарность Git, файлов и SQLite не обещается: шаги внешнего сохранения имеют явный receipt/recovery; неизвестный исход не повторяется вслепую. В первом срезе достаточно одного выбранного pack за вызов с множеством изменений; не строить распределённую транзакцию всех проектов.

Изменение process pack не мигрирует задачи и не меняет snapshot активной stage. Изменение требований действующей задачи — отдельный санкционированный сценарий Task. Конфиг редактируется только когда это входит в порученную работу или явное разрешение пользователя; пакетность не разрешает ослаблять проверки по желанию агента.

## 4. Создание артефактов
Три допустимых способа в одном API:

- известный шаблон и его параметризованное содержание;
- полное готовое содержание, когда шаблон не несёт пользы;
- путь существующего результата, созданного другим инструментом.

Для создания задаются область runtime/task/sprint, относительное имя либо явно сконфигурированное правило имени и содержание/шаблон. Владелец выводится из текущей привязки; при отсутствии task нельзя писать в task root. Инструмент вычисляет физическое расположение, создаёт каталоги/файл, проверяет границы, назначает ID и регистрирует технические сведения.

Для регистрации уже существующего артефакта по-прежнему нужен только путь, без назначения, описания, hash или иных деклараций. Внутренний ID возвращает AI poise. Параметры генерации не становятся новой обязанностью описывать существующий файл.

Применяются прежние ограничения symlink/выхода за root, повторной регистрации и неизменности сохранённого evidence. Для нового содержания существующего артефакта создаётся явная новая редакция; нельзя менять байты под прежним immutable receipt. Task/sprint-артефакты не расползаются по временным каталогам. Полезные runtime-результаты инструмент сохраняет у долговременного владельца до очистки.

Получение отчётов, DB sections, stage result, наборов parser views, handoff и других стандартных результатов должно использовать этот общий генератор/сериализатор либо специализированный адаптер через него. Не нужны отдельные CLI-вызовы create-directory, write-file, calculate-hash, register-artifact.

Бинарный результат обычно приходит из другого инструмента как путь/файловая ссылка, а не копируется моделью в base64. Содержательный автор текста, схемы или теста остаётся агентом; инструмент не заменяет инженерное решение шаблонной болванкой.

## 5. Ввод результата этапа без ручного файла
Будущий `verify` принимает семантический batch напрямую из tool payload/stdin и сам материализует техническое представление при необходимости. Bootstrap возвращает компактную схему и подготовленную форму/контракт, а не обязательное поручение редактировать result_path нативным редактором.

Можно одним пакетом создать артефакты, заполнить секции, зарегистрировать методы, обновить точки трассировки и завершить этап. Требующие рассуждения продолжения observe/check сохраняются: новые факты → новый аргумент → один CONTINUE того же этапа.

Файловый вход возможен, если файл уже создан инструментом. Подготовка такого файла вручную не должна быть обязательной предшествующей операцией. Идентичный повтор не создаёт новые layers/artifact IDs. Изменение проверяемого кода при прежнем семантическом пакете не мешает новой проверке, как в DDD-04.

## 6. Пределы пакетности и ошибок
Размеры пакета, лимиты исполнения, строки и bytes вывода задаются явно. Внутренние порции выполняет инструмент, а не агент. Ограниченный вход не называется «безлимитной атомарной операцией на 100500 записей»; при явном превышении возвращается понятный отказ без частичной business mutation.

Частичная обработка не должна выдаваться за полное применение. Business updates Task/Sprint выполняются одной UoW; для внешних файлов/команд статус отражает подготовку и завершение. Команды не запускаются лишь потому, что строка появилась внутри содержимого артефакта.

Отчёт содержит результат, количество принятых объектов, адреса ошибок, актуальную revision и дальнейшую содержательную работу. Большие подробности адресуемы; агент не выполняет ручной контроль каждого элемента. Inspector по-прежнему оценивает достаточность содержания, а не механическую сохранность файлов.

## 7. Граница поставки и внедрение
В DDD-04 эти API ещё отсутствуют: CLI читает result file, process config поставляется JSON, artifacts принимает существующие пути. Ни этот документ, ни обновление skill не делают новые вызовы исполнимыми.

Следующий срез **DDD-04A** создаёт пакетный редактор process config. **DDD-04B** вводит прямой пакет результата/генерацию артефактов и первый сбор событий пользовательских сообщений. Затем **DDD-05** использует общую библиотеку при создании задач и спринтов.

До поставки нужного инструмента не выдавать ручное редактирование конфигов/БД за штатный новый интерфейс. Разработка самого инструмента и его исходных шаблонов ведётся обычными coding tools по TDD; новые рабочие данные агента после его поставки — через API. Текущие demo-скрипты остаются примерами прежнего runtime, а не доказательством выполненной автоматизации.

## Поставленный прямой вход DDD-04B
Обновлено: **2026-09-06T21:22:42+05:00**.

`python -m poise work` реализует direct packet для task bootstrap/verify/CONTINUE, генерируемых артефактов и batch show. Шаблон результата возвращается объектом; агент не пишет/редактирует operational result JSON. `artifacts`-операция сама регистрирует пути, а verify может одновременно принять созданные файлы и все семантические изменения. Одинаковый файл не требует hash/ID от агента.

`messages` входит в тот же пакет. Поля привязки вычисляет инструмент. Coverage partial/unavailable: автоматического захвата всех сообщений ChatGPT пока нет. Границы и точная грамматика: [batch-work](../workflows/batch-work.md). Прежние формулировки будущего времени описывают общий целевой контракт; для фактической реализации используется [статус](implementation-status.md).

## Поставленное обновление живой project configuration

Обновлено: **2026-09-12**.

`python -m poise project-config --settings <project-setup-settings>` принимает один
`project-config-update-1` и через `ProjectConfigCommands` публикует валидированный полный
кандидат действующего project manifest/process snapshots. Это отдельный сценарий от
`GoalConfigCommands`: внутренние process changes по-прежнему строит `GoalTypeDefinition`, а
project route координирует общую revision, несколько файлов, readiness и durable recovery.

Операция не является generic file editor: structural roots имеют отдельных владельцев,
state переносится только явным relocation protocol, активные Task сохраняют собственные
snapshots. Точная грамматика, CLI, receipt/retry и ограничения relocation описаны в
[подготовке проекта](../configuration/project-setup.md#обновление-действующего-проекта).
Quiescence считает `completed`, `cancelled` и `superseded` terminal состояниями. Первый
запрос не присваивает себе и не удаляет уже существующий deterministic staging; право на
очистку частичной staging-копии появляется только у exact replay с matching pending receipt.
