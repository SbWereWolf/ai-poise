# Пакетная подготовка проекта и анкета

Обновлено: **2026-10-26**.

## Назначение

Согласованная целевая схема данных и конфигураций, карта подтверждённых
потребителей и порядок миграции описаны в [размещении ресурсов](storage-layout.md).
Она отделяет текущую поддержку от изменений спринта: документирование схемы
не означает переноса данных или появления новых параметров генератора.

Получить независимый полный конфиг проекта и выбранные workflow snapshots без ручного
редактирования файлов. Это подготовка окружения, не создание Task/Sprint, не выполнение
бизнес-этапа и не разрешение на изменение целевого приложения.

Объявленные локальные файлы приложения из предоставленного снимка восстанавливает
[отдельная команда local-assets](local-assets.md#назначение-и-владельцы).
Она не публикует project manifests и не выбирает значения owning repair.

Публикуемый project manifest выбирается внутри явно заданного AI poise root.
Пути шаблонов и `workflow_sources.*.path` задаются в настройках: абсолютные используются
как указаны, относительные вычисляются от setup `root`. Графы нового проекта
записываются по `workflows.*`: абсолютный путь используется как указан, относительный —
`Path(project_manifest).parent / workflows.<goal_type>`. Каталог данных может находиться
вне каталога конфигов и setup root.
Настройки самого генератора: `config/project-setup.json`. Корень задан в этих настройках
относительно файла, а не угадан по текущему каталогу. Mutable project state может находиться
вне AI poise root: `paths.state` задаётся явно и может быть абсолютным. Относительное значение
по-прежнему разрешается относительно project manifest. Относительные пути Task storage
разрешаются внутри выбранного `paths.state`. `paths.requirements_database` и
`paths.requirements_lock` принимают также явные абсолютные пути вне state; оба файла
должны различаться между собой и с Task DB/lock, в том числе не ссылаться на те же
существующие файлы. Внутри `git.repository` оба пути должны быть исключены из Git и не
отслеживаться им; вне репозитория проверка Git для этой пары не требуется. Полные условия
задаёт [владелец размещения](../workflows/requirements-registry.md#владение-и-явные-пути).
Источники миграций задаются тремя отдельными обязательными строковыми полями:
`paths.requirements_schema_migrations` — DDL в приложении управления задачами;
`paths.requirements_data_migrations` — DML в документации проекта;
`paths.requirements_schema_file` — один актуальный SQL-bootstrap в документации.
Пропущенные значения отклоняются; неизвестные ключи конфигурации игнорируются.
Примеры используют явные абсолютные пути; относительные пути миграций разрешаются от
каталога загруженного manifest проекта. Публичные операции реестра используют эти ресурсы
приложения независимо от Task; отдельная подготовка миграций при завершении фактической Task
описана в [границе завершения](../workflows/requirements-registry.md#склейка-миграций-задачи).

Это проверка размещения, не перенос хранилищ. У `paths.worktrees` есть отдельные [правила
размещения](#рабочие-деревья-внутри-репозитория).

## Проверка согласованности проекта

`poise project check` проверяет явно выбранную конфигурацию до работы с Task.
Установка, project manifest, хранилища и обслуживаемый репозиторий могут находиться
в разных каталогах. Источник запущенного Poise не становится целевым репозиторием
из-за текущего каталога, а совпадение имени проекта не доказывает совпадение базы Task.
Конкретное рабочее дерево задачи определяется её процессом и владением; оно не является
дополнительным полем ответа этой проверки.

Запустите команду через Python выбранной установки с её установленным модулем `poise`.
`--settings` выбирает настройки проектных инструментов этой установки; `config_path`
в JSON выбирает проверяемый manifest напрямую. Наличие manifest в registry не требуется.
Команда не требует текущей Task или native-сессии, не создаёт claim, worktree, хранилище
или запись в истории и не выбирает другой проект при отказе.

```bash
python -m poise project check --settings /opt/poise/config/project-setup.json <<'JSON'
{
  "schema": "project-preflight-1",
  "config_path": "/srv/poise/projects/demo/project.json",
  "project_id": "demo",
  "task_id": null,
  "probe_repository": true,
  "commit_message": "Change\n\nReason"
}
JSON
```

Пути и сообщение в примере — значения для замены на фактически выбранные; сообщение
проверяется по политике выбранного manifest. Запрос содержит ровно шесть полей:

| Поле | Значение |
|---|---|
| `schema` | Ровно `project-preflight-1`. |
| `config_path` | Явный абсолютный путь к manifest, непустая строка без NUL. |
| `project_id` | Непустой идентификатор без NUL; должен совпасть с `project` manifest. |
| `task_id` | Непустая строка без NUL для поиска в выбранной Task DB либо явный `null`. |
| `probe_repository` | Явный boolean; `false` оставляет Git непроверенным. |
| `commit_message` | Строка для существующей commit policy либо явный `null`. Пустая строка — реальный кандидат, а не пропуск. |

Ввод — один JSON-объект в UTF-8 в пределах `max_input_bytes` из settings. Дубли ключей,
некорректный JSON, лишние/пропущенные поля и неверные типы отклоняются. Значения не
подставляются из другой конфигурации или переменных окружения.

### Результат и границы готовности

Структурированный ответ содержит ровно `schema`, `status`, `ready`, `reason`, `context`,
`checks`, `recovery`; `schema=project-preflight-result-1`. `reason` — строка причины
либо `null`. `context` содержит двенадцать полей:

| Поля | Факты |
|---|---|
| `installation_source` | Фактический путь исходников запущенного Poise. |
| `config_path`, `requested_project_id`, `requested_task_id` | Допустимые явно переданные селекторы; отсутствующий/невалидный факт — `null`. |
| `project_id` | Идентификатор, прочитанный из manifest. |
| `state`, `task_database`, `task_lock` | Разрешённые пути выбранного Task storage. |
| `requirements_database`, `requirements_lock` | Разрешённые пути выбранного Requirements storage. |
| `repository`, `base_ref` | Наблюдённые значения Git из manifest. |

Уже прочитанные допустимые факты сохраняются и при отказе дальнейшей валидации.
`null` означает, что соответствующий факт не получен; пути не угадываются. Наблюдённый
контекст сам по себе не доказывает валидность всей конфигурации или существование файла.
Некорректные обязательные пути диагностируются у владельца с именем параметра, например
`paths.runtime` или `accounting.storage.database`. Проверяются тип, пустое значение и NUL;
запрет строки из одних пробелов применяется там, где это требует контракт. Допустимое
имя файла с пробелами не запрещается общим правилом. Сохраняются проверки размещения
и независимости хранилищ.

`checks` — упорядоченный массив четырёх объектов с точными ключами `name`, `status`,
`reason`. Статус компонента — `passed`, `rejected`, `unknown` или `not_checked`.

| Порядок и имя | Что проверяется |
|---|---|
| `configuration` | Общая валидация manifest и workflow snapshots, совпадение project ID. |
| `git` | Существующий локальный Git probe при `probe_repository=true`; без fetch/push. |
| `commit_policy` | Существующая политика сообщений при `commit_message` не `null`. |
| `task_lookup` | Наличие точного ID в явно выбранной Task DB, если `task_id` не `null`. |

После отказа или неожиданной ошибки владельца последующие компоненты не вызываются.
Пропуск по явному параметру оставляет `not_checked`; сам по себе он не запрещает выполнить
последующие компоненты. Поиск Task подтверждает наличие ID, не её доступность для старта
и не получение владения. При `task_id=null` база Task этой проверкой не открывается.
Размещение Requirements DB/lock проверяется конфигурацией; содержимое этой базы не
проверяется и не мигрируется.

| Наблюдение | `status` | `ready` | Код CLI |
|---|---|---|---|
| Первые три компонента прошли, запрошенный поиск Task также прошёл | `checked` | `true` | `exit_codes.success` из settings |
| Некорректный ввод или известный отказ компонента | `rejected` | `false` | `exit_codes.rejected` |
| Неожиданная ошибка владельца (`unknown`) | `checked` | `false` | `exit_codes.rejected` |
| Git или commit policy явно пропущены, известных отказов/ошибок нет | `checked` | `false` | `exit_codes.rejected` |

При некорректном вводе все компоненты остаются `not_checked`. При известном отказе
сохраняется исходная причина, при `unknown` — тип и текст неожиданной ошибки; пропуск
не выдаётся за подтверждённую готовность. `ready=true` не является гарантией будущего
старта: состояние может измениться, а обычный `bootstrap` заново проверяет свои условия.
Проверка не заменяет проверку host, процесса Task, прав публикации и ветки интеграции.

Если настройки проектных инструментов недоступны или невалидны до построения проверки,
сохраняется существующий краткий ответ `{"status":"rejected","reason":"…"}` и код `2`.
Отсутствующий обязательный `--settings` остаётся ошибкой аргументов CLI. Эти случаи не
являются полным ответом `project-preflight-result-1`.

Поиск Task и обзор `next` используют один
[защищённый владелец чтения](../architecture/library-api.md#защищённое-чтение-хранилища-задач).
Поддержан согласованный rollback-файл SQLite текущей схемы с Linux LP64 OFD и
`sqlite3.Connection.deserialize`. WAL, любой сопутствующий WAL/SHM/journal и конфликтующий
писатель вызывают защитный отказ без открытия исходной базы через SQLite. Проверка
не восстанавливает журнал и не читает устаревший основной файл вместо committed WAL.
Существующие блокировки вызывающего процесса сохраняются; снимок требует память
порядка размера базы. Полные ограничения принадлежат указанному библиотечному контракту.

### Восстановление после диагностики

При готовности `recovery=[]`. Иначе возвращаются четыре маршрута в таком порядке:

| `action` | `interface` | Действие оператора |
|---|---|---|
| `retry_check` | `poise project check` | Повторить проверку с явными корректными входами. |
| `list_projects` | `poise project list` | Просмотреть настроенные проекты с теми же `--settings`. |
| `select_work_config` | `poise work` | Явно задать нужный manifest через `POISE_CONFIG` для работы. |
| `select_requirements_config` | `poise requirements` | Передать нужный manifest через `--config` для Requirements API. |

Каждый маршрут содержит ровно `action`, `interface`, `settings_path`, `config_path`,
`supported_fields`, `limitations`. `settings_path` — использованные настройки инструментов.
У повторной проверки `config_path` содержит допустимый входной путь либо `null`; у двух
маршрутов выбора и списка — `null`. У первых четырёх маршрутов `supported_fields=[]`,
а `limitations` — массив с одним пояснением ограничения. `interface` — имя маршрута,
не готовая команда с полным пакетом: нужные аргументы и ввод передаются по контракту
соответствующего API.

Только если `configuration=passed`, а `git=rejected`, добавляется пятый маршрут
`supported_config_update` / `poise project-config` с выбранным `config_path` и
`supported_fields=["git.repository", "git.base_ref"]`. Применяйте
[публичное обновление](#обновление-действующего-проекта) с актуальной revision и
[ресурсными блокировками](#активные-задачи-и-перенос-state). Наличие незавершённых
Task само по себе не запрещает правку.
Перед исправлением `git.base_ref` прочитайте
[правило выбора целевой ветки](#выбор-ветки-основного-checkout-для-интеграции).
Результат проверки не переключает основной checkout и не разрешает изменить его ветку.

Неверный выбор manifest исправляется явным выбором, а параметры — через их публичного
владельца. Generic edit Git-полей не даёт права менять `paths` или переносить базы.
При неподдержанном/недоступном состоянии SQLite сначала восстановите согласованное
хранилище через его владельца в пределах отдельного полномочия, затем повторите проверку.
Не подменяйте runtime, проект или базу другой копией и не удаляйте journal для получения
`ready=true`. Выбор конфигурации не переносит данные, не меняет claim и не предоставляет
разрешение на миграцию. Диагностика не выполняет автоматическое исправление.

Рабочую Requirements DB и sidecar-файлы размещают в путях данных приложения вне Git.
В Git хранят раздельные исходные истории DDL и DML, а не бинарный снимок БД.
Проверки явных путей и отделения хранилищ сохраняются. Точные роли путей — в
[правиле размещения](../workflows/requirements-registry.md#владение-и-явные-пути).

При проверке кандидата manifest и workflow snapshots читаются из временного каталога,
но относительные рабочие пути и пересечения с конфигурацией разрешаются относительно
окончательного назначения проекта. Недопустимое размещение отклоняется до создания
Requirements-хранилища и до записи pending или публикации живой конфигурации.
Обновление повторно проверяет существующие Requirements-пути, в том числе при смене
обслуживаемого репозитория. Обычные `manifest_edits` не разрешают редактирование
`paths.requirements_database`, `paths.requirements_lock` и три пути миграций.
Для существующего профиля сначала выбирают применимого владельца публикации;
отказ generic editor не считается разрешением вручную менять managed config.
Поддерживаемые
[перенос state](#активные-задачи-и-перенос-state) через `state_relocation` и
[изменение корня worktree](#рабочие-деревья-внутри-репозитория) через
`project-worktree-root-1` сохраняют требования к разрешению, revision и блокировкам
фактически изменяемых ресурсов; статусы задач не запрещают изменение конфигурации.

Через `manifest_edits` можно явно добавить необязательный раздел `task_ids`, даже
если его ещё нет в manifest. Значение проходит обычную проверку политики
идентификаторов задач; отсутствие раздела не заменяется скрытой политикой.

Первичная подготовка требует отсутствующего каталога назначения. Предварительное
создание Requirements-файлов под ним нарушает это условие. Для уже существующих
файлов внутри репозитория можно явно задать абсолютный `paths.state` или абсолютные
Requirements-пути вне отсутствующего каталога конфигурации, соблюдая правило размещения.
Относительные существующие, отсутствующие и смешанные пары проверяются при загрузке
и обновлении уже подготовленного проекта.

## Доступные задачи во всех проектах

```bash
python -m poise next --settings "$PWD/config/project-setup.json"
python -m poise next --settings "$PWD/config/project-setup.json" --project ERP
```

`next` читает тот же configured-project registry, что и `project list`. Фильтр
`--project` — точный идентификатор, с учётом регистра; префиксы и имена каталогов
не подставляются. Неизвестный идентификатор возвращает явную ошибку. Команда не
читает stdin, не требует текущей Task/native-сессии или `POISE_CONFIG`, не создаёт
launcher, claim, worktree, БД или журнальные записи и не мигрирует старые БД.

Результат содержит `status`, `tasks` и `errors`. Каждый элемент `tasks` содержит
`project`, абсолютный `config_path`, `task`, `sprint` (либо `null`) и `goal`.
Все доступные задачи упорядочены лексикографически по паре `(project, task)`;
это порядок выдачи, а не новая политика приоритета. Пустая очередь — успешный
результат с пустым `tasks`. Ошибки отдельных проектов не скрывают доступные задачи
других проектов: `status=listed_with_errors`, непустой `errors` с идентификатором,
путём и причиной, код завершения CLI `2`. Для неизвестного идентификатора
путь не выдумывается: возвращаются идентификатор, `status=unknown` и причина.
Без ошибок — `listed`, код `0`.
Фильтр ограничивает как задачи, так и диагностику выбранным проектом.

Доступность означает возможность **начать** Task по сохранённому состоянию, а не
возобновить чужую/прерванную работу. Используются владельцы правил Task и Sprint:
статус `available`, отсутствие владельца, корректный начальный маршрут и входной
контент, опубликованный Sprint, его completion/result-зависимости и явные waivers.
Зарегистрированные входные артефакты проверяются по текущим файлам и digest;
утраченные или изменённые файлы не удовлетворяют входным требованиям. Незаконченная
execution-операция исключает задачу; разрешённый restart проверяется тем же правилом,
что и обычный `start`. Newborn, начатые/переданные, заблокированные и терминальные
задачи в эту очередь не входят.

Чтение выполняется отдельной read-only транзакцией каждого проекта. Общего снимка
нескольких БД и резервирования результата нет: после выдачи состояние может
измениться, поэтому обычный `start` заново проверяет условия и атомарно получает
владение. Проверка конфигурации и схемы БД не заменяет проверку доступности runtime,
Git или host в момент запуска. Недоступная, повреждённая или несовместимая БД
попадает в `errors`, а не создаётся или исправляется запросом `next`.

## Интерактивный путь

```bash
export PYTHONPATH="$PWD/src"
python -m poise project-init \
  --settings "$PWD/config/project-setup.json" \
  --template common \
  --destination config/projects/erp-local \
  --request-id ERP-SETUP-1 \
  --probe-repository yes
```

`common` — явно выбранный ID полного шаблона. Реестр задаёт его `path`;
генератор читает текущее содержимое файла. Версия и digest для выбора и чтения
шаблона не требуются. Все обязательные аргументы явные.

Анкета спрашивает идентификатор, существующий Git repository, base ref, неиспользуемое имя remote,
имя/email
автора, обязательное `push_required=false`, явный state root (абсолютный либо относительный) и имена
наследуемых
environment variables. Значение `true` отклоняется до любой Git-команды.
Вопросы, их порядок, типы и подсказки определяются данными шаблона, не условием по имени проекта.

Ответы:

* `set "ERP"` или `set "/home/user/erp"` — задать JSON-строку;
* `set false` — явное отключение push; `set ["PATH","HOME"]` — список;
* `keep` — явно принять показанное значение (из шаблона либо свой прежний ответ);
* `back` — вернуться, сохранив все ранее введённые ответы;
* `abort` или EOF — не публиковать;
* `publish` — доступно на финальном просмотре полного кандидата.

Пустая строка не означает ни согласие, ни default. После возврата изменение ответа попадает
в новый полный кандидат; при публикации повторно проверяются все связанные правила. Число
шагов анкеты ограничено `max_survey_steps`. Обнаруженное значение не подставляется скрыто.
Промпты идут в stderr, один итоговый JSON — в stdout.

## Пакетный путь для агента

```bash
python -m poise project --settings "$PWD/config/project-setup.json"
```

Без позиционного действия команда сохраняет прежний контракт создания и читает один пакет
из stdin. Для чтения настроенных проектов используется действие того же CLI:

```bash
python -m poise project list --settings "$PWD/config/project-setup.json"
```

`list` не читает stdin и не изменяет registry, project manifests, setup lock или каталоги
проектов. Настройки обязаны явно задавать `registry` внутри `root`. Документ registry имеет
схему `configured-project-registry-1`; объект `projects` сопоставляет устойчивый идентификатор
проекта с объектом `{ "config_path": "относительный/путь/project.json" }`. Directory scan,
template registry и скрытый путь по умолчанию не используются.

Результат содержит `status`, `projects` и `errors`. Элементы обоих массивов упорядочены
лексикографически по `project`. Успешный элемент содержит `project` и абсолютный
`config_path`. Отсутствующий manifest попадает только в `errors` со `status=missing`;
невалидный manifest или несовпавший `project` — со `status=invalid`. Каждая ошибка также
содержит абсолютный `config_path` и непустой `reason`; такой проект не выдаётся как пригодный.
При наличии ошибок итоговый status равен `listed_with_errors`, иначе `listed`; пустой registry
возвращает два пустых массива. Невалидная схема или структура самого registry отклоняет всю
операцию через обычный CLI error contract.

Успешная публикация через `project` или `project-init` регистрирует тот же manifest под его
полем `project`. Общая блокировка защищает только актуальное чтение, проверку и запись
реестра; подготовка проекта выполняется вне неё. Существующий идентификатор нельзя
перепривязать к другому пути. Опубликованный общий профиль добавляет к этой же записи
относительный `harness_config_path`; остальные записи и дополнительные метаданные
сохраняются. Публичный `list` продолжает возвращать `project` и `config_path`.
Границы записи и восстановления описаны в [публикации и повторе](#публикация-и-повтор).
Если каталог проекта уже опубликован, а запись registry не
сохранилась, повтор исходного `request_id` проверяет временный маркер операции,
действующий manifest и графы и завершает регистрацию. Уже записанные графы
сохраняются; источники читаются только для недостающих графов.

На stdin один объект `project-setup-1` с полями:

| Поле | Значение |
|---|---|
| `schema` | `project-setup-1` |
| `request_id` | Идентичность этого намерения создания |
| `destination` | Новый относительный каталог внутри AI poise root |
| `template` | Объект `{"id":"common"}`; ID выбирается из registry |
| `edits` | Список `{path: [имена полей], value: точное значение}` |
| `probe_repository` | Явное true/false |

`path` адресует поле выбранного project definition, не файл или таблицу. Каждый путь должен
существовать в полном шаблоне. Список/подобъект заменяется целиком. Дубликаты и одновременная
правка родителя и потомка отклоняются; порядок пакета не выбирает победителя. Поля вопросов
обязаны быть явно переданы. Остальные значения берутся из выбранного полного шаблона,
не из встроенных defaults. Изменение `automatic_checks` передаёт точные правила проекта;
редактор не читает команды из prose AGENTS и не изобретает их.

### Политика Task ID

Automatic Task creation доступен только при явном поле `task_ids` полного project config:

```json
{
  "task_ids": {
    "namespace": {"minimum": 1, "maximum": 9999},
    "width": 4,
    "progression": {"first": 1, "step": 1}
  }
}
```

Значения выше — пример политики, не default. `minimum` и `maximum` задают включительный
неотрицательный namespace; `width` обязан представлять `maximum`; `first` входит в namespace;
`step` — положительный. Кандидаты имеют decimal-представление с ведущими нулями до `width`.
Invalid policy отклоняет загрузку конфигурации. Отсутствующая policy сохраняет чтение и
explicit-ID creation существующих проектов, но automatic intent завершается явной ошибкой.

Project templates и уже опубликованные project configs не получают `task_ids` автоматически.
Этот срез не выбирает за пользователя числовой диапазон. Чтобы проект поддерживал automatic
allocation, выбранный полный template должен уже содержать принятую policy. `project-config`
изменяет только существующие manifest fields и не добавляет отсутствующий `task_ids`; ручная
правка managed manifest не является поддержанным обходом.

### Каталог поставленных skills

Метаданные ID/path, назначения и специализации, а также прямой интерфейс чтения описаны
в [контракте каталога skills](skill-catalog.md). Каталог не копирует инструкции и не
меняет выбранную project policy автоматически.

### Маршрутизация декомпозиции Task

task_decomposition хранит project-specific routing навыков и областей ответственности.
В `skills` каждый известный skill получает уникальный `id`, класс `meta`, `general` или
`narrow` и `responsibility`; у `meta` и `general` она равна `null`, у `narrow` — непустая.
В `areas` каждый project-specific glob связывается с одной responsibility. Дубликаты и
неверная форма отклоняют загрузку полного project config.

Для установленного общего каталога доступна альтернативная явная форма:
`catalog` (полный snapshot metadata), `skill_ids` (выбор проекта), `areas`.
Её строит read-only операция `poise skills` / `policy`, описанная в
[контракте каталога](skill-catalog.md#политика-проекта-и-проверка-пакета-без-harness).
Она принимается тем же `load_config`; классы и responsibilities берутся из общего
владельца metadata, а не переопределяются рядом. Смешивать `skills` с `catalog`
нельзя. Экспорт политики не является её публикацией и не изменяет конфигурацию проекта.

При создании и переводе Task в ready неизвестный skill или неразмеченная area отклоняют план.
Та же политика применяется к материализации и публикации Sprint, поэтому сохранённое деление
фаз не может обойти проверку фокуса. Area, связанная в политике с narrow responsibility,
проверяется в каждой фазе и должна соответствовать responsibility объявленного в этой фазе narrow
skill;
area с responsibility, которой не владеет ни один narrow skill политики, не становится narrow
только из-за соседства с таким skill. Конфигурация является маршрутом проверки декларации, а
не доказательством её фактической полноты.

Переносимые примеры AI poise показывают только форму контракта. ERP inventory и его классификация
принадлежат
конфигурации ERP, а не AI poise; пример
`config/examples/erp-task-decomposition.example.json` фиксирует явный кандидат миграции,
который должен быть принят владельцем ERP перед публикацией в целевой проект.
Этот исторический пример и `erp-migrated-skills.json` не являются инвентарём
поставленных skills; актуальная поставка перечислена в `.agents/skill-catalog.json`.

Перед публикацией инструмент проверяет весь кандидат штатным `load_config`, в том числе
каждый workflow через общий GoalTypeDefinition. При `push_required=true` кандидат отклоняется до
Git.
При `push_required=false` выполняются только локальные Git-проверки: repository root,
разрешимость base ref и имя ветки. Ни remote probe, fetch/push, установка пакетов, ни изменение
trust не выполняются; readiness remote равен `not_required`.

### Постоянные материалы комментариев Task

Для [task_feedback](../workflows/batch-work.md#комментарии-и-исходные-вложения-task)
явно задайте `paths.task_materials` через существующий `project-config-update-1`.
Это именованное optional поле: допускается его первое добавление в действующий
manifest. Остальные поля `paths` сохраняют своих владельцев. Старые операции
работают без новой настройки; новый API при её отсутствии сообщает конкретную
необходимость настройки, корень по умолчанию не выбирается.

| Опция | Значение и источник |
|---|---|
| `paths.task_materials` | Непустая после `strip` строка пути без NUL. Относительная — от настроенного `paths.state`, абсолютная — точно. Например, `user-materials` внутри state либо выбранный постоянный абсолютный каталог. |
| Выбор места | Постоянные данные установки вне Git и удаляемых Task-root/worktree/session областей. Выберите доступное обслуживающему процессу место и сохраняйте его вместе с Task DB. |
| Смена места | Публикация строки не переносит сохранённые байты. Для действующих материалов сохраняйте прежний доступный корень; перенос выполняется отдельно согласованным владельцем с проверкой данных. Автоматического переноса этот writer не добавляет. |

Выберите Python поставки с реализованной возможностью, абсолютный `project_json`
существующего проекта и `settings` его project-setup owner. Настройка не требует
claim текущей Task. `expected_revision` относится к полному текущему manifest
и всем его workflow snapshots. Подходит revision предыдущего owner result,
если это состояние фактически сохранилось. Для явного read-only наблюдения
оператор может использовать те же установленные `load_config`/`digest`:
сохраните следующий генератор в рабочий `prepare_task_materials.py` вне Git.
Он получает абсолютный config path и выбранное значение root двумя argv и
выводит полный пакет, не редактируя manifest.

```python
import json
import sys
from poise.common import digest, load_config

config_path, materials_root = sys.argv[1:3]
_, config, workflows = load_config(config_path)
print(json.dumps({
    "schema": "project-config-update-1",
    "request_id": "task-materials-setup-1",
    "config_path": config_path,
    "expected_revision": digest({"config": config, "workflows": workflows}),
    "manifest_edits": [{"path": ["paths", "task_materials"], "value": materials_root}],
    "workflow_updates": [],
    "state_relocation": None,
    "probe_repository": False,
    "receipt_path": "operations/task-materials-setup-1.json"
}, ensure_ascii=False))
```

Задайте `poise_python`, `generator`, `project_json`, `materials_root`, `packet`
и `settings` фактическими путями/значениями выбранной установки.
`generator` — сохранённый выше файл, `packet` — новый рабочий JSON-файл вне Git.
Для root допустимы обе описанные формы. Полный запрос сохраните до публикации:

```bash
"${poise_python:?Select installed Python}" -I -B "${generator:?Select saved generator}" \
  "${project_json:?Select absolute manifest}" "${materials_root:?Select permanent root}" > "${packet:?Select packet file}"
"$poise_python" -I -B -m poise project-config --settings "${settings:?Select project setup settings}" < "$packet"
```

Для проверки явно выбранного исходника, отдельно от установленного пакета,
задайте абсолютный `poise_root` этой копии. Используйте подготовленный Python
с её зависимостями и явный source launch; `-I` в этом варианте заменяется `-P`:

```bash
env PYTHONPATH="${poise_root:?Select explicit Poise source}/src:$poise_root" \
  "$poise_python" -P -B "$generator" "$project_json" "$materials_root" > "$packet"
env PYTHONPATH="$poise_root/src:$poise_root" \
  "$poise_python" -P -B -m poise project-config --settings "$settings" < "$packet"
```

Проверка исходника не переключает установленную поставку; для обычной установки
выбирайте первый вариант с обновлённым пакетом. Сохраняйте полный ответ команды.

После успешного `status: updated` прочитайте фактический manifest и полный receipt:
добавлена выбранная строка, прочие значения/workflows сохранены, результат содержит
прежнюю/новую revision и расположение receipt. Точный повтор выполняйте сохранённым
пакетом, не вычисляя ему заново revision: он возвращает прежний результат с
`replayed: true`. При прерывании продолжайте тем же пакетом через этого владельца;
конфликт требует сверки реального состояния до нового намерения.

Опция не создаёт файлы комментария при публикации manifest. Публикацию байтов
при append, их непрозрачные пути/IDs и продолжение после прерывания обслуживает
[владелец материалов](../architecture/storage-lifecycle.md#материалы-комментариев-task).
Рабочая публикация этой опции и обновление установленного потребителя — отдельные
проверяемые действия, пример сам по себе их не выполняет.

### Общий профиль команд и сессии

Общие возможности Poise выбирают профиль `poise-harness-project-1`. Они читают его
собственную конфигурацию, выбранный checkout и хранилище идентичности без загрузки
Task workflow. `placement`, `content-read`, общие проверки и инструкции сохраняют
своих владельцев. Наличие текущей Task или Sprint для них не требуется.

Все перечисленные поля профиля обязательны. Необязательна сама возможность управления
Task: поле `task_adapter` явно равно `null` либо содержит полную ссылку на adapter.
Числа — явные настройки выбранного профиля, а не подставляемые значения по умолчанию.

| Поле | Значение |
|---|---|
| `schema`, `project` | Ровно `poise-harness-project-1` и непустой ID выбранного проекта. |
| `git.repository` | Абсолютный путь основного checkout выбранного Git repository. |
| `paths.state` | Явный корень состояния; относительный путь разрешается от каталога профиля. |
| `paths.database`, `paths.lock` | Разные относительные пути хранилища идентичности и его lock внутри state. |
| `paths.runtime`, `paths.runs`, `paths.stdout`, `paths.stderr`, `paths.response` | Непустые относительные пути внутри state, без выхода через `..`. |
| `limits.git_seconds`, `limits.lock_seconds`, `limits.lock_poll_seconds`, `limits.sqlite_read_seconds` | Положительные конечные длительности в секундах. |
| `limits.output_chars` | Положительное целое ограничение агентского представления. |
| `batch.max_items`, `batch.max_input_bytes` | Положительные целые пределы пакета и его входных байтов. |
| `batch.file_mode` | Явное целое POSIX mode от 0 до 511. |
| `batch.message_source` | Полные `id` и `mode`; режим `runtime_event`, `reported` или `transcript` соответствует реальному источнику. |
| `runtime_resources` | Полный ресурсный договор: явный `project_setup` и список `hooks`; [границы владельцев](runtime-hooks.md#настройки-установки). |
| `task_adapter` | `null` для общего режима либо объект `schema: stride-task-adapter-1`, `config_path: /absolute/task/project.json`. |

При подключении Task adapter сохраняются полный Task manifest, его workflow и правила
проверки; общий профиль не заменяет их урезанным договором. Adapter сверяет project,
repository, state, database/lock и зарегистрированную связь профиля с manifest.
Несогласованное подключение даёт `task_adapter_mismatch`; попытка Task-возможности при
`null` даёт `task_adapter_required`. Эти отказы не включают скрытое подключение Task.

Публикация профиля и его связи описана ниже, с полным JSON-примером. Этот конкретный
маршрут начинается с уже зарегистрированного полного manifest даже при `task_adapter: null`.
Успешная публикация не переключает запущенный runtime: его потребитель явно выбирает
общий профиль. После выбора общий путь исполнения не загружает workflow этого manifest.
Приведённый ниже JSON-пример публикации использует `batch.message_source.mode: runtime_event`
и ID `codex-hook-main`; для его работы нужны настоящая доставка native events и совпадение
ID с источником выбранного definition2. Режим `reported` выбирается отдельно для явно
сообщаемых сообщений и сам по себе не обеспечивает доставку native events.
Изменение адреса рабочего профиля в hook settings не относится к разрешённым полям
`reconfigure`; переход существующей установки проектируется через её настоящего владельца.

### Публикация общего профиля и связи в реестре

Общий профиль публикуется тем же `project-config`, отдельным пакетом
`project-harness-transition-1`. Этот маршрут записывает профиль и его связь в общем
реестре; полный Task manifest остаётся по прежнему `config_path`. Это не generic
редактирование manifest, установка хуков или автоматическое переключение работающего
runtime. Выбор профиля действующим потребителем остаётся отдельной настройкой этого
потребителя; успешная публикация сама по себе не подтверждает поддержку им схемы профиля.

Используйте Python выбранной установки с доступным модулем `poise`:

```bash
python -B -m poise project-config --settings /srv/poise/config/project-setup.json
```

На stdin передаётся один UTF-8 JSON-объект в пределах `max_input_bytes` из выбранных
setup settings. Схема содержит ровно семь полей:

| Поле | Значение |
|---|---|
| `schema` | Ровно `project-harness-transition-1`. |
| `request_id` | Непустая строка — идентичность явно выбранного намерения. |
| `expected_revision` | Непустая строка фактически наблюдённой версии; [порядок продолжения](#публикация-и-повтор) учитывает конфликт и незавершённую публикацию. |
| `project_id` | Идентификатор уже зарегистрированного Task manifest. |
| `task_config_path` | Абсолютный путь этого полного Task manifest внутри `root` setup settings. |
| `harness_config_path` | Другой абсолютный managed path внутри того же `root`, куда записывается общий профиль. |
| `profile` | Полный объект `poise-harness-project-1`, включая явный `task_adapter`. |

У этого пакета нет `probe_repository`, `receipt_path`, `manifest_edits` или
`workflow_updates`. Локальный Git probe обязателен: Task manifest должен проходить
свои проверки репозитория, base ref и шаблона ветки. Профиль должен выбирать тот же
`project`, `git.repository` и владельца setup settings. Если выбран Task adapter,
проверяются его manifest и совпадение identity storage.

Полный пример ниже требует замены санитарных путей, ID проекта и
`OBSERVED-REVISION` фактическими значениями выбранной установки. Числа — явные значения
примера, а не defaults, которые подставит сервер. Репозиторий должен уже существовать,
а `project_id` — иметь правильную запись в выбранном реестре.

```json
{
  "schema": "project-harness-transition-1",
  "request_id": "DEMO-PROFILE-1",
  "expected_revision": "OBSERVED-REVISION",
  "project_id": "demo",
  "task_config_path": "/srv/poise/projects/demo/project.json",
  "harness_config_path": "/srv/poise/projects/demo/harness.json",
  "profile": {
    "schema": "poise-harness-project-1",
    "project": "demo",
    "git": {
      "repository": "/srv/repos/demo"
    },
    "paths": {
      "state": "/srv/poise-data/demo",
      "database": "sessions.sqlite",
      "lock": "sessions.lock",
      "runtime": "runtime",
      "runs": "runs",
      "stdout": "stdout.txt",
      "stderr": "stderr.txt",
      "response": "response.json"
    },
    "limits": {
      "git_seconds": 5,
      "lock_seconds": 3,
      "lock_poll_seconds": 0.01,
      "sqlite_read_seconds": 3,
      "output_chars": 5000
    },
    "batch": {
      "max_items": 30,
      "max_input_bytes": 1048576,
      "file_mode": 384,
      "message_source": {
        "id": "codex-hook-main",
        "mode": "runtime_event"
      }
    },
    "runtime_resources": {
      "project_setup": "/srv/poise/config/project-setup.json",
      "hooks": []
    },
    "task_adapter": null
  }
}
```

Все известные обязательные разделы профиля заполняются явно:

| Раздел | Поля и проверки публикации |
|---|---|
| `schema`, `project` | Схема `poise-harness-project-1`, непустой ID, совпадающий с выбранным Task manifest. |
| `git` | Абсолютный `repository`, совпадающий с репозиторием Task manifest. |
| `paths` | Непустые `state`, `database`, `lock`, `runtime`, `runs`, `stdout`, `stderr`, `response`. Кроме `state`, пути относительные, без `..`; `database` и `lock` различаются. При проверке adapter относительный `state` разрешается от каталога профиля. |
| `limits` | Явные конечные положительные `git_seconds`, `lock_seconds`, `lock_poll_seconds`, `sqlite_read_seconds`; `output_chars` — положительное целое. Эти поля профиля не заменяют лимиты самой операции из setup settings. |
| `batch` | Положительные целые `max_items`, `max_input_bytes`, POSIX `file_mode` от `0` до `511`; `message_source` содержит непустой `id` и `mode`: `runtime_event`, `reported` или `transcript`. |
| `runtime_resources` | Абсолютный `project_setup`, совпадающий с выбранным файлом setup settings, и явный список `hooks`. Каждый элемент содержит уникальный непустой `installation_id` и уникальный абсолютный `settings_path`. Пустой список допустим и не устанавливает хуки. |
| `task_adapter` | Явный `null` либо объект `schema: stride-task-adapter-1`, `config_path`: абсолютный путь выбранного полного Task manifest. При adapter пути state/database/lock профиля должны совпасть с identity storage этого manifest. |

Общие правила неизвестных конфигурационных опций сохраняются, но сам внешний API-пакет
имеет строгий набор полей. Настройки hook installations этим маршрутом не публикуются.

Успех содержит `status: updated`, `project`, `config_path`, `harness_config_path`,
`revision`. Владелец записывает полный профиль, добавляет собственный `harness_config_path`
в актуальный реестр и сохраняет рядом с профилем квитанцию: её имя содержит digest
`request_id` и суффикс `.publication.json`; временный sibling имеет ещё `.pending`.
Выбирать или вычислять это техническое имя вручную не требуется.

Для первой публикации, когда связь профиля ещё отсутствует, версия относится к полному
Task manifest и его workflow snapshots. Используйте фактическую revision результата
подготовки или обновления только пока это состояние остаётся актуальным. После привязки
профиля версия включает также текущий профиль и **весь** общий реестр. Поэтому изменение
другого проекта может сделать ранее полученную revision устаревшей. Новой отдельной команды
чтения этой версии данный маршрут не добавляет: явный stale-отказ сообщает настоящую
ожидаемую и актуальную версии и действие продолжения.

Исходная редакция публикации охватывает **полный manifest и все выбранные им workflow**:
состав mapping, полные исходные JSON-документы графов и допустимые неизвестные расширения.
Сравнивается смысловая JSON-редакция: перестановка ключей, пробелы и форматирование
не меняют её. Это не снимок всех файлов runtime или установки.

Перед первой записью профиля владелец надёжно сохраняет намерение публикации с
отпечатком этой исходной редакции. При повторе он отдельно проверяет неизменность
исходника и известные собственные состояния профиля/реестра до или после эффектов.
Начальная composite `expected_revision` после привязки по-прежнему включает профиль
и весь реестр; её не заменяют отпечатком одного исходника. Повтор уже начатой операции
не требует равенства первоначальной composite revision состоянию после собственных
частичных эффектов.

Создаваемая этим маршрутом служебная запись `project-config-pending-2` содержит ровно
пять полей:

| Поле | Сохранённое значение |
|---|---|
| `schema` | `project-config-pending-2`. |
| `request_digest` | Отпечаток полного исходного public packet. |
| `source_revision` | Отпечаток полного исходного manifest и всех выбранных raw workflow. |
| `before` | Ровно `profile` и `registry`: отпечатки компонентов до публикации. |
| `after` | Ровно `profile` и `registry`: отпечатки согласованных компонентов после публикации. |

Отпечатки — строки из 64 шестнадцатеричных символов SHA-256 в нижнем регистре.
`source_revision` не хранит копию документов и не позволяет восстановить утраченный
исходник. Запись создаёт и читает сам владелец: отправлять её вместо публичного
семипольного пакета или дописывать поля вручную не требуется. Этот формат относится
только к публикации общего профиля; generic update, bootstrap и stage-criteria имеют
свои прежние форматы. Формат завершённой квитанции `project-config-receipt-1` сохранён.

Примеры условий и наблюдаемых исходов для того же исходного пакета:

| Условие перед повтором | Результат |
|---|---|
| После прерывания изменено значение manifest, содержимое любого выбранного workflow или состав выбранных графов | Явный source conflict до новых записей публикации; pending и текущие данные сохраняются. |
| Изменилось только JSON-форматирование исходника | Исходная смысловая редакция совпадает; известное собственное частичное состояние допускает завершение. |
| Владелец осознанно восстановил известную принятую прежнюю редакцию через public update | Тот же исходный пакет может завершить собственную частичную публикацию. |
| Сохранён старый pending без подтверждения исходной редакции | Явный отказ о missing/unverified source; текущие данные и запись сохраняются. Возврат одного файла не создаёт отсутствующую историю. |
| Публикация завершена, затем исходник допустимо изменён | После прежних предварительных проверок возвращается сохранённый результат с `replayed: true`. |
| После сверки известного исхода выбран новый явный intent на актуальной редакции | Новый `request_id` публикует выбранный профиль; прежний pending сохраняется и не считается завершённым. |

Квитанция хранит результат момента публикации. Точный повтор после предварительных
проверок возвращает его с `replayed: true`, без повторной записи старого реестра и
без общей registry-блокировки. Он сохраняет предварительную валидацию входа, профиля,
путей, manifest, identity/adapter и локальный Git probe; квитанция не освобождает от них.
Сохранённая `revision` не выдаётся за наблюдение всего реестра после чужих публикаций.
Если текущий manifest нарушает обязательные проверки, они могут отказать до чтения
квитанции. Исторический повтор не означает пропуск этой валидации.
Другой пакет с тем же `request_id` отказывает. Ошибки и частичные состояния описаны в
[общем порядке публикации и восстановления](#публикация-и-повтор).

### Рабочие деревья внутри репозитория

`paths.worktrees` принимает явный абсолютный путь к дочернему каталогу
`git.repository`. Корень репозитория, его `.git`, выход наружу и symlink в пути
отклоняются. Уже заданные относительные пути по-прежнему относятся к `paths.state`.
Каталог рабочих деревьев внутри репозитория должен исключаться из Git.

Исправление пути у восстановленного проекта выполняет тот же `project-config`
пакетом `project-worktree-root-1`: поля как у `project-config-update-1`, плюс
непустые `reason` и `authorization`. Допускается ровно одна `manifest_edits`
для `["paths", "worktrees"]`; `workflow_updates=[]`, `state_relocation=null`.
`expected_revision` — точный digest текущего manifest и workflow snapshots.
Этот узкий операторский путь также фиксирует текущую revision после восстановления,
когда исходная setup-квитанция относится к прежнему расположению установки.
Остальные параметры и workflow snapshots не изменяются.

Под общим state lock проверяется отсутствие активного исполнения, выделенных
Task worktrees/веток и незавершённых внешних действий. Не начатые задачи и
задача, возвращённая в newborn без выделенного дерева, не требуют отмены или
пересоздания. Существующие рабочие деревья этот API не перемещает.
Сохраняются проверка точной revision, квитанция намерения и восстановление
прерванной публикации; точный повтор не меняет историю задач.

Один публичный пакет обновляет существующий project manifest и его workflow snapshots без
удаления и повторного создания проекта:

```bash
python -m poise project-config --settings "$PWD/config/project-setup.json"
```

На stdin передаётся ровно один bounded JSON-объект `project-config-update-1`:

```json
{
  "schema": "project-config-update-1",
  "request_id": "ERP-CONFIG-2",
  "config_path": "/absolute/poise/root/config/projects/erp-local/project.json",
  "expected_revision": "known-project-revision",
  "manifest_edits": [
    {"path": ["git", "push_required"], "value": false}
  ],
  "workflow_updates": [
    {"goal_type": "development", "expected_revision": "known-workflow-revision", "changes": []}
  ],
  "state_relocation": null,
  "probe_repository": false,
  "receipt_path": "operations/ERP-CONFIG-2.json"
}
```

`config_path` выбирает существующий managed manifest внутри root из settings.
`expected_revision` — digest полного действующего project manifest вместе со всеми workflow
snapshots; операция сравнивает её с точной текущей revision. Наличие revision
в старых setup/update receipts не является условием обновления.
Каждый workflow update дополнительно содержит digest выбранного workflow и декларативные
`changes` контракта `GoalTypeDefinition`. Изменения одного workflow публикуются полным
валидированным snapshot, а не правкой JSON-файла на месте.

`manifest_edits` адресует существующие поля по логическому пути. Корни `project`, `schema`,
`workflows` и `paths` имеют отдельных владельцев и через generic edit не меняются. Весь
manifest и все workflow snapshots проверяются общим `load_config` до публикации. Локальный
Git probe выполняется только при `probe_repository=true`; сеть, fetch и push не входят в эту
операцию.

### Revision, receipt и восстановление

#### Удаление устаревшего параметра artifact_lock

`batch.artifact_lock` больше не требуется и не используется для работы с материалами.
Четыре поставляемых примера конфигурации проекта не содержат этот параметр.
Старый ключ обрабатывается как неизвестная опция: его исходное значение сохраняется
при редактировании и публикации конфигурации, но не включает блокировку.
Удалять его для продолжения работы не требуется. Это изменение не переписывает
рабочие конфиги или исторические документы автоматически.

Независимые Task работают с материалами без общей блокировки проекта; порядок
завершения текущих запросов перед терминальным действием описан в
[договоре материалов](../workflows/terminal-materials.md#порядок-завершения-операций-с-материалами).

#### Удаление устаревшего параметра transfer

Неизвестные опции конфигурации проекта и процесса игнорируются при исполнении,
но сохраняются в исходном документе, ревизии и публикации редактора. Это также
относится к settings редактора, hook transport, runtime adapter и каталога,
политике чтения исходников и [конфигурации маршрутизации
разработки](development-routing.md#расширения-конфигурационных-документов).
Известные обязательные поля, их типы, ограничения путей и поддерживаемая версия
схемы продолжают проверяться. Имена процессов, шаблонов, этапов и исходов графа —
предметные данные, а не неизвестные опции. API-пакеты, квитанции и сохранённые
контракты Task сохраняют строгую схему.

Прежние разделы `runtime_services.handoff` и `runtime_services.transfer` целиком
считаются неизвестными опциями. Их значения не валидируются как активные настройки,
не запускают сервис и не блокируют обычную работу; редактор сохраняет raw values.
Удаление этих ключей не требуется и не удаляет исторические файлы.
Сопровождающие конфигурации проверок задаются отдельно через `check_runner.systems`:
раздел необязателен; если задан, нужны полные `poise` и `project` с абсолютным
`repository` и непустым списком абсолютных `configs`. Известные поля проверяются
строго независимо от присутствия старых опций.

Ошибка известного обязательного параметра отклоняет публикацию, неизвестная
опция — нет. Состояние, владение,
рабочие деревья и pending задач не запрещают правку конфигурации и не изменяются
редактором. Проверка и публикация используют существующие project lock и
material → state locks при переносе состояния. Незавершённые внешние операции не запускаются и не
переписываются ради редактирования конфигурации.

`request_id`, содержимое запроса и `receipt_path` образуют неизменное намерение. Receipt
располагается относительно root из setup settings и содержит прежнюю/новую project revision,
readiness и итог операции. Точный повтор возвращает тот же результат с `replayed=true` и не
создаёт вторую revision. Другой пакет с тем же receipt, неизвестная или устаревшая live
revision и посторонняя правка managed файлов завершаются конфликтом без принятия этих данных.

Перед внешними публикациями сохраняется pending receipt с digest каждого компонента до и
после. После прерывания следует повторить тот же пакет: восстановление принимает только
точную комбинацию известных before/after-компонентов, допубликовывает недостающую часть и
создаёт один durable receipt. Неизвестный исход нельзя исправлять новым request ID, ручным
overwrite или удалением проекта.

### Подтверждение проверки Git

Результат создания проекта и квитанция обновления `project-config-receipt-1`
содержат результат проверки Git в `readiness`. Для этого результата предусмотрены
две точные формы:

| Проверка | Поля и значения |
| --- | --- |
| Выключена явно | Только `repository=not_checked` и `remote=not_checked`. |
| Выполнена | `repository=verified`, `remote=not_required` и `base_revision` — непустая строка с наблюдавшимся Git commit. |

Читатель квитанции проверяет состав полей и эти значения. В выполненной проверке
`base_revision` обязателен; пустая строка или значение другого типа отклоняются.
Дополнительные поля и другие сочетания значений отклоняются. Сохранённый commit
не сравнивается с текущим HEAD: чтение квитанции не запускает Git повторно и
не переписывает её историю. Проверки схемы квитанции, проекта, пути и revision
продолжают действовать отдельно от проверки `readiness`.

### Исторические процессы проекта

Если сохранённым процессам и Task не хватает обязательных `purpose` и
`criteria_authority`, обычное чтение или обновление проекта может остановиться
на проверке схемы. Для такого перехода используйте
[явную миграцию типов и
критериев](../task-workflow-snapshot-migration.md#миграция-типов-и-критериев-этапов).
У процессов, опубликованных подготовкой проекта в собственный пакет,
[владельца выбирают через
`--project-settings`](../task-workflow-snapshot-migration.md#выбор-владельца-публикации).
Аргумент указывает действующие setup settings; текущий manifest выбирается
отдельно через `--config`. Полный согласованный mapping и публичная копия
Task DB готовятся в исключительном окне без writers.
В инвентаризацию входят и постановки без подготовленных договоров этапов:
они используют [явный
`newborn_draft`](../task-workflow-snapshot-migration.md#постановки-без-договоров-этапов).
Для миграции не требуется заранее выбирать им процесс или готовить договоры.

Этот вход сохраняет историческую квитанцию подготовки и использует реестр и
историю публикаций существующего владельца. Ручная вставка полей в managed
JSON/Task metadata, новый editor DB или перенос targets не заменяют миграцию.
Обычный `project-config` продолжает принимать только корректную текущую схему;
его нельзя использовать для обхода проверки исторического источника.

### Активные задачи и перенос state

Workflow update не переписывает workflow snapshot уже созданной Task: она продолжает работать
по сохранённому определению, а новая revision применяется к будущим задачам.
Наличие задач любого статуса, владельца, рабочего дерева или pending не является
запретом редактирования manifest, workflow или корня будущих рабочих деревьев.
Сохранённые контракты, история, ветки и размещённые рабочие деревья не мигрируют
неявно. Редактор сохраняет проверки revision, владельцев путей, locks и журнал
атомарной публикации. Новый запуск выбирает текущую конфигурацию. Уже созданный runtime
сверяет размещение перед записью и отклоняет устаревшую привязку; редактор не перенастраивает
объекты runtime в памяти.

#### Привязка владельцев ресурсов

Для изменяющих операций manifest явно связывает проект с владельцами через
`runtime_resources`: абсолютный `project_setup` и список `hooks`. Каждый элемент `hooks`
содержит уникальные `installation_id` и абсолютный `settings_path`. Пустой список означает
проект без связанных установок хуков. Владелец проверяет выбранный реестр проектов,
соответствие его записи текущему manifest и фактическую зарегистрированную установку.
Настройки, реестр и общий project lock первоначальной публикации должны находиться
вне переносимого state. Project lock остаётся вне обоих корней при переносе.

Первую привязку публикуют через `project-config` отдельным пакетом
`project-runtime-resources-bootstrap-1`. Он использует явно выбранные setup settings и
не требует заранее создавать изменяющий runtime без `runtime_resources`. Запуск выполняют через
общий выбранный каталог Poise: launcher получает `--poise-root` и `--project`,
а настроенный Python читает код из `<poise-root>/src` с `-P -s -B`. Наличие
проверенной правки в другом Task worktree не переключает этот каталог.
Используется текущий общий код с поддержкой указанной схемы, без отдельной
установки пакета для проекта. См. [запуск](stride-launcher.md#выполнение-команды).

Пример для проекта **без установок хуков**; пути и известную текущую revision заменяют
своими значениями. Receipt выбирают вне state, относительно `root` из setup settings:

```json
{
  "schema": "project-runtime-resources-bootstrap-1",
  "request_id": "bind-project-resources-1",
  "config_path": "/absolute/poise/projects/example/config/project.json",
  "expected_revision": "<известная-текущая-revision>",
  "runtime_resources": {
    "project_setup": "/absolute/poise/config/project-setup.json",
    "hooks": []
  },
  "receipt_path": "operations/bind-project-resources-1.json"
}
```

Проект с хуками передаёт полный список существующих связей. Bootstrap проверяет authority
существующей установки по её сохранённой публикации и фактическим группам native-файла.
Новые флаги текущего генератора команд не меняют уже опубликованный факт: bootstrap
не переустанавливает hooks и не требует совпадения старой команды с новым планом генерации.
Связь проекта, идентификатор установки, определение и целевой файл продолжают проверяться.
Отдельная установка новой редакции hooks проверяет и публикует её выбранные producer-группы.
Публикация требует известную ожидаемую revision и сохраняет pending/receipt. Точный
повтор принимает только своё намерение и известное состояние публикации. Уже существующая
привязка, чужая установка или изменённая revision отклоняются; bootstrap не является
универсальным редактором существующих связей. Его результат имеет
`schema=project-runtime-resources-bootstrap-result-1`, `status=completed`,
`before_revision` и `after_revision`. В сохранённой квитанции `prior_revision`
равен `before_revision`, а `revision` равен `after_revision`. Следующий запрос
использует опубликованную revision.

При публикации без прерывания `replayed` в сохранённой квитанции равен `false`.
Если manifest уже опубликован,
а запись квитанции прервана, точный повтор завершает публикацию и сохраняет
`replayed=true`. Последующий точный повтор возвращает `replayed=true` в ответе,
сохраняя прежние байты квитанции и её исходное значение `replayed`.
Подлинная квитанция первой привязки может подтвердить исходную revision для
[явной миграции
критериев](../task-workflow-snapshot-migration.md#публикация-атомарность-и-восстановление).
Завершение самой миграции подтверждается её отдельной квитанцией обновления.
Если внешняя разрешённая публикация затронула managed head редактора процессов, применяют
его [status/reconcile](goal-config.md#сверка-управляемой-revision-с-live-конфигурацией),
сохраняя существующую БД редактора.

#### Пакет переноса

Объект `state_relocation` имеет ровно пять полей:

| Поле | Значение |
|---|---|
| `schema` | `project-state-relocation-1`. |
| `expected_source` | Действующий существующий корень state. |
| `destination` | Новый корень, не равный source и не вложенный в него; source также не вложен в destination. |
| `source_disposition` | `retain` либо `delete_after_publish`. |
| `hook_destinations` | Полный список целевых предложений для установок из `runtime_resources.hooks`. |

Каждое целевое предложение содержит ровно `installation_id`, `settings_path` и `settings`.
`settings` — полный объект `hook-settings-1`, а не набор изменяемых полей. Все известные
пути, среда, probe filenames, exit codes и элементы `cwd_roots` проверяются до публикации
намерения и копирования. Непригодные типы и встроенный NUL дают адресный отказ.
Неизвестные поля versioned API-пакета отклоняются; неизвестные опции внутри конфигурации
сохраняются по [общему правилу](#удаление-устаревшего-параметра-transfer).
Полный [образец hook settings](../../config/hook-settings.example.json)
заполняют целевыми значениями с учётом его `root` и путей проекта, установки и данных.
Его условные пути не являются рабочей конфигурацией.

Полный пример запроса для проекта с явно пустым списком установок хуков:

```json
{
  "schema": "project-config-update-1",
  "request_id": "relocate-project-state-1",
  "config_path": "/absolute/poise/projects/example/config/project.json",
  "expected_revision": "<известная-текущая-revision>",
  "manifest_edits": [],
  "workflow_updates": [],
  "state_relocation": {
    "schema": "project-state-relocation-1",
    "expected_source": "/absolute/data/source",
    "destination": "/absolute/data/destination",
    "source_disposition": "delete_after_publish",
    "hook_destinations": []
  },
  "probe_repository": false,
  "receipt_path": "operations/relocate-project-state-1.json"
}
```

У проекта с хуками вместо пустого списка передают полные предложения всех связанных
установок с прежними идентификаторами. Адреса конфигурации и её revision получают от
действующего реестра и успешных публичных receipts, а не от случайно найденной БД.
Пакет передают установленному производителю с явно выбранными абсолютными путями
`project_python`, `project_setup` и `project_request`:

```bash
"${project_python:?}" -I -B -m poise project-config \
  --settings "${project_setup:?}" < "${project_request:?}"
```

После успешного создания setup settings CLI использует их `exit_codes.rejected` для
структурированного `status=rejected`. Если создать settings не удалось, применяется
резервный код `2`. Значение `2` в примере настроек не является фиксированным кодом всех
установок. [Код отказа Stride](stride-launcher.md#отказ-и-восстановление) выбирается
отдельно в launcher settings.

#### Допуск и порядок переноса

Правка manifest и перенос состояния имеют разные допуски. Для переноса нужны освобождённые
Task writers. Все bindings переносимых native установок должны иметь состояние `DEAD` по
последнему зарегистрированному native событию; `LIVE` и `UNCERTAIN` отклоняются. Точный
критерий и ограничения проверки описаны у
[владельца хуков](runtime-hooks.md#привязка-проекта-и-перенос-установки).
Освобождение Task не заменяет этот допуск. Native authority проверяется при допуске,
возобновлении и перед удалением source.

Общая блокировка установки не используется ни при переносе, ни при обычной работе
агентов, создании проекта и публикации конфигурации. Настройку и перенос оператор
выполняет последовательно, после завершения записей в переносимые данные.
Владельцы отдельных хранилищ сохраняют свои локальные границы записи и короткие
транзакции SQLite; они не удерживают общую блокировку установки на время тестов.
Действия над файлами не объявляются одной SQLite-транзакцией: существенные эффекты
имеют сохранённые монотонные фазы.

| Фаза | Проверяемый результат |
|---|---|
| `admitted` | Связи, writers и native authority проверены; Task records и полный исходный набор файлов зафиксированы. |
| `copied` | Всё дерево скопировано во временный соседний каталог, опубликовано rename и сверено с исходником. |
| `materials_published` | Владелец интеграции записал привязки подтверждённых терминальных поставок; владелец материалов зарегистрировал связи и смену физических путей артефактов. |
| `hooks_published` | Владелец установки опубликовал её целевые settings и native groups. |
| `configuration_published` | Manifest выбирает новый state и целевые связи хуков. |
| `consumers_confirmed` | Сохранённые receipts, выводы, конфигурации, манифесты и их входы читаются через реальных владельцев; связи хуков подтверждены. |
| `source_retired` | Выполнены повторные проверки; source удалён при `delete_after_publish` либо сохранён при `retain`. |

Task/Sprint identity, Task version, workflow snapshot, история, исходные receipts и digest
материалов не переписываются ради переноса. Физическое размещение читает существующий
владелец сохранённых материалов по зарегистрированным связям. Уже начатую терминальную
очистку перенос не отменяет и удалённые ею материалы не воссоздаёт; действует
[исторический
договор](../workflows/terminal-materials.md#чтение-и-повторное-использование-после-удаления).

Для подтверждённой терминальной интеграции сохраняется отдельная связь исходной
квитанции с переносом runtime-каталога. Привязка записывается в той же транзакции,
перед связями артефактов и пропуском уже удалённых служебных материалов. Поэтому
завершённая Task сохраняет подтверждение размещения и после удаления её журналов.
Проверяется полное исходное подтверждение публикации, а не только статус или путь.
Неподтверждённые и неподдержанные исторические квитанции переносятся без изменения;
новое подтверждение для них не создаётся. Точный повтор запроса сохраняет прежнюю
привязку без дублирования; несовпадающее содержимое того же запроса отклоняется.
Порядок проверки цепочки и исходного доказательства описан у
[владельца перепланирования
Sprint](../workflows/sprints.md#вернуть-опубликованный-sprint-в-черновик).

При сверке скопированной Task DB владелец интеграции проверяет новые строки
привязок по исходному допущенному снимку: точные Task и версия, оба запроса, хеш
исходной квитанции, исходный и целевой runtime. Временное сравнение исключает
только подтверждённые строки и соответствующее выделение номеров журнала;
после этого владелец артефактов проверяет собственные эффекты. Исходные строки,
идентичности, схема, другие последовательности и неподтверждённые изменения
сохраняют прежнюю строгую проверку. Это не переписывает сохранённую БД или её
историю и не добавляет обязательных настроек либо миграции схемы.

История завершённых задач переносится без повторного чтения и привязки raw-журналов,
даже если в старых данных ещё нет договора поставки. Действующие зарегистрированные
файлы при этом сохраняют обязательную проверку identity и digest; терминальный статус
не является разрешением пропустить или удалить регистрацию.

Смена state не меняет автоматически независимые абсолютные Requirements-пути или путь
worktrees. Относительные пути разрешаются по правилам их владельцев;
[размещение ресурсов](storage-layout.md#перенос-дерева-state-и-независимые-ресурсы)
проверяют отдельно. Успешный результат обновления имеет `status=updated`, `changed`,
`prior_revision`, `revision`, `config_path`, `readiness`, `receipt_path` и `replayed`.
Вложенный `state_relocation` содержит `status=completed`, `source`, `destination` и
`source_disposition`.

#### Прерывание и точный повтор

Для восстановления повторяют тот же пакет с теми же `request_id` и `receipt_path`.
Фазы не откатываются. Непустой или посторонний destination не перезаписывается.
Временный каталог имеет имя `.<destination-name>.project-update`. Если он уже существует
при первом запросе, операция отказывает до pending receipt и сохраняет его содержимое.
Только точный повтор собственного pending намерения может удалить свой частичный staging
и выполнить копирование заново.

| Наблюдение при повторе | Поведение |
|---|---|
| Сохранена только `admitted`, destination отсутствует | Через владельцев переносимых хранилищ заново допускается полный актуальный released source: первая копия включает принятые после прерывания записи. |
| Destination уже существует либо сохранена фаза `copied` или позднее | Исходный seal остаётся обязательным; новый исходный файл, запись истории или конфликт скопированных байтов дают отказ с сохранением обеих копий. |
| Изменена произвольная скопированная SQLite | Требуется побайтовое равенство исходному файлу; SQLite-формат сам по себе не разрешает изменение. |
| Изменена явно настроенная Task DB, связанный Hook Registry или accounting storage | Владелец допускает только точные подтверждённые служебные эффекты; schema, версия, `application_id`, наблюдаемые row identities и все исходные строки сохраняются. |
| Source уже удалён после подтверждения потребителей | Законный pending повтор завершает прежнее намерение, не создавая старый root. Необъяснимое отсутствие source отклоняется. |
| Уже есть завершённый receipt того же запроса | Возвращается сохранённый результат до повторного допуска исторических runtime inputs; это не свежая проверка файлов или потребителей. |

Служебное исключение accounting ограничено новыми успешными `recover_artifacts` envelopes
без usage ingestion, подтверждёнными recovery audit Task, session, identity и полной
проекцией владельца. Другие изменения телеметрии отклоняются с сохранением исходника.
Сопоставление меняет только временную проекцию проверки, а не сохранённые строки и историю.

При `delete_after_publish` source удаляется только после проверки потребителей и повторной
проверки native authority и seals. При `retain` он остаётся. Конфликт не устраняют новым
request ID, удалением pending, подменой seal, ручным слиянием БД или перезаписью одной копии.
Сначала устанавливают причину и согласуют действие с владельцем изменённых данных.
Автоматический архив или резервная копия не являются частью этой операции.

## Публикация и повтор

Генератор готовит и проверяет кандидат manifest, графы, пути назначения и выбранную
локальную готовность вне общей блокировки реестра. Manifest публикуется отдельным
rename; графы создаются по своим настроенным путям без перезаписи существующих файлов.
После чтения полного проекта обычным `load_config` финальная регистрация захватывает
Linux lock из `settings.lock`, заново читает актуальный общий реестр, проверяет identity
и атомарно публикует собственную связь вместе со всеми текущими чужими записями.
Та же связь возвращает результат «уже зарегистрирована» без перезаписи её метаданных;
другой manifest под прежним ID вызывает конфликт. Подготовка и Git probe не удерживают
эту общую границу. `lock_seconds` и `lock_poll_seconds` берутся из явных setup settings.

[Публикация общего профиля](#публикация-общего-профиля-и-связи-в-реестре) использует
собственную project-блокировку, затем ту же короткую registry-блокировку. Под ней
перечитываются реестр и текущий профиль, проверяются связь/revision/pending и выполняется
порядок pending → profile → registry → durable receipt → удаление pending.
Полные manifest и выбранные workflow также перечитываются; исходная редакция фиксируется
в pending до первого эффекта, с `fsync` файла и директории. При продолжении
`project-config-pending-2`
проверяет форму записи, исходный запрос, сохранённую исходную редакцию и отдельные
before/after-состояния компонентов до новых записей публикации. Публикацию конфигурации
оператор выполняет последовательно через её существующего владельца; защита от
несогласованной прямой записи файлов вне этого порядка здесь не обещается.
Итоговая квитанция возвращается раньше общей блокировки. Обратного порядка
registry → project lock в этих двух путях нет. Публикация нескольких файлов не является
одной атомарной операцией файловой системы.

До завершения рядом с manifest находится `.project-setup-pending.json`: ID операции,
ID проекта и выбранные пути графов. После регистрации этот временный маркер
удаляется. Постоянная квитанция создания, хэши исходников и подтверждение
происхождения конфига не требуются. Уже существующие старые квитанции генератор
не читает и автоматически не удаляет.

Повтор для зарегистрированного проекта читает текущие manifest и графы,
сохраняет правки оператора и заново выполняет выбранный readiness probe.
Дополнительные неизвестные опции registry и метаданные его записей сохраняются.
Повтор незавершённой публикации требует совпадающего маркера: существующие графы
читаются как текущие, недостающие создаются из текущего выбранного источника.
Полностью записанный проект может завершить регистрацию без старого шаблона
или исходных графов. Чужой незарегистрированный каталог без маркера не принимается.

При ошибке до полной записи графов удаляются только созданные этим вызовом файлы;
ранее существующие файлы сохраняются. Если полный проект уже записан, а регистрация
не завершилась, manifest, графы и маркер остаются для повтора той же операции.
Task DB, сессии, worktrees и код целевого приложения генератор не создаёт.

Для обоих путей общий реестр сохраняет каждую принятую связь и дополнительные
метаданные. Отказ не означает, что все уже выполненные файловые действия откатились:

| Фактический исход | Состояние и продолжение |
|---|---|
| Общая блокировка занята дольше заданного ожидания | `rejected` с конкретным registry/lock и указанием повторить тот же запрос после освобождения. Чужой lock не удаляют. При setup собственные manifest/графы/маркер уже могли быть подготовлены; при profile запись профиля под этой блокировкой ещё не началась. |
| Устаревшая версия нового намерения публикации профиля | Отказ сообщает supplied/current revision до записи нового pending. Проверьте текущее состояние, затем отправьте новый явный `request_id`, фактически сообщённую актуальную `expected_revision` и желаемый полный `profile`. Это не способ повторять неизвестный исход под другим ID. |
| Ошибка записи profile/registry/receipt | `rejected` сохраняет настоящую причину и указание повторить **тот же** запрос. CLI использует существующие `status: rejected`, `reason` и `exit_codes.rejected`

Сохраняются проверки читаемости и структуры, блокировки и коллизии реальных

В manifest `schema` выбирает формат, `project` — идентификатор; `paths` задаёт
хранилища, рабочие деревья и имена runtime-файлов, `git` — репозиторий,
ветку-получатель, формат task-веток, автора и запрет/режим remote-публикации.
В примерах и шаблонах создания проекта `git.commit_pattern` равен `(?s).+`:
он допускает сообщение с заголовком, пустой строкой и многострочным телом,
а также служебный WIP-коммит.
Это проверка непустого текста, а не автоматическая проверка смысла или длины строк;
для новых коммитов действует [правило
50/70](../workflows/commit-messages.md#продуктовый-смысл-и-формат-5070).
`limits` ограничивает время Git/блокировок, попытки и объём вывода.
Обязательный `limits.sqlite_read_seconds` задаёт отдельное ожидание физической
блокировки SQLite при чтении; `limits.lock_seconds` сохраняет пределы записи,
`limits.lock_poll_seconds` задаёт polling. Значение чтения явно добавляют в
существующий manifest до активации версии, которая его требует. Ограничения
значений, шаблоны и поведение отказа описаны в
[контракте наблюдения](runtime-services.md#наблюдение-и-пишущие-намерения);
`environment_names` перечисляет разрешённые переменные среды. `workflows`
сопоставляет goal types с рабочими файлами, `task_ids` задаёт пространство,
ширину и порядок ID. `automatic_checks` сопоставляет изменённые пути и этапы с
проверками, `batch` задаёт пределы пакетов, артефакты, шаблоны и источник
сообщений; `sprint` задаёт лимиты, допустимые конечные состояния и шаблоны.
`task_decomposition` определяет классы навыков и ответственность областей;
`runtime_services` — профиль runner, вывода, handoff и transfer;
`accounting` — источники, категории, календарь, tokenizer и пределы учёта.
Значения в примере не являются настройками произвольной площадки.

В каждом workflow-примере `goal_type` выбирает вид цели, `benefit` описывает
назначение, `worktree_required` задаёт потребность в отдельном checkout,
`route.entry` — первый этап. `stages` задаёт ID, роль, handler, инструкцию,
разрешённые пути, секции, артефакты, переходы и допустимые цели возврата;
`content_contract` задаёт требования к секциям и маршрутам содержимого.
В определении хука `events` связывает события с обработчиками,
`gate_operations` ограничивает операции, `probes` проверяет capabilities,
`context_template` и `stop_template` задают вывод агенту; `agent_id`,
`message_source`, `id` и `schema` задают идентичность и формат.

Пути с `/ABSOLUTE/PATH/TO/` и `YOUR_PRIMARY_CHECKOUT_BRANCH` в примерах
обязательно заменяются значениями действующей установки. В частности,
`git.base_ref` должен совпадать с веткой, которая уже выбрана в основном checkout;
он не требует переключения checkout на `master`. Исторически попавшие в Git
рабочие конфиги не включаются в новые коммиты; эта операция не переписывает
существующую историю Git.

или уже назначенная Task не исполняется из собственного `worktree/src`: эта директория остаётся
предметом разработки, проверки и project-bound probes. Поэтому старая копия AI poise source не может
заблокировать чтение текущей конфигурации, `bootstrap`, `verify` или `handoff`. Выбор source не
изменяет project manifest или binding.

Начать чтение без формальной задачи:

```bash
bash "${AI_POISE_WORK:?Set the launcher path supplied by the native hook}" <<'JSON'
{"operation":"bootstrap","input":{"task":null,"decision":null,"feedback":null,"rework_stage":null},"messages":[]}
JSON
```

После проверки результата чтения завершить ту же сессию:

```bash
bash "${AI_POISE_WORK:?Set the launcher path supplied by the native hook}" <<'JSON'
{"operation":"verify","input":{"result":null,"artifacts":[]},"messages":[]}
JSON
```

Для новой сессии без задач ожидаются `read_only` и `read_only_verified`. Последний статус
подтверждает завершение
runtime, а не содержательную проверку ответа: список `checks` пуст. Пустой `messages` в этих
проверочных командах не
означает, что пользовательских сообщений не было. В обычной работе hook-транспорт подставляет
зарегистрированные
нативные события; прямой диагностический вызов с `messages=[]` демонстрирует работу без их
регистрации и не
восстанавливает события, пропущенные до подключения. Правила наблюдаемых событий описаны в
[контракте
пакета](../workflows/batch-work.md#пользовательское-сообщение).

### Выбор ветки основного checkout для интеграции

Перед первоначальной настройкой возьмите выбранный абсолютный checkout из анкеты.
Перед исправлением `git.base_ref` и вызовом публичного `integrate` прочитайте
точный `git.repository` из рабочего manifest. Только для выбранного checkout
выполните команды чтения:

```bash
git -C "/absolute/path/to/primary-checkout" rev-parse --show-toplevel
git -C "/absolute/path/to/primary-checkout" worktree list --porcelain -z
git -C "/absolute/path/to/primary-checkout" symbolic-ref --quiet --short HEAD
git -C "/absolute/path/to/primary-checkout" symbolic-ref --quiet HEAD
```

Замените путь в примере выбранным checkout; для действующего проекта это значение
`git.repository`. Сверьте фактический корень с ним и по списку worktree убедитесь,
что выбран основной checkout репозитория, а не дочернее дерево Task. Успешный
`symbolic-ref` даёт имя выбранной ветки; если
`HEAD` detached, команда завершится ошибкой. При detached `HEAD`, неясной привязке
основного checkout или другом неразрешённом состоянии остановите настройку либо
интеграцию и получите точное решение о ветке у владельца checkout. Не выбирайте
ветку по имени из примера и не переключайте основной checkout ради значения manifest.

Сравните полный наблюдаемый ref `refs/heads/<имя>` с `git.base_ref` рабочего
manifest: короткое имя и полный ref могут обозначать одну ветку. Проверьте commit
наблюдаемой ветки в том же checkout, заменив оба значения примера:

```bash
git -C "/absolute/path/to/primary-checkout" rev-parse --verify --end-of-options 'YOUR_PRIMARY_CHECKOUT_BRANCH^{commit}'
```

При несовпадении исправляйте `git.base_ref` только через [публичное обновление
проекта](#обновление-действующего-проекта) с точной наблюдённой revision и
`manifest_edits` для `git.base_ref`. Наличие незавершённых Task не запрещает эту
правку; редактор сохраняет ресурсные блокировки и проверку revision. Отказ по
этим проверкам не даёт основания менять ветку checkout или править managed JSON
вручную. При начальной
настройке задайте в анкете уже наблюдаемую ветку. У Git нет требования использовать
`master`.

Выбор target не переносит подготовку в основной checkout. Принятый результат
обновляется и проверяется в существующем дочернем worktree Task. Только отдельно
разрешённый публичный `integrate` сравнивает `expected_target_commit` с текущим
commit настроенного `git.base_ref`, повторно читает target под блокировкой
публикации, проверяет привязку основной рабочей копии и выполняет локальный
`git merge --ff-only <task-branch>`. Чужие изменения основного checkout и рабочий
manifest сохраняются; `git push` запрещён. Подробный lifecycle находится в
[интеграции завершённого
результата](../governance/development-rules.md#интеграция-завершённого-результата).

Проверка оператора при выборе назначения и [ранний допуск
интеграции](../workflows/batch-work.md#ранняя-проверка-назначения-интеграции) имеют
разные моменты выполнения. Новая интеграция и незавершённый кандидат проверяют
фактические корни, общий Git-каталог, активные ветки и зарегистрированное дерево Task
до изменений кандидата или состояния. При отказе диагностика содержит настроенные
и наблюдённые значения и способ исправления. После поддерживаемого исправления
повторяется исходный запрос; поздние проверки публикации продолжают действовать.

Передавайте путь целиком одним аргументом, сохраняя его значимые символы. Пробелы,
табуляция, CR и LF могут входить в имя папки; нельзя нормализовать их через `strip`
или восстанавливать путь из preview. Для машинного чтения списка worktree используйте
полный NUL-разделённый вывод. Полный ref и Git path относятся к разным данным:
сравнение веток не разрешает менять написание пути.

соответствующего управления в Codex App нужно проверять в установленной версии. Генерация файла,
успешная локальная

способом восстановить выбранное окружение, затем повторить нативное событие Codex. AI poise не
подменяет interpreter и не выдаёт отдельную команду восстановления; сохранённая в

доказывают доставку native events. Это диагностический вход, а не замена hook-источника сообщений.

спринта и эталонная
БД здесь не импортируются.


### Каталог конфигураций и расположение задач

Рабочие данные находятся в `projects/ai-poise/`, конфигурации — отдельно в
`config/projects/ai-poise/`. Основной файл
`project.json` соседствует с receipt и подкаталогом `config/workflows/` из 13 конфигураций. Имя
manifest задаётся в
настройках генератора и не является требованием JSON-формата; текущий публичный генератор публикует
целый новый каталог.
Один файл `config/projects/ai-poise.project.json` не заменяет весь комплект.

Изменение размещения выполнено повторной публикацией нового комплекта штатным инструментом после
сохранения исходного
комплекта. Рабочих задач в первоначальной базе не было; её проверочные журналы сохранены отдельно,
не перенесены как
задачи. Текущая база создана runtime в новом месте. Lock генератора находится в
`projects/.project-setup.lock` и
исключён из Git.

Самостоятельная Task хранит файлы в
`projects/ai-poise/standalone/<task-id>/`. Для Task с сохранённым `sprint_id` единый
владелец путей выбирает `projects/ai-poise/sprint/<sprint-id>/task/<task-id>/`; Sprint-level
артефакты остаются в `projects/ai-poise/sprint/<sprint-id>/`. Конфигурация обязана содержать
`paths.standalone_tasks`; прежнее `paths.tasks` отклоняется без alias, fallback или dual read.
Существующие каталоги прежнего формата не переносятся автоматически. Ответственный агент
перемещает только конкретную мешающую запись по отдельному разрешённому lifecycle и сообщает
об этом; само наличие исторического каталога не включает совместимость.

При публикации изменения самого имени корня действующая установка требует отдельного ручного
cutover. Ответственный агент через публичный inventory фиксирует каждую сохраняемую Task и её
`sprint_id`, сопоставляет этот inventory с каждым каталогом прежнего `task/<task-id>/` и заранее
проверяет отсутствие всех целевых путей. После успешной публикации и доказанного отсутствия
процессов Poise, пишущих рабочие данные, он перемещает каждую запись отдельным атомарным rename:
Task с `sprint_id=null` — в `standalone/<task-id>/`, Task с `sprint_id` — в
`sprint/<sprint-id>/task/<task-id>/`. Статус Task не меняет её owner: завершённые и исторические
записи маршрутизируются по сохранённому `sprint_id`, а неизвестный inventory каталог блокирует
cutover до отдельного решения о его владельце. После перемещения агент проверяет отсутствие
старых путей и наличие каждого ожидаемого нового пути. Переименовывать весь смешанный `task/`,
оставлять одновременно два доступных корня, создавать symlink, копировать данные либо добавлять
runtime fallback запрещено. Если отсутствие писателей или полное однозначное соответствие
источников и целей не доказано, публикация остаётся заблокированной.

### Явное подключение development routing AI-poise

`project-config` допускает один именованный новый раздел `development_routing`,
переданный целиком через `manifest_edits`: `path=["development_routing"]`. Это не

## Workflow: имя и размещение графов этапов

Принято пользователем 2026-10-15. Это договор новой версии Poise и нового
формата конфигурации с потерей обратной совместимости. Рабочие конфиги, код и текущие данные
poise-op переведены на новое имя.

Граф прохождения этапов задачи называется `workflow`. Основной конфиг проекта
выбирает собственные графы через `workflows`; прежний ключ `processes` заменяется
во всех действующих конфигах и примерах. Читатель нового формата использует
новое имя без чтения прежнего ключа. Системные процессы и обработка сообщений
к этому переименованию не относятся.

Собственные графы проекта — изменяемые данные работы над задачами. Общий
каталог примеров и шаблонов остаётся отдельным набором: изменение примера
не подменяет собственный граф проекта или сохранённый граф существующей Task.
Конфигурация задаёт выбранный файл. Абсолютное значение используется как
задано; относительное вычисляется как
`Path(config_path).resolve().parent / workflows[goal_type]`.
Чтение и запись используют одинаковое правило. Размещение файла вне
каталога конфигурации или внутри корня данных разрешено. Проверка кандидата
использует его документы в памяти и не записывает их в рабочие файлы.

Для poise-op рабочее назначение собственных графов:
`/home/sbwerewolf/workdata/poise-project-data/poise-op/workflows/<goal_type>.json`.
Переключение выполняется в порядке: копирование в рабочее назначение,
проверка чтения и выбора того же назначения для записи, удаление ровно
перенесённых исходных файлов. Поздние изменения назначения сохраняются.
Дополнительные резервные копии, архивы и снимки не создаются.

Переименование текущего формата сохраняет собственные графы Task и Sprint,
этапы, итерации, версии, владение, требования, связи, WIP и ожидающие операции.
Исторические журналы, отправки и квитанции не переименовываются. Продолжение
корректного текущего состояния не зависит от проверки происхождения по старым
квитанциям; текущие правила владения и завершения ожидающих операций действуют.

Общие примеры находятся в `config/catalogue/workflows/`, исходные шаблоны
графов — в `config/catalogue/workflow-templates/`, заготовки задач — в
`config/catalogue/task-templates/`. При создании Task заготовка объединяется
с выбранным графом проекта. Изменение общего шаблона не меняет существующие
проектные графы и задачи.

При явном преобразовании текущего формата меняются только согласованные
структурные поля. Черновик без собственного графа остаётся без него; текстовые
исторические разрешения сохраняются дословно. Преобразователь не вызывается
автоматически при обычном чтении. БД других проектов этим переносом не изменялись.
