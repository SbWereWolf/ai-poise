# Домены, агрегаты и инварианты

Создано: **2026-09-06T16:04:53+05:00**.

Статус: **проект архитектуры для реализации; код продукта не изменён**.

## 1. Архитектурное решение

DDD принимается как инвариант проектирования: правила выражаются на языке предметной области, имеют конкретного владельца и не обходятся через CLI, runner, SQL или произвольное изменение полей. DDD здесь не означает отдельный сервис для каждой сущности и не означает обязательный базовый класс для всех объектов.

Применяем модульный монолит. Границы проверяются через публичные контракты библиотек и направление импортов. Задача и спринт — самостоятельные доменные модули и агрегаты. Они находятся в одном контексте управления работой: у них общий язык требований, этапов, принятия и отмены, а публикация спринта должна согласованно создавать задачи.

Семь handler-семейств — прикладные стратегии исполнения этапов, не семь новых доменов. Тринадцать goal types — независимые конфигурации процессов, не тринадцать отдельных реализаций модели Task.

Подход к явным границам моделей, агрегатам, Repository и Unit of Work опирается на [S1–S4](../sources.md). Конкретные границы и локальные транзакционные исключения ниже — решения для данного Harness, а не универсальные требования DDD.

## 2. Контексты и библиотеки

| Контекст | Библиотеки | Собственная модель | Что получает извне |
|---|---|---|---|
| Управление работой | `tasks`, `sprints`, `content`, `processes`, `verification` | Цель, контракт задачи, этап, итерация, находка, предложение исправления, доказательство, принятие, зависимости | Наблюдаемые состояния и receipts, сведения о сохранённых артефактах, пользовательская инструкция |
| Исполнение и ресурсы | `sessions`, `workspaces`, `executions`, `artifacts` | Привязка сессии, рабочее дерево, точный запуск, фактический результат, файл владельца | Разрешённый план действий и область выполнения; не право принимать этап от имени пользователя |
| Учёт результата и затрат | `metrics` | Usage event, рабочий интервал, зачёт и отзыв пользы, причина затрат | Типизированные события работы, измеренный собственный результат, реальный usage |
| Прикладная координация, не новый бизнес-контекст | `application`, `operations` | Сценарий вызова, шаг операции, повтор, receipt, готовый ответ | Публичные контракты перечисленных библиотек |
| Общая основа | `foundation`, `configuration`, `observability`, адаптеры | Идентификаторы, типизированные ссылки, версии, проверенная конфигурация, диагностика | Не владеет жизненным циклом Task/Sprint |

`content` — переиспользуемая доменная библиотека, а не независимый сервис записи любых данных. Она реализует слои секций и ссылки; применять их к конкретной задаче разрешает Task, к спринту — Sprint. Внешний API не отдаёт обходной `content.update_any_owner`.

## 3. Единый словарь

| Термин | Точный смысл |
|---|---|
| `Task` | Работа ради одной цели одного goal_type; хранит весь содержательный результат, включая прошлые подходы |
| `Sprint` | Цель набора задач, принадлежность и DAG зависимостей только внутри спринта; не контейнер всех mutable объектов Task |
| `ProcessDefinition` | Полностью определённый неизменный снимок независимого route config |
| `StageDefinition` | Описание одного узла: handler, фазы, вход, проверки, выход, переходы |
| `StageIteration` | Один конкретный подход к этапу; его результат может быть представлен, проверен и принят либо возвращён |
| `Submission` | Содержательный пакет агента для разрешённой фазы: секции, методы, findings, аргументы, пути и сообщение коммита |
| `VerificationAttempt` | Конкретная попытка исполнения проверок для submission и наблюдаемого состояния; не новая итерация только из-за повтора тестов |
| `Evidence` | Связанный с предметом и методом результат проверки/аргумент; его наличие, актуальность и содержательное принятие различаются |
| `Finding` | Недостаток предмета осмотра с происхождением; статистическая классификация зависит от предъявленного результата, а не только названия этапа |
| `ResolutionProposal` | Предложение исправления с доказательствами; не решение о принятии собственного исправления |
| `UserDecision` | Записанный смысл однозначной инструкции пользователя с областью действия; не произвольное `accepted=true` |
| `WorkCycle` | Работа после инструкции пользователя до доклада; привязана к сессии и максимум одной формальной задаче |
| `Operation` | Составной прикладной вызов, возможно с внешними шагами; не цель и не этап задачи |
| `ExecutionReceipt` | Наблюдение executor о фактически выполненной команде/эффекте; само не меняет состояние задачи |
| `ArtifactRef` | Внутренняя ссылка на зарегистрированный файл в runtime/task/sprint; публичный ввод агента остаётся путём |
| `WorkspaceResultRef` | Результат в целевой кодовой базе: codebase + revision/tree + relative path; не внутренний artifact Harness |
| `UnitOfWork` | Короткая транзакционная сессия репозиториев, не LLM work cycle и не весь verify |

Метод домена выражает действие: `accept_iteration`, `request_rework`, `waive_finding`. Методы `set_status`, `update_json` или универсальный mutable словарь не являются публичным доменным API.

## 4. Агрегат Task

Task — владелец правил текущего контракта, разрешённой итерации и её изменения. В его согласованную область входят текущие ссылки на слои секций, требования/DoD, definitions методов, обязательства проверки, активные findings, предложения исправлений, решения и результаты этапов.

Большая история связана с Task, но не обязана каждый раз загружаться в память. Для команды repository загружает root и необходимые текущие дочерние данные. Старые immutable слои читаются отдельным Query API. Ни обработчик, ни агент не редактирует исторический слой напрямую.

Основные операции:

| Метод | Доменные проверки | Результат |
|---|---|---|
| `Task.create(contract, process)` | Один goal_type; собственный creation contract; явные applicability и точные существующие методы | Новая валидная task или определённая ошибка входа |
| `begin_iteration(transition, entry_subject, authority)` | Разрешённый route edge; предыдущий этап принят там, где требуется; одна активная итерация | Новый подход и его входное состояние |
| `apply_submission(submission, phase_contract)` | Разрешённая фаза, авторство полей, scope, полнота/типы ссылок | Кандидатное состояние и новые содержательные слои |
| `attach_observations(observations)` | Правильные предмет, метод, попытка и owner | Evidence без вымышленного user acceptance |
| `propose_resolution(finding, proposal)` | Находка актуальна; предложение не самоутверждается | Сохраняемое предложение исправления |
| `record_inspection(result, reviewed_subject)` | Осмотр относится к зафиксированному результату; предмет не изменён осмотром | Coverage, findings и отдельные решения осмотра |
| `mark_verified(gate_assessment, finalization_receipts)` | Выполнены именно условия текущего этапа; актуальные доказательства; сохранность/публикация соблюдены | Verified iteration и доклад, не следующий этап |
| `accept_iteration(decision)` | Решение пользователя относится к предъявленному результату | Принятие; разрешение продолжения учитывается отдельно |
| `request_rework(decision, target_stage)` | Допустимая цель возврата, причина и область | Новая итерация и точная инвалидация зависимых результатов |
| `waive_finding(decision)` | Пользовательская санкция и конкретная находка | Waiver, не фиктивное исправление |
| `complete(assessment)` | Финальный контракт выполнен, последняя требуемая работа принята | Completed и неизменный снимок результата |
| `cancel(decision)` | Только санкционированное прекращение | Cancelled с причиной; обычная приёмка/тесты не запускаются |

`gate_assessment` не приходит от модели как голый флаг. Прикладной слой получает его от доменных проверок `verification` и адаптированных фактических receipts. Конфиг выбирает правила, домен запрещает обход этих правил.

Классификация результата `available/active/blocked/completed/cancelled` может вычисляться из lifecycle, текущего binding и blockers. Не требуется хранить несколько независимо редактируемых копий одного статуса. Внешнее представление сохраняет согласованные значения; изменение внутренней модели не вводит новый terminal `failed`.

## 5. Агрегат Sprint

Sprint владеет целью и требованиями спринта, своим содержимым, принадлежностью задач, графом зависимостей, решениями об отмене ветвей и результатом спринта. Он хранит идентификаторы участников и компактные факты их состояния, а не вложенные mutable Task.

| Метод | Что делает | Чего не делает |
|---|---|---|
| `publish(plan, task_contract_facts)` | Проверяет готовый план, refs, собственные validators задач и DAG | Не дописывает отсутствующие условия дочерних задач |
| `revise_plan(change, observed_versions, authority)` | Меняет план в разрешённой области без уничтожения завершённых результатов | Не меняет активную работу другого агента под ногами |
| `add_dependency(source, target, readiness_contract)` | Проверяет членство, отсутствие цикла, явный способ доступности результата | Не создаёт межспринтовую зависимость |
| `decide_cancelled_dependency(decision)` | Записывает судьбу зависимой работы | Не считает cancelled predecessor успешным |
| `evaluate_progress(task_facts, readiness_facts)` | Вычисляет весь eligible set и blockers | Не выбирает модель/агента и не запускает задачи |
| `assess_closure(task_facts, sprint_evidence)` | Проверяет целостность и условия закрытия | Не включает full product test без санкции |
| `complete(closure_assessment)` | Фиксирует нормальный результат | Не маскирует незавершённые задачи |
| `cancel(task_ids, reason)` | Отменяет Sprint и возвращает незавершённых участников для Task-owned transitions | Не переписывает completed/cancelled и не затрагивает посторонний Sprint |

Домен Sprint не вызывает TaskRepository и не выполняет цикл `task.cancel()` самостоятельно. Координатор получает от Sprint список разрешённых действий по членам и применяет команды Task через их API. Все такие действия остаются в области выбранного спринта.

Граф зависимостей отвечает на два вопроса: принят ли нужный результат и доступен ли он successor. Совпадение имён файлов или сам по себе Git ancestry не заменяет явно заданный контракт доступности.

## 6. Остальные согласованные границы

`WorkSession` владеет current binding, одним рабочим циклом и фактом прекращения работы. Он не владеет бизнес-результатом Task. Чтение другого спринта не меняет binding. Аренда одной задачи двумя агентами и cancel в середине verify не проектируются как пользовательские сценарии; проверка согласованности binding остаётся защитой от ошибочного вызова.

`ExecutionAttempt` владеет фактом запуска и receipt. Executor знает точный invocation, cwd, среду, лимит и парсер. Он не знает, должна ли задача завершиться при отрицательном вердикте продукта. Интерпретацию относительно контракта делает `verification`.

`ArtifactEntry` владеет идентичностью файла в области владельца и его техническими фактами. Он не хранит выдуманную агентом семантическую классификацию. Ограничения path/count принадлежат контракту; бизнес-связь с evidence делает владелец задачи/спринта.

`Operation` владеет шагами составного сценария и повторяемостью. Это не task state machine. Успешный SQL commit не означает, что Git push или внешний транспорт также состоялись.

`Metrics` принимает факты затрат и зачёта результата. Он не объявляет Task завершённой и не меняет её goal_type. Его строки — источник учёта, а не источник разрешённых действий агента.

Ссылка из другой задачи на finding/evidence является значением `TaskRecordRef(task_id, record_revision_id)`, а не ссылкой на изменяемый дочерний объект. Чужое содержимое читается через Query API владельца; чужая находка не редактируется через такую ссылку. Для исправления сохраняется собственный ResolutionProposal и связь с исходным immutable record. Это сохраняет aggregate boundary и одновременно не требует копировать чужое evidence.

## 7. Общая библиотека содержимого без общего «бога-объекта»

Повторно используются `SectionBook`, `SectionRevision`, `TraceLinks`, схемы проверяемых ссылок и алгоритмы состояния `empty/template/populated`. Эти компоненты композиционно входят в Task и Sprint. Это не наследование `Task(BaseWorkItem)` / `Sprint(BaseWorkItem)` с десятками неиспользуемых полей.

Например `Task.apply_submission()` и `Sprint.revise_plan()` используют один `SectionBook.append()`, но каждый проверяет собственный контракт и разрешение изменения. В `content` не появляется знание о порядке этапов development, а в task/sprint не копируется алгоритм подсчёта digest секции.

## 8. Инварианты проектирования кода

| ID | Инвариант |
|---|---|
| DDD-01 | Значимое бизнес-правило имеет владельца-домен и названный метод/политику; не дублируется в CLI и SQL adapter |
| DDD-02 | Чужой агрегат изменяют через его публичный API; чужую таблицу — только соответствующий mapper, вызванный repository/UoW |
| DDD-03 | Домен не импортирует SQLite, subprocess, OS filesystem, HTTP/MCP SDK и не обращается к текущему времени/глобальному config |
| DDD-04 | Наблюдаемые факты, ID, время и проверенная политика передаются явно; отсутствующий обязательный config не получает default/fallback |
| DDD-05 | Все точки входа используют один application API; hook не имеет обходного права изменить task status |
| DDD-06 | Task и Sprint — разные библиотеки; одинаковая механика секций/сохранения композиционно общая |
| DDD-07 | Handler не присваивает state root и не запускает соседний этап; Task и RoutePolicy проверяют предлагаемый переход |
| DDD-08 | Запросы не изменяют бизнес-состояние; bootstrap объявлен командой, show — запросом |
| DDD-09 | Текущий результат и append-only история разделены; повтор submission не размножает слои, новый объект проверки допускает новый attempt |
| DDD-10 | Проверенное дерево, коммит и receipt публикации относятся к одному результату; внешний эффект не покрывается SQL-транзакцией |
| DDD-11 | Incidents не смешиваются с обычным непрохождением теста; сами Incidents не скрываются из доклада |
| DDD-12 | Каждая таблица, файл состояния, команда и проекция имеют одного владельца записи |
| DDD-13 | Синхронные решения, влияющие на доступность следующей работы, не зависят от async metrics/parser worker |
| DDD-14 | Код общих механизмов не ветвится по 13 goal_type; процессы независимы и заданы явно |

Это архитектурные ограничения проекта. Предметные исключения пользователя относятся к процессу в указанной области; они не разрешают повреждать БД, обходить сохранение решений или подменять проверку.
