# Известные баги и ограничения AI poise

Основание: полный обзор снимка `61151e59e3e068f7680444b20154cfeeaf3ecab1`
и последующие указания пользователя. Здесь находятся **только актуальные неисправленные
замечания**, включая явно принятые риски. Это не список автоматически созданных Task.

## Ведение реестра

В каждой записи сохраняются проявление, затронутый путь, доказанная граница и решение
о работе. После исправления и адресной проверки запись удаляется либо сужается до
действительно оставшейся проблемы **в той же правке**. История остаётся в Git, коммите
исправления и архиве обзора; отдельный вечный список закрытых багов здесь не ведётся.
Отложенное исправление, ручной обход и принятие риска не означают, что код исправлен.

Малая очевидная правка по прямому поручению пользователя выполняется без искусственной
Task/Sprint. Независимые замечания не группируются в Sprint; применяются
[правила связности и локальных дублей](../workflows/sprints.md#замкнутость-зависимостей-и-локальные-дубли).
RV2-01 снято из области: его нет среди активных багов. Требования `support`, отдельной
cache-lock подсистемы и защиты от намеренной подмены исходников не возвращаются.

## RV2-02 — прерванная запись индекса кэша

**Статус:** известное ограничение, без поручения добавлять обвязку.

В [test_package_cache.py](../../src/poise/infrastructure/test_package_cache.py)
индекс записывается `Path.write_text` в окончательный путь. Воспроизведённый отказ
оставляет `{` вместо прежнего валидного JSON. Следующее чтение отклоняет record;
первичные stdout/stderr/JUnit прежнего запуска при этом остались.

Уже доступен явный запуск того же пакета с `--fresh`; это новый запуск, не исправление
старого индекса и не повод удалять его primary evidence. Конкурентная часть прежнего
замечания не является практически значимым штатным риском по принятой модели: одно
рабочее дерево принадлежит одной сессии, кэш хранится в этом дереве. Дополнительные
cache-lock, watchdog и протокол перехвата не требуются. См.
[текущий контракт кэша](../configuration/test-package-cache.md#монопольная-запись-через-владение).

Доказательства исходного обзора: `evidence/RV2-02.json` и `RV2-02b.json`.
Конкурентный эксперимент — историческая проверка, а не обязательный новый сценарий.

## RV2-03 — повтор уже применённого удаления этапа

**Статус:** риск принят пользователем; автоматическое восстановление не разрабатывается.

В [project_config.py](../../src/poise/infrastructure/project_config.py) изменение процесса
может быть записано до ошибки записи receipt. В воспроизведении этап `code_review` уже
удалён, а точный retry повторяет `remove_stage`, получает отказ «stage не объявлен»
и оставляет `.pending` без receipt. Это отказ восстановления после конкретного сбоя
записи, не обычная ошибка каждого изменения конфигурации.

По указанию пользователя такая ситуация разбирается и исправляется вручную по факту,
а не расширением кода. Нельзя считать это выполненным исправлением, создавать новую
editor DB, ослаблять проверку произвольного `remove_stage` или вслепую стирать pending.
Разовый разбор должен опираться на фактические process/before/after/receipt.
Доказательство: `evidence/RV2-03.json` и соответствующий apply/retry probe.

## RV2-06 — чтение незавершённого первого caller binding

**Статус:** отложено, без нового поручения на реализацию.

[session_establishment.py](../../src/poise/infrastructure/session_establishment.py)
создаёт файл с `O_CREAT | O_EXCL` перед записью JSON. В контролируемом параллельном
первом вызове второй caller видит пустой файл и получает
`POISE_CALLER_BINDING is unreadable or invalid`. После завершения первого писателя
повтор получает тот же caller ID. Доказаны временный отказ и успешный повтор;
подмена идентичности, два устойчивых ID или повреждение Task DB не показаны.

Не создавать новый caller ID как обход. Доказательство `evidence/RV2-06.json`
использует два потока с остановкой первой записи, не два независимых ОС-процесса.

## RV2-07 — усечение машинных данных в адаптере интеграции

**Статус:** известное отклонение от общего правила; специальная Git-обвязка не создаётся.

В [result_integration.py](../../src/poise/infrastructure/result_integration.py)
`_run` сокращает stdout до `preview_chars`, затем `_git` передаёт этот фрагмент
`_conflicts` для разбора. В реальном merge восемь конфликтов при лимите 300 дают
четыре полных пути и один фрагмент. Это неполный список, не потеря содержимого файлов.

Агент может получить полный текущий список обычным read-only Git в том же своём дереве:

```sh
git -C "$OWNED_WORKTREE" diff --name-only --diff-filter=U -z
```

`OWNED_WORKTREE` — фактический принадлежащий сессии путь, не новый параметр Poise.
Результат NUL-разделённый; его нужно читать целиком, не по строкам preview. Если
инструмент ограничивает экранный вывод, сохранить stdout в свой файл и прочитать его.
Не повторять merge ради вывода и не добавлять исключения для числа/длины конфликтов.

[Общее правило полного вывода](../workflows/runner.md#полный-вывод-и-preview) действует
для всех команд. Runner проверок уже отдаёт пути к полным журналам, но это не означает,
что интеграционный `_run` сохраняет отброшенные им байты. Обход через штатный Git
не исправляет машинное поле `conflicts`, поэтому запись остаётся здесь.
Доказательство: `evidence/RV2-07.json` и probe с реальным Git merge.

## RV2-08 — чужая телеметрия в отчёте ограниченной области

**Статус:** открыто, без новой Task в этом изменении.

[accounting_queries.py](../../src/poise/infrastructure/accounting_queries.py)
применяет `include(binding)` к основным событиям, но не к циклу необязательной
телеметрии. Три проверки проекции показали двухсекундное наблюдение чужой Task
в `active_seconds` и группе `foreign-task` отчётов, ограниченных Task, Sprint или
проектом. Контроль с совпадающей областью проходит.

Полный CLI-путь не проверялся; ошибки всех счётчиков токенов или финансовой оценки
из этого не следуют. Доказательства: `evidence/RV2-08-task.json`, `RV2-08-sprint.json`,
`RV2-08-project.json` и `probes/test_accounting_scope.py`.

## Неактуальная подготовка backup-теста

**Статус:** тестовая фикстура, не продуктовый дефект.

В [tests/backups/test_service.py](../../tests/backups/test_service.py)
`test_create_rejects_non_database_without_success_or_leftover_copy` вызывает
`mkdir(parents=True)` на уже существующем каталоге и получает `FileExistsError`
до продуктового вызова. Исправлению подлежит подготовка, а не backup service.

## Неактуальная подготовка двух transfer-тестов

**Статус:** тестовые фикстуры, не продуктовая регрессия.

В [tests/transfer](../../tests/transfer) сценарии сохранения посторонней задачи и
отказа замены существующего ID не подготавливают destination Requirements Registry
для предварительно создаваемой Task. Они падают до импорта. В обзоре оба исходных
тела прошли после предоставления только отсутствующего предусловия в отдельной
фикстуре. Исправление исходных фикстур пока не внесено.

## Устаревший пример Evidence

**Статус:** пример, без изменения продуктового контракта.

[examples/evidence_demo.py](../../examples/evidence_demo.py) меняет requirements,
оставляя прежний snapshot/agreement. Сценарий `logical` с рабочим caller binding
отклоняется: `Task requirements snapshot does not match Task requirements`.
При исправлении примера нужно согласовать его исходные данные с текущим контрактом,
а не отключать проверку snapshot.

## DUP-REUSE — завершение дубля по готовому семейному результату

**Статус:** известная незавершённая возможность; не обходить через force.

Создание явного семейства, общий библиотечный reader и допуск этапа реализованы.
Положительно завершённый родственник имеет расстояние 0 и блокирует повторную реализацию
незавершённого дубля. Однако отдельного публичного lifecycle-пути, который проверяет
включение результата в `base_ref`, доступность в локальной ветке и требования, а затем
оформляет локальный verification-only reuse без повторного исполнения процесса, пока нет.

Отказ `family_ahead` остаётся корректным. `force_duplicate_start=true` его не снимает;
нельзя переписывать расстояние, статус, Task history или копировать чужие test receipts.
Ожидающий дубль не объявляется выполненным и его зависимости не считаются удовлетворёнными.
Разработка этого пути требует явного контракта локальной проверки и принятия результата.
См. [готовый семейный результат](../workflows/sprints.md#готовый-семейный-результат-и-база-ветки).

## Происхождение доказательств и границы

Полный исходный обзор и probes: Gmail `1a0b6667369a5102`;
проверенное обратное восстановление: `1a0b667895c7602d`.
SHA-256 архива обзора:
`b430cfffe848c31f6f996ae83b36ff551b811d63b095603370504ed486a0ca1b`.
Пути `evidence/` и `probes/` выше относительны этому архиву, а не checkout продукта.

Запуск permission-теста под root и прерванные контейнерным лимитом выборки не
добавляются как продуктовые баги. Отсутствие автоматического контроля всей политики
планирования не освобождает агента от её соблюдения; граница текущего graph validator
описана в [Sprint workflow](../workflows/sprints.md#замкнутость-зависимостей-и-локальные-дубли).
