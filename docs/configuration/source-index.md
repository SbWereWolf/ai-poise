# Поиск по индексу выбранной рабочей копии

## Назначение и подготовка

`poise source-index` использует явно выбранный установленный `ast-index` для поиска
в исходниках продукта. Команда работает без Task: общий профиль выбирает проект,
а `--checkout` — корень его зарегистрированного Git checkout или worktree.
Перед поиском выполняется обновление индекса сохранённых файлов этой копии.

Подготовьте [общий профиль команд и сессии](project-setup.md#общий-профиль-команд-и-сессии),
установленный Python пакета Poise и внешний executable. Передавайте абсолютные пути
`--config`, `--checkout`, `--policy`. Профиль должен указывать действительный основной
Git checkout; выбранное дерево должно быть зарегистрировано в том же репозитории.
Путь не выводится из расположения Poise или текущего каталога вызывающего процесса.

Используйте версионируемые примеры этой поставки:

- [Политика поиска](../../config/examples/source-index-policy.example.json).
- [Bash adapter для Git](../../config/examples/source-index-post-commit.example.sh).
- [Конфигурация command handler](../../config/examples/source-index-handler.example.json).

Заполненные рабочие файлы храните вне source Git. Примеры доступны в исходной поставке;
их наличие внутри wheel не предполагается. Сам пакет потребитель устанавливает своей
системой управления пакетами с явно выбранной версией.

В корне индексируемого продукта постоянно хранится рабочая `.ast-index.yaml`.
Настройте `include` под его каталоги исходников; для Poise есть
[пример](../../config/ast-index.example.yaml) и
[пояснение локальной настройки](../workflows/code-navigation.md#заполнение-конфигурации).
Не копируйте профиль поверх собственных настроек повторно. Обёртка не заменяет YAML
на время вызова и не включает `--no-ignore`.

Заранее исключите рабочий YAML и область данных из Git. Пример для выбранного продукта:

```gitignore
.ast-index.yaml
.runtime/
```

Пути БД, блокировки и результатов должны находиться внутри выбранного checkout и
быть Git-ignored. Это проверяется до записи. У каждого дерева собственные ресурсы.
В примере wrapper использует `poise.lock`: он отличается от `index.lock` самого
`ast-index`. Блокировку не удаляют для обхода занятой операции.

## Политика и явные значения

Скопируйте пример политики в рабочее место и заполните все известные поля.
Числа и пути примера не являются значениями по умолчанию.

| Поле | Тип и назначение |
|---|---|
| `schema` | Строка `poise-source-index-policy-1`. |
| `enabled` | Boolean: включение внешнего индексатора. |
| `command_argv` | Непустой список непустых строк: executable и его явные начальные аргументы. |
| `query_commands` | Непустой список уникальных имён разрешённых read-only подкоманд. Имена не начинаются с `-`; `update` и `rebuild` здесь недопустимы. |
| `paths.database` | Относительный путь БД, например `.runtime/ast-index/index.db`. |
| `paths.lock` | Относительный путь отдельной wrapper-блокировки, например `.runtime/ast-index/poise.lock`. |
| `paths.runs` | Относительный каталог полных результатов, например `.runtime/ast-index/runs`. |
| `limits.lock_seconds` | Положительное конечное число секунд ожидания блокировки. |
| `limits.lock_poll_seconds` | Положительный конечный интервал проверки блокировки. |
| `limits.run_seconds` | Положительный конечный предел отдельного внешнего процесса. |
| `limits.cleanup_seconds` | Положительный конечный предел завершения процесса и захвата. |

Обязательные известные поля, их типы и значения проверяются. Пути не содержат
абсолютного адреса, пустых компонентов, `.`, `..`, обратной косой черты или NUL.
Неизвестные опции в корне политики, `paths` и `limits` игнорируются при исполнении;
их исходные значения остаются в файле. Политика читается, но не переписывается.
Это отличается от строгого API-запроса: лишнее поле запроса вызывает отказ.

Выбирайте executable, который работает в фактическом окружении Git callback,
включая его `PATH`, а не только в интерактивном Bash. Установленный npm launcher
может зависеть от Node и настроек shell; в проверенном окружении использовался
явно выбранный native executable `ast-index 3.50.0`. Подстановка другого пути,
исправление глобального Node или автоматическая установка не выполняются.

## Запросы и первоначальный индекс

Оператор заранее задаёт абсолютные пути к установленному Python Poise, общему
профилю, checkout и заполненной политике:

```bash
index_python=/absolute/path/to/installed/python
index_profile=/absolute/path/to/project-profile.json
index_checkout=/absolute/path/to/registered/checkout
index_policy=/absolute/path/to/source-index-policy.json
index_cli=( "$index_python" -I -B -m poise source-index
  --config "$index_profile" --checkout "$index_checkout" --policy "$index_policy" )
```

Каждый вызов читает один JSON с ровно двумя полями `operation` и `arguments`.
Сначала проверьте состояние:

```bash
"${index_cli[@]}" <<'JSON'
{"operation":"status","arguments":[]}
JSON
```

При отсутствии индекса выполните первоначальное построение явно:

```bash
"${index_cli[@]}" <<'JSON'
{"operation":"rebuild","arguments":[]}
JSON
```

Для обновления существующего индекса:

```bash
"${index_cli[@]}" <<'JSON'
{"operation":"update","arguments":[]}
JSON
```

Поиск принимает аргументы разрешённой внешней подкоманды:

```bash
"${index_cli[@]}" <<'JSON'
{"operation":"query","arguments":["search","net_total","--format","json"]}
JSON
```

`net_total` здесь — искомое имя; замените его предметным символом продукта.
`arguments` — список строк, для `status`, `rebuild`, `update` он пуст.
При `query` список непуст и начинается с имени из `query_commands`.
Поиск без БД возвращает реальную невозможность работы; скрытого rebuild нет.

`query` удерживает одну межпроцессную блокировку на проверке состояния,
обновлении и поиске. Учитываются сохранённые изменения без нового коммита.
Запрос этой же копии ждёт занятую операцию в пределах своего явного лимита,
другая копия использует собственную блокировку. Наблюдённая смена HEAD во время
операции даёт `inconclusive`; атомарный снимок всего дерева не обещается.

`status` подтверждает состояние выбранной БД через настоящий `stats` и её наличие,
а не актуальность всех исходников. Нулевой exit внешнего процесса с сообщением
об отсутствии индекса не является готовностью. Для Python в проверенном
`ast-index 3.50.0` поиск подтвердил определения и текстовые совпадения, `refs` —
импорты; `usages net_total` вернул пустой результат. Полнота Python call graph
и семантические проверки IDE этим механизмом не подтверждаются.

## Git callback и цепочка hooks

Из собственного `post-commit` и `post-merge` вызывайте поставляемый adapter явно
через Bash, передав выбранные установленные Python, профиль и политику:

```bash
bash /absolute/path/to/source-index-post-commit.example.sh \
  /absolute/path/to/installed/python \
  /absolute/path/to/project-profile.json \
  /absolute/path/to/source-index-policy.json
```

Adapter получает корень через Git в контексте текущего callback и вызывает
`update` этой зарегистрированной копии. Это покрывает обычные коммиты, merge и
коммиты штатных инструментов, когда к ним подключён тот же Git hook.
Он не устанавливает hooks и не меняет `core.hooksPath`. При добавлении вызова
сохраните существующие команды, их порядок и обработку ошибок в операторском
script; не заменяйте весь hook одним `exec`, если после него есть другая работа.

Ошибка обновления после коммита не отменяет уже состоявшийся Git commit.
Сохраните полный ответ callback, устраните указанную причину и явно обновите
индекс; последующий `query` также требует успешного обновления до поиска.

Для контекста агента есть отдельный необязательный command/sync handler из
третьего примера. Заполните его абсолютные аргументы и включите конфигурацию
в нужную позицию существующего
[маршрута цепочки](runtime-hooks.md#определение-и-порядок-конфигураций).
Остальные конфигурации и их порядок сохраняются. Установка и доставка событий
остаются у существующих владельцев runtime, а не у `source-index`.

Режим `--handler` принимает существующий `poise-hook-handler-input-1`, вызывает
только `status`, возвращает исходный `invocation_id`, сохраняет response и
добавляет контекст через общий `append_context`; control — `continue` с null reason.
Это сообщение о состоянии не заменяет Git обновление или явный поиск.
В примере внешний предел handler равен 90 секундам, cleanup — 3 секундам,
`on_error=stop`; согласуйте их с выбранными limits и действительной цепочкой.

При `enabled=false` индексатор не запускается, БД не изменяется, дополнительные
индексные сведения в handler response не добавляются. Остальные настроенные
handlers продолжают свой обычный путь. Корректные binding, известные поля политики
и форма запроса требуются и в отключённом режиме.

## Полный результат и восстановление

CLI возвращает полный машинный JSON с полями `schema`, `operation`, `status`,
`checkout`, `database`, `reason`, `recovery`, `observations`.
Каждое наблюдение содержит имя операции и полный execution receipt. Полные
stdout/stderr внешнего процесса находятся в указанных там файлах; ответ поиска
читайте из `execution.stdout` наблюдения `query`. Причина отказа и действие
восстановления сохраняют фактический исход процесса и выбранные пути.

Машинные данные не обрезаются по бюджету отображения агента. Краткое представление
и доступ к полному выводу принадлежат общему
[`tool-result`](tool-results.md#чтение-последнего-результата).
Полный файл читайте по общим правилам, включая
[диапазоны строк](project-file-reading.md#выборки-и-границы-содержимого).
Не повторяйте изменяющую операцию ради получения уже сохранённого ответа.

| Статус | CLI exit | Действие |
|---|---|---|
| `ready` | 0 | `status`, `rebuild` или `update` подтвердили состояние выбранной БД. |
| `complete` | 0 | Обновление и запрос завершились успешно. Читайте полный query stdout. |
| `disabled` | 0 | Явное отключение; внешний индексатор не запускался. |
| `rejected` | 2 | Исправьте конкретный запрос, binding, известную опцию или неразрешённый storage path. |
| `unavailable` | 1 | Проверьте выбранный executable, доступ к storage и интерпретируемое состояние БД; при её отсутствии выполните явный rebuild. |
| `busy` | 1 | Дождитесь реальной операции этой копии либо повторите после её завершения; lock-файл не удаляйте. |
| `failed` | 1 | Прочитайте полные captures, устраните nonzero/timeout/capture/update/query failure, затем явно повторите нужную операцию. |
| `inconclusive` | 1 | При смене HEAD повторите запрос после завершения изменения копии. |

При неверной БД не используйте данные другого worktree как результат текущего.
После смены `include` явно перестройте индекс. Подключение живых hooks, доступность
конкретного executable и языковые возможности внешнего индексатора подтверждаются
в выбранной установке отдельно. Специализированный
[IDE/AST provider proof](../workflows/code-navigation.md#конкретная-папка-и-подтверждение-индекса)
сохраняет собственный договор и не заменяется общей CLI-обёрткой.
