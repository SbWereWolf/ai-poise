# Предстартовая проверка Task и восстановление пилотной работы

Обновлено: **2026-10-03**. Процедура применяется до `ready` и первой записи в продукт, а при
ошибке постановки — к той же незавершённой Task. [Выбор способа
поставки](../governance/development-rules.md#прямое-исправление-без-task-выбор-и-поставка)
принадлежит каноническим правилам разработки. Этот текст не добавляет runtime-валидацию,
новый API, перемещение worktree или разрешение на публикацию.

## Выбор маршрута до первой записи

Зафиксировать пять разных фактов: источник запущенной установки Poise, authoritative managed
store, выбранный project, репозиторий продукта и конкретный Task worktree либо собственный
worktree прямого исправления. Стабильная установка `poise-op` может намеренно обслуживать другой
изменяемый checkout. Разные корни сами по себе не дефект; диагностировать следует неверную
**явную привязку** или доказанную несовместимость runtime/storage. Новые Task этой работы
создаются через `poise-op`. Рабочие конфигурации не переносить в Git и не подменять случайной
копией из target.

До работы выбрать маршрут и его условия:

| Маршрут | Что установить заранее | Как фиксировать результат |
|---|---|---|
| Task | Точный ID в выбранном проекте, требования, target repository, `goal_type`/process, разрешённые пути и gates приёмки/интеграции. | Публичные `task/edit` → `task/ready` → `bootstrap`/stage `verify`/handoff. После завершения и отдельного разрешения — публичный `integrate`. |
| Прямое исправление без Task | Прямое поручение, собственные ветка/worktree, локальная цель, независимый проверяющий, полномочие на ручную поставку и защита чужого WIP. | Git-кандидат, проверка точного commit, переносимая контрольная точка и отдельно разрешённый ручной локальный fast-forward. Poise Task status/receipts не создаются задним числом. |
| Диагностика без правки | Источник наблюдения и граница чтения. | Точный вывод и неопределённости; отсутствие Task не превращает наблюдение в продуктовый результат. |

[Реестр известных багов](../operations/known-bugs.md#ведение-реестра) допускает малую очевидную
правку без искусственной Task. Для кандидата из **47 изменённых путей** эта оговорка не
доказывает применимость исключения. Если работа уже начата без Task, сохранить кандидат и
установить действительное полномочие на ручную поставку. Не создавать Task ради вымышленного
прошлого исполнения и не объявлять Task-only `integrate` сломанным из-за отсутствия Task ID.

## Инвентаризация договора до ready

Выбранный template — материализованная заготовка. До `ready` планировщик может изменить
собственный draft, включая process, этапы, handlers, пути, методы и доказательства. `ready`
замораживает **разрешённый итоговый договор**; runtime применяет его, а не начальный template.
Публичные формы `edit`/`ready`/`restart` описаны в [планировании Task](task-planning.md#исполнимый-контракт).
Будущий output может ещё не существовать: заранее указывают его producer stage и путь, но
не требуют будущий hash. Блокер формулируют для конкретного нарушенного инварианта либо
обязательного отсутствующего входа.

До `ready` составить таблицу для **каждого** предметного требования и условия DoD:

| Поле решения | Проверяемое содержание |
|---|---|
| Требование → результат | Пользовательский результат, его расположение, producer stage и независимый inspection stage. |
| Обычные записи | Все пути кода, тестов, документации, `.gitignore`, примеров и add/remove в `known-bugs`; соответствие task-owned `stage_contracts[].allowed_paths` и реальным route/handler gates. Не копировать старый whitelist по догадке. |
| Методы проверки | Existing inputs, future outputs с producer stage, exact runner/parser, RED/GREEN либо логический осмотр, полное requirement→check coverage. Отсутствующий будущий файл допустим только как заявленный future output. |
| Приёмочные файлы | Immutable artifact или ещё редактируемый при review/rework draft: классифицировать до первой регистрации и применять [lifecycle черновика](batch-work.md#редактируемые-приёмочные-черновики). |
| Доставка | Task-only public integration либо отдельно разрешённая ручная taskless поставка; target, полномочие, checkpoint, чужой WIP, запрет push. Кодовую поставку и установленный live rollout разделять при разных полномочиях/доказательствах. |

После `task/edit` выполнить существующий публичный `task/ready` на **разрешённом** договоре;
ошибку исправлять в том же newborn draft. Независимый проверяющий затем осматривает
семантическую полноту: все ли записи и inputs перечислены, покрывают ли проверки смысл
DoD, достижим ли результат по route. Структурная проверка graph/path/mutability не
доказывает фактическую полноту инвентаря. Оставшаяся автоматическая проверка
input/handler/write feasibility принадлежит отдельной работе `AIP-TASK-FEASIBILITY-001`;
эта процедура её не реализует. Неясный маршрут или полномочие останавливают продуктовую
запись до их разрешения.

## Остановка и восстановление без потери WIP

При чужом живом claim, чужом или неясном изменённом пути, неверной branch/worktree binding,
незавершённом внешнем эффекте либо неподтверждённой Git-цели остановить запись. Не отзывать
claim по догадке, не готовить результат в чужом checkout и не обходить gate новым caller ID.
До рискованного перехода сохранить принадлежащие работе commit/branch, точный WIP и
[локально проверенную переносимую контрольную точку](checkpoint-recovery.md#контрольная-точка-и-восстановление).
Уборка не решает судьбу уникальных commits и не заменяет решение о публикации.

Когда frozen Task contract делает DoD недостижимым или следующий DoR невыполнимым,
исполнитель сохраняет доказательство и согласует точный `restart` с независимым
проверяющим. Публичный `task/restart` той же незавершённой Task, затем `edit`/`ready`,
сохраняют ID, историю, Sprint membership, worktree, branch и WIP. `cancel` с terminal
cleanup не исправляет постановку. Для поля вне frozen restart policy проверяющий
явно предоставляет `authorization.revision_fields`; исполнитель не выдаёт себя за
проверяющего. Ошибку project/process configuration нельзя лечить правкой product
source либо называть дефектом Poise без доказательства соответствующей границы.

Если пользователь отдельно поручил миграцию сохранённой работы, каждый агент фиксирует
**только свои** авторизованные изменения в собственной ветке. Новые дочерние worktrees
создаются из этих commits; содержимое сверяется **до** удаления прежних ресурсов. Новые
Task создаются только при явном поручении с картой старых и новых ID; прежняя immutable
history не переписывается. Это предметная процедура, не полномочие строить общий
relocation service. `workspace-recover` остаётся защищённым; обход claim, новый launcher
и подмена identity здесь не предписаны.

Проверенный **taskless** кандидат `47222a7d80d9974539494142e694d66440a9db9b`
находился в ветке `codex/paired-stage-templates-20261003` собственного worktree
`/home/sbwerewolf/workdata/ai-poise/projects/ai-poise/worktrees/paired-stage-templates-20261003`.
Исходный HEAD целевой ветки `poise-stride-v2` был
`9b199c9c2c8551fc40b38cb6966aca31a0e797de`. Независимый проверяющий на
неизменном кандидате выполнил 125 узких проверок, шесть maintained smoke, проверку
ссылок и `git diff --check`. Ручной отчёт находится по пути
`/home/sbwerewolf/workdata/ai-poise/projects/ai-poise/.runtime/paired-stage-review-47222a7-20261003.md`;
он сначала фиксировал недоступность Task-only `integrate`; последующий раздел
содержит разъяснение пользователя и итог ручной поставки. Этот отчёт — не Poise
inspection-stage receipt. Исторический digest ранней версии отчёта из Task draft —
`2d30ab87b94fe33607de4a80bc87c6ed29343fac066e32499`, а текущие байты дают
`66ad04af2a3b2b43c8d845815455e3e6b1919f05c02cd5bdd2d9a9ce797b21d9`.
Текущий файл нельзя выдавать за неизменённую раннюю версию.

После **явного пользовательского разрешения** проверяющий заново сверил commit,
чистоту собственного worktree, исходный target HEAD, пустой staged index и четыре
чужих изменённых пути. Exact-candidate checkpoint был локально проверен прямо
перед поставкой; Task DB в нём была старым sealed snapshot, не свежим состоянием
живых Task. Новый content commit не создавался, поэтому узкие и smoke проверки
относились к тому же commit. Ручной локальный `git merge --ff-only` передвинул
`poise-stride-v2` на точный кандидат без push. После операции проверены target HEAD,
branch binding, SHA-256 четырёх чужих файлов и digest их совокупного binary diff
`c4eac1b14059ac31d0c4be62f8995e28886b6fdee7844641e69f7aa04befc489`.
Исходные branch/worktree сохранены. Это Git outcome, **не** принятие или завершение
Poise Task.

Новая авторизованная прямая правка повторяет порядок фактов, а не commit примера:

1. В собственном checkout зафиксировать кандидат и убедиться, что независимый review,
   узкие checks, smoke и проверка ссылок относятся к его точному commit. Локально
   проверить checkpoint и зафиксировать пределы полномочия.
2. В целевом checkout прочитать ветку/HEAD, индекс, незавершённые операции и
   tracked/untracked чужой WIP; зафиксировать содержимое, типы и режимы путей.
   Проверить, что fast-forward возможен и кандидат не перекрывает чужую работу.
   Не выполнять `stash`, `reset`, `restore`, `checkout`, `clean` или staging чужих файлов.
3. Только при явной цели и разрешении выполнить `git merge --ff-only <собственная-кандидатная-ветка>`.
   После операции сверить точный target HEAD и
   сохранённые факты чужого WIP. Не выполнять `git push`.

При сдвиге цели или конфликте не использовать основной checkout для ремонта.
Обновить собственное кандидатное дерево, разрешить конфликт там, получить новый
commit и заново проверить именно его; перед публикацией повторить чтение target.
При отказе fast-forward доказать неизменность основного checkout, прежде чем
назвать отказ безопасным. Отсутствие Task identity не разрешает вызывать
`integrate`, создавать фиктивные stages, переносить ручное review в Poise receipts
или автоматически принимать результат.
